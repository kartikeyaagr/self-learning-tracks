## The obvious path, and why it hurts
Users upload things: profile photos, documents, videos, backups. The obvious design is that the client sends the file to your **API server**, which checks the user is allowed, then forwards the bytes to **object storage** (S3, Google Cloud Storage, Azure Blob Storage; lesson 07.13 covers why large files belong there rather than in a database). For a 200 KB profile photo, that is fine. For videos and large files, it is wasteful in four ways.
- **You pay for the bandwidth twice.** Every byte crosses your servers' network once on the way in and once on the way out to storage. Your load balancers, NAT gateways and servers all carry it.
- **Slow clients tie up servers.** A 2 GB video from a phone on a 5 Mbps uplink takes nearly an hour. For that whole time the upload holds a connection, a thread or event-loop slot, memory buffers, and often a slot on the load balancer.
- **Limits and timeouts.** Load balancers, API gateways and serverless functions cap request size and duration (an API gateway may cap bodies at 10 MB and requests at 30 seconds; serverless functions often cap payloads at a few MB). Long uploads hit them and fail at the worst moment.
- **You scale the wrong thing.** API servers exist to run business logic. Adding servers just to shovel bytes is expensive, and a burst of uploads can starve the normal API traffic on the same fleet.

Object storage, by contrast, is built for exactly this job: it accepts enormous numbers of parallel uploads, from anywhere, at high throughput, and bills you for storage rather than for your servers' time. So the better design lets the client upload **directly** to object storage, while your API keeps control of **who** may upload **what**.

%%compare Proxying uploads through the API versus uploading directly to storage. The direct path keeps control in the API but takes the bytes off it.
[Through the API]
Client -(2 GB)-> API server -(2 GB)-> Object storage
- Bytes cross your network twice
- Server busy for the whole upload
- Hits gateway size and time limits
[*Direct to storage]
Client -(small request)-> API -(signed URL)-> Client -(2 GB)-> Object storage
+ API handles only metadata
+ Storage absorbs the bandwidth
+ Upload can be parallel and resumable
%%

! Example: what proxying costs at scale
! A video app receives 1 million uploads a day, averaging 50 MB: 50 TB a day. Averaged over the day that is about 4.6 Gbps, with peaks perhaps 3 times higher at about 14 Gbps. Proxied, your fleet carries 14 Gbps in and 14 Gbps out at peak.
! Now the connection time. Mobile uplinks average perhaps 4 Mbps, so a 50 MB upload takes about 100 seconds. At peak, about 35 uploads start per second, so by Little's law (concurrency = arrival rate × duration) about 3,500 uploads are in progress at any moment, each holding a connection and buffers on an API server.
! Direct: the API handles 35 small JSON requests per second to issue upload URLs and 35 completion events per second. A single small server could do it. The 14 Gbps and the 3,500 slow connections become the object store's problem, which is what it is designed and priced for.

## Presigned URLs
A **presigned URL** is a URL that grants **time-limited** permission to perform **one specific operation** on **one specific object**, to anyone who holds it, without that holder having any cloud credentials. Your backend creates it by **signing** a description of the request with its own credentials:
- the **bucket** and **object key** (the path of the object);
- the **HTTP method**: `PUT` to upload, `GET` to download;
- the **expiry**;
- optionally, **headers** that must be present with exact values, such as `Content-Type` or `Content-Length`, or a checksum.

The signature is an HMAC computed with a key derived from your secret access key, the date, the region and the service. No call to S3 is needed to create one: signing is pure computation on your server, taking microseconds. S3 recomputes the same HMAC when the request arrives and rejects it if anything was changed.

```
https://media-uploads.s3.eu-west-1.amazonaws.com/raw/9f1c2e.mp4
  ?X-Amz-Algorithm=AWS4-HMAC-SHA256
  &X-Amz-Credential=AKIA.../20261112/eu-west-1/s3/aws4_request
  &X-Amz-Date=20261112T101500Z
  &X-Amz-Expires=900
  &X-Amz-SignedHeaders=content-type;host
  &X-Amz-Signature=5f2a...c91e
```

%%seq Direct upload: the API checks permission and signs a URL; the bytes go straight from the client to object storage, and an event closes the loop.
Client > API : POST /uploads (name, size, type)
API > API : auth, quota, create record (pending)
API -> Client : presigned PUT URL, expires 15 min
Client > S3 : PUT bytes to presigned URL
S3 -> Client : 200 OK + ETag
S3 > Queue : event: object created
Queue > Worker : validate, scan, start processing
Worker > API : record status = uploaded
%%

### The rules that matter
- **Permissions come from the signer.** The URL carries the permissions of whoever created it. The signing identity must itself be allowed to do the operation (for example `s3:PutObject` on that bucket prefix). Give the signing service a narrow role that can only write to the upload prefix.
- **Expiry limits.** With Signature Version 4 a presigned URL can last at most **7 days** when signed with long-term IAM user keys. The console allows 1 minute to 12 hours. And it can never outlive the credentials used: a URL signed by a role session or EC2 instance role dies when those temporary credentials expire, which may be sooner than the expiry you asked for.
- **Expiry is checked when the request starts.** An upload or download in progress finishes even if it passes the expiry; a request started after expiry fails.
- **It is a bearer token.** Anyone who has the URL can use it until it expires. Keep expiries short (minutes for uploads), never log full presigned URLs, and send them only over HTTPS.
- **Extra restrictions.** Bucket policies can reject presigned requests whose signature is older than N minutes (the `s3:signatureAge` condition), or that come from outside certain IP ranges or VPC endpoints.
- **Integrity.** You can require a checksum header (SHA-256, CRC32C, CRC64NVME and others) as part of the signature, so S3 rejects an upload whose bytes do not match.
- **Unique keys.** A `PUT` to an existing key **replaces** the object. Generate the key on the server (a UUID or the record ID), never from the user's file name, or one user could overwrite another's file.

### Controlling size and type
A plain presigned `PUT` does not limit size unless you sign the `Content-Length` header. Two ways to enforce limits:
- **Sign the exact size and type**: the client declares them up front, your API checks they are acceptable, and the signature covers `Content-Length` and `Content-Type`, so the upload must match.
- **Presigned POST**: an HTML-form style upload with a signed **policy document** that can say, for example, `content-length-range` between 1 byte and 50 MB, and key must start with `raw/u42/`. S3 enforces each condition.

Even then, never **trust** the declared type: a file named `cat.jpg` with `Content-Type: image/jpeg` may be anything. Check the real content after upload (lesson 13.02 covers image validation).

### Browser uploads need CORS
If a web page uploads directly to the bucket, the browser makes a cross-origin request. The bucket must have a **CORS** (cross-origin resource sharing) rule allowing `PUT` from your site's origin and exposing the `ETag` header, or the browser blocks the request. This is the most common reason a first direct-upload implementation "works in curl but not in the browser".

## Keeping the database in step
Once bytes bypass your servers, your **database** (which holds the file's metadata: owner, name, size, status) and the **bucket** (which holds the bytes) can disagree. The client could get a URL and never upload; it could upload and never tell you; it could upload something different from what it declared. The standard pattern makes the database the record of intent and lets storage events confirm it.
1. Create the metadata record **first**, with status `pending` and the object key you chose.
2. The client uploads with the presigned URL.
3. Object storage emits an **event notification** (S3 can send to a queue, a topic or a function) when the object is created. A handler checks the object exists with the expected size and type, then marks the record `uploaded` and starts processing (thumbnails, virus scan, transcoding).
4. A **reconciliation job** handles the leftovers: `pending` records older than the URL expiry plus a margin are marked `expired`, and a **lifecycle rule** deletes objects in the upload prefix that never got a matching record.

Do not rely only on the client calling "I'm done": phones lose connectivity right after finishing, and malicious clients lie. The storage event is the trustworthy signal. Many apps still accept a client "complete" call as a fast path, and let the event confirm it.

%%state The lifecycle of an upload record. The API creates it; storage events and background jobs move it forward or clean it up.
[*] -> Pending
Pending -> Uploaded : object-created event, size matches
Pending -> Expired : no object after URL expiry
Uploaded -> Processing : scan and transcode start
Uploaded -> Rejected : wrong type or malware
Processing -> *Ready : all variants done
Processing -> Failed : processing error, retry or alert
%%

### Quarantine first
A good habit is to upload into a **quarantine prefix** (say `raw/`) that nothing serves to users. Only after validation and scanning does the worker write processed outputs to a public or CDN-served prefix (`media/`). That way, a malicious file never reaches other users even briefly.

## Downloads use the same idea
Downloads of private files work the same way in reverse: your API checks permission and returns a presigned `GET` URL (or redirects to one), and the client downloads straight from storage. Better still, serve through a **CDN with its own signed URLs or cookies** (lesson 13.07), so popular files come from edge caches near users and the bucket is not hit for every request.

! Example: a 1 GB video upload, step by step
! 1. The app calls `POST /videos` with `{size: 1 GB, type: video/mp4}`. The API checks the user is logged in and has 1 GB of quota left.
! 2. It inserts `{id: v77, key: raw/9f1c.mp4, status: pending}` and returns a presigned URL. For a file this large it actually starts a **multipart upload** and returns one presigned URL per 16 MB part, 64 in total, valid for 30 minutes (lesson 13.04).
! 3. The phone uploads parts straight to S3, four at a time. The API servers never touch the gigabyte.
! 4. When the upload completes, S3 emits an object-created event. A worker confirms the size is 1 GB, checks the file really is an MP4 container, marks v77 `uploaded` and starts the transcoding pipeline (lesson 13.05).
! 5. If the user had closed the app at 30% and never come back, the reconciliation job would mark v77 `expired` the next hour, and the lifecycle rule would abort the incomplete multipart upload after a day so its parts stop costing money.

## Common mistakes
- **User-controlled object keys.** Letting the client pick `uploads/report.pdf` invites overwrites and path tricks. Generate keys on the server.
- **Long expiries.** A presigned URL valid for 7 days, pasted into a chat, is a 7-day public link.
- **No size limit.** Without a signed length or a POST policy, a client can upload 5 GB where you expected 5 MB, and you pay to store it.
- **Trusting the client's "done".** The record says uploaded; the object is not there. Use storage events.
- **Serving straight from the upload bucket.** Unvalidated files become reachable by others. Quarantine, validate, then publish.
- **Forgetting CORS** for browser uploads.

## In an interview
When a design involves user uploads larger than a few megabytes, say early that bytes go **directly to object storage with presigned URLs**, and that the API only authorises and records metadata. Then cover the follow-ups interviewers expect: how the database learns the upload finished (storage events plus reconciliation), how you limit size and type, how you handle large files (multipart, lesson 13.04), and how downloads are served (CDN with signed URLs). That shows you understand both the data path and the control path.

> Takeaway: let clients upload and download large files directly to object storage using short-lived presigned URLs that your backend signs after checking permissions; the API handles only metadata, so bandwidth and slow connections never touch your servers. Create a pending record first, let an object-created event confirm the upload, and clean up with reconciliation and lifecycle rules. Treat presigned URLs as bearer tokens: short expiry, server-generated keys, signed size and checksums, and a quarantine prefix until the content is validated.

## What a CDN does
A **content delivery network** (CDN) is a geographically distributed group of servers that **caches content close to end users**. Instead of every browser in Paris, Tokyo and São Paulo fetching an image from your servers in Virginia, each fetches it from a nearby CDN server that already has a copy. CDNs deliver HTML, JavaScript, stylesheets, images and video, and they bring four benefits:
- **Lower latency.** Content is served from a nearby **point of presence** (PoP), a data centre the CDN runs in or near a city, often at an **internet exchange point** where many networks interconnect. A round trip from Paris to Virginia is about 80 ms; to a Paris PoP, a few milliseconds. For an image that needs several round trips (TCP and TLS handshakes, then the request), the saving is hundreds of milliseconds.
- **Lower bandwidth costs.** Cached responses never reach your origin, so you pay for much less origin egress.
- **Availability.** The CDN absorbs traffic spikes and can keep serving cached content when your origin is slow or down.
- **Security.** TLS terminates at the edge, and large CDNs absorb DDoS attacks that would flatten a single origin.

A CDN **does not host** your content: it caches it. You still need an **origin**, the authoritative source it fetches from on a miss: an object storage bucket, a web server, or (for images) an image-processing service.

## How the tiers fit together
A request for an image passes through several caches, each larger and further away than the last.

%%layers The caching tiers an image request passes through, from nearest and smallest to furthest and authoritative.
Browser cache | on the device, reused across pages, controlled by Cache-Control
*Edge PoP | hundreds of cities, milliseconds away, most hits happen here
Origin shield | one regional cache in front of the origin, collapses misses from all PoPs
Image service | resizes and encodes on a miss, for example imgproxy on libvips
Object storage | the uploaded originals, the source of truth
%%

The **origin shield** (also called a tier-2 or mid-tier cache) deserves a note. Without it, a new image requested in 300 PoPs causes 300 separate misses to your origin. With it, all PoPs miss to the shield, and the shield misses to the origin once. For an image service that does expensive work per miss, a shield can cut origin load by one or two orders of magnitude.

Cache behaviour is controlled by HTTP headers. `Cache-Control: public, max-age=31536000, immutable` tells browsers and CDNs to keep a response for a year and never revalidate it, which is right for any URL whose content never changes. The CDN's **cache key** is normally the URL (plus any headers listed in `Vary`); two URLs that differ in any way are two cache entries.

## Images need many variants
A single uploaded photo is displayed in many places: a 64-pixel avatar, a 320-pixel feed thumbnail, a 1080-pixel phone view, a 2× version for high-density ("retina") screens, and in modern formats such as **WebP** or **AVIF** for browsers that support them, because they are 25% to 50% smaller than JPEG at similar quality. Serving the 8 MB original everywhere would waste bandwidth and make pages slow.

%%bars Bytes for one product photo in different variants. Serving the original to a phone is about 90 times more data than the right variant.
Original JPEG 6000 x 4000 | 8000 | 8 MB
1600 px JPEG | 420 | 420 KB
800 px JPEG | 150 | 150 KB
800 px WebP | 105 | 105 KB
*800 px AVIF | 90 | 90 KB
320 px WebP | 22 | 22 KB
%%

So you need variants. The design question is **when** to make them.

## Option 1: resize on upload
An upload pipeline (triggered by the object-created event from lesson 13.01) generates a fixed set of sizes and formats as soon as the image arrives, and stores them all in object storage. Serving is then trivial: each variant is a static file the CDN caches.
- **Reads are simple and fast.** No work at request time, no first-view delay.
- **Failures are visible early.** A corrupt image fails in the pipeline, not in front of a user.
- **You must know the sizes in advance.** A redesign that needs a 480-pixel version means **reprocessing every image ever uploaded**: a backfill job over perhaps billions of objects.
- **Storage multiplies.** Five sizes in three formats is 15 files per image, including variants nobody ever requests. Most photos on most platforms are viewed rarely, so most of that storage and compute is wasted.

## Option 2: resize on request
An **image server** generates a variant the first time it is requested, and the CDN caches the result. The URL itself describes the variant. **imgproxy** is a typical example: a standalone HTTP server that receives a source image location and processing options **in the URL** (resize, crop, rotate, quality, watermark, output format), fetches the original, processes it with the **libvips** library (fast and memory-efficient because it streams the image in small regions instead of decoding it all at once), and returns the result.

`https://img.example.com/<signature>/rs:fit:800:0/q:75/f:avif/plain/s3://products/p91.jpg`

Three practices make this safe in production.
- **Put it behind a CDN.** The image server is meant to sit behind a CDN or caching proxy, so each variant is generated once per cache and then served from cache. On its own, it would redo the work on every request.
- **Sign the URLs.** Without a signature, anyone could ask your server to resize arbitrary images or generate millions of random sizes, burning your CPU and filling your cache (a denial-of-service attack). The URL includes an HMAC of the options and source, computed by your application with a secret key; the server rejects anything unsigned. Header-based authorisation can additionally stop clients from bypassing the CDN.
- **Defend against image bombs.** An **image bomb** (decompression bomb) is a tiny file that decodes into an enormous image, say a 50 KB PNG declaring 50,000 × 50,000 pixels, which would need 10 GB of memory. The server checks the real image type and dimensions from the header **before** fully downloading and decoding, and rejects anything over a pixel limit. It can also restrict allowed sources, sizes and options.

%%seq Resize on request: the first request for a variant is processed once and cached; later requests are pure edge hits.
Browser > CDN edge : GET /sig/rs:fit:800/f:avif/p91.jpg
CDN edge > Origin shield : miss, forward
Origin shield > Image service : miss, forward
Image service > Object storage : GET original p91.jpg (8 MB)
Object storage -> Image service : original bytes
Image service > Image service : check size, decode, resize, encode AVIF
Image service -> Origin shield : 90 KB, max-age 1 year
Origin shield -> CDN edge : cached at shield
CDN edge -> Browser : cached at edge, about 400 ms first time
%%

## Comparing the two
| | Resize on upload | Resize on request |
| New sizes or formats | Reprocess every image | Just use a new URL |
| Storage | All variants for all images | Originals plus cached hot variants |
| First-view latency | None | One-time processing delay per variant per cache |
| Compute | Paid for every image, viewed or not | Paid only for variants actually requested |
| Main risk | Pipeline backlog after a big upload burst | Abuse through arbitrary sizes, cold-cache storms |

%%compare When variants are made. Most production systems combine the two: pre-generate the common sizes, generate the rest on demand.
[Resize on upload]
Upload -> Pipeline makes 15 variants -> Storage -> CDN
+ No request-time work
+ Errors caught at upload
- Redesign means a full backfill
- Stores variants nobody views
[*Resize on request]
Request -> CDN miss -> Image service -> CDN cache
+ Any size or format via the URL
+ Compute follows real demand
- First view of a variant is slower
- Needs signed URLs and size limits
%%

Common practice combines them: generate the one or two sizes you know are always needed (a thumbnail and a standard view) at upload, so the first view of a new image is fast and broken uploads are caught early, and serve everything else on demand, from a **limited set of allowed sizes** (for example 160, 320, 640, 960, 1280, 1920), behind a CDN with long cache lifetimes. Rounding requested sizes up to the nearest allowed width keeps the number of variants, and therefore cache misses, small.

! Example: a product photo
! A seller uploads a 6000 × 4000 JPEG (8 MB) to object storage. The product page asks for `/img/<sig>/rs:fit:800/f:avif/products/p91.jpg`.
! The CDN edge misses, the shield misses, and imgproxy fetches the original (about 80 ms from storage in the same region), decodes and resizes it (about 150 ms on libvips) and encodes AVIF (about 100 ms; AVIF encoding is slow). It returns 90 KB with `Cache-Control: public, max-age=31536000, immutable`. The first viewer waits roughly 400 ms longer than a cache hit.
! The next million views come from CDN edges in a few milliseconds each. When the design changes to 960 pixels, the page simply starts requesting `rs:fit:960`, and those variants are generated as they are requested. No backfill job.

## Format negotiation without fragmenting the cache
Browsers advertise supported formats in the `Accept` request header (`image/avif,image/webp,*/*`). Two approaches:
- **Put the format in the URL**, chosen by your HTML (the `<picture>` element lets the browser pick from AVIF, WebP and JPEG sources). Each URL is a clean cache entry.
- **Negotiate on the server** with `Vary: Accept`. This is convenient but dangerous: raw `Accept` strings differ between browser versions, so the cache can fill with near-duplicate entries. CDNs that support it normalise `Accept` into a few buckets (AVIF, WebP, other) before using it in the cache key.

## Cache arithmetic and cold starts
Resize on request shifts cost to the first request of each variant, **per cache**. With an origin shield, that is roughly once per variant overall; without one, once per variant per PoP.

! Example: a cold-cache storm
! A marketplace launches a redesign that uses a new 960-pixel size. 2 million product images are viewed in the first hour, across 200 PoPs.
! Without a shield: each image is first requested in, say, 30 different PoPs during that hour, so the image service sees about 60 million resize requests. At 300 ms of CPU each, that is 5,000 CPU-hours in one hour: about 5,000 cores. The service falls over and images break site-wide.
! With a shield: about 2 million resize requests (one per image), 170 CPU-hours, so about 170 cores for that hour, and much less after as the cache warms. Better still, pre-warm the most viewed 100,000 products before launch by requesting their new URLs from a script.

## Pitfalls
- **Unsigned or unlimited URLs.** Anyone can make your image service do arbitrary work. Sign URLs and allow only a fixed set of sizes.
- **Short cache lifetimes.** Variants of an immutable original never change; cache them for a year. If the original can change, put a version in the URL (lesson 13.03) instead of shortening the lifetime.
- **No origin shield.** Every PoP's first miss hits your image service.
- **Decoding untrusted images naively.** Without dimension checks, one image bomb can exhaust memory on every worker that touches it.
- **Upscaling.** Requests for 1920 pixels from a 640-pixel original should return the original size, not an enlarged blurry copy that wastes bytes.
- **Stripping nothing.** Originals from phones carry EXIF metadata, including GPS coordinates. Strip metadata from public variants for privacy.

## In an interview
Draw the tiers: browser, CDN edge, shield, image service, object storage. Explain both options, and recommend the hybrid: a couple of standard sizes on upload, everything else on request from an allowed list, with signed URLs and long-lived immutable caching. Mention image bombs and the cold-start storm, and how the shield and pre-warming handle it. That covers latency, cost, flexibility and abuse, which is what the question is testing.

> Takeaway: a CDN caches content at edges near users, cutting latency and origin load, but needs an origin behind it, ideally protected by an origin shield. Resizing on upload gives predictable, pre-made variants but is rigid and stores everything; resizing on request (an image service such as imgproxy behind a CDN, with signed URLs, allowed sizes and image-bomb checks) is flexible and pays only for variants actually used, at the cost of a one-time delay per variant. Most systems pre-generate the common sizes and serve the rest on demand.

## The problem an avatar service solves
Almost every product shows small pictures of people: next to comments, in chat lists, on profile pages, in email clients. An **avatar service** stores those images and serves them. It looks trivial, but it has an unusual load profile: avatars are **tiny** (a few kilobytes), **extremely numerous** (one per user, in several sizes), **read constantly** (a comment thread with 200 comments shows 200 avatars) and **changed rarely** (most people change their picture a few times in their life). That profile makes it almost entirely a **caching** problem.

This lesson looks at how Gravatar, a public avatar service, lets any website show a user's picture knowing only their email address, then at how to cache avatars well, and finally at designing your own.

## How Gravatar works
Gravatar ("globally recognised avatar") lets a user upload a picture once, linked to their email address, and have it appear on any site that supports it. The site never calls an API to find the avatar. It **builds the URL itself**:
1. Take the user's email address and **normalise** it: trim leading and trailing spaces and convert it to lower case. `  Alice@Example.com ` becomes `alice@example.com`. Without normalisation, the same person would get different hashes on different sites.
2. Compute its **SHA-256 hash** (older integrations used MD5, which is still accepted). The result is 64 hexadecimal characters.
3. Request `https://gravatar.com/avatar/HASH`, adding query parameters for size and fallback behaviour.

The hash identifies the account without putting the email address itself into page HTML, where it could be scraped. Gravatar keeps a map from hash to account and serves the account's image.

%%flow Building a Gravatar URL needs no lookup call: the key is derived from data the site already has.
Alice@Example.com -(trim, lowercase)-> alice@example.com -(SHA-256)-> *Hash 3f2a... -(add s=96, d=identicon)-> Avatar URL
%%

### The parameters
- `s` (size): one number, since avatars are square; **1 to 2048** pixels, default **80**. The service resizes the stored image to that size.
- `d` (default): what to return if the hash has no avatar. `404` returns an HTTP 404 so the site can handle it; `mp` ("mystery person") returns a generic grey silhouette; `identicon` (a geometric pattern), `monsterid`, `wavatar`, `retro` (8-bit style) and `robohash` return generated images unique to the hash; `blank` returns a transparent image; `initials` draws letters from the user's name; or you can pass a custom image URL of your own.
- `f=y`: force the default image even if an avatar exists (useful for testing).
- `r` (rating): `g` (default, suitable for all audiences), `pg`, `r` or `x`. Users rate their own image; if it is rated above what the site asks for, the default is returned instead.

%%seq One Gravatar request. The default is resolved on the server, so the browser always receives an image.
Browser > CDN edge : GET /avatar/3f2a...?s=96&d=identicon
CDN edge > Gravatar origin : miss, forward
Gravatar origin > Gravatar origin : look up hash, check rating
Gravatar origin > Gravatar origin : no avatar, generate identicon from hash
Gravatar origin -> CDN edge : 96 x 96 PNG, cache for minutes
CDN edge -> Browser : image
Browser > CDN edge : same URL on next page
CDN edge -> Browser : cache hit
%%

### The design ideas worth stealing
Two ideas stand out, and both apply well beyond avatars.
- **Derived keys.** The lookup key is computed from data the caller already has, so there is no extra round trip to ask "what is this user's avatar ID?". Any page can render avatar tags immediately.
- **Server-side defaults.** The fallback is resolved on the server. The client always gets an image, so there is no broken-image icon and no client logic for "user has no avatar". A generated identicon is also **deterministic**: the same hash always gives the same pattern, so it is cacheable like a real image and users stay visually distinguishable.

### A privacy weakness
A hash hides the address only from someone who does not already have a list of candidate addresses. Anyone with a list of email addresses (from a leak, or from guessing common patterns like `firstname.lastname@gmail.com`) can hash them all and match the hashes they see on a site, linking accounts across sites. Hashes of email addresses have been reversed in bulk this way. If you design your own service, use a **random, application-generated ID** in avatar URLs instead of anything derived from personal data.

## Caching avatars
### Fixed URL or versioned URL?
This is the central design decision.

A **fixed URL**, like `/avatar/HASH?s=96`, always refers to "this user's current avatar". When the user changes their picture, the content behind the URL changes. Caches must therefore **expire** the old one: you set a `max-age` of minutes to an hour and accept that the new picture takes that long to appear everywhere, or you **purge** the URL from the CDN when it changes (purges take seconds to propagate and cannot reach browser caches).

A **versioned URL**, like `/avatars/u42/v7-96.jpg`, refers to one specific image that never changes. The user's profile record stores the current version (`avatar_version = 7`). When the user uploads a new picture, the app writes v8 and updates the profile. Pages rendered after that reference v8. Since v7's content never changes, it can be cached **forever**: `Cache-Control: public, max-age=31536000, immutable`. Nothing needs purging, because nobody asks for v7 any more and it ages out of caches on its own.

### Other caching rules
- **Put a CDN in front.** Avatars are the ideal CDN workload: small, numerous, read constantly, identical for every viewer.
- **Limit the sizes.** Support a handful (32, 64, 128, 256, perhaps 512 for profile pages) and round requests up to the nearest. Allowing all 2,048 sizes would fragment the cache into thousands of variants per user, each with a cold first request.
- **Normalise the URL.** Fixed parameter order, lower-case hash, no unused parameters, so equivalent requests share one cache entry. `?s=96&d=mp` and `?d=mp&s=96` are different cache keys unless the CDN normalises them.
- **Negative caching.** "No avatar" (a 404 or a generated default) should also be cached, briefly (say 10 minutes), so pages full of users without pictures do not hammer the origin with the same lookup.
- **Application-side caching.** Store the avatar URL (or the version) on the user object your app already loads. A comments API should return each author's avatar URL alongside their name; it should not make a call to the avatar service per comment.
- **Use `srcset`.** Let the browser choose 1× or 2× density: `<img src=".../v7-48.jpg" srcset=".../v7-96.jpg 2x">`.

! Example: a comment thread with 200 comments
! The page includes 200 `<img>` tags. The comments API already returned each author's avatar URL (versioned), so rendering needs no extra lookups. Many commenters repeat, so there are only 60 distinct avatars.
! The browser requests 60 images. Twenty are already in its own cache from earlier visits. The other 40 come from the CDN edge, nearly all hits because popular commenters' avatars are requested by thousands of readers. The origin might see one or two requests. Each avatar at 48 × 48 is about 2 to 4 KB in WebP, so the whole set is under 200 KB.
! When Bob changes his picture, his profile switches from v3 to v4. New pages reference v4; the first request for v4 at each edge misses once and is cached for a year. Old v3 copies age out unused. No purge was needed.

## Designing your own avatar service
Putting the pieces from this module together:
- **Upload.** The client gets a presigned URL and uploads the original directly to object storage (lesson 13.01). Limit the size (say 10 MB) and accept only image types.
- **Processing.** An object-created event triggers a worker that validates the image (real type, dimensions, no image bomb), crops it to a square (centred, or using a face-detection crop), strips EXIF metadata, and generates the standard sizes in WebP and JPEG (lesson 13.02). Writing a handful of fixed sizes at upload is the right choice here: the set of sizes is small and stable, and every avatar is viewed.
- **Moderation.** Optionally run the image through an automated classifier before publishing, since avatars appear next to everything a user does.
- **Publish.** Write the variants under `avatars/<user_id>/<version>-<size>.webp`, then update `avatar_version` in the user record. The order matters: write files first, then flip the pointer, so no page ever references a version that does not exist yet.
- **Serving.** A CDN in front of the bucket, with year-long immutable caching. URLs use the user ID (or a random avatar ID), not the email.
- **Defaults.** If a user has no avatar, render initials or an identicon generated from the user ID, either on the client (an SVG) or by a small service whose output is cached like any other image.
- **Deletion.** When a user deletes their account or picture, update the record immediately (new pages stop showing it) and delete the objects. For privacy-sensitive deletions, also purge the CDN so cached copies vanish within minutes rather than ageing out.

! Example: sizing the service
! 100 million users, 60% with a custom avatar: 60 million originals at about 1 MB each is 60 TB, plus 5 sizes in 2 formats at an average of 10 KB each, about 6 TB more.
! Read load: 2 million page views per minute, each showing 20 avatars, is about 670,000 avatar requests per second. With a 99% CDN hit rate (realistic for year-long immutable URLs), the origin sees about 6,700 requests per second, all simple object reads from storage. Writes: perhaps 50,000 avatar changes a day, under 1 per second. Processing them needs a couple of small workers.

## Pitfalls
- **Fixed URLs with long cache lifetimes.** Users change their picture and see the old one for a day. Version the URL.
- **Arbitrary sizes.** Cache fragmentation and an easy abuse vector. Allow a fixed set.
- **Email hashes in URLs.** Reversible with a dictionary of addresses; use random IDs.
- **Per-item lookups.** Calling the avatar service once per comment turns one page into 200 backend calls. Return URLs with the data.
- **Flipping the pointer before the files exist.** Users briefly see broken images.

## Why one big upload fails
Lesson 13.01 moved uploads off your servers with presigned URLs. For a photo, a single presigned `PUT` is enough. For a **5 GB video** from a phone, a single HTTP request is fragile, slow and sometimes impossible.
- **All or nothing.** A single request either completes or fails. A network blip at 80% (the train enters a tunnel, Wi-Fi hands over to 4G, the app is backgrounded and the OS kills its socket) loses all 4 GB sent so far, and the next attempt starts from zero. On a 10 Mbps uplink, 4 GB is nearly an hour of wasted transfer.
- **One connection is slow.** A single TCP connection's throughput is limited by its congestion window and the round-trip time. Over a long-distance path it may reach only a fraction of the available bandwidth. Several connections in parallel fill the pipe much better.
- **Hard limits.** S3 accepts at most **5 GB in a single PUT**. Larger objects must be uploaded in parts.
- **Unknown length.** A single PUT needs the total size up front. A live recording or a file being generated on the fly does not have one yet.

The fix, in S3 and in every major object store, is to split the upload into independently uploaded pieces.

## Multipart upload
**Multipart upload** sends one object as a set of independently uploaded **parts**, in any order and in parallel, which the store assembles into a single object when you finish. S3 recommends it for objects of **100 MB or more** and requires it above 5 GB. It has three steps.
1. **Initiate** with `CreateMultipartUpload`. S3 returns an **upload ID**, a handle used in every later call.
2. **Upload parts** with `UploadPart`. Each part has a **part number from 1 to 10,000** chosen by you, and S3 returns an **ETag** (an identifier for that part's content, in practice derived from its MD5) for each. Uploading the same part number again simply **overwrites** that part, which makes retries safe.
3. **Complete** with `CompleteMultipartUpload`, sending the upload ID and the list of part numbers with their ETags. S3 concatenates the parts **in part-number order** and creates the object atomically: before this call, no object exists at the key; after it, the whole object does.

At any time you can **abort** with `AbortMultipartUpload`, which discards the uploaded parts.

### The limits
| Limit | Value |
| Part size | 5 MiB to 5 GiB (the last part may be smaller) |
| Number of parts | 1 to 10,000 |
| Object size | up to 5 TiB |
| Single PUT without multipart | up to 5 GB |
| Parts listed per ListParts call | up to 1,000 |

Part numbers do not need to be consecutive (you could use 1, 5 and 9), and parts can be uploaded in any order; only the numbers in the completion request decide the final order.

## Doing it directly from the client
Combining this with lesson 13.01, the client uploads parts **straight to storage** with presigned URLs, while your API keeps control of the upload. Each `UploadPart` request is signed for a specific upload ID and part number, so a client can only upload the parts you authorised.

%%seq Multipart with presigned parts: the API starts the upload and signs one URL per part; the client uploads parts in parallel and the API completes it.
Client > API : start upload (name, 5 GB)
API > S3 : CreateMultipartUpload
S3 -> API : uploadId
API -> Client : uploadId + presigned URLs for parts 1 to 500
Client > S3 : PUT parts 1..500, 4 at a time
S3 -> Client : ETag for each part
Client > API : complete(uploadId, part numbers + ETags)
API > S3 : CompleteMultipartUpload
S3 -> API : object created
API -> Client : upload done
%%

For very many parts, the API can hand out presigned URLs in batches (say 50 at a time) rather than all 500 up front, so that URLs do not expire before the client reaches them and so that the server sees progress.

## The benefits
- **Throughput.** Upload parts **in parallel** over several connections. On a long-distance link where one connection reaches 50 Mbps, eight connections may reach 300 to 400 Mbps.
- **Quick recovery from network issues.** A failed part is retried on its own; parts already acknowledged are unaffected. The most you lose to a failure is the parts in flight.
- **Pause and resume.** An initiated multipart upload **does not expire**: it stays until you complete or abort it. The client can stop for an hour, or a day, and continue.
- **Start before you know the final size.** Upload parts as the file is being produced (a recording, a database dump being streamed), then complete when it ends.

%%bars Wall-clock time to upload 5 GB on a link that one connection can only drive at 50 Mbps, as parallel part uploads increase.
1 connection | 800 | about 13 min
2 parallel parts | 400 | about 7 min
4 parallel parts | 200 | about 3.5 min
*8 parallel parts | 110 | about 2 min, link nearly full
%%

## Resuming at 80%
Here is the scenario from the question, worked through. With **10 MB parts**, a 5 GB file has **500 parts**. At 80%, about **400 parts** have been uploaded and acknowledged with ETags; a few more were in flight when the network dropped.
1. **Remember what is done.** The client (or the server, which tracked progress) knows the upload ID and the part numbers and ETags of every completed part.
2. **Reconnect and continue the same upload.** Because the upload has not expired, the client asks the API for fresh presigned URLs (the old ones may have expired) for the remaining parts, **401 to 500**, plus any earlier part whose upload never returned an ETag.
3. **Upload only those parts.** About 1 GB is sent, not 5 GB.
4. **Complete** with all 500 part numbers and ETags.

%%timeline A 5 GB upload in 10 MB parts that fails at 80% and resumes. Only the missing parts are re-sent.

10:00 to 10:27 | Parts 1 to 400 uploaded, ETags saved on the device
10:27 | *Network drops, parts 401 to 404 were in flight

%%

### Where the progress is recorded
The client should **record part numbers and ETags itself**, persistently (on disk, not just in memory, so it survives the app being killed). The server can also keep track, for example by storing per-part status in the file's metadata record as parts are reported, so another device or a support tool can see progress.

S3's `ListParts` call returns the parts it has received for an upload. Use it to **verify** before completing (for example after a crash, to check which parts really arrived), but not as the only source for building the completion request: the client knows which ETags it expects, and comparing the two catches parts that were overwritten or corrupted.

! Example: the resume in numbers
! 5 GB file, 10 MB parts, 500 parts. Uplink 20 Mbps (2.5 MB/s), 4 parts in parallel. Each part takes about 16 seconds on its share of the link, and the whole upload would take about 34 minutes.
! At 80% (about 27 minutes in), the connection drops with 4 parts in flight. Lost work: at most 4 partial parts, 40 MB. On resume, the client uploads 100 parts (1 GB), taking about 7 minutes.
! Without multipart, the failure would have cost 27 minutes of transfer and 4 GB of mobile data, and the retry would need the full 34 minutes again, with the same chance of failing.

## Choosing a part size
Part size is a trade-off.
- **Larger parts** mean fewer requests (less per-request overhead and fewer presigned URLs to manage), but more data re-sent per failure and coarser progress.
- **Smaller parts** mean cheap retries and smooth progress, but more requests and a lower maximum object size (10,000 parts × part size).

A good rule: size parts so each takes a few seconds to tens of seconds on the expected network, and make sure 10,000 parts covers the largest file you accept. Ranges of **8 to 64 MiB** are common.

! Example: picking a part size
! A 5 GB file in 5 MiB parts is about 1,000 parts: fine. A 200 GiB file in 5 MiB parts would need about 41,000 parts, over the 10,000 limit, so it needs parts of at least about 21 MiB; in practice 32 MiB, giving about 6,400 parts.
! On a phone uploading at 4 Mbps, a 32 MiB part takes over a minute, so a dropped connection loses a lot. For mobile clients and files up to a few GB, 8 MiB parts (about 16 seconds each at 4 Mbps) are a better fit. Some clients choose the part size from the file size: max(8 MiB, file size ÷ 9,000).

## The upload as a state machine
It helps to see the multipart upload, as your system tracks it, as a lifecycle.

%%state A multipart upload as the application tracks it. Abandoned uploads must be aborted, because their parts are billed.
[*] -> Initiated
Initiated -> Uploading : first part acknowledged
Uploading -> Paused : network lost or app closed
Paused -> Uploading : resume with fresh URLs
Uploading -> Completing : all ETags collected
Completing -> *Complete : CompleteMultipartUpload succeeds
Paused -> Aborted : abandoned for 7 days, lifecycle rule
Completing -> Uploading : a part is missing or bad, re-send it
%%

## Cleaning up and integrity
- **Incomplete uploads cost money.** S3 stores and bills for uploaded parts until the upload is completed or aborted, and these parts are invisible in normal object listings. A busy app can quietly accumulate terabytes of abandoned parts. Abort abandoned uploads in your reconciliation job, and add a bucket **lifecycle rule** with `AbortIncompleteMultipartUpload` after N days (say 7) as a safety net.
- **Checksums.** SDKs send a checksum with each part (CRC32, CRC32C, SHA-1, SHA-256 or CRC64NVME), and S3 rejects a part whose bytes do not match (`BadDigest`). **Full-object** checksums (such as CRC64NVME) cover the whole object; **composite** checksums are a checksum of the per-part checksums. With full-object checksums, part numbers must be consecutive starting at 1.
- **The final ETag is not the file's MD5.** For a multipart object it is the MD5 of the concatenated part MD5s followed by a dash and the part count, such as `"9b2cf535...-500"`. Do not compare it with a locally computed MD5 of the file; use the checksums above.
- **Concurrent uploads to one key.** Two multipart uploads to the same key can both complete, and the last one wins. If overwriting must be prevented, use a conditional write (`If-None-Match: *`) on completion, or give every upload a unique key.

## Other resumable protocols
The same idea appears elsewhere with different shapes:
- **Google Cloud Storage resumable uploads** use one session URL; the client sends chunks sequentially and, after a failure, asks the server how many bytes it has, then continues from that offset.
- **tus** is an open protocol for resumable HTTP uploads with the same offset-based design, used by several upload libraries and video platforms.

Offset-based protocols are simpler (no ETag list) but sequential; S3-style parts allow parallelism.

## Common mistakes
- **Keeping progress only in memory.** The app is killed, the upload ID and ETags are gone, and the next attempt starts a new upload while the old parts sit there being billed.
- **No lifecycle rule.** Abandoned parts accumulate forever.
- **Parts too small for the largest file.** 5 MiB parts cap uploads at about 48 GiB.
- **Presigning all parts with a short expiry.** The later URLs expire before the client reaches them. Issue them in batches or with expiries that match the expected upload time.
- **Comparing the multipart ETag with an MD5.** It never matches.

Add the operational points that show experience: lifecycle rules for incomplete uploads, choosing part size against the 10,000-part limit, and checksums.

## What the pipeline is for
An uploaded video arrives as **one large file in one format**: a camera's high-bitrate H.264, a studio's ProRes master, a phone's HEVC recording. Viewers cannot use it as it is. A phone on 4G cannot stream a 50 Mbps master; an old smart TV cannot decode the newest codec; a player that adapts to bandwidth (lesson 13.06) needs the same video at several quality levels, cut into short segments. The **transcoding pipeline** turns the one upload into all of those.

A few terms first:
- A **codec** (coder-decoder) is the compression method: H.264 (AVC), H.265 (HEVC), VP9, AV1. Newer codecs compress better (AV1 is roughly 30% to 50% smaller than H.264 at the same quality) but are slower to encode and not supported everywhere.
- A **container** wraps encoded video, audio and subtitles into a file: MP4, MPEG-TS, WebM, MKV.
- **Transcoding** means decoding the source and re-encoding it with different settings: a different codec, resolution or bitrate.
- A **rendition** is one output version: for example "720p, H.264, 3 Mbps". The set of renditions is the **bitrate ladder**.

Netflix's pipeline is a good reference shape: ingest high-quality sources, **inspect** them, encode **multiple codec profiles** (historically VC1, H.264 Baseline, H.264 Main and HEVC) at **multiple quality levels from 100 kbps to 16 Mbps**, to serve connections from under 0.5 Mbps on cellular to over 100 Mbps on fibre, then package the results and deploy them to a CDN.

    720p | 3 Mbps

## How video compression shapes the pipeline
To understand why you can split a video into chunks, you need one fact about how it is compressed. Video codecs store most frames as **differences** from other frames.
- An **I-frame** (intra frame, or **keyframe**) is a complete picture, compressed on its own like a JPEG. It is large.
- A **P-frame** stores only what changed since an earlier frame. A **B-frame** can refer to frames before and after it. These are small.
- A **GOP** (group of pictures) is a keyframe plus the frames that depend on it, typically 2 to 10 seconds long. A **closed GOP** does not reference frames outside itself.

So a decoder can start cleanly only at a keyframe. That is why chunk boundaries (and later, streaming segment boundaries) must fall on keyframes or closed GOPs: then each chunk can be decoded and encoded independently, and the encoded chunks can be joined without glitches.

## Inspect first
Netflix rejects bad sources rather than patching them: "garbage in, garbage out". A source with corrupted frames, a wrong frame rate or a production error (a few seconds of black, a missing audio channel) produces bad encodes for every rendition, and fixing that after encoding wastes all the compute. **Inspection** verifies the source conforms to its specification, detects problems, and generates metadata the encoder needs (resolution, frame rate, colour space, scene changes). If a source fails, the content partner is asked to redeliver it.

A 4K studio master can be **larger than an EC2 instance's local disk**, so inspection itself is parallelised:
1. **Index** the file: record byte offsets for frame-accurate seeking, the resolution and the frame count.
2. **Inspect chunks in parallel** on different instances, each reading only its byte range. Each computes spatial and temporal **fingerprints** (compact signatures of what each frame looks like and how it changes).
3. **Aggregate** the results into one report and one fingerprint set for the whole source.

Netflix inspects a 4K source in **under 15 minutes, independent of its length**: a longer film just has more chunks running at the same time.

## Why chunk the encoding
This is the heart of the design. Encoding a whole film sequentially on one machine is how pipelines started, and it fails in five ways that chunking fixes.
1. **Parallelism cuts wall-clock time.** Before chunked encoding, a 1080p movie **could take days** to encode across all its profiles. With chunks encoded on many instances at once, a title is inspected and encoded for every profile, with quality checks, **within a few hours**, and the time no longer grows with the length of the video.
2. **Small failures stay small.** If an instance dies or is reclaimed (Netflix runs encodes on spare capacity from an internal spot market, where instances can be taken back at any time), only that chunk's work is lost and rescheduled. A failure 40 hours into a 48-hour single encode would restart everything.
3. **Less local storage.** Each worker needs only its chunk (a few hundred MB), not the whole multi-hundred-gigabyte source.
4. **Earlier error detection.** Each encoded chunk is checked as soon as it finishes; problems are retried or triaged immediately instead of being discovered when the whole video is done.
5. **Elastic capacity.** Short tasks fit into spare compute anywhere, so the pipeline scales up for a big release and back down afterwards, using cheap interruptible capacity.

%%compare One long sequential encode versus many short parallel ones, for a two-hour film.
[One job per rendition]
2 h film -(one encoder)-> One long encode

- A late failure restarts everything
- Needs the whole source on local disk

! Example: a 10-minute 1080p upload
! The file is split at keyframes into 20 segments of 30 seconds. Encode targets: 1080p, 720p, 480p, 360p and 240p in H.264, plus 1080p and 720p in AV1: 7 renditions × 20 segments = **140 tasks**.
! Sequentially, H.264 at 1080p might run at about real time on one machine (10 minutes for the whole video), the lower resolutions faster, and AV1 several times slower: perhaps 60 minutes of compute in total for all renditions.
! With 140 workers, every task runs at once. The job takes about as long as the slowest single task, one 30-second AV1 1080p segment, perhaps 2 to 3 minutes, plus splitting and assembly. If one worker dies, one 30-second task is retried, adding a couple of minutes, not an hour.

## The task model
A chunked pipeline is a **workflow**: a directed acyclic graph (DAG) of tasks with dependencies. "Split" must finish before "encode chunk 7 at 720p" can start; all 720p chunks must finish before "assemble 720p". A workflow engine (a managed one, or a queue plus a coordinator service) tracks each task's state and hands runnable tasks to a pool of workers.

%%state One encode task in the workflow. Tasks are idempotent, so a retry simply overwrites the output.
[*] -> Queued
Queued -> Running : worker claims task, lease 10 min
Running -> Verifying : chunk encoded, output written
Verifying -> *Done : quality and frame count pass
Verifying -> Queued : check fails, retry
Running -> Queued : worker lost or lease expired
Queued -> Failed : retries exhausted, alert
%%

Two properties make this robust:
- **Idempotent tasks.** Each task writes its output to a deterministic key (`job/v77/720p/chunk-007.mp4`). Running it twice produces the same file, so retries are always safe.
- **Leases, not locks.** A worker claims a task for a limited time and renews the claim while it works. If the worker vanishes, the lease expires and the task returns to the queue (the same pattern as a work queue with visibility timeouts, lesson 08.06).

## Putting chunks back together safely
Chunking introduces new failure modes: chunks assembled in the **wrong order**, frames **dropped or duplicated** at chunk boundaries, slight timing drift that throws audio out of sync. Netflix's assembler stitches each stream's chunks and **validates the result by comparing fingerprints** of the encoded stream against the source's fingerprints from inspection: if a frame is missing or out of place, the fingerprints do not line up. It also computes **full-reference quality metrics** (which compare each encoded frame with the corresponding source frame; VMAF is Netflix's well-known one) for every output stream, to monitor quality and catch encoder bugs. For sources that pass inspection, Netflix achieves **99.99% or better** encode reliability.

There is one more subtlety: rate control. An encoder targeting 3 Mbps decides how many bits each frame gets by looking at what comes before and after. A chunked encoder sees only its chunk, so quality can jump slightly at boundaries. Pipelines handle this with some overlap between chunks, two-pass encoding per chunk, or choosing chunk boundaries at **scene changes**, where a jump in quality is invisible.

## Smarter ladders
A fixed ladder (the same bitrates for every video) wastes bits. A cartoon with flat colours looks perfect at 1080p and 1.5 Mbps; an action film full of rain and grain needs 6 Mbps for the same visual quality. **Per-title encoding** analyses each video's complexity and picks its own ladder. Going further, **shot-based encoding** picks settings per scene. Both rely on the chunked architecture: trying several settings per chunk and keeping the best is only affordable when chunks run in parallel.

%%bars Illustrative bitrates needed at 1080p for similar visual quality, by content type. A per-title ladder saves bits on easy content.

Drama | 4 | 4 Mbps
*Sports, action | 6 | 6 Mbps

## A YouTube-style pipeline for user uploads
For user-generated video the same structure applies, with a focus on speed to first playback:
1. The original is uploaded directly to object storage (lessons 13.01 and 13.04).
2. The object-created event starts a workflow that validates the file (is it really a video, is it too long, is it corrupt?), extracts metadata and a thumbnail, and splits the video into segments at keyframes.
3. A queue of encode tasks (segment × resolution × codec) feeds a pool of workers.
4. Assemblers join the encoded segments and **package** them into HLS and DASH segments and manifests (lesson 13.06), and write them to storage, from where the CDN pulls them.
5. The video is marked ready. To shorten the wait, publish a **low resolution first** (360p is quick to encode) so the video is watchable within a minute, and add higher renditions as they finish. Expensive codecs like AV1 can be encoded later, and only for videos that get enough views to justify the compute.

! Example: prioritising compute by popularity
! A platform gets 500 hours of video uploaded per minute. Encoding everything in AV1 at all resolutions might cost 5 times the H.264 compute. But most uploads are watched a handful of times.
! Policy: encode every upload immediately in H.264 at 360p to 1080p. When a video passes 1,000 views, schedule AV1 renditions as low-priority tasks on spare capacity. If 2% of videos pass that threshold and they account for 80% of watch time, the platform gets most of AV1's bandwidth saving for about 10% extra compute instead of 400%.

## Pitfalls
- **Chunk boundaries off keyframes.** Chunks that cannot be decoded on their own, or that duplicate frames when joined.
- **No verification after assembly.** A dropped frame per chunk is invisible in a spot check and obvious to viewers as audio drift.
- **Non-idempotent tasks.** Retries that append rather than overwrite create corrupted outputs.
- **One queue for everything.** A celebrity's 4-hour upload should not block thousands of 30-second clips. Use priorities or separate queues by job size.
- **Encoding everything in every codec.** Most compute goes to videos nobody watches. Encode cheaply first, expensively when demand proves it.

## In an interview
Sketch the stages: upload to storage, validate and inspect, split at keyframes, encode chunks in parallel per rendition, assemble and verify, package for streaming, push to the CDN, mark ready. Then answer the "why chunks" question with the five reasons: parallelism (days to hours), small failures, little local disk, early error detection, elastic cheap capacity. Mention that the price is careful reassembly and verification, and that publishing a low rendition first improves time to playback.

> Takeaway: a transcoding pipeline inspects the source, splits it at keyframes into chunks, encodes each chunk for every codec and bitrate in parallel as idempotent, leased tasks, then assembles and verifies the streams (Netflix compares fingerprints with the source) before packaging for the CDN. Chunking turns a days-long, fragile job into hours of small, retryable, parallel tasks with modest local storage and early error detection, at the cost of careful reassembly and boundary handling.

?? Encoding a whole film sequentially on one machine can take days, needs the entire huge source on local disk, and loses all progress if the machine fails late. Splitting it at keyframes into chunks lets many machines encode in parallel, so time stays roughly constant regardless of length (Netflix went from days to a few hours), a failed or reclaimed spot instance only costs one chunk's retry, each worker needs little storage, each chunk can be quality-checked as soon as it finishes, and the short tasks fit cheap elastic capacity. The price is reassembling chunks in the right order without dropped or duplicated frames and verifying the stitched stream, which Netflix does by comparing fingerprints with the source.

## The problem: bandwidth changes every second
A viewer's network is not a constant. A train enters a tunnel, someone else in the house starts a download, the phone hands over from Wi-Fi to 4G, the mobile cell gets busy at rush hour. Within one episode, available bandwidth can swing from 50 Mbps to 1 Mbps and back.

If you stream one fixed quality, you lose either way. Stream high quality and the video **stalls** (rebuffers) whenever bandwidth dips, which viewers hate more than anything else. Stream low quality and everyone on a good connection gets a blurry picture. **Adaptive bitrate streaming** (ABR) solves this by switching quality on the fly.

## How ABR works
The ingredients come from the transcoding pipeline (lesson 13.05):
1. The same video is encoded at **several bitrates and resolutions**, the renditions of the bitrate ladder (240p at 0.3 Mbps up to 1080p at 5 Mbps, say).
2. Each rendition is cut into **short segments** of a few seconds (2 to 6 seconds is typical), with every segment starting at a keyframe and the boundaries **aligned across renditions**, so segment 37 covers the same moment in every rendition.
3. A **manifest** (playlist) lists the renditions, their bitrates and resolutions, and where to find each segment.
4. The player downloads the manifest, picks a starting rendition, and then, **for each next segment**, decides which rendition to request. Because segments align, switching is seamless: segment 37 at 1080p is followed by segment 38 at 480p and the viewer sees only a change in sharpness.

%%tree An HLS manifest hierarchy. The master playlist lists renditions; each media playlist lists that rendition's segments.
master.m3u8 | all renditions and their bandwidths
  360p/index.m3u8 | 0.8 Mbps
    seg-001.m4s | 4 s
    seg-002.m4s | 4 s
  720p/index.m3u8 | 3 Mbps
    seg-001.m4s
    seg-002.m4s
  *1080p/index.m3u8 | 5 Mbps
    seg-001.m4s
    seg-002.m4s
  audio/index.m3u8 | 128 kbps AAC
%%

A master playlist looks like this (simplified):

```
  #EXTM3U
  #EXT-X-STREAM-INF:BANDWIDTH=800000,RESOLUTION=640x360
  360p/index.m3u8
  #EXT-X-STREAM-INF:BANDWIDTH=3000000,RESOLUTION=1280x720
  720p/index.m3u8
  #EXT-X-STREAM-INF:BANDWIDTH=5000000,RESOLUTION=1920x1080
  1080p/index.m3u8
```

## Who decides: the player
In HTTP-based ABR, **all the adaptation logic runs on the client**. The server side is an ordinary **web server or CDN** that serves files when asked. It keeps **no per-viewer session state**: it does not know or care which rendition a given viewer is on. That is precisely what makes it scale, because any edge server can serve any segment request from cache, and segments of a popular episode are shared by millions of viewers.

The client is also the only party that **can** decide well. It sees, in real time:
- **Throughput**: how fast its recent segment downloads completed.
- **Buffer level**: how many seconds of video it has downloaded but not yet played.
- **Device capabilities**: screen resolution (no point fetching 1080p for a 360-pixel-wide window), decoder support, CPU load, battery.
- **Dropped frames**: if the device cannot decode 1080p smoothly, step down even if the network could carry it.

%%seq The player drives everything. The CDN serves files; it never knows which rendition a viewer is on.
Player > CDN edge : GET master.m3u8
CDN edge -> Player : renditions 360p to 1080p
Player > CDN edge : GET 360p/seg-001 (fast start)
CDN edge -> Player : 0.4 MB in 0.3 s, about 11 Mbps
Player > Player : buffer 4 s, throughput 11 Mbps, step up
Player > CDN edge : GET 1080p/seg-002
CDN edge -> Player : 2.5 MB in 2 s, about 10 Mbps
Player > Player : buffer 10 s, stay at 1080p
%%

### The algorithms
There are three main families of rate-selection algorithm.
- **Throughput-based.** Estimate available bandwidth from recent segments (bytes divided by download time), usually smoothed with a moving or harmonic average over the last few segments, multiply by a **safety factor** (say 0.8), and pick the highest rendition whose bitrate is below the result.
- **Buffer-based.** Use the buffer level as the main signal. Below a **reservoir** (say 10 seconds), pick the lowest rendition to refill quickly. Above it, raise quality as the buffer grows, reaching the top rendition at a full buffer (say 30 seconds or more). The insight: the buffer already integrates all the network's ups and downs, so it is a more stable signal than noisy throughput samples.
- **Hybrid.** Combine both: throughput to choose quickly at start-up, when the buffer is empty and tells you nothing, then buffer level in the steady state. Many production players (and open-source ones like dash.js, which can switch between a throughput rule and the buffer-based BOLA rule) work this way. More advanced players optimise a predicted score over the next few segments, trading quality against stall risk and switch frequency.

Good algorithms also avoid **oscillation**: switching up and down every segment is visually distracting, so players use hysteresis (step up only after several good segments, step down immediately if the buffer is falling).

! Example: the throughput rule on real numbers
! Segments are 4 seconds long. The player just downloaded segment 12 at 720p (3 Mbps, so 4 s × 3 Mbps = 12 Mbit = 1.5 MB) in 1.0 second: measured throughput 12 Mbps. The previous two segments measured 10 and 14 Mbps. The harmonic mean of 12, 10 and 14 is about 11.7 Mbps; with a 0.8 safety factor the budget is 9.4 Mbps. The highest rendition below that is 1080p at 5 Mbps, so segment 13 is requested at 1080p.
! Segment 13 (2.5 MB at 5 Mbps) then takes 20 seconds to arrive because the train has entered a tunnel: throughput 1 Mbps. Meanwhile the buffer drained from 20 seconds to 4. Both signals now say "step down hard", and segment 14 is requested at 240p (0.3 Mbps, 150 KB), which arrives in about 1.2 seconds even at 1 Mbps.

%%timeline A commute: the player adjusts the rendition for each segment from measured throughput and buffer level, and playback never stalls.
0 s | Start at 480p for a fast first frame
4 s | Segments arrive at 12 Mbps, buffer 8 s, step up to 720p

%%

### Buffer states
From the viewer's point of view, the player is in one of a few states, and the algorithm's job is to stay out of the bad one.

%%state The player's buffer states. The adaptation logic exists to avoid Rebuffering, the state viewers notice most.

Playing -> *Steady : buffer above target, best sustainable quality
Steady -> Playing : buffer falling, step down

## Why HTTP and segments won
Before HTTP-based ABR, streaming used dedicated protocols (RTMP, RTSP) and special servers that held a stateful session per viewer and pushed media at a controlled rate. HTTP segments replaced them for on-demand and broadcast video because:
- **They pass through firewalls and NAT** like any web traffic, on port 443.
- **Segments are ordinary files**, so **browsers, proxies and CDNs cache them**. A popular episode's segments are served from thousands of edges, and the origin sees a trickle. This is the decisive advantage.
- **Ordinary infrastructure.** Any web server or object store can be an origin, any CDN can deliver.
- **The server stays stateless**, so it scales horizontally without coordination.

The costs: more encoding and storage (every rendition of every segment), extra latency (players buffer whole segments, which matters for live video, lesson 13.08), and some awkward interactions between the player's rate choices and TCP's own congestion control.

## The protocols
- **HLS** (HTTP Live Streaming): introduced by Apple in 2009 with iOS 3.0, later published as RFC 8216. Playlists are `.m3u8` text files that index MPEG-TS or fragmented MP4 segments. A **master playlist** lists renditions; each **media playlist** lists segments.
- **MPEG-DASH** (ISO/IEC 23009-1, 2012): the international standard, with an XML manifest called the MPD (media presentation description). Widely used on Android, smart TVs and in browsers through JavaScript players.
- **CMAF** (Common Media Application Format, 2018): a common fragmented-MP4 segment format usable by both, so **one set of segment files** can serve HLS and DASH players, halving storage and doubling cache efficiency.

HLS and DASH are the two formats still actively developed; older ones (Smooth Streaming, HDS) have faded.

## The CDN "decider"
The player decides **which quality**. A different decision, **which CDN or edge server** the bytes come from, is usually made by the **service**. Call it the **CDN decider** (or steering service).
- A CDN routes each viewer to a nearby edge, typically with DNS or anycast.
- Large services use **several CDNs** (commercial ones, or their own, like Netflix's **Open Connect** appliances placed inside internet providers' networks) and choose per session, using measured performance (real-user measurements of throughput and errors by region and network) and cost.
- The choice is communicated by giving the player **different URLs**: the playback API returns a manifest whose segment URLs point at the chosen CDN, or a manifest listing several base URLs in priority order.
- **Mid-stream changes**: HLS **Content Steering** lets a steering server tell players to switch between CDN "pathways" during playback, for example when one CDN is degraded in a region. DASH has a similar steering mechanism, and players can fall back to an alternative base URL after errors.

%%compare The two decisions in a streaming session, and who makes each.
[Service: where from]
Playback API -> Steering service -> CDN choice in URLs
+ Sees performance across all viewers
+ Balances cost and capacity between CDNs
+ Can move sessions when a CDN degrades
[*Player: which quality]
Measure throughput and buffer -> Pick rendition -> Next segment
+ Sees its own network in real time
+ Knows screen size and decoder limits
+ Server stays stateless and cacheable
%%

! Example: a commute with both decisions
! The viewer presses play. The playback API checks the subscription and, based on the viewer's ISP and region, steers the session to an Open Connect appliance inside their provider's network, falling back to a commercial CDN. It returns a manifest with those URLs.
! The player starts at 480p to get a first frame within a second, sees segments arriving at 12 Mbps with 20 seconds buffered, and steps up to 1080p (5 Mbps). In a tunnel, throughput falls to 1 Mbps and the buffer drains from 20 to 8 seconds; the player requests the next segments at 360p (0.8 Mbps) and playback never stalls.
! Meanwhile the appliance at the viewer's ISP has a fault. The steering service notices the error rate climbing for that pathway and tells players to switch to the commercial CDN. The player's next segment request goes there. The viewer notices nothing. Throughout, every edge simply served whichever segment files were requested.

## Pitfalls
- **Starting too high.** A first segment at 1080p on a slow network means a long wait for the first frame. Start low (or from the last session's measured throughput) and climb.
- **Trusting one throughput sample.** A single fast segment from a burst of Wi-Fi capacity leads to an over-ambitious switch and a stall. Smooth over several samples.
- **Misaligned segments.** If renditions do not share keyframe boundaries, switches produce visual glitches.
- **Long segments.** 10-second segments make adaptation sluggish (one decision per 10 seconds) and increase start-up time.
- **Ignoring the device.** Fetching 4K for a phone screen wastes the user's data allowance.

## Two different questions
A video service has paid content and must protect it. "Protect" covers two quite different questions, and the technologies that answer them are different:
1. **Who may download the bytes, and until when?** This is **access control**, and signed URLs and signed cookies answer it.
2. **What can someone do with the bytes once they have them?** This is **content protection**, and DRM (digital rights management) tries to answer it.

Most confusion in this area comes from expecting a tool for the first question to solve the second. This lesson walks through both, using CloudFront (Amazon's CDN) as the concrete example of signed delivery, and the browser DRM stack for content protection.

## What signed URLs do
A plain CDN URL is public: anyone who has it can fetch the file, forever. A **signed URL** adds a cryptographic proof that **your application** authorised this particular request, plus a **policy** saying what is allowed. CloudFront's version works like this:
1. You create a **trusted key group** on the distribution containing one or more **public keys** (RSA 2048 or ECDSA 256). You keep the matching **private keys** on your application servers.
2. When a user asks to watch something, your application checks they are **entitled** (logged in, subscribed, in a permitted country), then builds a **policy** (which resource, until when, optionally from which IP range) and signs it with the private key. The signature and policy go into the URL's query string.
3. When the request reaches a CloudFront edge, CloudFront verifies the **signature** with the public key (so the URL was not forged or tampered with) and checks the **policy** (not expired, right resource, right IP). Only then does it serve the file, from cache or from the origin.

The edge verifies the signature locally with the public key: it does not call your application. That is what makes the scheme scale to millions of requests per second.

### Canned versus custom policies
| Policy feature | Canned policy | Custom policy |
| Expiry time | Yes | Yes |
| Start time (not valid before) | No | Optional |
| IP address or range | No | Optional |
| Covers multiple files with wildcards | No | Yes |
| URL length | Short | Longer (policy is embedded) |

A **canned** policy is just "this exact URL until this time", encoded compactly. A **custom** policy is a small JSON document (base64-encoded into the URL) that can add a start time, a source IP range, and a wildcard resource like `https://cdn.example.com/series/s1e3/*`.

Expiry is checked when a request **starts**: a download already in progress finishes, but a restarted download or a later **range request** (a request for part of a file, which video players use constantly) after expiry fails. Adding or changing query parameters after signing breaks the signature and returns 403.

### Signed cookies for streaming
An HLS or DASH video (lesson 13.06) is not one file: a two-hour film is thousands of segment files across several renditions. Signing every segment URL individually means rewriting every manifest per viewer, which also defeats manifest caching. **Signed cookies** solve this: your application sets three cookies (the policy, the signature and the key pair ID) scoped to the CDN domain, with a custom policy covering `/series/s1e3/*`. Every segment request automatically carries the cookies, and the manifests stay identical for all viewers and cacheable.

### Lock the origin
Signed URLs are useless if users can bypass the CDN and fetch the files straight from the bucket. CloudFront's **origin access control** (OAC) makes the bucket accept requests only from the distribution: the bucket policy allows reads only when the request is signed by CloudFront itself. Every protected setup needs this.

%%flow Signed delivery: the app checks entitlement and signs; the CDN verifies the signature and policy at the edge before serving. The bucket only talks to the CDN.
User -(watch episode)-> App: check subscription -(signed cookie, 4 h, /s1e3/*)-> *CDN edge verifies signature -(origin access control)-> Bucket of segments
%%

## What signed URLs stop, and what they do not
Signed URLs and cookies control **who can fetch the bytes, and for how long**.
- A link posted publicly **stops working when it expires**. With a short expiry (minutes for single files, a few hours for a viewing session), sharing it is pointless.
- With an **IP-restricted** custom policy, the link does not work from anyone else's network at all.
- **Hotlinking** (another site embedding your content using your bandwidth) stops working too.

They do **not** control what happens **after** the bytes arrive. The segments are delivered as ordinary, **unencrypted** media files. A paying subscriber with a valid cookie can:
- save the segments and stitch them into a single MP4 to share forever;
- run a downloader that fetches every segment of every rendition while the cookie is valid;
- re-host the video on another site, where your signature no longer matters.

Access control protects the **door**. Once someone is legitimately through the door, the content is in the clear. For free or low-value content, that is often good enough. For premium films and live sport, studios and leagues require more, usually contractually.

### A half-way step: encrypted segments with a plain key
HLS supports **AES-128 encryption** of segments, with the decryption key fetched from a URL listed in the playlist. If the key URL is protected (signed, short-lived), casual copying of segments fails because they are encrypted. But the key is delivered to the player's JavaScript in the clear, so anyone who can play the video can also fetch the key and decrypt the files. It raises the bar slightly; it is **not DRM**.

## What DRM adds
**DRM** tries to protect the **content itself**, even on the authorised user's own device.
- **Encryption at rest and in transit.** The video is encrypted once at packaging time, typically with **Common Encryption** (CENC, ISO/IEC 23001-7), and stored and cached encrypted. Downloaded segments are useless on their own. CENC allows **one** set of encrypted files to work with **several** DRM systems, because only the key delivery differs.
- **Licences.** To play, the player obtains a **licence** containing the content key from a **licence server**. The licence server checks entitlement (the same checks your app does) and attaches **rules**: expiry (a rental lasts 48 hours), whether offline playback is allowed, a maximum resolution, how many devices.
- **A sealed decryption module.** Decryption happens inside a **Content Decryption Module** (CDM), a component supplied by the DRM vendor that runs outside the web page's JavaScript and, at the highest security levels, inside the device's **trusted execution environment** or secure video path. The key never reaches the application, and on hardware-backed devices decrypted frames never reach memory the operating system can read.

%%seq DRM playback: segments stay encrypted end to end; only the CDM, holding a licence, can decrypt them for display.
Player > CDN : GET encrypted segment (signed cookie)
CDN -> Player : encrypted segment, key ID in header
Player > CDM : need key for this key ID
CDM -> Player : licence request, signed by CDM
Player > Licence server : forward request + user token
Licence server > Licence server : check entitlement, set rules
Licence server -> Player : licence, key sealed to this CDM
Player > CDM : load licence
CDM > CDM : decrypt and decode, frames to screen
%%

### In browsers: EME
**Encrypted Media Extensions** (EME), a **W3C Recommendation since September 2017**, is the browser API that lets an HTML `<video>` element talk to a CDM. It replaced the old browser plugins (Flash, Silverlight) that previously handled protected video. EME works with **Media Source Extensions** (the API JavaScript players use to feed segments to the video element) and CENC content, so one JavaScript player can handle all of them. The main CDMs:
- **Widevine** (Google): Chrome, Firefox, Edge, Android and many smart TVs.
- **PlayReady** (Microsoft): Edge on Windows, Xbox, many smart TVs.
- **FairPlay** (Apple): Safari, iOS, Apple TV.

A service that wants to play everywhere uses **multi-DRM**: one set of CENC-encrypted files (the `cbcs` encryption mode now works with all three), and a licence service that speaks all three licence protocols.

EME was controversial. CDMs are proprietary, closed components with per-browser licensing, raising concerns about open-source browsers, security research, privacy and accessibility; the **EFF resigned from the W3C** the day EME was published as a standard.

## What DRM does not stop either
DRM raises the bar a lot, but it is not absolute.
- **The analogue hole.** Pointing a camera at the screen still works. So does capturing a display output on hardware that ignores protection.
- **Compromised devices.** Software-only CDMs (Widevine **L3**) can be and have been broken; extracted keys let people decrypt content.

Services respond with layers:
- **Security levels.** Issue HD and 4K keys only to hardware-backed CDMs (Widevine **L1**, PlayReady SL3000); software-only clients get SD at most.
- **Output protection.** **HDCP** encrypts the link from the device to the display, so a cheap capture device on the HDMI cable gets nothing.
- **Forensic watermarking.** Embed an invisible, per-viewer mark in the picture so a leaked copy can be traced to the account that leaked it. A common scalable technique is **A/B watermarking**: encode two slightly different variants of each segment, and serve each viewer a unique sequence of A and B segments, chosen at the CDN edge. The sequence spells out a session ID, readable from a leaked copy.
- **Business controls.** Concurrent-stream limits, device registration, and fast takedown of leaked streams (especially for live sport, where the value is in the next 90 minutes).

! Example: a subscription video service, tier by tier
! **Free trailers**: plain public CDN URLs with long cache lifetimes. Protection would cost more than it saves.
! **Episodes**: signed cookies valid for 4 hours covering `/series/s1e3/*`, set when the user presses play after an entitlement check, so every HLS segment request is authorised while manifests stay cacheable. The bucket is reachable only through the CDN with origin access control. A shared link stops working within 4 hours.
! **Premium films and live sport**: additionally CENC-encrypted and licensed through Widevine, FairPlay and PlayReady. HD and 4K keys are issued only to hardware-secure devices with HDCP; software-only browsers get 720p at most. Each stream carries an A/B forensic watermark, so a pirated copy found online can be traced back to the subscription within minutes, and that account's sessions are revoked.

! Example: what each layer costs
! Signed cookies: one signing operation per session on your app servers (microseconds) and no change to caching. Cheap.
! DRM: a licence server (or a multi-DRM vendor billed per licence, often fractions of a cent each), packaging changes, and player integration on every platform. For 10 million plays a day, licence fees and engineering are a real budget line.
! Watermarking: two encoded variants of every segment (double the storage and packaging for protected titles) plus edge logic to pick variants per session. That is why it is usually reserved for the highest-value content.

## Common mistakes
- **Thinking signed URLs prevent copying.** They prevent sharing links, not saving files.
- **Long expiries.** A 7-day signed URL is close to a public link.
- **Leaving the bucket open.** Signed CDN URLs with a public origin bucket protect nothing.
- **Per-segment signed URLs in manifests.** Breaks manifest caching; use signed cookies or tokenised paths.
- **Treating AES-128 HLS as DRM.** The key goes to JavaScript in the clear.
- **DRM everywhere.** Protecting trailers and user-generated clips adds cost and playback failures for no benefit.

Matching protection to content value (public, signed, DRM, watermarked) shows judgement.

## Latency is a design choice
For on-demand video, nobody cares how old the content is. For **live** video, the delay from the camera to the viewer's screen (often called **glass-to-glass latency**) matters a lot, but how much depends on the use:
- A **video call** feels broken above about 300 to 400 ms; people talk over each other.
- A **live auction**, a sports bet placed during play or an interactive game stream needs under a second or it is unfair.
- A **sports broadcast** is fine at a few seconds, although a 30-second delay means your neighbour cheers a goal before you see it.
- A **concert stream or news channel** is fine at 15 to 30 seconds.

The two dominant technologies sit at opposite ends. HTTP segment streaming (HLS and DASH, lesson 13.06) typically delivers live video **10 to 30 seconds** behind real time and scales to millions of viewers cheaply. **WebRTC** delivers it in **a few hundred milliseconds** and costs far more per viewer. This lesson explains where each one's latency comes from, which is the same thing as explaining why each one scales the way it does.

## Where HLS latency comes from
HLS is built for scale and robustness, not immediacy. Follow one video frame from the camera to a viewer.
1. **Capture and encode.** The encoder compresses frames as they arrive: tens to hundreds of milliseconds.
2. **Wait for the segment to finish.** HLS works in whole files. A frame captured at the start of a 6-second segment cannot be published until the **whole segment** is complete, up to 6 seconds later. (Apple originally recommended 10-second segments; the guidance later moved to 6.)
3. **Package and upload to the origin.** The packager writes the segment and **updates the media playlist** to list it: a few hundred milliseconds.
4. **Discovery.** The player learns about the new segment only when it next **polls** the playlist, which it does roughly once per segment duration. On average that adds half a segment.
5. **CDN propagation.** The edge fetches the new playlist and segment from the origin or shield on the first request: hundreds of milliseconds.
6. **The player's buffer.** Players traditionally start **about three segments behind the live edge** to absorb network hiccups. With 6-second segments, that is **18 seconds of buffer by design**.

Add it up and a classic HLS live stream runs **15 to 30 seconds** behind real time.

%%bars Where a classic HLS live stream's delay comes from, with 6-second segments. The player's deliberate buffer dominates.
Capture and encode | 0.5 | 0.5 s
Wait for segment to complete | 6 | up to 6 s
Package and publish playlist | 0.5 | 0.5 s
Player discovers it by polling | 3 | about 3 s
CDN fetch from origin | 0.5 | 0.5 s
*Player buffer, 3 segments | 18 | 18 s
%%

The design choices that cause the delay are exactly the ones that make HLS scale:
- **Files over HTTP** can be cached on CDN edges, so a million viewers fetching the same segment cause one origin request per edge.
- **Large buffers** ride out network variation, so viewers on poor connections rarely stall.
- **Polling and stateless servers** mean no per-viewer connection state anywhere.

### Low-latency HLS and DASH
**Low-Latency HLS** (LL-HLS) cuts the delay to about **2 to 5 seconds** while keeping CDN cacheability:
- **Partial segments** ("parts") of 200 ms to 1 s are published as soon as they are encoded, so the player does not wait for a 6-second segment to finish.
- **Blocking playlist reloads**: the player asks for "the playlist once part 7 of segment 120 exists", and the server holds the request open until it does, replacing polling delay with a push-like response.
- **Preload hints** tell the player the URL of the next part before it exists, so it can request it early.
- Players can then sit **one or two seconds** behind the live edge instead of three segments.

Low-latency DASH achieves the same with CMAF **chunked transfer**: a segment is sent over HTTP in small chunks as it is encoded. The cost is more requests per second, more sensitivity to network jitter (a smaller buffer means more stalls on bad networks), and CDNs that must handle held-open requests well.

## WebRTC
**WebRTC** (Web Real-Time Communication) is a set of browser APIs and protocols that let browsers capture and stream audio and video, and exchange arbitrary data, **directly between peers**, often without servers in the media path. Its pieces:
- **RTCPeerConnection**: the connection between two peers, carrying media **tracks** and **data channels** (an API deliberately similar to WebSocket, for arbitrary messages).
- **Signalling**: before connecting, peers must exchange **session descriptions** in **SDP** (session description protocol) format, an **offer** and an **answer** listing codecs, media and encryption fingerprints. WebRTC deliberately does not define how; applications usually use their own WebSocket server.
- **ICE** (interactive connectivity establishment) finds a working network path between the peers through NATs and firewalls. Each peer gathers **candidates**: its local addresses, its public address as seen by a **STUN** server, and a relay address on a **TURN** server. The peers test candidate pairs and use the best that works. When no direct path exists (strict corporate firewalls, some mobile carriers), media flows through the TURN relay.
- **Transport**: media travels over **RTP** (real-time transport protocol) on UDP, encrypted with **SRTP**, using keys negotiated by **DTLS**. Data channels use SCTP over DTLS.

%%seq Setting up a WebRTC call. Signalling goes through the app's server; once ICE finds a path, media flows directly over UDP.
Alice > Signalling server : SDP offer (codecs, fingerprints)
Signalling server > Bob : forward offer
Bob -> Signalling server : SDP answer
Signalling server -> Alice : forward answer
Alice > STUN server : what is my public address?
STUN server -> Alice : 203.0.113.7:54012
Alice > Bob : ICE candidates via signalling, connectivity checks
Bob -> Alice : check succeeds on best pair
Alice > Bob : DTLS handshake, then SRTP media over UDP
%%

## Why WebRTC is sub-second
Every source of HLS delay is designed out:
- **No segments.** Frames are sent **as soon as they are encoded**, as a continuous stream of small RTP packets (about 1,200 bytes each). There is no waiting for a multi-second file to complete.
- **UDP rather than TCP.** With TCP, a lost packet blocks delivery of everything behind it until it is retransmitted (**head-of-line blocking**). Over UDP, the receiver can ask for a retransmission (NACK) if there is time, use forward error correction, or simply **conceal** the gap (repeat the last frame, smooth over the audio) and move on. For live conversation, a brief glitch is far better than a delay.
- **Tiny jitter buffers.** A **jitter buffer** holds incoming packets briefly to smooth out variations in arrival time. WebRTC keeps it at **tens to a few hundred milliseconds**, adjusted dynamically, instead of tens of seconds.
- **The encoder adapts in real time.** Congestion control estimates available bandwidth continuously from packet timing and loss and tells the **encoder** to lower its bitrate or resolution immediately. HLS instead switches between renditions encoded in advance, one segment at a time.
- **A direct path.** Peer to peer, or through one media server, rather than through a packager, an origin and several CDN tiers.

%%

## Scaling WebRTC to an audience
Pure peer-to-peer only works for small calls. In a **mesh**, each sender uploads a separate copy to every other participant: in a 6-person call each person uploads 5 streams, which saturates home uplinks. Larger sessions use a **Selective Forwarding Unit** (SFU): a media server that receives one stream from each sender and **forwards** it to every receiver, without decoding or re-encoding (which is what keeps it cheap compared with an MCU, a server that mixes everything into one stream).

SFUs use **simulcast** to serve receivers with different bandwidths: the sender encodes 2 or 3 versions at once (say 180p, 360p and 720p), and the SFU forwards to each receiver the layer that fits its connection. **Scalable video coding** (SVC) achieves the same with layered encoding of one stream. For big audiences, SFUs **cascade**: an origin SFU forwards to regional SFUs, which forward to viewers.

%%flow Scaling a WebRTC broadcast: the presenter sends simulcast layers once; cascaded SFUs forward the right layer to each viewer.
Presenter -(simulcast 180p, 360p, 720p)-> *Origin SFU -(all layers)-> Regional SFU Europe -(720p or 360p)-> 1,000 viewers
Origin SFU -(all layers)-> Regional SFU US -(layer per viewer)-> 1,000 viewers
%%

This works, but it **costs far more per viewer** than CDN delivery. Every viewer holds a live UDP session with an SFU, which must forward every packet individually, track congestion per receiver and handle retransmissions. A single SFU server might handle a few hundred to a few thousand viewers, and cloud bandwidth for SFUs is priced well above CDN bandwidth. That is why large broadcasts still use HLS or DASH, and reserve WebRTC for the interactive participants.

Newer protocols narrow the gap: **WHIP** and **WHEP** standardise WebRTC ingest and playback over simple HTTP requests (useful for broadcasters), and work on **Media over QUIC** aims at sub-second latency with CDN-style fan-out.

  Under 1 s, two-way interaction
    *Small group: WebRTC with an SFU

! Example: a live auction
! Bidders must see the auctioneer within half a second or bids are unfair, so the auctioneer's stream goes out over WebRTC to **2,000 bidders** through two regional SFUs, each serving 1,000 viewers at 1.5 Mbps (720p simulcast layer) or 0.5 Mbps (360p). Peak SFU egress is about 3 Gbps.
! **200,000 spectators** who cannot bid watch the same event over low-latency HLS from the CDN at about 4 seconds behind: 200,000 × 3 Mbps = 600 Gbps, served from CDN edges at a much lower price per gigabyte, with the origin seeing only a few requests per part per edge.
! Delivering the spectators over WebRTC instead would need about 200 SFU servers and 600 Gbps of SFU egress, several times the cost, for a latency improvement they do not need.

! Example: tuning a sports stream from 25 seconds to 4
! A sports app runs classic HLS with 6-second segments and players three segments back: about 25 seconds behind the TV broadcast, and users complain about spoilers from social media.
! Step 1: 2-second segments and players two segments back: about 8 to 10 seconds. More playlist requests and a little more stalling on bad networks.
! Step 2: LL-HLS with 333 ms parts, blocking playlist reloads and players about 1 second behind the live edge: about 3 to 4 seconds. The CDN must support held-open playlist requests; the encoder must produce parts aligned with keyframes every 2 seconds.
! Going below 1 second would mean WebRTC for millions of viewers, an order of magnitude more expensive. The product decides 4 seconds is good enough.

## Pitfalls
- **Promising WebRTC latency at HLS prices.** Sub-second delivery to millions is expensive; check whether the product really needs it.
- **Forgetting TURN.** Without a TURN relay, a minority of users behind strict NATs or firewalls cannot connect at all. Budget TURN bandwidth.
- **Tiny buffers on bad networks.** Low latency means less protection against jitter; expect more stalls and quality drops, and measure them.
- **Mesh calls that grow.** Peer-to-peer is fine for 1:1 and maybe 3 or 4 people; above that, use an SFU.
- **Ignoring signalling.** WebRTC gives you no signalling; you need a reliable channel (usually WebSocket, lesson 11.02) to exchange offers, answers and candidates.

## The goal
A **file sync service** (Dropbox, Google Drive, OneDrive, iCloud Drive) keeps a folder identical across a user's devices and the people they share it with. Change a file on your laptop, and within seconds the new version is on your phone, your desktop at work and your colleague's machine.

The core efficiency requirement is captured by one scenario: a user changes **1 byte** in a **1 GB** file. Uploading the whole gigabyte again would take over 13 minutes on a 10 Mbps uplink, burn mobile data, and multiply across every device that then downloads it. The ideal is to transfer roughly **the size of the change plus a little metadata**, both up from the editing device and down to every other device.

This lesson builds the design that achieves that, modelled on Dropbox's architecture, and then fills in the rest of a sync system around it.

## The block model
The foundation is to stop treating a file as one indivisible blob.
- Every file is split into **blocks** of a fixed size; Dropbox uses **4 MB** (the last block may be smaller).
- Each block is identified by the **SHA-256 hash** of its contents: a 32-byte fingerprint that, in practice, is unique to that content.
- A file is represented by its **blocklist**: the ordered list of its blocks' hashes.
- **Only blocks the server does not already have are uploaded.**

Hashing is what makes this work. Two blocks with the same hash have the same content, so the server can tell whether it already has a block without seeing it, just by looking up the hash. Lesson 13.10 explains this **content addressing** in depth.

### Two kinds of server
The design splits storage into two services with very different jobs:
- **Block servers** (the block store): a giant key-value store mapping **hash → block contents** (encrypted at rest). They know nothing about users, files, names or folders. They just store and return blocks by hash. This is where the bytes, petabytes or exabytes of them, live.
- **The metadata server** (metaserver): knows about users, shared folders (**namespaces**), file paths and versions. Its core is the **Server File Journal** (SFJ), an append-only log recording, for each namespace, which blocklist each path has at each point in time. This data is small but must be strongly consistent.

%%flow The architecture of a block-based sync service. Bytes and metadata take separate paths; notifications tell other devices to pull.
[Upload] Laptop: file watcher -(changed file)-> Hasher: blocklist -(commit)-> *Metaserver and journal
[Upload] Hasher: blocklist -(missing blocks only)-> Block servers
[Download] Metaserver and journal -(change notification)-> Phone -(fetch blocklist, missing blocks)-> Block servers
%%

## The commit protocol
The upload uses a short conversation in which the server tells the client exactly which blocks it needs.
1. The client computes the file's new blocklist and tries to **commit** it: "path `/designs/logo.psd` now has blocklist h1, h2, ..., h256".
2. The metaserver checks which of those hashes already exist in the block store (and that this user is allowed to reference them). If any are missing, it refuses the commit and answers **"need blocks"** with the list of missing hashes.
3. The client uploads just those blocks directly to the block servers.
4. The client commits again. Now every block exists, so the metaserver appends the new version to the journal and the commit succeeds.

%%seq The commit protocol. The client proposes a blocklist; the server replies with the blocks it lacks; the client uploads only those, then commits again.
Client > Metaserver : commit(path, base rev 41, blocklist h1..h256)
Metaserver -> Client : need blocks: h137'
Client > Block server : store(h137', 4 MB)
Block server -> Client : ok
Client > Metaserver : commit(path, base rev 41, blocklist h1..h256)
Metaserver > Metaserver : append rev 42 to journal
Metaserver -> Client : ok, rev 42
Metaserver > Other devices : namespace changed
%%

Other devices are notified that the namespace changed, ask the metaserver for changes since the last journal position they saw, receive the new blocklist, compare it with the blocks they already have locally, and **download only the blocks they lack**. Sync is efficient in both directions.

## The 1-byte edit
Now the question. A 1 GB file split into 4 MB blocks has **256 blocks**. If one byte is **overwritten in place** (the file's length does not change), only the block containing that byte changes, so exactly **one** hash in the blocklist changes.

The client uploads:
- **one 4 MB block**, and
- a blocklist of 256 hashes × 32 bytes = **8 KB**, plus a few hundred bytes of request overhead.

That is about **0.4%** of the file. Every other device downloads the same 4 MB.

! Example: the 1-byte edit traced
! A user opens `video-project.bin` (1 GB, 256 blocks), changes one byte at offset 571,000,000, and saves.
! The client's file watcher reports a change. The client re-reads the file and hashes each 4 MB block: SHA-256 runs at roughly 0.5 to 1 GB per second on a modern CPU, so this takes 1 to 2 seconds. Offset 571,000,000 falls in block 137 (counting from 1: 571,000,000 ÷ 4,194,304 ≈ 136.1, so the 137th block). Only h137 changes, to h137'.
! Commit: the metaserver replies "need h137'". The client uploads 4 MB, which takes about 3.4 seconds at 10 Mbps. The second commit succeeds as revision 42. Total upload: 4 MB + 8 KB instead of 1 GB, about 250 times less.

%%bars Bytes uploaded after a 1-byte change to a 1 GB file, by sync strategy. Scale is logarithmic.
Whole file | 1000000 | 1 GB
Fixed 4 MB blocks | 4000 | 4 MB + 8 KB list
Smaller 1 MB blocks | 1000 | 1 MB + 32 KB list
Content-defined 64 KB chunks | 64 | about 64 KB + list
*rsync-style delta in block | 2 | a few KB
%%

### Making it better still
- **Smaller blocks** reduce what a small change costs, at the price of longer blocklists and more metadata and hash lookups. Many designs use 1 to 8 MB.
- **Deltas within a block**: an rsync-style delta (lesson 13.10) can send just the changed bytes inside the changed block, plus enough to rebuild it, so a 1-byte change costs a few kilobytes. The server reconstructs the new block from the old one plus the delta.
- **Insertions are the hard case.** If the edit **inserts** a byte rather than overwriting one, every fixed block boundary after it shifts by one byte, so every later block's hash changes and the rest of the file looks new. **Content-defined chunking** (lesson 13.10) fixes this by placing boundaries where the content dictates, not at fixed positions.

## Streaming sync: overlap upload and download
Originally, sync had two strict phases: the uploading device uploaded every block and committed; only then did other devices hear about the file and start downloading. For a large new file shared with a colleague, the total time was upload time plus download time.

**Streaming sync** lets downloading clients **prefetch blocks of a file that has not been committed yet**, while the upload is still in progress. As soon as the uploader has stored a block, the server can tell interested clients its hash, and they start fetching. By the time the commit lands, they are nearly done. Dropbox calculated up to **2× faster** multi-client sync in theory; in a test with about 1.2 Mbps upload and 5 Mbps download, it measured about **25%** faster in practice (a 500 MB file: 293 s instead of 383 s; 100 MB: 64 s instead of 89 s).

%%timeline Sharing a new 100 MB file with a colleague. Streaming sync starts the download while the upload is still running.
0 s | Uploader starts sending blocks
10 s | *Streaming: colleague's client begins prefetching stored blocks
60 s | Last block stored, commit succeeds
64 s | Streaming: colleague already has nearly every block, done
89 s | Classic: download only started at 60 s, finishes now
%%

## The rest of a sync design
The block model is the heart, but a complete design needs the parts around it.

### Detecting changes
- **Local changes** are detected with operating-system file events (FSEvents on macOS, ReadDirectoryChangesW or FileSystemWatcher on Windows, inotify on Linux) and queued. A periodic scan comparing size and modification time catches anything the events missed.
- **Remote changes** arrive by a push notification over a long-lived connection (WebSocket, server-sent events or long polling, lesson 11.02), with periodic polling (`GET /changes?since=<cursor>`) as a safety net. The notification only says "something changed"; the client then fetches changes since its **cursor** (its position in the journal), which makes missed notifications harmless.

### Uploads and downloads
- Large blocks or files go **directly to blob storage** with presigned URLs and multipart upload, supporting files up to tens of gigabytes (lessons 13.01 and 13.04). Per-chunk status in the file's metadata lets uploads resume.
- **Fingerprints** (SHA-256) for each chunk and the whole file enable deduplication and resumability, and let the client verify every downloaded block.
- **Compression** on the client before upload (and before encryption, since encrypted data does not compress), skipped for already-compressed media such as JPEG and MP4.
- **Downloads** come from storage or a CDN with short-lived signed URLs (lesson 13.07).

### Conflicts
Two devices may edit the same file while one is offline. Each commit carries the **base revision** it was edited from. If the server's current revision is newer than the base (someone else committed in between), the commit is a **conflict**.
- The simplest policy is **last write wins**, which silently loses one person's work.
- Real clients usually **keep both**: the server keeps the version that arrived first, and the second device saves its version as a separate file, such as `report (Ana's conflicted copy 2026-11-12).docx`, and syncs that. No data is lost, and a human resolves it.

%%compare Two policies for concurrent edits to the same file while one device was offline.
[Last write wins]
Ana commits rev 42 -> Ben commits on base 41 -> Ben overwrites Ana
+ Simple, one file
- Ana's work silently lost
[*Keep both]
Ana commits rev 42 -> Ben commits on base 41 -> Conflict detected -> Ben's copy saved beside it
+ Nothing is ever lost
+ Base revision makes conflicts detectable
- A human must merge the two copies
%%

! Example: a designer saves a 1 GB Photoshop file
! The client re-hashes the file and finds blocks 37 and 38 changed (the edit touched a 6 MB region spanning a block boundary). Commit returns "need h37', h38'"; 8 MB is uploaded and the commit succeeds as revision 18.
! The designer's desktop at home gets a notification, fetches changes since its cursor, receives the new blocklist, sees it already has 254 of the 256 blocks, and downloads 8 MB. With streaming sync, it had started downloading those 8 MB before the commit finished.
! Meanwhile the designer's laptop, offline on a train, had also edited the file from revision 17. When it reconnects, its commit says "base rev 17", the server is at 18, and the laptop saves its version as a conflicted copy. Both versions survive.

## Pitfalls
- **Uploading whole files.** It works in a demo and fails users on slow connections with large files.
- **Fixed blocks with insertions.** A design that only handles overwrites well. Mention content-defined chunking.
- **Trusting notifications as data.** Notifications get lost; the cursor-based changes API is the source of truth.
- **Last write wins by default.** Fine for some data, unacceptable for people's documents.
- **Identifying files by path.** Renames and moves look like delete plus create, which breaks history and sharing (lesson 13.11 returns to this).
- **Hashing everything on every event.** Check size and modification time first, and re-hash only files that may have changed.

## Content addressing
Most storage systems name data by **location**: a file path, a database row ID, an object key that you chose. A **content-addressed** store names data by **what it is**: the key of each piece of data is a **cryptographic hash** of the data itself. Put in some bytes, and you get back their hash; give the hash, and you get the bytes back. You cannot choose the key, and you cannot change the bytes stored under a key without changing the key.

A **cryptographic hash function** such as SHA-256 maps any input to a fixed-size output (32 bytes for SHA-256) such that, in practice, no two different inputs ever produce the same output, and changing a single bit of the input changes about half the bits of the output. That property is what lets a hash stand in for the content.

### Git is a content-addressed store
Git is the best-known example: at its core it is a content-addressable filesystem, a simple key-value store where you insert content and get back a key (a SHA-1 hash) to retrieve it.
- `git hash-object` hashes a short header (`blob <size>\0`) followed by the file's content. The object is zlib-compressed and stored at `.git/objects/xx/yyyy...`, where `xx` is the first two hex characters of the hash and the rest is the file name.
- **Blobs** hold file contents only, with no names.
- **Trees** list entries: a name, a mode (file, executable, symlink, directory) and the hash of a blob or of a subtree.
- **Commits** point to one top-level tree, to their parent commit(s), and record who made the change, when, and why (the message).

```
$ echo 'test content' | git hash-object -w --stdin
d670460b4b4aece5915caf5c68d12f560a9fe3e4
$ git cat-file -p d670460b4b4aece5915caf5c68d12f560a9fe3e4
test content
```

%%tree Git's object graph. Each node is stored under the hash of its content, and parents refer to children by hash, so unchanged subtrees are shared between commits.
Commit c3 | tree t9, parent c2
  Tree t9 | root directory
    README.md | blob a1, unchanged since c1
    *src/ | tree t7, changed
      main.go | blob b8, new content
      util.go | blob b2, unchanged
    docs/ | tree t4, reused from c2 by hash
%%

## What it gives you for free
Naming data by its hash produces five properties without any extra machinery.
1. **Deduplication.** Identical content always has the same hash, so it is stored **once**, whether it is two copies of a file in one folder, the same file across a thousand commits, or (in a sync service like Dropbox) the same 4 MB block in files belonging to different users. Writing content that already exists is a no-op: "already have it".
2. **Integrity.** The name **is** a checksum. If stored bytes are corrupted by a failing disk or tampered with, they no longer hash to their key, and the problem is detected on read. Git's `fsck` and every sync client's download check work this way.
3. **Cheap snapshots and versions.** A commit references a whole tree, but unchanged subtrees and blobs are reused **by hash** rather than copied. Each new snapshot costs only what changed, plus small new tree objects along the path to the change (lesson 13.11 applies this to file versions).
4. **Easy caching and replication.** Content at a given hash can **never change**, so it can be cached forever, by anyone, and copied anywhere without any invalidation or consistency protocol. There is no such thing as a stale copy.
5. **Efficient sync.** To synchronise two stores, compare hashes and send only the objects the other side lacks. This is Dropbox's "need blocks" (lesson 13.09) and Git's fetch negotiation ("I have these commits; send me what I am missing").

A sixth property comes along with these: **a single hash identifies an entire structure**. A commit hash covers its tree, which covers every subtree and blob, so if two commit hashes are equal, the whole snapshots are equal. Comparing two million-file trees starts with comparing two hashes. Structures built this way are called **Merkle trees** (or Merkle DAGs).

### What it costs
- **Hashing time.** Every byte must be hashed on write, roughly 0.5 to 2 GB per second per core for SHA-256 with hardware support.
- **Immutable objects need garbage collection.** Nothing is ever overwritten, so something must eventually delete objects no longer referenced (lesson 13.11).
- **Collisions are theoretical but not ignorable for weak hashes.** SHA-1, which Git originally used, has had a practical collision demonstrated (two different PDFs with the same SHA-1), so Git now uses a collision-detecting SHA-1 and supports SHA-256 repositories. With SHA-256 you would need about 2^128 objects before a random collision became likely; that is not a practical concern.
- **Privacy.** In a shared store, "do you already have this hash?" can leak that someone else stored the same file. Lesson 13.11 discusses limiting dedup to one account.

## Fixed-size blocks and the insertion problem
To content-address large files efficiently, you split them into blocks and hash each one. The simplest split is **fixed-size**: block 1 is bytes 0 to 4 MB, block 2 is 4 to 8 MB, and so on. As lesson 13.09 showed, that is excellent for **in-place overwrites**: change one byte and one block's hash changes.

Now **insert** one byte at the start of the file. Every byte after it moves one position later. Block 1 now holds the new byte plus the first 4 MB minus one byte of the old content; block 2 starts one byte earlier than before; and so on to the end. **Every block's content shifts by one byte, so every block's hash changes**, and the whole file looks new. The same happens with deletions. A 1 GB file with a word inserted near the beginning costs a full 1 GB upload.

That matters because insertions are common: adding a paragraph to a document, a row in the middle of a CSV, a line in source code, a new entry in an archive.

%%compare The boundary-shift problem: one inserted byte at the front shifts every fixed block boundary, so every hash changes.
[Before]
ABCD EFGH IJKL -(hash each 4-byte block)-> h1, h2, h3
+ Overwriting one letter changes one hash
[After inserting X at the start]
XABC DEFG HIJK L -(hash each 4-byte block)-> h4, h5, h6, h7
- All new hashes: nothing deduplicates
- One byte costs the whole file
%%

There are two classic answers: find matches at **any offset** (rsync), or put block boundaries at positions **determined by the content** (content-defined chunking).

## rsync's answer: match at any offset
The rsync algorithm solves "update a file over a slow link when the other side has an old version". Machine β has the old file B; machine α has the new file A; they want β to end up with A while sending as little as possible.
1. β splits B into **fixed blocks** of S bytes (say 700 bytes) and computes, for each block, a cheap **weak 32-bit rolling checksum** and a **strong 128-bit checksum** (MD4 originally; newer versions use MD5 or faster hashes). It sends this list to α: about 20 bytes per block.
2. α slides a window of S bytes across A at **every byte offset**, not just multiples of S. At each offset it computes the weak checksum and looks it up in a hash table of B's checksums. Only on a weak match does it compute the strong checksum to confirm.
3. α sends β a sequence of instructions: "copy block k of B" for matches, and **literal bytes** for the parts that match nothing. β assembles A from its own blocks plus the literals.

One round trip, and only the genuinely new data travels.

%%seq An rsync transfer. The side with the old file sends checksums; the side with the new file replies with block references and literal bytes.
Beta (old file B) > Alpha (new file A) : weak + strong checksum per 700-byte block
Alpha (new file A) > Alpha (new file A) : slide window at every offset, match checksums
Alpha (new file A) -> Beta (old file B) : copy block 0, literal "X", copy blocks 1..n
Beta (old file B) > Beta (old file B) : rebuild A from own blocks plus literals
Beta (old file B) > Beta (old file B) : verify whole-file checksum
%%

### The rolling checksum
Scanning every offset would be hopeless if each window needed its checksum computed from scratch (S operations per offset). The **rolling checksum** updates in constant time as the window slides. For the window of bytes X_k to X_l it has two parts:
- **a** = the sum of the bytes in the window (mod 2^16);
- **b** = a position-weighted sum, where the first byte is weighted by the window length and the last by 1 (mod 2^16).

The checksum is a + 2^16 × b. When the window slides one byte to the right, dropping X_k and adding X_(l+1):
- `a' = a − X_k + X_(l+1)`
- `b' = b − (window length) × X_k + a'`

Two subtractions, an addition and a multiply per byte, however large the window.

! Example: rolling the checksum by hand
! Take a 4-byte window over "abcd", bytes 97, 98, 99, 100. Then a = 97 + 98 + 99 + 100 = 394, and b = 4×97 + 3×98 + 2×99 + 1×100 = 388 + 294 + 198 + 100 = 980.
! Slide one byte to "bcde" (e is 101). a' = 394 − 97 + 101 = 398. b' = 980 − 4×97 + 398 = 990.
! Check directly: 4×98 + 3×99 + 2×100 + 1×101 = 392 + 297 + 200 + 101 = 990. Same answer, without re-summing the window.

So an inserted byte costs only the block containing it as literal data; every following block still matches, just at an offset shifted by one. Measured on two versions of the Linux kernel source as tarballs (about 24 MB each), with blocks of 500 bytes or more, rsync transferred **only a few percent of the file**, less than the equivalent diff and patch, and false matches of the weak checksum occurred less than once per thousand true matches.

rsync is ideal for one-off transfers between two machines. It is less suited to a **block store**, because the old file's blocks are defined by position, and after many edits the stored blocks no longer line up with anything. For storage, you want boundaries that stay put.

## Content-defined chunking
**Content-defined chunking** (CDC) chooses chunk boundaries by looking at the content itself:
1. Slide a small window (say 48 bytes) across the file, computing a **rolling hash** of the window at every byte (Rabin fingerprinting is the classic choice; Gear hashing, used by FastCDC, is faster).
2. Declare a **chunk boundary** wherever the hash meets a condition, for example its **low 13 bits are all zero**. For random-looking data that happens on average once every 2^13 = 8,192 bytes, giving **8 KB average chunks**.
3. Enforce a **minimum and maximum** chunk size (say 2 KB and 64 KB), so long runs of repetitive data (where the condition never or always fires) do not produce absurd chunks.
4. Hash each chunk with SHA-256 and store it in the content-addressed store, exactly as with fixed blocks.

The key property: a boundary depends only on the 48 bytes before it. Insert a byte somewhere, and the boundaries before the insertion are unchanged; the chunk containing the insertion changes; and the **next boundary after it reappears at the same content**, because the bytes around it are the same as before. From then on, chunks are identical to the old ones and deduplicate.

%%flow Content-defined chunking: boundaries follow the content, so after an insertion they resynchronise and later chunks keep their hashes.
Bytes -(rolling hash over 48-byte window)-> Low 13 bits zero? -(yes: cut here)-> *Boundary tied to content -(insert a byte)-> Only 1 or 2 chunks change
%%

CDC is used widely in backup and sync tools (restic, Borg and the Low-Bandwidth File System are well-known examples) and in deduplicating storage systems. The average chunk size is a trade-off: small chunks (4 to 16 KB) deduplicate finely but create millions of chunks and large chunk lists; large ones (1 MB) keep metadata small but waste more on each edit. Backup tools often use around 1 MB averages for large datasets; sync tools for documents use smaller ones.

%%bars Bytes sent after inserting one paragraph near the start of a 40 MB document, including metadata. Fixed blocks resend almost everything.
Fixed 4 MB blocks | 40000 | about 40 MB, all blocks
Fixed 64 KB blocks | 40000 | about 40 MB, almost all blocks
rsync, 700-byte blocks | 1100 | about 1.1 MB, mostly checksums
*Content-defined, 8 KB avg | 176 | 16 KB chunks + 160 KB list
%%

! Example: inserting a paragraph
! A 40 MB document is stored as about 5,000 content-defined chunks averaging 8 KB. The user inserts a 500-byte paragraph on page 3.
! The client re-chunks the file. Every boundary before page 3 is found at exactly the same place. The chunk containing the insertion now holds 500 more bytes and gets a new hash; occasionally the insertion itself creates or removes a boundary, so its neighbour changes too. After that, the next boundary falls on the same content as before, and every later chunk has its old hash.
! The client asks the server which hashes it lacks: 2 new chunks, about 16 KB, plus a new chunk list (5,000 hashes × 32 bytes = 160 KB, which itself can be deduplicated or sent as a diff). With fixed 4 MB blocks, all 10 blocks would have changed: 40 MB.

## Common mistakes
- **Assuming fixed blocks handle edits.** They handle overwrites; they fail on insertions and deletions.
- **Using a weak hash as the address.** CRC32 or a rolling checksum is fine for finding boundaries or candidates, never as the identity of stored data. Confirm with a cryptographic hash.
- **No minimum or maximum chunk size.** Files full of zeros or repeated patterns produce millions of tiny chunks or one enormous one.
- **Chunks too small.** Metadata (chunk lists, index entries) can outgrow the savings.
- **Forgetting garbage collection.** Content-addressed stores only grow unless something deletes unreferenced objects.

## A version is a list of hashes
Lessons 13.09 and 13.10 built two ideas. First, a file's content is stored as **blocks** (or content-defined chunks) in a **content-addressed block store**, where each block's key is its SHA-256 hash and identical blocks are stored once. Second, the file itself is represented by its **blocklist**: the ordered list of its block hashes. The metadata service records, for each file, which blocklist is current.

To keep **version history**, make one small change: **never overwrite a blocklist; append a new version**. Each save creates a new row pointing at a new list.

```
file_versions
  file_id | version | blocklist                      | size   | modified_at | author
  f9      | 1       | [h1, h2, h3, ..., h250]        | 1.0 GB | 10:02       | ana
  f9      | 2       | [h1, h2, h3', ..., h250]       | 1.0 GB | 10:47       | ana
  f9      | 3       | [h1, h2, h3', ..., h250, h251] | 1.0 GB | 11:30       | ben
```

Dropbox's metadata server keeps exactly this kind of record in its **Server File Journal**, an append-only log of which blocklist each path has; its block servers store hash → block and know nothing about files, users or versions. That separation is the whole trick: **history lives in metadata, bytes live once in the block store**.

## Why history is cheap
Version 2 differs from version 1 in one block. Storing version 2 costs:
- **one new block** (h3', 4 MB) in the block store, and
- **one new metadata row** with a list of 250 hashes (250 × 32 bytes, about 8 KB).

The other 249 blocks are **shared by reference**: the hashes in both lists point to the very same stored objects. Logically, each version is a **complete snapshot** of the file: you can read version 1 in full at any time. Physically, only the changes were stored. This is the same mechanism as Git's commits and trees (lesson 13.10): every commit is a full snapshot of the repository, but unchanged blobs and subtrees are reused by hash.

%%flow Two versions share every unchanged block by hash; only the edited block is stored again.
[Version 1] Blocklist v1 -> h1, h2 -> *h3 -> h4 ... h250
[Version 2] Blocklist v2 -> h1, h2 -> *h3-new -> h4 ... h250
[Block store] Stored once each -> h1, h2, h3, h3-new -> h4 ... h250
%%

! Example: a year of edits
! A 200 MB spreadsheet is edited 500 times over a year, each edit changing about 2 blocks (8 MB).
! **Full copies**: 500 × 200 MB = 100 GB.
! **Blocklists**: the first version's 50 blocks (200 MB), plus 500 × 8 MB of new blocks = 4 GB, total 4.2 GB, plus 500 metadata rows of about 1.6 KB each (50 hashes × 32 bytes), under 1 MB. That is about 24 times less storage.
! Restoring the version from March is a single metadata write. When versions older than 180 days expire, a garbage-collection sweep finds about 300 blocks no longer referenced by any live version and deletes them, freeing about 1.2 GB.

%%bars Storage for 500 versions of a 200 MB file, each edit changing about 8 MB.
Full copy per version | 100000 | 100 GB
*Blocklists and shared blocks | 4200 | 4.2 GB
Metadata rows alone | 0.8 | under 1 MB
%%

## What falls out of the model
Once versions are lists of hashes, many features become almost free.
- **Restore an old version.** Make the old blocklist current again by writing a **new** version row that points to it (version 4 = the blocklist of version 1). No data is copied; the blocks are already there. Writing a new row rather than deleting later versions keeps the history honest: you can undo the restore.
- **View or download an old version.** Fetch the blocks in its list, in order. Blocks the device already has (because they are shared with the current version) need not be downloaded.
- **Compare versions.** Diff the two lists to see which regions changed, without reading any file data.
- **Deduplication across files.** Two files with identical regions (a copied file, a document saved under a new name, the same photo in two folders) share blocks automatically.
- **Integrity.** Every downloaded block is checked against its hash.
- **Moves and renames are metadata only.** No block moves or is copied when a file is renamed or a folder of 10,000 files is moved.

### Deduplication across users: careful
If two users upload the same file, a global block store would store it once. That saves a lot (think of popular installers or videos), but it creates an information leak: if uploading a file you do not have completes instantly because the server says "already have all blocks", you have learned that **someone else stored that file**. An attacker can use this to confirm whether a specific document exists in the system, or even guess contents by trying variations. Many systems therefore deduplicate **only within one account or namespace** from the client's point of view, or encrypt blocks with per-user keys, which makes identical content produce different stored blocks. Any server-side dedup across users happens invisibly, without changing what the client sees.

## Garbage collection
Sharing has a cost: **deleting is hard**. When old versions expire (many services keep 30 or 180 days of history, depending on the plan) or files are deleted, you cannot simply delete their blocks, because a block may still be referenced by other versions, other files or other users. You need **garbage collection**: delete a block only when **no live version anywhere** refers to it.

Two classic approaches:
- **Reference counting.** Keep a count per block of how many live blocklist entries refer to it. Increment on commit, decrement when a version expires, delete at zero. Simple in principle, but every commit and every expiry must update counts for many blocks, and a single missed decrement (a crash at the wrong moment) leaks storage forever while a double decrement deletes live data. At large scale the counts themselves become a hot, hard-to-shard dataset.
- **Mark and sweep.** Periodically **mark** every hash reachable from any live version (by scanning all live blocklists), then **sweep**: delete every block that was not marked. Slower and batch-oriented, but robust: it recomputes the truth from scratch each time, so errors do not accumulate.

Large systems often combine them: approximate counts or recent-activity logs for most blocks, with periodic mark and sweep to correct drift.

### The race you must handle
The dangerous moment is a block that has been **uploaded but not yet committed**. In the commit protocol (lesson 13.09), the client uploads blocks the server asked for, then commits. Between those steps, the new block is referenced by no version. A sweep running at that instant would delete it, and the commit would then point at a missing block. A similar race happens when a commit reuses an existing block (dedup) at the same moment the sweep decides that block is unreferenced.

The standard fixes:
- A **grace period**: never delete a block younger than, say, 24 hours, or one that became unreferenced less than a day ago. Uploads and commits finish long before.
- **Two-phase deletion**: the sweep first marks candidates as **tombstoned** (no longer offered for dedup), and deletes them only after a later sweep confirms they are still unreferenced. A commit that references a tombstoned block is told to upload it again.

%%state A block's life in the store. The grace period and tombstone stop a sweep from deleting a block that a commit is about to use.
[*] -> Uploaded
Uploaded -> Referenced : commit includes its hash
Uploaded -> Tombstoned : never committed, older than grace period
Referenced -> Unreferenced : last version using it expires
Unreferenced -> Referenced : a new commit reuses it
Unreferenced -> Tombstoned : sweep, still unreferenced after grace
Tombstoned -> *Deleted : second sweep confirms
%%

## Metadata as its own hard problem
The block layer is the easy part: a key-value store of immutable blobs, scaled by hashing keys across machines. The metadata is where the difficulty lives. Dropbox's scale illustrates it: **hundreds of millions of users**, **hundreds of billions of files**, **trillions of file revisions**, **exabytes** of data. Dropbox rewrote its sync engine (the rewrite is called Nucleus, written in Rust) largely because of its **data model**:
- The old engine had **no stable identifiers** for files that survived moves: a move was recorded as a delete plus an add. That made shared folders and concurrent moves error-prone (a file moved on one device while edited on another could vanish or duplicate). The new model gives files and shared folders **globally unique IDs** and is designed so a file is never observed in a transiently duplicated or missing state.
- The old engine was hard to test. The new one is **deterministic** given its inputs and the order of events, so it can be fuzzed with **millions of randomised scenarios a day**, each reproducible from a random seed.

The lesson for your own design: **identify files by a stable file ID, not by path.** Keep the path (or parent folder ID and name) as an attribute that can change. Versions hang off the file ID. Then a rename is one metadata update, a move is one metadata update, and history follows the file wherever it goes.

%%tree The metadata model. A stable file ID owns the versions; the path is just an attribute, so renames and moves keep history.
Namespace: Ana's folder
  File f9 | name logo.psd, parent folder d2
    Version 1 | blocklist [h1 .. h250], 10:02, ana
    Version 2 | blocklist [h1, h2, h3' .. h250], 10:47
    *Version 3 | current, 11:30, ben
  File f12 | name notes.txt, parent folder d2
    Version 1 | blocklist [h900]
  Folder d2 | name designs, renamed without touching files
%%

### A simple interview-scale schema
- `files(file_id, namespace_id, parent_id, name, current_version, deleted_at)`
- `file_versions(file_id, version, blocklist, size, created_at, created_by, base_version)`
- `blocks(hash, size, storage_location, created_at)` in the block store's own index.
- A per-namespace **journal** (an increasing sequence number on every change) that devices use as a cursor: "give me everything after 5,812".

For a simpler file-upload service you might start with a single `FileMetadata` record holding `id`, `name`, `size`, `mimeType`, `uploadedBy`, `status`, and a `chunks` list with per-chunk status (for resumable uploads, lesson 13.04). Adding versions is then a matter of keeping previous chunk lists instead of overwriting them.

! Example: restore, rename and expire on one file
! Monday: Ana creates `logo.psd` (file f9, 1 GB, version 1). Tuesday: she edits it twice (versions 2 and 3, about 8 MB of new blocks each). Wednesday: she renames it to `logo-final.psd` and moves it to another folder: one update to f9's name and parent; no blocks touched; versions 1 to 3 still attached.
! Thursday: she realises Tuesday's edits were wrong and restores version 1. The service writes version 4 with version 1's blocklist. Her other devices see a new version and compare its blocklist with what they hold. Almost every block is shared with version 3, so they fetch only the few original blocks that Tuesday's edits replaced (about 16 MB), or nothing if those are still in a local cache.
! Six months later, versions 2 and 3 expire. Their unique blocks (about 16 MB) become unreferenced; after the grace period, two sweeps confirm it and the blocks are deleted. Versions 1 and 4 share all their blocks, so nothing else is freed.

## Pitfalls
- **Copying data on restore.** A restore should be a pointer change, not a 1 GB copy.
- **Overwriting blocklists in place.** You lose history and break devices that are mid-download of the old version.
- **Deleting blocks eagerly.** Without grace periods and two-phase deletion, a sweep will eventually delete a block a commit was about to use, corrupting a file.
- **Path as identity.** Moves become delete plus create, history breaks, and concurrent moves misbehave.
- **Global dedup visible to clients.** It leaks which files exist in other users' accounts.

## In an interview
Say it in one line: a version is an immutable list of block hashes, and blocks are stored once in a content-addressed store, so a new version costs only its new blocks plus a small row. Then show you know the consequences: restores are pointer writes, renames are metadata, dedup is automatic (with a privacy caveat across users), and the price is garbage collection with reference counts or mark and sweep, protected by grace periods. Finish with stable file IDs rather than paths, which is the lesson Dropbox's rewrite teaches.

> Takeaway: store each file version as an immutable, ordered list of content hashes pointing into a deduplicated block store. A new version costs only its new blocks plus a small metadata row, restores are pointer changes, renames and moves touch only metadata, and blocks are garbage-collected (by reference counting or mark and sweep, with grace periods and tombstones) when no live version references them.
