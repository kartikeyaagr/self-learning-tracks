## What we are building
Ride matching in the style of Uber or Lyft. A rider opens the app, sees a price, taps "request", and within seconds a nearby driver is offered the trip, accepts it, and drives over. Under the friendly map are three hard problems: tracking millions of moving drivers in real time, finding the right driver fast, and guaranteeing that one driver is never given two riders at the same time.

### Functional requirements
- Riders get a **fare estimate** (price and pickup ETA) for a trip.
- Riders **request** a ride and are **matched** with a nearby available driver.
- Drivers **accept or decline** an offer, then navigate to the pickup and destination.
- Out of scope: payments (lesson 16.03), ratings, scheduled rides, pooled rides.

### Non-functional requirements
- Matching finishes (a match or a clear failure) within about **1 minute**.
- **Strong consistency for matching**: a driver must never be assigned two rides at once, and a rider must never get two drivers.
- High throughput at local peaks, such as **100,000 requests from one area** when a stadium empties.
- Location updates may be slightly stale (a few seconds is fine); losing some is acceptable.

## Entities and API
- **Rider** and **Driver** (with vehicle and status: offline, available, offered, on trip).
- **Fare**: an estimated price and ETA for a pickup and destination, valid for a few minutes.
- **Ride**: the lifecycle from request to completion, with rider, driver and timestamps.
- **Location**: a driver's latest position and the time it was reported.

```
POST  /fare {pickup, destination}          -> fare_id, price, eta
POST  /rides {fare_id}                     -> ride_id (status: requested)
POST  /drivers/location {lat, lng}         -> 204
PATCH /rides/{id} {action: accept|decline} -> ride
```

Two security habits matter here. The rider or driver ID always comes from the session token, never the request body, otherwise anyone could accept rides as any driver. And the server must not trust client-supplied fares or timestamps: `POST /rides` takes a `fare_id` that the server created and stored, so a modified app cannot request a ride at a price of 1 cent.

## The ride lifecycle
Before the architecture, pin down the states. Most bugs in matching systems are illegal transitions: a ride assigned twice, or cancelled after it was completed.

%%state A ride's lifecycle. Each transition is a conditional update, so two actors cannot move it in conflicting directions.
[*] -> Requested
Requested -> Matching : queued
Matching -> *Accepted : driver accepts
Accepted -> In progress : rider picked up
In progress -> Completed : drop-off
Matching -> No driver : 1 minute passes
%%

A rider can cancel from Requested, Matching or Accepted. Every transition is written as `UPDATE rides SET status='accepted', driver_id=D WHERE id=R AND status='matching'`, so if the rider cancelled a millisecond earlier, the driver's accept finds zero rows updated and is told the ride is gone.

## Numbers
! Example: sizing the location stream
! 10 million drivers online at a global peak, each reporting position every 5 seconds: 10,000,000 / 5 = 2 million writes per second.
! Each update is about 50 bytes (driver ID, latitude, longitude, timestamp, heading). That is 100 MB per second of incoming data, about 8.6 TB a day if you kept it all.
! But matching only needs the latest position per driver: 10 million x about 100 bytes in an index is 1 GB. The whole live state fits in memory on a handful of machines. The challenge is the write rate, not the size.
! Ride requests: perhaps 20 million rides a day, about 230 per second on average, but with sharp local spikes (100,000 requests in 15 minutes around one stadium is over 100 per second from a few city blocks).

## High-level design
%%flow The main services: locations in an in-memory geo index, matching behind a queue, offers pushed to drivers.
[Locations] Driver app -(every 5 s)-> Location service -(GEOADD)-> *Redis geo index
[Requests] Rider app -(POST /rides)-> Ride service -(enqueue)-> Kafka -(consume)-> Matching service
[Offer] Matching service -(GEOSEARCH nearby)-> Redis geo index -(lock + offer)-> Notification to driver
%%

- **Ride service**: computes fares (calling a maps service for route distance and time, then applying pricing including surge), stores Fares and Rides, and enqueues ride requests for matching.
- **Location service**: receives driver location updates and answers "which available drivers are near this point?".
- **Matching service**: chooses drivers by pickup ETA, availability, vehicle type and other factors, and runs the offer loop.
- **Notification service**: pushes offers to drivers. While the driver app is in the foreground it usually holds a persistent connection, so offers arrive in under a second; APNs and FCM are the fallback.

## Driver locations
Two million writes per second into a normal relational database, each updating a row and a spatial index, is far too much. And "drivers near this point" needs a spatial index (lessons 12.01 to 12.04). A good fit is **Redis geo commands**:
- `GEOADD drivers:available <lng> <lat> driver:123` stores the driver as a member of a sorted set whose score is a 52-bit geohash of the position. Updating a driver's position is an O(log N) sorted-set update.
- `GEOSEARCH drivers:available FROMLONLAT <lng> <lat> BYRADIUS 3 km ASC COUNT 20` finds the nearest drivers by scanning the geohash ranges that cover the circle and filtering by exact distance (lesson 12.04 covers how).

Practical details:
- **Remove stale drivers.** Keep a second sorted set scored by last-update time, and every few seconds remove drivers whose last update is older than, say, 30 seconds (the app was closed or the phone died). Otherwise matchers offer rides to ghosts.
- **Separate sets by status.** Keep only available drivers in the searchable set; remove a driver when an offer is made or a trip starts, and add them back when it ends.
- **Tolerate loss.** If a Redis node fails, a few seconds of locations are lost, but every active driver sends a fresh update within 5 seconds, so the index heals itself. Replication with automatic failover limits the gap. This is one of the few places where in-memory, eventually consistent state is exactly right.
- **Reduce updates on the client.** Send less often when the driver is parked or the app is idle, more often when moving fast or close to a pickup. Adaptive reporting can cut the write rate by half.
- **Shard by area.** One Redis instance handles perhaps 100,000 to 200,000 writes per second. Split the world into regions (city or H3 cell groups) with their own instances: 2 million writes per second across 20 to 40 shards.

## Never matching two riders to one driver
This is the lesson's central question. Two matching workers, each handling a different rider near the stadium, both search nearby and both pick driver D as the closest. If both send offers, D might accept both, or tap accept on one while the other rider waits on a driver who is already taken. Three ways to prevent it:

%%compare Three ways to stop two matchers offering the same driver.
[Lock in each process]
Matcher -(local mutex)-> Offer
- Other machines cannot see it
- Crash leaves it held
[Status column]
UPDATE driver where free -> Offer
+ Atomic and durable
- Timeout lives in process memory
[*Redis lock with TTL]
SET NX EX 10 -> Offer
+ Atomic across all matchers
+ Expires on its own
- Depends on Redis being up
%%

- **A lock inside each matching process** (bad). Workers on different machines do not see each other's locks, so the race remains.
- **A status column in the database** such as `outstanding_offer` (good). A conditional `UPDATE drivers SET offer=ride17 WHERE id=D AND offer IS NULL` is atomic, so only one matcher wins. But who clears it if the driver never responds? A timer in the matcher's memory is lost if that process crashes, leaving D unavailable forever unless a sweeper runs.
- **A distributed lock in Redis with a TTL** (best). Before offering a ride to driver D, the matcher runs `SET lock:driver:D ride-17 NX EX 10`. Only one matcher can succeed, because `NX` sets the key only if it does not exist. The driver has **10 seconds** to respond; if they do not, the key expires on its own and D becomes available again. No sweeper, no timer to lose.

%%seq Two matchers want the same driver; the atomic lock lets only one make an offer.
Matcher A > Redis : SET lock:driver:D rideA NX EX 10
Redis -> Matcher A : OK
Matcher B > Redis : SET lock:driver:D rideB NX EX 10
Redis -> Matcher B : nil, try next driver
Matcher A > Driver D : offer ride A (10 s)
Driver D > Matcher A : accept
Matcher A > DB : assign D if ride open and D free
%%

### The database is still the final guard
Redis locks are leases, and leases can fail: a Redis failover can lose a recently written key, and a matcher paused by garbage collection for 12 seconds might still believe it holds a lock that expired (lesson 06.09 covers fencing tokens for exactly this). So the final assignment is a conditional database write: assign D to ride A **only if** D has no active ride **and** ride A is still in `matching`. If that write finds zero rows, the matcher treats it as a failed offer and moves on. Redis keeps the common case fast; the database guarantees correctness in the rare case.

! Example: the race traced with timestamps
! 18:02:00.000 Matchers A and B both receive requests from riders at the stadium gate and both get driver D as nearest (300 m away).
! 18:02:00.004 Matcher A's SET NX succeeds. 18:02:00.005 Matcher B's SET NX returns nil; B immediately tries driver E (450 m), whose lock succeeds, and offers E the ride.
! 18:02:03.200 D accepts. Matcher A runs the conditional assignment; one row is updated. Ride A is accepted; D is removed from the available set.
! If instead D had ignored the offer, at 18:02:10.004 the lock key would expire, and at 18:02:10.050 Matcher A (still holding the ride) would lock the next candidate. Total time lost to an unresponsive driver: 10 seconds.

## Not dropping requests
If a matching instance holds a rider's request only in memory and crashes, the rider waits forever staring at "finding your driver". Put requests on a **queue** (Kafka), and have the matcher commit the offset only after the request is matched or definitively failed. A crash then means another instance picks the request up. Partition the queue **by geography** so each matcher owns an area and its candidates rarely overlap with another matcher's, which also reduces lock contention.

### The offer loop as a durable workflow
Drivers who do not respond are normal. After 10 seconds the matcher must offer the ride to the next driver, then the next, until someone accepts or the minute is up. That is a long-running, multi-step process with timers. Keeping it in one process's memory means a deploy or crash loses every in-flight ride. Model it as a **durable workflow** (Temporal, AWS Step Functions, or a state table plus a timer service): "offer, wait up to 10 s, on timeout or decline try the next" is persisted step by step and survives restarts.

%%timeline One ride request offered to drivers in turn until one accepts, within the one-minute budget.
0 s | Request queued, 8 candidates found
0.1 s | Lock driver 1, offer sent
10 s | No answer, lock expires
10.1 s | Lock driver 2, offer sent
14 s | Driver 2 declines
14.1 s | Lock driver 3, offer sent
19 s | *Driver 3 accepts, ride assigned
%%

## Hot spots and surge
When a stadium empties, 100,000 requests arrive from a few city blocks while only a few hundred drivers are nearby. Matching more cleverly does not create drivers. The system responds in several ways:
- **Batch matching**: instead of greedily matching each request to its nearest driver, collect requests for a second or two and solve the assignment for the batch, minimising total pickup time. Greedy matching gives the first rider a good driver and leaves later riders with far worse ones.
- **Widen the radius** progressively as nearby supply runs out.
- **Surge pricing** raises fares in the area, which reduces demand and draws drivers in. Fare estimates must be computed from current supply and demand per area, which is another per-region aggregate updated every few seconds.
- **Queue and inform**: tell riders their position or expected wait rather than spinning.

## Scaling and failure handling
- **Shard by geography.** Riders and drivers in one city mostly interact locally. Map regions to shards (consistent hashing over region IDs spreads load). Queries near a region boundary ask both shards and merge results (scatter-gather).
- **Read replicas** help with ride history and fares; the ride table's writes stay on the primary.
- **Redis failure** loses locks and positions for a few seconds. In-flight offers may be duplicated, but the conditional database write prevents double assignment, and positions refill within 5 seconds.
- **Driver app disconnects mid-offer**: the lock expires and the next driver is tried.
- **Matcher crash**: the workflow engine resumes the offer loop on another worker from its last persisted step.

## Common mistakes
- Writing every location update to the primary database.
- Locks without expiry, or locks only in local memory.
- No conditional database write behind the lock.
- Keeping offer timers in process memory.
- Trusting the client for price or identity.
- Matching purely greedily during surges.

## In an interview
Do the location write-rate calculation early: it justifies the in-memory geo index. Draw the ride state machine, then go deep on the double-assignment question: Redis `SET NX EX`, why it beats the alternatives, and the conditional database write as the final guard. Finish with durability (queue plus workflow) and hot spots. Ask: how long should drivers have to respond, can a driver receive several offers at once, and is pooling in scope?

> Takeaway: keep driver locations in an in-memory geo index (Redis GEOADD and GEOSEARCH, sharded by area) that tolerates losing a few seconds of updates. Put ride requests on a queue so nothing is dropped. Before offering a ride, take a Redis lock on the driver with SET NX and a 10-second TTL so only one rider's offer can reach them, back it with a conditional database write, and drive the offer, timeout and retry loop with a durable workflow.

## What we are building
A video platform in the style of YouTube: creators upload videos, the platform processes them, and viewers watch them on phones, laptops and TVs over networks that range from fibre to a train's patchy 4G. Module 13 covered the pipeline pieces one at a time: multipart uploads (13.04), parallel transcoding (13.05), adaptive bitrate streaming (13.06) and signed URLs (13.07). This lesson puts them together into one design and then answers the question that decides most of the cost: which videos are served from the CDN, and which from origin?

### Requirements
- Creators upload videos up to tens of GB, with **resumable** uploads (a dropped connection at 80% must not restart from zero).
- Viewers watch with playback that **adapts to network speed** and starts quickly.
- Viewers see metadata: title, description, view counts.
- Scale: about **1 million uploads** and **100 million views** a day.
- Out of scope: comments, recommendations (lesson 16.05), live streaming (lesson 13.08), monetisation.

## Numbers
! Example: storage and bandwidth
! 1 million uploads a day at an average of 500 MB each is 500 TB of originals a day. Transcoding into about 6 renditions (240p to 4K) adds roughly the same again, so about 1 PB of new storage a day, around 365 PB a year. Storage is a real cost, which is why some platforms keep fewer renditions for unpopular videos.
! 100 million views a day, average 8 minutes watched at an average of 3 Mbit/s: each view streams 8 x 60 x 3 / 8 = 180 MB. That is 18 PB of egress a day, about 1.7 Tbit/s on average, perhaps 5 Tbit/s at the evening peak.
! Egress at even 1 cent per GB would be 180,000 dollars a day. Bandwidth, not storage or compute, is the dominant bill, and where it is served from is the main lever on it.

Those numbers say: uploads are a large but manageable batch-processing problem, and playback is a massive content-delivery problem. They also say the backend servers should never touch video bytes on the playback path.

## Upload
1. The client sends metadata (title, size) to the API and receives a video ID and **presigned URLs** for an object store such as S3: time-limited URLs that let the client write one specific object without holding storage credentials.
2. The client uploads straight to S3 with **multipart upload**, in parts of 5 to 10 MB, several in parallel, recording each part's number and ETag (a checksum returned by S3).
3. To resume after a failure, the client asks which parts already exist (`ListParts`) and uploads only the missing ones.
4. When all parts are in, the client calls `CompleteMultipartUpload`, and S3 emits an "object created" event that starts processing.

The application servers only handle small JSON requests. A 20 GB upload never passes through them, so they need no special scaling for it.

## Processing: a DAG of jobs
A **DAG** (directed acyclic graph) of jobs is run by an orchestrator such as Temporal or a workflow engine (lesson 08.07):
- **Split** the original into segments of a few seconds each (ffmpeg can cut at keyframes).
- **Transcode each segment in parallel** into several **renditions**: combinations of resolution and bitrate (for example 240p at 400 kbit/s up to 4K at 15 Mbit/s), with codecs such as H.264 for compatibility and VP9 or AV1 for efficiency.
- Process audio tracks, thumbnails and captions in parallel branches.
- Write **manifests**: HLS or DASH playlists that list every segment of every rendition.
- Mark the video ready in the metadata store.

Workers pass S3 URLs between steps, not files, so any worker can pick up any step. Parallelism is what makes a 2-hour film available in minutes: 1,440 five-second segments transcoded across hundreds of workers instead of one machine working for hours.

! Example: transcoding time
! A 60-minute video split into 6-second segments gives 600 segments. Transcoding one segment into 6 renditions takes a worker about 30 seconds of CPU.
! On one machine: 600 x 30 s = 5 hours. With 300 workers in parallel: about 60 seconds plus split and merge overhead, so the video is ready in roughly 2 to 3 minutes.
! At 1 million uploads a day averaging 10 minutes each, total transcoding is about 1,000,000 x 100 segments x 30 s = 3 billion CPU-seconds a day, which is roughly 35,000 cores busy all day. That is why platforms buy dedicated hardware encoders or transcode the long tail lazily.

Metadata (title, owner, status, rendition list) lives in a scalable store such as Cassandra, partitioned by video ID, with a cache in front, because reads outnumber writes by far.

%%flow Upload goes to storage and a transcoding DAG; playback is just manifest and segment fetches.
[Upload] Creator -(multipart PUT, presigned)-> S3 original -(upload event)-> *Transcode DAG
[Outputs] Transcode DAG -(segments + manifest)-> S3 origin
[Watch] Viewer -(manifest, then segments)-> CDN edge -(miss)-> S3 origin
%%

## Playback: adaptive bitrate
The player downloads the **manifest**, picks a starting rendition based on its estimate of bandwidth, and downloads segments of a few seconds each. After each segment it re-measures throughput and how much video is buffered, and switches rendition up or down for the next segment. That is **adaptive bitrate (ABR)** streaming: the picture gets softer on a bad connection instead of stopping to buffer.

%%seq A player starting playback: everything after the metadata call is a plain file fetch from the CDN.
Player > API : GET /videos/v42 (title, manifest URL)
API -> Player : metadata + signed manifest URL
Player > CDN edge : GET manifest.m3u8
CDN edge -> Player : list of renditions and segments
Player > CDN edge : GET 480p segment 1 (fast start)
Player > CDN edge : GET 1080p segment 2 (bandwidth good)
CDN edge -> Player : segment from edge cache
%%

The key observation: if the CDN holds the manifest and segments, playback does not touch your backend at all apart from one metadata call. Every one of the 5 Tbit/s at peak can come from caches.

## Which videos go to the CDN?
This is the lesson's question. A **CDN** (content delivery network) is a fleet of cache servers placed in or near viewers' internet providers. Serving from an edge in the viewer's own network is faster (tens of milliseconds instead of hundreds) and much cheaper per gigabyte than serving across the internet from your origin. But edge storage is limited: an edge site might hold hundreds of terabytes, while the catalogue is hundreds of petabytes. So the question is which bytes deserve edge space.

The answer comes from one fact: video popularity is extremely **skewed**. A small fraction of videos gets most of the views, and a huge **long tail** gets a handful each. Roughly, the top 10% of videos might account for 80 to 90% of views.

%%bars Share of daily views by video popularity group (illustrative skew).
*Top 1% of videos | 50 | 50% of views
Next 9% | 35 | 35%
Next 40% | 13 | 13%
Bottom 50% | 2 | 2%
%%

- **Popular and new-but-trending videos** go on the CDN, in edge caches near viewers. This is where the bandwidth is.
- **The long tail** (old or rarely watched videos) is served from **origin** (object storage), usually through a regional mid-tier cache. Keeping millions of rarely watched videos at every edge would push out content people actually watch. A video watched twice a month gains almost nothing from being at the edge.
- **Not all of a popular video.** Viewers mostly watch the first minutes, and mostly in a couple of renditions (say 720p and 1080p on phones and laptops). Caches naturally hold the hot segments (the start, the common bitrates) and evict the rest. A 2-hour film might have its first 10 minutes at every edge and its last hour only at a few.

### How it happens: pull, push and tiers
- **Pull caching** (the default): the CDN fetches a segment from origin on the first request and keeps it while it stays popular; least-recently-used segments are evicted when space is needed (lesson 05.03). This sorts popular from unpopular automatically, with no one deciding anything.
- **Push, or pre-positioning**: for videos you *know* will be big (a premiere, a trending creator's new upload, a new season), push them to edges ahead of time, usually during off-peak hours when bandwidth is cheap. Netflix fills its Open Connect appliances, cache servers placed inside internet providers, overnight based on predicted popularity.
- **Tiered caching**: edge caches fall back to a regional **shield** cache before origin, so a long-tail video requested in ten cities fetches from origin once rather than ten times.

%%layers Where a video segment is served from, by popularity.
*Edge cache near viewer | hot titles and opening segments; premieres pushed ahead
Regional shield cache | moderately popular; absorbs repeated misses
Origin object storage | every rendition of every video; the long tail lives here
%%

%%compare Pull caching versus pre-positioning, and when each fits.
[*Pull through]
First request -(miss)-> Origin -> Cached at edge
+ Automatic, no prediction needed
+ Tracks real popularity
- First viewers in each city get a miss
[Push ahead]
Prediction -(off-peak)-> Copy to edges
+ No cold misses at launch
+ Uses cheap night bandwidth
- Wasted space if prediction is wrong
%%

! Example: two videos
! A trending music video gets 5 million views in its first day. Its first 30 seconds at 720p and 1080p are requested in every city, so they sit in nearly every edge cache; its CDN hit rate is above 99%, and origin serves it a few hundred times in total.
! A 2014 lecture recording gets 3 views a week. Each view misses the edge (its segments were evicted long ago), may hit the regional shield, and otherwise streams from origin. That costs a few hundred megabytes of origin egress a week, a rounding error, and caching it everywhere would push out videos people actually watch.

### What the hit rate is worth
! Example: why a few points of hit rate matter
! Of 18 PB of daily egress, a 95% edge hit rate leaves 0.9 PB a day served from origin or shield. At 98% it is 0.36 PB. The difference of 0.54 PB a day, at an illustrative 2 cents per GB for origin egress against near zero inside a provider's network, is about 10,000 dollars a day, over 3 million dollars a year, for three points of hit rate.
! That is why video platforms tune cache sizes, pre-position aggressively and design manifests so that the opening segments (which everyone requests) are identical across devices.

## Other cost levers
- **Storage**: many renditions per video, often several times the original's size. Some platforms transcode the long tail into fewer renditions, or only on first view, to save storage and compute.
- **Codecs**: AV1 or VP9 save around 30 to 50% bandwidth compared with H.264 at the same quality, but cost far more CPU to encode. Worth it for popular videos (encode once, save on millions of views), not for the long tail.
- **Cold storage** for originals that will never be re-transcoded.

## Security and failure handling
- **Signed URLs or signed cookies** (lesson 13.07) on manifests and segments let the CDN check that a viewer is allowed to watch without calling your backend. Private and paid videos add DRM.
- **Origin protection**: if a popular video's segments are evicted everywhere at once (say, after a CDN configuration mistake), millions of requests could stampede origin. The shield tier collapses identical concurrent misses into one origin fetch (request coalescing).
- **Transcode failures**: each DAG step retries independently; a poison video (corrupt file) is marked failed after a few attempts and the creator is told.
- **Multi-CDN**: large platforms use several CDNs and steer traffic between them by price and performance, which also covers a single CDN's outage.

## Common mistakes
- Uploading through application servers.
- Transcoding a whole video serially on one machine.
- Proposing to put every video on every edge.
- Ignoring that bandwidth dominates cost.
- Forgetting manifests, so there is nothing for the player to adapt with.

## In an interview
Do the egress calculation first; it is the number that makes everything else obvious. Draw upload and playback as separate paths. For the CDN question, say "popularity is skewed, so pull-through caching with LRU keeps the head at the edge and the long tail at origin behind a shield; pre-position predictable hits". Ask: what share of views is on new videos, are there premieres, and what is the device mix?

> Takeaway: upload directly to object storage in parts, transcode segments in parallel into several renditions with manifests, and stream with adaptive bitrate so playback is just file fetches. Let the CDN pull and keep what is popular (and pre-position predictable hits); serve the long tail from origin through a shield cache, because popularity is highly skewed, edge space is limited, and bandwidth is the largest cost.

## What we are building
A file sync service in the style of Dropbox, Google Drive or OneDrive: a folder on each of your devices that stays the same everywhere. Save a file on your laptop and it appears on your phone and desktop a few seconds later. Edit while on a plane and it syncs when you land. Lessons 13.09 to 13.11 covered the building blocks (the sync model, chunking and content addressing, versioned block lists). This lesson assembles them and then answers the question that every sync system must get right: two devices edit the same file offline, and then both reconnect. What happens?

### Requirements
- Upload, download and share files up to tens of GB.
- **Automatic sync** across all of a user's devices, including after offline periods.
- **Version history**: restore earlier versions for 30 days or more.
- Never silently lose a user's work.
- Scale: say 100 million users, 500 million devices, 1 billion file changes a day.

## Numbers
! Example: sizing
! 1 billion file changes a day is about 11,500 per second on average. Most are small (documents, code, notes), but some are large media files.
! If the average change uploads 1 MB of new chunk data after deduplication and delta sync, that is 1 PB of new blob data a day. Without delta sync (uploading whole files on every change, average 20 MB), it would be 20 PB a day. Delta sync is not a nice-to-have; it is the difference between a feasible and an absurd system.
! Metadata: each file version has a block list of chunk hashes (32 bytes each). A 100 MB file in 4 MB chunks has 25 hashes, under 1 KB. Billions of file versions fit in a sharded metadata database of tens of terabytes.

## The design in brief
- **Upload**: the client splits files into chunks (fixed 4 MB blocks in Dropbox's design, or content-defined chunks), computes a **SHA-256 fingerprint** of each, and asks the server which chunks it already has. It then uploads only the missing ones, in parallel, straight to blob storage through **presigned URLs**. The server verifies the parts exist before committing.
- **Metadata**: a database (sharded Postgres, MySQL or DynamoDB) holds each file's ID, path, size, owner, **current version number**, and for each version its **block list** (the ordered list of chunk hashes).
- **Local to remote**: a client agent watches the file system (inotify on Linux, FSEvents on macOS) and queues changed files.
- **Remote to local**: each device keeps a **WebSocket or SSE** connection for change notifications, and also polls `GET /changes?cursor=...` every few minutes in case it missed one. The cursor is the position in the user's change journal that this device has already applied.
- **Delta sync**: only chunks whose fingerprints changed are uploaded. With **content-defined chunking** (lesson 13.10), chunk boundaries are chosen by a rolling hash of the content, so inserting a paragraph near the start of a file changes one or two chunks instead of shifting every later fixed-size block.

%%flow Sync: changed chunks go up, a metadata commit makes a new version, other devices are told.
[Upload] Laptop -(changed chunks only)-> *Blob storage -(chunks verified)-> Metadata: new version
[Notify] Metadata -(change event)-> Phone and desktop -(fetch missing chunks)-> Local copy updated
%%

### Why content addressing helps
A chunk is stored under its hash, so identical content is stored once no matter how many files or users contain it. That gives deduplication for free, makes uploads resumable (the client re-asks which hashes are missing), and makes every chunk immutable: a chunk with hash X will always contain the same bytes. Versions are then just different block lists pointing at mostly shared chunks.

%%tree One file, two versions. Versions are block lists; unchanged chunks are shared, so a new version costs only its changed chunks.
report.docx
  v5 | block list
    chunk a1f3
    chunk 7c20
    chunk e991
  *v6 | block list
    chunk a1f3 | shared
    chunk 44bd | new
    chunk e991 | shared
%%

## The commit: a compare-and-set on the version
After its chunks are uploaded, the client **commits** a new version: "set report.docx to this block list". Every commit states which version the edit was based on: "this is my edit of **version 5**". The server accepts the commit only if version 5 is still the latest. This is a **compare-and-set** (CAS) on the file's version number:

```
UPDATE files SET version = 6, block_list = :new
WHERE file_id = :id AND version = 5;
-- 1 row updated: success.  0 rows: someone else committed first.
```

The check and the write happen atomically in one statement, so two simultaneous commits cannot both succeed. This is the same optimistic concurrency idea used in many places (lesson 03.06): do not lock while the user edits for hours; check at commit time whether anything changed underneath you.

## Two devices edit the same file offline
Your laptop and your desktop both have `report.docx` at version 5. You go offline on both (say the laptop is on a plane and the desktop's network is down), edit the file on each, and both reconnect. What should happen?

The simplest rule is **last write wins** (LWW): whichever save reaches the server last becomes the file. It is easy, and it silently throws away one of your edits. For a sync service whose promise is "never lose my work", that is unacceptable, so real services detect the conflict and keep both.

1. The laptop reconnects first and commits "new content, based on v5". v5 is current, so the CAS succeeds and this becomes **v6**.
2. The desktop reconnects and commits "new content, based on v5". The latest is now v6, so the CAS updates zero rows and the server **rejects** the commit as a conflict.
3. The desktop client handles the conflict. It cannot merge a Word document's binary contents, so it keeps both: it uploads its edit as a **new file** next to the original, such as `report (Desktop's conflicted copy 2026-11-09).docx`.
4. It then downloads v6, so its `report.docx` matches everyone else's.
5. Both files sync to every device. The user opens them and decides how to combine them.

%%seq Both devices edited version 5; the second commit conflicts and becomes a conflicted copy.
Laptop > Server : commit report.docx, base v5
Server -> Laptop : OK, now v6
Desktop > Server : commit report.docx, base v5
Server -> Desktop : conflict: latest is v6
Desktop > Server : create "report (conflicted copy).docx"
Server -> Desktop : v6 and the copy sync to all devices
%%

%%timeline Two offline edits of the same file, and how the server resolves them on reconnect.
[Laptop] 09:00 | Has v5, goes offline
[Desktop] 09:00 | Has v5, goes offline
[Laptop] 10:15 | Edits, saved locally
[Desktop] 11:40 | Edits, saved locally
[Laptop] 13:00 | Reconnects, commit wins: v6
[Desktop] 13:05 | *Reconnects, conflict, conflicted copy
[Desktop] 13:06 | Downloads v6
%%

Notice the order of reconnection decided the outcome, not the order of the edits. The desktop's edit was later in wall-clock time, but the laptop committed first. That is deliberate: device clocks are not trustworthy (lesson 06.05), and "who committed first to the server" is the only order the server can establish reliably.

## Why not last write wins, or merging?
| Approach | What happens | Good for |
| Last write wins | the later commit replaces the earlier one; one set of edits vanishes | settings and data where losing an edit is harmless |
| Conflicted copy | both versions kept as separate files; the user merges | arbitrary files: documents, images, spreadsheets |
| Automatic merge | changes combined (OT, CRDTs, line-based merge) | formats the system understands: plain text, structured documents (15.05) |

%%compare Three ways to resolve two offline edits of one file.
[Last write wins]
v5 -(laptop, desktop)-> Desktop wins
- Laptop edits silently lost
+ Simplest
[*Conflicted copy]
v5 -(laptop)-> v6 + copy
+ Nothing lost
+ Works for any file type
- User must merge by hand
[Automatic merge]
v5 -(both)-> Merged v6
+ No user effort
- Only for formats the service understands
%%

A general file sync service does not understand most file formats, so it cannot merge. A conflicted copy loses nothing and makes the problem visible. Google Docs and similar editors can merge, because they own the format and record each edit as an operation (lesson 15.05). Version history (lesson 13.11) is a second safety net: even if something is overwritten, the previous version is still recoverable for 30 days or more.

! Example: three devices, one file
! Phone, laptop and desktop all have notes.txt at v12. All go offline and all edit.
! Desktop reconnects first: commit based on v12 succeeds, now v13. Laptop reconnects: based on v12, conflict, becomes "notes (Laptop's conflicted copy).txt". Phone reconnects: based on v12, conflict, becomes "notes (Phone's conflicted copy).txt".
! The user ends up with three files. Annoying, but every word typed on every device survives. With last write wins, the phone (last to reconnect) would have overwritten both others, and two devices' work would be gone without a trace.

## Details that matter
- **Record the base version when editing starts.** The base is the version on disk before the local edit, not the version the server has when the device reconnects. The client keeps a local database of the version it last synced for each file.
- **Identical content is not a conflict.** If both devices produced the same file hash (you saved the same downloaded file on both), accept it silently.
- **Delete versus edit.** One device deletes the file while another edits it. Usually the edit wins and the file comes back, because losing work is worse than an undeleted file.
- **Folders and renames.** Renaming a folder on one device while adding a file to it on another must not lose the file. Store files under stable IDs with a parent folder ID, and apply operations to IDs, not paths. The rename changes one row; the new file still points at the folder's ID.
- **Many small commits.** Editors save often. The client debounces (waits a second or two after the last change) before uploading, so ten autosaves become one commit.
- **Partial uploads.** If the device dies halfway through uploading chunks, nothing is committed; the old version stays current, and the uploaded chunks are reused next time because they are addressed by hash.

## Failure handling
- **Missed notifications** are covered by the cursor: whenever a device connects or polls, it fetches every change after its cursor, so a lost WebSocket message only delays sync.
- **Server-side races** are handled by the CAS; there is no lock to leak.
- **Orphaned chunks** (uploaded but never committed, or referenced only by expired versions) are found by a garbage collector that counts references, after a grace period long enough for in-flight commits.
- **Corruption** is caught by hashes: a downloaded chunk whose SHA-256 does not match its name is discarded and fetched again.

## Common mistakes
- Defaulting to last write wins for user files.
- Using device timestamps to decide which edit is newer.
- Uploading whole files on every change.
- Treating paths as identity, so renames break things.
- Relying only on push notifications without a cursor-based catch-up.

## In an interview
Explain chunks, hashes and block lists first, because the conflict mechanism sits on the commit step. Then walk the two-device scenario with version numbers on the board: base v5, first commit wins with CAS, second conflicts, conflicted copy, version history. Contrast with last write wins and automatic merging. Ask: which file types matter most (if mostly text, automatic merging becomes attractive), and is shared-folder collaboration in scope (many users conflict far more often than one user's devices)?

> Takeaway: sync uploads only changed, fingerprinted chunks and commits a new version with a compare-and-set that succeeds only if the device's base version is still current. When two offline edits collide, the first commit wins and the second is rejected; since the service cannot merge arbitrary file formats, the second edit is kept as a conflicted copy beside the winning version, so no work is lost, and version history backs that up.

?? When the devices reconnect, each tries to commit its edit stating the version it started from, and the server applies a compare-and-set on the file's version number. The first device's base version is still current, so its commit becomes the new version. The second device's base is now out of date, so its commit updates nothing and the server reports a conflict instead of overwriting. Because a sync service cannot merge arbitrary file formats, the client keeps both: the first edit stays as the file, the second is saved alongside as a "conflicted copy", the device downloads the winning version, and both files sync to every device for the user to reconcile. Last write wins would silently lose one edit, device clocks are not used to decide, and version history can still recover older versions.

## What we are building
A metrics monitoring system in the style of Prometheus, Datadog or Facebook's internal Gorilla: every server and service reports numbers (CPU, memory, request latency, error counts, queue depth, business counters) every few seconds, engineers graph them on dashboards, and alert rules page someone when a service's SLO is in danger (lesson 14.02). It is the system you rely on when everything else is broken, so it must be cheaper and more reliable than the systems it watches.

### Requirements
- **Ingest** metrics: CPU, memory, latency, custom counters, each with labels.
- **Query and graph** them with filters ("only service=checkout"), aggregations (sum across hosts, p99) and time ranges from the last 5 minutes to the last year.
- **Alert** on rules like "p99 latency over 500 ms for 5 minutes", notifying by email, Slack or PagerDuty.
- Dashboards answer within a few seconds even over weeks of data. Alerts fire within **1 minute** of the data arriving.
- Alerting must be reliable even if dashboards are briefly behind. Late and out-of-order points must be handled.

## Numbers
! Example: the raw load
! 500,000 servers each send 100 metrics every 10 seconds: 500,000 x 100 / 10 = 5 million points per second.
! On the wire each point carries labels, so it is 100 to 200 bytes: roughly 1 GB per second of raw ingest, which is why ingestion is batched and compressed.
! Focus on storage for a cluster holding 10 million active series, each sampled every 10 seconds: 1 million points per second, 86.4 billion points a day.
! Stored naively at 16 bytes per point (an 8-byte timestamp and an 8-byte float), one day is 86.4 billion x 16 = 1.4 TB, a year over 500 TB, before any index. Querying the last hour would mean reading 3.6 billion points x 16 bytes = 58 GB.

So the question this lesson answers is: how do you store 10 million series cheaply and still query the last hour fast? The techniques below come mainly from Facebook's Gorilla time-series database (2015) and the Prometheus storage engine.

## What a time series is
A **series** is one metric name with one exact set of labels:

```
http_latency_ms{service="checkout", host="web-17", route="/pay"}
```

Each series is a stream of `(timestamp, value)` points. Change any label value (`host="web-18"`) and it is a different series. Two structures are needed:
- the **points** of each series, stored in time order, compressed;
- an **index** from label values to series IDs (an inverted index, like search in lesson 09.02), so a query for `service="checkout"` can find every matching series quickly.

%%tree How a metrics store organises data: an index from labels to series, and compressed chunks of points per series.
Metrics store
  Label index | inverted
    service=checkout | series 1, 2, 3
    host=web-17 | series 1, 7
  Series 1 | latency, checkout, web-17
    Chunk 10:00 to 12:00 | about 1.4 B/point
    *Open chunk 12:00 | in memory
  Series 2
%%

## Compression: from 16 bytes to about 1.4 per point
Metrics data has strong patterns, and Gorilla's two tricks exploit them.

### Timestamps: delta of delta
Points arrive at a steady interval: 10:00:00, 10:00:10, 10:00:20, 10:00:30. Store the first timestamp in full. Then the **deltas** (differences) are 10, 10, 10, and the **deltas of the deltas** are 0, 0. A zero is stored in **1 bit**. Occasional jitter (a delta of 11, so a delta-of-delta of +1) costs a short prefix plus a few bits. In practice around 96% of timestamps compress to a single bit.

### Values: XOR with the previous value
Consecutive values are often identical (a counter that did not change, a memory gauge) or close. Floating-point numbers that are close share their sign, exponent and leading mantissa bits. XOR two consecutive values:
- if they are equal, the XOR is zero, stored as **1 bit**;
- if they are close, the XOR has many leading and trailing zeros, so you store only the count of leading zeros, the length of the meaningful middle, and those middle bits. If the meaningful bits fall in the same window as the previous point, even the counts are skipped.

%%flow Delta-of-delta timestamps and XOR values shrink a point from 16 bytes to about 1.4.
[Time] 10:00:00, :10, :20, :31 -(deltas 10, 10, 11)-> Delta of delta 0, +1 -(mostly 1 bit)-> *Tiny
[Value] 42.0, 42.0, 42.5 -(XOR with previous)-> 0, few bits -(store changed bits)-> Tiny
%%

Gorilla reported an average of **1.37 bytes per point** instead of 16, about **12 times** smaller. That made it possible to keep the last 26 hours of Facebook's metrics in memory, which in turn made queries over that window tens of times faster than the disk-based store it replaced.

! Example: what compression buys you
! At 1.37 bytes per point, 10 million series at one point per 10 seconds produce 3.6 billion points an hour: 3.6 billion x 1.37 is about 4.9 GB per hour, and about 118 GB per day.
! Uncompressed, the same day would be 1.4 TB. The last hour, 58 GB uncompressed, is 4.9 GB compressed: it fits in RAM on two or three machines with room for replicas.
! A dashboard panel showing one series for the last hour decodes 360 points, about 500 bytes, in microseconds. A panel summing 1,000 hosts decodes 360,000 points, still a few milliseconds.

The trade-off: compressed chunks must be decoded sequentially from the start, so you cannot jump to the middle of a chunk. Chunks are therefore kept short (Prometheus cuts a new chunk every 120 samples), so any time range needs only a few chunk decodes.

## The last hour in memory
Recent data is queried constantly (every dashboard refresh, every alert rule every minute) and is still being written. So:
- Keep the most recent **hours** (2 in Prometheus, 26 in Gorilla) as compressed chunks **in memory**, with one open chunk per series being appended to. The last hour of 10 million series is about 5 GB compressed, which fits on a few machines **sharded by series** (hash of the series' labels).
- A **write-ahead log** (WAL) on disk records each incoming batch before it is acknowledged, so a crash can rebuild the in-memory state by replaying it (lesson 03.08 explains WALs).
- Every couple of hours, finished chunks are written to disk as an **immutable block**: a directory with the compressed chunks, the label index for those series, and metadata. Older blocks are **compacted** into larger ones (2 hours into 6, 6 into 24, and so on) so queries open fewer files.

This is the same shape as an LSM tree (lesson 07.09): an in-memory write buffer, a log for durability, immutable sorted files on disk, and background compaction.

%%layers Tiered storage for metrics: recent data hot and detailed, old data cold and coarse.
*In memory | last few hours, raw, about 1.4 B/point; dashboards and alerts
Local disk blocks | last days, raw, immutable compressed files
Object storage | weeks to a year, 1-minute and 1-hour rollups
%%

## Cheap long-term storage: downsample
Nobody needs 10-second resolution from six months ago, and nobody can see it: a graph 1,000 pixels wide showing six months has one pixel per 4 hours. **Rollups** (downsampling) pre-aggregate old data into coarser points. Keep **min, max, sum and count** per rollup point, not just the average, because averages of averages are wrong when counts differ, and min and max preserve spikes that an average would hide.

| Age | Resolution | Points per series per day |
| last 2 days | raw, 10 s | 8,640 |
| up to 30 days | 1 minute | 1,440 |
| up to 1 year | 1 hour | 24 |

A query for "the last 6 months" reads hourly rollups: about 4,380 points per series instead of 1.5 million. Old blocks go to **object storage**, which costs a few cents per GB per month; retention rules delete beyond a year. Systems such as Thanos, Cortex and Mimir add exactly this layer to Prometheus.

%%bars Storage per day for 10 million series at each stage (log scale).
Raw, uncompressed | 1400 | 1.4 TB
*Raw, compressed | 118 | 118 GB
1-minute rollups | 70 | about 70 GB
1-hour rollups | 1.2 | about 1.2 GB
%%

The 1-minute figure looks high because each rollup point stores four numbers (min, max, sum, count) and compresses less well than raw values, but it is a sixth of the raw point count and lives on cheap storage.

## Cardinality: the real cost driver
Every distinct label combination is a new series, with its own in-memory chunk and index entries. Adding a `user_id` label to a request metric with 10 million users turns one series into 10 million. This **cardinality explosion** is the classic way metrics systems fall over: memory fills, ingestion slows, and queries that touch the metric time out.

! Example: one innocent label
! A team adds `route` to `http_requests_total`, but uses the raw path, so `/orders/123`, `/orders/124` and so on each become a label value. They have 50 hosts, 5 status codes, and 2 million distinct order IDs a day.
! Series created: 50 x 5 x 2,000,000 = 500 million in one day, 50 times the whole cluster's normal 10 million. The ingesters run out of memory within hours.
! With the route template `/orders/:id`, the same metric has 50 x 5 x 1 = 250 series. Per-order detail belongs in logs and traces.

Defences:
- Never put unbounded values (user IDs, request IDs, full URLs, email addresses) in labels.
- Use **route templates** (`/orders/:id`, not `/orders/123`).
- Enforce **limits**: series per metric and per tenant, rejecting or dropping above a cap and alerting the owner.
- Put per-request detail in traces and logs (lesson 14.01), not metrics.

## Ingestion and alerting
%%flow Ingestion buffered through Kafka; alerting reads the hot in-memory tier first.
[Ingest] Agents -(batches every 10 s)-> Gateways -(partition by series)-> Kafka -> *Ingesters (RAM + WAL)
[Store] Ingesters -(2-hour blocks)-> Object storage -(compact, downsample)-> Rollups
[Alert] Rule evaluator -(every 1 min)-> Ingesters -(firing)-> Alert manager
%%

- Ingestion usually goes through a buffer like **Kafka**, so a traffic spike or a slow storage node delays data rather than dropping it. Replicating each series to two or three ingesters protects against losing an ingester's memory.
- Store latency as **histograms** (counts per bucket, such as under 50 ms, under 100 ms, under 250 ms), not averages. Histograms can be added up across hosts, and any percentile can be estimated from them. Averages and precomputed percentiles cannot be combined correctly.
- **Alert rules** such as burn-rate alerts (lesson 14.02) are evaluated every minute against the in-memory tier. Alerting within a minute is exactly what the hot tier makes possible. Alert evaluation gets priority over dashboard queries, and the alerting path should be monitored by something outside the system itself (a "dead man's switch" alert that fires if alerts stop arriving).
- **Late and out-of-order points**: accept points within a small window behind the head of the series (for example 1 hour), and reject older ones, because the open chunk is append-only.

## Common mistakes
- Storing raw points in a general-purpose database row by row.
- Averaging percentiles across hosts.
- Unbounded label values.
- Keeping everything at full resolution forever.
- Alerting from the same cluster without any outside heartbeat check.
- Rollups that keep only the average, hiding spikes.

## In an interview
Do the naive storage calculation (16 bytes per point, 1.4 TB a day), then show how compression, a hot in-memory tier, immutable blocks and downsampling each cut it. Mention cardinality before the interviewer does. Ask: how long must raw data be kept, how many tenants, and what is the alerting latency target?

> Takeaway: compress series with delta-of-delta timestamps and XOR-encoded values (about 1.4 bytes a point instead of 16), keep the last few hours in memory with a write-ahead log for fast dashboards and alerts, write immutable blocks to disk and object storage and compact them, and downsample old data into minute and hour rollups that keep min, max, sum and count. Control label cardinality, because each label combination is another series.

## The goal
Move a 2 TB table (say `orders`) from the old database to a new one while the application keeps running: no maintenance window, no lost writes, no wrong data. The new home might be a new cluster with bigger machines, a different engine (MySQL to PostgreSQL, or to a distributed SQL database), or a sharded layout. The techniques are the same in each case.

This lesson combines three ideas covered earlier: the four-step dual-write migration (lesson 14.05), shadow reads that compare old and new results on live traffic (lesson 14.06), and, for schema changes inside one MySQL server, gh-ost's copy, replay and swap approach. The question asks for the phases, so the lesson is organised around them, with the failure modes of each.

## Why not just copy it?
The naive plan is "stop the app, dump the table, load it into the new database, point the app at it, start the app". It fails on time alone.

! Example: how long does the copy take?
! 2 TB at 100 MB/s is 2,000,000 MB / 100 = 20,000 seconds, roughly 5.5 hours. Throttled to 50 MB/s to protect production, about 11 hours. Building indexes on the target can add hours more.
! A 6 to 12 hour outage for an orders table is not acceptable for most businesses. And while a live copy runs for those hours, the table keeps changing: at 2,000 writes per second, 11 hours is about 80 million changed rows that a one-time copy would miss.
! So the plan must copy in the background and also capture every change made during and after the copy.

## The core idea: change capture plus backfill
Any zero-downtime migration has the same skeleton:
1. Make sure every **new change** reaches the new database from some moment T.
2. Copy the **existing rows** (the backfill) as they were around T, without overwriting newer changes.
3. Prove the two are the same.
4. Move reads, then writes, one reversible step at a time.

%%timeline The phases of a zero-downtime table migration. Every phase before the last can be rolled back.
Day 0 | Prepare: new table, flags
Day 1 | Start change capture
Day 1 to 2 | Backfill 2 TB in batches
Day 3 | Verify with checksums
Day 3 to 10 | Shadow reads, fix mismatches
Day 10 | Switch reads to new DB
Day 12 | *Switch writes (cut-over)
Day 12 to 26 | Bake, old table as fallback
Day 30 | Remove old table and code
%%

## The phases in detail
### 0. Prepare
Create the table in the new database, with the schema and indexes it needs. Make sure the application can connect to both. Put each switch (where reads go, where writes go, whether to shadow-read) behind **feature flags**, so each step is a configuration change that takes seconds and can be reversed in seconds, not a deploy.

### 1. Start capturing changes
From this moment, every insert, update and delete on `orders` must also reach the new database. Two ways:
- **Dual writes in the application**: every write goes to both databases. Simple to understand, but if the second write fails you must retry or record it somewhere, it adds latency, and the two writes are not atomic, so the databases can diverge after a crash between them.
- **Change data capture (CDC)**: read the old database's replication log (MySQL binlog, PostgreSQL logical replication) with a tool such as Debezium and apply each change to the new database. It needs no application changes and catches writes from every source: batch jobs, admin tools, other services, manual fixes. gh-ost uses this approach inside MySQL.

Stripe ramped its dual writes gradually while watching database load, rather than switching them on for all traffic at once.

%%compare Two ways to capture changes during a migration.
[Dual writes]
App -(write)-> Old DB + New DB
+ No extra infrastructure
- Misses writes from other tools
- Not atomic across two databases
[*Change data capture]
Old DB -(binlog)-> CDC -> New DB
+ Catches every writer
+ No app code changes
- Replication lag to monitor
%%

### 2. Backfill
Copy the existing rows in batches by primary key range, for example 10,000 rows at a time: `SELECT ... WHERE id > :last AND id <= :last + 10000`. Three properties are essential:
- **Throttled**: pause when the source's replica lag or CPU rises, so production does not suffer. gh-ost throttles itself on replica lag; your backfill should too.
- **Resumable**: store the last completed key range as a checkpoint, so a crash at hour 7 does not restart from zero.
- **Never overwrite newer data**: a row copied by the backfill may have been changed a second ago through step 1. Use upserts that skip rows that are already newer in the target (compare an `updated_at` or version column), or start CDC from a log position recorded just before the copy, so replay applies later changes on top.

Stripe avoided scanning production at all for one migration: it found the rows to migrate from a database **snapshot** loaded into Hadoop, then wrote them through the normal application path.

! Example: the backfill race
! At 10:00:00.000 the backfill reads order 501 with status `paid` (version 7).
! At 10:00:00.020 the customer cancels. The old database updates order 501 to `cancelled` (version 8), and CDC writes version 8 to the new database at 10:00:00.150.
! At 10:00:00.300 the backfill's batch insert reaches order 501 with its stale copy, version 7. A plain `INSERT ... ON DUPLICATE KEY UPDATE` would overwrite `cancelled` with `paid`: a cancelled order would ship.
! With a guarded upsert (`... UPDATE status = IF(VALUES(version) > version, VALUES(status), status)`), the stale version 7 is ignored and the new database keeps version 8. This single rule is the difference between a safe and an unsafe backfill.

### 3. Verify
Compare **row counts and checksums** per primary key range between the two databases (for example a hash of all rows with IDs 1 to 100,000), and fix differences by re-copying those ranges. Repeat until clean. Stripe re-ran its migration job afterwards to confirm nothing was missing. gh-ost's test-on-replica mode leaves both tables in place so you can compare them before any cut-over.

### 4. Shadow reads
Checksums prove the data matches; shadow reads prove the **application** gets the same answers. With a library like GitHub's Scientist (lesson 14.06), each read runs against both databases, the old result is returned to the user, and any mismatch is logged with both results. Start at 1% of traffic and ramp up. Mismatches reveal subtle issues checksums miss: different collation (sorting of accented characters), different time zone handling, different default ordering when a query has no `ORDER BY`. Continue until mismatches are zero or every one is explained.

### 5. Switch reads
Flip the read flag. The new database now serves reads, while writes still go to both (or to the old one plus CDC). If anything looks wrong, flip it back: the old database is still complete and current.

### 6. Switch writes: the cut-over
Make the new database the one that is written to. This is the riskiest moment, because after it the old database starts to fall behind. Options:
- **With dual writes**: make the new database the primary write (written first, its failure fails the request), then stop writing the old one.
- **With CDC**: briefly pause writes (a few seconds, using the flag), wait for CDC lag to reach zero, flip the write target, and resume. gh-ost does the equivalent with an atomic table rename at **cut-over**, which it can postpone until a quiet moment.
- Optionally run **reverse replication** (new to old) for a while, so a rollback to the old database does not lose the writes made since cut-over.

%%seq Write cut-over with CDC: a few seconds of paused writes, no lost data.
Ops > App : pause writes to orders (flag)
CDC > NewDB : apply remaining binlog events
CDC -> Ops : lag = 0
Ops > App : write target = NewDB, resume
App > NewDB : new writes
NewDB > OldDB : reverse replication (fallback)
%%

Stripe found the write switch the hardest step, because writes were spread across many code paths. It changed them a few hundred lines at a time and made the old data accessor **raise an error** when called, to flush out forgotten callers in tests and staging before they could cause silent divergence in production.

### 7. Bake
Keep the old table intact (and, with reverse replication, current) for days or weeks. Some problems only appear at month-end, during a sale, or when a rare report runs.

### 8. Remove
Drop the old table, the dual-write or CDC pipeline, the shadow-read code and the flags. Only this step is irreversible, which is why it comes last and after a long bake.

%%state Where reads and writes point as the flags change. Each state can return to the previous one until the old table is removed.
[*] -> Old only
Old only -> Capture on : start CDC
Capture on -> Shadow reads : backfill verified
Shadow reads -> Reads on new : no mismatches
Reads on new -> *Writes on new : cut-over
Writes on new -> Old removed : bake complete
Reads on new -> Shadow reads : roll back
%%

## What to watch for
- **Long transactions and locks**: never `SELECT * FROM orders` in one transaction. Batch by key ranges and keep each batch's transaction short.
- **Replication lag** on the old database caused by the backfill's reads and CDC's load.
- **Auto-increment IDs**: the new database must generate IDs above the old maximum, or switch to application-generated IDs (lesson 04.08) before the migration, so the two never hand out the same ID.
- **Foreign keys and joins**: queries that join `orders` with tables still in the old database must be rewritten or served from one side during the transition.
- **Other writers**: batch jobs, admin tools and other services. CDC catches them; application dual writes do not.
- **Capacity**: the new database must take full production load on day 10, not just the backfill. Load test it with replayed traffic.

## Common mistakes
- Backfilling before starting change capture, so writes during the copy are lost.
- Plain upserts in the backfill that overwrite newer rows.
- Skipping verification because "the copy finished without errors".
- Switching reads and writes in the same step.
- Deleting the old table the day after cut-over.
- Deploys instead of flags, so each rollback takes 30 minutes.

## In an interview
List the phases in order, then pick two to go deep: the backfill race (and the guarded upsert) and the cut-over (pause, drain lag, flip, reverse replication). Mention dual writes versus CDC. Ask: who else writes to this table, how much write downtime (if any) is acceptable at cut-over, and are we changing the schema at the same time? (Prefer not to: one change at a time.)

> Takeaway: to move a 2 TB table with no downtime, start capturing changes first (dual writes or CDC), backfill in throttled, resumable batches that never overwrite newer data, verify with checksums, shadow-read with comparison, switch reads, then switch writes with a brief pause or atomic cut-over, keep the old table as a fallback, and only then delete it. Every step before deletion can be rolled back with a flag.

## The interview prompt
"Design Instagram." This lesson is a complete walkthrough of the kind you would give in an interview, following one photo from the moment the user taps "Share" to the moment it appears in a follower's feed. It assembles parts from earlier lessons: presigned uploads (13.01), image variants and CDNs (13.02), the feed design (16.07 and 11.05), and ID generation (04.08). The aim is to show how the pieces connect and where each decision comes from.

### Requirements
- Users **post photos and videos** with a caption.
- Users **follow** other users.
- Users see a **feed** of posts from people they follow, newest first.
- Out of scope: likes, comments, search, stories, direct messages, ranking.

### Non-functional requirements
- **500 million daily users**, **100 million posts a day**.
- Feed loads in under **500 ms**.
- Photos up to 8 MB, videos up to 4 GB.
- A new post may take a few seconds to reach followers' feeds (eventual consistency is fine); the poster should see their own post immediately.
- Media must never be lost once the user sees "posted".

## Back-of-the-envelope numbers
! Example: sizing the system
! Posts: 100 million a day is about 1,200 per second on average, perhaps 3,000 at peak.
! Media storage: if the average upload is 2 MB after on-device compression, and processing creates variants adding about 50%, each post costs about 3 MB. 100 million x 3 MB = 300 TB a day, about 110 PB a year. Object storage is the only sensible home for this.
! Feed reads: 500 million users open the app 10 times a day: 5 billion feed loads, about 58,000 per second on average and 150,000 at peak. Each load returns about 10 posts, so the CDN serves around 1.5 million image requests per second at peak.
! Fan-out: with 200 followers per author on average, 1,200 posts per second become 240,000 feed-list inserts per second.

Three conclusions follow: media bytes must never pass through API servers, the feed must be precomputed because reads dwarf writes, and images must come from a CDN.

## Data model and API
| Entity | Key fields | Store |
| User | user_id, name, avatar_url | relational (sharded) |
| Follow | follower_id, followee_id | relational or graph store, indexed both ways |
| Post | post_id, author_id, caption, media_ids, status, created_at | relational or wide-column, by post_id |
| Media | media_id, post_id, variants, status | with posts |
| Feed list | user_id to list of post_ids | Redis |

```
POST /posts/uploads {type, size}       -> media_id, presigned_url
POST /posts {media_id, caption}        -> post_id
POST /follows {followee_id}            -> 204
GET  /feed?cursor=...                  -> posts with CDN URLs + next cursor
```

**Post IDs** should be unique across shards and roughly time-sortable, so feeds can be sorted by ID. Instagram's own design used 64-bit IDs made of a millisecond timestamp, a logical shard ID and a per-shard sequence (lesson 04.08), generated inside PostgreSQL.

## Step 1: upload the photo
1. The app asks the **post service** to start a post: `POST /posts/uploads {type: photo, size}`. The service checks the user is allowed to post and the size is within limits, then creates a media record with status `pending` and a **media ID**.
2. It returns a **presigned URL** for `raw/{media_id}.jpg` in object storage, valid for perhaps 15 minutes and only for that one key.
3. The phone uploads the file **straight to object storage**. Phones usually resize and compress first, so an 8 MB photo might upload as 1 to 2 MB. Large videos use multipart upload so they can resume (lesson 13.04).

The API servers never handle image bytes. At 3,000 uploads per second of 2 MB each, that is 6 GB per second of traffic you do not have to scale your application tier for.

## Step 2: process the media
1. Object storage emits an "object created" event onto a queue.
2. **Media workers** validate the file (is it really an image, is it within limits), strip location metadata if the user's settings require it, run safety checks, and generate **variants**: a small thumbnail for grids, a few widths (for example 320, 640 and 1080 pixels) for different screens, in modern formats such as WebP or AVIF, which are 25 to 50% smaller than JPEG at the same quality. Videos go through the transcoding pipeline instead (lesson 17.02).
3. Variants are written to object storage under predictable keys (`media/{media_id}/1080w.webp`), and served through a **CDN**.
4. The media record becomes `ready` with its variant keys.

If a worker crashes, the queue redelivers the event and another worker repeats the job. Because the variant keys are deterministic, repeating the work simply overwrites the same objects: the job is idempotent.

%%state A media item's lifecycle. Followers only ever see posts whose media is ready.
[*] -> Pending
Pending -> Uploaded : object created
Uploaded -> Processing : worker picks up
Processing -> *Ready : variants written
Processing -> Failed : invalid file
Pending -> Expired : no upload in 24 h
%%

## Step 3: create a post and fan out
1. The app finalises this post with a caption: `POST /posts {media_id, caption}`. The posts service saves it **once** in the **posts store**, keyed by post ID. If the media is not ready yet, this post is saved with status `processing` and published when the media worker reports `ready`.
2. The posts service publishes an event `post_created {post_id, author_id}`, using a transactional outbox so the event cannot be lost if the service crashes after saving.
3. The **fan-out service** checks the poster's follower count:
   - **Normal author** (say under 100,000 followers): read follower IDs from the social graph in pages of a few thousand and enqueue batches. **Fan-out workers** push this post ID onto the front of each follower's **feed list** in Redis (`LPUSH feed:{user} post_id` then `LTRIM feed:{user} 0 499`), keeping the most recent few hundred.
   - **Celebrity**: no fan-out. Their posts are pulled at read time (the hybrid from lesson 16.07).
4. The poster's own feed and profile get it immediately, so they see it at once even before fan-out finishes (read-your-own-writes).

%%flow From the phone to followers' feeds: bytes, processing, post record, then fan-out of IDs.
[Upload] Phone -(presigned PUT)-> Object storage -(object created)-> *Media workers
[Post] Phone -(caption, media id)-> Post service -(save once)-> Posts store
[Fan-out] Post service -(post_created)-> Queue -(followers in batches)-> Feed lists in Redis
%%

! Example: fan-out for one post
! An author with 2,000 followers posts. The fan-out service reads followers in 2 pages of 1,000 and enqueues 2 messages. Two workers each pipeline 1,000 LPUSH plus LTRIM commands to Redis, which takes about 10 ms per batch.
! Within a second of this post being saved, all 2,000 followers' feed lists contain its ID. A follower who opens the app 3 seconds later sees it at the top.
! A celebrity with 50 million followers posts. Nothing is fanned out. Each of the followers who opens the app in the next hour merges that celebrity's recent posts at read time, a single read of a hot key replicated across cache nodes.

## Step 4: a follower opens the app
1. The **feed service** reads the follower's feed list (post IDs) from Redis, merges in recent posts from celebrities they follow, and takes the newest page of about 10.
2. It **hydrates** the IDs in parallel: post details from a post cache, author names and avatars from a user cache. Posts that were deleted or whose author blocked this follower are dropped here.
3. The response contains **CDN URLs** for the photo variants sized for this device (a 390-pixel-wide phone gets the 640w or 1080w variant, not the original).
4. The phone loads images directly from the nearest CDN edge, usually in tens of milliseconds, and prefetches the next page as the user scrolls.

%%seq A follower's feed request: IDs from the precomputed list, bytes from the CDN.
Follower > Feed svc : GET /feed
Feed svc > Redis : feed list for follower (post IDs)
Feed svc > Posts : recent posts of followed celebrities
Feed svc > Cache : hydrate posts + authors
Feed svc -> Follower : page of posts with CDN image URLs
Follower > CDN : GET photo 1080w.webp
%%

! Example: the latency budget for one feed load
! Redis read of the feed list: 1 ms. Celebrity posts for the 4 celebrities followed: 2 ms, in parallel. Hydration multi-gets to post and user caches: 3 ms. Service overhead and serialisation: 10 ms. Network to the phone: 50 to 150 ms.
! Total time to the JSON response: well under 200 ms, comfortably inside 500 ms. Images then load from the CDN in parallel; the first photo is visible a few tens of milliseconds later.

## Why each choice
- **Presigned upload**: 100 million posts a day of photos and videos would otherwise flow through API servers.
- **Async processing**: the user sees "posted" quickly; thumbnails appear within seconds; a slow image library cannot slow down the API.
- **Fan-out on write for most authors**: reads outnumber writes about 50 to 1, so precomputing feeds makes the 500 ms target easy. Feed lists hold IDs only, so they are small (about 500 IDs x 8 bytes = 4 KB per user).
- **Pull for celebrities**: pushing one post to 300 million feeds would take minutes and enormous write capacity.
- **CDN for media**: the bytes are by far the heaviest part of the feed; edges near users make images load fast and keep origin egress low.

%%compare Two ways to get the photo bytes into storage. Presigned uploads keep API servers out of the data path.
[Through the API]
Phone -(8 MB)-> API servers -> Object storage
- API must scale for 6 GB/s
- Slow uploads hold connections
[*Presigned URL]
Phone -(8 MB, signed PUT)-> Object storage
+ API handles only small JSON
+ Storage scales on its own
- URL must be scoped and short-lived
%%

## Failure handling
- **Upload succeeds but no post is ever created** (the app crashed): the media stays `pending` or `ready` without a post; a cleanup job deletes orphaned media after 24 hours.
- **Media processing fails**: retried a few times, then marked failed; the user is asked to try again.
- **Fan-out worker crash**: the queue redelivers the batch; `LPUSH` of an ID already present would duplicate it, so the feed service deduplicates IDs when reading (or workers check the head of the list first).
- **Redis feed node lost**: rebuild affected users' feeds on demand by pulling recent posts from the accounts they follow.
- **Post deleted**: the ID remains in feed lists, but hydration finds this post gone and drops it.

## Instagram's early lessons
Early Instagram shows how far this simple shape goes. With a handful of engineers and millions of users, the team's principles were **keep it very simple**, **do not reinvent the wheel**, and **use proven technologies**. The stack: Django on Amazon EC2 behind load balancers and nginx; **PostgreSQL** for users and photo metadata, sharded, with streaming replicas; photos stored on **S3** and served through **CloudFront**; **Redis** for the feed and sessions; **memcached** for caching; a task queue for fan-out and other async work; and push notifications through APNs. That is the same shape as this lesson: object storage plus CDN for bytes, a relational store for metadata, Redis feeds and async workers. Lesson 18.01 looks at it more closely.
