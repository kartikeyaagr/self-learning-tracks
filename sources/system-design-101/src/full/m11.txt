## Two hops
Chat, live dashboards, notifications, multiplayer cursors and presence dots all share one shape. Something happens on the server side, and a particular user's screen must change within a fraction of a second. Every real-time feature has two separate hops:
1. **Server to client**: how an update gets from a server down to a user's device. Polling, Server-Sent Events and WebSockets are the options (lesson 11.02).
2. **Source to server**: how the update gets from wherever it was created to **the particular server holding that user's connection**.

The first hop gets most of the attention, but the second is the scaling problem. A WebSocket is a long-lived TCP connection between one device and one specific server process. A plain HTTP request can be answered by any server behind the load balancer, because each request is independent. A pushed message can only be delivered by the one server that holds the socket.

With 100 connection servers and millions of connected users, a message created on server 2 (because the sender's HTTP request happened to land there) must find the one server, say server 7, that holds the recipient's socket. Server 2 doesn't know where the recipient is. This lesson is about how it finds out.

### What a connection server costs
It helps to know the numbers first. An idle WebSocket costs the server a TCP socket, a TLS session and some buffers: typically **10 to 50 KB of memory** depending on the language and buffer sizes. A well-tuned server (Go, Rust, Erlang, or Node with care) holds **50,000 to several hundred thousand** mostly idle connections. Ten million concurrently connected users therefore means something like 100 to 200 connection servers, and the routing problem is "which of 200 machines holds user X right now?", a question whose answer changes every time a phone switches networks.

## Option 1: pub/sub through a broker
Every connection server subscribes to topics for the users or channels it currently holds. Senders publish to a topic; the broker delivers to whichever servers subscribed. Neither side needs to know the other.

%%seq Pub/sub routing: server 7 subscribed on behalf of its connected user, so the broker delivers server 2's publish to it.
Bob > Server 7 : WebSocket connect
Server 7 > Broker : SUBSCRIBE user:bob
Alice > Server 2 : send "hi" to Bob
Server 2 > Database : store message 9001
Server 2 > Broker : PUBLISH user:bob "hi"
Broker -> Server 7 : "hi"
Server 7 -> Bob : push over socket
%%

The topic can be per user (`user:bob`), per conversation (`dm:alice:bob`) or per channel (`channel:general`). Per-channel topics are much cheaper for group chat: a message to a 500-member channel is one publish, delivered once to each server that has at least one member online, instead of 500 publishes.

Redis pub/sub is a common choice: fast, simple and with dynamic subscriptions. But it is **fire-and-forget**: a message published while a subscriber is disconnected is simply gone; there is no buffer and no replay. So the durable copy of each message lives in a database, and clients re-sync on reconnect. Alternatives with persistence (Kafka, NATS JetStream, Redis Streams) let a subscriber resume from an offset, at the cost of more machinery. Kafka in particular is poor at millions of tiny dynamic topics, so it is usually used for the event backbone, not per-user routing.

## Option 2: consistent hashing of users or channels to servers
Instead of a broker, route by hash. Each user (or channel) belongs to a known server on a **consistent hash ring**, a scheme where keys and servers are hashed onto the same circle and each key belongs to the next server clockwise, so adding or removing a server moves only a small fraction of keys (lesson 04.07). A sender's server computes hash(recipient), looks up the owner, and forwards directly. There's no broker hop, and no subscription state, because placement **is** the routing table.

The catch: connection placement must follow the ring. Either the load balancer routes each user's WebSocket to their owner server (which means the load balancer must understand the hash), or a stateless edge tier accepts the connection and forwards to the owner. When servers join or leave, the affected users' connections must move. Discord, which runs on Erlang/Elixir, uses a similar idea: each guild (server community) is a process placed on a node by consistent hashing, and user sessions send events to the guild's process, which fans out to members' sessions.

%%compare Two ways for server 2 to reach the server holding the recipient: ask a broker, or compute the owner.
[Broker pub/sub]
Server 2 -(publish)-> Broker -> Server 7
+ Connections can land anywhere
+ Simple: subscribe on connect
- Extra hop and a broker to scale
- Redis pub/sub drops messages on blips
[Consistent hashing]
Server 2 -(hash user)-> Server 7
+ No broker, one direct hop
+ Owner holds state, e.g. presence
- Placement must follow the ring
- Rebalancing moves connections
[*Both, as at Slack]

%%

## How Slack does it
Slack's real-time messaging architecture combines both ideas. Its components:
- **Channel Servers (CS)**: stateful and in-memory, each owning a subset of channels by **consistent hashing** of the channel ID. At peak, about **16 million channels per host**. Every kind of entity (user, team, file, huddle, channel) has a channel ID, so the same mechanism carries every kind of event.
- **Gateway Servers (GS)**: stateful servers holding users' WebSocket connections and their channel subscriptions, deployed in **multiple regions** so clients connect to one nearby.
- **Admin Servers (AS)**: stateless, sitting between the web app backend and the channel servers.
- **Presence Servers**: track who's online (the green dots); users are hashed to them.
- **Envoy**: the edge proxy and load balancer, terminating TLS.

When a client connects, the gateway fetches the user's channel list from the web app and **subscribes to the channel servers** owning those channels. A message then flows: client → web app (stores it) → admin server → (hash) channel server → every gateway subscribed to that channel → every connected client in that channel.

%%flow A Slack message: the web app stores it and hands it to an admin server, which finds the channel's owner by consistent hashing; that channel server fans out to every subscribed gateway.
Sender -(API)-> Webapp -> Admin server -(hash channel id)-> *Channel server -(to every subscribed gateway, all regions)-> Gateway servers -> Members' sockets
%%

So the channel server plays the broker's role, but each channel has exactly one owner found by hashing, and gateways (which hold connections anywhere) subscribe to owners. Slack reports **tens of millions of connected clients** and delivery across the world within **500 ms**. Consistent hash ring managers replace an unhealthy channel server in **under 20 seconds**, during which delivery for its channels is slower.

## Things every design needs
- **A connection registry or subscriptions.** Something must know which server holds whom: subscriptions in a broker, ownership on a ring, or an explicit registry (`user:bob → gw-7`, in Redis with a TTL refreshed by heartbeats).
- **Reconnect and catch-up.** Connections drop constantly: mobile networks change, laptops sleep, servers deploy. The client reconnects, probably to a different server, and asks for everything since its last seen message ID. Real-time delivery is an **optimisation on top of a durable store**, never the only copy.
- **Heartbeats.** Ping frames every 20 to 60 seconds detect dead connections (a phone that lost signal doesn't send a TCP close) and stop proxies and NAT gateways from closing idle connections, many of which drop idle TCP flows after 60 to 350 seconds.
- **Load balancing and draining.** WebSockets are long-lived, so connections don't rebalance by themselves after a deploy or scale-out. Servers drain gradually (stop accepting, then close existing connections in batches over minutes), and clients reconnect with exponential backoff and **jitter** (random delay) so they don't all return at once.
- **Ordering and duplicates.** A message may arrive by push and again in the catch-up fetch. Clients deduplicate by message ID and order by server-assigned sequence.

%%state The client side of a real-time connection: every drop leads back through a catch-up fetch before the client trusts pushes again.
[*] -> Disconnected
Disconnected -> Connecting : start or backoff timer fires
Connecting -> Disconnected : failed, retry later
Connecting -> Catching up : socket open, subscribed
Catching up -> *Live : fetched messages since last ID
Live -> Disconnected : heartbeat missed
%%

! Example: a direct message, online and offline
! Bob is connected to gateway server 7, which subscribed to `user:bob` (or to the DM channel's channel server). Alice sends "hi" through server 2's API. Server 2 writes the message to the database with ID 9001, then publishes it. The broker or channel server pushes it to server 7, which writes it to Bob's socket. Bob's client stores 9001 as its last seen ID. End to end: a database write (5 ms), a publish (1 ms), a broker hop (1 ms), a socket write and network transit (20 to 100 ms).
! If Bob was offline, nothing is pushed; the publish reaches no subscriber and disappears, which is fine. When he reconnects (to gateway 12 this time), his client says "give me everything after 8,950", fetches 9001 and the rest from the database, then switches to live pushes. A mobile push notification (APNs or FCM) can be sent in parallel to wake his phone.

! Example: a deploy without a reconnect storm
! A gateway holds 80,000 connections and must restart. If it closes all of them at once, 80,000 clients reconnect within a second, each doing TLS, authentication, subscription and a catch-up query: 80,000 database queries in a burst, enough to hurt.
! Instead, the server stops accepting new connections and closes its existing ones in batches of 1,000 every 3 seconds, over 4 minutes. Clients reconnect after a random delay of 0 to 5 seconds. The other gateways absorb about 330 new connections per second, smoothly.

%%timeline A gateway server failure: clients notice through heartbeats, reconnect elsewhere with jitter, and fill the gap from the database.
0 s | Gateway 7 crashes, 60,000 sockets die
0 to 30 s | Clients miss heartbeat, mark disconnected
30 to 40 s | *Reconnect to other gateways with random backoff
31 to 45 s | Gateways resubscribe to channels for new users
32 to 50 s | Clients fetch messages since last seen ID
50 s | *All clients live again, no message lost
%%

## Common mistakes
- **Treating push as delivery.** If the database write happens after the publish, or not at all, a disconnected user loses the message. Store first, then publish.
- **One topic per user for group messages.** Publishing a 10,000-member channel message to 10,000 user topics is 10,000 publishes. Publish once per channel.
- **No jitter on reconnect.** Synchronised retries turn a small failure into a self-inflicted outage.
- **Sticky sessions as the routing plan.** Stickiness only keeps one client on one server; it doesn't tell server 2 where Bob is.
- **Forgetting the idle timeouts** of load balancers and NAT, which silently kill quiet connections.

## In an interview
Draw the two hops explicitly. Then say: "connection servers subscribe, on behalf of their connected users, to channel topics in a pub/sub layer (or channels are owned by servers found by consistent hashing, as at Slack); the sender's server stores the message and publishes; the broker forwards to subscribed servers; on reconnect, clients fetch from the database since their last seen ID". Mention sizing (50,000 to 100,000+ connections per server), heartbeats, and draining with jittered reconnects.

> Takeaway: real-time delivery has two hops; the hard one is getting a message from the server where it was created to the server holding the recipient's socket. Use pub/sub (servers subscribe for their connected users or channels) or consistent hashing of channels to owner servers, or both as Slack does, and always back it with a durable store, heartbeats, and catch-up on reconnect.

## The problem: HTTP can't speak first
Plain HTTP is request-response. The client asks, the server answers, and the exchange is over. The server has no way to say "something changed" unless the client happens to be asking at that moment. Every real-time feature (a chat message, a goal in a match, a price tick, a notification badge) needs a way around that.

There are four common techniques. They differ in who opens what, how long it stays open, which direction data flows, and how they behave with the proxies, load balancers and flaky mobile networks in between. Choosing well depends on one main question: does the client need to send frequent real-time messages too, or does it mostly listen?

%%matrix The four ways to get updates from server to browser, compared on the properties that decide most designs.
Technique | Server push | Client sends on same channel | Latency | Works through any HTTP proxy | Server cost when idle
Short polling | no, client pulls | yes, each poll is a request | up to the poll interval | yes | high, constant requests
Long polling | partial, emulated | partial, separate requests | low, plus reconnect gap | yes | medium, held requests
Server-Sent Events | yes | no, use normal POSTs | low | yes, if not buffered | low, one idle stream
WebSockets | yes | yes, both directions | lowest | partial, needs Upgrade support | low, one idle socket
%%

## Short polling
The client asks "anything new?" every few seconds: `GET /scores?since=118`. The server answers immediately, usually with nothing.

It is simple and works everywhere, but it's wasteful and slow. Latency averages half the polling interval, and most requests are empty. Every poll carries full HTTP headers (often 500 to 1,000 bytes with cookies), a TLS record, and a trip through the load balancer, auth middleware and application.

! Example: what polling costs at scale
! 1 million fans follow a match, polling every 5 seconds. That's 200,000 requests per second, all day, whether or not anything happens.
! At about 800 bytes of request headers plus a small response, that's roughly 200 MB per second of traffic, and 200,000 authenticated requests per second hitting the application. A football match has perhaps 10 goals and a few hundred minor events in 2 hours, so over 99.9% of those requests return "nothing new".
! And a goal still takes on average 2.5 seconds (and up to 5) to show up. Halving the latency doubles the cost.

## Long polling
The client asks, and the server **holds the request open** until there's data or a timeout (often 20 to 30 seconds), then responds. The client immediately sends a new request. When nothing is happening, each client costs one idle request every 30 seconds instead of six; when something happens, it arrives almost instantly.

%%seq Long polling: the request waits at the server until there is news, then the client immediately asks again.
Client > Server : GET /updates?since=118
Server > Server : hold up to 30 s
Server -> Client : 200: goal, id 119 (after 12 s)
Client > Server : GET /updates?since=119
Server > Server : hold, nothing happens
Server -> Client : 204 no content (after 30 s)
Client > Server : GET /updates?since=119
%%

Its weaknesses: one message per response, so bursts cause a flurry of request cycles; a **gap** between the response and the next request in which events must be buffered server-side (the `since` parameter makes that safe); and held requests occupy server resources and can hit proxy timeouts. It was the backbone of early web chat (Facebook chat, Gmail) and remains a robust fallback when nothing else gets through a corporate proxy.

## Server-Sent Events
SSE is a **one-way** channel: one HTTP response that never ends, into which the server writes events whenever it likes. The client cannot send events back over it; it uses ordinary HTTP requests for that. The browser API is `EventSource`, and the server responds with `Content-Type: text/event-stream`. The format is plain UTF-8 text lines, with a blank line ending each event:
- `data:` the payload (several `data:` lines join with newlines)
- `event:` a named event type, so the client can register different handlers
- `id:` sets the last event ID
- `retry:` reconnection delay in milliseconds
- Lines starting with `:` are comments, useful as **keep-alive** pings.

The browser **reconnects automatically** if the connection drops, and sends the last ID it saw in a `Last-Event-ID` header, so the server can resume from where the client left off. That gives you reliable delivery semantics almost for free.

%%seq An SSE stream that survives a network change: the browser reconnects by itself and the Last-Event-ID header lets the server resume.
Browser > Server : GET /matches/42/stream (Accept: text/event-stream)
Server -> Browser : 200, text/event-stream
Server -> Browser : id: 118, event: goal, data: 2-1
Server -> Browser : ": ping" every 15 s
Browser > Browser : Wi-Fi to 4G, connection drops
Browser > Server : GET /matches/42/stream, Last-Event-ID: 118
Server -> Browser : id: 119, event: card, data: yellow, 71 min
%%

The main warnings:
- **Connection limits on HTTP/1.1.** Browsers allow only about **6 connections per browser and domain**, across all tabs. Six tabs with an SSE stream each and the seventh tab's ordinary requests hang. Over **HTTP/2** the streams are multiplexed on one connection and the limit is negotiated by the server (commonly 100 or more streams; nginx defaults to 128), so serve SSE over HTTP/2.
- **Buffering proxies.** A proxy that buffers responses holds events until the buffer fills, destroying the real-time behaviour. For nginx, send `X-Accel-Buffering: no` or disable `proxy_buffering`; also disable response compression buffering.
- **Text only, no custom headers.** SSE carries UTF-8 text (send JSON; binary must be encoded). The `EventSource` API can't set an `Authorization` header, so authenticate with cookies or a short-lived token in the URL.

## WebSockets
WebSockets give a **two-way interactive session**: either side can send messages at any time without polling. The connection starts as an HTTP/1.1 request and is **upgraded** through a handshake:
1. The client sends `GET /chat` with `Upgrade: websocket`, `Connection: Upgrade`, `Sec-WebSocket-Version: 13` and a random `Sec-WebSocket-Key`.
2. The server replies `101 Switching Protocols` with `Sec-WebSocket-Accept`, a hash of the key combined with a fixed GUID, proving it understood the WebSocket protocol rather than being a confused cache.
3. From then on, the TCP connection carries WebSocket **frames**, not HTTP. Each frame has a 2 to 14 byte header; frames from the client are masked (XOR with a random key) so that intermediaries can't be tricked into caching attacker-chosen bytes.

Frame overhead is tiny compared with HTTP headers, so for frequent small messages (a typing indicator, a cursor position 30 times a second, a game input) WebSockets are by far the most efficient.

The costs:
- **Stateful connections** on the server, and the routing problem of lesson 11.01.
- **Infrastructure support.** Every proxy and load balancer in the path must support the Upgrade and long idle connections. Most do now, but some corporate proxies still break it, which is why libraries such as Socket.IO fall back to long polling.
- **No built-in reconnection or resume.** You write reconnect, backoff, heartbeats and "resume from message ID" yourself.
- **No backpressure in the browser API.** If messages arrive faster than the page can process them, memory or CPU can be exhausted. The newer `WebSocketStream` and WebTransport APIs address that.
- An open WebSocket can stop a page entering the browser's back/forward cache, so close it when the page is hidden for long.

## Choosing
%%tree A quick decision: who sends, how often, and how much infrastructure can you change?
Need server push?
  No, data changes rarely | short polling or plain fetch
  Yes
    Client also sends often, low latency? | chat, games, editors
      *WebSockets
    Mostly server to client? | scores, feeds, notifications
      *Server-Sent Events
      Hostile proxies or very old clients | long polling fallback
%%

For **live sports scores**, choose **SSE**:
- Data flows one way: the server pushes score changes; the fan doesn't send anything in real time. Anything they do send (a prediction, a reaction) is an ordinary POST.
- It is plain HTTP, so it passes through existing load balancers, CDNs and proxies, works with HTTP/2 multiplexing, and uses your existing auth cookies.
- Automatic reconnection with event IDs comes free, which matters on mobile networks that drop every few minutes.
- Updates are infrequent (a few per minute), so long polling would also work; WebSockets' bidirectional channel and custom protocol would be complexity without benefit.

WebSockets win when the client also sends frequently and with low latency: chat with typing indicators, multiplayer games, collaborative editing, trading terminals.

+ Plain HTTP, auto-reconnect, resume by ID
- Fans' own actions go as POSTs
[Collaborative editor: WebSockets]
Messages both ways, every keystroke
+ Both sides send tens of messages per second
+ Tiny frame overhead
- Must build reconnect and resume yourself
%%

! Example: one SSE stream for a match
! The client runs `new EventSource("/matches/42/stream")`. The server sends `id: 118`, `event: goal`, `data: {"home":2,"away":1,"min":67}`, followed by a blank line. Every 15 seconds it sends a `:` comment line to keep proxies and mobile carriers from timing out the idle connection.
! The phone switches from Wi-Fi to 4G and the connection drops. The browser waits the `retry` interval (say 3 seconds), reconnects and sends `Last-Event-ID: 118`, so the server sends anything after 118 from a short per-match event buffer in Redis. The fan sees nothing odd.
! Server side, 1 million fans are 1 million idle HTTP/2 streams spread over, say, 20 servers holding 50,000 each. A goal is one publish, fanned out by each server to its 50,000 streams: a few hundred bytes each, done in well under a second.

## Common mistakes
- **WebSockets by default.** Many features are server-to-client only; SSE is simpler and plays better with HTTP infrastructure.
- **SSE over HTTP/1.1** with several tabs open, hitting the 6-connection limit.
- **Forgetting keep-alives.** Idle connections are silently closed by NATs and load balancers.
- **No resume.** Whatever the transport, a reconnect must fetch what was missed, by event or message ID.
- **Polling at 1 second "to be safe".** At scale, that is a self-inflicted load test.

## In an interview
Name the choice and justify it with direction and frequency: "scores flow one way a few times a minute, so SSE over HTTP/2: plain HTTP, auto-reconnect with Last-Event-ID, cheap idle connections; reactions go as POSTs." Then mention the second hop (lesson 11.01): how the score update reaches the server holding each stream.

> Takeaway: short polling is simplest and wasteful; long polling emulates push one message at a time; SSE is a one-way push stream over plain HTTP with built-in reconnection and resume; WebSockets are a full two-way channel with tiny frames but more to build and operate. Use SSE when the server pushes and the client mostly listens, and WebSockets when both sides talk often.

## What has to be fast
A social graph is a set of directed edges: "A follows B". (Friendships, as on Facebook, are undirected: two edges, or one edge stored in both directions. Follows, as on Twitter, Instagram or GitHub, are directed: A can follow B without B following A.) The graph itself is simple. What makes it a design problem is that two opposite queries must both be fast, at enormous volume:
- **Who do I follow?** The outgoing edges of A. Needed to build A's feed on read, to show A's "following" list, and to answer "does A follow B?" when rendering a follow button.
- **Who follows me?** The incoming edges of B. Needed to deliver B's posts to followers (fan-out on write, lesson 11.05), to show follower counts and lists, and to notify followers.

Twitter-scale numbers show how heavily these queries are used: **100 million active users**, **500 million tweets per day**, an average of **10 fan-out deliveries per tweet** (5 billion per day), and **250 billion reads per month**, about **100,000 reads per second** and **60,000 fan-out deliveries per second**. Every tweet triggers a "who follows whoever wrote this?" lookup, and every timeline needs "who does this user follow?".

The access pattern is extremely read-heavy. People follow or unfollow a few times a week; the graph is read on every tweet and every feed load. That asymmetry justifies spending extra work and storage on writes to make both reads cheap.

## A relational model
```
CREATE TABLE follows (
  follower_id  BIGINT NOT NULL,
  followee_id  BIGINT NOT NULL,
  created_at   TIMESTAMP NOT NULL,
  PRIMARY KEY (follower_id, followee_id)
);
CREATE INDEX follows_by_followee ON follows (followee_id, created_at DESC, follower_id);
```

How each piece earns its place:
- The **primary key** (follower_id, followee_id) is a B-tree sorted by follower first. "Who does A follow?" is a range scan over the entries starting with A, reading exactly A's edges and nothing else. The same key answers "does A follow B?" as a single point lookup, and it **prevents duplicate follows** for free: inserting (A, B) twice violates the key.
- The **second index** (followee_id, ...) is the same data sorted the other way. "Who follows B?" becomes a range scan on followee_id = B.
- Putting created_at in the index lets "most recent followers first" come straight off the index in order, with keyset pagination (lesson 04.12) for long lists, rather than sorting millions of rows.
- An `ON CONFLICT DO NOTHING` insert makes "follow" idempotent: a double tap or a retried request is harmless.

%%flow One edge, two access paths: the primary key serves "following", the reverse index serves "followers".
[Who A follows] follower_id = A -(primary key scan)-> *B, C, D
[Who follows B] followee_id = B -(reverse index scan)-> *A, E, F
%%

On one machine this is all you need, and it goes surprisingly far. Each edge costs roughly 24 bytes of key data per index plus overhead, so a billion edges is on the order of 100 GB across the table and its index, which a single large PostgreSQL server can hold with the hot parts in memory.

### Why not a graph database?
Graph databases (Neo4j and similar) shine at **multi-hop** traversals: friends of friends, shortest paths, pattern matching across many hops. Social products mostly need **one hop**: my followees, my followers, do we follow each other, whom do we both follow. One-hop queries on sorted adjacency lists are exactly what a B-tree or a key-value store does well, and those systems shard and replicate in well-understood ways. That is why large social networks built their own simple adjacency stores (lesson 11.04) rather than adopting general graph engines. Multi-hop features ("people you may know") are usually computed offline in batch jobs.

## When it no longer fits on one machine
Sharding breaks the neat picture. A **shard key** decides which machine each row lives on. If you shard the follows table by follower_id, all of A's outgoing edges sit together on A's shard, so "who does A follow?" hits one shard. But B's incoming edges are scattered: every shard may hold some follower of B. "Who follows B?" must ask **every** shard (a scatter-gather) and merge the answers. Shard by followee_id instead, and the opposite query becomes the scattered one.

%%matrix Which shards each query touches under each layout. Storing the edge twice is the only layout where both common queries hit one shard.
Layout | Who A follows | Who follows B | Does A follow B | Writes per follow
One table, sharded by follower | yes, one shard | no, every shard | yes, one shard | 1
One table, sharded by followee | no, every shard | yes, one shard | yes, one shard | 1
Two tables, each sharded by its own key | yes, one shard | yes, one shard | yes, one shard | 2
%%

Scatter-gather is tolerable for a rare admin query, but not for a lookup that runs 60,000 times per second for fan-out. With 256 shards, each fan-out lookup would become 256 queries, most returning nothing, and the slowest shard sets the latency.

The standard fix is to **store each edge twice**: once in a `following` table sharded by follower_id, and once in a `followers` table sharded by followee_id. Each query hits exactly one shard. Twitter's FlockDB did exactly this (lesson 11.04).

%%tree Each follow edge is written to two places: the following list on the follower's shard and the followers list on the followee's shard.
Edge: A follows B
  following table | sharded by follower_id
    *Shard of A | row (A, B, time)
  followers table | sharded by followee_id
    *Shard of B | row (B, A, time)
%%

In DynamoDB the same idea looks like this: a Follow table with partition key `userFollowing` and sort key `userFollowed`, plus a **global secondary index** with the keys swapped. The GSI is DynamoDB maintaining the second copy for you, asynchronously, so a just-made follow can take a moment to appear in the follower list. In Cassandra, you'd create two tables (`following_by_user` and `followers_by_user`) and write both, often with a logged batch.

### Keeping two copies consistent
Two writes to two shards can't usually be one local transaction. If the first succeeds and the second fails, A appears in B's followers but B isn't in A's following, or vice versa. Options:
- **Transactional outbox**: write the first copy and an "edge created" event in the same local transaction on A's shard; a relay publishes the event, and a consumer writes the second copy, retrying until it succeeds (lesson 08.03 covers the outbox pattern). The copies converge within seconds.
- **Idempotent writes in both places**, driven by a queue that retries until both exist. Because inserts are keyed by (follower, followee), retries are harmless.
- **Periodic repair**: a background job compares the two copies for recently changed users and fixes differences.

%%seq A follow with a transactional outbox: the first copy and an event commit together, and a consumer writes the second copy, retrying until it exists.
Client > Graph API : follow(A, B)
Graph API > Shard of A : BEGIN; insert following(A, B); insert outbox event; COMMIT
Shard of A -> Graph API : ok
Graph API -> Client : 200 following
Relay > Shard of A : read outbox
Relay > Queue : edge_created(A, B)
Queue > Followers writer : edge_created(A, B)
Followers writer > Shard of B : upsert followers(B, A); counts +1
%%

Unfollow is the same, with deletes (or a "removed" state, so that late-arriving creates can't resurrect a deleted edge: compare timestamps, or keep tombstones).

## Counts and hot users
- **Follower counts** shouldn't be computed with `COUNT(*)` over millions of rows on every profile view. Keep a counter per user (`follower_count`, `following_count`), updated with each follow and unfollow, and accept that it may be briefly off. For a celebrity gaining thousands of followers a minute, batch the counter updates as in lesson 10.01.
- **Celebrities** have huge follower lists. Their incoming-edge list may be hundreds of millions of rows. Page through it with a cursor, never load it all, and treat them specially in fan-out (lesson 11.05). Their followers list may also need to be split across several partitions so one shard isn't overwhelmed.
- **Follow limits.** Many networks cap following (Twitter famously at 5,000 for most accounts, with exceptions), which bounds the "who do I follow" side and protects against spam bots.
- **Cache the hot lists.** Keep follower lists in a memory cache (or Redis sets) for the fan-out service, and only keep feeds for users active in the last 30 days.

! Example: sizing the graph
! 300 million users, an average of 200 followees each: 60 billion edges. Stored twice: 120 billion rows. At about 30 bytes per row with key and timestamp, plus storage overhead, call it 50 bytes: 6 TB.
! Spread over 256 shards: about 23 GB per shard, comfortably in memory on each. Reads: 100,000 per second spread by user ID is under 400 per second per shard, trivial. Writes: if each user changes a follow twice a week, that is 600 million per week, about 1,000 per second, so 2,000 row writes per second including both copies, about 8 per shard per second.

! Example: A follows B
! Single database: insert (A, B, now) into follows; both indexes update in the same transaction, and the follower and following counters are incremented in the same transaction.
! Sharded: write (A → B) into following on A's shard and (B ← A) into followers on B's shard, plus increment A's following count and B's follower count. Use the outbox so a failure between the two writes is retried until both exist. If B is a celebrity gaining 5,000 followers a minute, B's counter is incremented by a batching consumer once a second instead of 5,000 times.

## Common mistakes
- **One table, one shard key, then scatter-gather.** Fine at 10 shards in a demo, unworkable at hundreds under fan-out load.
- **COUNT(*) for follower counts.** A celebrity's profile view should not scan 100 million rows.
- **Non-idempotent follow.** Without the (follower, followee) key, double taps create duplicate edges and inflate counts.
- **Loading whole follower lists.** Always paginate; a 100-million-follower list is gigabytes.
- **Reaching for a graph database for one-hop queries.** It adds a new operational system for queries a key-value layout handles better.

## What FlockDB was
FlockDB is the distributed graph database Twitter built to store its social graph: who follows whom, who blocks whom, and similar relationships. It (now archived) stored **adjacency lists** for high-throughput, low-latency online use, on top of ordinary MySQL databases, with a sharding framework called **Gizzard** in front. As of April 2010, Twitter's cluster held **over 13 billion edges** and sustained peaks of **20,000 writes per second** and **100,000 reads per second**.

It is worth studying not because you will run FlockDB, but because its design is the standard answer to "how do I store a huge social graph", and every choice in it is a deliberate trade-off you can reuse.

## Goals and non-goals
It was explicit about scope:
- **Goals**: a high rate of add, update and remove operations; potentially complex **set arithmetic** queries; **paging** through result sets with millions of entries; archiving edges and restoring them later; horizontal scaling including replication; online data migration.
- **Non-goals**: **multi-hop graph traversal** ("friends of friends of friends") and automatic shard migration.

It described itself as much simpler than general graph databases such as Neo4j, because it solves fewer problems. Twitter's online graph queries are almost all one hop: "who follows X?", "does A follow B?", "whom do A and B both follow?". A multi-hop traversal on a graph of billions of edges touches an unpredictable number of shards and can take seconds; a one-hop query touches one sorted list. Choosing not to support multi-hop queries is what let the system be fast, predictable and easy to shard.

## The edge model
Each edge has:
- a 64-bit **source ID** and 64-bit **destination ID**;
- a **state**: normal, removed, or archived;
- a 32-bit **position** used for sorting. For a follow ("Nick follows Robey"), the position is the time the follow happened, so follower lists come back newest first.

The (source, destination) pair is unique; state and position can change. Note what is missing: there are no properties, labels or weights beyond position. An edge is a fact that A relates to B, with a state and a sort key. Different relationship types (follows, blocks, mutes) are separate graphs.

### Edge states
Deleting a row is a poor fit for a distributed system with retries and replication: a delayed "add" that arrives after a "delete" would resurrect the edge, and a deleted row leaves no trace for auditing. So FlockDB never hard-deletes in normal operation. It changes state, and every change carries a timestamp, so a later operation always wins regardless of arrival order.

%%state The lifecycle of one edge: unfollowing marks it removed, suspending an account archives its edges, and reinstatement restores them.
[*] -> *Normal
Normal -> Removed : unfollow or unblock
Removed -> Normal : follow again
Normal -> Archived : account suspended or deactivated
Archived -> Normal : account restored
%%

**Archived** edges go into "cold sleep". When an account is suspended, its thousands of edges are archived rather than deleted, so they vanish from every list and count. If the account is reinstated, they are restored in one operation, and the person gets their followers back.

## Stored twice, forward and backward
Edges are stored **in both directions**, so they can be queried by source or by destination. For example, node 134 follows node 90. That produces a forward row (134 → 90) and a backward row (90 ← 134).

%%flow FlockDB writes each edge twice so both directions are a single-shard lookup.
"134 follows 90" -(forward row, stored with 134)-> *134: 90, ... -(backward row, stored with 90)-> *90: 134, ...
%%

Why twice? Because of sharding. At billions of edges, the graph is split across many MySQL databases. Gizzard decides which shard a row lives on from its **first ID**, through a forwarding table that maps ranges of IDs to shards:
- The forward copy of (134 → 90) has first ID 134, so it sits on 134's shard.
- The backward copy (90 ← 134) has first ID 90, so it sits on 90's shard.
- "Whom does 134 follow?" reads only 134's forward rows, on one shard, already sorted.
- "Who follows 90?" reads only 90's backward rows, on one shard, already sorted.

%%tree Where the two copies of "134 follows 90" live: each copy is placed by its first ID, so each direction of lookup reads one shard.
Gizzard forwarding table | ID range to shard
  Shard 7, IDs 100 to 199
    *forward 134 → 90 | whom 134 follows
    forward 134 → 412
  Shard 3, IDs 0 to 99
    *backward 90 ← 134 | who follows 90
    backward 90 ← 57
%%

With a single copy, one of those queries would have to visit **every** shard. For someone with 50 million followers, scanning every shard for each tweet's fan-out would be impossible at 100,000 reads per second: each tweet would become hundreds of shard queries, most finding a handful of rows, and the slowest shard would set the latency of every delivery.

The cost is double the storage and two writes per change, which must be kept consistent. Since follows change far less often than they are read (20,000 writes per second at peak against 100,000 reads, and the reads are much heavier, often returning thousands of rows), the trade is clearly worth it.

## How writes stay consistent
Two copies on two shards, written by a distributed system with failures, will sometimes disagree. Gizzard's approach is simple and worth copying: **every write must be idempotent and commutative**.
- **Idempotent**: applying the same operation twice gives the same result. "Set edge (134, 90) to normal at time T" can be retried safely.
- **Commutative**: operations can be applied in any order and still converge. Because each operation carries a timestamp and the newer state wins, "remove at T2" and "add at T1" give "removed" whichever arrives first.

With those two properties, the system doesn't need distributed transactions. Writes go to both shards (and their replicas); any that fail go to an **error queue** and are retried later, and the copies converge. A short window where the forward and backward copies disagree is acceptable for a follow graph.

%%seq An unfollow whose backward write fails at first: the retry queue applies it later, and timestamps make the late write safe.
Graph service > Shard of 134 : set (134 → 90) removed at T2
Shard of 134 -> Graph service : ok
Graph service > Shard of 90 : set (90 ← 134) removed at T2
Shard of 90 -> Graph service : timeout
Graph service > Error queue : retry backward write, T2
Error queue > Shard of 90 : set (90 ← 134) removed at T2
Shard of 90 -> Error queue : ok, T2 newer than T1, applied
%%

## Set operations and paging
Because each node's adjacency list is stored sorted, one-hop set queries are merges of sorted lists, the same trick as intersecting posting lists in search (lesson 09.03):
- **Intersection**: "people A follows who also follow B" (for "followed by people you know").
- **Difference**: "people who follow me whom I don't follow back".
- **Union**: "everyone either of these two accounts follows".
- **Paging**: return 100 edges at a time ordered by position, with a cursor (the last position seen), so a 50-million-follower list is never loaded at once.

! Example: intersecting two sorted lists
! A follows (sorted by ID): 3, 9, 14, 22. B follows: 9, 17, 22. Walk both with two pointers:
! 3 vs 9: 3 is smaller, advance A. 9 vs 9: match, output 9, advance both. 14 vs 17: advance A. 22 vs 17: advance B. 22 vs 22: match, output 22. A is exhausted: done.
! Result: both follow 9 and 22. The cost is proportional to the lengths of the two lists, with no random lookups. For large lists on different shards, each shard streams its sorted list and the merge happens in the query service.

%%compare FlockDB's narrow design against a general graph database for a social network's online queries.
[*FlockDB-style adjacency store]
Sorted adjacency lists, each edge twice
+ One-hop queries hit one shard
+ Set arithmetic by merging sorted lists
+ Simple sharding on MySQL
- No multi-hop traversal
- Double storage and writes
[General graph database]
Nodes, edges, properties, traversals
+ Friends of friends, paths, patterns
+ Rich queries in one language
- Traversals cross shards unpredictably
- Hard to shard at billions of edges
%%

! Example: blocking
! A blocks B: write edge (A → B) in the "blocks" graph, forward copy on A's shard and backward copy on B's shard. When B loads A's profile, the service checks the backward rows for B ("who blocks B?") or the forward rows for A, each a one-shard point lookup.
! When A unblocks, the edge's state becomes removed rather than being deleted, so the change can propagate safely even if an earlier "block" write is still sitting in a retry queue (the newer timestamp wins), and the history is auditable.

! Example: sizing a FlockDB-style cluster
! 13 billion edges stored twice is 26 billion rows. At roughly 30 bytes of row data (two 8-byte IDs, a 4-byte position, state, timestamps) plus MySQL index overhead, budget 60 bytes per row: about 1.6 TB.
! Spread over, say, 64 shards with replicas, that's 25 GB per shard, mostly in the buffer pool. 100,000 reads per second is about 1,600 per second per shard; 20,000 edge writes per second is 40,000 row writes (both copies), about 600 per second per shard. Ordinary MySQL numbers, which was the point.

## Lessons to reuse
- **Restrict the query model** to what the product needs (one hop), and the storage design becomes simple.
- **Store data the way you query it**, even if that means duplicating it.
- **Make writes idempotent and commutative** with timestamps, so retries and reordering are harmless and you can avoid distributed transactions.
- **Soft-delete with states**, so late writes can't resurrect deleted data and accounts can be restored.
- **Paginate everything** that can be large.

## In an interview
If asked to store a social graph at scale, describe the FlockDB layout: edges with (source, destination, state, position), stored forward on the source's shard and backward on the destination's shard, sorted by position so lists are pageable newest first. Explain the trade (double storage and writes, cheap because writes are rare) and how consistency works (timestamped, idempotent writes with a retry queue). Say explicitly that multi-hop queries are out of scope online and computed offline.

> Takeaway: FlockDB stored a huge, one-hop social graph as sorted adjacency lists, each edge written twice (forward under the source, backward under the destination) so "who does X follow" and "who follows X" each hit one shard. Timestamped, idempotent, commutative writes with soft-delete states kept the two copies consistent without distributed transactions, and it deliberately skipped multi-hop traversal in exchange for very high throughput.

?? Because the graph was split across many shards by each row's first ID, a lookup is only cheap if all the rows it needs sit together on one shard. Storing the forward edge with the source and the backward edge with the destination makes both "whom does X follow" and "who follows X" single-shard, sorted, pageable reads. With a single copy, one of those two common queries, including the follower lookup needed to fan out every tweet, would have to scatter to every shard and wait for the slowest. The cost is double storage and two writes per change, which is cheap because follows are written far less often than they are read, and the copies are kept consistent with timestamped, idempotent writes that are retried until both succeed.

## The core trade-off
A news feed (home timeline) is the newest posts from everyone you follow, merged into one list. The work of assembling it has to happen at some point, and there are exactly two choices:
- **Fan-out on read (pull)**: when a user opens the feed, look up whom they follow, fetch each one's recent posts, merge and sort. Nothing is precomputed.
- **Fan-out on write (push)**: when someone posts, insert the new post's ID into each follower's precomputed feed. Reading a feed is one lookup.

"Fan-out" means one event turning into many operations. Pull fans out at read time, to the people you follow. Push fans out at write time, to the people who follow you. Which is cheaper depends on two numbers: how often feeds are read compared with how often posts are written, and how unevenly followers are distributed.

We'll work through both for a system with **2 billion users**, unlimited follows, feeds that load in under **500 ms**, and up to **1 minute of staleness** acceptable.

## Pull
The data model: a Follow table (partition key `userFollowing`, sort key `userFollowed`, with a GSI the other way, lesson 11.03) and a Posts table with a GSI on (`creatorID`, `createdAt`), so "recent posts by X" is one query.

Building a feed:
1. Query Follow for the user's followees.
2. For each followee, query the Posts GSI for their recent posts (say the newest 20).
3. Merge all those lists by time (a k-way merge with a heap) and return the top 50.

Writes are trivially cheap: posting is one row insert. But one feed read becomes **tens to hundreds of requests** plus a large merge, on every read. A user following 500 accounts triggers 500 post queries, and the slowest of them sets the latency (lesson 02.12 on tail latency explains why fan-out to many backends makes p99 much worse). Feeds are read far more than posts are written, often 100 times more, so pull puts the expensive work on the common path.

! Example: the cost of one pulled feed
! A user follows 400 accounts. Each feed load issues 1 followee query plus 400 "recent posts" queries, each returning up to 20 post IDs: 8,000 candidates merged to pick 50.
! If 100 million users load their feeds 10 times a day, that's 1 billion feed loads, about 11,600 per second on average and perhaps 35,000 at peak. Times 400 queries: 14 million queries per second at peak. Even if each is a cache hit at 0.5 ms, the p99 of 400 parallel calls is far worse than the p99 of one.

## Push
The fix is a **PrecomputedFeed** table: key `userId`, value a list of the newest post IDs (say 200). When a post is created:
1. The new post is stored, and a message goes on a queue (for example SQS with at-least-once delivery, or Kafka).
2. **Feed workers** consume it, look up the followers of whoever posted (paging through the follower list), and prepend the new ID to each follower's feed, trimming each feed back to 200 entries.
3. Reading a feed is one key lookup for 200 IDs, then a multi-get of the first 50 posts from a post cache.

Because delivery is at-least-once, the prepend must be idempotent: skip the ID if it is already at the head of the list, or store feeds as sorted sets keyed by post ID so a duplicate insert changes nothing.

%%flow Fan-out on write: each new post is copied into each follower's precomputed feed by async workers; reading is one lookup.
New post -> Queue -(feed workers)-> Look up followers -(prepend post id)-> *Feed of each follower -(read: one key)-> Viewer
%%

Storage check: 200 IDs × 10 bytes = **2 KB per user**, **4 TB** for 2 billion users. That's a lot of memory but entirely feasible across a cache cluster, and it shrinks a lot if only active users have feeds.

A classic Twitter design is the same: a fan-out service inserts each tweet into followers' home timelines held in **Redis lists** (entries of tweet ID, user ID and a meta byte, a few bytes each), and only users active in the last 30 days keep cached timelines; others are rebuilt from storage when they return.

## The celebrity problem
Push breaks for accounts with huge followings. One post by an account with 100 million followers means 100 million feed writes. Even a fast feed cluster doing 1 million list inserts per second spends **100 seconds** on that one post, and celebrities post several times a day, often in bursts. Fan-out for such accounts can take **minutes**, and posts can appear out of order: a reply from an ordinary user (fanned out in milliseconds) shows up in feeds before the celebrity's message it replies to.

%%bars Feed writes caused by one post, by the poster's follower count. Push cost grows linearly with followers, so a single celebrity post costs as much as a million ordinary posts.
Typical user, 200 followers | 200 | 200 writes
Popular, 50,000 | 50000 | 50,000 writes
Threshold, 100,000 | 100000 | 100,000 writes
*Celebrity, 100 million | 100000000 | 100,000,000 writes
%%

%%compare Pull, push and hybrid feeds: where the work happens and what breaks.
[Pull]
Read -(fetch every followee)-> Merge
+ Posting is one insert
+ Always fresh
- Hundreds of queries per read
- Slow and spiky p99
[Push]
Write -(copy to every follower)-> Feeds
+ Read is one lookup
+ Fast, predictable reads
- Celebrity posts cost millions of writes
- Storage for every user's feed
[*Hybrid]
Push ordinary authors, pull celebrities
+ Bounded write cost per post
+ Reads: one lookup plus a few cached fetches
- Two code paths and a threshold to tune
%%

## Hybrid: push for most, pull for celebrities
The hybrid:
- Mark accounts with more followers than a **threshold** as "not precomputed". The threshold is tuned (often somewhere around 10,000 to 1,000,000 followers), and can also take posting frequency into account.
- Feed workers **skip** fan-out for those accounts' posts.
- At read time, the feed service takes the user's precomputed feed and **merges** in recent posts from the few above-threshold accounts they follow, fetched directly. Those posts are heavily cached, because millions of readers request the same handful of celebrity timelines.

%%flow Hybrid feed: ordinary authors push into feeds at write time; celebrity posts are pulled and merged at read time.
[Write] Ordinary author posts -(fan-out workers)-> *Followers' precomputed feeds
[Read] Viewer opens feed -(one lookup)-> Precomputed feed -(merge recent posts of followed celebrities)-> *Final feed
%%

So: **ordinary users' posts are pushed** (cheap: a few hundred followers each), and **celebrities' posts are pulled** (a handful per reader, all served from cache). Two further refinements are common:
- **Skip inactive followers.** Don't push to users who haven't logged in for 30 days; rebuild their feed with a pull when they return. Since a large fraction of accounts on any network are dormant, this can cut fan-out writes by half or more.
- **Per-reader lists of followed celebrities.** Store, with each user, the short list of above-threshold accounts they follow, so the read path doesn't have to scan the full followee list to find them.

%%seq Reading a hybrid feed: one precomputed lookup, a few cached celebrity timelines, a merge, then a multi-get of the posts.
Viewer > Feed service : GET /feed
Feed service > Feed cache : get feed:viewer (200 post IDs)
Feed service > Follow store : celebrities this viewer follows
Follow store -> Feed service : 3 accounts
Feed service > Post cache : recent posts of 3 accounts
Feed service > Feed service : merge by time, take 50
Feed service > Post cache : multi-get 50 posts
Feed service -> Viewer : feed page 1, cursor
%%

! Example: the numbers behind the threshold
! A user with 300 followers posts: 300 feed prepends, done in well under a second by workers.
! An account with 80 million followers posts: 80 million writes would take over a minute even at a million writes per second, and burn capacity other posts need. With a threshold of 100,000 followers, that account is marked pull.
! A reader following 400 accounts, 3 of them above the threshold, gets one feed lookup plus 3 cached "recent posts" lookups, merged by time. Total: about 5 cache calls instead of 400.
! The read-side cost of that celebrity's posts: if 80 million followers each load their feed 10 times a day, that's 800 million reads of that account's recent posts per day, about 9,000 per second. Spread over a replicated cache, that's easy, and it is far cheaper than 80 million writes per post.

### Choosing the threshold
The threshold balances write cost against read cost. Push costs roughly (followers × posts per day) writes; pull costs roughly (active followers × feed loads per day) cached reads, but reads of the same hot timeline are cheap because they're cache hits on a few keys. Teams typically pick the threshold empirically, by watching fan-out queue lag and read latency, and some make it dynamic: an account that suddenly goes viral is switched to pull before its next post.

## Remaining details
- **Hot posts.** A viral post is read by millions in its first hours, overloading the one cache shard that holds it. The fix is a **replicated post cache**: several identical cache instances, any of which can serve any post, so the load spreads. A small in-process cache on the feed servers for the very hottest posts also helps.
- **Pagination.** Use a cursor: the timestamp (or ID) of the oldest post already shown, and fetch older posts after it. Offsets break when new posts are prepended between page loads.
- **Deletes and unfollows.** A deleted post leaves its ID in millions of feeds. Rather than removing it everywhere, filter at read time (the multi-get of posts returns "deleted") and let the IDs age out. Unfollows can likewise be filtered at read time.
- **Ranking.** Real feeds re-rank the candidate posts by predicted engagement; the precomputed list becomes a **candidate set** rather than the final order.

! Example: a celebrity post timeline under pure push
! 12:00:00, a pop star with 80 million followers posts. 12:00:01, a fan with 200 followers replies; that reply is fanned out in 50 ms. 12:00:40, half the pop star's followers have it; the other half see the fan's reply first, with no context. 12:01:20, fan-out completes, and meanwhile the queue for everyone else's new posts has backed up by 80 seconds. With the hybrid, the pop star's update is visible to every follower on their next feed load, with no write cost at all.

## Common mistakes
- **Pure push "because reads are faster".** It falls over on the first celebrity post.
- **Pure pull "because it's simpler".** Read latency and backend load scale with the number of follows.
- **Fanning out to dormant users.** Wasted writes and memory for feeds nobody will read.
- **Non-idempotent prepends** under at-least-once delivery, producing duplicate entries in feeds.
- **Offset pagination** on a list that changes at the head.

## In an interview
Explain both models in two sentences each, state the read/write ratio and the follower skew, then propose the hybrid with a threshold. Give the numbers: 2 KB per user for 200 IDs, 4 TB for 2 billion users (less with only active users), a celebrity post costing tens of millions of writes under push. Ask about ranking (chronological or ranked?) and freshness (seconds or a minute?), because both change the read path.

> Takeaway: pull computes feeds at read time (cheap writes, slow fan-out reads); push precomputes them at write time (fast reads, expensive writes for big accounts). The hybrid pushes posts from ordinary accounts into active followers' feeds and pulls posts from accounts above a follower threshold at read time, merging the two, so neither a celebrity post nor a feed read is ever unboundedly expensive.

?? Accounts with ordinary follower counts get push: when they post, async workers prepend the new post's ID to every active follower's precomputed feed (skipping dormant users), so reads are a single lookup. Accounts above a tuned follower threshold, the celebrities, get pull: their posts are not fanned out at all, and when a user opens the feed, the service takes the precomputed feed and merges in the recent posts of the few celebrities that user follows, which are cheap to fetch because millions of readers hit the same cached timelines. This avoids tens of millions of writes per celebrity post, and the out-of-order delivery they cause, while keeping each feed read to one lookup plus a handful of cache fetches.

## The feature
Chat apps bold a channel's name when it has messages you haven't read, show a badge with the number of times you were mentioned, and draw a "new messages" line where you stopped reading. It looks like a small UI detail. At scale it is one of the hottest paths in the whole system, because it is touched every time anyone sends a message, every time anyone reads one, and every time anyone connects.

The question proposes the standard model: store, per user per channel, the **ID of the last message the user has read**. Then:

`has unread = channel.last_message_id > read_state.last_read_message_id`

If message IDs increase over time (Snowflake-style IDs, lesson 04.10, or per-channel sequence numbers), this is a single integer comparison. No message is scanned, and no per-message "read" flag is stored.

%%flow Unread is one comparison: the channel's newest message ID against the user's last-read ID.
Channel last_message_id = 1,057 -(compare)-> *User last_read = 1,049 -> 1,057 > 1,049, so bold
%%

## Why not a read flag per message?
The obvious alternative is a `message_reads(user_id, message_id)` table: mark each message read for each user. It fails on arithmetic. A message in a 10,000-member server channel would need 10,000 read rows. A busy community with 100 messages a minute would generate a million read rows a minute, for one channel. And "has unread" becomes "does any message in this channel lack a read row for me?", which is a scan.

The pointer model works because reading in a chat is **sequential**: when you open a channel and scroll to the bottom, you've read everything up to the newest message. One number captures it. (Email is different: people read messages out of order, which is why email systems do keep a per-message read flag, and why their mailboxes are per user rather than shared.)

%%compare Two ways to track what a user has read in a shared channel: a flag per message per user, or one pointer per user per channel.
[Read flag per message]
One row per user per message
- 10,000 rows per message in a big channel
- "Has unread" needs a scan
+ Handles out-of-order reading
[*Last-read pointer]
One row per user per channel
+ Has unread is one comparison
+ Tiny: about 30 bytes per row
+ One write when the user catches up
- Assumes sequential reading
%%

## Why it's cheap, and what makes it expensive
The comparison is cheap. Getting the two numbers to the comparison, for every channel, for every user, every time, is where the cost lives.
- **Per channel**: store `last_message_id` on the channel, updated on every new message. Reading it is a key lookup, usually from a cache of channel heads.
- **Per user per channel**: a **read state** `{last_read_id, mention_count}`. When the user opens the channel or scrolls to the bottom, set `last_read_id` to the newest visible ID and reset `mention_count` to 0. Updates are monotonic: never move the pointer backwards, so a stale update from another device can't un-read messages (`SET last_read_id = max(last_read_id, :new)`).
- **On connect**: to draw the channel list, the client needs both numbers for each of the user's channels. With hundreds of channels, this must be one batch lookup served from RAM, not hundreds of database queries.
- **Mentions**: a mention increments the mentioned user's `mention_count` for that channel. That's a write fan-out, but only to the people mentioned. `@everyone` in a 100,000-member channel means 100,000 counter writes, which is why that feature is restricted by permissions and often rate limited.
- **Multiple devices**: when you read on your phone, your laptop's bold names should clear. The read-state update is published to all of the user's connected sessions (lesson 11.01).

### Exact unread counts
"Has unread" is cheaper than "12 new messages". An exact count needs the number of messages with ID > last_read_id, which with Snowflake IDs is a range count over the channel's message index. Two cheaper routes:
- **Dense per-channel sequence numbers.** If each channel numbers its messages 1, 2, 3, ..., then unread count = `channel.last_seq − last_read_seq`, again one subtraction. Deleted messages make it slightly high, which is usually acceptable. The price is a per-channel counter that every new message must increment (a hot row for a busy channel; lesson 10.01 applies).
- **Cap the display.** Many apps show "99+" or just a dot, so they only need to count up to 100, a bounded range scan.

%%matrix Cost of each unread feature, per channel shown in the sidebar.
Feature | Data needed | Work per check | Write cost
Has unread (bold) | last_message_id, last_read_id | one comparison | one pointer write on read
Mention badge | mention_count | read one counter | one increment per mention
Exact count, sequence numbers | last_seq, last_read_seq | one subtraction | sequence per message
Exact count, Snowflake IDs | message index | range count | none extra
Count capped at 99+ | message index | bounded scan, at most 100 | none extra
%%

## Discord's Read States service
Discord runs this design at very large scale in a dedicated **Read States** service, which tracks which channels and messages users have read. Its characteristics:
- One read state **per user per channel**, holding the last-read message ID and counters (such as the number of @mentions) that are updated atomically and often reset to 0.
- **Billions** of read states in total.
- It is on the hot path: accessed **every time a user connects, every time a message is sent, and every time a message is read**.
- Each instance holds an **LRU cache** of read states (least recently used entries are evicted first), with millions of users and tens of millions of read states per cache.
- **Hundreds of thousands of cache updates per second** and **tens of thousands of database writes per second**.
- Persistence: **Cassandra**. A read state is written to the database when evicted from the cache, and a write is scheduled **30 seconds** after each update, batching many updates into one write.

%%flow Discord's Read States: updates hit an in-memory LRU cache; Cassandra receives at most one write per read state per 30 seconds, plus one on eviction.
Message sent or read -(update)-> *LRU cache of read states -(30 s after update, or on eviction)-> Cassandra
%%

The 30-second delayed write is the same batching idea as lesson 10.01. A user actively reading a busy channel might update its read state every few seconds; mentions arrive in bursts. Coalescing all updates in a 30-second window into one Cassandra write cuts database writes by an order of magnitude. The cost: if an instance crashes, up to 30 seconds of read-state changes are lost, and a few channels look unread again. For this feature that is an acceptable trade.

Users are partitioned across instances (by user ID), so all of one user's read states live in one instance's cache and the connect-time batch lookup is a single call to a single instance.

! Example: sizing the read-state cache
! Suppose 20 million users are online, in an average of 80 channels each: 1.6 billion potential read states, but most belong to channels the user rarely opens. Say 25% are hot: 400 million.
! A read state is about 8 bytes (channel ID) + 8 (last read ID) + 4 (mention count) + flags and LRU pointers, roughly 64 bytes in memory: 400 million × 64 bytes ≈ 26 GB, spread over a few dozen instances at around 1 GB each, comfortably in memory.
! Without the 30-second coalescing, 300,000 updates per second would mean 300,000 Cassandra writes per second; with it, tens of thousands.

## The Go-to-Rust lesson
Discord's first version of Read States was written in Go and suffered **latency and CPU spikes about every 2 minutes**. Go's garbage collector forces a collection at least every 2 minutes, and each collection had to scan the huge LRU cache, tens of millions of objects, to find what was still referenced. The cache was the whole point of the service, so it couldn't be made smaller.

Discord rewrote the service in Rust, which has no garbage collector: memory is freed deterministically as soon as a read state is evicted. The Rust version beat Go on latency, CPU and memory, with average response times in **microseconds**, and it used a `BTreeMap` in the LRU for memory efficiency. Tail latency became flat because nothing paused to scan the heap.

%%timeline The pattern Discord saw with the Go version: steady latency punctuated by a spike each time the forced garbage collection scanned the cache.
0:00 | Normal: sub-millisecond responses
2:00 | *Forced GC scans tens of millions of cached entries: latency and CPU spike
2:05 | Back to normal
4:00 | *Forced GC again: another spike
6:00 | *And again, every 2 minutes
After Rust rewrite | No collector pauses: flat microsecond latency
%%

The general lesson: very large, long-lived in-memory caches and tracing garbage collectors are an awkward combination. Options other than a rewrite include moving the cache off-heap, splitting it into many smaller processes, or using an external store like Redis, each with its own cost.

## Pitfalls
- **Non-monotonic updates.** Two devices sending read updates out of order can move the pointer backwards. Always take the max.
- **IDs that aren't ordered.** Random UUIDs can't be compared. Use time-ordered IDs or per-channel sequences.
- **Per-channel queries on connect.** 300 channels × 2 queries is 600 round trips before the sidebar draws. Batch, and serve from RAM.
- **Persisting every update synchronously.** Read positions change constantly; coalesce writes.
- **@everyone without limits.** One message can create 100,000 counter writes.

! Example: opening the app
! A user in 300 channels connects. The gateway asks Read States for the user's 300 read states (one call to the instance that owns the user) and gets the channels' `last_message_id` values from the channel cache in one multi-get.
! 41 channels have last_message_id greater than last_read_id and are drawn in bold; 3 have mention_count > 0 and show a badge. The user opens one: one update sets its last_read_id to 1,057 and mention_count to 0, the update is pushed to the user's other devices, and Cassandra receives the write within 30 seconds.

> Takeaway: store one read state per user per channel (last read message ID plus a mention counter). With increasing message IDs, "has unread" is just channel.last_message_id > last_read_id, and with dense per-channel sequence numbers the unread count is one subtraction. ## The feature
Posts contain hashtags: "Great run today #marathon #NYC". The system must extract them when a post is saved and then answer:
- "All posts with #x", newest first, paginated (the tag page).
- Posts with several tags at once ("#marathon and #nyc"), sometimes.
- How many posts use #x, and which tags are trending right now.

The question asks you to choose between two storage designs: keep the tags as an **array column** on the posts table, or keep them in a **separate tag table** with one row per (tag, post). Both work at small scale. They behave very differently when a tag is popular, which is exactly when the feature matters most.

## Extraction: a small parser at write time
**Extraction** happens once, when a post is created or edited, never at query time. The steps:
1. **Find candidates** with a regex such as `#(\w+)`, using Unicode word characters so `#café`, `#東京` and `#ราชการ` work. Exclude matches inside URLs (`example.com/#section`) and code.
2. **Normalise**: lower-case (`#NYC` and `#nyc` are the same tag), apply Unicode normalisation (NFKC) so visually identical strings compare equal, and optionally strip accents or fold known variants.
3. **Deduplicate** within one post: "#nyc #NYC #nyc" is one tag.
4. **Cap** the number of tags (ignore the 31st) and their length, to block spam that stuffs posts with hundreds of trending tags.
5. **Store** the normalised tag for lookup and keep the original text, with its capitalisation, for display.

%%flow Tag extraction runs once on write: find candidates, normalise, deduplicate and cap, then store normalised tags for lookup.
Post text -(regex, Unicode words)-> Candidates #NYC, #nyc, #Marathon -(lower-case, NFKC)-> nyc, nyc, marathon -(dedupe, cap at 30)-> *Tags: nyc, marathon
%%

! Example: normalisation edge cases
! "#NYC #nyc #Nyc!!" yields one tag, `nyc`. "#Café" typed with a combining accent and "#Café" typed with a precomposed é look identical but are different byte sequences; NFKC normalisation makes them the same `café`. "Visit example.com/#pricing" yields no tag, because the match is inside a URL. "#2024" is often rejected (pure numbers are not tags on most platforms). A post with 200 hashtags is stored with its first 30.

## Option 1: an array column with a GIN index
In PostgreSQL, store the tags in each post row: `tags text[]`. A normal B-tree index can't answer "rows whose array contains 'marathon'", because a B-tree indexes the whole value, and the whole value is `{marathon,nyc}`. **GIN** (Generalized Inverted Index) is built for exactly this: it is designed for composite values (arrays, jsonb, full-text documents) and indexes the **elements** inside them. Its built-in `array_ops` operator class supports `&&` (overlap), `@>` (contains), `<@` (is contained by) and `=`.

```
CREATE INDEX posts_tags_gin ON posts USING GIN (tags);
SELECT id FROM posts WHERE tags @> ARRAY['marathon'];
SELECT id FROM posts WHERE tags @> ARRAY['marathon','nyc'];  -- both tags
```

Internally, a GIN index is a B-tree over **keys** (the distinct tag values), and each key points to a **posting list** of the row IDs that contain it, or to a **posting tree** (a B-tree of row IDs) when the list is large. It is the inverted index from Module 9 (lesson 09.02), inside your database.

%%tree Inside a GIN index on the tags column: a B-tree of distinct tags, each pointing to the rows that contain it, with large lists stored as their own trees.
GIN entry tree | B-tree of distinct tags
  "marathon" | posting list
    rows 7, 19, 42 | small list stored inline
  "nyc"
    *posting tree | 40 million row IDs, sorted by row ID
  "running"
    rows 7, 88
%%

The trade-off: GIN favours **search speed over write speed**, since one row can generate many index entries (one per tag), each landing on a different page. To soften this, the **fastupdate** option buffers new entries in an unsorted **pending list** that is merged into the main structure later (on VACUUM, or when it exceeds `gin_pending_list_limit`, 4 MB by default). Searches must also scan the pending list, so a big backlog slows reads and makes latency spiky.

The deeper problem is **ordering**. The posting list is sorted by row ID (physical location), not by creation time. GIN can tell you **which** rows have #nyc, but not which are newest. To return the newest 20, the database must fetch every matching row's `created_at` and sort, or walk a time index and check each row's tags.

## Option 2: a separate tag table
```
CREATE TABLE post_tags (
  tag        TEXT NOT NULL,
  created_at TIMESTAMP NOT NULL,
  post_id    BIGINT NOT NULL,
  PRIMARY KEY (tag, created_at, post_id)
);
```
One row per (post, tag). The primary key is a B-tree sorted by tag, then time, then post ID. "All posts with #marathon, newest first" is a backwards range scan on the key starting at `tag = 'marathon'`, **already in time order**, so it reads exactly the rows it returns. Pagination with a cursor `(created_at, post_id) < (last_seen_time, last_seen_id)` is efficient no matter how deep you go (keyset pagination, lesson 04.12). Including post_id in the key makes it unique and gives a stable tie-break for posts created in the same millisecond.

This is a hand-built inverted index whose posting lists are sorted **by time** instead of by row ID, which is exactly the order the tag page needs.

## Trade-offs
%%matrix Array column with GIN against a separate tag table, for the operations a hashtag feature needs.
Operation | Array column + GIN | Separate tag table
Write a post with 3 tags | yes, one row, 3 GIN entries | partial, 1 post row + 3 tag rows
Newest 20 posts with #x, popular tag | no, sort all matches | yes, reads 20 index entries
Deep pagination | partial, re-sort each page | yes, keyset cursor
Posts with #a AND #b | yes, tags @> both | partial, intersect or self-join
Count posts per tag, trending | no, count all matches | yes, counter table per tag
Shard by tag | no, tags live with posts | yes, partition by tag
Simplicity at small scale | yes | partial, more moving parts
%%

The decisive question is "all posts with #x" for a popular tag. With GIN, `#nyc` might match 40 million rows that must be sorted to get the newest 20 (unless combined with other selective filters). The tag table, keyed by (tag, created_at), reads exactly 20 rows. At scale, the tag table usually wins; the array column is fine for small datasets, for multi-tag filters, and for tags used as attributes ("labels on an issue") rather than as feeds.

%%bars Index entries read to serve the newest 20 posts for a tag with 40 million posts. The tag table reads only what it returns.
GIN, then sort by time | 40000000 | 40 million rows
Tag table, first page | 20 | 20 entries
Tag table, page 500 | 20 | 20 entries, cursor
%%

! Example: the two queries side by side
! GIN: `SELECT id FROM posts WHERE tags @> '{nyc}' ORDER BY created_at DESC LIMIT 20`. The planner either reads all 40 million matching row IDs from the posting tree, fetches each row's created_at and does a top-20 sort (seconds), or walks a created_at index backwards checking each row for the tag, which is fast for #nyc but terrible for a rare tag whose newest use was a year ago.
! Tag table: `SELECT post_id FROM post_tags WHERE tag = 'nyc' AND (created_at, post_id) < ($t, $id) ORDER BY created_at DESC, post_id DESC LIMIT 20`. It descends the B-tree once and reads 20 consecutive index entries, about a millisecond for any tag, any page.

## Counts and trending
"How many posts use #x?" with GIN is a count over a posting tree, expensive for big tags. With the tag table you still shouldn't run `COUNT(*)` on each tag page view; keep a `tag_counts(tag, count)` table incremented when tag rows are inserted (batched for hot tags, lesson 10.01).

Trending is a different question: which tags are growing fastest right now. That belongs in the streaming pipeline (lesson 10.09): emit a "tag used" event for each extracted tag, count per tag in time buckets, compare with a baseline, and keep the top K in a cache. Don't compute trending from the tag table with `GROUP BY` queries.

## Scaling the tag table
Once the tag table is sharded, the natural partition key is the tag: all of #marathon's rows on one shard, so a tag page is one shard query. That creates a new problem: **hot tags**. During a World Cup final, #worldcup might get 50,000 posts per second, all inserted into one partition, at the "newest" end of one B-tree.

The fix is to add a **time bucket** to the partition key: partition by (tag, day) or (tag, hour) for big tags. Inserts for #worldcup today go to the (worldcup, 2026-11-12) partition; the tag page reads today's partition first and moves to yesterday's when it runs out. For extreme tags, add a small random suffix as well and merge a few partitions on read. Wide-column stores such as Cassandra are a natural fit: partition key (tag, bucket), clustering key (created_at DESC, post_id).

%%compare Partitioning the tag index only by tag, versus by tag and time bucket, when one tag gets very hot.
[Partition by tag]
#worldcup -> One partition, forever
- Every insert hits one shard
- Partition grows without limit
+ Tag page is always one partition
[*Partition by tag and day]
#worldcup, 2026-11-12 -> Today's partition
+ Load moves to a fresh partition daily
+ Old buckets are cold and compact
- Deep pages read several buckets
%%

Very large systems often move tag search into the search engine (Module 9), which also handles combining tags with text queries, language filtering and ranking ("top" rather than "latest" posts for a tag). The tag table or wide-column index still serves the simple "latest" tab.

! Example: sizing the tag table
! 500 million posts a day, an average of 0.8 tags each: 400 million tag rows a day. At about 50 bytes per row including index overhead, that's 20 GB a day, about 7 TB a year.
! Partitioned by (tag, day), most partitions are tiny (a rare tag used three times today) and a few are large (#worldcup with 20 million rows on final day, 1 GB). Spread over 128 shards by hash of (tag, day), the 400 million rows a day are about 4,600 inserts per second in total, under 40 per shard on average, with peaks several times higher; the shard holding a hot tag's bucket takes far more, which is why the hottest tags also get a random suffix.

## Common mistakes
- **Extracting at query time** with `LIKE '%#nyc%'`. It can't use an index and matches #nycmarathon.
- **No normalisation**, so #NYC and #nyc are different pages.
- **Assuming GIN gives you order.** It finds matches; it doesn't sort them by time.
- **COUNT(*) per tag page view.** Keep counters.
- **Ignoring edits and deletes.** When a post is edited, diff its old and new tag sets and delete or insert tag rows; when it is deleted, remove its tag rows or filter at read time.

Put trending in the streaming pipeline.

> Takeaway: extract and normalise tags at write time. An array column with a GIN index (an inverted index on array elements) is simple and handles multi-tag filters, but returns matches in row order, so a popular tag's newest posts need a huge sort. ## Two different questions
Every post in a feed shows reaction counts ("❤ 1.2K 😂 340") and whether **you** reacted (your heart is filled in). Those look like one feature but are two different access patterns:
- **Counts**: read on every view of a post, by everyone. Must be fast; can be slightly stale. Nobody notices 1,200 versus 1,203.
- **My reaction**: per viewer, per post. Must be correct for that viewer: if I tap heart, it must stay filled when I scroll away and back, and tapping again must remove it, not add a second heart.

A good model serves each pattern from data shaped for it, and keeps the two consistent. The question is how to do that when a feed page shows 20 posts, each needing both answers, and a viral post receives tens of thousands of reactions per second.

## The data model
1. **Reactions table**, the source of truth: one row per (post_id, user_id) with the reaction type and time. The primary key (post_id, user_id) means a user has **at most one reaction per post**, and changing it (heart to laugh) is an update of that row, not a second row. Platforms that allow several reaction types per user per post (as Slack does on messages) put the type in the key: (post_id, user_id, type).
2. **Counts**, stored separately: `post_reaction_counts(post_id, type, count)`, or a small map of counters on each post record. This is a **denormalised** copy: derived from the reactions table, stored separately so reads never have to compute it.

Never compute counts with `COUNT(*) ... GROUP BY type` over the reactions table on each view. A post with 2 million reactions would scan 2 million index entries every time anyone scrolls past it.

%%compare Computing counts on every read versus maintaining a counter on every write. Reads outnumber reactions by orders of magnitude, so the counter wins.
[Count on read]
View -(COUNT GROUP BY type)-> Reactions table
+ Always exact
+ Nothing to keep in sync
- Scans every reaction on every view
- 2M reactions: millions of entries per view
[*Counter on write]
Reaction -(+1 or -1)-> Counts row -> Cache
+ Reading counts is one key lookup
+ Cacheable for every viewer
- Must stay in sync with the rows
- A hot post makes one hot counter
%%

%%flow A reaction updates the source-of-truth row, then the denormalised counter; views read the cached counter plus a point lookup for "did I react".
User taps heart -(upsert post 9, user 4)-> *Reactions table -(increment, async or same transaction)-> Counts per type -> Cache -> Post view
%%

### What one viewer can do
Each viewer's reaction on a post is a tiny state machine. Modelling it explicitly tells you exactly which counter changes each transition must make.

%%state One viewer's reaction on one post. Each transition names the counter changes it causes; tapping the same reaction again is a no-op, not a second count.
[*] -> None
None -> Heart : tap heart: heart +1
Heart -> Laugh : switch: heart -1, laugh +1
Laugh -> None : remove: laugh -1
Heart -> None : remove: heart -1
None -> *Laugh : tap laugh: laugh +1
%%

## Reading "did I react?"
For a feed of 20 posts, the viewer's reactions are a **batch point lookup**:

`SELECT post_id, type FROM reactions WHERE user_id = ? AND post_id IN (…20 ids…)`

For that to be one fast query, the data must be indexed or partitioned by (user_id, post_id), which is the **reverse** of the primary key (post_id, user_id). This is the same two-direction problem as follows in lesson 11.03: one direction serves "who reacted to this post" (rarely needed, for the "liked by" list), the other serves "what did I react to" (needed on every feed render). Options:
- A **secondary index** on (user_id, post_id) on a single database.
- A **second table** keyed by user, written alongside the first, when sharded (the primary table sharded by post_id, the second by user_id).
- A **cache** of "posts this user reacted to recently", since feeds mostly show recent posts.

For very large systems, a per-user **Bloom filter** (lesson 04.13) of reacted post IDs can answer "definitely not reacted" without a lookup, falling back to the store only when the filter says "maybe". Most posts in a feed are ones the viewer hasn't reacted to, so most lookups are skipped.

! Example: rendering a feed
! The feed service has 20 post IDs. It fetches counts for all 20 from the counts cache (one multi-get, about 1 ms) and the viewer's reactions with one query on the (user_id, post_id) index, returning 3 rows (about 2 ms). Each post renders its counts, and 3 of them show the viewer's filled-in reaction.
! The viewer taps heart on post 9: the upsert inserts a row, an event increments post 9's heart count within a couple of seconds, and the client already shows the heart filled and 1,201 instead of 1,200, without waiting.

## Writing at scale: hot posts
A viral post may get tens of thousands of reactions per second. The reaction **rows** are spread out (each user's row is separate and lands in a different place), but the **counter** is a single hot row: the problem of lesson 10.01. The same fixes apply:
- **Batch increments**: push reaction events onto a queue partitioned by post ID; a consumer sums them for a second or two and applies `count += n`.
- **Sharded counters**: split a post's count into N sub-counters with random suffixes, summed on read and cached.
- **Hierarchical aggregation**: servers count locally and forward partial sums, as with live reactions (lesson 10.13).

%%flow Hot-post counting: reaction events are summed per post for a couple of seconds, so the counter sees one write per interval.
Reactions, 20k per s -(partition by post)-> Queue -> *Aggregator sums per 2 s -(count += 40,000)-> Counter row -> Cache
%%

The reactions table itself also needs care for a viral post if it is partitioned by post_id: 20,000 inserts per second into one partition. Wide-column stores handle this better than a single B-tree page, but for the most extreme cases that post's reaction rows can be split across several partitions with a suffix, since "list everyone who reacted" is rarely needed and can merge a few partitions.

## Keeping them consistent
- **Idempotency.** A double tap or a retried request must not double-count. Because the reactions table enforces one row per user per post, increment the counter **only when the upsert actually inserted or changed** a row. In PostgreSQL, `INSERT ... ON CONFLICT (post_id, user_id) DO UPDATE SET type = EXCLUDED.type WHERE reactions.type IS DISTINCT FROM EXCLUDED.type RETURNING (xmax = 0) AS inserted` tells you whether a row was inserted, updated or untouched. Alternatively, emit counter events from change data capture (CDC) on the reactions table, so only real row changes produce events.
- **Changing a reaction** (heart to laugh) is decrement heart, increment laugh, derived from the old and new type of the row.
- **Removing a reaction** deletes the row (or marks it removed) and decrements.
- **Drift.** Counters maintained by events can drift after bugs, lost events or replays. A periodic job recounts from the reactions table for recently active posts and fixes discrepancies. Counts for old posts rarely change, so the job only needs to look at posts with recent activity.
- **Read-your-own-write.** The client shows the user's own reaction (and adds one to the displayed count) immediately, even before the aggregated counter catches up. On refresh, the "did I react" lookup comes from the reactions store or its user-keyed copy, which is updated synchronously, so the filled heart never disappears.

%%seq A double tap on a slow network: the second request finds the row unchanged, so the counter is incremented exactly once.
Client > Reaction API : heart on post 9 (request 1)
Reaction API > Reactions DB : upsert (9, user 4, heart)
Reactions DB -> Reaction API : inserted
Reaction API > Queue : heart +1 for post 9
Client > Reaction API : heart on post 9 (retry)
Reaction API > Reactions DB : upsert (9, user 4, heart)
Reactions DB -> Reaction API : unchanged
Reaction API -> Client : ok, no event emitted
Queue > Aggregator : heart +1, applied once
%%

! Example: switching a reaction under load
! User 4 has a heart on post 9 and switches to laugh. The upsert changes the row's type from heart to laugh and returns the old type. The API emits two events: heart −1, laugh +1, both keyed by post 9. The aggregator, summing over its 2-second window, might combine them with 9,000 other events into `heart += 6,212, laugh += 1,031`. A second later the cached counts reflect the change; the user saw it instantly on their own screen.

! Example: sizing reactions storage
! 500 million posts a day, an average of 20 reactions each: 10 billion reaction rows a day. At 30 bytes each (post ID, user ID, type, time) plus index overhead, budget 60 bytes per row per copy, and two copies (by post and by user): 1.2 TB a day. That's why many systems age out the user-keyed copy (keep "what I reacted to" for 90 days, the window feeds actually show) and archive old reaction rows, while the counters, a few bytes per post per type, are kept forever.

## Common mistakes
- **Counting on read.** Fine in a prototype; a viral post makes every feed view slow.
- **Incrementing on every request.** Without checking whether the row changed, double taps and retries inflate counts.
- **One index direction only.** Keying only by post makes "did I react to these 20 posts?" a scatter across 20 partitions; keying only by user makes "who reacted" a full scan.
- **A single hot counter row** for a viral post.
- **Hiding the user's own reaction** until the backend catches up, which makes the button feel broken.

## The problem
Photo tagging stores "Alice is at this point (or in this box) in photo 123". It looks like the simplest data model in this module: a photo ID, a user ID and a position. The catch is in the word "position". The same photo is shown at many sizes:
- a 4000 × 3000 original from the camera,
- a 1080-pixel-wide version on phones,
- a 320-pixel thumbnail in the feed,
- a 2× version for high-density ("retina") screens,
- a cropped square preview in a profile grid,
- and future renditions nobody has designed yet (a new tablet layout, a new image format).

The tag marker must land on Alice's face in all of them, and must keep doing so when the image pipeline changes. The answer is to store positions as **fractions** of the image, not pixels. This lesson explains why, and covers the cases where fractions alone aren't enough: crops, rotation and letterboxing.

## Coordinates are relative to an origin
A position on the web is an offset from an **origin**, by default the **top-left corner**, with x increasing to the right and y **downward** (unlike school graphs, where y goes up). The same click has different coordinates depending on which origin you measure from. A mouse event in the browser carries several:

%%layers The same click measured from four different origins. Only coordinates relative to the image itself mean anything for a tag.
screenX / screenY | from the physical screen's corner
pageX / pageY | from the top of the whole document
clientX / clientY | from the viewport; changes as you scroll
*offsetX / offsetY | from the target element's padding edge
%%

For tagging, you want coordinates relative to the **rendered image itself**. The robust way is to use the image's bounding box: `rect = img.getBoundingClientRect()`, then `x = (event.clientX − rect.left) / rect.width` and `y = (event.clientY − rect.top) / rect.height`. That gives fractions directly and works even when the image is scaled by CSS or transformed, where `offsetX` can be surprising (it measures from the padding edge, so borders and padding shift it).

## Pixels break across sizes
Suppose a user clicks Alice's face at (540, 300) on an image displayed 1080 × 810 pixels. If you store (540, 300):
- On the 320 × 240 thumbnail, (540, 300) is **off the image** entirely.
- On the 4000 × 3000 original, it is in the top-left area, nowhere near Alice.
- On a high-density screen, CSS pixels and device pixels differ (a 2× screen has four device pixels per CSS pixel), so even "the same" display size can disagree on raw pixel numbers depending on which kind you recorded.
- If the thumbnail pipeline is later changed from 320 to 360 pixels wide, every stored tag is wrong.

You could store pixels plus the size they were measured at, and rescale on every read. That is the fraction approach with extra steps and more ways to get it wrong.

## Fractions are size-independent
Store the position as a **fraction** of the image's width and height, each between 0 and 1. These are often called **normalised coordinates**:

`x = 540 / 1080 = 0.5`, `y = 300 / 810 ≈ 0.370`

To draw the tag on any rendition, multiply by that rendition's displayed size. On the 320 × 240 thumbnail the marker goes at (160, 89); on the 4000 × 3000 original at (2000, 1111). A box tag stores (x, y, width, height), all as fractions.

%%flow One tag, many sizes: capture fractions once, then multiply by whatever size each rendition is displayed at.
[Capture] Click at 540, 300 on 1080 x 810 -(divide by size)-> *Stored: x 0.50, y 0.37
[Thumbnail] Stored fractions -(times 320 x 240)-> Marker at 160, 89
[Original] Stored fractions -(times 4000 x 3000)-> Marker at 2000, 1111
%%

Why this is the right representation:
- **Resolution independence.** Any rendition with the same aspect ratio maps correctly, including ones created later.
- **Responsive layouts.** The client only needs the rendered size, which it always knows, not the original's dimensions.
- **Re-encoding and resizing.** Regenerating thumbnails, serving WebP or AVIF instead of JPEG, or changing quality settings changes nothing.
- **Simple validation.** Anything outside 0 to 1 is invalid, and a box must satisfy x + width ≤ 1 and y + height ≤ 1.
- **Portable.** Mobile apps, web clients and server-side renderers (say, generating a share image with name labels) all use the same numbers.

%%compare Storing a tag as pixels versus as fractions of the image.
[Pixels]
540, 300 measured on a 1080 x 810 display
- Wrong on every other size
- Ambiguous: CSS or device pixels?
- Breaks when renditions change
+ Matches what the click handler reports
[*Fractions]
0.50, 0.37 of width and height
+ Same on every rendition
+ Survives new sizes and formats
+ Easy to validate, 0 to 1
- Crops and rotation need explicit mapping
%%

! Example: a tag stored and drawn
! Stored row: `{photo_id: 123, user_id: alice, x: 0.5000, y: 0.3704, w: 0.0800, h: 0.1100}`.
! Feed card renders the photo at 375 × 281: box at (0.5 × 375, 0.3704 × 281) = (187.5, 104.1), size (0.08 × 375, 0.11 × 281) = 30 × 31 pixels.
! Desktop lightbox at 1600 × 1200: box at (800, 444.5), size 128 × 132.
! One row serves every client and every future rendition.

## What fractions don't fix
Fractions are relative to a particular **frame**: the full, upright, uncropped image. Anything that changes the frame needs an explicit mapping.

### Crops
A square feed preview of a landscape photo shows only part of the image. Store the crop rectangle in fractions too, then map a tag into the crop's own frame:

`x_in_crop = (x − crop.x) / crop.width`, `y_in_crop = (y − crop.y) / crop.height`

Tags whose mapped coordinates fall outside 0 to 1 are outside the crop and are hidden.

! Example: a centred square crop
! The original is 4000 × 3000. A centred square crop keeps x from 500 to 3500 and all of y. As fractions: crop.x = 0.125, crop.width = 0.75, crop.y = 0, crop.height = 1.
! Alice's tag at x = 0.5 maps to (0.5 − 0.125) / 0.75 = 0.5: still centred. Bob's tag at x = 0.1 maps to (0.1 − 0.125) / 0.75 = −0.033: outside the crop, so the square preview hides his marker, and the full view shows it.

### Rotation and EXIF orientation
Phone cameras often save the pixels sideways and add an **EXIF orientation** flag telling viewers to rotate on display. If one client tags the raw sideways pixels and another the rotated view, their fractions disagree. Normalise the image (apply the rotation and strip the flag) when it is uploaded, before anyone can tag it, so every client sees the same upright frame. If a user later rotates a photo 90° clockwise, transform the stored tags: `x' = 1 − y`, `y' = x` (the top-left corner moves to the top-right), and swap width and height for boxes.

### Aspect ratio and letterboxing
Fractions assume each rendition has the same aspect ratio as the original. If a layout fits a 4:3 photo into a square box with `object-fit: contain`, the image is **letterboxed** (bars above and below), and the box's size is not the image's size. Compute the image's actual rendered rectangle inside the container and map into that.

%%matrix What each display transformation does to stored fractions, and what to do about it.
Change | Fractions still valid? | What to do
Resize, same aspect ratio | yes | multiply by rendered size
New format or quality | yes | nothing
Crop | partial | map into crop frame, hide outside
Rotate 90 degrees | no | transform: x' = 1 - y, y' = x
EXIF orientation flag | no, if clients disagree | normalise on upload
Letterbox, object-fit contain | partial | map into the image's rendered rectangle
Stretch to a new aspect ratio | partial, distorted | avoid; preserve aspect ratio
%%

! Example: drawing a tag in a letterboxed view
! A 4000 × 3000 photo is shown with `object-fit: contain` in a 400 × 400 box. Scale = min(400 / 4000, 400 / 3000) = 0.1, so the image renders at 400 × 300, centred with 50-pixel bars above and below.
! Alice's tag at (0.5, 0.37) is drawn at x = 0 + 0.5 × 400 = 200 and y = 50 + 0.37 × 300 = 161. Using the box's 400-pixel height instead of the image's 300 would put the marker at y = 148, 13 pixels too high, on Alice's forehead.

## Storage and precision
A tag row needs photo ID, tagged user ID, tagger ID, the position and, for boxes, a size, plus a status (pending approval, approved, removed), since many platforms let the tagged person approve or remove tags. Index by photo (to draw tags on a photo) and by tagged user (for "photos of Alice"), the same two-direction pattern as follows and reactions.

Precision is a non-issue: a 32-bit float has about 7 significant digits, and even a fixed-point integer (fraction × 10,000, stored as a 16-bit or 32-bit integer) is plenty: 0.0001 of a 4000-pixel image is 0.4 pixels. Fixed-point integers compare exactly and avoid float formatting surprises in JSON.

## Common mistakes
- **Storing pixels from whatever size the tagger saw.** Correct only on that one size.
- **Using offsetX without thinking about borders and padding**, or clientX without subtracting the image's position.
- **Ignoring EXIF orientation**, so tags made on iOS appear sideways on web.
- **Using the container's size** instead of the image's rendered rectangle when the image is letterboxed.
- **Forgetting crops**, drawing markers outside a cropped preview or in the wrong place within it.

## In an interview
Say "store normalised coordinates: x, y, width, height as fractions of the upright original, and multiply by the rendered size on each client". Then mention the edge cases unprompted: normalise EXIF orientation on upload, map through crop rectangles, compute the rendered rectangle under letterboxing. It shows you've thought about the whole pipeline, not just the happy path.

> Takeaway: browser coordinates are offsets from a top-left origin and depend on the reference element and display size, so pixels are only right for one rendition. Store tag positions (and crop boxes) as fractions 0 to 1 of the upright original's width and height, then multiply by each rendition's rendered size, handling crops, rotation and letterboxing explicitly.

## The challenge
A World Cup final: hundreds of millions of viewers, and fans posting comments far faster than anyone can read. When a goal is scored, comment volume can jump tenfold within seconds. Everything in lesson 10.13 applies, but comments, unlike reactions, are **distinct messages** that can't simply be summed. You can send "2,070 hearts" as one number; you can't send "2,070 comments" as one number.

This lesson builds the standard live-comment design, shows why sharding pub/sub **by event** is the right default, and then shows why the biggest event of all breaks that default and what to do about it.

## The base design
Requirements: millions of concurrent live videos or events, **thousands of comments per second per video**, availability over consistency (a comment arriving a second late or slightly out of order is fine), and **under 200 ms** delivery for normal streams. The building blocks:
- Comments are posted over normal HTTP and **persisted** to a database, so late joiners can load recent history and nothing depends on the real-time path for durability.
- Viewers receive new comments over **SSE** (lesson 11.02), since reads vastly outnumber writes.
- **Realtime messaging servers** hold viewer connections, tens of thousands to a hundred thousand each.
- **Pub/sub** carries new comments from the comment service to the realtime servers (lesson 11.01).

## Sharding pub/sub by event
A naive pub/sub where every realtime server receives every comment for every video doesn't scale: each server would process the whole world's comments to deliver a tiny fraction of them. With 1,000 realtime servers and 100,000 comments per second worldwide, that's 100 million deliveries per second between servers, nearly all discarded. Shard it:
- Comments for a video are published to channel `hash(liveVideoId) % N`. A realtime server subscribes only to the channels for videos its viewers are watching.
- An **L7 load balancer** (one that understands HTTP and can route on the URL) routes viewers by **consistent hashing on liveVideoId**, so viewers of the same video land on the same few realtime servers. Then each server subscribes to few channels, and each comment is delivered to as few servers as possible.
- Redis pub/sub is used for low latency and dynamic subscriptions; its fire-and-forget delivery is acceptable because comments are persisted and clients re-sync after disconnects.

%%flow Comments sharded by event: a video's comments go to one channel, and only the servers holding that video's viewers subscribe.
Comment on final -(persist)-> Comments DB -(publish to hash of video id mod N)-> *Channel 17 -(subscribed servers only)-> Realtime servers for the final -(SSE)-> Viewers
%%

Why co-location matters: without it, a video's 50,000 viewers would be scattered across all 1,000 servers, every server would subscribe to every popular video, and each comment would be delivered 1,000 times between servers. With consistent hashing, those 50,000 viewers sit on one or two servers, and each comment crosses the server network once or twice.

## When one event is the whole load
Sharding by event spreads **different** events across shards. The World Cup final is a **single** event, and on that day it may be most of the platform's traffic. Hash-based placement alone puts the final on one shard, one channel and one or two realtime servers, which can't hold 200 million connections. A single key that is hotter than any machine is the hot-key problem again (lesson 10.01), now for connections and fan-out.

%%compare Placing one event's viewers: hashing the event to one server works for normal streams and collapses for the final; mapping a hot event to a group of servers spreads it.
[Hash event to one server]
Final -(consistent hash)-> Server 17
+ Fewest subscriptions per comment
+ Perfect for 99% of streams
- One server cannot hold 200M viewers
- One channel becomes a hotspot
[*Hot event to a server group]
Final -(hash viewer within group)-> 2,000 servers
+ Load spread across the fleet
+ Same channel, many subscribers
- Needs a hot-event registry
- Fan-out must be tiered
%%

What changes for a mega-event:
1. **Spread one event's viewers across many servers.** Keep a small registry of hot events. For a normal video, hash the video ID to one server; for a hot one, hash (video ID, viewer ID) into a **group** of servers sized to the audience: the final gets, say, 2,000 realtime servers, each subscribing to the event's channel. The comment is published once, and the pub/sub layer fans it out to 2,000 subscribers, each pushing to its 100,000 viewers.
2. **Tiered fan-out.** A single Redis channel feeding 2,000 subscribers at thousands of messages per second is itself a hotspot: one Redis node writing to 2,000 sockets for every message. Add a **relay tier**: the publisher sends to, say, 40 relays, each feeding 50 realtime servers. Each hop multiplies; no node fans out to everything.
3. **Sample the comments.** No human can read 10,000 comments per second; at more than about 10 per second the stream is an unreadable blur. For mega-streams, **sample**, lowering the share of comments delivered from 50% down to 1 to 2%, and far lower at peaks, as comment velocity rises. Always include the viewer's own comments (rendered locally) and perhaps comments from friends, verified accounts or highly rated commenters. All comments are still stored.
4. **Batch per tick.** Send comments in small batches (for example every 250 ms) rather than one message each, cutting per-message overhead at every hop.
5. **Snapshots via CDN.** For the largest streams, deliver periodic snapshots through a CDN: viewers fetch "the latest 50 comments" every second or two from an edge cache, which absorbs almost unlimited read load. It is pull instead of push, but at this scale, a one-second-old snapshot from a nearby edge is indistinguishable from live.

%%tree The fan-out tree for one batch of comments during the final: each node forwards to a bounded number of children, so no machine sends to everyone.
Event publisher | 4 batches per second
  Relay 1 | forwards to 50 servers
    Realtime server 1 | 100,000 viewers
    Realtime server 50 | 100,000 viewers
  Relay 2
    Realtime server 51
  *Relay 40 | 40 relays x 50 = 2,000 servers
%%

%%flow Mega-event fan-out: sample and batch first, then fan out through a relay tier to thousands of realtime servers.
Comments, 50k per s -(sample to about 20 per s, batch per 250 ms)-> *Event publisher -(40 relays)-> Relay tier -(50 servers each)-> 2,000 realtime servers -> 200M viewers
%%

! Example: sizing the final
! 200 million viewers at 100,000 SSE connections per server = 2,000 realtime servers.
! Raw comments: 50,000 per second. Sampled to about 20 per second (0.04%, the per-viewer target used below), batched every 250 ms into 4 messages per second of about 5 comments each, roughly 600 bytes per batch.
! The publisher sends 4 messages per second to 40 relays: 160 sends per second. Each relay forwards to 50 servers: 200 sends per second. Each server writes 4 frames per second to each of its 100,000 viewers: 400,000 SSE writes per second and about 250 to 300 MB per second (2 to 2.5 Gbit/s) of outbound data per server, which is heavy but within a modern server with a fast network card. Every node's fan-out is bounded.
! Per viewer: 600 bytes × 4 = 2.4 KB per second, about 20 kilobits per second, negligible next to the video stream. Delivering 1% (500 comments per second) instead would be 25 times more: about 60 KB per second per viewer and about 6 GB per second per realtime server, far beyond one network card. That is why the sampling rate has to fall as velocity rises.

### Adaptive sampling
The sampling rate should follow the comment velocity, not be fixed. A target such as "deliver about 20 comments per second to each viewer" works across the whole match.

%%timeline Comment velocity during the final and the sampling rate that keeps delivery at about 20 comments per second per viewer.
Kick-off | 8,000 per s, deliver 0.25%
30 min, quiet play | 2,000 per s, deliver 1%
*67 min, goal | 60,000 per s for 30 s, deliver 0.03%
Half-time | 1,000 per s, deliver 2%
*Final whistle | 90,000 per s, deliver about 0.02%
After the match | 500 per s, deliver 4%
%%

! Example: velocity-based sampling at a goal
! Before the goal the stream runs at 2,000 comments per second, delivering 1% (20 per second per viewer). In the five seconds after the goal it jumps to 60,000 per second. The sampler measures velocity over a sliding 2-second window (lesson 10.06) and recomputes the rate: 20 / 60,000 ≈ 0.033%. Without the change, each viewer would receive 600 comments a second, the batches would grow 30 times larger, and every relay and realtime server would see a 30-fold burst at the exact moment everyone is watching.
! Which 20 are kept is a product choice: random (fair), weighted towards verified accounts and friends (more interesting), or filtered by a spam and toxicity score first (safer). Many systems do all three: filter, then a weighted sample.

## Other parts that need sharding
- **Write path.** 50,000 comments per second into one event. Partition the comment store by (event, time bucket) or a random suffix so writes spread across nodes; a single partition per event would be the hot row of lesson 10.01. Moderation and spam filtering run on a stream (Kafka partitioned by a hash of the comment ID, not the event ID, so the filter workers share the load) before publishing.
- **Rate limits.** Per user (for example one comment every few seconds during the final) and per event, enforced at the API, so a bot farm can't flood the stream.
- **History for late joiners.** Serve "last 50 comments" from a cache refreshed every second, not from the database per viewer. Ten million people opening the stream at kick-off would otherwise run ten million identical queries.
- **Reactions.** Aggregate as counts (lesson 10.13), not messages.
- **Pre-scaling.** Mega-events are scheduled. Warm the realtime fleet, the relays and the CDN before kick-off, and register the event as hot in advance rather than waiting for autoscaling to react to a 10-times surge.

## Common mistakes
- **Assuming hashing solves hotspots.** Hashing spreads many keys; it does nothing for one huge key.
- **Delivering every comment.** Beyond a few dozen per second it is unreadable, and the cost is real at every hop.
- **One pub/sub node fanning out to thousands of servers.** Add a relay tier.
- **Querying the database for history** on every join.
- **A fixed sampling rate.** It either wastes capacity in quiet periods or collapses at the goal.

## In an interview
Start with the default: "shard pub/sub by event, channel = hash(event) mod N, and co-locate an event's viewers with consistent hashing at the L7 load balancer so each comment reaches few servers". Then say the important part unprompted: "the final is one key, so it needs special handling: a hot-event registry that spreads its viewers over thousands of servers, a relay tier so fan-out is bounded per node, velocity-based sampling and batching, history and possibly the stream itself from a CDN, and pre-scaling because the date is known".

> Takeaway: shard live-comment pub/sub by event (channel = hash(event) mod N) and co-locate an event's viewers on the same servers with consistent hashing at the L7 load balancer. A single huge event outgrows one shard, so spread its viewers over a group of servers, fan out through relay tiers, sample comments by velocity and batch them per tick, serve history and snapshots from a cache or CDN, and pre-scale for the scheduled peak.
