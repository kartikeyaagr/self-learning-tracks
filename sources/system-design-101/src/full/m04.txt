@04.01
## Start from SQL, move only for a reason
The default choice for a new system's main data store should be a relational database, usually Postgres or MySQL. Relational databases give you joins, constraints, ACID transactions (lesson 03.01), a mature query planner, and decades of tooling for backups, monitoring and migrations. The claim that they "do not scale" is overstated. Read replicas, caching, connection pooling, partitioning and finally sharding (lesson 03.10) take them a very long way: Shopify, GitHub, Stack Overflow and Notion run enormous businesses on MySQL or Postgres.

Picking an unusual database in an interview, or at work, without a concrete reason tends to hurt rather than help. The interviewer will ask "why?", and "it scales" is not an answer. A good answer names a specific access pattern or requirement that the relational database handles badly, and a specific store that handles it well.

## What "NoSQL" actually means
**NoSQL** is not one thing. It is a loose family of databases that each give up some relational features to gain something specific. The main members:
- **Key-value stores** (Redis, DynamoDB, Memcached): look up an opaque value by a key. Extremely fast and simple (lesson 04.02).
- **Document stores** (MongoDB, Couchbase, Firestore): store JSON-like documents and can index fields inside them (lesson 04.02).
- **Wide-column stores** (Cassandra, ScyllaDB, HBase, Bigtable): rows grouped into partitions, sorted inside each partition, built for huge write rates (lesson 04.03).
- **Graph databases** (Neo4j, Neptune): nodes and edges, built for multi-hop traversal (lesson 04.04).
- **Search engines** (Elasticsearch, OpenSearch): inverted indexes for full-text search and filtering (Module 9).
- **Time-series and columnar analytics stores** (InfluxDB, ClickHouse) are often discussed alongside them, though ClickHouse speaks SQL.

The common trade most of them make: they **partition data automatically** across many machines, they encourage **denormalising** data (storing copies to avoid joins), they do joins in application code if at all, they offer **limited transactions** (often single-key or single-partition only), and many default to **eventual consistency**, where replicas may briefly disagree. That style is sometimes summarised as **BASE**: basically available, soft state, eventually consistent, in contrast to ACID.

%%compare What you typically gain and lose moving from a relational database to a partitioned NoSQL store.
[*Relational, e.g. Postgres]
Normalised tables -(joins at read time)-> Any query
+ Ad hoc queries and joins
+ Multi-row ACID transactions

[Partitioned NoSQL, e.g. Cassandra]

%%

## When SQL is the better fit
- **Structured data with a clear schema** that changes occasionally.
- **Relational data that needs joins**: orders with customers with addresses with products.
- **Transactions across several rows or tables**: payments, inventory, bookings, anything where "half done" is a bug.
- **Many different query patterns**, including ones nobody has thought of yet (reporting, support tools, analytics), served by indexes on many columns.
- **Moderate scale**: up to tens of thousands of writes per second and a few terabytes on one primary, which covers most products.

## When NoSQL is the better fit
- **Data accessed by a known key**, without joins, at very high rates: sessions, carts, feature flags, rate-limit counters.
- **Write rates or data sizes beyond one machine** where you want the database to partition and rebalance for you: terabytes to petabytes, hundreds of thousands of writes per second.
- **Semi-structured data** whose shape varies a lot between records or changes often.
- **Very low, predictable latency** for simple operations, such as an in-memory store answering in under a millisecond.
- **Append-heavy, time-ordered data** read back by entity and time range: event logs, metrics, chat history, IoT readings.

## Choosing by access pattern
The most important input is the **access pattern**: for each API endpoint, what does it read and write, by which key, and how often? Then data volume, growth rate, and consistency needs. A useful exercise is to write the list of queries before naming any database.

%%matrix Workloads and the store family that usually fits them best, with the reason.
Workload | Relational | Key-value | Document | Wide-column | Columnar
Orders, payments, inventory | yes, transactions | no | partial | no | no
Sessions, flags, rate limits | partial | yes, by key | partial | no | no
Catalog with varied attributes | partial, JSONB | no | yes | no | no
Chat messages, events at huge scale | partial, until sharded | no | partial | yes | no
Analytics over billions of rows | partial | no | no | no | yes
%%

Postgres covers more of this table than people expect: JSONB columns with GIN indexes for flexible attributes, partial indexes, full-text search, table partitioning for time-series, and extensions for geospatial data and vectors. "SQL for the core, a key-value cache in front" is the most common real architecture. A second or third store is added when a particular access pattern outgrows it.

%%tree A decision path for one dataset. Most branches end at the relational database.
Does it need multi-row transactions or joins?
  Yes | Relational
    *Fits on one primary? | Postgres or MySQL
    Too big? | Shard it, or NewSQL like Spanner, CockroachDB
  No
    Fetched whole by one key? | Key-value, Redis or DynamoDB
    Query fields inside nested records? | Document store, or JSONB
    Huge append rate, read by key and time? | Wide-column, Cassandra
    Scans and aggregates over billions? | Columnar, ClickHouse
    Multi-hop relationships? | Graph, rarely needed
%%

A newer option blurs the line: **NewSQL** or distributed SQL databases (Google Spanner, CockroachDB, YugabyteDB, TiDB) partition data automatically like NoSQL stores but keep SQL and multi-row transactions. They cost more latency per write (consensus between replicas, Module 6) and more money, but they remove the choice between "SQL" and "scale" for many workloads.

## The real costs of NoSQL
The benefits are easy to list. The costs are what an interviewer wants to hear you acknowledge.
- **Queries are designed up front.** In Cassandra or DynamoDB, you design tables around the queries you will run. A new query pattern next year may need a new table and a backfill of all historical data.
- **No joins** means denormalised copies of the same data in several tables, and your code must keep them in sync. When a user changes their name, every copy must change.
- **Weaker transactions** push correctness work into your application: idempotency keys, conditional writes, compensating actions.
- **Eventual consistency** means users can see stale data, such as a message that appears on one device a second before another.
- **Operational cost**: a second database is a second set of backups, upgrades, dashboards, failure modes and on-call knowledge.

## Signals in an interview
Phrases that should make you consider a NoSQL store: "billions of events a day", "write-heavy", "only ever looked up by ID", "time-ordered history per user", "global, always writable". Phrases that should keep you on SQL: "money", "inventory", "booking", "must never double-sell", "reporting", "admin can search by anything". When in doubt, say "Postgres, and here is what would make me move off it".

! Example: choosing for a ride-hailing app
! Trips, payments and driver payouts go in Postgres. They need transactions (a trip completing must create a charge and a payout atomically) and constraints. Volume: a city of 2 million rides a day is about 23 trips per second on average, perhaps 200 at peak, trivially within one primary.
! Live driver locations go in Redis. 500,000 active drivers sending a location every 4 seconds is 125,000 writes per second, only the latest value matters, and lookups are by driver ID or by area (Redis has geospatial commands). Losing a few seconds of locations in a crash is harmless; they are refreshed in 4 seconds.
! Raw GPS traces for analytics (the same 125,000 points per second, kept for a year: about 4 trillion points) go to a columnar store, where queries like "average speed by road segment by hour" scan a few columns over billions of rows.
! Three stores, each chosen for one access pattern, and each with a clear reason.

! Example: two workloads where NoSQL is a clear win, and two where it is not
! Win 1: an ad platform logs 2 million impression events per second, each looked up later by campaign and time. That is 170 billion rows a day. Cassandra spreads writes across 100 nodes and reads one campaign-hour partition at a time. A single relational primary cannot absorb that write rate.
! Win 2: a game stores session state for 10 million concurrent players, each read and written by player ID 10 times a second, lost harmlessly on expiry. Redis answers in under 1 ms from RAM; a relational database would spend most of its effort on durability nobody needs.
! Not a win 1: a bank ledger, where a transfer must debit and credit atomically and never go negative. You want multi-row transactions and check constraints.
! Not a win 2: an internal reporting tool where analysts ask new questions every week, joining customers, orders and support tickets. A store designed around fixed queries would need a new table for every question.

## Common mistakes
- **Choosing NoSQL "for scale"** when the numbers fit on one Postgres primary.
- **Choosing a document store to avoid migrations**, then discovering the schema still exists, now scattered through application code.
- **Using a key-value store for data that needs secondary queries**, then scanning everything.
- **Ignoring the operational cost** of every additional database.
- **Forgetting that NoSQL data models are query-first**, and being surprised when a new feature needs a new table.

> Takeaway: use a relational database by default. Pick a NoSQL store when a specific access pattern, scale or latency need is something it handles clearly better, and accept the loss of joins, ad hoc queries and multi-row transactions knowingly. Many real systems use SQL for the core plus one or two specialised stores.

?? NoSQL is a clear win for (1) very high-volume, append-heavy writes read back by key and time range, such as event logs, metrics or chat history in a wide-column store like Cassandra, where write rates exceed one machine and the database partitions for you; and (2) simple, latency-critical key lookups on ephemeral data, such as sessions, carts, rate-limit counters or live locations in Redis or DynamoDB. It is a poor fit for (1) payments, ledgers, inventory or bookings, which need multi-row ACID transactions and constraints, and (2) reporting or admin tools with ad hoc queries and joins across many entities, because NoSQL tables are designed around fixed queries.

## Key-value stores
A **key-value store** is a giant dictionary with three core operations: `get(key)`, `set(key, value)` and `delete(key)`. The **value is opaque** to the database: it is a blob of bytes, and the store never looks inside it. That is the whole contract, and it is why key-value stores are so fast and so easy to scale. Every operation touches exactly one key, so there are no joins, no query planning and no cross-key coordination. To spread data over many machines, you hash the key to pick a machine (lesson 04.07), and every request goes to exactly one place.

The price is that **all the logic lives in the application**. You can only find data if you know its key. "Find all sessions for users in Germany" is impossible without reading every value.

Some key-value stores keep keys **sorted** instead of hashed (RocksDB, FoundationDB, Bigtable). That allows range scans: "all keys between `user:42:` and `user:42;`". Choosing key names carefully then becomes a way to model data, which lesson 04.03 develops further.

### Redis: a data structure server
Redis is the best-known key-value store, and it is really a **data structure server**: values can have types, and each type has its own atomic operations that run inside the server. Because Redis executes commands one at a time on a single thread, each command is atomic without locks.

%%matrix Redis value types and the jobs they are typically used for.
Type | Atomic operations | Typical use
String | GET, SET, INCR, SETEX | Cache entries, counters, rate limits
Hash | HGET, HSET, HINCRBY | An object's fields, user:42 to name, plan
List | LPUSH, RPOP, BLPOP | Simple queues, recent items
Set | SADD, SISMEMBER, SINTER | Unique members, tags, who is online
Sorted set | ZADD, ZRANGE, ZINCRBY | Leaderboards, ranking, time-ordered feeds
Stream | XADD, XREADGROUP | Append-only event log with consumer groups
Geo | GEOADD, GEOSEARCH | Drivers within 2 km
HyperLogLog | PFADD, PFCOUNT | Approximate distinct counts in 12 KB
%%

A sorted set is a good example of why types matter. A leaderboard stored as one opaque blob would need "read the whole blob, update one score, re-sort, write it back", with a race between concurrent updates (lesson 03.06). As a sorted set it is `ZINCRBY leaderboard 50 player:7` and `ZREVRANGE leaderboard 0 9`, each atomic and O(log n).

Redis keeps everything in memory, so a read takes tens of microseconds inside the server and well under a millisecond over the network. It can persist to disk with snapshots or an append-only log, but the dataset must fit in RAM (or be spread across a Redis Cluster).

### DynamoDB: key-value with a sort key
DynamoDB is a managed key-value and document store. Each item is found by a **partition key**, which is hashed to pick a storage partition, and optionally a **sort key**, which orders items within that partition. A table with partition key `user_id` and sort key `order_date` can answer "user 42's orders in March" as one efficient range read. Items can hold nested attributes and DynamoDB can filter on them, but efficient access is always by key; other access patterns need **secondary indexes**, which are copies of the data keyed differently.

%%seq A key-value store only understands keys. The application serialises and parses the value itself.
App > KV store : GET cart:42
KV store -> App : 1.2 KB of opaque bytes
App > App : parse JSON, add item
App > KV store : SET cart:42 new bytes, TTL 30 days
KV store -> App : OK
%%

## Document stores
A **document store** keeps self-contained, JSON-like **documents**, grouped into **collections**. The crucial difference from a key-value store is that **the database understands the structure** of the value. You can query fields inside documents (`find({"address.city": "Pune"})`), create indexes on them, update one field without rewriting the document (`$inc` a counter, `$push` to an array), and project only the fields you need.

Documents in one collection can have different fields, so adding a field does not need a migration. MongoDB stores documents in a binary JSON format called BSON, which adds types such as dates and 64-bit integers.

### Modelling: store together what is read together
The central rule of document modelling is: **data that is accessed together should be stored together**. Instead of normalising into many tables and joining at read time (lesson 03.01), you shape each document around the screen or API call that reads it. You choose, for each relationship, between two options.

**Embedding** puts the related data inside the document: an order with its line items and shipping address, a blog post with its tags. One read returns everything, with no joins. Updates to a single document are **atomic**, so an order and its items can never be half-written.

**Referencing** stores another document's ID instead, like a foreign key. Use it when the related data is **large**, **shared** by many documents, or **unbounded** in number. The application (or MongoDB's `$lookup` aggregation stage) fetches the referenced documents in a second step.

%%tree An order document with embedded line items and address, and a reference to the customer, who is shared by many orders.
order 9001
  customer_id | reference to customers collection
  status | shipped
  placed_at | 2026-03-04T10:12Z
  *items | embedded array, read with the order
    item 1 | sku A17, qty 2, price 19.99
    item 2 | sku B03, qty 1, price 5.00
  shipping_address | embedded snapshot at order time
    city | Pune
    postcode | 411001
%%

A useful middle path is the **subset pattern**. A product page shows the five newest reviews. The product document embeds those five, while all reviews, possibly thousands, live in their own collection, referenced by product ID. The page loads with one read; the "all reviews" page queries the reviews collection.

%%compare Embedding versus referencing related data in a document store.
[*Embed]
Order -(contains)-> Line items
+ One read returns everything
+ Atomic single-document update
- Document grows with the data
- Duplicates shared data
[Reference]
Order -(customer_id)-> Customer document
+ Shared data stored once
+ Unbounded relationships OK
- Second query or $lookup
- No atomicity across documents by default
%%

### Limits to know
- **Document size cap**: 16 MB in MongoDB. An unbounded array, such as every comment on a viral post embedded inside that post document, will eventually hit it, and long before that every update rewrites a huge document.
- **Atomicity is per document** by default. Multi-document transactions exist in MongoDB since version 4.0, but they are slower and limited, and the modelling advice is still to design so most writes touch one document.
- **Duplicated data must be updated everywhere it lives.** If the customer's name is embedded in 300 orders, a name change is 300 updates, or a decision that orders keep the name as it was at order time (which is often the right business rule anyway, as with the address snapshot above).
- **Indexes still matter.** A query on a field without an index scans the whole collection, exactly like a relational sequential scan.

## How to choose
Pick a **key-value store** when:
- You always fetch by one key, and use the value whole.
- You need extreme speed (in-memory, sub-millisecond) and simple operations: caching, sessions, rate-limit counters, leaderboards, feature flags.
- Values can expire automatically (TTL) and losing them is tolerable or recoverable.

Pick a **document store** when:
- You need to **query or index by fields inside the value**, not just the key.
- Records are naturally nested objects that are read together (a product with variants, a user profile with settings, a form submission).
- Different records have genuinely different shapes, such as a catalogue where shoes have sizes and laptops have RAM and CPU.

A caveat for interviews: requirements rarely involve rapidly changing schemas, which removes the main reason to choose a document store over Postgres. A relational table with a `JSONB` column and a GIN index on it often gives you both: relational integrity for the core fields and flexible, queryable attributes for the rest.

! Example: a shopping cart, two ways
! Key-value: `cart:{user_id}` holds the serialised cart, read and written whole, with a 30-day TTL. With 20 million active carts at 1.5 KB each, that is 30 GB, which fits in a small Redis cluster. Each page view is one `GET` taking about 0.3 ms end to end.
! New requirement: when product 123 drops in price, notify everyone with it in their cart. With opaque values, the only way is to read and parse all 20 million carts: 30 GB of transfer for one question.
! Document store: carts are documents with `items: [{product_id, qty}]` and an index on `items.product_id`. "Find carts containing product 123" is one indexed query returning, say, 4,000 carts in a few milliseconds. The requirement decided the store: querying inside the value is exactly what a document store adds.

! Example: when embedding goes wrong
! A social app embeds every comment inside its post document. A typical post has 20 comments of 300 bytes: a 6 KB document, fine.
! A celebrity post receives 200,000 comments. The document would reach 60 MB, beyond the 16 MB cap, and long before that each new comment rewrites megabytes and every feed read downloads every comment.
! The fix is the subset pattern: embed the latest 10 comments and a `comment_count`, and store all comments in a `comments` collection indexed by `(post_id, created_at)`. Feed reads stay small; the full thread is paged from the comments collection (lesson 04.12).

## Common mistakes
- **Using a key-value store, then needing secondary queries**, and scanning everything to answer them.
- **Embedding unbounded arrays** in documents.
- **Normalising a document store like SQL**, with references everywhere, and doing joins by hand on every read.
- **Forgetting indexes in a document store** because "it's NoSQL, it's fast".
- **Treating "schemaless" as "no schema"**: the schema is still there, now enforced (or not) by every piece of code that reads the documents.

## In an interview
When you choose between the two, say what you will query by. "Only by session ID" means key-value. "By user, and also by product inside the cart" means document store or relational with JSON. For a document store, say what you embed and what you reference, and why: read together, bounded size and not shared means embed.

> Takeaway: key-value stores fetch an opaque value by key, extremely fast, and know nothing else. Document stores understand the value, so you can query, index and partially update fields inside it. In documents, embed what is read together and bounded; reference what is large, shared or unbounded.

?? Pick a document store when you need to query, filter or index by fields inside the record rather than only fetch it by its key (for example "find all carts containing product 123", or products by brand and price), when you want to update individual fields atomically without rewriting the whole value, or when records are nested objects with varying shapes that are read together, like a product catalogue or an order with its line items. If you only ever fetch and replace the whole value by one key, such as a session, cache entry or rate-limit counter, a key-value store like Redis is simpler and faster.

@04.03
## Two very different "column" databases
The word "column" appears in the names of two unrelated families of database, and mixing them up is a common interview mistake.
- **Wide-column stores** (Cassandra, ScyllaDB, HBase, Google Bigtable) are distributed, **row-oriented** key-value stores built for huge write volumes and fast lookups by key. "Wide" means a row can have many columns, and different rows can have different columns. They serve applications: **OLTP** (online transaction processing), meaning many small reads and writes.
- **Columnar stores** (ClickHouse, BigQuery, Redshift, Snowflake, DuckDB, and the Parquet file format) store **each column's values together on disk**. They are built for analytical queries that scan and aggregate billions of rows. They serve analysts and dashboards: **OLAP** (online analytical processing).

The names come from different ideas. In a wide-column store, "column" is about the **data model** (flexible columns inside a row). In a columnar store, it is about the **physical layout** on disk. Cassandra stores a row's columns together; ClickHouse stores a column's rows together.

## Wide-column stores: Cassandra
Cassandra was built at Facebook for inbox search and is now used for messaging, time-series and event data at companies such as Apple, Netflix and Discord (which later moved to the Cassandra-compatible ScyllaDB). Its design goals are: accept writes at very high rates, scale linearly by adding nodes, and stay available when nodes or whole data centres fail.

### Design from the queries
Cassandra's data modelling rule is to **design from the queries, not from the entities**. There are no joins and only limited secondary indexes, so everything a query needs must be in one table, readable with one key lookup. The usual pattern is **one table per query**. The same data is written to several tables, each organised for a different query. That duplication is cheap because Cassandra writes are very fast.

### The primary key has two parts
- The **partition key** decides which nodes hold the data. Cassandra hashes it onto a ring of nodes using consistent hashing (lesson 04.07), and each partition is stored on a few replica nodes (typically 3). All rows with the same partition key live together on the same nodes.
- The **clustering columns** sort the rows **inside** a partition on disk. Reading a range of neighbouring rows ("messages after 10:00") is therefore one sequential read.

For a chat app: `PRIMARY KEY ((conversation_id), message_ts)`. The double parentheses mark the partition key. All of a conversation's messages are stored together, sorted by time, so "latest 50 messages in this conversation" reads one partition, one contiguous slice. To list magazines by publisher, you would make `publisher` the partition key and `id` a clustering column.

%%tree A Cassandra messages table: the partition key picks the replica nodes, and clustering columns keep rows sorted within each partition.
messages table
  partition (conv 77, 2026-03) | stored on nodes 2, 5, 9
    msg_ts 10:00:01 | from Ana, hi
    msg_ts 10:00:09 | from Raj, hello
    *msg_ts 10:01:30 | read slice starts here
  partition (conv 77, 2026-04) | stored on nodes 4, 6, 1
    msg_ts 09:12:44
  partition (conv 81, 2026-03) | stored on nodes 7, 3, 8
%%

### Two goals for the partition key
1. **Spread data evenly** across the cluster. A partition key with few values (country, status) piles data onto a few nodes.
2. **Read as few partitions as possible** per query, ideally exactly one.

The two goals pull against each other, and good modelling balances them. Keep partitions **bounded**: a common guideline is under about 100,000 rows and 100 MB per partition. A chat conversation that runs for years would grow without limit, so it is split into **buckets**, for example `PRIMARY KEY ((conversation_id, month), message_ts)`. Reading the latest messages then reads the current month's partition, and older history means stepping back one bucket at a time.

### Why writes are so fast
Cassandra uses a **log-structured merge tree** (LSM tree), not a B-tree. A write is appended to a **commit log** on disk (sequential, for durability) and inserted into an in-memory sorted table called a **memtable**. That is all; the client gets its acknowledgement. When the memtable fills, it is flushed to disk as an immutable sorted file called an **SSTable**. Background **compaction** merges SSTables to discard overwritten and deleted values. No write ever reads or rewrites a page in place, which is why a single node can absorb tens of thousands of writes per second. Reads pay instead: they may have to check the memtable and several SSTables, using Bloom filters (lesson 04.13) to skip files that cannot contain the key. Module 7 covers LSM trees in depth.

%%seq A Cassandra write on one replica: append to the commit log, insert into the memtable, acknowledge. Disk files are written later.
Client > Coordinator : INSERT message, consistency QUORUM
Coordinator > Replica : write
Replica > Replica : append to commit log
Replica > Replica : insert into memtable
Replica -> Coordinator : ack
Coordinator -> Client : success after 2 of 3 acks
Replica > Replica : later, flush memtable to SSTable
%%

Wide-column stores suit massive write volumes where data is read back by a known key and often by time range: messaging, time-series, telemetry, activity feeds, event logs.

## Columnar stores: ClickHouse
ClickHouse is a column-oriented database for OLAP: queries that aggregate over very large datasets, often needing answers in under a second.

### Row layout versus column layout
- **Row storage** keeps each row's fields together on disk. That is ideal for "fetch order 123 with all its fields" or "update this one row": one page read or write.
- **Column storage** keeps all the values of one column together, in a separate file per column. A query that touches 3 of a table's 100 columns reads only those 3 columns from disk and ignores the other 97.

%%compare The same orders table on disk: a row store keeps each order together; a column store keeps each field together.
[Row store]
Page: order1 all fields -> order2 all fields -> order3 all fields
+ Fetch one whole order: one read
+ Cheap single-row update
- SUM(amount) reads every field
[*Column store]
File amount: 19.9, 5.0, 42.0 ... -> File country: IN, IN, DE ...
+ SUM(amount) reads one file
+ Similar values compress 5 to 10 times
- Fetching one whole row touches every file
- Updates are expensive
%%

### Why columnar is so fast for analytics
Three effects multiply together.
1. **Read only the columns you need.** If the query uses 3 columns out of 100, you read about 3% of the data.
2. **Compression.** Values of one column are similar (country codes, timestamps that increase, prices in a narrow range), so they compress extremely well, often 5 to 10 times and sometimes far more. Run-length encoding turns "IN, IN, IN, IN" into "IN × 4"; delta encoding stores increasing timestamps as small differences. Less data on disk means less I/O.
3. **Vectorised execution.** The engine processes columns in batches of thousands of values with tight loops that suit modern CPUs (SIMD instructions), instead of interpreting one row at a time.

ClickHouse also keeps each table sorted by a chosen key and stores a **sparse index** (one entry per 8,192 rows) plus min/max values per block, so a filter on a date range skips most blocks without reading them.

For a feel of the speed: a query over 100 million rows of web analytics, filtering by region, date and phone model and grouping by model, ran in 92 ms, roughly a billion rows per second on one server.

%%bars Data read from disk for SUM(amount) WHERE country = 'IN' over 1 billion orders with 50 columns, about 200 bytes per row.
Row store, full scan | 200 | about 200 GB
Column store, 2 columns uncompressed | 12 | about 12 GB
*Column store, 2 columns compressed | 2 | about 2 GB
%%

### What columnar stores are bad at
Columnar stores are poor at frequent single-row updates and deletes (a change touches many column files, and ClickHouse handles them as heavy background "mutations"), at point lookups of whole rows, and at many tiny inserts (they prefer batches of thousands of rows). That is why they sit **next to** an OLTP database rather than replacing it. Data usually flows from the application database or event stream into the columnar store in batches or through a pipeline (Module 8).

## Side by side

! Example: one product, two stores
! A messaging app sends 50,000 messages per second. They are stored in Cassandra with `PRIMARY KEY ((conversation_id, bucket), message_ts)`. Opening a chat reads the newest 50 rows of one partition: one replica set, one sorted slice, about 5 ms.
! Every message event is also streamed, in batches of 100,000 rows, into ClickHouse. Analysts run "messages per country per day for the last year": 1.6 trillion rows in total, but the query reads just the `country` and `date` columns, compressed to a few bytes per row, and the sort key lets it skip irrelevant blocks. It returns in seconds on a cluster.
! Running the analytics query on Cassandra would mean reading every partition in the cluster. Running "open this chat" on ClickHouse would work, but each lookup would touch many column files and the tiny per-message inserts would overwhelm it. Different jobs, different stores.

! Example: sizing a Cassandra partition
! An IoT platform stores readings with `PRIMARY KEY ((sensor_id), ts)`. Each sensor reports every second: 86,400 rows a day, about 31 million a year. At 50 bytes per row, a year is 1.5 GB in one partition, far beyond the guideline of about 100 MB.
! Bucketing by day, `PRIMARY KEY ((sensor_id, day), ts)`, gives 86,400 rows and about 4.3 MB per partition. "Last hour for sensor 7" reads one partition; "last week" reads 7 partitions, which is still cheap and can be done in parallel.

## Common mistakes
- **Saying "Cassandra is columnar".** Its data model has flexible columns, but it is row-oriented on disk and terrible at analytical scans.
- **Modelling Cassandra like SQL**, with normalised tables and an expectation of joins.
- **Unbounded partitions**, such as all messages of a conversation forever in one partition.
- **Low-cardinality partition keys** that concentrate data on a few nodes.
- **Using a columnar store as the application database** and doing many single-row updates.

## In an interview
When asked to store high-volume events, separate the two needs out loud: an OLTP store keyed by the access pattern (wide-column, or sharded SQL) for serving users, and a columnar store fed by a stream for analytics. Name the partition key and clustering order for the first, and the sort key for the second.

> Takeaway: wide-column stores (Cassandra) are distributed, query-first, row-oriented stores for heavy writes and reads by partition key, with rows sorted inside each partition. Columnar stores (ClickHouse) store each column separately and compressed, so analytical scans read only the columns they need. Different jobs, often used side by side.

?? Cassandra is a wide-column store: rows are grouped into partitions by a hashed partition key spread across nodes and sorted inside each partition by clustering columns, and writes go through an LSM tree (commit log plus memtable), so it is built for huge write volumes and reading a known partition, an OLTP-style workload serving the application. ClickHouse is a columnar store: each column is stored separately and heavily compressed on disk, and queries are executed in vectorised batches, so analytical queries read only the few columns they need across billions of rows, an OLAP workload. Cassandra is bad at scans and aggregations; ClickHouse is bad at frequent single-row writes and updates. Cassandra serves the app; ClickHouse serves analytics.

@04.04
## The property graph model
A **graph database** stores data as a network instead of as tables. The most common model, the **property graph**, has three ingredients:
- **Nodes** are entities: a person, a product, a city, a bank card. Each node can carry one or more **labels** such as `Person` or `Card`, and any number of key-value **properties** (`name: "Ana"`, `country: "IN"`).
- **Relationships** (also called edges) connect two nodes. Each has a **type** (`FOLLOWS`, `BOUGHT`, `USED_CARD`), a **direction**, and optional properties of its own (`since: 2021`, `amount: 40`).
- **Properties** live on both nodes and relationships.

The key design choice is that **relationships are stored directly, as first-class data**. In Neo4j, each node record holds a pointer to its first relationship, and relationship records are chained together, so moving from a node to its neighbours is a matter of following pointers. This is called **index-free adjacency**: the cost of one hop depends on how many neighbours that node has, not on how big the whole database is. A relational join, by contrast, looks up matching rows in an index whose depth grows (slowly) with the size of the table, and the planner must decide how to join at every step.

The practical consequence is that a graph database can traverse millions of relationships per second on one machine, and the cost of a query depends on the part of the graph it touches, not on the total graph size.

%%tree A small property graph seen from Alice: nodes with labels and properties, and typed relationships with their own properties.
Alice | Person, country IN
  FOLLOWS since 2021 | to Bob
    Bob | Person
      FOLLOWS | to Carol
        *Carol | Person, likes jazz
          LIKES | to Post 9
  USED_CARD | to Card 4411
    Card 4411 | also used by Dave
%%

## Querying a graph
Graph databases have their own query languages. **Cypher** (Neo4j, and the basis of the ISO standard GQL) describes patterns with ASCII-art arrows. Gremlin is a step-by-step traversal language used by several other systems.

```
MATCH (me:Person {id: 1})-[:FOLLOWS*2..3]->(fof:Person)
WHERE fof.likes = 'jazz' AND NOT (me)-[:FOLLOWS]->(fof)
RETURN DISTINCT fof.name LIMIT 20
```
This reads: start at person 1, follow 2 to 3 `FOLLOWS` relationships, keep people who like jazz and whom I do not already follow. The `*2..3` is a **variable-length path**: the number of hops is part of the pattern, not hard-coded into the query's structure.

## Where SQL struggles
In SQL, a relationship is a foreign key, and following it is a **join**. One or two hops are perfectly fine with good indexes; this is what relational databases do all day. The trouble starts with queries that have **many hops** or an **unknown number of hops**:
- "Friends of friends of friends who like jazz."
- "Shortest path between two people" (degrees of separation).
- "Is account A connected to account B through any chain of shared devices, cards or addresses?" (fraud rings).
- "Every part that eventually depends on this component" (deep bill-of-materials) or "everyone who reports up to this VP" (org charts).

With a `follows(follower_id, followee_id)` table, three hops is three self-joins:
```
SELECT DISTINCT f3.followee_id
FROM follows f1
JOIN follows f2 ON f2.follower_id = f1.followee_id
JOIN follows f3 ON f3.follower_id = f2.followee_id
WHERE f1.follower_id = 1;
```
That is readable for a fixed three hops. But "anywhere from 1 to 6 hops", or "until you reach account B", needs a **recursive common table expression** (`WITH RECURSIVE`), which is awkward to write, hard to stop early, hard for the planner to estimate, and prone to revisiting the same nodes along different paths.

%%compare The same three-hop question in SQL and in a graph query language.
[SQL self-joins]
follows f1 -(join)-> follows f2 -(join)-> follows f3
- One join per hop, fixed in the query
- Variable hops need WITH RECURSIVE
- Planner struggles to estimate rows
+ Works in your existing database
[*Graph traversal]
(me)-[:FOLLOWS*1..3]->(x)
+ Hop count is a parameter
+ Follows stored pointers per node
+ Shortest path is built in
- A second database to run
%%

### The explosion of intermediate results
The deeper problem is not syntax; it is **fan-out**. If each person follows 200 others, one hop reaches 200 people, two hops reach up to 40,000 (200 × 200), and three hops up to 8 million, before removing duplicates. Every database, graph or relational, must deal with that growth. The difference is in how efficiently each hop is taken and whether the engine can prune, stop early or search from both ends at once (**bidirectional search**, which meets in the middle and turns 200^4 into 2 × 200^2 for a four-hop path).

%%bars How many paths a friends-of-friends query may touch when each person follows about 200 others.
1 hop | 200 | 200
2 hops | 40000 | 40,000
3 hops | 8000000 | 8 million
*4 hops | 1600000000 | 1.6 billion
%%

This is also why "6 degrees of separation" queries are expensive in any system: within 4 or 5 hops, a well-connected social graph reaches most of its members.

## Why interviews rarely need one
Reaching for a graph database is a common interview mistake. The word "social" in a prompt does not mean "graph database". Even companies built on social graphs keep their core relationships in relational or key-value storage: Facebook stores its social graph in sharded MySQL, behind a graph-shaped caching and API layer called TAO; Twitter built its follow graph service (FlockDB) on MySQL too. Most product features need exactly one hop:
- "Who do I follow?" and "who follows me?": an indexed edges table, `follows(follower_id, followee_id)`, with an index on each column (or the table stored twice, sharded once by each column).
- Follower and following **counts** are stored denormalised on the user row rather than counted on each request.
- "Do I follow this person?": a primary-key lookup on `(follower_id, followee_id)`.

One-hop queries on an indexed table take a millisecond and scale by sharding on the user ID (lesson 04.05). A graph database adds a new system to run and, as the next section explains, is much harder to shard.

## The decision boundary
Use a graph database when:
- The core value of the feature is **multi-hop traversal or path finding**, and the number of hops is variable.
- **Relationships themselves carry rich data** and are queried in flexible, exploratory ways.
- Typical examples: fraud detection over shared identifiers, network and IT dependency analysis ("what breaks if this switch fails?"), knowledge graphs, access-control graphs ("can this user reach this resource through any group?"), and recommendation exploration.

Do not use one when:
- Queries are mostly **one or two hops** with known shapes.
- You need **huge write throughput** or simple horizontal scaling. Partitioning a highly connected graph across machines is fundamentally hard: whatever cut you make, many edges cross machines, and every traversal across a cut becomes a network hop. Most graph databases scale reads with replicas but keep the full graph on each machine.
- The data is mostly **aggregations** ("total sales per region"), which graph engines are not built for.

%%matrix Common relationship questions and whether a graph database is the right tool.
Question | Hops | Graph DB worth it?
Who do I follow? | 1 | no, indexed edges table
Mutual friends with X | 2, fixed | no, two indexed lookups and intersect
People you may know | 2 to 3 | partial, often batch-computed
Fraud ring through shared devices | variable, up to 6 | yes
Shortest path between two users | variable | yes
What depends on this service? | variable, deep | yes
%%

A middle path that many teams use: keep the system of record in Postgres or a key-value store, and **export** the relationships into a graph database (or a graph processing framework run in batch) for the specific analytical questions that need deep traversal. The graph is then a derived, read-mostly copy that can be rebuilt.

! Example: fraud ring detection
! A payments company models accounts, cards, devices, phone numbers and IP addresses as nodes, with relationships like `(:Account)-[:USED]->(:Card)` and `(:Account)-[:LOGGED_IN_FROM]->(:Device)`. About 50 million accounts and 400 million relationships.
! Question: "which accounts are within 4 hops of this known fraudster through shared cards or devices?" In Cypher: `MATCH (f:Account {id: $id})-[:USED|LOGGED_IN_FROM*1..4]-(a:Account) RETURN DISTINCT a`. Because most cards and devices link only a few accounts, the traversal touches a few thousand nodes and returns in tens of milliseconds.
! In SQL, it is four rounds of self-joins across several link tables (account to card, card to account, account to device, device to account), with the combinations of link types multiplying the query size. A recursive CTE can do it but is slow and hard to bound.
! The main transaction ledger stays in Postgres. The graph is a separate store fed by account and login events, used by the fraud team's scoring service.

! Example: the follow graph that does not need a graph database
! A social app has 100 million users with an average of 300 follows each: 30 billion edges. Every query in the product is one hop: list followers, list following, check follow status, show counts.
! Store edges twice, as `following(user_id, followee_id, created_at)` sharded by `user_id`, and `followers(user_id, follower_id, created_at)` sharded by `user_id`. Each list is a single-shard range read; each check is a primary-key lookup. At about 40 bytes per row and two copies, that is about 2.4 TB, spread over 32 shards at 75 GB each.
! "People you may know" (friends of friends not yet followed) is computed nightly in a batch job and stored per user, so no live multi-hop query is needed.

## Common mistakes
- **Choosing a graph database because the data "is a graph".** All data with relationships is a graph; the question is whether you query it with deep traversals.
- **Ignoring fan-out.** Deep traversals on high-degree nodes (celebrities) explode in any engine; cap the depth and the per-node expansion.
- **Planning to shard a graph database like a key-value store.**
- **Moving the system of record into a graph database** for one analytical feature.

## In an interview
If the prompt involves relationships, ask how many hops the core queries need. One or two: an indexed edges table, sharded by user, with denormalised counts. Variable and deep: consider a graph database as a separate, derived store, and mention how you keep it in sync and how you bound traversal cost.

> Takeaway: graph databases store relationships as first-class data so that variable, multi-hop traversals and path queries are natural and fast. Most product features only need one or two hops, which an indexed edges table in SQL or a key-value store handles well and scales more easily.

?? Multi-hop and variable-length traversals, such as "friends of friends of friends who like jazz", the shortest path between two users, or finding every account connected to a known fraudster through any chain of shared cards or devices within 4 hops. In SQL each hop is another self-join on the edges table with fast-growing intermediate results, and a variable number of hops needs an awkward, hard-to-optimise recursive CTE. A graph database stores each node's relationships directly (index-free adjacency), so a query like MATCH (a)-[:FOLLOWS*1..3]->(b) follows pointers hop by hop with the hop count as a simple parameter, and offers path-finding built in.

@04.05
## Partitioning versus sharding
The two words are often used loosely, but they mean different things.
- **Partitioning** splits one big table into pieces **within one database**. Postgres can store an `orders` table as one partition per month. A query for March only reads the March partition (this is called **partition pruning**), and dropping a year of old data is dropping 12 partitions instead of deleting millions of rows. It makes a large table more manageable, but it does not add any hardware.
- **Sharding** splits data across **separate machines**, each holding a subset of the rows and taking a subset of the load. Each piece is a **shard**. This is the one that adds capacity: more disks, more memory, more CPUs, more write throughput.

In distributed databases such as Cassandra and DynamoDB, the pieces are called partitions even though they are on different machines, which is where the confusion comes from. In this lesson, "sharding" means spreading data across machines.

## When to shard
Shard when one machine cannot keep up with **storage**, **write throughput** or **read throughput**, even after query tuning, caching, a bigger machine and read replicas (lesson 03.10). Name the bottleneck before you shard; sharding to fix a missing index is a very expensive mistake.

Some reference numbers. 500 million users at 5 KB each is about 2.5 TB, which one well-provisioned Postgres server handles. Ten times that growth, or a sustained 50,000 writes per second at peak, probably does not. Other signs: backups and restores taking most of a day, index builds taking many hours, or vacuum unable to keep up (lesson 03.07).

## How a request finds its shard
Every sharded system needs a **routing** step: given a key, which shard holds it? The routing can live in a client library, in a proxy in front of the databases (Vitess's VTGate, a MongoDB `mongos` router), or inside the database itself (Cassandra and DynamoDB nodes route for you).

%%flow A request carries the shard key, and the router maps it to the one database that owns it.
[Route] Request user_id 9123 -> Router -(hash to logical shard 211)-> *Shard map: host 14
[Answer] *Host 14 -(query one shard)-> Result
%%

## Choosing a shard key
The **shard key** (also called the partition key) is the column whose value decides which shard a row lives on. It is the most important decision in a sharded design, because changing it later means moving every row. A good key has three properties:
- **High cardinality**: many distinct values. A boolean key gives you at most two shards; a country key gives you about 200, very unevenly sized.
- **Even distribution** of both data and traffic. Sharding by country fails if 40% of users are in one country. Sharding by creation time sends **all** new writes to the newest shard, so one machine does all the work while the rest sit idle.
- **Alignment with queries**: the most common queries should include the shard key, so they hit exactly one shard. Shard by `user_id`, and "get user profile", "get user's orders" and "get user's settings" each touch one shard.

A useful trick is to **co-locate** related tables by sharding them on the same key. If `users`, `orders` and `addresses` are all sharded by `user_id`, a user's orders join with their addresses inside one shard, and a transaction that touches all three stays on one machine. Notion did exactly this with workspace ID (lesson 03.10).

## Strategies
There are three ways to map key values to shards.

**Range-based**: each shard owns a contiguous range of key values, such as user IDs 1 to 1 million on shard A and 1 million to 2 million on shard B. Range scans over the key are efficient because neighbouring keys live together. The danger is that new data clusters on one shard if keys increase over time. It works well for multi-tenant systems where each tenant is a range, and it is how HBase, Bigtable and MongoDB's default ranged sharding work.

**Hash-based** (the usual default): compute `hash(key)` and use it to pick the shard. A good hash spreads keys evenly, so load is even even if the keys themselves are sequential. The cost: neighbouring keys end up on different shards, so range queries over the key must ask every shard. The naive `hash(key) % N` moves almost every key when N changes, so real systems use **consistent hashing** (lesson 04.07) or a large, fixed number of **logical shards** mapped to fewer physical machines.

**Directory-based**: a lookup service stores, for each key or group of keys, which shard holds it. It is the most flexible, because you can move one heavy customer to its own dedicated shard, but every request needs the lookup (usually cached), and the directory becomes critical infrastructure that must never be wrong or down.

%%compare Three ways to map keys to shards, for the same user_id key.
[Range]
user_id 1 to 1M -> Shard A
user_id 1M to 2M -> Shard B
+ Range scans on one shard
- New users all land on the newest shard
[*Hash]
hash(user_id) -> Logical shard -> Host
+ Even spread, even for sequential IDs
- Range queries hit every shard
[Directory]
Lookup table -> Shard per key or tenant
+ Move any tenant anywhere
- Extra lookup on every request
- Directory must never fail
%%

### Logical shards: plan for growth
Splitting a shard later is hard; moving a whole shard is easy (copy it, catch up, switch). So most systems create many more **logical shards** than they have machines, and place several logical shards on each machine. With 1,024 logical shards on 16 hosts, each host holds 64. Growing to 32 hosts means moving half the logical shards from each host to a new one, with no change to which logical shard any key maps to.

%%tree Logical shards decouple the key mapping from the hardware: keys map to one of 1,024 logical shards, and logical shards map to hosts.
hash(user_id) mod 1024
  Host 1 | logical shards 0 to 63
    shard 0
    shard 1
    shard 63
  Host 2 | logical shards 64 to 127
  *Host 16 | logical shards 960 to 1023
    move shards 992 to 1023 to new Host 17 when growing
%%

## What sharding costs
- **Cross-shard queries.** Anything not keyed by the shard key must ask every shard and merge the answers, a pattern called **scatter-gather**. A global "top 10 posts today" across 64 shards is 64 queries plus a merge, and its latency is set by the slowest shard. Handle these with caching, precomputation, a denormalised copy keyed differently (a secondary index table or a search index), or by accepting that rare admin queries are slow.
- **Cross-shard transactions.** A single database transaction cannot span shards. Two-phase commit is slow and blocks if the coordinator fails. Prefer data models where each transaction stays within one shard; otherwise use sagas with compensating steps (lesson 08.07).
- **Global constraints.** A unique constraint only holds within one shard. "Usernames must be unique" across shards needs a separate table sharded by username, or a lookup service.
- **Hot shards.** One celebrity can generate a thousand times normal traffic on one key (lesson 04.06).
- **Resharding.** Moving data while serving traffic needs double writes, backfills and verification (lesson 03.10), and application logic gets more complex everywhere.

%%seq A scatter-gather query: a request without the shard key asks every shard and waits for the slowest.
App > Shard 1 : top posts today, LIMIT 10
App > Shard 2 : top posts today, LIMIT 10
App > Shard 64 : top posts today, LIMIT 10
Shard 1 -> App : 10 rows, 8 ms
Shard 2 -> App : 10 rows, 9 ms
Shard 64 -> App : 10 rows, 140 ms, busy
App > App : merge 640 rows, keep top 10
%%

## Where the databases stand
- **Cassandra** hashes partition keys onto a ring with virtual nodes (lesson 04.07).
- **DynamoDB** hashes partition keys and splits partitions automatically as they grow in size or traffic.
- **MongoDB** shards by key ranges (optionally on a hashed key), with a balancer that moves chunks between shards.
- **Vitess** (MySQL) and **Citus** (Postgres) add sharding to relational databases, with a router that sends each query to the right shard.
- **Spanner and CockroachDB** split data into ranges automatically and move them around, while keeping SQL and transactions.

! Example: choosing a key for a chat app's messages table
! Candidates: `message_id`, `sender_id`, `conversation_id`, `created_at`.
! `created_at` sends every new message to the shard holding "now": one hot shard. `message_id` (hashed) spreads writes evenly, but loading one conversation's history must ask every shard. `sender_id` keeps a user's sent messages together, but a conversation's messages come from several senders, so loading a chat still touches several shards.
! `conversation_id` wins. Loading or paging a conversation, by far the most common query, hits one shard, and messages are ordered by time within it (in Cassandra, as a clustering column; lesson 04.03). With 500 million conversations, distribution is even except for a few huge group chats, which are bucketed by month.
! What it makes hard: "all messages sent by user X across all conversations" (for account export or moderation) and global search. Both are served from secondary stores keyed differently: a `messages_by_user` table sharded by `sender_id`, and a search index, both filled asynchronously from message events.

! Example: when does this app need to shard?
! 200 million messages a day at about 300 bytes each, plus indexes, is about 90 GB a day, or 33 TB a year. Writes average 2,300 per second, peaking near 10,000.
! The write rate alone would fit on one strong primary, but storage would not: a year of data far exceeds what one server should hold and back up. With 1,024 logical shards on 32 hosts, each host stores about 1 TB per year and takes about 300 writes per second at peak. Growing to 64 hosts later moves 16 logical shards per host, with no key remapping.

## Common mistakes
- **Sharding by time**, creating a single hot shard for all new writes.
- **A low-cardinality key** such as country or status.
- **Ignoring which queries become scatter-gather** until production.
- **As many shards as machines**, so growth means splitting shards instead of moving them.
- **Assuming unique constraints and transactions still work globally.**

## In an interview
Propose a shard key from the main access pattern, choose hash-based distribution with consistent hashing or logical shards, then say which queries the key makes hard and how you will serve them (secondary index tables, search, precomputation). Mention how you will grow, for example "start with 1,024 logical shards on 16 hosts".

> Takeaway: partitioning splits a table inside one database; sharding spreads data across machines. Pick a shard key with many values, even load, and alignment with your most common query, and use many logical shards so growth means moving shards, not splitting them. Every key makes some queries cross-shard: name them and plan how to serve them.

?? Shard the messages table by conversation_id (hashed, with many logical shards). One conversation's messages then live together on one shard, ordered by time, so loading or paginating a chat, the most common query, touches a single shard, and with hundreds of millions of conversations the load spreads evenly (very large group chats can be bucketed by month). It makes queries across conversations hard: "all messages sent by user X", account export, moderation by sender and global search must fan out to every shard. Serve those from secondary stores keyed differently, such as a messages_by_user table sharded by sender_id and a search index, filled asynchronously from message events.

@04.06
## What a hot partition is
A partitioned database (lesson 04.05) splits data by key and gives each partition a **share** of the system's capacity: a slice of one machine's CPU, disk and network. The design assumes traffic spreads roughly evenly across keys. If traffic concentrates on one key instead, the partition holding that key hits its limit while the others sit idle. Requests to it are **throttled** (rejected with "slow down" errors) or queue up and become slow, even though the system as a whole has plenty of spare capacity.

This is called a **hot partition**, **hot shard** or **hot key**. It is one of the most common ways real distributed databases fail, because the total load graphs look healthy right up to the moment one key melts.

Hot keys come from the real world, which is never uniform:
- **Celebrities**: a pop star posts and gets a million likes in a minute; their profile is read by millions of fans.
- **Events**: a flash sale on one product, a breaking news article, a ticket release for one concert.
- **Time**: a key based on today's date receives every one of today's writes.
- **Bots and bugs**: one misbehaving client or a retry loop hammering a single ID.

Traffic on social platforms is famously skewed: a few accounts can receive a thousand times the traffic of a typical one.

%%bars Requests per second on eight partitions during a viral moment. The table is at about 30% of total capacity, yet partition 7 is throttling.
Partition 1 | 250 | 250
Partition 2 | 300 | 300
Partition 3 | 220 | 220
Partition 4 | 280 | 280
Partition 5 | 260 | 260
Partition 6 | 240 | 240
*Partition 7 | 16700 | 16,700, limit 1,000
Partition 8 | 310 | 310
%%

## Uniformity matters, not the number of keys
What matters is how **uniformly** traffic spreads across partition key values, not how many key values exist. A table with a billion keys can still have one hot one.

| Partition key | Uniform? | Why |
| User ID, many active users | Good | Each user is a small share of traffic |
| Status code, a few values | Bad | "active" holds most rows and traffic |
| Creation date rounded to the day | Bad | All of today's writes hit one key |
| Device ID, similar traffic per device | Good | Even load |
| Device ID, one device far busier than the rest | Bad | That device's partition runs hot |

### The limits are per partition
In DynamoDB, each physical partition supports roughly **3,000 read units and 1,000 write units per second** (a write unit is one write of up to 1 KB), and stores up to 10 GB. So a single key is limited to about 1,000 small writes per second, **no matter how much capacity the table has**. DynamoDB softens short spikes with **burst capacity** (unused capacity saved from the last few minutes) and **adaptive capacity** (shifting unused throughput towards busy partitions, and eventually splitting a hot partition so its keys spread over more machines). These help with uneven-but-spread traffic. They cannot help a single item that needs 16,000 writes per second, because one key cannot be split.

Other systems have the same shape of limit: one Cassandra partition lives on its few replica nodes, and one Redis key lives on one shard's single thread.

## Write sharding
The standard fix for write-heavy hot keys is **write sharding**: spread one logical key across many physical keys, so the load lands on many partitions.

**Random suffix.** Instead of writing every order for 9 July to the key `2014-07-09`, write to `2014-07-09.1` through `2014-07-09.200`, choosing the suffix at random for each write. Writes spread evenly over 200 keys, and so over many partitions. The cost: reading all of that day's items means querying all 200 keys and merging the results, and you cannot look up a single item directly, because you do not know which suffix it got.

**Calculated suffix.** Derive the suffix from another attribute instead, such as `hash(order_id) % 200`. Writes still spread evenly, and now you **can** find one item: recompute its suffix from its order ID and read one key. Reading the whole day still fans out to all 200.

%%compare Two ways to spread one hot key across 200 physical keys.
[Random suffix]
Write -(random 1 to 200)-> key 2014-07-09.137
+ Perfectly even writes
- Single-item lookup must try all 200
- Full read fans out to 200 keys
[*Calculated suffix]
Write -(hash order_id mod 200)-> key 2014-07-09.42
+ Even writes
+ Single-item lookup recomputes the key
- Full read still fans out to 200 keys
%%

How many suffixes? Enough to keep each one comfortably under one partition's limit, and no more than readers can afford to query. For 16,000 writes per second against a limit of 1,000, you need at least 16; 32 or 64 gives headroom for growth and uneven randomness.

## Other tools for hot keys
### Sharded counters
A like or view counter is the classic hot key. Store the count as N separate counter keys: `likes:post123:0` to `likes:post123:63`. Each like increments a random one. Reading the total means summing 64 small values, which is cheap and can be cached. A background job can periodically roll the shards into a single total if reads are frequent.

### Buffer and batch
Instead of applying 18,000 increments of `+1`, collect them for a short window (in memory, or in a stream such as Kafka) and apply one update of `+18,000`. This turns a write rate problem into a tiny write rate. The cost is a delay of about the window length before the count is updated, and you must make the aggregation durable or accept a small loss on a crash.

%%seq Buffer and batch: thousands of like events are aggregated for one second and written as one increment per counter shard.
Clients > Stream : 16,700 like events per second
Stream > Aggregator : events for post 9, partitioned by post
Aggregator > Aggregator : sum for 1 second
Aggregator > Counter shard 5 : add 520
Aggregator > Counter shard 6 : add 515
Reader > Cache : like count for post 9

### Cache hot reads
A key that is **read** heavily, such as a celebrity profile, is best served from a cache. A single cache node can itself become hot, so very hot items are replicated across several cache nodes (append a random suffix to the cache key, or keep a small in-process cache on each app server for the top few hundred keys). Static content goes to a CDN.

### Isolate
Move known-hot keys (verified celebrities, the flash-sale product) to dedicated capacity: their own shard, their own cache cluster, or a separate code path. A directory-based shard map (lesson 04.05) makes this easy.

### Approximate
For display counts, a slightly stale or approximate number is fine. Nobody can tell 1,000,421 from 1,000,388, and "1M" is what the button shows anyway. Exactness matters for money and inventory, not for likes.

## Detecting hot partitions
Watch **per-partition or per-key** metrics, not just totals: throttled requests, latency per shard, and top keys by request rate. DynamoDB's CloudWatch Contributor Insights and Redis's `--hotkeys` option show the busiest keys. A table at 30% of provisioned capacity can still be throttling one key, and an average latency of 5 ms can hide one shard at 2 seconds. Alerts should fire on the worst partition, not the mean.

! Example: a viral like counter
! A post gets 1 million likes per minute: about 16,700 writes per second, far above one partition's limit of about 1,000.
! Design: each like event is written to a stream partitioned by `(post_id, random 0 to 31)`, so the stream's load is spread too. Aggregators read the stream, sum likes per post per second, and apply one increment per second to each of 32 counter shards: 32 writes per second instead of 16,700.
! The displayed count is the sum of the 32 shards, cached for 2 seconds. Whether a given user has liked this post (to show a filled heart, and to stop double likes) is stored separately under `(user_id, post_id)`, which is evenly distributed because each user likes each post at most once.
! Result: no partition sees more than a few hundred writes per second, and the count lags reality by at most 3 seconds.

! Example: the date key that melted on Black Friday
! An orders table in DynamoDB uses `order_date` as its partition key so the operations team can list a day's orders. On a normal day there are 200,000 orders, about 2 per second on average and 50 at peak: no problem.
! On Black Friday, peak traffic is 3,000 orders per second, all for the same date key. The partition is limited to about 1,000 writes per second, so two thirds of orders are throttled, and the checkout service's retries make it worse.
! Fix: partition key `order_date#(hash(order_id) mod 50)`. Each suffix receives about 60 writes per second at peak. Listing a day's orders becomes 50 parallel queries, which the operations dashboard can afford; looking up one order recomputes its suffix.

## Common mistakes
- **Judging health by total capacity** rather than per-partition load.
- **Time-based or low-cardinality partition keys** on write-heavy tables.
- **Exact, synchronous counters** for things users only see as "1.2M".
- **Too many suffixes**, making every read fan out to hundreds of keys for no benefit.
- **Caching a hot key on one cache node** and moving the hot spot instead of removing it.

## The rehashing problem
You have N cache servers (or database shards) and need every client to agree which server holds each key, without asking anyone. The simple formula is:
```
server = hash(key) % N
```
A good hash spreads keys evenly, every client computes the same answer, and lookups cost nothing. It works perfectly until **N changes**.

Take 4 servers and 8 keys. Removing one server changes the formula to `% 3`, and for most keys the remainder changes: in a typical example, 6 of the 8 keys now map to a different server. Adding a server has the same effect. For a cache, that is a disaster: most lookups suddenly go to a server that does not have the key, the cache **hit rate collapses**, and the full read load falls on the database behind it, often at the worst moment (you were adding a server because load was high). For a sharded database it is worse: most rows would have to be physically moved.

### How many keys move?
With modulo hashing, a key stays put only if `hash % N` and `hash % (N+1)` happen to agree, which is true for about 1 in N+1 keys. So going from N to N+1 servers moves about **N/(N+1)** of all keys. From 10 to 11 servers, about 10/11, or **91%**, of keys move.

The ideal is that only the new server's fair share moves: it should end up with 1/11 of the keys, so about **9%** should move to it, all other keys should stay where they are, and the 9% should come evenly from all existing servers.

%%bars Share of keys that change server when growing from 10 to 11 servers.
Modulo hashing | 91 | about 91% move
*Consistent hashing | 9 | about 9% move
%%

## The hash ring
**Consistent hashing** gets close to that ideal. The construction:
1. Take the output range of a hash function (for a 32-bit hash, 0 to 2^32 − 1; for SHA-1, 0 to 2^160 − 1) and imagine its two ends joined, forming a **ring**.
2. Hash each **server** (its name or IP address) to a position on the ring.
3. Hash each **key** to a position on the same ring. The key belongs to the **first server clockwise** from its position.

Each server therefore owns the **arc** of the ring between the previous server (counter-clockwise) and itself.

**Adding a server**: it lands somewhere on the ring and takes over only the keys between it and the previous server counter-clockwise. Those keys used to belong to the next server clockwise. Every other key stays where it was.

**Removing a server**: only its keys move, all to the next server clockwise. Everything else stays put.

To find which keys are affected by a change, walk counter-clockwise from the changed server to the previous one; only keys in that arc move. Try it below: add and remove servers and watch which keys change owner.

%%widget ring Each key belongs to the first server clockwise. Add or remove a server and only the keys in one arc move; more virtual nodes per server even out the load.
%%

### How a lookup works in code
In practice the ring is a **sorted array** of server positions. To find a key's server, hash the key and **binary search** for the first position greater than or equal to it, wrapping around to the first entry if you fall off the end. With 1,000 positions, that is about 10 comparisons: well under a microsecond. Every client holds the same array, built from the same server list, so they all agree without any coordination.

## Two problems with the basic ring
1. **Uneven arcs.** Servers are placed at pseudo-random positions, so some arcs are much longer than others. With few servers, one may own 3 times the share of another. Worse, when a server is removed, its whole arc goes to **one** neighbour, which can suddenly double that neighbour's load.
2. **Uneven key distribution.** Even with equal arcs, keys can cluster by chance on one arc.

### The fix: virtual nodes
Give each physical server many positions on the ring, called **virtual nodes** (vnodes), for example by hashing `"cache-07#0"`, `"cache-07#1"` up to `"cache-07#199"`. Each server now owns many small arcs scattered around the ring, and its total share is the sum of those arcs, which averages out close to 1/N.

%%tree Virtual nodes: each physical server appears at many scattered points on the ring, so its share is the sum of many small arcs.
Ring positions, sorted
  cache-01
    vnode at 0.03 | owns arc 0.01 to 0.03
    vnode at 0.41
    vnode at 0.77 | ... 150 vnodes in all
  cache-02
    vnode at 0.12
    vnode at 0.56
  *cache-11, new
    vnode at 0.09 | takes keys from cache-02's arc
    vnode at 0.63 | takes keys from cache-05's arc
%%

The effects:
- **Balance improves with more vnodes.** With 100 virtual nodes per server, the standard deviation of load is about 10% of the mean; with 200, about 5%.
- **Moves are spread out.** When a server leaves, its many small arcs go to many different neighbours, so the load spreads across the whole cluster instead of doubling one machine. When a server joins, it takes small slices from every existing server.
- **Heterogeneous hardware.** A machine with twice the memory can be given twice as many vnodes and so receives about twice the keys.

The cost is metadata: 100 servers × 200 vnodes is a sorted array of 20,000 entries, which is trivial for memory and lookup speed but means more ranges to track when data is physically moved (as in Cassandra, where each vnode's range is streamed separately).

## Replication on a ring
Distributed databases use the same ring to place **replicas**. Dynamo-style systems such as Cassandra store each key on the first server clockwise and then on the next **N − 1 distinct physical servers** clockwise (skipping further vnodes of servers already chosen). With a replication factor of 3, each key lives on three different machines, and losing one machine leaves two copies. Cassandra can also skip servers in the same rack or data centre so that replicas survive a rack failure.

## Where it is used
Consistent hashing is used by Amazon's Dynamo and by Cassandra and ScyllaDB for data partitioning, by Discord to route users to chat servers, by Akamai's CDN to pick cache servers, by Memcached client libraries (the "ketama" scheme), and in load balancers such as Google's Maglev, which uses a variant designed for fast lookup tables. Lesson 02.07 covers **bounded loads**, a variant that caps how much more than average any single server can receive, and how to handle hot keys on a ring by replicating or salting them (lesson 04.06).

## Alternatives worth knowing
%%matrix Ways to map keys to servers, compared on how many keys move when a server is added and what each costs.
Scheme | Keys moved on add | Even load | Lookup cost | Notes
hash mod N | about N/(N+1) | yes | O(1) | breaks on resize
Ring, no vnodes | about 1/N | no | O(log N) | arcs uneven
*Ring with vnodes | about 1/N | yes | O(log V) | widely used
Rendezvous hashing | about 1/N | yes | O(N) | no ring needed
Jump hash | about 1/N | yes | O(log N) | servers numbered 0 to N-1 only
Fixed slots, e.g. 16,384 | slots moved explicitly | yes | O(1) | moves are planned
%%

- **Fixed logical shards (slots)**: create far more shards than machines and move whole shards between machines when the cluster changes. Redis Cluster uses 16,384 hash slots; Notion uses 480 logical shards (lesson 03.10). It is simple to reason about, a slot-to-server table is tiny, and moves are explicit and controlled.
- **Rendezvous hashing** (also called highest random weight): for each key, compute a score `hash(key, server)` for every server and pick the highest. Removing a server only affects keys for which it scored highest, so about 1/N of keys move, with no ring at all. The cost is scoring every server on every lookup, which is fine for tens of servers.
- **Jump consistent hash**: a tiny algorithm that maps a key to one of N numbered buckets with minimal movement and no memory, but it only supports adding or removing the **highest-numbered** bucket, so it suits storage shards more than caches with arbitrary failures.

! Example: growing from 10 to 11 cache servers
! A cache holds 100 million keys across 10 servers and serves 200,000 reads per second at a 95% hit rate, so the database sees 10,000 reads per second.
! With modulo hashing, about 91 million keys change server. For the next several minutes the hit rate drops towards 9%, and the database suddenly receives about 180,000 reads per second, 18 times its normal load. It falls over, and the cache cannot refill because the database is down.
! With a ring and 150 virtual nodes per server, the new server takes about 9 million keys, roughly 900,000 from each existing server. The other 91 million stay put. The hit rate dips from 95% to about 86% and recovers as the new server warms up; the database sees about 28,000 reads per second for a few minutes. Annoying, not fatal.

! Example: what happens when one server dies
! A ring of 4 cache servers with no virtual nodes has arcs of 40%, 25%, 20% and 15% by chance. The 40% server dies. All of its keys move to its clockwise neighbour, the 25% server, which now owns 65% of keys and receives 65% of traffic. It overloads and dies too, and its 65% moves to the next server. This is a **cascading failure**.
! With 200 virtual nodes per server, each server owns about 25% ± 1.5%. When one dies, its 200 small arcs are spread across the other three, each going from about 25% to about 33%. A 33% increase is something to provision for; it does not cascade.

## Common mistakes
- **Using modulo hashing for anything that will be resized**, especially caches in front of a database.
- **A ring without virtual nodes**, which gives uneven load and cascading failure on node loss.
- **Clients with different server lists**, which then disagree about key ownership. The membership list must be distributed consistently (a configuration service, or gossip).
- **Forgetting hot keys.** Consistent hashing balances the number of keys, not the traffic per key.

When you introduce a cache cluster or shards, say how keys map to nodes: "consistent hashing with virtual nodes, so adding a node moves only about 1/N of keys, spread evenly", or "a fixed number of slots moved explicitly". Give the numbers for one change, and mention that replicas go to the next distinct nodes on the ring.

> Takeaway: modulo hashing remaps almost every key when the server count changes, which can collapse a cache and overload the database behind it. A hash ring remaps only about 1/N of keys, those in one arc, and virtual nodes make both the steady-state split and the redistribution after a change even.

## The problem
On a single database, an auto-increment primary key is close to perfect. It is **unique** (the database's counter never repeats), **compact** (an 8-byte integer), **ordered by creation** (row 1,001 was created after row 1,000), and **free** (no extra service, no extra round trip).

Once data is **sharded** across many databases (lesson 04.05), each shard has its own counter, and they all start at 1. Shard 3 creates tweet 5,000 and so does shard 9. Several things break at once:
- **Uniqueness.** An ID no longer identifies one row. URLs like `/tweet/5000`, cache keys, foreign references from other tables and messages in queues all become ambiguous.
- **Moving data.** Rebalancing a user from shard 3 to shard 12 copies rows whose IDs may already exist on shard 12.
- **Merging data.** An analytics warehouse that combines all shards sees duplicate keys.
- **Ordering.** There is no global creation order: shard 9's ID 5,000 may be hours newer than shard 3's ID 7,000.
- **Location.** An ID tells you nothing about where the row lives, so you need a separate lookup to find it.

Twitter hit exactly this in 2010. Moving tweets from a single MySQL setup to Cassandra and sharded MySQL meant losing automatic IDs. The service it built, **Snowflake**, became the template most large systems still follow.

## What we want from IDs
Twitter's requirements for the new IDs are a good checklist for any system:
- **Unique** across all machines, forever, including across data centres.
- **Fits in 64 bits**, so it works as a compact integer key everywhere. A larger ID would have meant changing every system, client and database column that stored tweet IDs as 64-bit integers.
- **Roughly time-ordered**, so that sorting by ID approximates sorting by creation time. Timelines are sorted newest first, and if IDs follow time, "tweets newer than ID X" is a simple range query.
- **High throughput**: at least 10,000 IDs per second per process, with headroom for spikes.
- **High availability and low latency**: ID generation is on the critical path of every write, so it must never block or be a single point of failure.

## The options
%%matrix The main ways to generate IDs across shards, against the requirements above.
Option | Unique | 64 bits | Time-ordered | No per-ID network hop | No single point of failure
Central auto-increment | yes | yes | yes | no | no
Multi-master with step | yes | yes | no | no | yes
UUID v4 | yes | no | no | yes | yes
Coordination service | yes | yes | yes | no | partial, a quorum
*Snowflake style | yes | yes | yes, roughly | yes | yes
%%

**Central auto-increment.** One database hands out every ID. It is simple and strictly ordered, but every insert anywhere needs a round trip to it, it caps throughput at what one machine can do, and when it is down, nothing can be written anywhere.

**Multi-master auto-increment with a step.** N databases each increment by N with different offsets: one issues 1, 3, 5..., the other 2, 4, 6.... Flickr's ticket servers (lesson 03.09) are this idea with two dedicated servers, and block allocation makes it fast. But IDs from different servers are not time-ordered (one server can race ahead of the other), and changing N later is painful. Twitter rejected it mainly for the lack of ordering.

**UUIDs.** A 128-bit identifier generated anywhere with no coordination; the common version 4 is 122 random bits. Collisions are so unlikely they can be ignored. But it is twice the size of a 64-bit integer, it is not time-ordered, and random values scatter inserts across B-tree indexes (lesson 04.09). Twitter rejected UUIDs as too big.

**A coordination service.** ZooKeeper or etcd can hand out sequential numbers through a consensus protocol. The IDs are strictly ordered, but every ID costs a network round trip to a quorum of servers (milliseconds), throughput is limited, and the service is a dependency on every write. Twitter rejected it for performance and availability.

%%seq Asking a coordination service for every ID puts a consensus round trip on every write; a Snowflake-style generator answers locally.
App > Coordinator : next ID please
Coordinator > Quorum : agree on sequence number
Quorum -> Coordinator : agreed
Coordinator -> App : 1,000,042, about 2 ms later
App > Local generator : next ID please
Local generator -> App : time + machine + sequence, about 1 µs
%%

**Snowflake style.** Each generator builds IDs locally from three parts: the **current time** in milliseconds, its own **machine number**, and a **sequence** counter that resets every millisecond. Two generators can never produce the same ID because their machine numbers differ; one generator never repeats because the time or the sequence always moves forward. There is no network call per ID, the result fits in 64 bits, and because time is in the most significant bits, IDs sort roughly by creation time. This is what Twitter built. Lesson 04.10 breaks down the bits, and lesson 04.11 covers the hard part, which is clocks.

The price of Snowflake-style IDs is that each generator needs a **unique machine number**, assigned and kept unique (usually through configuration or a coordination service at startup, not per ID), and its **clock must not go backwards**.

## Instagram's variation
Instagram needed IDs for photos sharded across thousands of logical Postgres shards, and did not want to run a separate ID service. It generated Snowflake-like 64-bit IDs **inside Postgres itself**, with a stored function used as each table's default value:
- **41 bits**: milliseconds since a custom epoch (enough for about 69 years).
- **13 bits**: the **logical shard ID** (up to 8,192 shards).
- **10 bits**: a per-shard sequence, taken modulo 1,024, so each shard can create 1,024 IDs per millisecond.

%%tree The bits of an Instagram-style ID: time first, so IDs sort by creation, then the shard, then a per-shard sequence.
64-bit photo ID
  *41 bits | milliseconds since custom epoch
  13 bits | logical shard ID, 0 to 8,191
  10 bits | sequence mod 1,024, per shard per ms
%%

Embedding the shard ID is the clever part: **any ID tells you which shard holds the row**. Given a photo ID, the service shifts out the shard bits and queries that shard directly, with no directory lookup. Because generation happens in the same database transaction as the insert, there is also no extra round trip at all.

## Why "roughly" ordered is enough
Strict global ordering requires a single point that decides the order, which is exactly the bottleneck we are trying to remove. Snowflake IDs are instead **k-sorted**: IDs generated within a small window of each other (about a second, given clock differences between machines) may be out of order relative to each other, but IDs generated further apart always sort correctly.

%%timeline Two generators with clocks 3 ms apart. IDs created within a few ms of each other can sort out of order; IDs further apart never do.
[Machine A, clock fast by 3 ms] real 10:00:00.000 | issues ID with time .003
[Machine B, accurate] real 10:00:00.001 | *issues ID with time .001, sorts before A's
[Machine B, accurate] real 10:00:00.010 | issues ID with time .010
[Machine A, clock fast by 3 ms] real 10:00:01.000 | issues ID with time 1.003, sorts after all above
%%

That is good enough for nearly every purpose:
- **Timelines**: a few milliseconds of disorder between tweets from different people is invisible to users.
- **Index locality**: new IDs are always near the "end" of the B-tree, so inserts touch a small, hot, cached set of pages (lesson 04.09).
- **Pagination**: "IDs less than X" pages through history by time (lesson 04.12).

What it is not good enough for: anything that needs a guaranteed order of events, such as "this payment happened before that refund". Use a sequence within one shard or a log for that.

! Example: putting the shard in the ID
! A photo app has 2,048 logical shards. Each photo ID is laid out as 41 bits of milliseconds, 11 bits of shard, and 12 bits of sequence. With 12 sequence bits, each shard can create 4,096 IDs per millisecond.
! To find a photo, the service computes `shard = (id >> 12) & 0x7FF`. For an ID whose middle 11 bits hold 731, the request goes straight to logical shard 731, which the shard map places on host 23. No directory service, no cache lookup.
! IDs still sort roughly by upload time, so "newest photos by this user" is an index range scan on `(user_id, id DESC)`, and the ID itself doubles as a creation timestamp: `(id >> 23) + epoch` gives the upload time to the millisecond.

! Example: why the central counter fails at scale
! A social app creates 30,000 objects per second at peak (posts, comments, likes, messages) across 64 shards.
! With a central auto-increment database, each insert first makes a 1 ms round trip to it. That adds 1 ms to every write, and the central database must sustain 30,000 durable commits per second on its own, which needs group commit and a fast log disk. If it fails over (30 seconds), every write in the whole system fails for 30 seconds.
! With Snowflake-style generators running in each app server's process, each ID takes about a microsecond, the 64 shards are independent, and losing any one machine affects only that machine's writes.

## Common mistakes
- **Keeping auto-increment after sharding** and discovering collisions during the first data move.
- **Choosing UUIDv4 by default** without considering index performance and size (lesson 04.09).
- **Assuming time-ordered IDs are strictly ordered** across machines.
- **Assigning machine IDs by hand** and accidentally running two generators with the same one, which produces duplicates.
- **Exposing sequential IDs publicly** when they leak business volume (competitors can count your orders); consider an opaque public ID as well.

Optionally put the shard number in the ID so routing needs no lookup, and mention that clocks must not run backwards.

> Takeaway: sharding breaks auto-increment because each shard counts independently, so IDs collide, lose their global order and say nothing about where a row lives. The common answer is 64-bit, roughly time-ordered IDs built locally from the time, a machine or shard number, and a per-millisecond sequence.

## UUIDs and their versions
A **UUID** (universally unique identifier) is a 128-bit value designed to be unique without any coordination: any machine can generate one at any time, and it will not collide with any other in practice. It is usually written as 32 hexadecimal digits in five groups, such as `0190f2a4-6b3c-7d21-9a4e-3f5c8b7e1d02`. A few bits in fixed positions record the **version** (how the rest was generated) and the **variant** (the layout family).

The current standard, RFC 9562 (published 2024), defines these versions:
- **v1**: a 60-bit timestamp (in 100-nanosecond steps since 1582) plus a node ID, often the machine's MAC address. It leaks hardware identity, and the timestamp bits are stored in an awkward order (low bits first), so v1 values do not sort by time.
- **v3 and v5**: a hash (MD5 for v3, SHA-1 for v5) of a namespace and a name. The same input always gives the same UUID, which is useful for deterministic IDs such as "the UUID for this URL".
- **v4**: 122 random bits. By far the most common today.
- **v6**: v1's fields reordered so the value sorts by time. Meant for systems already using v1.
- **v7**: a 48-bit Unix timestamp in milliseconds first, then 74 bits of randomness (or a counter). Recommended for new systems that want time-ordered keys.
- **v8**: a free-form layout for custom schemes.

### How unique is random?
With 122 random bits, there are about 5.3 × 10^36 possible v4 values. By the birthday bound, you would need to generate about 2.7 × 10^18 UUIDs (a billion per second for 85 years) for a 50% chance of even one collision. In practice, collisions come only from broken random number generators (for example, two virtual machines cloned with the same random seed), not from the maths.

## How a B-tree reacts to the order of keys
A B-tree index (lesson 03.04) keeps its keys **sorted**. Where a new key goes is decided entirely by its value. That makes the **order in which keys are generated** matter a great deal for insert performance.

**Sequential or time-ordered keys** (auto-increment, Snowflake, UUIDv7): each new key is larger than every existing key, so every insert goes to the **rightmost leaf page**. That one page, plus the path of branch pages above it, stays permanently in memory. It fills up, and the database starts a new page next to it. Postgres and InnoDB both recognise this pattern and split the rightmost page by leaving the old page full instead of half full, so the index ends up densely packed, close to 90 to 100% full.

**Random keys** (UUIDv4): each insert lands on a random leaf **anywhere** in the index. On a small table that does not matter: the whole index is in memory. On a large table, most leaf pages are not in memory, so an insert must first **read a random page from disk**, then modify it, and later write it back. The cache is constantly churned by pages that are each touched once. Full pages split in the middle, leaving two half-full pages, so the index settles at around **70% full** on average and is correspondingly larger. More pages also means more dirty pages at each checkpoint, and with Postgres's full-page writes (lesson 03.08), the first change to each page after a checkpoint writes the whole 8 KB page to the WAL, so random keys can multiply WAL volume several times over.

%%compare Where inserts land in a large primary-key index with random keys versus time-ordered keys.
[UUIDv4, random]
New key -(random position)-> Any of 10M leaf pages
- Most target pages not cached: disk read per insert
- Mid-page splits leave pages about 70% full
- Many dirty pages, much more WAL
[*UUIDv7 or Snowflake, time-ordered]
New key -(always largest)-> Rightmost leaf page
+ Same few pages stay hot in memory
+ Pages fill to near 100%
+ Few dirty pages per checkpoint
%%

This effect is the main reason UUIDv6 and v7 were added: values that are not time-ordered, such as v4, scatter inserts across database indexes and can significantly hurt performance, while time-ordered v7 values cluster together and sort correctly as raw bytes.

### Reads suffer too
Rows created at about the same time are usually read together: today's orders, this week's events, a user's recent posts. With time-ordered keys, those rows sit in neighbouring index pages (and, in InnoDB, where the table is clustered by primary key, in neighbouring table pages). With random keys, "the 1,000 newest orders" are spread over 1,000 different pages.

### And size matters
A UUID is 16 bytes; a 64-bit integer is 8. The difference is repeated in the primary key index, in every **secondary index** (in InnoDB each secondary index entry carries the primary key), and in every **foreign key** column that references the row and its index. Storing a UUID as a 36-character string instead of a native 16-byte type more than doubles it again. Flickr gave index size as a reason to avoid GUIDs (lesson 03.09).

%%bars Approximate primary-key index size for 1 billion rows, combining key size and how full the pages end up.
BIGINT, sequential | 22 | about 22 GB

## UUIDv7 in detail
- **Bits 0 to 47**: Unix time in milliseconds. Because these are the most significant bits, sorting the raw bytes sorts by creation time.
- **4 bits**: the version, 7.
- **12 bits**: random, or a sub-millisecond fraction or counter.
- **2 bits**: the variant.
- **62 bits**: random.

That gives 74 bits that can be random. If a generator creates many IDs in one millisecond and wants them strictly increasing, it can use some of those bits as a **counter** that increments within the millisecond, seeded randomly. A generator must never return a duplicate: if the counter overflows, it waits for the clock to advance (the same rule as Snowflake, lesson 04.11).

%%layers UUIDv7's 128 bits from most to least significant. Time comes first, so values sort by creation time.
*Unix time in ms | 48 bits
Version, 7 | 4 bits
Random or counter | 12 bits
Variant | 2 bits
Random | 62 bits
%%

You get coordination-free generation like v4, and the index locality of sequential keys. Postgres 18 added a built-in `uuidv7()` function, and libraries exist for every major language.

The trade-off: **the creation time is visible** in the ID. Anyone who sees an ID can read when the record was created, and by comparing two IDs they may infer rates (how many signups happened between two accounts, for example, if they can sample many IDs). If that matters, use v7 internally and a separate random or encrypted ID in public URLs.

## MongoDB's ObjectId
An **ObjectId** is the 12-byte ID MongoDB generates by default for each document's `_id`:
- **4 bytes**: seconds since the Unix epoch.
- **5 bytes**: a random value chosen once per process.
- **3 bytes**: a per-process counter, starting at a random value.

Because the timestamp comes first, ObjectIds sort roughly by creation time, but only to the **second**. Within one second, IDs from the same process are ordered by the counter, but IDs from different processes interleave arbitrarily. Do not rely on them for strict ordering; use them as roughly time-ordered unique keys.

## Comparing the options
%%matrix The common ID types compared on the properties that matter for a primary key.
ID | Size | Time-ordered | Needs coordination | Leaks creation time
Auto-increment | 8 bytes | yes, strictly on one DB | yes, one database | partial, and row counts
UUIDv4 | 16 bytes | no | no | no
UUIDv7 | 16 bytes | yes, ms | no | yes
ObjectId | 12 bytes | partial, seconds | no | yes
Snowflake | 8 bytes | yes, roughly ms | partial, unique worker IDs | yes
%%

! Example: an events table outgrows memory
! An events table receives 5,000 inserts per second with a UUIDv4 primary key. The server has 64 GB of RAM for the buffer pool.
! At 200 million rows the primary key index is about 9 GB and fits in memory: inserts take about 0.2 ms. At 2 billion rows it is about 90 GB, well beyond the buffer pool. Now roughly 70% of inserts must read their target leaf page from disk first. At 0.1 ms per SSD read, that is fine in isolation, but 3,500 random reads per second from inserts alone compete with every query. WAL volume has also grown about 4 times because each checkpoint interval touches millions of distinct pages, each logged in full the first time. Insert latency climbs to 3 ms and replicas lag.
! Switching new rows to UUIDv7 (same column type, so no schema change) makes every insert hit the newest few pages, which stay cached. Index growth slows because pages fill completely, WAL volume drops back, and insert latency returns to about 0.2 ms. Old v4 rows remain valid; the index is simply random in its old part and ordered in its new part.

! Example: the cost in a join-heavy schema
! An orders table with 500 million rows is referenced by `order_items` (3 billion rows) and `payments` (500 million rows), each with an index on `order_id`.
! With a 16-byte UUID instead of an 8-byte integer, every reference grows by 8 bytes: 3.5 billion references × 8 bytes = 28 GB of extra column data, plus about the same again in the foreign-key indexes. That is roughly 56 GB more to store, back up, replicate and, above all, cache. If the hot part of the database was 60 GB and the server has 64 GB of RAM, the extra size can be the difference between serving from RAM and serving from disk.

## Common mistakes
- **Using UUIDv4 primary keys on large, write-heavy tables** without measuring the effect on index size and cache hit rate.
- **Storing UUIDs as strings** (`VARCHAR(36)`) instead of a native 16-byte type.
- **Assuming ObjectId or Snowflake order is exact** across processes.
- **Exposing v7 or Snowflake IDs publicly** when creation time is sensitive.
- **Generating UUIDs from a weak random source**, the only realistic way to get collisions.

## In an interview
If you choose UUIDs, say which version and why: "UUIDv7, so generation needs no coordination but inserts stay at the end of the B-tree". If an interviewer asks why v4 is slow, explain the three effects: random leaf pages that are not cached, half-full pages from mid-page splits, and extra WAL. Mention the 16-byte size cost in every index and foreign key.

> Takeaway: random UUIDv4 keys scatter inserts across a B-tree, causing cache misses, mid-page splits, half-empty pages and extra log volume once the index outgrows memory. Time-ordered IDs (UUIDv7, ObjectId, Snowflake) keep inserts at the end of the index, where pages stay hot and fill completely.

?? A B-tree keeps keys sorted, so where an insert goes depends on the key's value. UUIDv4 values are random, so each insert lands on a random leaf page anywhere in the index. Once the index is larger than memory, most of those pages are not cached, so inserts cause random disk reads and churn the cache; full pages split in the middle and settle around 70% full, making the index bigger; and many distinct pages are dirtied, multiplying write-ahead log volume (full-page writes). UUIDv7 puts a 48-bit millisecond timestamp in its most significant bits, so each new key is larger than the previous ones and always goes to the rightmost leaf pages, which stay in memory and fill sequentially to nearly 100%, just like an auto-increment key, while still needing no coordination to generate.

## Twitter's design
**Snowflake** is the ID generator Twitter built in 2010 when it moved tweets off a single MySQL database (lesson 04.08). Each ID is made of three parts: a **timestamp**, a **worker number** and a **sequence number**. Worker numbers are assigned once, when a generator starts, through ZooKeeper (a coordination service) or a configuration file. After that, generating an ID needs **no coordination at all**: it is a few lines of arithmetic on local state. That is what gives Snowflake its throughput and availability.

Twitter's requirements were specific:
- At least **10,000 IDs per second per process**, with a response time of about 2 ms or better including the network hop to the generator service.
- **No coordination** between generating machines.
- IDs **k-sorted**: roughly time-ordered, with any disorder bounded (Twitter promised within 1 second and aimed for tens of milliseconds).
- **Sortable without loading the objects**, so clients and services can order tweets by ID alone.
- **Under 64 bits**, so the IDs fit in the signed 64-bit integers used everywhere in Twitter's code and in many client languages.

## The 64 bits
| Bits | Field | Meaning |
| 1 | Sign | Always 0, so the ID is a positive signed integer |
| 41 | Timestamp | Milliseconds since a custom epoch |
| 10 | Machine | Configured worker ID; later designs often split it into 5 bits of data centre and 5 bits of worker |
| 12 | Sequence | Counter within the same millisecond on this machine |

That is 63 bits of content. The top bit stays 0 so the value is a positive number in languages that only have signed 64-bit integers (Java's `long`, for example).

%%tree The bits of a Snowflake ID, from most significant to least. Time comes first so that IDs sort by creation time.
Snowflake ID, 64 bits
  Sign, 1 bit | always 0
  *Timestamp, 41 bits | ms since custom epoch
  Machine, 10 bits | up to 1,024 generators
    Data centre, 5 bits | optional split, up to 32
    Worker, 5 bits | up to 32 per data centre
  Sequence, 12 bits | 0 to 4,095 within one ms
%%

### What those sizes give you
- **41 bits of milliseconds**: 2^41 ms is about 2.2 × 10^12 ms, or **69.7 years**. Counting from 1970 would waste 40 of those years, so Snowflake uses a **custom epoch**, a start date close to the system's launch (Twitter's is in November 2010). Twitter's IDs will run out around 2080.
- **10 machine bits**: 2^10 = **1,024** generators running at once.
- **12 sequence bits**: 2^12 = **4,096 IDs per millisecond per machine**, which is about 4.1 million per second per machine.

Across all 1,024 machines, the theoretical ceiling is about 4.2 billion IDs per second, far beyond what Twitter, or almost anyone, needs. The real limit is how fast one generator process can run its loop, which is millions per second.

If a single machine needs a 4,097th ID within the same millisecond, it **waits** (spins) until the clock reaches the next millisecond, then resets the sequence to 0. At 4 million IDs per second per machine, that is rare.

## Generating an ID
The generator keeps two pieces of state: `last_ts`, the timestamp of the last ID it issued, and `seq`, the sequence used within that millisecond.

```
def next_id():
    now = current_millis()
    if now < last_ts:               # clock went backwards (lesson 04.11)
        now = wait_until(last_ts)
    if now == last_ts:
        seq = (seq + 1) & 0xFFF     # 12-bit wrap
        if seq == 0:                # 4,096 used this ms
            now = wait_until(last_ts + 1)
    else:
        seq = 0
    last_ts = now
    return ((now - EPOCH) << 22) | (machine_id << 12) | seq
```
The final line is the whole encoding: shift the time left by 22 bits (10 + 12) to put it above the machine and sequence fields, shift the machine ID left by 12 to put it above the sequence, and combine with bitwise OR. The function must be called under a lock (or from a single thread) so that two callers never read the same `seq`.

%%state The generator's decision on each call, based on the current time compared with the last timestamp it used.
[*] -> Read clock
Read clock -> Same ms : now equals last_ts
Read clock -> New ms : now after last_ts
Read clock -> Clock went back : now before last_ts
Same ms -> *Issue ID : seq + 1 fits in 12 bits
Same ms -> Wait for next ms : seq overflowed
Wait for next ms -> New ms : clock ticks
New ms -> *Issue ID : seq reset to 0
Clock went back -> Wait for next ms : small jump
%%

### Assigning machine IDs
The whole scheme rests on **no two running generators ever having the same machine ID**. If they did, both would produce identical IDs whenever their clocks and sequences coincided, which at high rates is constantly. Common ways to assign them:
- **ZooKeeper or etcd at startup**: each generator claims a free number by creating a lock node, holds it while running, and releases it on exit. If a process dies, its claim expires after a session timeout before the number can be reused.
- **Configuration**: a fixed number per host, managed by deployment tooling. Simple, but risky when containers are rescheduled.
- **Derived from the environment**: for example the pod's ordinal in a Kubernetes StatefulSet, or the low bits of a private IP address (which risks collisions if addresses are reused).

%%seq Machine IDs are coordinated once at startup; after that, every ID is generated locally.
Generator > ZooKeeper : claim a free worker ID
ZooKeeper -> Generator : you are worker 37
Generator > Generator : issue IDs locally, millions per second
App > Generator : next ID
Generator -> App : 562,036,736,000,151,557
Generator > ZooKeeper : heartbeat keeps claim alive
%%

## Properties
- **Roughly sorted ("k-sorted")**: within one machine, IDs are strictly increasing. Across machines, IDs from the same millisecond interleave arbitrarily, and small clock differences between machines mean ordering is only approximate. Twitter aimed for a disorder bound well under one second.
- **Time is recoverable**: shift the ID right by 22 bits and add the epoch to get the creation time to the millisecond. Useful for debugging ("when was this created?") and for time-range queries by ID ("all tweets after ID X is all tweets after time T").
- **No central bottleneck**, but machine IDs must be unique and clocks must not go backwards (lesson 04.11).
- **Compact**: 8 bytes, the same as a `BIGINT` auto-increment key, so indexes stay small and inserts land at the end of the B-tree (lesson 04.09).
- **Guessable**: anyone can read the creation time from an ID, and IDs are dense enough to estimate volumes. That is acceptable for tweets, and a reason to use an opaque public ID for some other data.

## Tuning the layout
The split of bits is a design choice, not a law. You trade **lifetime** (timestamp bits), **number of generators** (machine bits) and **per-generator throughput** (sequence bits) against each other within 63 bits.

%%matrix Some well-known variants of the Snowflake layout and what each trades.
Scheme | Time bits and unit | Machine bits | Sequence bits | Notes
Twitter Snowflake | 41, 1 ms | 10 | 12 | 69 years, 4,096 per ms per machine
Discord | 42, 1 ms | 10, worker + process | 12 | epoch 2015, same idea
Instagram | 41, 1 ms | 13, logical shard | 10 | ID reveals its shard
Sonyflake | 39, 10 ms | 16 | 8 | 174 years, 65,536 machines, 25,600 per s each
%%

- Fewer machine bits and more sequence bits suit a **few very busy** generators.
- More machine bits suit **many small** generators, such as one per container in a large fleet.
- Coarser time units (Sonyflake's 10 ms) buy a longer lifetime but reduce precision and per-machine burst rate.
- Instagram replaced the machine field with a 13-bit **logical shard ID**, so every ID says which shard holds its row (lesson 04.08).

! Example: decoding an ID
! ID = 562,036,736,000,151,557.
! Timestamp: shift right by 22 bits. 562,036,736,000,151,557 ÷ 4,194,304 = 134,000,000,000 (rounded down). So the ID was created 134,000,000,000 ms after the custom epoch, which is about 4.25 years after it.
! Machine: shift right by 12 and keep the low 10 bits. 562,036,736,000,151,557 − (134,000,000,000 × 4,194,304) = 151,557. Then 151,557 ÷ 4,096 = 37 remainder 5. So the machine ID is 37.
! Sequence: the low 12 bits, the remainder: 5. This was machine 37's sixth ID in that millisecond (the sequence starts at 0).

! Example: will the layout last, and is it fast enough?
! A system plans 300 generator instances (well under 1,024) and peak traffic of 500,000 new IDs per second in total. Spread evenly, each instance needs about 1,700 per second, or under 2 per millisecond against a capacity of 4,096 per millisecond. Even a single instance taking all the traffic would only need 500 per millisecond.
! With a custom epoch of 1 January 2026, the 41-bit timestamp runs out in late 2095. If the team expects the system to need more than 69 years, or more than 1,024 generators (say 5,000 containers), they could take 2 bits from the sequence (leaving 1,024 per ms) and give them to the machine field (4,096 generators): a layout decided once, at design time.

## Common mistakes
- **Duplicate machine IDs**, the fastest way to produce duplicate IDs.
- **Using the 1970 Unix epoch**, wasting 56 years of a 69-year range.
- **No lock around the sequence** in a multi-threaded generator.
- **Treating IDs as strictly ordered across machines.**
- **Storing IDs as JavaScript numbers.** JavaScript's numbers are exact only up to 2^53, so 64-bit IDs lose precision; APIs send them as strings (Twitter added an `id_str` field for exactly this reason).

## In an interview
Draw the 64 bits, give the field sizes and say what each buys: 41 bits of milliseconds is about 69 years from a custom epoch, 10 bits is 1,024 generators, 12 bits is 4,096 IDs per millisecond per generator. Mention that machine IDs are assigned once at startup and that the generator waits if the sequence overflows or the clock goes back.

> Takeaway: Snowflake packs a sign bit, 41 bits of milliseconds since a custom epoch, 10 bits of machine ID and 12 bits of per-millisecond sequence into a 64-bit integer: about 69 years of range, 1,024 generators, 4,096 IDs per millisecond per machine, and no coordination per ID once machine IDs are assigned.

?? 1 sign bit, always 0 so the ID is positive; 41 bits of milliseconds since a custom epoch (2^41 ms is about 69 years); 10 bits of machine ID (1,024 generators, often split into 5 bits of data centre and 5 bits of worker); and 12 bits of sequence that counts IDs within the same millisecond on that machine. So each machine can generate 2^12 = 4,096 IDs per millisecond, about 4 million per second; if it needs more within one millisecond it waits for the next millisecond and resets the sequence. ## Computer clocks are not reliable
A Snowflake ID (lesson 04.10) puts the current time in its top 41 bits and relies on one promise: **a generator never issues the same timestamp and sequence twice**. That promise depends on the clock never running backwards. Unfortunately, computer clocks are far less reliable than most people assume.

Every computer keeps time with a **quartz crystal** oscillator, which ticks at a nominal frequency. Real crystals are slightly off and their error changes with temperature. The error is called **drift** and is measured in **parts per million (ppm)**. One ppm is one microsecond per second, which is about **86 ms per day**. Typical server clocks are within about 50 ppm, so an unsynchronised clock can wander by **4 seconds a day**. Two machines left alone for a week can disagree by most of a minute.

### NTP and how it corrects the clock
**NTP** (Network Time Protocol) keeps clocks close to a reference. A client sends a request to a time server, records four timestamps (when it sent, when the server received, when the server replied, when it received the reply), and estimates both the network round trip and its own **offset** from the server's time. The estimate assumes the delay is the same in both directions. When it is not (a congested uplink, a different route back), the error goes straight into the offset. In good conditions in one data centre, NTP keeps machines within a millisecond or a few; over the internet, tens of milliseconds; under bad conditions, far worse. Cloud providers now offer more precise time services, some within microseconds, but no clock is ever exactly right.

How the NTP daemon applies a correction depends on how far off the clock is:
- Offset under about **128 ms**: **slew** the clock. It runs slightly fast or slow (by at most 500 ppm, so about half a millisecond per second) until it has caught up. Time keeps moving forwards, just at a slightly different rate.
- Offset between about 128 ms and 1,000 seconds: **step** the clock, jumping it straight to the right time. If the clock was ahead, **this moves it backwards**.
- Offset over 1,000 seconds: assume something is badly wrong and give up, leaving it to an operator.

Other things also step clocks: an administrator running `date -s`, a virtual machine being paused and resumed or live-migrated to another host, a container starting with a wrong clock and syncing a minute later.

%%bars How far a clock can be off in different situations, in milliseconds.
NTP in one data centre | 1 | about 1 ms
NTP over the internet | 30 | tens of ms
Typical step-back event | 50 | tens to hundreds of ms
*Unsynced for a day at 50 ppm | 4320 | about 4.3 s
%%

### Leap seconds
To keep clocks aligned with the Earth's rotation, a **leap second** has occasionally been added, making some days 86,401 seconds long. Unix time cannot represent the extra second, so systems typically **repeat** a second, which means time goes backwards by one second. The leap second of 30 June 2012 triggered a Linux kernel bug that sent many Java and MySQL processes into 100% CPU loops and caused outages at several large websites. Many companies now **smear** the extra second, slowing their clocks very slightly over many hours so time never repeats. Leap seconds are due to be abolished by 2035, but backward steps from other causes remain.

## Two kinds of clock
Operating systems offer two different clocks, and confusing them causes real bugs.
- A **time-of-day clock** (wall clock), such as Java's `System.currentTimeMillis()`, Unix `gettimeofday()` or `CLOCK_REALTIME`, returns the date and time. It is comparable across machines (roughly), but it can **jump forwards or backwards** when NTP steps it.
- A **monotonic clock**, such as Java's `System.nanoTime()` or `CLOCK_MONOTONIC`, only ever moves forwards. NTP may slew its rate but never steps it. Its absolute value is meaningless (often the time since boot) and cannot be compared between machines.

%%compare The two clocks every operating system provides, and what each is safe for.
[Time-of-day clock]
currentTimeMillis, CLOCK_REALTIME
+ Comparable across machines, roughly
+ Gives a calendar date
- Can jump backwards on NTP step
- Unsafe for measuring durations
[Monotonic clock]
nanoTime, CLOCK_MONOTONIC
+ Never goes backwards
+ Right for timeouts and elapsed time
- Value means nothing on another machine
- Resets on reboot
%%

Rule of thumb: **measure durations with the monotonic clock**, and use the wall clock only when you need an actual date or a value other machines will interpret. A timeout computed from the wall clock can fire instantly or never if the clock steps.

A Snowflake generator needs the **wall clock**, because its timestamps must be comparable across machines and must survive restarts. So it must handle backward jumps explicitly.

## What a Snowflake generator should do when the clock goes back
Suppose the last ID used timestamp 1,000 ms with sequence 17, and the clock now reads 995 ms. If the generator simply carried on, it would issue IDs with timestamp 995 and sequence 0, 1, 2.... Five milliseconds ago it may already have issued `(995, 0)`, `(995, 1)` and so on, so these would be **duplicate IDs**: two different tweets, or two payments, with the same primary key. Depending on the system, that means a failed insert, an overwritten row, or a cache returning the wrong object.

The options:
- **Refuse and wait.** Twitter's original implementation refused to generate IDs until the clock had passed the last timestamp it used, returning an error in the meantime. For a 5 ms jump, waiting 5 ms is trivial and callers barely notice.
- **Keep using the last timestamp.** Treat time as not having moved: keep issuing IDs with timestamp 1,000 and sequence 18, 19, 20.... When the sequence reaches 4,095, wait for the real clock to pass 1,000. This never blocks for small jumps at normal rates, IDs keep increasing, and it is safe. Its only cost is that a few IDs carry a timestamp a few milliseconds in the "future".
- **Large jumps: stop and alert.** If the clock went back by more than some threshold (100 ms, or a second), something is wrong with time sync on that machine. Waiting a minute would block all writes through this generator, so it is better to fail health checks, take the instance out of service and page someone.
- **Persist the last timestamp across restarts**, or at least refuse to start until the clock is past the time of the previous shutdown. Otherwise a generator could crash, restart after a backward step, and reuse timestamps from before the crash. An alternative is to take a fresh worker ID on every restart, so old IDs cannot collide with new ones.

%%seq A generator facing a 5 ms backwards step keeps issuing from its last timestamp instead of reusing old ones.
Caller > Generator : next ID
Generator > Clock : read time
Clock -> Generator : 1,000 ms
Generator -> Caller : ID (1,000, seq 17)
Clock > Clock : NTP steps back 5 ms
Caller > Generator : next ID
Generator > Clock : read time
Clock -> Generator : 995 ms, behind last
Generator -> Caller : ID (1,000, seq 18), metric logged
%%

Prevention helps too. Configure NTP (or chrony) to **slew rather than step** whenever possible, start generators only after the clock is synchronised, and monitor clock offset on every machine.

%%matrix Strategies for a backwards clock, compared on safety and impact.
Strategy | No duplicates | Blocks callers | Handles large jumps
Ignore it | no | no | no
Refuse until caught up | yes | yes, for the jump length | no, blocks for long
Keep last timestamp | yes | only if sequence runs out | partial
Alert and stop above threshold | yes | yes, instance removed | yes
%%

## Why IDs only give rough order
Even with perfect generators, two machines' clocks differ by some milliseconds. An event on machine A can get a smaller timestamp than an event on machine B that happened **after** it, even one **caused** by it: a user posts a tweet (machine A, clock 3 ms fast) and a reply arrives 2 ms later through machine B (accurate clock). The reply's ID is smaller than the tweet's.

So physical timestamps cannot reliably order events across machines. Distributed systems use the **happens-before** relation instead: A happens before B if they are on the same machine in that order, or A sent a message that B received, or through a chain of such steps. **Lamport clocks** capture it with counters: each process increments its counter for each event, attaches it to every message, and on receiving a message sets its counter to the larger of its own and the received value, plus one. If A caused B, A's counter is guaranteed to be smaller (Module 6 covers this and vector clocks). Google's Spanner takes a different route: its TrueTime API returns an interval with a guaranteed error bound, and the database waits out the uncertainty before committing.

Snowflake IDs are fine for "roughly by time". If you need **causal** order, you need logical clocks or a single sequencer, such as one partition of a log.

%%timeline A reply whose ID sorts before the tweet it replies to, because machine A's clock runs 3 ms fast.
real 12:00:00.000 | Tweet created on machine A, ID time .003
real 12:00:00.001 | *Reply created on machine B, ID time .001
real 12:00:00.002 | Sorting by ID shows the reply first
%%

! Example: handling a 5 ms backward jump
! The last ID used timestamp 1,000,250 ms with sequence 17. NTP steps the clock back, and it now reads 1,000,245.
! The generator keeps issuing IDs with timestamp 1,000,250 and sequence 18, 19, 20.... At the current rate of 300 IDs per millisecond, the 4,096 sequence values last about 13 ms, longer than the 5 ms the clock needs to catch up, so no caller ever waits.
! When the real clock passes 1,000,250, the generator returns to normal. A metric records a 5 ms backward jump. Alerts fire if any jump exceeds 100 ms, and the instance fails its health check if one exceeds 1 second.

! Example: the restart that would have caused duplicates
! A generator issues IDs up to timestamp T = 10:00:00.900, then crashes. The machine's clock was 2 seconds fast; on reboot NTP steps it back, and the generator restarts at 10:00:00.200 by the corrected clock.
! Without protection, the next 700 ms of IDs reuse timestamps from 10:00:00.200 to 10:00:00.900, which this machine ID already used. At 2,000 IDs per second, about 1,400 IDs could duplicate earlier ones.
! With protection, the generator writes a high-water mark to local disk once a second, always one second ahead of its clock, so the last value saved before the crash is 10:00:01.900 or earlier but never below any timestamp it used. On restart it reads that mark and refuses to issue IDs until the clock passes it: about 1.7 seconds of downtime for this instance, while the load balancer sends traffic elsewhere. No duplicates.

## Common mistakes
- **Assuming the wall clock only moves forwards.**
- **Measuring timeouts or durations with the wall clock.**
- **Ignoring restarts**, where the generator forgets its last timestamp.
- **Using timestamps to order events across machines**, such as "last write wins" with wall-clock times, which silently drops writes when clocks disagree.
- **No monitoring of clock offset**, so a drifting machine goes unnoticed until it causes duplicates or ordering bugs.

## In an interview
When you propose Snowflake-style IDs, raise clocks before you are asked: NTP can step the clock back; the generator must never reuse a timestamp, so it keeps using its last timestamp (or waits) for small jumps, alerts and stops for large ones, and persists its last timestamp across restarts. Add that IDs are only roughly ordered across machines, and causal order needs logical clocks.

> Takeaway: wall clocks drift and can jump backwards (NTP steps, leap seconds, VM pauses, restarts). A Snowflake generator must never reuse a timestamp: for small jumps, keep issuing from the last timestamp or wait for the clock to catch up; for large jumps, stop and alert; and remember the last timestamp across restarts.

?? It must not issue IDs with the earlier timestamps, because it may already have used those (timestamp, sequence) pairs, and reusing them would create duplicate IDs. For a small 5 ms jump it should either wait until the clock passes the last timestamp it used (Twitter's original approach, a delay of about 5 ms), or keep using the last timestamp and keep incrementing the sequence, waiting only if the 4,096 sequence values for that millisecond run out. It should record a metric and log the event, and refuse to generate (failing health checks and alerting) if a backward jump is large, such as more than 100 ms to a second. It should also persist its last timestamp so a restart after a backward step cannot reuse old timestamps.

## How OFFSET pagination works
Almost every list in an application is paginated: a feed, search results, an admin table, an API that returns 20 items at a time. The most common way to write it is with `LIMIT` and `OFFSET`:
```
SELECT id, title, created_at FROM posts
ORDER BY created_at DESC
LIMIT 20 OFFSET 200000;
```
This asks for page 10,001 (rows 200,001 to 200,020). It reads naturally: "skip 200,000, take 20". What the database actually does is very different. It has no way to jump to "the 200,001st row", because an offset is just a count and carries no information about where that row is. So it **produces the first 200,020 rows in order, throws away 200,000 of them and returns 20**.

Even with a perfect index on `created_at`, the database must walk 200,020 index entries and usually fetch the corresponding rows (to evaluate filters or columns) before discarding them. So:
- **Each page is slower than the last.** Cost grows linearly with page depth. Page 1 reads 20 rows; page 100 reads 2,000; page 10,000 reads 200,000.
- **Deep pages are expensive for everyone.** A crawler or a bot paging through an API to the end can produce queries that each read millions of rows, and a few of them can saturate a database.

%%bars Rows the database reads to return one page of 20, as the user pages deeper.
OFFSET, page 1 | 20 | 20
OFFSET, page 100 | 2000 | 2,000
OFFSET, page 10,000 | 200000 | 200,000
OFFSET, page 100,000 | 2000000 | 2 million
*Keyset, any page | 20 | 20
%%

### The correctness problem
OFFSET is also **wrong** on data that changes. The position "row 41" is recomputed on every request. If a new post is inserted at the top while a user is reading page 2, every later row shifts down by one place. The request for page 3 (`OFFSET 40`) now starts one row earlier than it would have, so the user **sees the last row of page 2 again**. A deletion has the opposite effect: everything shifts up, and one row is **skipped**, never shown at all. On a busy feed where many posts arrive per second, users see duplicates and gaps constantly.

%%timeline A new post arrives while a user is paging with OFFSET, so the next page repeats a post the user has already seen.
10:00:00 | User loads page 1, posts 1 to 20
10:00:05 | User loads page 2, posts 21 to 40
10:00:07 | *New post inserted at the top
10:00:09 | User loads page 3 with OFFSET 40
10:00:09 | Old post 40 is now row 41: shown again
%%

## Keyset (seek) pagination
**Keyset pagination**, also called **seek pagination** or cursor pagination, fixes both problems. Instead of saying "skip N rows", the client says "**give me rows after the last one I saw**". It sends back the sort values of the last row on the current page, and the query uses them in a `WHERE` clause.

With one unique sort column, it is simple:
```
SELECT id, title FROM posts
WHERE id < :last_id
ORDER BY id DESC
LIMIT 20;
```

With a sort column that is **not unique**, such as a timestamp or a date, you must add a **unique tie-breaker** column, because paging needs a fully determined order. If 50 posts share the same `created_at` and a page boundary falls among them, "after this timestamp" would skip the rest. Adding the ID makes every position unique:
```
SELECT sale_id, sale_date, amount FROM sales
WHERE (sale_date, sale_id) < (:last_date, :last_id)
ORDER BY sale_date DESC, sale_id DESC
FETCH FIRST 10 ROWS ONLY;
```
served by an index on `(sale_date, sale_id)`.

### Row value comparisons
The `(a, b) < (x, y)` syntax is a **row value** comparison. It compares `a` with `x` first, and only if they are equal does it compare `b` with `y`: the same as sorting by `a` then `b`. Support varies:
- **Postgres** (and Db2) evaluate it correctly and use a composite index to seek directly to `(x, y)`.
- **MySQL** evaluates it correctly, but historically cannot always use the index for it, so check the plan.
- **SQL Server** does not support row value comparisons. There you write the equivalent by hand: `sale_date <= :d AND NOT (sale_date = :d AND sale_id >= :id)`. The first part, `sale_date <= :d`, gives the optimiser a range it can seek on.

## Why it stays fast
With keyset pagination the database uses the index to **jump straight to the position just after the last-seen key** (a B-tree descent, lesson 03.04: 3 or 4 page reads), then reads the next 20 entries in order and stops. The cost is the same on page 1 and on page 10,000. Measurements on real databases show OFFSET response time climbing steadily with the page number, clearly visible from about page 20 onwards, while keyset stays flat.

%%tree How the index serves a keyset query: descend once to the last-seen key, then read forward along the leaf chain.
Index on (created_at DESC, id DESC)
  Root page
    Branch page | covers 2025-03-01
      Leaf page | ... 10:22:07 id 98251, 10:22:05 id 98240
      *Leaf page | seek lands after 10:22:05 id 98213
        10:22:05 id 98190 | row 1 of next page
        10:22:04 id 98177 | row 2, read on to 20
%%

It is also **stable**. The position is defined by **values**, not by counting rows from the top. A post inserted at the top since the last request has a newer timestamp, so it is simply not "after" the cursor and does not shift anything. A deleted row is just absent. No duplicates, no gaps.

%%compare OFFSET pagination versus keyset pagination for a feed.
[OFFSET]
Skip N rows -(read and discard N)-> Return 20
+ Jump to any page number
+ Trivial to implement
- Cost grows with page depth
- Inserts and deletes cause repeats and gaps
[*Keyset]
Seek past last key -(index descent)-> Return 20
+ Same cost on every page
+ Stable while data changes
- No jump to page 500
- Needs an index matching ORDER BY
%%

## Trade-offs
- **No jumping to an arbitrary page number.** You can only go to the next page (or previous). That suits infinite scroll and "next" links, which is what most feeds and APIs use. A "page 1 2 3 ... 500" control needs OFFSET or a different design. In practice nobody reads page 500; offer search and filters instead.
- **Going backwards** needs the comparison and sort order reversed (`> :first_key ORDER BY ... ASC`), then the results reversed again for display.
- **The client must carry the keyset values.** In an API, wrap them in an **opaque cursor token** (lesson 02.01), such as base64-encoded JSON, so clients cannot depend on its contents and you can change the encoding later. Sign or encrypt it if the values are sensitive.
- **The index must match.** Filters and sort order need an index whose columns match the `WHERE` and `ORDER BY`: equality filters first, then the sort columns in order, including the tie-breaker. For a user's feed, `(user_id, created_at, id)`.
- **Total counts are separate.** "Showing 20 of 1,284,331" needs a `COUNT(*)`, which is expensive on large tables whatever the pagination method. Use an estimate or omit it.

## Combining both
Some interfaces want both: fast infinite scroll for most users, and occasional deep jumps. A common compromise allows OFFSET only up to a small maximum (say 50 pages), and uses keyset beyond that. Elasticsearch takes the same approach: `from` and `size` are limited to 10,000 results by default, and deeper paging uses `search_after`, which is keyset pagination over the sort values.

! Example: a feed API
! First request: `GET /feed?limit=20` runs `WHERE user_id = 7 ORDER BY created_at DESC, id DESC LIMIT 20`, served by an index on `(user_id, created_at, id)`. The last row returned has `created_at = 2025-03-01T10:22:05Z` and `id = 98213`.
! The response includes `next_cursor = base64("2025-03-01T10:22:05Z|98213")`.
! Next request: `GET /feed?limit=20&cursor=...`. The server decodes the cursor and runs `WHERE user_id = 7 AND (created_at, id) < ('2025-03-01T10:22:05Z', 98213) ORDER BY created_at DESC, id DESC LIMIT 20`. The database descends the index to `(7, 10:22:05, 98213)`, reads the next 20 entries and stops: about 4 index pages and 20 rows, the same as page 1.
! When fewer than 20 rows come back, the server omits `next_cursor`, and the client knows it has reached the end.

%%seq A cursor-based API: the server hands out an opaque cursor with each page, and the client sends it back to get the next one.
Client > API : GET /feed?limit=20
API > DB : WHERE user_id = 7 ORDER BY created_at, id DESC LIMIT 20
DB -> API : 20 rows, last is (10:22:05, 98213)
API -> Client : items + next_cursor
Client > API : GET /feed?cursor=...
API > DB : WHERE (created_at, id) < (10:22:05, 98213) LIMIT 20
DB -> API : next 20 rows, same cost
API -> Client : items + next_cursor
%%

! Example: the export job that took the database down
! A nightly job exports 10 million orders with `OFFSET` pages of 1,000. Page n reads n × 1,000 rows, so the job reads 1,000 + 2,000 + ... + 10,000,000 rows: about 10,000 × 10,000 × 1,000 / 2 = 50 billion rows in total, for an export of 10 million. It runs for 14 hours and slows production queries all night.
! Rewritten with keyset (`WHERE id > :last_id ORDER BY id LIMIT 1000`), each page reads 1,000 rows. The whole job reads 10 million rows, 5,000 times less, and finishes in about 6 minutes. The same pattern is the right way to write batched backfills (lesson 03.12).

## Common mistakes
- **Keyset on a non-unique column without a tie-breaker**, which skips or repeats rows at page boundaries.
- **An index that does not match the sort order**, so each "seek" becomes a scan plus sort.
- **Exposing raw keyset values** in the API instead of an opaque cursor.
- **Using OFFSET for batch jobs and exports.**
- **Building deep page-number navigation** that nobody uses but every crawler hammers.

## In an interview
Whenever you design a list endpoint, say "cursor-based (keyset) pagination": the cursor encodes the last item's sort key plus a unique ID, the query seeks with `(sort_key, id) < (cursor values)` on a matching index, and every page costs the same. Mention that it also avoids duplicates when new items arrive, which matters for feeds.

> Takeaway: OFFSET makes the database read and discard every skipped row, so deep pages get slower and slower, and inserts or deletes cause repeated or missing rows. Keyset pagination seeks past the last-seen key through an index: constant cost on every page and stable results while data changes, at the price of no random page jumps.

?? With OFFSET the database has no way to jump to the Nth row, so it must produce every earlier row in order and discard it: page 10,000 of 20 rows reads about 200,000 index entries and rows to return 20, so cost grows linearly with depth (and inserts shift rows, causing duplicates and gaps). Keyset pagination remembers the last row's sort values and uses WHERE (sort_key, id) < (last values) ORDER BY sort_key, id with a matching composite index, so the database descends the B-tree straight to that position (3 or 4 page reads) and reads only the next 20 entries. The cost is the same on page 1 and page 10,000, and results stay stable because the position is defined by values, not by counting rows.

## The problem a Bloom filter solves
Many systems repeatedly ask "is this item in the set?" where the honest answer is usually **no**, and finding out is expensive. A database checks whether a key might be in a data file before reading the file from disk. A web crawler checks whether it has already visited a URL among billions. A URL shortener checks whether a requested code exists before querying the database. Storing the whole set in memory would answer exactly, but a billion URLs at about 100 bytes each is 100 GB.

A **Bloom filter**, invented by Burton Bloom in 1970, answers set membership in a tiny fraction of that memory, at the cost of sometimes being wrong in **one direction only**. It can say "**definitely not in the set**" or "**maybe in the set**". It never says "definitely in the set".

## The structure
A Bloom filter has two parts:
- An array of **m bits**, all starting at 0.
- **k hash functions**, each mapping an item to one bit position between 0 and m − 1.

**Adding** an item: hash it with all k functions and set those k bits to 1. Bits that are already 1 stay 1.

**Checking** an item: hash it with the same k functions and look at those k bits.
- If **any** bit is 0, the item was **definitely never added**. Adding it would have set that bit to 1, and bits are never cleared.
- If **all** k bits are 1, the item is **probably** in the set.

Nothing about the items themselves is stored: no keys, no pointers, only bits. That is where the memory saving comes from.

%%seq Adding two items to a 16-bit filter with three hash functions, then checking two items that were never added.
App > Filter : add "cat"
Filter > Filter : h1, h2, h3 give 2, 7, 11: set to 1
App > Filter : add "owl"
Filter > Filter : 3, 9, 14: set to 1
App > Filter : contains "dog"? bits 3, 7, 10
Filter -> App : bit 10 is 0: definitely not
App > Filter : contains "fox"? bits 2, 9, 14
Filter -> App : all 1: maybe, a false positive
%%

## Why it cannot say "definitely present"
Bits are **shared**. Every item sets bits in the same array, and those bits are never cleared. An item you never added may hash to k positions that **other** items happened to set. In the trace above, "fox" was never added, but bit 2 was set by "cat" and bits 9 and 14 by "owl". The filter has no record of which item set which bit, so it cannot tell whether those 1s came from "fox" or from others. All it can honestly say is "maybe". That wrong "maybe" is a **false positive**.

**False negatives are impossible**: if an item was added, its k bits were set to 1 at that moment, and nothing ever sets them back to 0. So every check for an added item finds all 1s.

The same fact explains why a standard Bloom filter **cannot delete** items. To remove "cat" you would clear bits 2, 7 and 11, but bit 7 might also belong to another item, which would then start failing its checks: a false negative, breaking the one guarantee the filter offers. Variants fix this at a cost:
- A **counting Bloom filter** stores a small counter (typically 4 bits) per position instead of one bit. Adding increments, deleting decrements. It uses about 4 times the memory.
- A **cuckoo filter** stores short fingerprints of items in a hash table, supports deletion, and is often smaller than a Bloom filter at low error rates. Redis's probabilistic module offers both Bloom and cuckoo filters.

%%matrix Exact and approximate ways to answer "is X in the set?", for one billion items.
Structure | Memory for 1 billion items | False positives | False negatives | Delete
Hash set of the items | about 100 GB | no | no | yes
Bloom filter at 1% | about 1.2 GB | yes, 1% | no | no
Counting Bloom filter | about 4.8 GB | yes | no | yes
Cuckoo filter at 1% | about 1.1 GB | yes | no | yes
%%

## Sizing it
Three numbers describe a Bloom filter: n items, m bits and k hash functions. The false positive rate after inserting n items is approximately:
- p ≈ (1 − e^(−kn/m))^k

The intuition: after n insertions of k bits each, the chance that a particular bit is still 0 is about e^(−kn/m). A false positive needs all k checked bits to be 1. For a given m/n, too few hash functions leave too few bits to check; too many fill the array with 1s. The **best number of hash functions** is:
- k = (m/n) × ln 2, which is about 0.69 × bits per item.

At that optimum, the bits needed per item for a target error rate p is about 1.44 × log2(1/p). Useful rules of thumb:
- About **10 bits per item with 7 hash functions** gives roughly a **1%** false positive rate.
- Each extra **4.8 bits per item** divides the error rate by 10.
- **Halving** the error rate costs only about **1.44 extra bits** per item.

%%bars Bits needed per item for a target false positive rate, with the best number of hash functions.
10% false positives | 4.8 | 4.8 bits, k = 3
1% | 9.6 | 9.6 bits, k = 7
*0.1% | 14.4 | 14.4 bits, k = 10
0.01% | 19.2 | 19.2 bits, k = 13
%%

So a billion items at 1% needs about 9.6 billion bits, **1.2 GB**, compared with around 100 GB to store the items themselves. Try changing the numbers below and watch how the false positive rate responds.

%%widget bloom How the false positive rate depends on bits per item and the number of hash functions, plus a tiny filter to add items to and test.
%%

### The sizing process
1. Estimate **n**, the number of items, with headroom for growth. A Bloom filter cannot grow: if you add many more items than planned, the error rate climbs steeply. At double the planned n, a 1% filter's error rate rises above 10%.
2. Choose the target false positive rate **p** from what a false positive costs (an extra disk read? an extra database query?).
3. Compute **m** = −n × ln(p) / (ln 2)^2 and **k** = (m/n) × ln 2, rounded.
4. If the data keeps growing, plan to rebuild the filter periodically, or use a **scalable Bloom filter** that adds new, larger filters as it fills.

### Hashing
Use fast non-cryptographic hashes such as MurmurHash, xxHash or FNV, not SHA-1 or MD5, which are several times slower and add nothing here. You do not need k independent hash functions either: compute two hashes h1 and h2 and derive the rest as h1 + i × h2 (the **double hashing** trick), with almost no loss in accuracy. Insert and lookup are both O(k), independent of how many items are stored.

## Where they are used
The pattern is always the same: **a cheap, in-memory check in front of an expensive operation**, where a "no" saves the expensive work, and an occasional false "maybe" only costs one wasted lookup that gives the real answer.

%%flow A point read in an LSM-tree database: a Bloom filter per data file lets the read skip files that cannot contain the key.
[Read key 42] Memtable -(miss)-> Filter SSTable 1 -(definitely not)-> Filter SSTable 2 -(maybe)-> *Read SSTable 2 from disk
%%

- **LSM-tree databases** (RocksDB, Cassandra, ScyllaDB, HBase) keep a Bloom filter for each immutable data file. A read for a key checks each file's filter first and skips files that definitely lack the key, so most point reads touch at most one file on disk (lesson 04.03 and Module 7).
- **Web crawlers**: "have I already crawled this URL?" across billions of URLs. A false positive means one page is not crawled, which is acceptable.
- **Caches and CDNs**: avoid caching **one-hit wonders**, objects requested only once. Only cache an object the second time it is requested, using a Bloom filter to remember first requests. Akamai found that a large share of objects were requested only once, and this saved a great deal of cache space.
- **Avoiding lookups for missing keys**: reject requests for IDs that do not exist without touching the database (a defence against cache penetration attacks that request random keys).
- **Safe browsing and availability checks**: the Chrome browser once used a local Bloom filter of malicious URLs, asking the server only on a "maybe". A sign-up form can rule out most usernames as "definitely available" locally before confirming with the server.
- **Distributed joins**: send a Bloom filter of one side's join keys to the other machines so they only send rows that might match.

! Example: avoiding database lookups for missing short codes
! A URL shortener has 500 million valid codes and receives 20,000 requests per second, of which 30% are for codes that do not exist (typos, scanners, bots), about 6,000 per second.
! A Bloom filter of all valid codes at 10 bits each needs 5 billion bits, about 600 MB of RAM per app server, with k = 7 and a false positive rate of about 0.8%.
! Missing codes: 99.2% are rejected in RAM with a 404 in microseconds. The other 0.8%, about 50 per second, fall through to a database lookup that returns 404. Valid codes always pass the filter (no false negatives) and are looked up as normal.
! Net effect: the database sees about 14,050 lookups per second instead of 20,000. New codes are added to the filter as they are created; the filter is rebuilt nightly from the database to stay sized correctly.

! Example: computing a filter by hand
! You expect n = 10 million items and accept p = 0.1%.
! m = −n × ln(0.001) / (ln 2)^2 = 10,000,000 × 6.91 / 0.48 ≈ 143.8 million bits, about 18 MB. That is 14.4 bits per item.
! k = 14.4 × 0.693 ≈ 10 hash functions.
! If the set unexpectedly grows to 20 million items in the same 18 MB, bits per item fall to 7.2 and the false positive rate rises to about 6% with k still 10 (about 3% even with the best k for that load, which is 5). This is why the estimate of n needs headroom.

## Common mistakes
- **Treating "maybe" as "yes"**, skipping the authoritative check after a positive.
- **Undersizing n**, so the filter fills up and the error rate explodes.
- **Trying to delete from a standard Bloom filter.**
- **Using slow cryptographic hashes.**
- **Using a Bloom filter where false positives are unacceptable without a fallback**, such as deciding whether a payment was already processed.

## In an interview
Reach for a Bloom filter when you see "most lookups are for things that do not exist" or "check against a huge set cheaply". State the guarantee precisely (no false negatives, tunable false positives), give the sizing rule (about 10 bits per item for 1%), and say what happens on a "maybe": fall through to the real lookup.

> Takeaway: a Bloom filter sets k bits per item in one shared bit array. A 0 bit proves the item was never added; all 1s only suggests it was, because other items may have set those bits. About 10 bits per item gives a 1% false positive rate, making it ideal for skipping expensive lookups that would mostly find nothing.

?? Because the bits are shared between all items and never cleared. When you check an item, its k bits may all be 1 because other items set them, not because this item was added; the filter stores no record of which item set which bit, so it cannot distinguish the two cases and can only say "maybe" (a false positive, at a rate set by bits per item and the number of hash functions). The reverse is certain: if any of the k bits is 0, the item was definitely never added, because adding it would have set that bit to 1 and bits are never reset. The same sharing is why a standard Bloom filter cannot delete items.

## Data cools over time
Most data is read heavily when it is new and rarely afterwards. Application logs are searched during an incident today, almost never a year later. Order history is viewed in the week after purchase, then occasionally for a return or a tax question. Photos are viewed a lot in the first days after upload. Backups exist for the rare day you need them. Data scientists sometimes call this the **temperature** of data: **hot** data is read often and needs to be fast, **warm** data is read sometimes, and **cold** data is read rarely, if ever.

Keeping everything on the fastest, most expensive storage wastes money, and the waste grows every day because old data accumulates while new data keeps arriving. The standard pattern is **tiering**: move data to cheaper storage as it ages, and accept slower or costlier access to the old data. The design questions are always the same: how fast must old data be readable, how often will it be read, and how long must it be kept at all?

%%layers The storage hierarchy from hot to cold: each step down is cheaper per gigabyte and slower or costlier to read.
*RAM and caches | microseconds, most expensive per GB
Local NVMe SSD | about 0.1 ms
Database and search cluster | ms queries, indexed, costly to keep large
Object storage, standard class | tens of ms, about 23 dollars per TB per month
Object storage, infrequent access | ms reads, retrieval fee per GB
Archive, instant retrieval | ms reads, higher retrieval fee
Deep archive | 12 to 48 hours to restore, about 1 dollar per TB per month
%%

## S3 storage classes
Amazon S3 is the reference example, and other clouds (Google Cloud Storage, Azure Blob Storage) offer very similar ladders. All S3 classes are designed for **eleven nines** (99.999999999%) of durability, so you are not trading safety for price. You are trading **storage price** on one side against **retrieval speed**, **retrieval fees** and **minimum storage duration** on the other.

| Class | For | Retrieval | Minimum duration |
| Standard | Frequently accessed data | Milliseconds, no retrieval fee | None |
| Intelligent-Tiering | Unknown or changing access | Milliseconds (optional archive tiers slower) | None; small monitoring fee per object |
| Standard-IA | Infrequent but needs fast access | Milliseconds, per-GB fee | 30 days |
| One Zone-IA | Infrequent, re-creatable data | Milliseconds, per-GB fee; one availability zone only | 30 days |
| Glacier Instant Retrieval | Accessed a few times a year | Milliseconds, higher per-GB fee | 90 days |
| Glacier Flexible Retrieval | Backups, rarely accessed archives | Minutes to hours (about 1 to 5 minutes expedited, 3 to 5 hours standard, up to 12 hours bulk) | 90 days |
| Glacier Deep Archive | Compliance archives | Within 12 hours standard, within 48 hours bulk | 180 days |

Approximate storage prices in a typical US region, which change over time but keep their ratios:

**Intelligent-Tiering** deserves a note. It watches each object's access and moves it automatically: to an infrequent tier after 30 days without access, to an archive-instant tier after 90 days, and back to the frequent tier as soon as it is read, with no retrieval fees. You pay a small monitoring fee per object. It is a good default when you cannot predict access patterns, and a poor choice for millions of tiny objects, where the per-object fee dominates.

### Things that catch people out
- **Minimum storage duration.** Deleting or moving an object from Standard-IA after 10 days still bills the full 30 days; from Deep Archive, 180 days. Data that is often deleted early should not go to these classes.
- **Retrieval fees.** Cheap storage with heavy reads can cost more than Standard. Standard-IA charges about $10 per TB retrieved; if you read the whole dataset twice a month, it costs more than leaving it in Standard.
- **Small objects.** The IA and Glacier Instant classes bill each object as at least 128 KB. Glacier Flexible and Deep Archive add about 40 KB of metadata per object, part of it billed at Standard rates. Transitions between classes are charged **per request** (per object). Millions of tiny log files can cost more to transition than to store, so **batch small objects** into large compressed files before archiving.
- **Single-zone classes** keep data in one availability zone and can lose it if that zone is destroyed. Use them only for data you can re-create.
- **Restores are asynchronous.** Reading from Glacier Flexible or Deep Archive means requesting a restore, waiting hours, then reading a temporary copy. Code and runbooks must expect that.

## Lifecycle rules
You do not move objects by hand. **Lifecycle rules** are attached to a bucket, optionally filtered by key prefix or object tags, and the storage service applies them automatically to existing and future objects:
- **Transition actions** move objects to another class N days after creation.
- **Expiration actions** delete objects N days after creation (and can clean up old versions and incomplete multipart uploads).

A common pattern: Standard for 30 days, Standard-IA or Glacier Instant Retrieval until 90 or 180 days, then an archive class, then deletion when the retention period ends.

%%timeline One log file's life under a lifecycle policy: it gets cheaper to keep and slower to read as it ages.
Day 0 | *Written to S3 Standard and indexed for search
Day 30 | Dropped from search index; moved to Glacier Instant Retrieval
Day 180 | Moved to Glacier Deep Archive
Year 3 | Restore requested for an audit: ready within 12 hours
Year 7 | *Expired and deleted
%%

## Beyond S3: tiering everywhere
The same idea appears in almost every data system:
- **Databases.** Partition large tables by time (lesson 04.05). Keep recent partitions in the main database on fast disks. Detach old partitions, export them to object storage as **Parquet** files (a compressed columnar format, lesson 04.03), and query them when needed with engines such as Athena, Trino, DuckDB or ClickHouse. Dropping a whole partition is instant, unlike deleting millions of rows.
- **Kafka tiered storage.** Recent log segments stay on broker disks for fast reads; older segments move to object storage, so topics can keep months of history without huge broker disks.
- **Search clusters.** Elasticsearch and OpenSearch support hot, warm, cold and frozen node tiers: new indexes on fast SSD nodes, older ones on cheaper nodes, the oldest searchable directly from object storage at higher latency.
- **Caches.** RAM for the hottest items, then local SSD, then the origin in object storage: a CDN (lesson 13.02) is a cache hierarchy built on the same principle.

## Designing a plan
1. **Measure access by age.** What fraction of reads touch data older than 7, 30, 90 days? Decide what latency old data actually needs. "Instant" is rarely needed for year-old logs.
2. **Decide retention** from legal, regulatory and business needs, not habit. Keeping everything forever costs money and creates privacy risk (lesson 03.13).
3. **Choose the transitions** with the minimum durations and retrieval fees in mind.
4. **Batch and compress** small objects before archiving.
5. **Design retrieval as an explicit, rare, possibly asynchronous operation** in the product: "your export will be ready in a few hours, we will email you".
6. **Test restores.** An archive you have never restored from is a hope, not a plan.

Age | Needs full-text search | Needs ms reads | Read frequency | Good home

! Example: application logs at 2 TB a day
! A company produces 2 TB of raw logs per day, which compress about 10 times to 200 GB. Compliance requires keeping them for 7 years.
! Hot: the last 30 days are indexed in a search cluster for incident investigation, and the compressed files sit in S3 Standard: 6 TB × $23 = about $140 per month for the files (the search cluster is a separate, larger cost).
! After 30 days, a lifecycle rule moves files to Glacier Instant Retrieval: still millisecond reads for the occasional "what happened in March?" investigation. After 180 days, they move to Deep Archive. After 7 years, they expire.
! At steady state there are about 511 TB of compressed logs. Left in S3 Standard, that would cost about $11,800 per month. With the tiered plan, about 30 TB sits in Glacier Instant ($120), 6 TB in Standard ($140) and about 475 TB in Deep Archive ($475): roughly $735 per month, about 16 times cheaper.
! Hourly files are first compacted into daily files of several gigabytes, so there are a few thousand objects per year instead of millions, keeping transition fees and per-object overhead negligible.
! The trade-off: investigating a 2-year-old incident means requesting a restore, waiting up to 12 hours (48 for bulk), paying retrieval fees, and querying the restored files with a separate tool rather than the search cluster.

! Example: when cold storage costs more
! A team moves 50 TB of product images to Standard-IA to save money: storage drops from about $1,150 to about $625 per month.
! But a nightly job regenerates thumbnails by reading every image. That is 50 TB × 30 nights = 1,500 TB of retrieval a month at about $10 per TB: $15,000 in retrieval fees. The "saving" costs $14,000 a month more.
! The fix is to change the job to process only new images, or to keep this bucket in Standard (or Intelligent-Tiering, which charges no retrieval fees). Tiering only pays when cold data is genuinely cold.

## Common mistakes
- **Keeping everything hot forever** because nobody owns a retention policy.
- **Archiving data that is still read regularly**, so retrieval fees exceed the savings.
- **Archiving millions of tiny objects** without batching them first.
- **Ignoring minimum durations** for data that is deleted soon after creation.
- **Never testing a restore**, and discovering during an audit that it takes days and nobody knows how.

## In an interview
When data grows without bound (logs, events, messages, media), say what happens to it as it ages: how long it stays hot, which cheaper tier it moves to, when it is deleted, and what reading old data costs in time and money. A sentence like "30 days hot and searchable, then archive with 12-hour restores, delete at 7 years" shows you have thought about cost, not just architecture.

> Takeaway: data cools with age, so move it down to cheaper tiers with lifecycle rules and delete it when retention ends. You save a great deal on storage and pay in retrieval time, retrieval fees, minimum storage durations and per-object overhead, so tier only data that is genuinely cold and batch small objects first.

?? Keep the last 30 days hot: compressed log files in S3 Standard plus a search index, so incidents can be investigated in seconds. A lifecycle rule then moves files older than 30 days to a cheaper class: Glacier Instant Retrieval (or Standard-IA) for the next months, which still reads in milliseconds but charges per GB retrieved, then Glacier Deep Archive for long-term compliance, and finally expires them when the retention period (for example 7 years) ends. Compact hourly files into large compressed objects before archiving to avoid per-object and transition fees. The trade-off: storage becomes many times cheaper (Deep Archive is about 1/23 of Standard's price), but reading old logs costs retrieval fees, is no longer searchable without a restore and a separate query tool, and from Deep Archive takes up to 12 to 48 hours; objects also incur minimum storage durations of 90 to 180 days if deleted early.
