@03.01
## Tables, rows and keys
A relational database stores data as **tables**. Each **row** is one thing (a user, a post, an order), and each **column** is one attribute of that thing (an email, a body, a total). Every table has a **primary key**: a column, or a set of columns, whose value identifies exactly one row. The primary key is unique and never null, so "user 42" always means one specific person.

The power of the relational model is that relationships are not stored as pointers or nested objects. They are stored as values: a post row holds the primary key of the user who wrote it. To answer "who wrote this post?" the database matches the two values, which is called a **join**. Because relationships are just values, you can query them in any direction: posts by a user, the user of a post, users who liked posts by a given user, and so on, without having decided those questions in advance.

For example, take two tables: `cities`, with `name` as its primary key, and `weather`, whose `city` column `REFERENCES cities(name)`. That **foreign key** makes the database reject a weather row for a city that does not exist. The rule lives in the database itself, so every application, every batch job and every engineer typing into a console at midnight obeys it.

%%tree The three tables of a small social app, showing which columns are keys and what each key points at.
Schema
  users
    *id | primary key
    email | UNIQUE, NOT NULL
    name
    created_at
  posts
    *id | primary key
    user_id | FK to users.id, NOT NULL
    body
    created_at
  likes
    *user_id + post_id | composite primary key
    user_id | FK to users.id
    post_id | FK to posts.id
    created_at
%%

## Choosing a primary key
There are two families of primary key.
- **Natural keys** use a value that already identifies the thing in the real world: an ISO country code, an email address, a passport number.
- **Surrogate keys** are invented by the database: an auto-incrementing integer (`BIGSERIAL` in Postgres, `AUTO_INCREMENT` in MySQL) or a generated ID such as a UUID.

Natural keys look tidy but often turn out not to be stable. Users change their email. A product code gets reused. If the email is the primary key, every foreign key that copied it must change too, across many tables. For that reason most systems use a surrogate `id` as the primary key and put a **unique constraint** on the natural value (`email UNIQUE`). You get a stable identity plus the business rule.

The key type also matters for performance. In InnoDB (MySQL's main storage engine) the table is physically stored in primary-key order (a **clustered index**), and every secondary index stores a copy of the primary key. A 4-byte or 8-byte integer keeps those secondary indexes small. A 36-character UUID string stored as text can triple their size. Random keys also scatter inserts across the whole index, which lesson 04.09 explains in detail. A `BIGINT` (8 bytes, up to about 9.2 × 10^18) is the safe default; a 4-byte `INT` tops out at about 2.1 billion, a limit real companies have hit on busy tables.

## Constraints are free correctness
Constraints turn business rules into guarantees that the database checks on every single write:
- `PRIMARY KEY`: unique and not null.
- `FOREIGN KEY`: the referenced row must exist. You also choose what happens when the parent row is deleted.
- `UNIQUE`: no two rows share this value or this combination of values. This is how you stop a user liking the same post twice.
- `NOT NULL`: the column must have a value.
- `CHECK`: an arbitrary condition on the row, for example `CHECK (price >= 0)` or `CHECK (status IN ('draft','published'))`.

### Why application checks are not enough
A common first instinct is to check in code: "does this email already exist? If not, insert it." This has a race. Two sign-up requests for the same email arrive 5 ms apart. Both run the `SELECT`, both see no row, and both `INSERT`. Now you have two accounts with one email, and the bug will only show up under load, which is the worst time to discover it.

A unique constraint closes the race because the check and the insert happen inside the database, under the protection of the index. The second insert waits for the first to commit, then fails with a unique-violation error. Your code catches that error and returns "email already taken". The application check is still useful for a friendly error message on the form, but the constraint is what guarantees correctness.

%%seq Two sign-ups race for the same email. The application check passes for both; only the unique constraint stops the duplicate.
Request A > DB : SELECT user WHERE email = x
DB -> Request A : no rows
Request B > DB : SELECT user WHERE email = x
DB -> Request B : no rows
Request A > DB : INSERT email = x
DB -> Request A : OK, committed
Request B > DB : INSERT email = x
DB -> Request B : ERROR unique violation
%%

### What happens when a parent is deleted
A foreign key needs a rule for the moment the referenced row disappears. The options:
| Rule | What happens to child rows | Typical use |
| `RESTRICT` / `NO ACTION` | The delete is refused while children exist | Orders that reference a customer |
| `CASCADE` | Children are deleted too | Likes when a post is deleted |
| `SET NULL` | The child's foreign key becomes null | A post's optional "edited_by" column |
| `SET DEFAULT` | The child's foreign key takes its default | Reassigning to a placeholder record |

`CASCADE` is convenient but dangerous at scale. Deleting one popular post with 2 million likes turns into a 2-million-row delete inside one transaction, holding locks and generating a huge amount of log. Large systems often use `RESTRICT` and delete children in small batches from a background job instead.

One more detail: in Postgres, declaring a foreign key does **not** create an index on the child column. Without an index on `likes.post_id`, every delete of a post must scan the whole likes table to check for children. Always index foreign key columns that you delete or join through.

## Normalisation in practice
**Normalising** means storing each fact exactly once. A user's name lives in `users`, not copied into every post. An update then happens in one place and the copies cannot disagree. The formal theory has numbered "normal forms"; in practice you need three ideas:
1. **One value per cell.** Do not store a comma-separated list of tags in one column; create a `post_tags` table.
2. **Every non-key column describes the whole key.** In `likes(user_id, post_id, user_name)`, `user_name` depends only on `user_id`, so it belongs in `users`.
3. **No column depends on another non-key column.** If `orders` stores `zip_code` and `city`, the city depends on the zip code, so it can drift out of sync.

The problems normalisation prevents are called **anomalies**: an update anomaly (you change a customer's address in 3 of their 40 order rows), an insert anomaly (you cannot record a customer until they place an order) and a delete anomaly (deleting the last order loses the customer's details).

%%compare Repeating customer details in every order versus storing them once and referencing them by key.
[Denormalised]
Order row holds name, email, address -(repeated per order)-> Many copies
- Change of address must touch every order
- Copies can disagree
+ No join needed to print an order
[*Normalised]
Order row holds customer_id -(join)-> One customer row
+ Each fact stored once
+ Updates touch one row
- Reads need a join
%%

The cost of normalising is joins at read time. Joins on indexed keys are cheap for small result sets (a few milliseconds), but a page that joins eight tables for every request can become slow. The working rule: **start normalised, then denormalise specific hot read paths on purpose, when you can measure the need.** A `like_count` column on `posts`, updated alongside each insert into `likes`, is a deliberate denormalisation: it avoids counting millions of rows on every page view, at the cost of keeping two things in sync. Lesson 03.10 and Module 4 return to this.

### Mapping relationships to tables
- **One-to-one** (a user has one profile): put the foreign key on either side with a unique constraint, or just add the columns to `users`.
- **One-to-many** (a user has many posts): the "many" side holds the foreign key, `posts.user_id`.
- **Many-to-many** (users like many posts, posts are liked by many users): a **join table**, `likes(user_id, post_id)`, with a composite primary key or unique constraint on the pair. Extra facts about the relationship itself, such as when the like happened, go in the join table.

## Transactions
A **transaction** groups several statements so that they all take effect or none do. A bank transfer subtracts from one account and adds to another between `BEGIN` and `COMMIT`. If anything fails in between, `ROLLBACK` leaves both accounts untouched. **Savepoints** let you undo part of a transaction without abandoning all of it.

The guarantees are summarised as **ACID**:
- **Atomicity**: all or nothing.
- **Consistency**: every constraint holds at commit time.
- **Isolation**: concurrent transactions do not see each other's half-finished work (to a degree you choose, lesson 03.06).
- **Durability**: once `COMMIT` returns, the change survives a crash (lesson 03.08).

Constraints and transactions work together. In a transfer, a `CHECK (balance >= 0)` makes the debit fail if the account would go negative, which aborts the whole transaction, so the credit never happens either.

## What a database engine is made of
The inside of a database is easiest to understand in layers. The rest of this module walks down them.

%%layers The layers inside a relational database engine, from the SQL you send down to the disk.
Query processing | parser and planner choose how to run SQL (03.05)
Concurrency control | locks and MVCC keep transactions apart (03.06, 03.07)
Access methods | B-tree and other indexes find rows fast (03.03, 03.04)
Buffer pool | in-memory cache of pages, with eviction
Recovery | write-ahead log makes commits durable (03.08)
*Storage | tables in fixed-size pages on disk, 8 KB in Postgres, 16 KB in InnoDB
%%

Knowing these layers lets you explain why a design is fast or slow instead of guessing. "This query is slow because it reads 400,000 pages that are not in the buffer pool" is an explanation. "Postgres is slow" is not.

! Example: users, posts and likes
! `users(id BIGINT PK, email TEXT UNIQUE NOT NULL, name TEXT NOT NULL, created_at TIMESTAMPTZ NOT NULL DEFAULT now())`
! `posts(id BIGINT PK, user_id BIGINT NOT NULL REFERENCES users(id), body TEXT NOT NULL CHECK (length(body) <= 5000), like_count INT NOT NULL DEFAULT 0, created_at TIMESTAMPTZ NOT NULL)`, with an index on `(user_id, created_at)` for "posts by this user, newest first".
! `likes(user_id BIGINT REFERENCES users(id), post_id BIGINT REFERENCES posts(id) ON DELETE CASCADE, created_at TIMESTAMPTZ, PRIMARY KEY (user_id, post_id))`, plus an index on `(post_id)` to list likes for a post and to make post deletion fast.
! The composite primary key on likes makes a double like impossible, even if the button is tapped twice in the same 10 ms. The second insert fails, and the application treats that as "already liked".
! The like and the counter update go in one transaction: `INSERT INTO likes ...; UPDATE posts SET like_count = like_count + 1 WHERE id = ?; COMMIT`. If the insert fails as a duplicate, the counter is not touched.

! Example: sizing the likes table
! Suppose 50 million users each like 20 posts a day. That is 1 billion new like rows a day, about 11,600 inserts per second on average.
! Each row is 8 + 8 + 8 bytes of data plus about 24 bytes of row header in Postgres, so roughly 50 bytes. The primary key index adds about 30 bytes per row and the `post_id` index another 20. Call it 100 bytes per like.
! 1 billion × 100 bytes = 100 GB per day, or about 36 TB a year. One machine will not hold that for long, which is why lesson 04.05 asks what to shard likes by. The schema stays the same; only where the rows live changes.

## Common mistakes
- **Trusting the application to enforce uniqueness.** Races will create duplicates. Use a unique constraint.
- **Forgetting indexes on foreign key columns.** Deletes and joins become full scans.
- **Storing lists in a column.** `tags = 'go,rust,sql'` cannot be indexed, joined or constrained.
- **Using a mutable natural key as the primary key.** Emails and usernames change.
- **Cascading deletes on huge relationships.** One click becomes a multi-million-row transaction.
- **Denormalising on day one.** You pay the sync cost before you know you need the speed.

## In an interview
When you sketch a schema, say out loud which columns are primary keys, which are foreign keys, and which have unique constraints, and say *why* (the race on duplicate likes is a good one to mention). Then name the two or three indexes your main queries need. Interviewers listen for whether you know that correctness rules belong in the database and that every index has a write cost.

> Takeaway: put relationships in foreign keys and business rules in constraints, so the database enforces them for every writer, including under concurrency. Normalise first, index your foreign keys, and denormalise only where measurements say you must.

?? `posts.user_id` is a NOT NULL foreign key to `users.id`. `likes` has foreign keys to both `users.id` and `posts.id`, and a composite primary key (or unique constraint) on `(user_id, post_id)` so a user can like a post only once, even when two requests race. `users.email` gets a unique constraint so two accounts cannot share an email. Use surrogate BIGINT ids as primary keys. Add an index on `likes.post_id` (Postgres does not create one for a foreign key) for counting likes and fast post deletion, and an index on `posts(user_id, created_at)` for profile pages. Choose ON DELETE behaviour deliberately, for example CASCADE for likes or RESTRICT plus batched cleanup for very large relationships.

@03.02
## The surprising pattern
When a relational database starts to hurt at scale, the obvious move is to adopt a NoSQL product built for scale. Yet several large companies did something that looks backwards: they kept MySQL and built a key-value or document store **on top of it**. Two well-known cases are FriendFeed in 2009 and Uber's Schemaless in 2016. Facebook's TAO, which serves the social graph, also sits on sharded MySQL, and Pinterest and Dropbox both built similar layers.

A **key-value store** is the simplest kind of database: you `put(key, value)` and `get(key)`, and the store does not understand the value. A **document store** is a key-value store whose values are structured documents (usually JSON) that it can partly index. The question this lesson answers is why a company would build one of these itself, on a relational engine, rather than download one.

## FriendFeed: schema changes had become impossible
FriendFeed was a social feed aggregator. It stored over 250 million entries in sharded MySQL, with read replicas and memcache in front. Traffic was not the problem. The problem was **change**. In the MySQL of that era, adding an index or a column to a table beyond 10 to 20 million rows rewrote the table and locked it for hours. Product teams started avoiding features that needed a schema change, which is a terrible place for a young company to be.

### The design
- **One entities table** holds every object as a compressed blob (a serialised Python dictionary) keyed by a 16-byte UUID. There is no column per property. Adding a property is just writing it into the blob. No migration, no lock.
- **Each index is its own table.** To query entries by user, there is a table `index_user_id(user_id, entity_id)`, sharded by `user_id`. Adding a new index means creating a new, empty table, then letting a background process called the **Cleaner** populate it from the entities while the site runs. Index rollouts went from about a week to about a day.
- **Joins happen in the application.** A query reads the index table to get entity IDs, then fetches those entities by primary key from their own shards.

%%tree FriendFeed's layout: one table of opaque blobs, plus one small index table per query pattern, each sharded independently.
Sharded MySQL
  entities | source of truth
    id | 16-byte UUID, primary key
    updated | timestamp
    body | compressed blob of all properties
  index_user_id | sharded by user_id
    user_id + entity_id
  index_link | sharded by link
    link + entity_id
  *index_new_feature | created later, filled by the Cleaner
%%

### Living without cross-shard transactions
Because an entity and its index rows live on different shards, there is no transaction that covers both. If the server crashes between writing the entity and writing the index, they disagree. FriendFeed made that safe with four rules:
1. The entities table is the **source of truth**. Index tables are only hints.
2. Writes go to the entity first, then to the indexes.
3. Reads use an index only to find **candidate** IDs, then fetch the real entities and re-check the filter against them. A stale index row that points at an entity that no longer matches is simply discarded.
4. The Cleaner continuously scans entities and repairs missing or wrong index rows, usually within a couple of seconds.

The effect is that an index can be briefly incomplete (a new entry might not show up in a user's list for a second or two) but it can never return a wrong result, because every result is verified against the source of truth.

%%seq A FriendFeed write and a later read. The read re-checks each candidate against the entity, so a stale index row is harmless.
App > Entities shard : write entity 9f3 (user 42, link L)
App > Index user shard : insert (42, 9f3)
App > Index link shard : insert (L, 9f3)
App > Index user shard : find entities for user 42
Index user shard -> App : 9f3, 7a1
App > Entities shard : fetch 9f3, 7a1
Entities shard -> App : 7a1 now belongs to user 50
App > App : drop 7a1, return 9f3
%%

## Uber Schemaless: running out of Postgres
In early 2014, Uber projected that trip growth would exhaust the storage of its single Postgres database before the end of the year. The requirements for a replacement were concrete:
- Add capacity by adding servers (horizontal scaling).
- Keep **accepting writes** even while a database is failing over, because a trip that cannot be written is lost revenue.
- **Notify downstream systems** (billing, analytics, receipts) when data changes.
- Support **secondary indexes**, such as "trips by driver".
- Be something the on-call team could debug at 3 a.m.

The team evaluated Cassandra, Riak and MongoDB. All three could scale out, but few accepted writes during failover in the way Uber needed, none had a built-in change notification mechanism, and the team lacked operational experience with them. The decisive factor was operational confidence: they knew MySQL deeply, including how it fails.

### The data model
Schemaless borrows from Bigtable's model. Data is a sparse three-dimensional map.
- A **cell** is an immutable JSON blob addressed by a **row key** (a UUID, for example the trip ID), a **column name** (a string such as `BASE`) and a **ref key** (an integer version).
- Updating means writing a new cell with a higher ref key. Nothing is ever overwritten in place.
- A trip stores `BASE`, `STATUS`, `NOTES` and `FARE_ADJUSTMENT` as separate columns. Different services write different columns at different times, so they never conflict on the same cell.

%%tree How a Schemaless trip is addressed: row key, then column, then version. Every version is kept.
trip 7c1e... | row key, a UUID
  BASE | written by dispatch
    ref 1 | pickup, dropoff, fare
  STATUS | written by billing
    ref 1 | charge pending
    *ref 2 | charge succeeded
  FARE_ADJUSTMENT | written by support
    ref 1 | refund 4.50
%%

### Triggers: the store is also a change log
Because the data is append-only, each shard is effectively an ordered log of every change. Schemaless exposes this as **triggers**: a service subscribes to a column and is called for each new cell. When a trip's `BASE` cell is written at the end of a ride, the billing service's trigger fires, charges the card and writes a `STATUS` cell. A failed charge is retried because the trigger tracks how far it has read, much like a consumer's position in a message queue (Module 8).

%%timeline One trip's life in Schemaless: separate services write separate columns, and triggers chain the work.
0 s | Ride ends, dispatch writes BASE ref 1
0.1 s | *Billing trigger fires on new BASE cell
2 s | Billing writes STATUS ref 1, charge pending
3 s | Card charged, billing writes STATUS ref 2
30 s | Receipt service trigger fires on STATUS ref 2
2 days | Support writes FARE_ADJUSTMENT ref 1
%%

### Secondary indexes
Indexes are sharded by a chosen field. Driver UUID is a good choice because it spreads evenly. City ID is a bad choice because a few large cities would overload a few shards (lesson 04.06 covers this "hot partition" problem). Indexes are **eventually consistent**, typically lagging well under 20 ms. Making them strictly consistent would require two-phase commit (a protocol that coordinates a commit across several databases) between the cell's shard and the index's shard, which Uber judged too slow and too fragile.

### Writes during failover
Each Schemaless cluster had a MySQL primary and replicas. If the primary for a shard was down, a write would be **buffered**: written to a different, healthy shard's buffer table, then copied to the right place once the primary returned. Because cells are immutable and versioned, replaying a buffered write later is safe. This is a good example of a feature that is easy to build in your own thin layer and hard to get from someone else's product.

## Why build on SQL?
The reasons generalise beyond these two companies:
- **A proven storage engine.** InnoDB has decades of hardening: crash recovery through a write-ahead log (lesson 03.08), replication, consistent backups, checksums, monitoring tools. Writing a new storage engine that is that reliable takes years.
- **Operational knowledge.** The team already knows how to tune it, back it up, restore it and debug it. In an outage, that knowledge is worth more than any feature list.
- **Use only the safe parts.** Each shard is used as a durable, sorted key-value store with single-row atomic writes. You skip the parts that do not scale across shards (joins, cross-shard transactions, global constraints).
- **You choose the trade-offs.** Eventually consistent indexes, buffered writes, triggers, retention rules: these are your decisions, not a vendor's defaults.

%%compare Adopting a NoSQL product versus building a thin key-value layer on sharded MySQL, as seen by a team that already runs MySQL.
[Adopt NoSQL product]
Cluster handles sharding and replication
+ Scaling is built in
+ Less code to own

[*KV layer on MySQL]

%%

### What it costs
You now own a database layer. Sharding, request routing, resharding when shards fill up, index maintenance and consistency repair are your code, and they need tests, on-call and documentation. You also give up ad hoc SQL: an analyst cannot write a join across blobs. Most companies that did this were large enough to staff a team for it. For a ten-person start-up, the trade usually goes the other way: use a managed database and spend the engineering time on the product.

The modern picture has also moved. MySQL 8 and Postgres can add many columns and indexes without long locks (lessons 03.11 and 03.12), and both have good JSON column types with indexes. So the original FriendFeed pain is smaller today, and "JSON column in a normal table" is often enough.

! Example: a user settings store
! A team needs a flexible per-user settings store for 500 million users. Each user has about 30 settings, and new setting types appear every week.
! Instead of a new database, they create `settings(user_id BIGINT, key VARCHAR(64), value_json JSON, updated_at TIMESTAMP, PRIMARY KEY (user_id, key))` on 64 MySQL shards, routed by `user_id % 64` through a small library (lesson 04.07 explains a better routing scheme).
! Size: 500M × 30 = 15 billion rows. At about 120 bytes per row with index overhead, that is 1.8 TB, or about 28 GB per shard. That fits comfortably on each shard's SSD and mostly in memory.
! Reads are "all settings for user X", which is one range scan on one shard: about 1 ms. New setting types need no migration. Backups, failover and dashboards are the same ones the DBAs already run.

! Example: the crash between entity and index
! A FriendFeed-style write stores entity E on shard 3, then the server crashes before the index row (user 42, E) is written on shard 7.
! For the next few seconds, a query for user 42's entries does not return E. Nothing incorrect is shown; E is just missing.
! The Cleaner's scan reaches E, sees that its user is 42, finds no index row on shard 7, and inserts it. From then on E appears. The window of inconsistency is the Cleaner's scan interval, about 2 seconds, and the failure mode is "missing for a moment", never "wrong".

## Common mistakes
- **Treating the index as truth.** If reads trust index rows without re-checking the entity, a crash leaves permanently wrong answers.
- **Sharding an index by a skewed field.** A city or country index puts New York on one overloaded shard.
- **Building it too early.** The layer is a product in itself. Without a team to run it, a managed database wins.
- **Forgetting that blobs hide the schema.** The schema still exists, now in application code. Version your blob formats and handle old versions when reading.

## In an interview
If asked "why not just use Cassandra?", answer with requirements, not fashion: operational familiarity, write availability during failover, change notification, and the cost of owning a new failure mode. Then name the price: application-level joins, eventually consistent indexes and a team that owns routing and resharding.

> Takeaway: FriendFeed and Uber used MySQL as a reliable, well-understood storage engine and built a thin schemaless layer on top. They traded SQL features (joins, cross-shard transactions, strict indexes) for painless schema change, custom features like triggers, and operational confidence.

?? Because the storage engine is proven and the team already knows how to run it: crash recovery, replication, backups, failover and 3 a.m. debugging are solved problems. Storing values as blobs means new fields need no migrations, and building the layer yourself lets you choose the trade-offs, such as eventually consistent secondary indexes, buffered writes during failover, and append-only cells that double as a change log for triggers. A new NoSQL product brings unfamiliar failure modes, and at the time few products met requirements like accepting writes during failover or built-in change notification. The cost is that you own sharding, routing and index repair, and lose joins and cross-shard transactions.

## Without an index, every query reads everything
A table's rows are stored in fixed-size **pages** on disk (8 KB in Postgres). In Postgres the table itself is a **heap**: rows sit wherever there was free space when they were inserted, in no useful order. To find `WHERE email = 'a@b.com'` without an index, the database must read every page of the table and test every row. This is a **sequential scan** (or full table scan). It is like looking for one book in a library by pulling every book off every shelf.

Put numbers on it. A users table with 10 million rows of about 200 bytes each occupies roughly 2 GB, or about 250,000 pages. Reading 2 GB from a fast SSD at 2 GB/s takes about a second, and that is if nothing else is running. If the query runs 100 times a second, the database is doing nothing else.

An **index** is a separate data structure, kept sorted by the indexed column or columns, where each entry points at a row. Because it is sorted, the database can jump to the right place, the way you find a name in a phone book without reading every page. With a B-tree index (lesson 03.04 explains its structure) the same email lookup reads 3 or 4 index pages and 1 table page.

%%compare The same lookup with and without an index on a 10-million-row table.
[Sequential scan]
WHERE email = x -(read every page)-> 250,000 pages -> 1 match
- About 1 s of I/O per query
- Cost grows with table size
[*B-tree index]
WHERE email = x -(descend tree)-> 4 index pages -> 1 table page
+ Under 1 ms when cached
+ Cost barely grows with size
- Every write updates the index
%%

## What the pointer points at
The index entry stores the indexed value plus a way to find the row. How that works differs between engines, and it matters for performance.
- **Postgres**: the entry holds a **TID** (tuple ID), the physical address of the row as (page number, slot). Finding the row is one jump to that page.
- **InnoDB (MySQL)**: the table itself is stored as a B-tree sorted by primary key, called a **clustered index**. A secondary index entry holds the **primary key value**, not a physical address. Finding the row means a second B-tree descent through the primary key. That is why InnoDB rewards short primary keys and why rows with nearby primary keys sit physically together.

## What indexes cost
Indexes are not free, and every one you add is paid for on every write.
- **Write cost**: every insert, and every update or delete that touches indexed columns, must also update every index on the table. A table with five indexes does up to six page modifications per insert, often on six different pages that may need reading from disk first.
- **Space**: an index on a wide column can be nearly as large as the table. On a 2 GB table, five indexes can add 2 to 4 GB.
- **Memory**: indexes compete with table data for the buffer pool (the in-memory page cache). An index that is never used still gets updated and still pushes useful pages out of memory.
- **Not always used**: for small tables, or queries that match a large fraction of rows, scanning is cheaper and the planner will ignore the index (lesson 03.05).

So index the queries you actually run, not every column. Write-heavy tables like event logs should have few indexes. In Postgres, `pg_stat_user_indexes` shows how often each index is used, and an `idx_scan` of zero after weeks of traffic is a strong hint to drop it.

## Index types
Postgres offers several index types. The B-tree is the default and covers most needs.
| Type | Good for | Example query |
| B-tree | Equality, ranges, sorting, prefix `LIKE 'abc%'` | `WHERE created_at > now() - interval '1 day'` |
| Hash | Equality only | `WHERE session_id = ?` |
| GIN | Values containing many keys: arrays, JSONB, full-text (an inverted index) | `WHERE tags @> '{sql}'` |
| GiST / SP-GiST | Geometry, ranges, nearest neighbour | `ORDER BY location <-> point(...) LIMIT 10` |
| BRIN | Huge tables whose values follow physical order, such as timestamps in an append-only log | `WHERE ts BETWEEN ...` on 1 TB of logs |

A **BRIN** (block range index) stores only the minimum and maximum value for each range of, say, 128 pages. It is tiny (megabytes for a terabyte table) but approximate: the database reads every block range whose min/max could contain the value. It only works when the physical order of rows follows the column, as with insert timestamps.

Other index families appear later: LSM trees, used by write-heavy stores such as Cassandra and RocksDB (Module 7), and geospatial indexes such as geohashes, quadtrees and R-trees (Module 12).

Hash | yes | no | no | no | no
GIN | yes, inside values | no | no | yes | no

## Composite indexes and column order
A **composite index** covers several columns. An index on `(a, b)` is sorted by `a`, and by `b` only **within** each value of `a`. It is exactly like a phone book sorted by surname, then first name. Finding every "Smith" is easy: all the Smiths are together. Finding every "John" means reading the whole book, because Johns are scattered across every surname.

So a composite index helps queries that use its **leftmost columns** (the "leftmost prefix" rule):
- `(a, b, c)` helps `WHERE a = ?`, `WHERE a = ? AND b = ?`, and `WHERE a = ? AND b = ? AND c = ?`.
- It helps `WHERE a = ? AND b > ?` (equality on `a`, range on `b`).
- It does **not** help `WHERE b = ?` or `WHERE c = ?` alone.
- For `WHERE a = ? AND c = ?` it can seek on `a` but must then check `c` on every entry for that `a`.

Some databases can do a **skip scan**, jumping from one value of `a` to the next and seeking `b` inside each. Oracle and MySQL 8 have it and Postgres 18 added it. It only pays off when `a` has very few distinct values, so do not design around it.

%%tree An index on (country, city) is sorted by country first. Cities only form a contiguous run inside one country, so WHERE city = 'Pune' alone has nowhere to seek.
Index (country, city)
  DE
    Berlin
    Munich
    Pune | a Pune in DE? sorted here if so
  IN
    Delhi
    Mumbai
    *Pune | WHERE country='IN' AND city='Pune' seeks here
  US
    Austin
    Pune | another possible Pune, far away
%%

### A real case
After a company merger, an employees table's primary key became `(employee_id, subsidiary_id)` so that IDs from the two companies could not clash. Queries for "all employees of subsidiary 3" suddenly did a full table scan, because `subsidiary_id` was the second column. Reversing the key to `(subsidiary_id, employee_id)` kept uniqueness exactly the same and turned the subsidiary query into a range scan. One well-ordered composite index beats two single-column indexes: it uses less space and costs less on every write.

### How to choose the order
1. Put columns compared with **equality** first.
2. Put the column used for a **range** or for **sorting** last. Once the index hits a range condition, the columns after it can no longer be used to seek.
3. Among equality columns, lead with the one that **most queries** filter on, so one index serves many queries.

The often-repeated rule "put the most selective column first" is mostly a myth for B-trees. For a query with equality on both columns, the order barely matters to the lookup cost. What matters is which queries can use the leftmost prefix.

%%matrix Which queries an index on (a, b, c) can use to seek, and how far.
Query | Seek on a | Seek on b | Seek on c
WHERE a = 1 | yes | no | no
WHERE a = 1 AND b = 2 | yes | yes | no
WHERE a = 1 AND b = 2 AND c > 5 | yes | yes | yes, range
WHERE a = 1 AND b > 2 AND c = 5 | yes | yes, range | no, filter only
WHERE b = 2 | no | no | no
WHERE a = 1 AND c = 5 | yes | no | no, filter only
%%

## More tools in the box
- **Unique indexes** enforce uniqueness as well as speeding lookups (lesson 03.01).
- **Expression indexes** index the result of a function: `CREATE INDEX ON users (lower(email))` serves `WHERE lower(email) = ?`. A plain index on `email` cannot, because the stored values are not lowercased.
- **Partial indexes** index only some rows: `CREATE INDEX ON orders (created_at) WHERE billed IS NOT TRUE` keeps an "unbilled orders" index tiny when 99.9% of orders are billed.
- **Covering indexes**: if the index holds every column a query needs, the database answers from the index alone (an **index-only scan**) and skips the table. Postgres lets you add non-key payload columns with `INCLUDE`, for example `CREATE INDEX ON posts (user_id, created_at) INCLUDE (title)`.
- **Sorted output**: a B-tree on `(user_id, created_at)` returns a user's posts already ordered by time, so `ORDER BY created_at DESC LIMIT 20` reads 20 entries and stops, with no sort step at all.

! Example: the feed query, two index orders
! Query: `SELECT id, body FROM posts WHERE user_id = 42 ORDER BY created_at DESC LIMIT 20`. The table has 500 million posts from 10 million users, so about 50 per user on average.
! With an index on `(user_id, created_at)`: descend 4 levels to the end of user 42's block, read 20 entries backwards (all on one or two leaf pages), then fetch 20 rows. About 26 page reads, under 2 ms even with some disk reads.
! With an index on `(created_at, user_id)`: the index is sorted by time, so user 42's posts are spread across the whole index. The database must walk backwards through every post from every user until it finds 20 by user 42. If user 42 last posted a month ago, that is most of a month's posts, millions of entries. The planner will probably choose a different plan entirely, and it will still be slow.

! Example: the cost of an extra index
! An orders table takes 2,000 inserts per second and has 4 indexes. Each insert touches the heap plus 4 index leaf pages: 5 page writes, 10,000 per second.
! Someone adds 3 more "just in case" indexes on columns no query uses. Now each insert touches 8 pages: 16,000 page writes per second, 60% more write I/O and roughly 60% more write-ahead log. Buffer pool hit rates fall because the new indexes take memory. Dropping them is often the cheapest performance win available.

## Common mistakes
- **Indexing every column separately.** Single-column indexes on `a` and `b` are rarely as good as one composite index on `(a, b)`.
- **Wrong column order.** A range column first stops the rest of the index being used for seeks.
- **Wrapping the column in a function.** `WHERE date(created_at) = '2026-01-01'` cannot use an index on `created_at`. Rewrite as a range: `created_at >= '2026-01-01' AND created_at < '2026-01-02'`.
- **Type mismatches.** Comparing a text column to a number can force a conversion on every row and disable the index.
- **Leading wildcards.** `LIKE '%son'` cannot seek in a B-tree. Use a trigram (GIN) index or full-text search.
- **Never checking usage.** Unused indexes cost writes and memory forever.

## In an interview
When you name a table, name its indexes in the same breath and tie each one to a query: "posts gets an index on `(user_id, created_at)` for the profile page." If the workload is write-heavy, say that you are keeping indexes to a minimum and why. If asked why a query is slow, think aloud: which index, in which column order, and does the query's `WHERE` clause match its leftmost prefix?

> Takeaway: an index is a sorted copy of some columns that lets the database seek instead of scan, paid for on every write and in memory. A composite index works left to right, so order its columns as equality first, range or sort last, and match them to the queries you actually run.

?? An index on (a, b) is sorted by a first and by b only within each value of a, like a phone book sorted by surname then first name. For WHERE a = ? the database descends the tree to the one contiguous block of entries with that a and reads only those. Rows with a given b are scattered: there is one small run of them inside every distinct value of a, so there is no single place in the sort order to seek to. The database would have to read the whole index (or the whole table), so the planner usually does a full scan instead. Some engines can skip-scan across values of a, but that only helps when a has very few distinct values.

@03.04
## The problem a B-tree solves
Disks, even fast SSDs, are slow compared with memory, and they read data in blocks rather than bytes. A random read from an NVMe SSD costs around 100 microseconds; from a spinning disk, around 10 milliseconds. Reading 8 KB costs about the same as reading 8 bytes. So the cost of a lookup structure on disk is measured almost entirely in **how many pages it has to read**, not in how many comparisons it does.

A binary search tree is a poor fit. Each node holds one key and two children, so a billion keys need a tree about 30 levels deep, which could mean 30 random disk reads per lookup. The **B-tree**, invented in 1970 for exactly this problem, makes each node one whole disk page holding hundreds of keys. Each node therefore has hundreds of children, and the tree is very wide and very shallow.

The version used by virtually every relational database is technically a **B+ tree**: all actual entries live in the bottom layer (the leaves), and the upper layers hold only separator keys that guide the search. This course follows common usage and calls it a B-tree.

## Two structures working together
A B-tree index is best understood as two structures combined.

**The leaf level** holds every index entry in sorted order: the indexed value plus a pointer to the table row (lesson 03.03 explains what that pointer is in Postgres and InnoDB). Each leaf is one page, 8 KB in Postgres or 16 KB in InnoDB, so it holds hundreds of entries. Leaves are linked to their neighbours in a **doubly linked list**, which lets the database walk forwards or backwards through a range without going back up the tree.

**The tree** sits on top so the database can find the right leaf quickly. Each entry in a **branch node** (also called an internal node) holds a separator key and a pointer to a child page. In one common layout, each separator is the largest value in the child it points to. Branch layers are added until everything above the leaves fits in a single **root** page.

%%tree A small B+ tree. Branch pages hold only separator keys; every real entry lives in a leaf, and leaves are chained left to right.
Root | separators 40, 83, max
  Branch A | keys up to 40
    Leaf 1 | 3, 9, 17
    Leaf 2 | 22, 31, 40
  *Branch B | keys 41 to 83
    Leaf 3 | 46, 51, 55
    *Leaf 4 | 57, 64, 83
  Branch C | keys above 83
    Leaf 5 | 88, 91, 97
    Leaf 6 | 102, 140, 199
%%

## Walking the tree
To find the key 57:
1. Read the root page. Scan its separators in order until you find one greater than or equal to 57. That is 83, so follow its pointer to Branch B.
2. Read Branch B. Its separators say keys from 56 to 83 are in Leaf 4. Follow that pointer.
3. Read Leaf 4. Find 57, and with it the pointer to the table row.
4. Read the table page that holds the row.

Within a page the search is a binary search over a few hundred keys in memory, which takes well under a microsecond. The expensive part is the page reads, and there is exactly one per level.

Because the tree is **balanced**, every leaf is the same distance from the root, so every lookup takes the same number of steps. Insertions and deletions keep it balanced automatically: the tree only ever grows at the top, by adding a new root.

## Why the depth stays tiny
The depth of the tree grows with the logarithm of the number of entries, with a base equal to the **fanout** (the number of children per node). With a toy fanout of 4, capacity multiplies by 4 at each level:
| Depth | Max entries with fanout 4 | Max entries with fanout 300 |
| 1 | 4 | 300 |
| 2 | 16 | 90,000 |
| 3 | 64 | 27 million |
| 4 | 256 | 8.1 billion |
| 5 | 1,024 | 2.4 trillion |

Real pages hold hundreds of entries. An 8 KB page of 8-byte integer keys with 6-byte pointers and some header bytes holds around 400 to 500; longer keys such as emails mean fewer, perhaps 100 to 200. So each extra level multiplies capacity by a few hundred. Indexes on tables with millions of rows are typically 3 or 4 levels deep; 5 is uncommon and 6 is rare.

%%bars How many levels a lookup needs for one billion keys, depending on how many children each node has.
Binary tree, fanout 2 | 30 | 30 levels
Fanout 10 | 9 | 9 levels
Fanout 100 | 5 | 5 levels
*Fanout 300 | 4 | 4 levels
Fanout 1,000 | 3 | 3 levels
%%

### The upper levels are always in memory
Every lookup reads the root, and every lookup in a given part of the key space reads the same branch pages. Those pages are therefore the hottest pages in the whole database and stay in the buffer pool permanently. With a fanout of 300, the root plus the second level is about 301 pages, under 3 MB. Even the third level is only about 90,000 pages, around 700 MB, which often fits in memory too.

So the practical answer to "O(log n), but fast" has two parts. The log has a huge base, so a billion entries means a depth of 4. And the top two or three of those four levels are cached, so a lookup costs **one or two real disk reads**, and often none.

## Why an "indexed" query can still be slow
Every index lookup has three steps, and only the first one is bounded.
1. **Tree traversal**: one page per level, 3 to 5 pages. Always fast.
2. **Following the leaf chain**: reading every matching entry. A range that matches a million entries reads a million entries, perhaps 3,000 leaf pages.
3. **Fetching table rows**: one table access per matching entry. Matching rows are usually scattered across many table pages, so this is random I/O, often one page read per row.

Steps 2 and 3 are where slow indexed queries spend their time. A common myth is that indexes "degenerate" and need rebuilding to be fast again; rebuilding cannot shorten the leaf chain or reduce the number of rows you asked for. The real fixes are a more selective condition, a better column order (so the matching entries are contiguous), or a covering index that answers from the index and skips step 3 entirely.

%%bars Where the time goes in an index range scan that matches 10,000 rows, assuming cold pages.
Tree descent | 4 | 4 pages
Leaf chain | 30 | about 30 leaf pages
*Table rows | 10000 | up to 10,000 random pages
%%

## How inserts keep it balanced: page splits
A new entry must go into the leaf where it belongs in sort order. If that leaf has room, it is inserted in place and nothing else changes. If the leaf is full, it **splits**:
1. Allocate a new page.
2. Move roughly the upper half of the entries to the new page.
3. Relink the leaf chain so the old page points to the new one and the new one to the old page's former neighbour.
4. Insert a new separator key and pointer for the new page into the parent branch.
5. If the parent is also full, it splits too, and so on up. If the root splits, a new root is created above it and the tree grows one level taller.

%%compare One leaf page before and after a split caused by inserting 60 into a full page.
[Before]
Leaf 4 is full -> 57, 64, 72, 83
- No room for 60
[*After]
Leaf 4 -(linked to)-> Leaf 4b
Leaf 4: 57, 60, 64
Leaf 4b: 72, 83
+ Parent gains separator 64
%%

Splits leave both pages about half full. That is why a B-tree built by random inserts tends to be around 70% full on average, wasting some space. Postgres and InnoDB both have an optimisation for the common case of always inserting at the right-hand end (an auto-incrementing ID or a timestamp): instead of splitting 50/50 they leave the old page full and start a fresh one, so sequential inserts produce nearly full pages. Random keys, such as UUIDv4, get no such benefit and also touch a random leaf for every insert, which is the root of the problem in lesson 04.09.

Deletes work the other way. Entries are removed (in Postgres, marked dead and cleaned up later by VACUUM, lesson 03.07), and nearly empty pages can be merged or recycled, though in practice databases are lazy about shrinking indexes.

## B-trees and writes
Every write updates a page **in place**, and with random keys those pages are scattered across the disk. Each change is also recorded in the write-ahead log first (lesson 03.08). On a read-heavy workload, that is a fine trade: reads are as cheap as they can be. On a workload of hundreds of thousands of small writes per second, it becomes the bottleneck. Write-heavy stores therefore often use **LSM trees** (log-structured merge trees), which buffer writes in memory and flush them to disk as sorted files in large sequential writes, at the cost of more work on reads (Module 7).

! Example: sizing an index on 1 billion emails
! A users table has 1 billion rows and a B-tree on `email`. An average email is about 25 bytes; with the row pointer and per-entry overhead, say 40 bytes per entry. An 8 KB page at about 90% fill holds roughly 180 entries, but branch pages hold shorter separators and fit around 300.
! Leaves: 1 billion / 180 = about 5.6 million leaf pages, about 45 GB. That is the bulk of the index.
! Branch levels: 5.6 million / 300 = 18,500 pages at level 2, then 62 pages at level 1, then 1 root. Total depth: 4 (root, two branch levels, leaves).
! The root and the 62 pages below it are always cached. The 18,500-page level is about 150 MB and almost certainly cached too. So a lookup reads 3 cached pages, then 1 leaf page and 1 table page that may need the disk: about 2 SSD reads, roughly 0.2 ms.

! Example: why a date-range report is slow despite an index
! A query asks for all orders in March from a 200-million-row table with an index on `created_at`. March has 6 million orders.
! The descent takes 4 page reads. The leaf chain for 6 million entries at about 400 per page is 15,000 pages, read mostly sequentially: fast. But fetching 6 million rows means up to 6 million random table page reads. Even at 100 microseconds each that is 10 minutes of I/O if nothing is cached.
! The planner will rightly switch to a bitmap scan or a sequential scan (lesson 03.05). The fix is not "rebuild the index" but a covering index with the columns the report needs, or a pre-aggregated summary table.

## Common mistakes
- **Thinking depth grows quickly.** It barely grows: going from 1 million to 1 billion rows usually adds one level.
- **Rebuilding indexes to fix slow queries.** It rarely helps; slow queries come from leaf and table reads.
- **Using random primary keys without thinking.** They cause splits all over the tree and poor cache locality.
- **Ignoring the table fetch.** An index that returns 100,000 rows still visits up to 100,000 table pages.

## In an interview
When asked why a B-tree is fast, say three things: each node is a page with hundreds of children, so the depth is about 4 even for billions of rows; the top levels are always cached, so a lookup costs one or two disk reads; and the real cost of a range query is the number of matching leaf entries and table rows, not the tree.

> Takeaway: a B-tree is a very wide, balanced tree of separator pages over a sorted, linked chain of leaf pages. Depth stays at 3 to 5 even for billions of rows, and the top levels live in memory. Slow index queries come from reading many leaves and table rows, not from the tree itself.

?? Each B-tree node is a whole disk page holding hundreds of keys, so it has hundreds of children and the base of the logarithm is in the hundreds, not 2. A billion keys need only about 4 levels (300^4 is 8.1 billion). The root and upper branch levels are read by every lookup, so they stay permanently in the buffer pool (the top two levels are only a few MB). A lookup therefore costs one or two real disk reads (the leaf and the table row), often fewer. The cost is dominated by page reads, not comparisons, and the wide fanout keeps the page count tiny.

@03.05
## The planner decides how
SQL is **declarative**: it says what result you want, not how to get it. `SELECT * FROM orders WHERE customer_id = 7` does not say "use the index" or "read the whole table". A component called the **query planner** (or optimiser) makes that choice. It enumerates possible plans (which index to use, which order to join tables in, which join algorithm), estimates the cost of each one using statistics about the data, and runs the cheapest.

This matters because the difference between a good and a bad plan for the same query can be a factor of 10,000: 2 ms against 20 seconds. When a query is slow, the **execution plan** is the first thing to look at, before adding hardware, caches or indexes.

%%flow The path from SQL text to rows. Statistics feed the cost estimates that decide which plan wins.
[Planning] SQL text -(parse)-> Query tree -(rewrite views)-> Candidate plans -(cost with stats)-> *Cheapest plan
[Execution] *Cheapest plan -(run)-> Rows to client
%%

## How the planner estimates cost
The planner needs two kinds of knowledge.

**Statistics about the data.** `ANALYZE` (run automatically by Postgres's autovacuum, or by hand) samples each table and records, per column: the number of distinct values, the fraction of nulls, a list of the **most common values** with their frequencies, and a **histogram** that splits the remaining values into buckets of equal population. From these the planner estimates **selectivity**: the fraction of rows a condition will match. If `status = 'shipped'` appears in the most-common list with frequency 0.85, the planner expects 85% of rows to match.

**A cost model.** Postgres prices everything relative to reading one page **sequentially**, which costs 1.0. Its default parameters are:
| Parameter | Default | Meaning |
| `seq_page_cost` | 1.0 | Read one page as part of a sequential scan |
| `random_page_cost` | 4.0 | Read one page at a random location |
| `cpu_tuple_cost` | 0.01 | Process one row |
| `cpu_index_tuple_cost` | 0.005 | Process one index entry |
| `cpu_operator_cost` | 0.0025 | Evaluate one operator, such as a comparison |

Random reads are priced at 4 times sequential reads because on spinning disks they really were far more expensive. On SSDs the real gap is much smaller, and many teams lower `random_page_cost` to about 1.1, which makes the planner more willing to use indexes.

### A worked cost
Take a table `tenk1` with 10,000 rows in 345 pages. A full sequential scan costs 345 pages × 1.0 plus 10,000 rows × 0.01 = **445**. Adding a filter `WHERE unique1 < 7000` adds 10,000 × 0.0025 for the comparison, giving about 470.

## Reading EXPLAIN
`EXPLAIN` prints the chosen plan as a tree of nodes. Each node takes rows from its children, does one job (scan, filter, join, sort, aggregate) and passes rows up. Read it from the most indented line outwards. Each line shows:
- `cost=X..Y`: the estimated **start-up cost** (before the first row is produced) and the **total cost**, in the units above.
- `rows`: the estimated number of rows this node outputs.
- `width`: the estimated average row size in bytes.

```
Hash Join  (cost=8.6..412.0 rows=100 width=44)
  Hash Cond: (o.customer_id = c.id)
  ->  Seq Scan on orders o  (cost=0..360.0 rows=10000 width=36)
  ->  Hash  (cost=8.5..8.5 rows=10 width=12)
        ->  Index Scan using customers_city on customers c  (rows=10)
              Index Cond: (city = 'Pune')
```

%%tree The plan above as a tree: the hash join consumes a hash table built from Pune customers and probes it with every order.
Hash Join | orders.customer_id = customers.id, 100 rows
  Seq Scan on orders | 10,000 rows, probe side
  *Hash | build side, 10 rows
    Index Scan on customers_city | city = 'Pune'
%%

## The same table, different plans
Here is how the plan for a single-table query on `tenk1` changes as the condition matches more rows:
| Query on tenk1 | Rows matched | Plan | Estimated cost |
| `unique1 = 42` | 1 | Index Scan | 8.30 |
| `unique1 < 100` | 100 (1%) | Bitmap Index Scan + Bitmap Heap Scan | 225 |
| `unique1 < 7000` | 7,000 (70%) | Seq Scan with filter | 470 |

The scan types, from fewest rows to most:
- **Index scan**: descend the index, then fetch each matching row in index order. Each fetch may be a random page read. Best for a handful of rows.
- **Index-only scan**: answer entirely from the index when it contains every column the query needs. In Postgres it also needs the table's visibility map to be up to date (lesson 03.07).
- **Bitmap scan**: first collect the locations of every matching row from the index into a bitmap, sort them by physical page, then read each needed page once, in order. This turns random reads into nearly sequential ones and reads each page only once even if it holds many matches. Good for hundreds to tens of thousands of rows. Two bitmaps from two indexes can be combined with `BitmapAnd` or `BitmapOr`.
- **Sequential scan**: read the whole table in physical order and filter. Best when a large fraction of rows match, because sequential reads are cheap and there are no random jumps.

%%bars Estimated cost for each plan type on tenk1 as the query matches more rows. The index plan's cost climbs with every matching row; the seq scan's is flat.
Index scan, 1 row | 8.3 | 8.3
Bitmap scan, 100 rows | 225 | 225
*Seq scan, 7,000 rows | 470 | 470
Index scan forced, 7,000 rows | 7000 | about 7,000+
%%

## When the planner ignores your index
Usually the planner is **right** to ignore it:
- **The query matches a large share of the table.** As a rough guide, once a condition matches more than about 5 to 20% of rows (it depends on row width and caching), thousands of random page reads cost more than one sequential pass.
- **The table is tiny.** A table of 3 pages is cheaper to scan than to probe through an index. This is why you should never judge plans on a small development database: the plan at 1,000 rows tells you nothing about the plan at 100 million.
- **The index cannot serve the condition.** The query filters only on the second column of a composite index (lesson 03.03), wraps the column in a function (`lower(email) = ?` with an index on `email`), uses a leading wildcard (`LIKE '%son'`), or compares mismatched types (a text column against a number).
- **`ORDER BY ... LIMIT` changes the trade-off.** With `LIMIT 10` the planner may walk an index in sort order and stop early, even if that index does not match the filter well. If matching rows are rare, this can backfire badly.

Sometimes the planner is **wrong**, almost always because its row estimates are wrong:
- **Stale statistics** after a bulk load or delete. Running `ANALYZE` fixes it.
- **Correlated columns.** The planner assumes conditions are independent. For `city = 'Paris' AND country = 'France'` it multiplies the two selectivities and badly underestimates the rows. Postgres's `CREATE STATISTICS` can record such dependencies.
- **Skewed data and parameters.** A prepared statement planned for a typical customer may be reused for a customer with 1,000 times more rows.

## EXPLAIN ANALYZE
`EXPLAIN ANALYZE` actually **runs** the query and shows, next to each estimate, the actual time, actual rows and `loops` (how many times the node ran; times and rows are per loop, so multiply). The single most useful check is whether estimated rows are close to actual rows at each node. When they differ by 100 times or more, the planner chose based on a false picture, and a bad plan is likely. Adding `BUFFERS` shows how many pages came from the cache (`shared hit`) and how many from disk (`read`), which explains why the same query is fast the second time.

Careful: because it really executes, `EXPLAIN ANALYZE` on an `UPDATE` or `DELETE` really changes data. Wrap it in `BEGIN; ... ROLLBACK;`.

## Joins in plans
For each join, the planner also picks an algorithm:
- **Nested loop**: for each row of the outer input, look up matching rows in the inner input, ideally through an index. Cost is roughly outer rows × lookup cost. Best when the outer side is small.
- **Hash join**: build an in-memory hash table on the smaller input, then stream the larger input and probe it. Cost is roughly linear in both inputs. Good for large, unsorted inputs, as long as the hash table fits in `work_mem`; otherwise it spills to disk in batches.
- **Merge join**: walk two inputs that are already sorted on the join key, like zipping two sorted lists. Good when both sides come out of indexes in order, or when sorting is cheap.

%%matrix Join algorithms and the situations each one suits.
Join | Small outer side | Two large inputs | Needs index on inner | Needs sorted input | Memory use
Nested loop | yes | no | yes, ideally | no | low
Hash join | partial | yes | no | no | high, build side
Merge join | partial | yes | no | yes | low
%%

The join **order** matters as much as the algorithm. For three tables there are 12 possible orders; for 10 tables, millions. Postgres searches all orders exhaustively up to about 12 tables, then switches to a genetic search. A bad row estimate early in the plan multiplies through every join above it, which is why big queries are the ones most often planned badly.

! Example: why the index was skipped
! `SELECT * FROM orders WHERE status = 'shipped'` on 10 million rows in 400,000 pages, where 85% are shipped. The planner estimates 8.5 million rows.
! Seq scan: 400,000 × 1.0 plus 10 million × 0.0125 = about 525,000.
! Index scan: 8.5 million entries, and since shipped rows are on almost every page, nearly every one of the 400,000 pages is fetched, many of them more than once at random cost 4.0. The estimate is well over 2 million. The seq scan wins by a factor of 4.
! For `status = 'refunded'` (0.2%, 20,000 rows) the index or a bitmap scan wins easily. A partial index `ON orders (created_at) WHERE status = 'refunded'` would be tiny and even faster.

! Example: a 100× misestimate and how to spot it
! A report joins `events` to `users` and takes 40 seconds. `EXPLAIN ANALYZE` shows a nested loop whose outer node estimated `rows=12` but actually produced `rows=180000`. The planner believed it would do 12 index lookups; it did 180,000.
! The cause: 50 million events were loaded an hour earlier and autovacuum had not yet analysed the table, so the statistics described yesterday's data.
! Running `ANALYZE events` corrects the estimate to about 175,000 rows. The planner switches to a hash join and the query takes 1.8 seconds. No index was added; the plan just had to see reality.

## Common mistakes
- **Testing plans on tiny tables.** The planner rightly scans them; production will behave differently.
- **Forcing plans.** Disabling seq scans globally to "make it use the index" fixes one query and breaks others.
- **Ignoring estimate versus actual.** That gap is the single best clue to a bad plan.
- **Reading cost as milliseconds.** Cost units are relative; compare them only within one plan.
- **Running EXPLAIN ANALYZE on a write without a rollback.**

## In an interview

Then say how you would check: `EXPLAIN ANALYZE`, compare estimated and actual rows, look at buffers.

> Takeaway: the planner picks the plan with the lowest estimated cost, using statistics about the data and a model where random page reads cost more than sequential ones. Sequential scans win when many rows match. When a plan is bad, compare estimated and actual rows in EXPLAIN ANALYZE.

?? When the planner estimates that a sequential scan is cheaper. ## Concurrency causes anomalies
A busy database runs hundreds of transactions at the same moment. Their reads and writes **interleave**: transaction A reads a row, then B writes it, then A writes it. The ideal is that the final result is the same as if the transactions had run one at a time in some order. That property is called **serializability**. Without care, interleaving produces results that no one-at-a-time order could ever produce. These wrong results are called **anomalies**.

The classic anomalies, from mildest to subtlest:
- **Dirty read**: you read another transaction's change before it commits. If that transaction then rolls back, you acted on data that never existed.
- **Non-repeatable read**: you read the same row twice in one transaction and get different values, because another transaction committed a change in between.
- **Phantom read**: you run the same query with a condition twice (`WHERE status = 'open'`) and get a different set of rows, because someone inserted or deleted a matching row in between.
- **Lost update**: two transactions read the same value, both compute a new value from it, and both write. The second write silently overwrites the first. It is not in the SQL standard's list, but it is the most common concurrency bug in real applications.
- **Write skew**: two transactions read overlapping data, each makes a decision based on it, and each writes a **different** row. Neither overwrites the other, yet together they break a rule. A well-known case is two doctors on call: the rule is that at least one must stay on call, both check that two are on call, and both remove themselves.
- **Serialisation anomaly**: the general term for any set of committed transactions whose combined result matches no serial order. Write skew is the most common example.

## The lost update in detail
%%seq A lost update on a wallet: both transactions read 100, and the second write erases the first deduction.
Tx 1 > Wallet row : SELECT balance
Wallet row -> Tx 1 : 100
Tx 2 > Wallet row : SELECT balance
Wallet row -> Tx 2 : 100
Tx 1 > Wallet row : UPDATE balance = 70
Tx 1 > Wallet row : COMMIT
Tx 2 > Wallet row : UPDATE balance = 50
Tx 2 > Wallet row : COMMIT, final 50 not 20
%%

The pattern is **read, compute in the application, write back**. It hides in many places: incrementing a counter by reading it first, editing a JSON document by loading it, changing it and saving it, decrementing stock in an online shop. Every one of them is safe in testing, where requests arrive one at a time, and broken in production, where two requests can land in the same 10 ms.

## Isolation levels
**Isolation** is the "I" in ACID: how much concurrent transactions are shielded from each other. The SQL standard defines four levels, each allowing fewer anomalies, and databases interpret them differently. In Postgres:
| Level | What a transaction sees | What it prevents |
| Read uncommitted | Same as read committed in Postgres | Dirty reads |
| Read committed (default) | Each **statement** sees data committed before that statement began | Dirty reads |
| Repeatable read | The whole **transaction** sees one snapshot taken at its first statement (snapshot isolation) | Also non-repeatable reads, phantoms and lost updates on the same row |
| Serializable | One snapshot, plus tracking of read/write dependencies | Everything: the result always equals some serial order |

%%matrix Which anomalies each Postgres isolation level allows. "no" means the anomaly cannot happen at that level.
Level | Dirty read | Non-repeatable read | Phantom | Lost update | Write skew
Read committed | no | yes, possible | yes, possible | yes, possible | yes, possible
Repeatable read | no | no | no | no, aborts one | yes, possible
Serializable | no | no | no | no | no
%%

MySQL's InnoDB differs: its default is repeatable read, and it uses locks on index ranges (gap locks) for locking reads rather than Postgres's snapshot rules. The names match across databases but the exact behaviour does not, so check before relying on a level.

### Read committed and its subtlety
At read committed, an `UPDATE` that finds a row changed and committed by another transaction **waits** for that transaction, then re-reads the latest committed version, re-checks its `WHERE` clause against it and applies the change to that version. So a single statement such as `UPDATE counters SET n = n + 1 WHERE id = 1` is safe: the increment is computed inside the database on the newest value.

But read-then-write in application code is **not** safe: `SELECT n` returns 5, the application computes 6, `UPDATE counters SET n = 6` overwrites another session's increment. The database cannot know that your 6 came from a stale 5.

### Repeatable read fails instead of waiting
At repeatable read, your transaction works on a snapshot. If it tries to update a row that another transaction changed and committed after your snapshot was taken, Postgres does not quietly apply your change on top. It raises `could not serialize access due to concurrent update`. The lost update is prevented by turning it into an error. Your application must **retry the whole transaction**, which will then read the new value.

### Serializable catches write skew
Repeatable read still allows write skew, because the two transactions write different rows and so never collide on a row. Serializable (in Postgres, **Serializable Snapshot Isolation**, SSI) also records what each transaction **read**, and looks for dangerous patterns of read/write dependencies between concurrent transactions. When it finds one, it aborts one of them.

An example: transaction A sums the amounts in class 1 and inserts the total as a new row in class 2, while transaction B sums class 2 and inserts its total into class 1. Under repeatable read both commit, and the result matches neither order (in any serial order, one of them would have seen the other's insert). Under serializable, one of them fails with SQLSTATE `40001` (serialization failure) and must be retried.

Serializable has costs: more aborts under contention, and some memory for tracking reads. Keep serializable transactions short, retry them automatically, and mark read-only ones `READ ONLY`, which lets Postgres optimise them.

## Explicit locks
Isolation levels are one tool. Locks are the other.
- **Row locks**: `SELECT ... FOR UPDATE` reads rows and locks them, so no other transaction can update, delete or lock them until you commit. It is the classic fix for read-modify-write. Plain `SELECT`s are not blocked, thanks to MVCC (lesson 03.07). `FOR UPDATE SKIP LOCKED` skips rows other sessions hold, which turns a table into a simple job queue for multiple workers. `FOR UPDATE NOWAIT` errors instead of waiting.
- **Table locks** are taken automatically by every statement. Most are harmless and compatible with each other. The dangerous one is `ACCESS EXCLUSIVE`, taken by many `ALTER TABLE` forms, `DROP`, `TRUNCATE` and `VACUUM FULL`: it blocks even reads. Plain `CREATE INDEX` takes a lock that blocks writes (lesson 03.11).
- **Advisory locks**: locks on an application-chosen number, for example `pg_advisory_lock(42)`. The database does not attach them to any row; they are useful for "only one worker runs this nightly job at a time".

%%seq SELECT FOR UPDATE fixes the lost update: the second transaction waits for the lock, then reads the new balance.
Tx 1 > Wallet row : SELECT balance FOR UPDATE
Wallet row -> Tx 1 : 100, row locked
Tx 2 > Wallet row : SELECT balance FOR UPDATE
Wallet row > Wallet row : Tx 2 waits for lock
Tx 1 > Wallet row : UPDATE balance = 70, COMMIT
Wallet row -> Tx 2 : 70, row locked
Tx 2 > Wallet row : UPDATE balance = 20, COMMIT
%%

### Optimistic locking
Instead of locking, you can **detect** conflicts. Add a `version` column. Read the row and remember its version, say 7. Write with `UPDATE accounts SET balance = 70, version = 8 WHERE id = 1 AND version = 7`. If another transaction got there first, the version is now 8, the `UPDATE` matches zero rows, and the application knows to reload and retry. This is called **optimistic concurrency control** because it assumes conflicts are rare. It holds no locks between the read and the write, so it works across HTTP requests (a user editing a form for five minutes) where holding a database lock would be unthinkable.

%%compare Pessimistic locking waits for conflicts it expects; optimistic locking detects conflicts after the fact and retries.
[Pessimistic: FOR UPDATE]
Lock row -> Compute -> Write -> Commit releases
+ No retries needed
+ Good under heavy contention
- Others wait while you hold it
- Cannot span user think time
[*Optimistic: version check]
Read version 7 -> Compute -> Write WHERE version = 7
+ No locks held
+ Works across HTTP requests
- Retries under heavy contention
%%

## Deadlocks
A **deadlock** happens when two transactions each hold a lock that the other is waiting for. Transaction A updates account 1 then account 2; transaction B updates account 2 then account 1. A holds 1 and waits for 2; B holds 2 and waits for 1. Neither can proceed. Postgres checks for cycles after a short wait (`deadlock_timeout`, 1 second by default), picks one transaction and aborts it with a deadlock error.

To avoid deadlocks: always lock rows in a **consistent order** (for example, by ascending ID, so a transfer from 2 to 1 still locks 1 first), keep transactions short, and avoid user interaction inside a transaction. Treat deadlock errors like serialisation failures: retry.

## The bigger map
All of this is one corner of a wider subject: **consistency models**, which are rules about which histories of operations a system may produce. They are often defined by which dependency cycles between transactions are forbidden. Serializable is near the top. Snapshot isolation and read committed are lower down. Distributed systems add models such as **linearizability** (every operation appears to take effect at one instant between its start and end) and **causal consistency** (Module 6).

! Example: lost update on a wallet, and four fixes
! The balance is 100. T1 reads 100 to deduct 30. T2 reads 100 to deduct 50. T1 writes 70 and commits. T2 writes 50 and commits. The final balance is 50; it should be 20. The customer just got 30 for free.
! Fix 1, atomic statement: `UPDATE wallets SET balance = balance - 30 WHERE id = 1 AND balance >= 30`. The arithmetic happens in the database on the latest value, and the `balance >= 30` check prevents overdrafts. Check the affected row count: zero means insufficient funds.
! Fix 2, pessimistic lock: `SELECT balance FROM wallets WHERE id = 1 FOR UPDATE`, compute, update, commit. T2 waits about 2 ms for T1, then reads 70.
! Fix 3, optimistic: `UPDATE ... SET balance = 70, version = 8 WHERE id = 1 AND version = 7`. T2's update matches zero rows; it re-reads 70 and version 8 and retries.
! Fix 4, isolation: run at repeatable read. T2's update raises a serialisation error; the retry reads 70 and writes 20.

! Example: write skew on a meeting room
! Rule: a room may not be double-booked. Two users book room 4 for 10:00 at the same moment. Each transaction runs `SELECT count(*) FROM bookings WHERE room = 4 AND slot = '10:00'`, sees 0 and inserts a booking.
! The two inserts are different rows, so `FOR UPDATE` on the select locks nothing (there was no row to lock), and repeatable read lets both commit. Now the room has two bookings.
! Fixes: a unique constraint on `(room, slot)`, which turns the race into a constraint error (the best fix); or serializable isolation, which detects the read/write dependency and aborts one; or an exclusion constraint for overlapping time ranges. This is why constraints (lesson 03.01) are so valuable: they catch races that isolation levels below serializable miss.

## Common mistakes
- **Assuming the default level is serializable.** Postgres, Oracle and SQL Server default to read committed; MySQL to repeatable read.
- **Read-modify-write in application code** without a lock, version check or atomic statement.
- **Using serializable without retries.** Serialisation failures are expected, not bugs.
- **Locking in inconsistent orders**, which invites deadlocks.
- **Holding transactions open across network calls** or user think time, which holds locks and snapshots for seconds.

When two writers can touch the same data (stock counts, seat bookings, balances), say how you will stop lost updates before you are asked: an atomic conditional update for counters, `FOR UPDATE` or a version column for read-modify-write, and a unique constraint for "only one" rules. ## Many versions instead of many locks
The simplest way to isolate transactions is with locks: a reader locks a row so nobody changes it under them, a writer locks it so nobody reads half a change. It works, but readers and writers queue behind each other. A ten-minute report would block every update to the rows it touches.

**MVCC** (multiversion concurrency control) takes a different route. Each transaction (or each statement, depending on the isolation level) sees a **snapshot**: the database as it was at one moment. When a row is updated, the database does not overwrite it. It writes a **new version** of the row and keeps the old one for any transaction whose snapshot still needs it. Postgres, MySQL's InnoDB, Oracle, SQL Server (in snapshot mode) and most modern databases use some form of MVCC.

The headline benefit: **reading never blocks writing, and writing never blocks reading.** A long report keeps reading its consistent snapshot while users update the same rows. Writers still block other writers on the same row (two people cannot both change row 7 at once), but that is far rarer.

## How visibility works in Postgres
Every row version (Postgres calls it a **tuple**) carries two hidden fields:
- `xmin`: the ID of the transaction that created this version.
- `xmax`: the ID of the transaction that deleted or replaced it, or zero if it is still current.

Transaction IDs (**XIDs**) are handed out from a counter as transactions start writing. A **snapshot** records three things: the lowest XID still running, the next XID to be assigned, and the list of XIDs running at that moment. With that, a transaction can decide for any tuple: **a version is visible to me if its creator committed before my snapshot, and its deleter (if any) had not committed before my snapshot.**

An `UPDATE` is therefore "set `xmax` on the old version, and insert a new version with `xmin` = my XID". A `DELETE` just sets `xmax`. Nothing is physically removed at that point.

In read committed, a new snapshot is taken for each statement. In repeatable read and serializable, one snapshot is taken at the first statement and kept for the whole transaction (lesson 03.06).

%%timeline One row's versions over time, and which version each reader sees from its own snapshot.
[Writers] t1 | Tx 100 inserts row v1, price 10
[Readers] t2 | Report Tx 150 takes snapshot
[Writers] t3 | Tx 200 updates: v1 gets xmax 200, v2 created with price 12
[Writers] t4 | *Tx 200 commits
[Readers] t5 | Report Tx 150 reads row: sees v1, price 10
[Readers] t6 | New Tx 300 reads row: sees v2, price 12
%%

%%seq Readers and writers do not block each other: each transaction reads from its own snapshot.
Tx A reader > Table : take snapshot
Tx B writer > Table : UPDATE row, creates v2

%%

## Two ways to store old versions
Databases differ in **where** the old versions live, and this decides what cleanup they need.

**Postgres** stores every version in the table itself. The old and new versions are both full tuples in the heap. Indexes point to tuples, so a new version usually needs new index entries too. One optimisation, **HOT** (heap-only tuple) updates, avoids that: if no indexed column changed and the new version fits on the same page, the indexes are not touched and the old tuple points to the new one.

**InnoDB and Oracle** update the row **in place** and copy the old values into a separate **undo log**. A reader that needs an older version follows a chain of undo records backwards to rebuild it. The table stays compact, but long-running readers make the undo log grow, and reading old versions gets slower the further back you go.

%%compare Postgres keeps old versions in the table; InnoDB updates in place and keeps old values in an undo log.
[Postgres: versions in heap]
UPDATE -> New tuple in table -> Old tuple marked dead
+ Rollback is instant
+ Old versions read directly
- Dead tuples bloat table and indexes
- Needs VACUUM
[InnoDB: undo log]
UPDATE -> Row changed in place -> Old values to undo log
+ Table stays compact
- Rollback must undo work
- Long readers grow undo log
- Purge thread cleans undo
%%

## The catch: dead rows pile up
In Postgres, once no running transaction can possibly see an old version, it is **dead**. But it still occupies space in the table page and in every index that points to it. A table with heavy updates accumulates dead tuples: this is called **bloat**. Scans slow down because they read pages full of dead rows, and indexes grow because they hold entries for versions nobody can see. A table updated 10 times per row can, without cleanup, be mostly dead space.

%%state The life of a Postgres row version, from insert to reuse of its space or permanent freezing.
[*] -> Live : INSERT commits
Live -> Superseded : UPDATE or DELETE sets xmax
Superseded -> Dead : no snapshot can see it
Dead -> *Space reusable : VACUUM removes it
Live -> Frozen : VACUUM freezes old xmin
Frozen -> Superseded : later UPDATE or DELETE
%%

## VACUUM's four jobs
This is why Postgres needs `VACUUM`. It has four jobs.
1. **Reclaim space.** Vacuum scans pages, removes dead tuples and their index entries, and records the freed space in the **free space map** so new rows can reuse it. Plain `VACUUM` runs alongside normal traffic and takes only a light lock, but it usually does not shrink the file on disk; it makes space reusable inside it. `VACUUM FULL` rewrites the table compactly and returns space to the operating system, but it takes an `ACCESS EXCLUSIVE` lock (blocking all reads and writes) and needs disk room for a full copy, so it is rarely the right tool on a live system.
2. **Update planner statistics.** `VACUUM ANALYZE`, or autovacuum's analyse step, refreshes the statistics the planner uses (lesson 03.05).
3. **Update the visibility map.** This is a bitmap with one bit per page meaning "every tuple on this page is visible to every transaction". Vacuum skips such pages next time, and **index-only scans** can avoid visiting the table for them. A table that is never vacuumed cannot use index-only scans effectively.
4. **Prevent transaction ID wraparound.** This is the job that can take a database down.

### Transaction ID wraparound
XIDs are 32-bit, so there are about 4.2 billion of them, and the counter wraps around. Postgres compares XIDs in a **circle**: for any XID, about 2.1 billion are treated as "in the past" and 2.1 billion as "in the future". If a row's `xmin` were left alone for more than 2.1 billion transactions, it would suddenly appear to be in the future, and the row would vanish from every query.

Vacuum prevents that by **freezing** old tuples: marking them as created "infinitely long ago", visible to everyone forever, regardless of the counter. As long as every table is frozen faster than XIDs are consumed, wraparound never matters.

If freezing falls behind, Postgres defends the data. It starts logging warnings when about 40 million XIDs remain before the danger point. With about 3 million left, it refuses to start any new transaction that would assign an XID, effectively stopping all writes until an administrator runs a vacuum. A busy system consuming 20,000 XIDs per second burns through 2 billion in a little over a day, so this is not a theoretical risk.

## Autovacuum
The **autovacuum** daemon is on by default and should stay on. It vacuums a table when its dead tuples exceed a threshold: by default 50 rows plus 20% of the table (`autovacuum_vacuum_scale_factor = 0.2`). It also forces an **anti-wraparound vacuum** on any table whose oldest unfrozen XID is more than 200 million transactions old (`autovacuum_freeze_max_age`), even if nothing else triggers it.

For big tables, 20% is far too lazy: a 500-million-row table would accumulate 100 million dead tuples before cleanup starts. Teams lower the scale factor per table (to 0.01 or less) and raise autovacuum's I/O budget so it keeps up.

### What stops vacuum working
Vacuum can only remove a version once **no snapshot anywhere** might still see it. The oldest snapshot in the system sets that horizon. Anything that holds an old snapshot pins every version created since:
- **Long-running transactions**, such as an analytics query that runs for 3 hours.
- **Idle-in-transaction sessions**: a connection that ran `BEGIN` and a query, then stopped. The transaction stays open indefinitely.
- **Stale replication slots**, where a replica or a change-data-capture consumer has disconnected but the slot remains, and old **prepared transactions** from two-phase commit.
- **Hot standby feedback** from a replica running long queries, which asks the primary to keep versions those queries need.

This is not theoretical. Notion's vacuum process was stalling on its monolithic Postgres, and transaction ID wraparound became an existential risk, which was one of the main pushes towards sharding (lesson 03.10).

! Example: the forgotten transaction
! A developer opens a `psql` session at 12:00, runs `BEGIN` and a `SELECT`, and goes to lunch. Their snapshot now pins every row version created after 12:00.
! The orders table receives 5 million updates over the next 3 hours. Vacuum runs repeatedly but cannot remove any of the 5 million old versions, because the forgotten snapshot might need them.
! At about 150 bytes per tuple plus index entries, that is roughly 1.5 GB of extra dead data. Queries that scanned 2 GB now scan 3.5 GB and slow down by about 75%. Index-only scans stop helping because the visibility map has few all-visible pages.
! Setting `idle_in_transaction_session_timeout = '5min'` would have killed the session at 12:05, and vacuum would have kept up. Monitoring the age of the oldest transaction (`pg_stat_activity.xact_start`) catches the rest.

! Example: how fast are you approaching wraparound?
! A database averages 5,000 write transactions per second. That is 432 million XIDs per day.
! Autovacuum forces a freeze on a table once its oldest XID is 200 million old, so every busy table must be fully freeze-vacuumed roughly every 11 hours.
! The largest table is 2 TB. If vacuum reads it at 100 MB/s, one pass takes about 5.8 hours. That fits, but with little margin. If a long transaction blocks freezing for 4 days, the oldest XID reaches about 1.7 billion old, uncomfortably close to the 2.1 billion limit. This is the arithmetic that should set alerting thresholds.

## Common mistakes
- **Turning autovacuum off** because it "uses I/O". The bloat and wraparound risk are far worse.
- **Leaving default thresholds on huge tables.** 20% of a billion rows is 200 million dead tuples.
- **Allowing long or idle transactions.** Set statement and idle-in-transaction timeouts.
- **Reaching for VACUUM FULL in production.** It locks the table for the whole rewrite; tools that rebuild tables online (such as `pg_repack`) are safer.
- **Forgetting replication slots.** An abandoned slot holds back cleanup and fills the disk with WAL.

## The durability problem
When `COMMIT` returns, the application tells the user "payment received". From that moment the change must survive anything: a power cut, a kernel panic, the database process being killed. That is the **D** in ACID, **durability**.

The naive way to provide it is to write every changed data page to its place on disk before returning from `COMMIT`. That has two problems.
- **It is slow.** A transaction that updates an order, a payment and three index entries dirties five pages scattered across different files. Writing them means five random writes, each followed by a wait for the disk to confirm.
- **It is not even safe.** If the machine loses power after two of the five pages are written, the files are left half-updated: the payment exists but the order does not. A single 8 KB page can also be **torn**, with the first 4 KB new and the last 4 KB old, because disks only guarantee atomic writes of smaller sectors.

The opposite naive approach, writing pages lazily and returning immediately, loses committed data on every crash. The database needs a way to make commits durable without writing data pages at commit time.

%%layers Where a committed change can be when the power goes out. Only what has reached durable storage survives.
Application | told "committed"
Database buffer pool | changed pages in RAM, lost on crash
WAL buffer | log records in RAM, lost on crash
OS page cache | written but not fsynced, lost on power cut
*WAL on disk | fsynced log, survives the crash
Data files on disk | updated later at checkpoint
%%

## Write-ahead logging
The solution is the **write-ahead log (WAL)**, also called a redo log or journal. The rule is one sentence: **a change to a data page may only be written to disk after the log record describing that change has been written to durable storage.** Log first, data later.

A commit then works like this:
1. The transaction changes pages in memory, in the **buffer pool** (Postgres calls it shared buffers). The pages are now **dirty**: newer in memory than on disk.
2. For every change, a **log record** is appended to the WAL buffer in memory. A record says, in effect, "on page 4711 of table orders, at slot 3, write these bytes". Each record gets a **log sequence number (LSN)**, its byte position in the log, which only ever increases. Each data page remembers the LSN of the last record that changed it.
3. At `COMMIT`, a commit record is appended and the WAL is flushed to disk with **fsync** (a system call that waits until the device confirms the data is durable). Only then is the client told "committed".
4. The dirty data pages are written to their real locations **later**, in the background, by a writer process or at a checkpoint. Before writing a page, the database checks that the WAL is flushed at least up to that page's LSN. That check is the write-ahead rule in code.

%%seq A commit with WAL: the log is flushed before COMMIT returns; the data page reaches disk much later.
Tx > Buffer pool : modify page 4711 in memory
Tx > WAL buffer : append record, LSN 0/5A10
Tx > WAL buffer : append commit record
WAL buffer > WAL on disk : write and fsync
WAL on disk -> Tx : durable
Tx -> Tx : return COMMIT to client
Buffer pool > Data files : write page 4711 at checkpoint
%%

### Why this is fast
- The WAL is written **sequentially**, always appending at the end. Sequential writes are the fastest thing a disk can do.
- A commit needs **one** fsync, of the log, no matter how many pages it changed.
- **Group commit**: if 50 transactions commit within the same millisecond, one fsync can make all of their commit records durable at once. Throughput rises with concurrency instead of being capped at one transaction per fsync.
- Data pages are written lazily, so a hot page changed 1,000 times between checkpoints is written to disk once, not 1,000 times.

The cost of an fsync depends heavily on the hardware. A datacentre SSD with power-loss protection can confirm in 20 to 100 microseconds. A consumer SSD without it may take several milliseconds. A spinning disk takes about one rotation, 4 to 8 ms. Cloud network block storage typically sits around 0.5 to 2 ms.

%%bars Typical time for one durable fsync of the log, which sets the floor for a single commit's latency.
Enterprise SSD with power-loss protection | 0.05 | about 50 µs
Cloud network block storage | 1 | about 1 ms
Consumer SSD | 3 | 1 to 5 ms
*Spinning disk | 6 | 4 to 8 ms
%%

## Recovery after a crash
On restart after a crash, the data files may be stale (pages never written) or contain a mix of old and new pages. The WAL contains everything that happened. Recovery works as follows:
1. Find the **last checkpoint** recorded in the WAL (its location is stored in a small control file).
2. Read the log forward from there. For each record, look at the target page. If the page's LSN is older than the record's LSN, the change never reached disk, so **redo** it. If the page's LSN is already newer, skip the record. This makes replay **idempotent**: replaying a record twice has no extra effect.
3. Continue to the end of the valid log. The database is now exactly as it was at the moment of the crash.
4. Accept connections.

This is **roll-forward**, or **REDO**, recovery. In Postgres there is no undo phase. Changes from transactions that never committed are redone too, but their tuples carry an `xmin` of a transaction that has no commit record, so MVCC (lesson 03.07) treats them as invisible, and vacuum later removes them.

Engines that write **uncommitted** changes into data pages in place, such as InnoDB, need one more step. The general recovery design, called **ARIES**, has three phases: **analysis** (work out which transactions were active and which pages were dirty at the crash), **redo** (replay history, including uncommitted changes) and **undo** (roll back the changes of transactions that never committed, using undo records).

### Torn pages and full-page writes
Redo assumes the page on disk is a valid old version. A torn page breaks that. Postgres therefore writes a **full copy of each page** into the WAL the first time that page is modified after a checkpoint (`full_page_writes`). Recovery restores the whole page from the log first, then applies the later records. This makes WAL noticeably larger just after each checkpoint. InnoDB solves the same problem with a separate doublewrite buffer.

## Checkpoints bound recovery time
Without checkpoints, recovery would replay the WAL from the very beginning. A **checkpoint** periodically flushes every dirty page to the data files and writes a checkpoint record into the WAL. After that, all changes before the checkpoint are safely in the data files, so recovery starts from there, and older WAL segments can be recycled.

The trade-off: frequent checkpoints mean short recovery but more write I/O (pages flushed more often, and more full-page images in the WAL). Infrequent checkpoints mean less I/O but longer recovery. Postgres's defaults are a checkpoint every 5 minutes (`checkpoint_timeout`) or after about 1 GB of WAL (`max_wal_size`), whichever comes first, with writes spread over most of the interval to avoid I/O spikes.

%%timeline A crash and recovery. Only the WAL after the last checkpoint needs replaying.
10:00:00 | Checkpoint: all dirty pages flushed
10:01:12 | Tx 501 commits payment, WAL fsynced
10:02:40 | Tx 502 starts, changes 3 pages, no commit
10:03:05 | *Power lost: data page for Tx 501 never written
10:03:50 | Restart: read WAL from 10:00:00 checkpoint
10:03:58 | Redo Tx 501 and Tx 502 records into pages
10:04:00 | *Open: Tx 501 visible, Tx 502 invisible
%%

## WAL does much more than crash recovery
Once every change is in one ordered log, the log becomes the backbone of several other features:
- **Point-in-time recovery (PITR)**: take a base backup (a copy of the data files) and archive every WAL segment after it. To recover from a mistake, restore the backup and replay WAL up to any chosen moment, such as 14:01:59, just before someone ran `DROP TABLE`. The base backup does not even need to be an instant, consistent snapshot, because replaying the log from its start repairs any inconsistency.
- **Replication**: replicas receive the WAL stream and replay it, so they stay a few milliseconds behind the primary (Module 6). This is called physical or streaming replication.
- **Logical decoding and change data capture (CDC)**: the WAL can be decoded into row-level change events ("order 7 updated: status shipped") and published to other systems. Tools such as Debezium do this to feed Kafka (Module 8).

## Trade-offs you can tune
- `synchronous_commit = off` returns success before the WAL flush. The commit is still written within a few hundred milliseconds (Postgres flushes about every 200 ms by default), and a crash loses at most that window of recent commits. Crucially, the database stays **consistent**: you lose the newest transactions, never half of one. It suits metrics or session data, not payments, and can be set per transaction.
- **Hardware that lies.** A disk with a volatile write cache and no battery or capacitor may report "done" for an fsync while the data is still in its RAM. A power cut then loses committed transactions, and no database setting can fix that. Use drives with power-loss protection.
- **`fsync = off`** disables flushing altogether. A crash can then corrupt the whole database, not just lose recent commits. It is only for throwaway test data.

%%compare Default synchronous commit versus asynchronous commit for a high-rate event table.
[*synchronous_commit = on]

+ Committed means durable
- Each commit waits for fsync
[synchronous_commit = off]
Change -> Reply to client -> WAL fsync within 200 ms

! Example: crash after commit
! A user pays an invoice. The `UPDATE invoices SET status = 'paid'` changes page 812 in memory and appends a WAL record at LSN 3/A1000. `COMMIT` appends a commit record, fsyncs the WAL (0.1 ms on the server's SSD) and returns success. The payment page shows "Thank you".
! One second later, before any checkpoint, the server loses power. Page 812 on disk still says "unpaid".
! On restart, Postgres finds the last checkpoint at LSN 3/9F000, replays forward and reaches the record at 3/A1000. Page 812 on disk has an LSN older than that, so the change is reapplied. The commit record is present, so the transaction counts as committed. When the database opens, the invoice shows as paid. Total recovery time: a few seconds.

! Example: what group commit buys you
! A service commits small transactions from 200 concurrent connections. The log disk's fsync takes 1 ms.
! Without group commit, commits would be serialised at one per fsync: at most 1,000 commits per second, however fast the CPU is.
! With group commit, each fsync carries the commit records of every transaction waiting at that moment. If 40 are waiting on average, the same disk sustains around 40,000 commits per second, while each commit still takes only about 1 to 2 ms. Throughput scales with concurrency; single-commit latency does not drop below the fsync time.

## Common mistakes
- **Believing data is safe once written to a file.** Without fsync it may still be in the OS cache.
- **Turning off fsync for speed.** You trade a small speed gain for possible total corruption.
- **Ignoring WAL volume.** Bulk loads and frequent checkpoints can generate gigabytes of WAL per minute, filling disks and lagging replicas.
- **Forgetting archived WAL.** Point-in-time recovery only works if every segment since the base backup was kept.
- **Treating a replica as a backup.** A replica replays a `DROP TABLE` within milliseconds; only PITR undoes it.

## In an interview
If asked how a database survives a crash, explain the write-ahead rule, the single sequential fsync at commit, and redo from the last checkpoint. Then connect it to replication and change data capture: they are all the same log. Mentioning group commit and the cost of fsync on different hardware shows real depth.

> Takeaway: log first, data later. A commit only needs a sequential fsync of the write-ahead log; data pages are written lazily. After a crash, the database replays the log from the last checkpoint and rebuilds every committed change. The same log powers point-in-time recovery, replication and change data capture.

## Why IDs get hard after sharding
On a single database, IDs are a solved problem. An auto-increment column (`AUTO_INCREMENT` in MySQL, a sequence or `IDENTITY` column in Postgres) hands out 1, 2, 3 and so on, and the database guarantees no two rows get the same number. The counter lives in one place, so uniqueness is trivial.

Once data is **sharded** (split across many databases, lesson 03.10 and Module 4), each database has its own counter. Shard 1 and shard 2 both happily create a photo with ID 1,000. That breaks anything that assumes an ID identifies one thing: URLs like `/photos/1000`, caches keyed by ID, references from other tables, and above all moving a row from one shard to another, where it would collide with a different row.

Flickr hit exactly this in the 2000s. Its data was sharded across many MySQL databases, each set up as a master-master pair (two servers that both accept writes and replicate to each other). Users' data sometimes had to move between shards, so IDs had to be unique **globally**, not just per shard. Lesson 04.08 looks at this problem in general; this lesson looks at one simple, durable solution.

## The requirements
Flickr's IDs needed to be:
- **Globally unique** across every shard, forever.
- **Compact**: 64 bits, so indexes on ID columns stay small and fit in memory.
- **Roughly increasing**, so new rows go at the end of B-tree indexes (lesson 03.04) and sorting by ID is close to sorting by time.
- **Highly available**: if ID generation stops, uploads stop.

## Options Flickr rejected
- **GUIDs/UUIDs**: unique without any coordination, but 128 bits is twice the size, and random values scatter inserts across the whole B-tree, causing page splits and poor cache use (lesson 04.09). Flickr's performance depended on indexes fitting in memory. Sequential IDs also made debugging and reporting easier.
- **Consistent hashing with GUID keys**, as in Amazon's Dynamo: suits write-optimised key-value stores, not MySQL tuned for fast random reads by primary key.
- **One central database with a normal auto-increment table**, where each ID is a new row: at 60+ photos per second, plus comments, favourites, tags and groups, that table would grow by millions of useless rows a day.

## The ticket server
A **ticket server** is a tiny, dedicated MySQL database whose only job is to hand out numbers. Its table looks like this:
```
CREATE TABLE Tickets64 (
  id   BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  stub CHAR(1) NOT NULL DEFAULT '',
  PRIMARY KEY (id),
  UNIQUE KEY stub (stub)
);
```
It always holds exactly **one row**. To get a new ID, a client runs two statements on the same connection:
1. `REPLACE INTO Tickets64 (stub) VALUES ('a');` Because `stub` has a unique key and the value `'a'` already exists, `REPLACE` deletes the old row and inserts a new one. The insert takes the next auto-increment value.
2. `SELECT LAST_INSERT_ID();` returns the ID generated **by this connection**, even if other clients are generating IDs at the same moment. MySQL tracks it per connection, so there is no race.

The table never grows past one row, and MySQL's auto-increment mechanism guarantees that each call gets a new number. Separate tables give separate sequences (one for photos, one for accounts, one for groups), or several tables can share one sequence.

%%seq Getting one ID from a ticket server, then using it to insert a photo on any shard.
App > Ticket DB : REPLACE INTO Tickets64 (stub) VALUES ('a')
Ticket DB > Ticket DB : delete row, insert new row, id 4,816,001
App > Ticket DB : SELECT LAST_INSERT_ID()
Ticket DB -> App : 4,816,001
App > Photo shard 7 : INSERT photo id 4,816,001
Photo shard 7 -> App : OK
%%

## Two servers without coordination
One ticket server is a **single point of failure**: if it is down, nothing can be created. The obvious fix, two servers replicating to each other, is slow and fragile at this write rate and risks both handing out the same number during a replication delay.

Flickr's trick avoids coordination completely. It runs two ticket servers and **splits the number space** between them using two MySQL settings:
- `auto_increment_increment`: how much the counter goes up each time.
- `auto_increment_offset`: the first value.

| Server | increment | offset | Sequence |
| A | 2 | 1 | 1, 3, 5, 7, 9... |
| B | 2 | 2 | 2, 4, 6, 8, 10... |

Server A only ever produces odd numbers and server B only even numbers, so they can **never** produce the same number, no matter what happens to the network between them. They do not talk to each other at all. Clients round-robin between the two and skip whichever is down.

%%timeline Two ticket servers serving requests independently. They never coordinate, and their counters drift apart without any harm.
[Server A, odd] 10:00:01 | issues 1,001
[Server B, even] 10:00:01 | issues 1,002
[Server A, odd] 10:00:02 | issues 1,003
[Server B, even] 10:00:03 | *goes down for maintenance
[Server A, odd] 10:00:05 | issues 1,005
[Server A, odd] 10:00:06 | issues 1,007
[Server B, even] 10:00:07 | back, issues 1,004
%%

### The price: roughly ordered, not strictly ordered
The two counters drift apart. If server B is down for an hour, server A races ahead; when B returns, it issues IDs lower than ones A gave out an hour ago. Flickr reported having a few hundred thousand more odd IDs than even ones. That is fine for their needs: IDs are unique and **roughly** increasing, which is enough for index locality and approximate time sorting. But you cannot rely on "a higher ID was created later", and you cannot use the IDs to detect gaps or count rows.

This setup ran in production from January 2006, in keeping with Flickr's principle of doing "the dumbest possible thing that will work". It is a good model for system design in general: a few lines of configuration on a technology the team already understood, instead of a new distributed system.

## Making it faster: allocate in blocks
A network round trip per ID costs about 0.5 to 1 ms and puts every insert on the ticket server's critical path. The common improvement is **block allocation** (sometimes called hi/lo or segment allocation): a client asks for a range instead of one number, then hands out IDs locally until the range runs out.

With a sequence that steps by 1,000, one call reserves 1,000 IDs. The database load drops by a factor of 1,000, and the client can fetch the next block in the background when the current one is, say, 80% used, so no request ever waits on the network.

%%seq Block allocation: one round trip reserves 1,000 IDs, which the app server then hands out locally.
App server > Ticket DB : reserve next block
Ticket DB -> App server : block 52,000 to 52,999
App server > App server : hand out 52,000, 52,001, ...
App server > Ticket DB : at 80% used, prefetch next block
Ticket DB -> App server : block 61,000 to 61,999
%%

The trade-offs:
- If an app server crashes, the unused part of its block is **lost**. With 64-bit IDs that waste does not matter, but it leaves gaps.
- IDs are now even less ordered: server 1 is issuing from 52,000 while server 2 issues from 61,000.

## Failure scenarios
- **One ticket server dies.** Clients use the other. Capacity halves, but nothing breaks.
- **A ticket server's disk is restored from an old backup.** Its counter jumps backwards, and it starts re-issuing IDs that are already in use. This is the dangerous case. The safe recovery is to set the counter well above the highest ID it could ever have issued (for example, the current maximum ID in the data plus a large margin) before letting it serve.
- **You need a third server.** The increment is baked into the scheme. Changing from step 2 to step 3 means picking a new start point above every ID already issued and reconfiguring all servers at once. This is the scheme's main inflexibility, and why many designs fix a generous step (say 16) from day one and run only as many servers as they need.

## Where it fits among ID schemes
%%matrix Common ways to generate unique IDs across shards, and what each one gives you.
Scheme | No central service | 64-bit | Time-ordered | Survives clock problems
Single auto-increment | no | yes | yes, strictly | yes
Ticket servers | no | yes | partial, roughly | yes
Block allocation | no | yes | partial, coarse | yes
UUID v4 | yes | no, 128-bit | no | yes
Snowflake style | yes | yes | yes, roughly | no, needs care
%%

Snowflake-style IDs (time + machine ID + sequence, lessons 04.10 and 04.11) remove the network call entirely but depend on clocks behaving. Ticket servers depend on no clocks at all, which is a real advantage. The same idea also works outside MySQL: in Postgres, `CREATE SEQUENCE photo_ids INCREMENT BY 2 START WITH 1` on one server and `START WITH 2` on another gives the same odd/even split, and Redis's atomic `INCRBY` can serve as a ticket counter if it is persisted carefully.

! Example: ID ranges with three servers
! With 3 ticket servers, set `auto_increment_increment = 3` and offsets 1, 2 and 3. Server 1 issues 1, 4, 7, 10; server 2 issues 2, 5, 8, 11; server 3 issues 3, 6, 9, 12. For any ID, `id mod 3` tells you which server issued it, which is handy for debugging.
! Adding a fourth server later requires a new increment of 4. Suppose every ID issued so far is below 9.2 billion. You configure all four servers with increment 4 and offsets 1 to 4, move each counter up to 10 billion (MySQL then issues the next value above the counter that matches its offset), and switch them over together. The old servers must stop before the new scheme starts, or the residues could overlap. Planning a step of 8 or 16 from the start avoids this migration.

! Example: is one ticket server pair enough?
! Peak traffic is 20,000 new objects per second across the whole site. Without batching, that is 20,000 `REPLACE` + `SELECT` pairs per second, split over two servers: 10,000 each. Each `REPLACE` is a delete and an insert on a one-row table, which a modern MySQL server can do at tens of thousands per second, but with durable commits it is limited by log fsyncs.
! With block allocation of 1,000 IDs, the load drops to 20 requests per second in total. Each server sees 10 requests per second and is essentially idle. A 64-bit space is 1.8 × 10^19 values; at 20,000 per second you would run out in about 29 million years, so wasting unused blocks is irrelevant.

## Common mistakes
- **Assuming IDs are strictly ordered** across servers and using them as timestamps.
- **Restoring a ticket server from backup** without bumping its counter above every issued ID.
- **Choosing an increment of exactly the current server count**, which makes adding servers a migration.
- **Calling the ticket server on every insert** instead of allocating blocks.

## In an interview
If asked how to generate unique IDs across shards, the ticket server is a strong, simple answer to give first: name the odd/even offset trick, block allocation to remove the per-insert round trip, and the trade-off (roughly ordered, a small service to run). Then compare it with Snowflake-style IDs, which avoid the network call but depend on clocks.

> Takeaway: a ticket server is a one-row MySQL table that hands out auto-increment IDs. Two servers with the same step and different offsets (odd and even) can never collide, need no coordination, and survive either one failing. Allocate IDs in blocks to remove the per-insert round trip, and accept that IDs are only roughly ordered.

## Diagnose before you scale
A relational database that is struggling rarely needs sharding first. Sharding is the most powerful option and also the most expensive to build and to live with. Before choosing any fix, find out **what** is running out. The four usual bottlenecks are:
- **CPU**: too many queries, or a few expensive ones (sorts, joins, scans).
- **Memory**: the **working set** (the data and indexes touched regularly) no longer fits in the buffer pool, so reads hit disk and latency jumps from microseconds to milliseconds.
- **Disk I/O**: too many random reads, or too much write and log volume.
- **Connections and locks**: too many open connections, or transactions waiting on each other.

A further category is **operational**: the database is big enough that backups take 12 hours, an index build takes a day, or vacuum cannot keep up (lesson 03.07). Each bottleneck has different fixes, so measure first: the slowest queries by total time (`pg_stat_statements` in Postgres), cache hit rate, CPU, I/O wait and replication lag.

## The order to try things
Cheapest and least disruptive first.

**1. Tune queries and indexes.** Find the queries that consume the most total time, read their plans (lesson 03.05) and fix them: add the right composite index, remove a function from an indexed column, stop selecting columns you do not need, replace `OFFSET` pagination (lesson 04.12). Fix the schema too: sensible types (`DECIMAL` for money, integers for IDs), and move rarely used large columns to a side table so hot rows are small. Often a single missing index is the whole problem. This step costs hours, not months.

**2. Add a connection pooler.** Each Postgres connection is a separate process using several megabytes. Hundreds of app servers each holding 20 connections can exhaust the database before any query is slow. A pooler such as PgBouncer lets thousands of client connections share a few dozen real ones.

**3. Cache hot reads.** Put Redis or Memcached in front of the database for data that is read far more often than written: profiles, product pages, configuration (Module 5). A cache hit costs well under a millisecond and no database work at all, so a 90% hit rate removes 90% of those reads. The price is staleness and invalidation logic.

**4. Scale vertically.** Move to a bigger machine: more RAM so the working set fits in memory, faster NVMe disks, more cores. Cloud instances reach hundreds of cores and several terabytes of RAM. It is boring and it works, with no code changes. But it has a ceiling, the price grows faster than linearly near the top, and some limits are not hardware at all: at Notion, vacuum degraded and maintenance became risky well before the hardware ran out. Vertical scaling is a bridge, not a destination.

**5. Add read replicas.** Replicas receive the primary's write-ahead log (lesson 03.08) and replay it, then serve read-only queries. They multiply read capacity and give you a standby for failover. Caveats:
- **Replication lag**: replicas are milliseconds to seconds behind. A user who saves a profile and is immediately routed to a replica may see the old version.
- **Writes do not scale**: every write still goes to the one primary, and every replica replays every write.
- **Failover** can lose writes not yet copied (with asynchronous replication), and promoting a replica needs tooling.

**6. Partition by function (federation).** Split into separate databases per domain: users, orders, payments, messaging. Each is smaller, and writes to different domains run on different machines in parallel. The cost: joins across domains move into the application, and a transaction that touches two domains needs extra care (lesson 08.07 covers sagas).

**7. Shard.** Split one table's rows across many databases by a **shard key**, such as `user_id`. Each shard holds a slice and takes a slice of the writes, so write capacity and storage scale out. Costs: queries that span shards are slow or impossible, joins and transactions across shards are hard, unique constraints only hold within a shard, an uneven key creates hot shards, and moving data between shards is complex (Module 4).

%%bars Rough engineering effort for each scaling step, in engineer-weeks. Sharding dwarfs the rest.
Tune queries and indexes | 1 | days
Connection pooler | 1 | days
Cache hot reads | 3 | weeks
Bigger machine | 1 | a maintenance window
Read replicas | 3 | weeks
Split by domain | 12 | months
*Shard | 40 | many months
%%

### The order is a guide, not a law
Caching and replicas usually come before vertical scaling only when the load is read-heavy and cheap to cache. In practice teams interleave steps 3 to 5, and a write-heavy load skips caching and replicas because they do not help writes at all. **Denormalisation** (storing a copy, such as a `like_count` column, to avoid an expensive join or count) also helps reads, at the cost of keeping copies in sync.

## Living with replicas: read-your-writes
The most common replica bug: a user updates their display name, the write goes to the primary, the next page load reads from a replica that is 300 ms behind, and the user sees the old name. They assume the save failed and try again.

The fixes, from simplest:
- **Read your own data from the primary** for a short window after writing, for example 5 seconds, tracked in the session.
- **Track the write position**: remember the WAL position (LSN) of the user's last write and only read from a replica that has replayed past it.
- **Route by data**: always read a user's own profile from the primary; read other users' profiles from replicas.

%%seq Read-your-writes on replicas: the app remembers the user's last write and avoids replicas that have not caught up.
User > App : save name "Ana"
App > Primary : UPDATE users, commit at LSN 900
App -> User : saved, remember LSN 900 in session
User > App : load profile
App > Replica : replayed past LSN 900?
Replica -> App : no, at LSN 870
App > Primary : read profile
Primary -> App : name "Ana"
%%

## Case study: Notion shards Postgres
Notion ran on a single Postgres database for five years, through four orders of magnitude of growth. By mid-2020 CPU spikes were paging on-call engineers, schema changes had become unsafe, vacuum was stalling and transaction ID wraparound loomed (lesson 03.07).

### Decisions
- **Application-level sharding**, rather than an extension such as Citus or a proxy such as Vitess, to keep full control over data placement and behaviour.
- **Shard everything reachable from a block by foreign key.** A block is Notion's unit of content. Comments, discussions and other tables that hang off blocks go to the same shard, so related data stays together and transactions within it still work.
- **Partition key: workspace ID.** Every block belongs to exactly one workspace, and users work within one workspace at a time, so nearly every query touches one shard.
- **480 logical shards on 32 physical databases**, 15 per host. Each logical shard is a Postgres schema. Many small logical shards mean you can later move whole shards to new hosts without splitting any of them. 480 was chosen because it has many factors: it divides evenly by 32, 40, 48, 60, 80 and more, so the fleet can grow 32 to 40 to 48 hosts with an even spread. 512 would only divide evenly by powers of two.

%%tree Notion's layout: workspace ID picks one of 480 logical shards, and each physical host holds 15 of them.
Workspace ID
  hash to logical shard 0 to 479
    Host 1 | logical shards 0 to 14
      schema0001 | blocks, comments, spaces
      schema0002
    Host 2 | logical shards 15 to 29
    *Host 32 | logical shards 465 to 479
%%

### Migration
1. **Double-write**: new writes went to both the old database and the shards. Writing directly to both from the application proved flaky, and logical replication could not keep up, so writes were recorded in an audit log and a catch-up script applied them to the shards.
2. **Backfill** existing data, which took about three days on a 96-vCPU machine. Records were skipped if the shard already held a newer version.
3. **Verify** by sampling records and by "dark reads": serving each read from the old database but also reading from the shards and comparing the results. Different engineers wrote the migration code and the verification code, so the same bug was unlikely to appear in both.
4. **Switch over** in about a five-minute maintenance window.

The main lesson Notion drew: **shard earlier**, before the old database is so strained that it struggles to absorb the extra load of the migration itself.

First 5 years | One Postgres, four orders of magnitude of growth
Mid 2020 | *CPU spikes, unsafe migrations, vacuum stalls
Planning | Workspace ID key, 480 shards on 32 hosts
Step 1 | Double-write via audit log
Step 2 | Backfill, about 3 days on 96 vCPUs
Step 3 | Dark reads compare old and new

! Example: a social app at 50,000 queries per second
! 95% of traffic is reads of profiles and posts: 47,500 reads and 2,500 writes per second. The primary is at 85% CPU and p99 latency is 400 ms.
! Step 1: `pg_stat_statements` shows one query, "recent posts by user", takes 40% of total database time. `EXPLAIN` reveals a missing index on `posts(user_id, created_at)`. After adding it (concurrently, lesson 03.11), CPU falls to 55% and p99 halves.
! Step 2: cache profiles and post bodies in Redis with a 60-second TTL. The hit rate is 85%, removing about 40,000 reads per second from the database.
! Step 3: add two read replicas for the remaining 7,500 reads per second, with read-your-writes handled by reading the user's own profile from the primary.
! Writes at 2,500 per second fit easily on one large primary. Sharding waits until write volume or data size demands it, but the plan (shard by `user_id`, many logical shards) is written down now so new tables are designed with it in mind.

! Example: when replicas are the wrong tool
! An IoT platform ingests 60,000 sensor readings per second and the primary's disk is saturated by writes and WAL. The team adds three replicas and nothing improves: each replica must replay all 60,000 writes per second too, and reads were never the problem.
! The right steps are write-side: batch inserts (one insert of 500 rows instead of 500 inserts), drop unused indexes on the readings table, use time-based partitions so old data is dropped as whole partitions instead of deleted row by row, and if that is not enough, shard by device ID or move the readings to a store built for this write pattern (Module 7).

## Common mistakes
- **Sharding first.** Months of work and permanent complexity for a problem an index would have fixed.
- **Adding replicas for a write problem.** Every replica replays every write.
- **Ignoring replication lag** until users report "my change disappeared".
- **Waiting too long to shard.** The migration itself needs headroom on the old system.
- **Too few logical shards.** If you start with exactly as many shards as hosts, growing means splitting shards, which is far harder than moving them.

## In an interview
When the interviewer says "the database is the bottleneck", ask which resource: reads, writes, data size or connections. Then walk the ladder out loud: tune and index, pool connections, cache, scale up, replicas for reads, and shard only for writes or size. When you do shard, name the key, say which queries it keeps on one shard and which become scatter-gather, and mention many logical shards for future moves.

> Takeaway: find the bottleneck first, then tune, cache, scale up and add replicas before sharding. Replicas and caches only help reads; splitting and sharding are the tools for write volume and data size. When you shard, pick a key that keeps related data and common queries on one shard, and use many logical shards so you can move them later.

?? First measure which resource is exhausted. Then: 1) tune queries and indexes (cheapest, often fixes it); 2) cache hot reads in Redis or Memcached; 3) scale vertically to a bigger machine with more RAM and faster disks; 4) add read replicas for remaining read load, handling replication lag with read-your-writes. Caching, replicas and vertical scaling can be interleaved depending on the workload: read-heavy loads favour cache and replicas, while write-heavy loads get nothing from them and go to vertical scaling and then sharding sooner. Shard last, only when write volume or data size outgrows one primary, because it brings cross-shard queries and transactions, hot shards and rebalancing work. When sharding, choose a key that keeps related data together and create many logical shards.

@03.11
## Why CREATE INDEX can take a site down
You have found the missing index that will fix your slowest query (lesson 03.03). You run `CREATE INDEX orders_customer_idx ON orders (customer_id)` on production. Ten seconds later, alerts fire: checkout is timing out.

A plain `CREATE INDEX` in Postgres takes a `SHARE` lock on the table for the whole build. That lock allows reads but **blocks every `INSERT`, `UPDATE` and `DELETE`**. The lock is held while the database scans the entire table, sorts all the values and writes the new B-tree. On a table of hundreds of millions of rows that takes minutes to hours.

On a busy table even a short block is a disaster. Picture a table taking 3,000 writes per second. Every write that arrives during the build waits. The application's connection pool fills with waiting requests within a second or two. New requests cannot get a connection and time out. Upstream services retry, adding load. The database is healthy, CPU is fine, yet the application is effectively down.

## The lock queue trap
There is a second trap, and it applies to any statement that needs a strong lock, including quick ones like `ALTER TABLE ... ADD COLUMN`.

Locks in Postgres are granted in queue order. A request for a strong lock must wait until every transaction currently holding a conflicting lock finishes. **While it waits, every new query that needs a conflicting lock queues behind it**, even plain `SELECT`s if the waiting lock is `ACCESS EXCLUSIVE`. So:
1. A reporting query has been reading `orders` for 4 minutes and will run for 6 more.
2. A migration runs `ALTER TABLE orders ADD COLUMN note text`, which needs `ACCESS EXCLUSIVE`. It would take 2 ms, but it must wait for the report.
3. Every new query on `orders`, reads included, now queues behind the migration.
4. For 6 minutes, nothing can touch `orders`.

A statement that would have taken milliseconds causes a 6-minute outage. The defence is to set a short **`lock_timeout`** on migrations (for example `SET lock_timeout = '2s'`). If the lock is not granted in 2 seconds, the migration fails, the queue drains instantly, and you retry later.

%%seq The lock queue trap: a 2 ms ALTER waits behind a long report, and every new query waits behind the ALTER.
Report > orders : SELECT, runs 10 minutes
Migration > orders : ALTER TABLE, wants exclusive lock
orders > Migration : wait for report
App query 1 > orders : SELECT
orders > App query 1 : wait behind migration
App query 2 > orders : INSERT
orders > App query 2 : wait behind migration
Report -> orders : finishes after 6 more minutes
orders -> Migration : lock granted, 2 ms
orders -> App query 1 : finally runs
%%

## CREATE INDEX CONCURRENTLY
`CREATE INDEX CONCURRENTLY` builds the index without blocking writes. It takes a weaker lock (`SHARE UPDATE EXCLUSIVE`) that lets inserts, updates and deletes continue, and solves the problem of rows changing during the build by working in phases:
1. **Register the index** in the system catalog, marked as **not ready** and **invalid**. Then wait for every transaction that could have the table open with the old definition to finish, so that from now on every new write knows the index exists.
2. **First scan.** Take a snapshot, scan the whole table and build the index from the rows visible in it. Meanwhile, ongoing writes start adding their own entries to the index (it is now marked **ready** for inserts, but still invalid for queries).
3. **Wait again**, then do a **second scan** to add any rows that were inserted or updated between the first snapshot and the moment writes began maintaining the index.
4. **Wait for older snapshots** that might not see the new entries to finish, then mark the index **valid**. From now on the planner can use it.

%%state The states an index passes through during CREATE INDEX CONCURRENTLY, including the failure path.
[*] -> Registered : catalog entry, invalid, not ready
Registered -> Ready : writers now maintain it
Ready -> Built : first scan done
Built -> Caught up : second scan done
Caught up -> *Valid : old snapshots finished
Ready -> Invalid leftover : error or cancel
Built -> Invalid leftover : duplicate key or deadlock
Invalid leftover -> [*] : DROP INDEX CONCURRENTLY
%%

### The costs
- **More work and more time.** Two full table scans plus the waits. Expect it to take two to three times as long as a plain build, while adding CPU and I/O load to a live system.
- **It waits for existing transactions**, several times. A single long-running transaction, or an idle-in-transaction session, stalls the build until it ends.
- **It cannot run inside a transaction block.** Migration tools that wrap every migration in `BEGIN ... COMMIT` must be told to skip that for this step.
- **One at a time.** Only one concurrent index build can run on a table at once.

%%compare A plain index build versus a concurrent one on a busy 400-million-row table.
[Plain CREATE INDEX]
Lock table for writes -> Scan and sort once -> Index valid
+ Fastest build, about 40 minutes
+ Atomic: works or leaves nothing
- Writes blocked the whole time
- Outage on a busy table
[*CREATE INDEX CONCURRENTLY]
Register -> Scan 1 -> Scan 2 -> Wait -> Valid
+ Writes keep flowing
- About 2 to 3 times slower
- Extra load on a live system
- Can fail, leaving an INVALID index
%%

## When it fails
A concurrent build can fail partway: a deadlock, a cancelled statement, a timeout, or duplicate values when building a **unique** index. Unlike a plain build, it does not clean up after itself. It leaves an **INVALID** index behind. Queries ignore it, but every write still pays to maintain it, so it is pure cost. You can find such leftovers with `SELECT indexrelid::regclass FROM pg_index WHERE NOT indisvalid`. Fix them with `DROP INDEX CONCURRENTLY` and a retry, or with `REINDEX INDEX CONCURRENTLY`.

Unique indexes have an extra twist. Uniqueness is enforced from the moment the second scan starts, so other transactions can get unique-violation errors **before** the index is usable, and even if the build then fails. If the existing data contains duplicates, the build will fail after doing most of its work, so check for duplicates with a `GROUP BY ... HAVING count(*) > 1` query first.

Partitioned tables add one more wrinkle: `CREATE INDEX CONCURRENTLY` is not supported directly on the parent. You build the index concurrently on each partition, create the parent index with `ON ONLY` (a metadata-only step), and attach each partition's index to it.

## Online schema changes in general
Every schema change on a large, busy table needs a plan. The first question is always: **which lock does this statement take, and for how long?**

%%matrix Common Postgres schema changes, the lock they take and whether they rewrite or scan the table.
Change | Blocks reads | Blocks writes | Rewrites or scans table
Add nullable column, no default | yes, briefly | yes, briefly | no
Add column with constant default (11+) | yes, briefly | yes, briefly | no
Change column type | yes | yes | yes, rewrite
Add NOT NULL | yes | yes | yes, full scan
Add foreign key NOT VALID, then VALIDATE | no | partial, briefly | yes, scan in validate step
CREATE INDEX | no | yes | yes, build
CREATE INDEX CONCURRENTLY | no | no | yes, two scans
%%

Some patterns that turn dangerous changes into safe ones:
- **Constraints in two steps.** Add a foreign key or check constraint with `NOT VALID` (instant, applies only to new rows), then run `VALIDATE CONSTRAINT`, which scans the table under a weak lock that allows writes.
- **NOT NULL via a check constraint.** Add `CHECK (col IS NOT NULL) NOT VALID`, validate it, and then `SET NOT NULL` can use the validated constraint instead of scanning.
- **MySQL online DDL.** InnoDB supports many changes with `ALGORITHM=INPLACE, LOCK=NONE` or even `ALGORITHM=INSTANT`. For the rest, tools such as **gh-ost** and **pt-online-schema-change** create a new copy of the table with the new schema, copy rows across in small batches, keep the copy in sync with ongoing changes (gh-ost by reading the binary log, pt-osc with triggers), and finally swap the two tables in an instant rename.
- **Always** set `lock_timeout`, run large changes in low-traffic hours, watch replication lag (index builds generate a lot of WAL) and have a way to cancel.

! Example: adding an index to orders
! The orders table has 400 million rows and takes 3,000 writes per second. A plain `CREATE INDEX` would block writes for roughly 40 minutes, queueing about 7 million writes. That is not an option.
! The team runs `CREATE INDEX CONCURRENTLY orders_customer_idx ON orders (customer_id);` outside a transaction, with `statement_timeout` disabled for that session and `lock_timeout` at 5 seconds so it cannot block traffic while waiting.
! It takes 90 minutes. Writes flow normally the whole time; disk I/O rises by about 30% and replicas fall a few seconds behind during the scans.
! Afterwards they check `pg_index.indisvalid` for the new index. It is true, so they run `EXPLAIN` on the target query and confirm it now uses an index scan. Had the build failed, they would `DROP INDEX CONCURRENTLY orders_customer_idx` and retry in a quieter hour.

! Example: the migration that took checkout down for 7 minutes
! At 14:00 an analytics job starts a 9-minute query on `payments`. At 14:02 a deploy runs `ALTER TABLE payments ADD COLUMN risk_score int`. That needs an `ACCESS EXCLUSIVE` lock and waits for the analytics query.
! From 14:02 every checkout request reads `payments`, queues behind the `ALTER`, and holds a pooled connection while it waits. Within 3 seconds all 200 pooled connections are waiting. Checkout returns errors until 14:09, when the analytics query ends, the `ALTER` runs in 3 ms, and the queue drains.
! With `SET lock_timeout = '3s'` in the migration, the `ALTER` would have failed at 14:02:03, freeing the queue at once. The deploy would have retried successfully at 14:09, and no customer would have noticed.

## Common mistakes
- **Running a plain CREATE INDEX on a live, busy table.**
- **No lock_timeout on migrations**, letting a quick change queue behind a long query.
- **Wrapping CONCURRENTLY in a transaction**, which makes it fail immediately.
- **Not checking for INVALID indexes** after a failed build; they slow every write.
- **Building a unique index on dirty data** without checking for duplicates first.
- **Ignoring replicas.** The index build's WAL must be replayed, and lagging replicas serve stale reads.

## In an interview
When your design adds an index or changes a schema on an existing large table, say how you would roll it out: concurrent or online variant, a lock timeout, low-traffic window, watching replication lag, and checking the result. It signals that you have operated real databases, not just designed them.

> Takeaway: a plain CREATE INDEX blocks writes for the whole build, and any strong lock request can queue all traffic behind a long transaction. Use CREATE INDEX CONCURRENTLY and online DDL tools on live tables, always set a lock timeout, accept slower builds, and check for and clean up invalid indexes when a build fails.

?? A normal CREATE INDEX holds a lock that blocks every INSERT, UPDATE and DELETE on the table until the build finishes, and on a large table that is minutes to hours. On a busy table, writes pile up behind the lock, the application's connection pool fills with waiting requests, new requests time out and retries add load, so the application goes down even though the database is healthy. Worse, the build must first wait for any in-progress write transaction on the table, and new writes queue behind it while it waits (for ALTER TABLE, which needs an exclusive lock, even reads queue). @03.12
## Code and schema cannot change at the same instant
On your laptop, changing a schema is easy: edit the table, edit the code, restart. In production it is not, because **there is no single instant at which everything changes**.
- A deploy rolls out over minutes. For that whole time, old and new versions of the application run side by side against the same database.
- If something goes wrong, you roll back the code, but not the data.
- Background workers, cron jobs, mobile apps that users never update, and other teams' services all read the same tables or messages on their own schedules.
- Queues, caches and replicas may still hold data written in the old shape.

So the rule is: **every individual change must be compatible with every version of code that might still be running.** A breaking change (rename, type change, split a column, move data to a new table) is never done in one step. It is broken into a sequence of compatible steps. This approach is usually called **expand and contract** (or parallel change): first expand the schema so it supports both the old and new shape, migrate code and data across, then contract by removing the old shape.

## Renaming a column with zero downtime
A rename is the classic case. `ALTER TABLE users RENAME COLUMN fullname TO display_name` is instant inside the database. But at that instant, every running app server still sends `SELECT fullname ...` and starts failing. Deploying the code first fails the other way: the new code asks for `display_name`, which does not exist yet. There is no ordering of "rename" and "deploy" that works.

Instead:
1. **Add the new column.** `ALTER TABLE users ADD COLUMN display_name text;` Nullable and with no default, it is a fast catalog-only change (with a `lock_timeout`, lesson 03.11). Old code ignores it.
2. **Deploy code that writes both columns** on every insert and update, and still **reads the old one**. A database trigger that copies `fullname` into `display_name` on write is an alternative that also covers writers you do not control.
3. **Backfill.** Copy existing values: `UPDATE users SET display_name = fullname WHERE id BETWEEN ? AND ? AND display_name IS NULL`, in batches of a few thousand rows, with a pause between batches so replicas keep up and locks are short.
4. **Deploy code that reads the new column** (still writing both). Verify: compare the two columns, watch error rates. If anything is wrong, roll back to step 2's code; the data is still intact in both places.
5. **Deploy code that stops writing the old column.** Nothing reads it any more.
6. **Drop the old column**, after a waiting period long enough that you are sure no straggling process, report or other team uses it.

%%timeline Renaming fullname to display_name: schema changes and code deploys alternate, so every running version always works.
[Schema] Day 1 | Add display_name, nullable
[Code] Day 2 | v2 writes both, reads fullname
[Schema] Day 2 | Backfill display_name in batches
[Code] Day 4 | *v3 reads display_name, writes both
[Code] Day 6 | v4 writes display_name only
[Schema] Day 20 | *Drop fullname
%%

Notice that each step is safe for the code running before **and** after it. That is the property to check for any migration plan.

%%matrix At each step of the rename, which code versions work correctly against the schema and data. Every step overlaps with the one before.
Step | v1 old code | v2 writes both | v3 reads new | v4 new only
After add column | yes | yes | no, data missing | no
After backfill | yes | yes | yes | no, v1 still reads old
v3 deployed | partial, its writes miss new | yes | yes | yes
After drop old | no | no | no | yes
%%

## Stripe's four-phase pattern
The same idea scales to much bigger changes. Stripe moved hundreds of millions of subscription records out of a field embedded in each customer record and into their own table, with no downtime. The scale makes the point: at one second per object, a naive serial migration of 100 million records would take over three years.

1. **Dual write.** Change the code to write every subscription change to both the old and new places. Then **backfill** existing records. To find which records needed copying without loading production databases, Stripe ran jobs on Hadoop over database snapshots, then copied records with a fleet of parallel workers.
2. **Change reads.** Switch reads to the new table. To check it was right, Stripe used GitHub's Scientist library: each read runs against both the old and new path, returns the old result to the user, and records any mismatch. Users are unaffected; engineers get a list of differences to fix.
3. **Change writes.** Make the new table the source of truth, writing to it first. This was the hardest phase: subscription logic spanned thousands of lines and several services. They made the old access paths raise errors in testing so stragglers surfaced.
4. **Remove old data and code.**

Each step was a small change (a few hundred lines) that could be rolled back on its own.

%%seq Comparing old and new read paths before switching: the user always gets the old result, and mismatches are logged.
App > Old path : read subscription
App > New table : read subscription
Old path -> App : result A
New table -> App : result B
App > Mismatch log : record if A differs from B
App -> App : return result A to user
%%

## Making backfills safe
Backfills are where many migrations hurt production. A single `UPDATE users SET display_name = fullname` on 200 million rows would hold row locks on every row until it commits, generate hundreds of gigabytes of WAL in one go, bloat the table with 200 million dead tuples (lesson 03.07) and push replicas minutes behind. Make backfills:
- **Batched**: a few thousand rows per transaction, walking the primary key (`WHERE id > last_id ORDER BY id LIMIT 5000`), not `OFFSET` (lesson 04.12).
- **Throttled**: sleep between batches, and slow down automatically if replication lag or database CPU rises.
- **Resumable**: record the last processed key so a crash or deploy does not restart from zero.
- **Idempotent**: running a batch twice gives the same result (`WHERE display_name IS NULL`).

## Evolving serialised data
The same thinking applies to data outside the database: messages in Kafka, values in caches, files in object storage, and requests between services. A consumer running last week's code may read a message written by this week's producer, and the other way round. Two kinds of compatibility matter:
- **Backward compatible**: new code can read data written by old code.
- **Forward compatible**: old code can read data written by new code (and ignore what it does not understand).

Binary encoding formats are built around these rules. Consider one small record encoded three ways: about 82 bytes as JSON, 33 bytes in Protocol Buffers, and 32 bytes in Avro.
- **Protocol Buffers and Thrift** store a numeric **tag** with each field, not its name. A reader that meets an unknown tag skips it, which gives forward compatibility. You can add fields with new tag numbers, remove optional fields, and rename fields freely, because names never appear in the data. You must never **reuse** a removed field's tag for something else, and never change a tag's type in incompatible ways. Marking a field `required` makes evolution risky, because removing it later breaks old readers; newer protobuf versions dropped `required` for this reason.
- **Avro** stores no tags at all, which makes it the most compact. The reader resolves each record using **both** the writer's schema and its own, matching fields by name. New fields need default values so old data can be read; renames go through aliases. The catch is that the reader must know the exact writer's schema, so it travels in a file header or is fetched from a **schema registry** by an ID stored with each message.

%%compare How Protocol Buffers and Avro make schema evolution safe.
[Protocol Buffers]
Each field: tag number + value
+ Unknown tags are skipped
+ Rename fields freely
- Never reuse a removed tag
- About 33 bytes for the sample
[Avro]
No tags, fields in schema order
+ Smallest, about 32 bytes
+ Reader matches fields by name
- Needs the writer's schema
- New fields need defaults
%%

These are the same rules as in lessons 01.11 and 02.08 for APIs and events: additive, optional changes are safe; changing the meaning of a field or reusing an identifier is not.

## Practical guardrails
- **Separate schema migrations from code deploys**, and ship them in the safe order: expand first, contract last.
- **Make every step reversible** until the final cleanup. Dropping the old column is the only one-way door, so do it last and late.
- **Compare before you switch**: dual reads, row-count checks, checksums on samples.
- **Test against production-sized data**, because a migration that takes 2 seconds on staging can take 2 hours on production.
- **Lint migrations** in code review for dangerous operations: type changes, `NOT NULL` without a check constraint, non-concurrent index builds, missing lock timeouts.

! Example: splitting name into first_name and last_name
! The `customers` table has 80 million rows with a `name` column. The product needs `first_name` and `last_name`.
! Day 1: add both columns, nullable. Deploy code that writes all three columns on every change and still reads `name`.
! Days 2 to 3: backfill by splitting existing names in batches of 5,000 rows, with a 50 ms pause. That is 16,000 batches; at about 150 ms each including the pause, about 40 minutes. Names that do not split cleanly ("Madonna", "Mary Ann de la Cruz") are logged for review rather than guessed.
! Days 4 to 10: deploy code that reads the new columns but compares them with `name` on each read, logging mismatches. Fix the 0.3% of oddly split names.
! Day 11: switch all reads to the new columns and stop writing `name`. Day 25: drop `name`. At no point was any running version of the code broken.

! Example: what goes wrong if you skip a step
! A team renames `price` to `price_cents` in one migration that runs just before the deploy. The rename takes 3 ms. The deploy takes 6 minutes to roll across 40 servers.
! For those 6 minutes, the servers still on old code send queries naming `price` and get "column does not exist". At 2,000 requests per second and an average of 20 old servers, roughly 360,000 requests fail. Rolling back the code does not help, because the column is now `price_cents`; only another emergency migration does. The six-step version would have produced zero errors.

## Common mistakes
- **Renaming or changing a type in one step.** There is no deploy order that makes it safe.
- **One giant backfill transaction.** Locks, WAL floods, bloat and replica lag.
- **Dropping the old column too soon**, before every reader has moved.
- **Reusing a protobuf tag number** for a different field; old data will be misread silently.
- **Adding a required field** to a message format; old producers cannot supply it.

## In an interview
If asked to change a schema in a running system, say "expand and contract" and walk through the steps: add, dual write, backfill in batches, switch reads with verification, stop old writes, drop. Then mention the risk in each step (lock time, backfill load, stragglers) and how you limit it.

> Takeaway: never make a breaking change in one step. Expand (add the new shape and dual write), migrate (backfill in batches and switch reads with verification), then contract (stop old writes and drop the old shape), keeping every step compatible with the code before and after it.

?? 1) Add the new column as nullable with no default (a fast change, with a lock timeout). 2) Deploy code that writes both the old and new columns on every insert and update but still reads the old one (or add a trigger that copies writes). 3) Backfill existing rows into the new column in small, throttled, resumable batches. 4) Deploy code that reads the new column while still writing both, and verify by comparing the two. 5) Deploy code that stops writing the old column. 6) After a waiting period with no remaining readers, drop the old column. Each step works with the code versions running before and after it, and every step except the final drop can be rolled back.

@03.13
## The appeal
**Soft deletion** means never running `DELETE`. Instead you add a column such as `deleted_at timestamptz` and "delete" a row by setting it: `UPDATE projects SET deleted_at = now() WHERE id = 42`. Rows with a timestamp are treated as gone. Undeleting is setting it back to null. A **hard delete**, by contrast, removes the row with a real `DELETE`.

The appeal is easy to see:
- A hard delete is permanent. One bad query or one mistaken click and the data is gone.
- Support staff and engineers can look at deleted data when investigating a bug or a customer complaint.
- An "undo" or a trash bin looks almost free to build.

Soft deletion is common, and frameworks make it a one-line setting. But the costs are spread thinly across the whole codebase and the whole lifetime of the data, and they usually outweigh the benefits. This lesson goes through what breaks and what to do instead.

%%state The life of a soft-deleted row. The restore path is rarely used, and the purge step is where the hidden cost appears.
[*] -> Active : INSERT
Active -> Soft deleted : set deleted_at
Soft deleted -> Active : restore, rarely used
Soft deleted -> *Purged : hard DELETE after retention
Purged -> [*] : gone, with its dependents
%%

## What goes wrong
### Every query must remember the filter
Every read needs `WHERE deleted_at IS NULL`. Every join needs it on **each** joined table. Miss it once, in a report, an admin tool, an analytics export, a background job or a hand-written query during an incident, and deleted data appears where it should not: a deleted user in a mention autocomplete, a cancelled order counted in revenue, a removed message shown in search.

ORM plugins and "default scopes" add the filter automatically, which helps in application code. But they do not help the analyst in a SQL console, the data pipeline that reads replicas directly, or raw SQL inside the application. And the filter is easy to forget on joins: `SELECT ... FROM orders JOIN customers ...` with the filter on `orders` but not `customers` shows live orders of deleted customers.

### Foreign keys stop protecting you
A foreign key checks that the parent **row exists**. A soft-deleted customer still exists as a row, so the database is perfectly happy for that customer's invoices, addresses and sessions to stay live underneath it. `ON DELETE CASCADE` never fires, because nothing was deleted. Nothing in the database enforces that children are soft-deleted when the parent is; every relationship needs application code, and every new table added later needs that code updated.

### Unique constraints break
A user deletes their account and later signs up again with the same email. The unique index on `email` rejects it, because the soft-deleted row still holds that email. The same applies to usernames, slugs, SKUs and any other unique business key.

%%seq Why re-signup fails with soft delete: the unique index still sees the soft-deleted row.
User > App : delete my account
App > users table : UPDATE SET deleted_at = now()
User > App : sign up again, same email
App > users table : INSERT email = ana@x.com
users table -> App : ERROR duplicate key on email
App -> User : email already taken
%%

The usual fix is a **partial unique index** that only covers live rows:
```
CREATE UNIQUE INDEX users_email_live ON users (email) WHERE deleted_at IS NULL;
```
Now any number of deleted rows can share an email, but only one live row can hold it. Every unique constraint on every soft-deletable table needs the same treatment, and some databases (MySQL among them) have no partial indexes, forcing workarounds such as a generated column that is null for deleted rows. Restoring a deleted row can now fail too, if someone else has taken its email in the meantime.

### Tables and indexes fill with dead data
Soft-deleted rows stay in the table and in every index. If 30% of rows are deleted, scans read 30% more data, indexes are 30% bigger, and the buffer pool caches rows nobody will ever see. Every index used by normal queries should become partial (`WHERE deleted_at IS NULL`) too, which is easy to forget.

### You still have to hard-delete eventually
Privacy law changes the picture. Under GDPR, a user's right to erasure means "deleted" must eventually mean gone, and keeping personal data forever without a reason is itself a problem. So soft delete does not remove the need for a hard-delete path; it just delays it and makes it harder.

Purging a soft-deleted row means hard-deleting its dependents first, in the right order, across every table that references it. One real-world purge query touched about 30 tables and broke whenever someone added a new table with a reference that the purge did not know about.

%%tree What purging one soft-deleted customer actually requires: every dependent table, in order, deepest first.
customer 42 | soft deleted 40 days ago
  orders | 120 rows
    order_items | 900 rows
    payments | 118 rows
      refunds | 3 rows
    shipments | 115 rows
  addresses | 4 rows
  sessions | 2,000 rows
  *new_feature_table | added last month, purge script unaware
%%

### Undelete rarely works anyway
Deleting usually has **side effects outside the database**: files removed from object storage, a subscription cancelled at the payment provider, a search index updated, emails sent, a virtual machine shut down, an access token revoked. Flipping `deleted_at` back to null undoes none of those. A "restored" project whose files are gone is worse than a deleted one. In practice, teams that build soft delete for undo find it is almost never used, and when it is, it needs manual work anyway.

## The alternative: an archive table
Delete rows for real, but **copy them into an archive** first. A single generic table works for every table in the schema:
```
CREATE TABLE deleted_record (
  id             bigserial PRIMARY KEY,
  deleted_at     timestamptz NOT NULL DEFAULT now(),
  original_table text NOT NULL,
  original_id    text NOT NULL,
  data           jsonb NOT NULL
);
```
In Postgres one statement can do both the delete and the copy, using a data-modifying common table expression:
```
WITH gone AS (DELETE FROM projects WHERE id = 42 RETURNING *)
INSERT INTO deleted_record (original_table, original_id, data)
SELECT 'projects', id::text, to_jsonb(gone) FROM gone;
```
A trigger on each table can do the same automatically, so no code path can forget.

%%compare Soft delete flags rows in place; an archive table deletes for real and keeps a JSON copy elsewhere.
[Soft delete column]
DELETE becomes UPDATE -> Row stays in live table -> Every query filters
- Filters leak when forgotten
- Foreign keys and unique keys break
- Purge spans many tables
+ One-step restore, in theory
[*Archive table]
DELETE copies row -> JSON in deleted_record -> Live table only has live rows
+ Queries need no filter
+ Constraints work as designed
+ Purge is one DELETE on one table
- Restore is manual
%%

The benefits are broad. Normal queries need no filter. Foreign keys work again: deleting a parent that still has children is an error, as it should be, or cascades as designed. Unique constraints need no partial indexes. Live tables and indexes contain only live data. And purging old archived data is one statement on one table: `DELETE FROM deleted_record WHERE deleted_at < now() - interval '90 days'`.

The cost: restoring means reading JSON and re-inserting it by hand or with a small tool, and the archived JSON does not follow later schema changes. That is acceptable because restores are rare, and the archived copy is still there for investigations.

Other alternatives exist for specific needs: **audit or history tables** that record every change (not just deletes), **event sourcing** where state is rebuilt from an append-only log of events, and simply relying on **backups and point-in-time recovery** (lesson 03.08) for the rare "we deleted the wrong thing" disaster.

%%matrix Ways to keep deleted data, compared on what matters day to day.
Approach | Queries need filter | Constraints work | Easy purge | Easy restore
Soft delete column | yes, everywhere | no | no | yes, in theory
Archive table | no | yes | yes | partial, manual
History or audit table | no | yes | yes | partial
Backups and PITR only | no | yes | yes | no, slow and coarse
%%

## When soft delete is still reasonable
- A real product feature such as a **trash bin with restore** (documents, emails, files), where the business wants it, users expect it, and the side effects are reversible or deferred until the trash is emptied.
- Small, simple tables where the filter is applied in exactly one place, such as a view or a single repository class, and nothing reads the table any other way.

Even then: use partial unique indexes, put the filter in a view (`CREATE VIEW live_users AS SELECT * FROM users WHERE deleted_at IS NULL`) that all reads use, make normal indexes partial, and run a scheduled purge that hard-deletes rows after a retention period.

! Example: fixing a users table that already uses soft delete
! Problem 1: `UNIQUE (email)` blocks re-signup. Fix: `CREATE UNIQUE INDEX CONCURRENTLY users_email_live ON users (email) WHERE deleted_at IS NULL`, then drop the old constraint.
! Problem 2: `SELECT count(*) FROM users` on the growth dashboard includes 3.1 million deleted users out of 12 million, overstating users by 35%. Fix: a `live_users` view, and a rule that dashboards and code read only from it.
! Problem 3: GDPR erasure requests. Fix: a nightly job that hard-deletes users soft-deleted more than 30 days ago, after deleting their dependents in 14 tables. The job runs in batches of 1,000 users so it never holds long locks, and a test fails if a new table references `users` without being added to the job.

! Example: the cost in storage and speed
! A comments table has 500 million rows, and over 4 years 40% have been soft-deleted. Each row with index entries is about 400 bytes.
! Dead weight: 200 million rows × 400 bytes = 80 GB, in a table of 200 GB. The hot indexes are 40% larger than they need to be, so less of them fits in the 64 GB buffer pool and the cache hit rate drops.
! Switching to an archive table moves those 80 GB to a cold, rarely read table (or out to object storage after 90 days, lesson 04.14). Live indexes shrink by 40%, and the most common queries go back to being served entirely from RAM.

## Common mistakes
- **Forgetting the filter on joins**, so live rows of deleted parents leak out.
- **Keeping a plain unique constraint** on a soft-deletable column.
- **Assuming restore undoes everything**, when files, payments and messages are already gone.
- **Never purging**, which collides with privacy law and lets tables grow forever.
- **Adding soft delete by default** on every table because a framework makes it easy.

## In an interview
If your design involves deleting data, say how: hard delete with an archive or audit trail for most tables, a trash feature only where the product needs one, and a retention policy for purging. Mention the unique constraint and filtering problems if soft delete comes up; it shows you have lived with the consequences.

> Takeaway: soft delete looks safe but leaks deleted data into any query that forgets the filter, breaks unique constraints and foreign keys, bloats tables and indexes, and makes the eventual hard delete harder. Prefer real deletes plus an archive table, and use soft delete only for a genuine trash feature, with partial indexes and a scheduled purge.

?? Unique constraints still see soft-deleted rows, so a deleted user's email or username cannot be reused (re-signup fails with a duplicate key) unless every unique constraint becomes a partial unique index WHERE deleted_at IS NULL, and restoring a row can then fail if someone else took the value. Every query and every join must remember WHERE deleted_at IS NULL, or deleted data leaks into results, counts and reports. Foreign keys no longer protect you: live children can point at a soft-deleted parent and ON DELETE CASCADE never fires. Tables and indexes fill with dead rows unless indexes are made partial, and the eventual hard purge must walk every dependent table in order.
