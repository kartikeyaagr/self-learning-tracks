@10.01
## Why counting gets hard
Counting looks like the easiest thing a computer can do: `UPDATE videos SET views = views + 1 WHERE id = 42`. At small scale it is. A blog with a few hundred readers a day can run that statement on every page view for years and never notice. The trouble starts when one number is incremented by a huge number of people at the same moment.

Consider a video platform with 70 billion views a day. That is about **700,000 increments per second** (70 billion divided by roughly 100,000 seconds in a day; a day is really 86,400 seconds, so rounding up to 100,000 makes the arithmetic easy but gives a slightly low answer: the true average is about 810,000, and peaks are higher still). A well-tuned relational database node handles on the order of 10,000 durable writes per second. A design where every view becomes its own database write misses by almost two orders of magnitude.

But this lesson's question is narrower and more surprising: why does even 50,000 increments per second on **one row** fall over, when the same database might happily take 50,000 writes per second spread across many rows? The answer is that a single row is a single point of serialisation, and nothing you add to the machine makes a single point faster.

## What happens inside one UPDATE
Walk through what a relational database such as PostgreSQL or MySQL (InnoDB) does for one `views = views + 1`:
1. **Find the row.** Look up id 42 in the primary-key B-tree. This is fast: the page is almost certainly in memory because it is so hot.
2. **Take an exclusive row lock.** No other transaction may modify this row until this one commits or aborts. This is what stops two increments from both reading 1,000 and both writing 1,001.
3. **Write the new version.** PostgreSQL writes a whole new copy of the row (MVCC, multi-version concurrency control: old readers keep seeing the old version). InnoDB updates in place but writes an undo record so readers can reconstruct the old version.
4. **Append a log record.** The change is recorded in the write-ahead log (WAL), the append-only file that makes the change durable.
5. **Commit.** Wait until the WAL record is flushed to disk with `fsync`, so a power cut cannot lose an acknowledged write.
6. **Release the lock.** Only now can the next transaction waiting on row 42 proceed.

The lock is held from step 2 until step 6. That window includes a disk flush, which on a good SSD takes perhaps 0.1 to 1 ms, and on network-attached cloud storage often 1 to 3 ms.

%%seq Two writers on the same row: the second one waits for the first one's whole commit, including the disk flush.
Writer A > Database : UPDATE views + 1 (row 42)
Database > Database : lock row 42 for A
Writer B > Database : UPDATE views + 1 (row 42)
Database > Database : B waits for lock
Database > Database : A: write WAL, fsync (1 ms)
Database -> Writer A : commit ok, release lock
Database > Database : lock row 42 for B
Database > Database : B: write WAL, fsync (1 ms)
Database -> Writer B : commit ok
%%

## The arithmetic of a hot row
If every increment holds the lock for 1 ms, the row can complete at most **1,000 increments per second**, regardless of how many CPU cores the server has. Cores don't help because the work cannot run in parallel: increment number 2 must see the result of increment number 1.

**Group commit** improves this. When many transactions are waiting to flush the WAL, the database flushes all their log records in one `fsync`. That amortises the disk cost across many commits, but it does not remove the lock: transactions on the same row still take turns, so each one must wait for the previous holder to commit before it can even write its log record. In practice a single hot row in a well-tuned database tops out somewhere between a few hundred and a few thousand updates per second. Fifty thousand is out of reach by a factor of 10 to 100.

The failure is not graceful either. At 50,000 arriving per second and 2,000 completing per second, the queue of waiting transactions grows by 48,000 every second. Each waiting transaction holds a connection from the pool. Within a second or two, the pool is exhausted, unrelated queries cannot get a connection, timeouts fire, clients retry (adding even more load), and the whole database looks down even though only one row is hot.

### The other costs stacked on top
- **MVCC garbage.** In PostgreSQL every update leaves a dead row version behind. 50,000 updates per second on one row means 50,000 dead tuples per second for VACUUM to clean. Until it does, the table and its indexes bloat, and every reader has to skip past dead versions.
- **Replication.** Each update produces a log record that every replica must apply in order. A single-threaded replay on the replica becomes another bottleneck, and replicas fall behind.
- **No way to shard one row.** Partitioning (sharding) spreads different keys across machines. A single key always lands on one machine, so adding machines does nothing for one hot counter.
- **Deadlocks and retries.** If the same transaction also touches other rows (a user row, a daily stats row), lock ordering problems appear, and aborted transactions retry, which adds load at the worst moment.

%%bars Rough ceilings on increments per second for one logical counter, by technique. Exact figures vary with hardware; the orders of magnitude are what matter.
One SQL row, fsync each commit | 1000 | about 1k/s
One SQL row, group commit | 3000 | a few k/s
Redis INCR, one key | 100000 | about 100k/s
16 sharded SQL rows | 30000 | about 30k/s
*Batched in a stream consumer | 10000000 | millions/s of events
%%

## Fix 1: count in memory with Redis INCR
`INCR key` increments the integer stored at a key by one and returns the new value. If the key doesn't exist it starts at 0. It is **O(1)**, works on 64-bit signed integers, and because Redis executes commands one at a time on a single thread, concurrent increments never lose updates: there is no read-modify-write race to protect against, so no lock is needed. With no disk wait per increment, one Redis node can absorb on the order of **100,000 simple commands per second per core**, and more with pipelining (sending many commands without waiting for each reply). `INCRBY key n` adds n in one step, which matters for batching.

The catch is durability. Redis is memory-first. If the counter must survive a crash exactly, you need the append-only file (AOF) with `appendfsync always`, which brings back a disk flush per write and much of the cost you were escaping. The common middle ground is `appendfsync everysec` (lose up to a second of increments on a crash) or a periodic job that copies counters to a database. A single hot key also still lives on one Redis node, so the 100,000 per second ceiling is real for one key.

## Fix 2: split the counter
A **sharded counter** stores N sub-counters for one logical counter, for example `views:42:0` to `views:42:15`. Each write picks a random sub-counter and increments only that one. A read sums all N.

%%flow A sharded counter: writes pick a random slot, so 16 writers rarely collide; reads add up all 16 slots.
[Write] View event -(random slot 0..15)-> *views:42:7 += 1
[Read] Read count -(sum 16 slots)-> views:42 = total
%%

With 16 sub-counters, the lock contention on each row drops by 16 times, so a database that managed 2,000 increments per second on one row can now manage roughly 30,000 on one logical counter. The sub-counters can even live on different shards or Redis nodes. Reads cost N lookups, which is fine when reads are rarer than writes or are served from a short-lived cache ("refresh the displayed total every 5 seconds").

Choosing N is a trade-off. Too few and the hottest counter still contends; too many and every read gets slow and every counter costs N times the storage, even for the millions of cold counters that see one view a day. A common refinement is **adaptive sharding**: start every counter with one slot and split it only when it gets hot.

## Fix 3: batch before writing
The biggest win is to stop doing one write per event. Instead of telling the database about each view, tell it about the total for the last few seconds. Put view events onto **Kafka, partitioned by video ID**, so all events for video 42 go to one partition and therefore one consumer. That consumer (or a stream processor such as Flink) keeps a hash map of `video_id → pending count` in memory and every few seconds flushes one write per video, such as `views = views + 3,812`.

%%flow Batching: Kafka partitions by video, a consumer sums in memory, and the database sees one write per video per flush.
View events -(partition by video id)-> Kafka -> *Consumer sums per video for 5 s -(views += 3,812)-> Counter DB, sharded by video
%%

Batching reduces write volume by roughly **2 to 100 times** in general, and far more for hot keys: a viral video's 40,000 views per second become one write every 5 seconds, a reduction of 200,000 times. This is why batching is also the answer to hot keys. Sharding the counter database by video ID (about 70 shards to bring 700,000 writes per second down to about 10,000 per instance) handles the remaining volume of cold and warm videos.

The trade-off is freshness: counts lag by the flush interval. Crash safety comes from Kafka. The consumer commits its Kafka offset only after the batch has been written. If it crashes before flushing, it restarts from the last committed offset and recounts those events. If it crashes after writing but before committing the offset, it will count those events twice when it restarts. Lesson 10.03 shows how to make that exactly right where it matters (ads); for a view count, a tiny overcount after a rare crash is usually acceptable.

! Example: a viral video, three designs
! Video 42 gets 40,000 views per second at peak.
! Direct writes: 40,000 lock acquisitions per second on one row. With about 1 ms per commit, the row completes about 1,000 per second, the backlog grows by 39,000 per second, the connection pool of 200 is exhausted in well under a second, and other pages that need the database start timing out.
! Sharded counter with 16 slots: about 2,500 increments per second per slot. Each slot still needs a commit per increment, so this is at the limit of what the database can do, and every page view of the count now costs 16 reads.
! Batching: the Kafka partition for video 42 feeds one consumer, which adds to an in-memory counter and every 5 seconds runs `UPDATE videos SET views = views + 200000 WHERE id = 42`. That is one write per 5 seconds. The displayed count is up to 5 seconds stale, which nobody notices.

! Example: sizing the whole platform
! 700,000 view events per second across all videos, so 3.5 million events in each 5-second window. Views follow a power law: the top few thousand videos absorb a large share of them, and most other videos get a single view. Suppose those 3.5 million events land on 1.5 million distinct videos. With a 5-second flush, the consumers emit 1.5 million writes per 5 seconds, about 300,000 per second: only a 2 to 3 times reduction overall, but a 100,000 times reduction on the hottest rows, which were the ones that broke. Spread over 70 database shards, that is about 4,000 writes per second each, which is comfortable. Lengthening the flush to 30 seconds for cold videos cuts it further.

## Picking a technique
| Situation | Use |
| Low rate, must be exact and transactional with other data | Plain SQL update |
| Medium rate, must be readable instantly | Redis INCR, with periodic copy to a database |
| One key gets very hot, reads are rare | Sharded counter |
| Very high total rate, seconds of staleness fine | Stream batching into sharded storage |
| Huge scale, distinct users rather than raw events | HyperLogLog (lessons 10.02 and 10.04) |

Real systems combine them: Kafka batching for durability and volume, Redis for the "live" number shown on screen, and a periodic reconciliation job that recounts from raw events (lesson 10.07).

## Common mistakes
- **Reaching for a bigger database.** More cores, more RAM and read replicas do nothing for one row's lock. The fix is structural, not hardware.
- **SELECT then UPDATE in application code.** Reading the count, adding one in your code and writing it back loses updates under concurrency (two readers both see 1,000 and both write 1,001). Always increment atomically in the store (`SET views = views + 1`, `INCR`).
- **Retrying blindly.** When the hot row times out, client retries multiply the load. Retries need backoff, and counters usually need to drop or batch rather than retry.
- **Forgetting the read side.** A sharded counter with 64 slots read on every page view moves the problem from writes to reads. Cache the summed value.
- **Assuming the batch is exactly-once.** A crash between "write batch" and "commit offset" double-counts. Decide whether that matters before you choose the design.

## In an interview
When a design includes "count likes", "count views" or "count clicks", say early that you will not write to a database per event. State the rate ("at peak 50,000 per second on a single viral item"), name the bottleneck ("a single row serialises on its lock and its commit"), and propose batching through a partitioned log, with sharded counters or Redis for the hottest keys. Then ask the question that decides the rest: "How exact and how fresh does this number need to be?" A like count can be 5 seconds stale and slightly off; an account balance cannot.

> Takeaway: one counter row serialises every increment on a single lock and a durable commit, so it tops out at a few thousand per second however big the server is. Count in memory (Redis INCR), split hot counters into sub-counters, and above all batch increments in a stream consumer so the database sees one write per key per interval.

@10.02
## The product decision behind a number
Reddit shows a view count on every post. That sounds like a counter problem (lesson 10.01), but it is a harder one, because Reddit wanted to count **people**, not page loads. When Reddit designed its view-counting system it set four requirements:
1. Counts must be **real time** or near real time, not daily or hourly batches. A post that goes viral should show its count climbing.
2. **Each user is counted once** within a short time window, so refreshing doesn't inflate views.
3. The displayed count must be **within a few percent** of the actual tally.
4. The system must run at production scale and process events within seconds.

Requirement 2 is what makes it hard. A simple counter can't tell a new viewer from a returning one. To know whether user u7 has already been counted for post p1, you must remember who has viewed p1. Remembering is where memory goes.

The interesting part of this lesson is requirement 3. Reddit decided, up front, that an answer within a few percent was good enough. That one product decision made an expensive problem cheap, and learning to spot when you are allowed to make it is one of the most useful habits in system design.

## Two different counts
It helps to name things precisely:
- **Total views (events)**: every page load. This is a plain counter, the problem of lesson 10.01.
- **Unique viewers (cardinality)**: the number of distinct users who loaded the page. "Cardinality" is the size of a set, so this is a count-distinct problem.

A total-views counter needs 8 bytes per post however many views it has. A unique-viewer count, done exactly, needs memory proportional to the answer.

## Why exact counts were rejected
An exact unique count needs the set of user IDs that viewed each post, checked on every view ("is u7 already in the set?") and added to if not. At Reddit, popular posts have over a million unique viewers. At 8 bytes per user ID, **1 million IDs take 8 MB for a single post**, and that is the raw data before the overhead of a hash set, which in practice doubles or triples it. Multiply by thousands of posts that are active at the same time and add the CPU cost of a set lookup on every view, and Reddit found it "extremely taxing" on both memory and CPU.

There were exact alternatives, and each has a flaw:
- **A database table of (post, user) pairs with a unique constraint.** Every view becomes an insert that may fail on a duplicate. That is a write per view into a table of billions of rows, with an index lookup each time.
- **A batch job over the logs.** Run a nightly `COUNT(DISTINCT user_id) GROUP BY post_id`. It is exact and cheap per row, but it breaks requirement 1: the number is a day old.
- **A Redis set per post.** `SADD p1 u7` then `SCARD p1`. Fast, but it is the 8 MB-per-post problem in RAM.

**HyperLogLog** (lesson 10.04 explains the mechanism) estimates the number of distinct items using a fixed, small amount of memory. Reddit uses Redis's implementation, which counts over a million IDs in **12 KB**, about 0.15% of the exact set's 8 MB. The price is a small error: Redis's standard error is **0.81%**, comfortably inside the "few percent" requirement.

%%bars Memory to track the unique viewers of one post with a million viewers. The exact set grows with the audience; the HyperLogLog stays fixed.
Hash set of IDs, with overhead | 20000 | about 20 MB
Raw 8-byte IDs | 8000 | 8 MB
*Redis HyperLogLog | 12 | 12 KB
%%

## The pipeline
%%flow Reddit's view-counting pipeline: Nazar decides whether a view counts, Abacus adds it to a HyperLogLog in Redis, and Cassandra persists it.
View event -> Event collector -(batches)-> Kafka -> *Nazar: should it count? -(flagged event)-> Kafka -> Abacus -(PFADD)-> Redis HLL -(every 10 s)-> Cassandra
%%

Each stage has one job:
- **Event collector.** Browsers and apps fire a view event when a post is displayed. The collector is a thin, stateless HTTP service that batches events into Kafka. It does no thinking, so it can scale horizontally and stay fast.
- **Nazar** (a Kafka consumer) applies rules about whether a view should count, using Redis to keep state. For example, it ignores **repeat views from the same user within a short period**. It adds a boolean "count this" flag to the event and writes it back to Kafka. Keeping the decision in a separate stage means the rules can change (new abuse patterns, new definitions of a "view") without touching the counting code.
- **Abacus** (a second consumer) reads Nazar's output. For counted views it runs `PFADD` on that post's HLL in Redis. If a post's HLL isn't in Redis (typically an older post whose key was evicted to save memory), it loads the saved HLL from Cassandra into Redis first, then adds to it.
- **Cassandra** persists both the HLL and the count. Abacus writes them out in batches, **grouped per post every 10 seconds**, so even a post viewed thousands of times per second generates one Cassandra write per 10 seconds.

Notice how many ideas from lesson 10.01 reappear. Kafka is the durable buffer. Consumers keep state in memory. The database sees one batched write per key per interval. The only new idea is replacing an exact count with a sketch.

### Small posts are counted exactly
Reddit evaluated linear probabilistic counting against HLL and chose an HLL variant that uses a **sparse** representation for small sets and switches to the **dense** HLL as the set grows. Redis does exactly this. In sparse form, an HLL for a post with 40 viewers stores only the handful of registers that are non-zero, a few dozen bytes, and the estimate in that range is very close to exact. Once the sparse encoding grows past a threshold (about 3,000 bytes by default in Redis, set by `hll-sparse-max-bytes`), Redis converts it to the dense 12 KB form. Most posts never get there, so most posts cost far less than 12 KB.

## Walking a view through the system
%%seq One user refreshes a post: Nazar's time-window rule drops the second view before it reaches the HyperLogLog.
Browser > Collector : view(p1, u7) at 12:00:00
Collector > Kafka : append event
Kafka > Nazar : event
Nazar > Redis : seen u7 on p1 recently?
Redis -> Nazar : no, record it
Nazar > Kafka : event, count = true
Kafka > Abacus : event
Abacus > Redis : PFADD hll:p1 u7
Browser > Collector : view(p1, u7) at 12:00:20
Nazar > Redis : seen u7 on p1 recently?
Redis -> Nazar : yes, 20 s ago
Nazar > Kafka : event, count = false
%%

! Example: one user refreshing
! User u7 opens post p1 at 12:00:00 and refreshes at 12:00:20. Nazar sees the second event, finds in Redis that u7 viewed p1 20 seconds ago, and flags it "don't count". Abacus skips it.
! Even if it were counted, `PFADD hll:p1 u7` a second time would not change the HLL. An HLL counts distinct values: the same user ID always hashes to the same register and the same run of zeros, so it can never change the sketch twice. So why does Nazar bother? Because the time-window rule supports policies the HLL cannot express, such as "count a user again if they come back after 6 hours", "ignore views from known bots", or "ignore views shorter than a second". Nazar is where the definition of a view lives; the HLL only counts.

! Example: sizing Redis for active posts
! Suppose 100,000 posts are "active" (viewed in the last day) at any time. A power-law split: 2,000 have enough unique viewers (a few thousand or more) to have outgrown the sparse encoding and use the dense 12 KB form, and 98,000 stay sparse at an average of perhaps 500 bytes.
! Dense: 2,000 × 12 KB = 24 MB. Sparse: 98,000 × 0.5 KB = 49 MB. Total: about 73 MB, which fits in one small Redis instance with room to spare.
! Exact sets for the same posts: the 2,000 big posts average, say, 200,000 viewers each, which is 2,000 × 200,000 × 8 bytes = 3.2 GB of raw IDs, plus hash-set overhead, so 8 GB or more. Older posts are evicted from Redis and reloaded from Cassandra on demand, which also only works cheaply because each one is at most 12 KB to fetch.

## Why approximate was acceptable
The answer to this lesson's question is product judgement, not cleverness. A view count is a signal of popularity shown to users. It is not money, it is not a contract, and it does not drive decisions that need exactness. Nobody can tell 1,004,213 views from 1,012,000, and the displayed number is usually rounded ("1.0M") anyway. Being within about 1% while using about 0.15% of the memory and staying real time beat exact counts that would have needed huge memory or slow batch jobs.

%%compare Exact versus approximate unique counting for a social view counter.
[Exact set per post]
Memory grows with viewers
+ Precise to the last user
- 8 MB or more per popular post
- Set lookup CPU on every view
- Or a day-old batch job instead
[*HyperLogLog per post]
Fixed 12 KB, sparse when small
+ Real time, cheap per view
+ Mergeable across servers and days
- About 0.81% standard error
- Cannot list who viewed
%%

Contrast this with ad billing (lesson 10.03), where every click is money paid by an advertiser and approximations are not acceptable. The same company may use HLL for the view counter on a post and exact, deduplicated, audited counting for the ads shown next to it. The rule is: **the cost of being wrong decides the precision you pay for.**

### What you give up
Approximation has real limits, and you should say them out loud:
- **You cannot ask who.** An HLL can't tell you whether u7 viewed p1, or list the viewers. If the product later wants "people you know viewed this", you need a different structure.
- **Small errors at small counts are visible.** "3 views" showing as "4" looks like a bug to a user. Sparse encoding and linear counting keep small counts very accurate, which matters for this reason.
- **Errors do not shrink with time.** 0.81% of 10 million is about 81,000 views either way. For a display number that's fine; for a payout to creators it might not be.

## Common mistakes
- **Choosing approximate counting without asking.** Always confirm the accuracy requirement; "within a few percent" must come from the product owner, not be assumed by the engineer.
- **Using HLL for counts that are not distinct.** Total page loads are a plain counter. HLL is only for "how many different".
- **Putting the rules inside the counter.** Abuse filtering and "what counts as a view" change often. A separate stage (Nazar) keeps them out of the hot counting path.
- **Persisting every PFADD.** Write the sketch to durable storage in batches (every 10 seconds per post), not on every view.

## In an interview
If asked to design a view counter, ask two questions: "Do we count views or unique viewers?" and "How exact must it be?" If the answer is unique and approximate, propose a Kafka pipeline with a filtering stage, a Redis HyperLogLog per item, and periodic persistence. Quote the numbers: 12 KB per item, about 0.81% standard error, versus megabytes for an exact set. Then mention the boundary: if the count is ever used for billing or payouts, it moves to exact, deduplicated counting.

@10.03
## Why duplicates are the central problem
For a view counter (lesson 10.02), being 1% off is fine. For ads it is not, because counts are money. Advertisers pay per click (CPC) or per thousand impressions (CPM, cost per mille). An **impression** is one showing of an ad to one user; a **click** is that user clicking it. Over-counting overcharges advertisers, who will notice, demand refunds and stop trusting the platform. Under-counting loses revenue. Both are unacceptable, so the system must count each event **exactly once**.

Typical requirements for an ad click aggregator:
- **Idempotent click tracking**: never count the same click twice.
- **No data loss**: an acknowledged click is never dropped.
- A peak of **10,000 clicks per second** across 10 million active ads, about 100 million clicks per day.
- Advertisers can query clicks per ad at **minute granularity**, with results available within a minute or so.
- After a click is recorded, the user is redirected to the advertiser's site quickly (under about 100 ms of extra latency).

### Where duplicates come from
Networks and computers fail in ways that make "exactly once" hard. Duplicates come from three sources:
- **Client retries.** The browser or app sends the click, the server records it, but the response is lost (a mobile network drops, a load balancer times out). The client cannot tell "never arrived" from "arrived, reply lost", so it re-sends. This is the classic problem of at-least-once delivery.
- **Pipeline retries.** A consumer reads an event from Kafka, adds it to a count, then crashes before committing its offset (its bookmark in the log). After restart it reads the same event again and counts it twice.
- **Abuse.** Users or bots click the same ad repeatedly, or a competitor runs a click farm to drain an advertiser's budget. These are not technical duplicates, but they are duplicates for billing purposes.

The first two need **idempotency**: processing the same event twice has the same effect as processing it once. The third needs **policy**: rules about which clicks are billable.

## Give every impression an ID
You can only deduplicate if you can tell that two events are "the same". The trick is to define sameness at the source. The **ad placement service**, the component that decides which ad to show, generates a unique **impression ID** each time an ad is shown to a user (a 128-bit random value or a UUID). That ID travels with the ad to the client, and a click carries its impression ID. Now "the same click" has a precise definition: two clicks with the same impression ID. The impression ID is the **idempotency key** for everything downstream.

Why not let the client make the ID? Because a dishonest client could invent a fresh ID for every fake click, and each would look new. So the impression ID is **signed**: the placement service computes an HMAC (a keyed hash, such as HMAC-SHA256) over the impression ID and ad ID using a server-side secret, and sends the signature with the ad. The click processor recomputes the HMAC and rejects any click whose signature doesn't match. A client can replay a real impression ID, but it can't mint new ones, and replays are exactly what dedupe catches.

The same idea covers impressions themselves: the impression beacon (the small request the page sends when the ad becomes visible) also carries the signed impression ID, so a beacon fired twice counts once.

## Deduplicate on the way in
%%seq Dedupe at the click processor: verify the signature, check the impression ID in a cache, write to the stream first, then remember the ID.
Browser > Click processor : click(ad 9, imp 7f3, sig)
Click processor > Click processor : verify HMAC
Click processor > Redis : seen imp 7f3?
Redis -> Click processor : no
Click processor > Kafka : append click event
Kafka -> Click processor : ack (replicated)
Click processor > Redis : SET imp 7f3 NX EX 86400
Click processor -> Browser : 302 to advertiser
%%

The order of the last steps matters. The processor writes to the stream **first** and records the ID in the dedupe cache **second**. Think about a crash between the two:
- **Stream first, then mark** (the right order): the event is in Kafka but the ID is not in Redis. A retry would pass the dedupe check and produce a second event. That is a duplicate, which the downstream layers (below) are built to catch. Nothing is lost.
- **Mark first, then stream** (the wrong order): the ID is in Redis but the event never reached Kafka. A retry is rejected as a duplicate. The click is silently lost forever, and nothing downstream can recover it.

When forced to choose between a possible duplicate and a possible loss, choose the duplicate, because duplicates can be removed later and losses cannot.

Use a distributed cache such as a Redis cluster for seen IDs, with a TTL (time to live) long enough to cover realistic retry windows, often 24 hours. `SET key value NX` sets the key only if it does not exist, which also handles two simultaneous retries racing each other: one wins and the other sees the key.

! Example: sizing the dedupe cache
! 100 million clicks per day, each impression ID 16 bytes. With key overhead in Redis, budget about 80 bytes per entry. A 24-hour TTL keeps at most a day's clicks: 100 million × 80 bytes = 8 GB. That fits across a small Redis cluster (say 4 nodes of 4 GB each, with replicas). At 10,000 clicks per second peak, that's 10,000 `GET`s and 10,000 `SET`s per second, trivial for Redis.
! If you deduplicated impressions too (often 100 times more numerous than clicks), the cache would need 800 GB. That's why impression dedupe is often done with a Bloom filter per time window, or left to the stream processor's keyed state, rather than with one Redis entry per impression.

## Exactly-once inside the pipeline
The stream processor (Flink) counts clicks per ad per minute. A crash in the middle could double-count events that were counted but whose progress wasn't saved. Flink handles this with **checkpoints**: periodically (say every 10 seconds) it snapshots both its state (the partial counts in each open window) and the Kafka offsets it has consumed, together, as one consistent picture. After a crash it restores the state and rewinds Kafka to the offsets in that same snapshot. Events after the checkpoint are replayed, but they are being added to state that does not yet include them, so nothing counts twice inside Flink.

That guarantee ends at Flink's edge. When a window closes, Flink writes the result to the analytics store, and a crash after writing but before the next checkpoint will cause the write to happen again after recovery. So writes must be **idempotent**: write "ad 9, minute 12:03 = 418" as an upsert keyed by (ad, minute), rather than "add 418 to ad 9". Writing the same result twice leaves the same row. An increment written twice would double the count.

%%flow End-to-end: one ID per impression, dedupe on ingest, checkpointed aggregation, idempotent upserts, and raw events kept for a batch job that reconciles.
[Real time] Signed impression ID -> *Dedupe cache -(new clicks only)-> Kafka -(Flink, checkpointed)-> Upsert ad, minute -> OLAP store
[Safety net] Kafka -(all raw events)-> S3 data lake -(daily Spark job)-> *Dedupe by impression ID -> Corrections
%%

### Dedupe inside the stream as well
The Redis check at the edge is best effort: if Redis is briefly unavailable, the processor should still accept clicks (losing clicks is worse) and let duplicates through. So a second dedupe layer runs inside Flink: key the stream by impression ID and keep a small piece of state per ID ("seen", with a timer to expire it after a day). The first event for an ID passes; later ones are dropped. Because this state is checkpointed with the offsets, it is exactly-once even across crashes.

## Reconcile with raw data
Add a final safety net: Kafka also dumps all raw click events to a data lake (S3, in a columnar format such as Parquet), and a **daily batch job** (for example in Spark) recomputes the aggregates from the raw events, deduplicating by impression ID and applying the latest fraud rules, then compares them with what the streaming path produced. Differences are corrected in the store, and the corrected numbers are what invoices use. This is the "batch layer checks the speed layer" idea from lesson 10.07: the fast path gives answers in seconds, the slow path makes them right.

%%matrix Which layer catches which kind of duplicate or bad click. No single layer is enough; together they cover every case.
Duplicate source | Signed ID | Edge cache | Flink keyed state | Daily batch
Client retry | partial, defines sameness | yes | yes | yes
Retry while Redis down | partial | no | yes | yes
Consumer crash and replay | no | no | yes, via checkpoints | yes
Write retried after crash | no | no | no, needs upsert | yes
Forged click IDs | yes | no | no | no
Bot or click farm | no | no | partial, simple rules | yes, new rules
%%

### Hot ads
A hugely popular ad (a Super Bowl campaign) can get thousands of clicks per second, all landing on one Kafka partition if you partition by ad ID, and that one partition's consumer becomes the bottleneck. The fix is a **salted key**: the partition key becomes `adId:N` with a random suffix N from 0 to 9. The ad's events now spread over 10 partitions, each worker counts its share, and a later step strips the suffix and sums the partial counts for the ad. Note that impression-ID dedupe still works if you key the dedupe step by impression ID before the salting step.

The browser retries three seconds later. The processor verifies the signature, finds 7f3 in Redis and redirects without writing a second event.
! Now replay the same story with Redis unavailable at both clicks. The processor accepts both, so Kafka holds two events for 7f3. Flink's keyed state sees 7f3 twice and drops the second. Three independent layers had to fail before the advertiser was overcharged by one click.

## Common mistakes
- **Using a client-generated ID unsigned.** It deduplicates honest retries and nothing else; attackers just send new IDs.
- **Marking seen before writing the event.** This turns a crash into a lost click.
- **Writing increments to the result store.** Any retry of the write double-counts. Write absolute values keyed by (entity, time bucket).
- **Calling Kafka "exactly-once" and stopping.** Exactly-once is a property of a whole pipeline, from source ID to final write, not of one component.
- **No raw data.** Without raw events there is no audit trail when an advertiser disputes a bill, and no way to apply a fraud rule retroactively.

A good question to ask: "Is the real-time number used for billing, or only for dashboards, with invoices from the reconciled batch?" The answer tells you how much of the exactness burden the streaming path carries.

## The problem: count distinct without remembering
"How many distinct users visited today?" An exact answer needs a set of every user seen so far, because each new event must be checked against it: is this user new? The set grows with the answer. A billion users need gigabytes, per day, per site, per metric. If you want unique users per country per device per hour, you multiply that by thousands.

**HyperLogLog** (HLL) answers within about 1% using a fixed 12 KB, however large the count. It sees each item once, never stores the items, and can be merged across machines (lesson 10.05). It is one of the most widely deployed probabilistic data structures: Redis, PostgreSQL extensions, BigQuery's `APPROX_COUNT_DISTINCT`, Druid, Presto and Spark all ship it. To trust it, you should understand why it works.

## The coin-flip intuition
Start with coins. Flip a coin repeatedly and note your longest run of heads in a row. If someone tells you their longest run was 3, they probably didn't flip many times. If it was 13, they must have flipped a lot, because a particular run of 13 heads has probability 1 in 8,192. The longest run is a rough clock of how many flips happened, even though nobody wrote the flips down.

HLL applies this to hashes. A good hash function (such as MurmurHash or xxHash, 64 bits) turns any item into a bit string that looks uniformly random: each bit is 0 or 1 with probability one half, independently. Look at the number of **leading zeros**, the zeros before the first 1:
- Half of all hashes start with `1` (0 leading zeros).
- A quarter start with `01` (1 leading zero).
- One in 8 start with `001`.
- In general, one in 2ᵏ⁺¹ start with exactly k zeros followed by a 1.

%%bars How likely a random hash is to start with at least k zeros. Each extra zero halves the chance, so a long run is evidence of many distinct hashes.
At least 1 zero | 50 | 1 in 2
At least 3 zeros | 12.5 | 1 in 8
At least 6 zeros | 1.5625 | 1 in 64
At least 10 zeros | 0.0977 | 1 in 1,024
*At least 20 zeros | 0.0000954 | 1 in 1,048,576
%%

So if the longest run of leading zeros you have seen is r, you have probably seen around 2ʳ **distinct** items. Why distinct? Because the same item always hashes to the same bit string. Seeing user:812 a million times produces one hash a million times, and a repeat can never extend the maximum. The structure is blind to duplicates by construction, which is exactly what count-distinct needs.

! Example: how likely is a long run?
! Suppose you hash 1,000 distinct items. The chance that a given hash has at least 10 leading zeros is 1/1,024. The chance that none of the 1,000 do is (1 − 1/1,024)^1,000 ≈ e^(−0.98) ≈ 0.38. So with 62% probability you will have seen a run of 10 or more, and 2¹⁰ = 1,024 is a decent guess of 1,000.
! The same calculation shows the weakness. The chance of at least one run of 13 or more among 1,000 hashes is about 1 − e^(−1000/8192) ≈ 11%. One time in nine, a single estimator would say "8,000" when the truth is 1,000. One maximum is far too noisy to use alone.

## Registers: many small experiments
The fix is to run many experiments and average them, like flipping many coins in parallel. Hashing every item with many different hash functions would be slow, so HLL uses one hash and splits it into two parts:
- The first p bits choose one of m = 2ᵖ **registers** (buckets).
- The remaining bits are scanned for leading zeros. The register keeps the **maximum** value seen, where the value stored is the position of the first 1 bit (leading zeros plus one).

%%layers How Redis splits one 64-bit hash: 14 bits pick a register, and the run of zeros in the other 50 bits gives the value (Redis actually takes the low 14 bits and counts zeros from the other end, which works the same way).
Bits 1 to 14 | register index, 0 to 16,383
*Bits 15 to 64 | count leading zeros, store position of first 1
Register | 6 bits, keeps the maximum ever seen
%%

Each register sees about 1/m of the distinct items and estimates its own share. Because each item is routed by its hash, an item always goes to the same register, so duplicates still can't change anything.

%%flow Each item updates exactly one register: the first 14 bits pick register 9,301, and the rest of the hash has 5 leading zeros, so the register becomes at least 6.
Item user:812 -(64-bit hash)-> First 14 bits: register 9,301 -(rest: 5 leading zeros)-> *register 9,301 = max(old, 6)
%%

### Combining registers: the harmonic mean
Each register j holds a value M[j], which suggests that register saw about 2^M[j] items. You could average those, but an arithmetic mean is dominated by the one register that got lucky. HLL uses the **harmonic mean** instead, which is the reciprocal of the average of reciprocals, and is pulled towards the small values. The estimate is:

`E = α · m² / Σ 2^(−M[j])`

where the sum runs over all m registers and α is a constant (about 0.7213 for large m) that corrects a known bias. Intuitively, m / Σ 2^(−M[j]) is the harmonic mean of the per-register estimates, and multiplying by m again scales one register's share up to the whole.

! Example: why the harmonic mean, with four registers
! Registers hold 3, 3, 3 and 13 (the last one got a lucky hash). Per-register estimates: 8, 8, 8 and 8,192.
! Arithmetic mean: (8 + 8 + 8 + 8,192) / 4 = 2,054. One outlier has inflated the answer 250 times.
! Harmonic mean: 4 / (1/8 + 1/8 + 1/8 + 1/8,192) = 4 / 0.3751 ≈ 10.7. The outlier barely moves it.
! The full estimate multiplies by m and α: about 0.7 × 4 × 10.7 ≈ 30 distinct items in total. (Four registers are far too few for real use; this only shows how the mean behaves.)

The standard error of the estimate is **1.04 / √m**. Doubling accuracy costs four times the registers. With m = 16,384 the error is 0.81%; with m = 1,024 it is 3.25%; with m = 65,536 it is 0.41%.

%%matrix Register count against memory and error, using 6-bit registers. Redis uses the 16,384 row.
Registers (m) | Index bits (p) | Memory | Standard error
1,024 | 10 | 768 bytes | 3.25%
4,096 | 12 | 3 KB | 1.63%
16,384 | 14 | 12 KB | 0.81%
65,536 | 16 | 48 KB | 0.41%
%%

## Corrections at the edges
The raw formula is biased when the count is small compared with m. With 100 distinct items and 16,384 registers, almost every register is still 0, and the harmonic mean of mostly-empty registers is meaningless. For small counts, below about 2.5 × m (about 40,000 for Redis), the original algorithm switches to **linear counting**: if V registers are still zero, estimate the count as `m · ln(m / V)`. This is the same maths as "how many balls were thrown into m bins if V bins are still empty", and it is very accurate when most bins are empty.

! Example: linear counting
! 16,384 registers, and after a morning of traffic 15,900 are still zero. Estimate = 16,384 × ln(16,384 / 15,900) = 16,384 × ln(1.0304) ≈ 16,384 × 0.0300 ≈ 491 distinct items. Linear counting is used here because 491 is far below 2.5 × 16,384.

In the middle range there is still some bias, which early implementations (including early Redis versions) corrected with curves fitted to measurements. Since version 4.0, Redis uses an improved estimator, published in 2017, that works from the histogram of register values and is accurate across small, middle and large counts in one formula, with no switch between methods. At the top end, the original 32-bit algorithm had a correction for hash collisions near 2³² items; with 64-bit hashes that problem effectively disappears.

## Redis's implementation
The numbers for Redis (since 2.8.9):
- **16,384 registers** (14 bits of a 64-bit hash pick the register; 50 bits remain).
- Each register is **6 bits**, enough to store values up to 63, more than the 51 possible here.
- 16,384 × 6 bits = 12,288 bytes, so **12 KB** per dense HLL (12,304 bytes including a small header and an 8-byte cached result).
- Standard error **0.81%** (1.04 / √16,384).
- **Sparse encoding** for small sets: runs of zero registers are compressed, so an HLL with a few hundred items takes a few hundred bytes. It is converted to the dense form once it exceeds `hll-sparse-max-bytes` (3,000 bytes by default).
- Commands: `PFADD key item...` (returns 1 if any register changed), `PFCOUNT key` (estimate), and `PFMERGE dest src...`, which takes the **per-register maximum** across HLLs. `PFCOUNT` on several keys merges them on the fly.
- `PFCOUNT` caches its last result in the header and recomputes only if a register changed, so repeated reads are almost free.

The "PF" prefix honours Philippe Flajolet, who created the algorithm with Éric Fusy, Olivier Gandouet and Frédéric Meunier in 2007.

## HyperLogLog in practice
Google's improved version, **HyperLogLog++**, reduces memory and significantly improves accuracy for an important range of cardinalities, while still running in a single pass and parallelising perfectly. The main changes are a 64-bit hash, empirical bias correction tables for the middle range, and a sparse representation for small sets. Redis's design follows the same ideas.

! Example: daily unique visitors
! `PFADD uv:2026-11-09 user:1 user:2 user:1`: registers are updated for user:1 and user:2; the repeat of user:1 changes nothing. After 3 million visits by 1.2 million distinct users, `PFCOUNT uv:2026-11-09` returns about 1,190,000 to 1,210,000 (within one standard error, 0.81%, about two times in three; within 2.4% almost always). The key is 12 KB. A set of 1.2 million 8-byte IDs would be about 10 MB before overhead. For a weekly figure, `PFCOUNT uv:2026-11-03 ... uv:2026-11-09` merges seven days without double-counting anyone.

## Pitfalls
- **Bad hashes break the maths.** The whole argument assumes uniform random bits. A weak hash on structured IDs (sequential integers) can cluster in some registers. Use a well-mixed 64-bit hash; libraries do this for you.
- **Error is relative, not absolute.** 0.81% of 100 million is about 800,000. Fine for a dashboard, not for billing.
- **No deletes.** A register only remembers a maximum, so you can't remove an item. Use time-bucketed HLLs and stop including old buckets instead.
- **No membership.** HLL can't answer "has user 7 visited?". That's a Bloom filter's job.
- **Intersections are weak.** |A ∩ B| = |A| + |B| − |A ∪ B| works, but the errors of three estimates add up, so a small overlap can come out wildly wrong or even negative.

## In an interview
When you need distinct counts at scale (unique visitors, unique searchers, distinct IPs), say "HyperLogLog: 12 KB per counter, about 1% error, mergeable". If asked how it works, give the three-step version: hash each item; use the first bits to pick a register and record the longest run of leading zeros; combine registers with a harmonic mean, because a run of r zeros is a 1-in-2ʳ event and only shows up after about 2ʳ distinct items.

> Takeaway: HyperLogLog hashes each item and records, in each of m registers, the longest run of leading zeros; seeing a run of r zeros suggests about 2ʳ distinct items, and duplicates can never change the sketch. Combining many registers with a harmonic mean gives an error of 1.04/√m: in Redis, 0.81% with 16,384 registers in 12 KB, with linear counting and bias correction for small counts.

## Distinct counts don't add
Most numbers you aggregate are **additive**: the total revenue of 100 stores is the sum of their revenues, and the clicks in an hour are the sum of the clicks in its 60 minutes. That property is what makes big data tractable. Each machine computes a partial result over its slice, and a coordinator adds them up. Map-reduce, sharded databases and stream processors all lean on it.

Unique counts break it. If an app store had 3 million unique visitors and a music site 2 million, the combined total is not 5 million, because people who visited both are counted twice. The same holds across time: Monday's unique users plus Tuesday's unique users is not the two-day unique count, because most of Tuesday's users were also there on Monday. And it holds across machines: if 100 web servers each count their distinct users, adding the 100 numbers counts every user who hit more than one server more than once, and with a load balancer spreading requests randomly, that is nearly everyone.

To answer exactly, you must keep **a copy of every unique item** seen, in one place, so the overlap can be removed. A site with a billion users a day needs a billion records on hand. Quantile queries (lesson 10.11) are worse, needing every value seen, sorted. So exact distinct counting can't be parallelised by computing partial counts and adding them: the partial counts have thrown away the information needed to remove the overlap.

%%compare Two servers, 3 million and 2 million uniques, 1 million users on both. A number loses the overlap; a sketch keeps enough to remove it.
[Merge exact counts]
Server A: 3M -(add)-> 5M
Server B: 2M
- 1M users counted twice
- Overlap unknowable from two numbers
- Exact fix needs every user ID in one place
[*Merge sketches]
HLL A, HLL B -(register max)-> HLL of A or B
Estimate about 4M
+ Overlap removed automatically
+ Each sketch is 12 KB
- Answer within about 1%, not exact
%%

## What a sketch is
A **sketch** is a small data structure, usually kilobytes, built by a streaming algorithm that sees each item once and answers a query approximately with a mathematically proven error bound. HyperLogLog (lesson 10.04) is a sketch for distinct counts; count-min (10.08) for frequencies; t-digest (10.11) for quantiles; a reservoir sample (10.10) for sampling.

The property this lesson is about is **mergeability**. A sketch type is mergeable if there is an operation that takes the sketch of dataset A and the sketch of dataset B and produces the sketch of A ∪ B (or one with the same error guarantee), without access to the original data. Input can then be split into any number of fragments, each summarised by its own sketch, and the sketches combined quickly into a sketch of the whole. Mergeability turns a non-additive statistic into something you can compute the way you compute sums.

## Why HLL merges exactly
For HyperLogLog, the merge is simple: take the **maximum of each register** across sketches. Redis does this with `PFMERGE`.

Why is that correct? Each register j holds the maximum "first 1 position" over all hashes that were routed to it. The hash of an item depends only on the item, not on which server saw it. So user u7 hashes to the same register, with the same value, on every server that sees u7. The register for the combined data should hold the maximum over all items seen anywhere, and the maximum over a union is the maximum of the maxima. A user who appears on two servers sets the same register to the same value on both, so the max doesn't double-count them.

The merged sketch is therefore **identical**, bit for bit, to the sketch you would have built by streaming all the data through one HLL. No accuracy is lost by merging, however many times you do it, in whatever order. (Formally, max is associative, commutative and idempotent, so merges can be arranged in any tree and repeated safely.)

! Example: register-wise max with four registers
! Server A's sketch: [2, 0, 5, 1]. Server B's sketch: [3, 0, 1, 1]. User u7 hashes to register 0 with value 2 and was seen by both, so both sketches have at least 2 there.
! Merge: [max(2,3), max(0,0), max(5,1), max(1,1)] = [3, 0, 5, 1].
! If you had streamed all of A's and B's users through one sketch, register 0 would hold the largest value of any user routed there: that's 3 (from a user only B saw). Register 2 would hold 5 (from a user only A saw). The merged sketch matches exactly, and u7 contributed once.

That is why 100 servers' HLLs can be merged but their exact counts can't. The HLL still encodes, in compressed form, which hash values were seen. A plain number doesn't.

%%flow Merging sketches: each server sketches its own traffic, a coordinator takes the register-wise max, and the global sketch is queried once.
Server 1 HLL, Server 2 HLL, ... Server 100 HLL -(register-wise max)-> *Global HLL -(PFCOUNT)-> Global distinct count
%%

### How other sketches merge
Not every sketch merges by max, but the useful ones all merge somehow:
- **Count-min sketch** (10.08): add the two arrays cell by cell. It is a linear sketch, so the sum of sketches is the sketch of the combined stream.
- **Theta sketch**: keep the k smallest hash values seen (scaled into 0 to 1). Merging takes the k smallest of the union. The count is estimated from how densely the hashes are packed.
- **t-digest** (10.11): pool the centroids and re-cluster them under the size limits. Accuracy is preserved within the bound, though not bit for bit.
- **Reservoir sample with random tags** (10.10): keep the k items with the smallest random tags from the union.
- **Misra-Gries summary** (10.09): add counters key by key, then reduce back to k counters.

## What this enables
### Parallel processing
Each worker sketches its shard of data; a reducer merges. A Spark job computing distinct users over a petabyte of logs never shuffles user IDs across the cluster: each task emits one 12 KB sketch, and a final step merges a few thousand of them.

### Rollups over time
Store one sketch per minute or hour. To answer "unique users this week", merge 168 hourly sketches; to answer "last 30 days", merge 30 daily sketches. You compute any time range from stored pieces, never rereading raw data. Mobile analytics systems such as Flurry work this way: they store small per-minute sketches and merge them on demand, so a report over any range is a merge of stored pieces, and merging sketches is fast enough to do millions of them per second.

%%tree Time rollups from mergeable sketches: each level is built by merging the level below, and any range is answered by merging the fewest pieces that cover it.
Month sketch | merge of 30 days
  Day 1 sketch | merge of 24 hours
    Hour 00 sketch | merge of 60 minutes
      Minute sketches | built from raw events
    Hour 01 sketch
  Day 2 sketch
  *Day 30 sketch | still filling
%%

### Rollups over dimensions
Keep one sketch per (country, device, day) combination. "Unique users in France on any device yesterday" merges the French sketches for each device; "unique users on iOS worldwide" merges the iOS sketches for each country. With exact counts, every grouping you might want would need its own count computed from raw data.

### Set expressions
**Theta sketches** support union, intersection and difference, and return sketches rather than numbers, so expressions like ((A ∪ B) ∩ (C ∪ D)) \ (E ∪ F) work. "Users who used search and checkout but not support" becomes a sketch calculation. Intersections have larger relative error when the overlap is small compared with the sets, because the answer is estimated from the few shared samples.

## Where you meet this
This is how OLAP (online analytical processing) stores such as Druid and Pinot answer "count distinct" over billions of rows interactively. At ingestion they **pre-aggregate**: for each segment (say, one hour of data), each combination of dimensions gets a sketch column instead of raw user IDs. At query time the broker merges the sketches from every segment the query touches. A query over 90 days and 50 countries may merge tens of thousands of sketches, which takes milliseconds. BigQuery's `HLL_COUNT.INIT` and `HLL_COUNT.MERGE` functions, and PostgreSQL's `hll` extension, expose the same idea in SQL: you can store sketches in a table and merge them in a `GROUP BY`.

! Example: weekly actives from daily sketches
! Each day, each of 100 app servers keeps an HLL of user IDs. At midnight, the 100 sketches are merged into one daily sketch (12 KB) and stored; the per-server sketches are discarded. For "weekly actives", merge 7 daily sketches: 84 KB read, one merge, answer within about 1%.
! Storing daily counts instead (4.1M, 4.3M, 4.2M, 4.0M, 4.4M, 3.1M, 2.9M) could never produce the weekly figure. Their sum is 27M, but if 80% of users come back on several days, the real weekly figure might be 9M. The overlap between days is exactly what the numbers lost.

! Example: storage for a dimensional rollup
! Dimensions: 200 countries, 4 device types, 365 days. That's 292,000 combinations. If each held a dense 12 KB HLL, that is 3.5 GB, but most combinations are small and stay sparse at a few hundred bytes, so the real figure is a few hundred MB for a year of unique-user data at full flexibility. The raw user-day pairs it replaces might be tens of billions of rows.

## Pitfalls
- **Mixing sketch parameters.** Two HLLs with different register counts or different hash functions can't be merged directly. Pick one configuration and keep it for the life of the data, or downsample the larger one first.
- **Mixing implementations.** A Redis HLL and a BigQuery HLL are not compatible formats. Merge only sketches from the same library.
- **Expecting intersections to be accurate.** Unions are excellent; intersections and differences can be poor when the result is a small fraction of the inputs.
- **Storing only the final numbers.** If you keep the daily count but throw away the daily sketch, you've lost the ability to roll up. Store the sketch; the number is cheap to compute from it.

## In an interview
When a design asks for unique counts over flexible time ranges or dimensions ("daily, weekly and monthly actives, by country"), say: "distinct counts don't add, so I'll store a mergeable sketch per bucket instead of a number, HLL for counts or Theta if we need intersections, and merge at query time." Mention that the merge is lossless for HLL (register-wise max) and that this is how Druid and Pinot do it.

> Takeaway: distinct counts aren't additive because the overlap is lost once you have a number. Sketches keep a compact summary that can be merged (HLL by register-wise max, count-min by cell sum, Theta by keeping the smallest hashes), so partial sketches from servers, time buckets or dimensions combine into an accurate total at query time.

An exact distinct count is just a number; adding numbers from 100 servers counts every user seen on several servers multiple times, and nothing in the numbers says how big the overlap was, so it can't be removed. An HLL sketch keeps, for each register, the largest leading-zero value of the hashes routed there; a given user always produces the same hash, so they set the same register to the same value on every server. ## Windows turn a stream into finite answers
A stream never ends, so "how many clicks?" has no answer until you add a time range: clicks in the last hour, per minute, today. A **window** is that time range. Windowing splits an infinite stream into finite pieces you can compute over, and the kind of window you pick decides how much state you keep and how often results change.

Stream processors such as Flink, Kafka Streams and Spark Structured Streaming share the same vocabulary:

| Window | Definition | Typical use |
| **Tumbling** | Fixed size, no overlap, back to back, e.g. every 5 minutes | Per-minute counts, hourly reports, billing periods |
| **Sliding** (hopping) | Fixed size, a new window every *slide*; windows overlap when slide < size, e.g. 10 minutes every 5 | "Last hour, updated every minute" |
| **Session** | Per key, closes after a gap of inactivity, e.g. 10 minutes | User sessions, visits, game matches |
| **Global** | All elements of a key in one window; needs a custom trigger | Count-based windows ("every 100 events"), custom logic |

%%timeline The same stretch of time cut three ways: tumbling windows tile it, sliding windows overlap, and session windows follow the gaps in one user's activity.
[Tumbling 10 min] 12:00 | *Window A opens
[Sliding 10 min, every 5] 12:00 | Window 1 opens
[Session, 5 min gap] 12:00 | user clicks, session opens
[Sliding 10 min, every 5] 12:05 | Window 2 opens
[Session, 5 min gap] 12:05 | clicks continue
[Tumbling 10 min] 12:10 | *A closes, B opens
[Sliding 10 min, every 5] 12:10 | 1 closes, 3 opens
[Session, 5 min gap] 12:10 | last click at 12:08
[Sliding 10 min, every 5] 12:15 | 2 closes, 4 opens
[Session, 5 min gap] 12:15 | *gap passed: session 12:00 to 12:08 closes
[Tumbling 10 min] 12:20 | B closes, C opens
%%

Tumbling windows can take an offset, for example daily windows offset by −8 hours so "a day" means midnight to midnight in California rather than in UTC. Session windows are the odd one: their length is not known in advance, and two sessions can merge if a late event fills the gap between them.

## Sliding windows: the naive cost
The question asks for clicks in the last hour, updated every minute. That's a sliding window of size 1 hour and slide 1 minute. Each event belongs to **60** windows at once: every window whose hour covers it. A generic stream processor assigns each element to every overlapping window and keeps state per window, so if you compute each window from scratch, every event is processed 60 times and 60 windows' worth of state is held. For a sliding hour with a 1-second slide, it would be 3,600 copies. That is wasteful, because consecutive windows share 59 of their 60 minutes.

## The bucketed approach
The efficient answer is to aggregate each event **once**, into a small time bucket, and then build every window out of buckets:
1. Keep a count per **1-minute tumbling bucket**. Each event increments exactly one bucket: the one for the minute it happened in.
2. Keep the last **60 buckets** in a ring buffer, an array of 60 slots where the slot for minute t is `t mod 60`, so the oldest slot is overwritten by the newest.
3. Keep a **running total**. When a minute closes, add the new bucket to the total and subtract the bucket that has just fallen out of the hour.

%%flow A sliding hour from 60 one-minute buckets: each minute, add the newest bucket and subtract the one that expired, so each update is constant work.
Buckets 12:01 to 13:00 -(minute 13:01 closes)-> *Total + bucket 13:01 - bucket 12:01 -> Updated hourly count
%%

So the answer to the question is **60 buckets**, plus one more for the minute currently filling (61 slots in the ring), with resolution equal to the update interval. Each update is O(1): one addition and one subtraction, instead of re-summing 60 numbers or recounting the hour's events.

! Example: the running total, minute by minute
! At 13:00 the 60 buckets for 12:01 to 13:00 sum to 24,800 clicks. The bucket for 12:01 holds 390.
! The minute 13:01 closes with 455 clicks. New total = 24,800 + 455 − 390 = 24,865. The 12:01 slot (index 1 in the ring, since 1 mod 60 = 1) is reused for 13:01.
! At 13:02, bucket 12:02 held 410 and the new minute has 470: 24,865 + 470 − 410 = 24,925.
! The dashboard reads one number per minute. The work per update doesn't depend on how many clicks there were.

### Choosing bucket size
The bucket size is a trade-off between smoothness, state and lateness:
- **Finer buckets** (10 seconds: 360 per hour) give a window that slides more smoothly and a fresher number, but six times the state.
- **Coarser buckets** (5 minutes: 12 per hour) are cheap but the "last hour" jumps in 5-minute steps and can be up to 5 minutes out of date at the edges.
- The bucket should match the **update interval** the product needs. Updating the display every minute with 10-second buckets buys smoothness nobody sees.

For long windows, use a **hierarchy** of buckets: 60 minute-buckets, 24 hour-buckets, 30 day-buckets. As each hour completes, its 60 minutes are rolled up into one hour bucket and the minute buckets can be dropped. "Last 30 days" then costs 30 day-buckets plus up to 24 hour-buckets for today, not 43,200 minute-buckets. Time-series databases (Prometheus recording rules, Druid rollups, RRDtool's round-robin archives) all work this way.

%%tree A bucket hierarchy for long windows: fine buckets for recent time, coarse buckets for the past, each built by rolling up the level below.
Last 30 days | 30 day buckets + today
  Today | 24 hour buckets
    Current hour | 60 minute buckets
      *Current minute | filling now
    Previous hours | rolled up from minutes
  Earlier days | rolled up from hours
%%

## Aggregate incrementally
Flink offers two styles of window function, and the difference is mostly about memory:
- **ReduceFunction / AggregateFunction**: update an accumulator as each element arrives. State is one small value per window (a count, a sum, a min and max). An `AggregateFunction` for an average keeps (sum, count) and divides at the end.
- **ProcessWindowFunction**: buffers **all** elements of the window and processes them when it fires. Flexible (it can sort, look at every element, read window metadata), but state grows with the number of events. A window holding a million events holds a million events. Combine it with an incremental aggregate when possible, so the buffered state is the accumulator, not the raw elements.

For counts and sums, always aggregate incrementally. This works because counts and sums are additive: you can add a bucket in and subtract it out. Some aggregates are not subtractable: you can't "subtract" a minute from a maximum, or from a distinct count. For those:
- **Max or min over a sliding window**: recompute from the 60 bucket maxima each minute (60 comparisons, still cheap), or use a monotonic deque.
- **Distinct counts**: keep a mergeable sketch (an HLL, lesson 10.05) per bucket and merge the 60 sketches when the window fires. You can't subtract an HLL, but merging 60 of them is fast.
- **Percentiles**: keep a histogram or t-digest per bucket and merge (lessons 10.11 and 10.12).

## When does a window fire, and what about late events?
Windows are defined in **event time**, when the click happened, as recorded by the device or edge server, not **processing time**, when it reached the processor. The two differ because events are delayed: a phone in a tunnel uploads its clicks five minutes late, Kafka partitions are consumed at slightly different speeds, and a consumer restarts and replays. If you bucket by processing time, a backlog after a restart dumps ten minutes of clicks into one bucket and the chart shows a spike that never happened.

But event time raises a question: when is minute 12:00 finished? You can never be sure no more 12:00 events will arrive. Flink tracks progress with **watermarks**: a watermark at time t is a claim that "no more events older than t are expected". A common strategy is **bounded out-of-orderness**: watermark = the largest event time seen so far minus a fixed delay, typically around **30 seconds**. When the watermark passes a window's end, the window fires and emits its result.

Events that arrive after the watermark are **late**. Flink's options:
- **Allowed lateness** (default 0): keep the window state a while longer and re-fire with updated results when late events arrive. Downstream must accept updated results, which is easy if writes are upserts keyed by (ad, minute), lesson 10.03.
- **Side output**: send late events to a separate stream for correction or inspection rather than silently dropping them.
- **Drop**: acceptable for a live dashboard, never for billing.

%%seq Event time with a 30-second watermark delay: the 12:00 bucket fires once the watermark passes 12:01:00, and a straggler re-fires it within allowed lateness.
Kafka > Flink : click at 12:00:40 (arrives 12:00:41)
Kafka > Flink : click at 12:01:31 (arrives 12:01:32)
Flink > Flink : watermark = 12:01:31 - 30 s = 12:01:01
Flink > Store : fire bucket 12:00 = 418 (upsert)
Kafka > Flink : late click at 12:00:55 (arrives 12:01:50)
Flink > Flink : within allowed lateness of 5 min
Flink > Store : re-fire bucket 12:00 = 419 (upsert)
Kafka > Flink : click at 11:52:00 (arrives 12:09:00)
Flink > Side output : too late: send for batch correction
%%

The watermark delay is a dial between **latency** and **completeness**. A 30-second delay means every minute's number appears 30 seconds after the minute ends and catches nearly every straggler. A 5-second delay is fresher but sends more events down the late path.

! Example: dashboard of clicks per ad, last hour
! Flink keys clicks by ad ID and counts them in 1-minute tumbling windows with an `AggregateFunction`, watermark delay 30 seconds, allowed lateness 5 minutes. Each closed minute is written to Redis as `clicks:ad9:202611091301 = 418`, with a 2-hour TTL so old buckets expire on their own. The dashboard service keeps a running hourly total per ad: on each new minute, add the newest bucket, subtract the one from 60 minutes ago.
! State sizing: 10 million active ads × 61 buckets × 8 bytes ≈ 4.9 GB, spread across the Flink cluster's keyed state. In practice most ads have few clicks in most minutes, so storing only non-zero buckets cuts this a lot. Redis holds about 2 hours of non-zero buckets for the dashboard.
! A late click re-fires the 12:01 window with 419. The upsert overwrites 418 with 419. If the running total had already used 418, the dashboard must apply the difference (+1) to its total: subtractable aggregates make that easy.

## An approximate alternative
When memory is very tight (a rate limiter tracking millions of API keys, for example), you can approximate a sliding window with just **two buckets**: the current fixed window and the previous one. Estimate = current count + previous count × (fraction of the previous window still inside the sliding window). If the previous minute had 100 requests, the current minute has 30 so far, and we're 20 seconds in, the estimate for the last 60 seconds is 30 + 100 × 40/60 ≈ 97. It assumes events in the previous window were spread evenly, which is often good enough for limiting, but not for analytics.

## Common mistakes
- **Using processing time for analytics.** Restarts and backlogs create fake spikes and dips.
- **Sliding windows as 60 separate windows.** Correct but 60 times the work; build from buckets.
- **Buffering raw events in windows.** A `ProcessWindowFunction` without incremental aggregation holds every event in state.
- **No plan for late data.** Silent drops make numbers quietly wrong; decide between allowed lateness, a side output and a batch correction.
- **Subtracting non-subtractable aggregates.** Max, min, distinct counts and percentiles need merging, not add-and-subtract.

> Takeaway: aggregate a stream into small tumbling buckets (say 1 minute) with incremental functions, then build longer or sliding windows by combining buckets: for "last hour, updated each minute", keep 60 buckets plus the one filling, add the newest and subtract the expired one. Use event time with watermarks, and decide explicitly what happens to late events.

## The question behind the question
Once you have tables of per-minute clicks, per-day uniques and top-K lists, why pay to store the raw events too? The aggregates answer today's dashboard queries faster and in a fraction of the space. The raw events are huge, mostly never read, and expensive to keep in a fast database.

The answer comes from looking at what an aggregate is. An aggregate is a **function of the raw data plus some code**: "count clicks, grouped by ad and minute, excluding events flagged as bots by rule set v3". Once you've computed it and thrown the inputs away, you can never change the code, the grouping or the rules for the past. Every bug, every new question and every audit needs the inputs. This lesson is about treating raw events as the source of truth and everything else as a disposable view.

## The log is the truth, everything else is derived
Look at four things databases already do internally: **replication**, **secondary indexes**, **caching** and **materialised views**. In each, something is derived from something else:
- A **replica** is the result of applying the primary's write-ahead log in order.
- A **secondary index** is a data structure computed from table rows; the database rebuilds it from the table if it's corrupted.
- A **cache** is a copy of query results that can be thrown away and recomputed.
- A **materialised view** is a stored query result, refreshed from its base tables.

Inside the database, the real source of truth is the log: an ordered sequence of immutable changes. A replication log turns an imperative update ("set quantity to 3") into an immutable event ("customer X changed quantity of product Y to 3 at time T"). The tables are just the current result of replaying that log.

The architectural idea, sometimes called "turning the database inside out", is to make this explicit at the system level. Treat an append-only **log of immutable facts** (in Kafka, say) as the source of truth, and treat tables, indexes, caches, search indexes and aggregates as **derived views** computed from it by stream processors.

%%flow Turning the database inside out: the immutable event log is the source of truth, and every table, aggregate, index and cache is a view derived from it.
Writes -> *Immutable event log -(derive)-> Tables, Aggregates, Search index, Cache
%%

The benefits of this structure:
- **Better data.** Updating in place destroys information. Take a shopping cart: a table only shows what's in the cart now, while the event log also shows items that were added and later removed, which is valuable for analytics and recommendations ("people often remove this item after seeing the shipping cost"). Accountants don't use erasers: a ledger records every transaction and corrections are new entries.
- **Recovery and auditing.** If a bug writes bad data into a table, you can see exactly what happened and recompute the table from events before the bug.
- **Fully precomputed caches.** Views are maintained from the log, so they can be warm from the start, and because the log fixes the order of writes, there are no invalidation races between the database and the cache.
- **New views without migrations.** A new feature can build a new view by reading the log from the beginning, beside the old one, without touching the systems already running.

## Lambda: two pipelines, one truth
Before streams were reliable, the common way to get both fast and correct answers was the **Lambda architecture**. Raw immutable data is written to a master dataset and feeds two systems in parallel:
- A **batch layer** (originally Hadoop) periodically recomputes complete, accurate views from all raw data. It is slow (hours) but simple and correct, because it always starts from scratch.
- A **speed layer** (originally Storm) processes recent events as they arrive and produces approximate, up-to-the-minute views covering only what the last batch hasn't processed yet.
- A **serving layer** merges both at query time: batch results for older data, speed results for the last few hours.

One part of this is worth keeping: retaining the input data unchanged and modelling processing as stages derived from it, because it makes **reprocessing** possible. Code changes, bugs are fixed, and you need to recompute outputs from inputs. The batch layer is a constant reprocessing machine.

The problem is the double implementation. Every metric's logic is written twice, in two different frameworks, and must give identical answers. Keeping them in sync is exactly as painful as it sounds: a bug fixed in the batch code but not the streaming code makes the dashboard jump every time a batch lands. Frameworks that promise to compile one definition to both systems tend to leak.

## Kappa: one pipeline, replay to reprocess
The alternative, called the **Kappa architecture**, keeps the raw log but uses one processing system:
1. Keep the full input log in Kafka (for example with 30 days' retention, or forever with tiered storage), allowing multiple subscribers.
2. To reprocess, start a **second instance** of the streaming job reading from the beginning of the log, writing to a **new output table**, with extra parallelism so it catches up quickly.
3. When it has caught up with the live end of the log, switch the application to read the new table.
4. Stop the old job and delete the old table.

%%compare Lambda runs two code paths and merges them; Kappa runs one streaming code path and reprocesses by replaying the log.
[Lambda]
Raw data -(batch job)-> Batch views
Raw data -(stream job)-> Speed views
+ Batch recompute is simple and robust
+ Works with weak stream processors
- Every metric written twice
- Two systems to run and keep identical
- Merge logic at query time
[*Kappa]
Retained log -(stream job v1)-> Table v1
Replay log -(stream job v2)-> Table v2
+ One code base, one set of semantics
+ Reprocessing is just a replay
- Needs long log retention
- Replays of months of data take time
%%

%%timeline A Kappa-style reprocessing after a logic fix: the new job replays the log into a new table, catches up, and readers switch over.
Mon 09:00 | Bug found in click aggregation v1
Mon 11:00 | Fix deployed as job v2, reading from offset 0
Mon 11:00 to 15:00 | v2 replays 30 days in 4 hours, about 180 times live speed
Mon 15:00 | *v2 reaches the live end of the log
Mon 15:10 | Compare v1 and v2 on recent days
Mon 15:30 | *App switches reads to table v2
Tue 09:00 | Stop v1, drop table v1
%%

In practice, many teams run a hybrid. The streaming path produces the live numbers, and a periodic batch job over the data lake recomputes them from raw events using the **same** code (Spark and Flink both run the same job in batch and streaming modes) to reconcile. The ad-click design in lesson 10.03 does exactly this.

## So why keep raw events?
Aggregates are lossy by design. A per-minute count can't tell you per-country counts, distinct users, the gap between a user's clicks, or which clicks came from a bot you only discovered last week. Keeping raw events lets you:
- **Fix bugs.** Recompute aggregates after correcting the logic, the time zone handling or the bot filtering.
- **Answer new questions over history.** The product team asks for clicks by device type. With raw events you build a new aggregate over the last year. Without them, the metric starts today.
- **Reconcile and audit.** Check real-time results against a recomputation, and show a customer the individual events behind a bill.
- **Backfill new systems.** Populate a new store, search index or machine-learning feature table from history.
- **Train models.** Recommendation and fraud models need individual events, not sums.

## Where raw events live
The cost is storage, which is why raw events move through tiers as they age. Kafka holds recent data for replay and for new consumers. After the retention period, the data lives in cheap object storage in columnar formats such as **Parquet**, partitioned by date, where batch engines (Spark, Trino, BigQuery) can scan it. Aggregates stay hot, in an OLAP store or a cache, for interactive queries.

%%layers Where each kind of data lives: aggregates are small and hot, raw events are big and cold, and every layer above can be rebuilt from the one below.
Cache | top-K lists, live counters; seconds old
*OLAP store | per-minute aggregates and sketches; months
Kafka | raw events, replayable; days to weeks
Object storage, Parquet | raw events, the permanent truth; years
%%

! Example: what raw events actually cost
! 100 million click events per day, about 200 bytes each as JSON: 20 GB per day. In Parquet, columnar compression (repeated ad IDs, timestamps that differ by milliseconds, a handful of countries) typically shrinks this by 5 to 10 times, so about 3 GB per day, or about 1.1 TB per year.
! Object storage at roughly 2 cents per GB per month: 1.1 TB is about 22 dollars a month for a full year of every click, and less on archival tiers. Compare the cost of one disputed invoice or one metric you can't backfill. The raw data is almost always worth keeping; the question is only how fast it must be to query.

## Pitfalls
- **Logging "events" that are really states.** "Cart now contains A, B" loses the removal. Log the facts that happened ("item C removed"), not snapshots.
- **No schema discipline.** Raw events kept for years are only useful if you can still parse them. Use a schema registry (Avro or Protobuf) and evolve schemas compatibly.
- **Personal data kept forever.** Raw events often contain user IDs and IP addresses. Privacy laws (GDPR's right to erasure) mean you need a deletion strategy, such as keying events by a pseudonymous ID whose mapping you can delete, or periodic rewrites of the data lake.
- **Replays that have side effects.** If a derived view's builder also sends emails, replaying the log sends them again. Keep side effects out of view builders, or make them idempotent.
- **Assuming you'll never reprocess.** Every long-lived metrics system eventually needs a backfill. Design for it on day one.

! Example: a bot filter after the fact
! On Thursday you learn a click farm inflated ad 9's clicks since Monday. With only per-minute aggregates, the bad clicks are mixed in forever: you can't tell which of the 418 clicks in minute 12:03 were fake.
! With raw events in S3, you run the new bot filter (say, more than 20 clicks per device per hour, or clicks from a known data-centre IP range) over Monday to Thursday, recompute ad 9's per-minute counts into a new table, compare (Monday 12:03 drops from 418 to 161), switch the dashboard to the corrected table, and issue the advertiser a credit with evidence attached: the list of rejected click IDs and why.

## In an interview
When you add aggregates to a design, add a line for raw events too: "Raw events go to Kafka and are archived to S3 in Parquet; aggregates are views we can rebuild." If asked Lambda or Kappa, say you'd prefer one code path (Kappa, or a framework that runs the same job in batch and streaming) and use batch recomputation for reconciliation, not as a second implementation.

> Takeaway: aggregates are derived and lossy; raw events are the source of truth. Keeping them lets you recompute after bugs, answer new questions over history, audit, and reconcile real-time results. Treat tables and caches as views over an immutable log, and reprocess with one streaming code base by replaying the log into a new table and switching readers.

Aggregated tables throw information away and bake in today's grouping and logic: a per-minute count can't be split by a new dimension, have a newly discovered bot filtered out, or be checked against an advertiser's dispute. With raw events kept as the immutable source of truth (in Kafka for recent data and cheap columnar storage for history), you can fix a bug or filter and recompute the aggregates, build new metrics over past data, reconcile real-time results against a batch recomputation, and backfill new stores and models. ## What count-min sketch answers
HyperLogLog (lesson 10.04) answers "how many **different** items?". Count-min sketch answers a different question: "**how many times** has item x appeared?", for any x you care to ask about, using memory much smaller than one counter per item. Graham Cormode and S. Muthukrishnan invented it in 2003 (published 2005).

Why not just keep a hash map from item to count? Because the number of distinct items can be enormous. A CDN counting requests per URL, a router counting packets per source IP, or a search engine counting queries sees hundreds of millions of distinct keys per day. A hash map with 300 million entries at around 50 bytes each is 15 GB, per server, per time window. A count-min sketch with a guaranteed error bound fits in tens of kilobytes, regardless of how many distinct items pass through it.

The price is that the answer is approximate, and approximate in one particular direction: it may be too high, but it is never too low. Understanding why is the whole lesson.

## Structure and operations
- A 2D array of counters with **d rows** and **w columns**, all starting at 0.
- Each row j has its own hash function hⱼ mapping any item to a column between 0 and w − 1. The hash functions are chosen independently (in practice, one good 64-bit hash with different seeds, or two hashes combined as h₁ + j × h₂).
- **Update(x, c)**: for each row j, add c to the counter at column hⱼ(x). For a plain count, c = 1.
- **Query(x)**: look at x's counter in each row, the cells at hⱼ(x), and return the **minimum**.

Both operations cost d hash computations and d memory accesses, independent of how many items exist: with d = 5, an update is five increments.

%%flow Count-min sketch with 3 rows: an update increments one cell per row; a query reads the same three cells and takes the minimum.
[Update #cats] #cats -(h1)-> row 1, col 4 += 1 -(h2)-> row 2, col 1 += 1 -(h3)-> row 3, col 7 += 1
[Query #cats] Read 52, 49, 61 -(minimum)-> *Estimate 49
%%

## Why it never underestimates
Follow item x through the sketch. Every time x appears, all d of its cells are incremented. Other items may hash to the same cells (collisions) and add to them too, but no operation ever subtracts. So each of x's cells holds:

`cell value = true count of x + counts of every other item that collided there ≥ true count of x`

The noise term is a sum of counts, and counts are never negative, so it is always ≥ 0. The minimum of d numbers that are all ≥ the true count is also ≥ the true count. That's the whole argument: overestimation is possible, underestimation is impossible.

Taking the minimum is the best you can do with this information. Every cell is an upper bound, so the smallest upper bound is the tightest. With several independent hash functions, it is unlikely that all of x's cells collided with heavy items, so at least one cell is usually close to the truth.

! Example: overestimation in action
! A sketch with one row and four columns, for illustration. Stream: a, b, a, c, a, d. Suppose h₁(a) = 2, h₁(b) = 0, h₁(c) = 2, h₁(d) = 3. After the stream the cells are [1, 0, 4, 1].
! Query a = 4 (true count 3: c collided with it). Query c = 4 (true count 1: badly inflated by a). Query b = 1 and d = 1 (exact, no collisions).
! Add a second row with a different hash: h₂(a) = 1, h₂(b) = 3, h₂(c) = 3, h₂(d) = 0. Row 2's cells become [1, 3, 0, 2].
! Now query a = min(4, 3) = 3, exact. Query c = min(4, 2) = 2, still too high (b collided with c in row 2) but better than 4. No query ever came out below its true count.

%%matrix The two-row sketch from the example after the stream a, b, a, c, a, d. Item a's cells are 4 and 3, so its estimate is 3; item c's are 4 and 2, so its estimate is 2.
Row | col 0 | col 1 | col 2 | col 3
Row 1, hash h1 | 1: b | 0 | 4: a, a, a, c | 1: d
Row 2, hash h2 | 1: d | 3: a, a, a | 0 | 2: b, c
%%

## The error guarantee
How much too high can the answer be? Let N be the total of all updates (the stream length for plain counts). Choose:
- w = ⌈e / ε⌉ columns, where e ≈ 2.718
- d = ⌈ln(1/δ)⌉ rows

Then for any item x, the estimate is at most **true count + ε·N**, with probability at least **1 − δ**. Memory depends only on ε and δ, not on how many distinct items there are.

The proof is short enough to follow. In one row, the other items' counts total at most N, and each lands in x's column with probability 1/w, so the expected noise in x's cell is at most N/w = εN/e. By Markov's inequality (a non-negative quantity exceeds e times its mean with probability at most 1/e), the noise exceeds εN with probability at most 1/e. The rows use independent hashes, so the chance that **every** row's noise exceeds εN is at most (1/e)^d = δ. The minimum is only that bad if every row is that bad.

| Target | w | d | Counters | Memory at 4 bytes |
| ε = 0.001, δ = 0.01 | 2,719 | 5 | about 13,600 | about 54 KB |

### Accurate for heavy items, useless for rare ones

! Example: what ε·N means for real items
! A stream of N = 10 million search queries per hour, sketch with ε = 0.001 and δ = 0.01 (54 KB). The error bound is 0.001 × 10,000,000 = 10,000.

! In practice the average error is much smaller than the bound (the bound is a worst case), but the shape holds: frequent items are measured well, rare ones are swamped.

## Variants and properties
- **Mergeable.** The sketch is linear: adding two sketches with the same dimensions and hash functions cell by cell gives exactly the sketch of the combined stream. Per-server or per-minute sketches merge like HLLs (lesson 10.05), so you can build a sliding window from bucket sketches (lesson 10.06). Being linear, a count-min sketch can even be subtracted, as long as every item's net count stays non-negative.
- **Conservative update.** When adding 1 to x, first compute x's current estimate m (the minimum), then raise each of x's cells only as far as needed, to max(cell, m + 1), rather than incrementing all of them. Cells already above m + 1 already account for this occurrence and don't need to grow. This reduces overcounting substantially on skewed data; the sketch is no longer linear (you can't subtract), but it remains an upper bound and merges reasonably by cell-wise sum.
- **Bias correction.** The minimum is biased upward. Estimators such as count-mean-min subtract an estimate of the average noise per row, giving less biased (but no longer one-sided) answers.
- **Count sketch** is a related structure: each row also has a ±1 sign hash, updates add or subtract, and the query takes the median of the rows. Collisions cancel on average, so it is unbiased and more accurate when the distribution is not skewed, but it can underestimate. Count-min works best when a few items dominate.

## In a design
For top-K, count-min is an option when exact per-item counts are too big: add each event to the sketch, query the sketch for the item's estimated count, and maintain a min-heap or sorted set of the current top 1,000 using those estimates (lesson 10.09). Redis supports this through the RedisBloom module with `CMS.INITBYPROB key 0.001 0.01`, `CMS.INCRBY key item 1` and `CMS.QUERY key item`, alongside a sorted set (`ZADD`). Network devices use count-min to spot heavy flows at line rate, and databases use similar sketches to estimate how many rows match a value when planning queries.

## Common mistakes
- **Using it for rare items.** If the question is "how many times did this one user do X?", the error bound swamps small counts. Use exact counting for small keyed sets.
- **Comparing sketches with different seeds or sizes.** Merging only works with identical w, d and hash functions.
- **Treating the estimate as exact for billing.** It is an upper bound with probability 1 − δ, not a ledger.
- **Forgetting that N keeps growing.** In a sketch that never resets, εN grows forever and estimates degrade. Use time-bucketed sketches and drop old buckets.

## The problem
"Top 10 hashtags in the last hour" over 1 million events per second. This is the **heavy hitters** or **top-K** problem: find the K items with the largest counts in a stream. It powers trending topics, most-viewed videos, hottest products, the most-requested URLs on a CDN and the noisiest IP addresses during an attack.

The exact approach is easy to describe: keep a counter per hashtag per time bucket, and every minute sort all the counters. The trouble is size and speed. There may be millions of distinct hashtags in an hour, the events arrive across many machines, and a sort of everything every minute is wasteful when you only want 10 results. This lesson combines the pieces from this module (bucketed windows, count-min, heaps, mergeable summaries) into a standard pipeline, and shows where approximation creeps in.

## Keeping the top K: a min-heap
Start with the smallest piece. Given a stream of (item, count) updates, how do you keep track of the current top K without sorting? Use a **min-heap of size K**. A heap is a binary tree stored in an array where every parent is smaller than its children, so the root is always the smallest element. In a min-heap of the current top K, the root is the **weakest** member of the top K, the one a newcomer must beat.

For each candidate (item, count):
1. If the item is already in the heap, update its count and restore heap order (O(log K)).
2. Else if the heap has fewer than K items, insert it (O(log K)).
3. Else if its count is greater than the root's, replace the root with it and sift down (O(log K)).
4. Otherwise ignore it: it can't be in the top K.

Each step costs O(log K), and K is small (10 or 100), so this is a handful of comparisons. Step 1 needs a side index (a hash map from item to heap position) so you can find an item in the heap. In Redis, a sorted set does all of this for you: `ZINCRBY trending 1 "#worldcup"`, then `ZREVRANGE trending 0 9 WITHSCORES` for the top 10, trimmed occasionally with `ZREMRANGEBYRANK`.

%%tree A min-heap holding the current top 5 hashtags by count: the root is the weakest of the five, so a newcomer only has to beat 4,100 to get in.
#cats 4,100 | root: the bar to beat
  #nyc 5,200
    #f1 9,800
    #oscars 7,300
  *#worldcup 61,000
%%

! Example: a newcomer enters the heap
! The heap above holds the top 5. A new count arrives for #eurovision: 4,600. It isn't in the heap, the heap is full, and 4,600 > 4,100 (the root, #cats), so #cats is evicted and #eurovision takes the root position. Sifting down compares it with its children (#nyc 5,200 and #worldcup 61,000); 4,600 is smaller than both, so it stays at the root. The new bar to beat is 4,600.
! Next, #cats gets more events and its count reaches 4,400. It isn't in the heap, and 4,400 < 4,600, so it is ignored.

## Misra-Gries: heavy hitters with k−1 counters
The heap needs accurate counts to feed it. When even a counter per distinct item is too much memory, the **Misra-Gries summary** (Misra and Gries, 1982) finds frequent items with only **k − 1 counters**. The update rule for each arriving item i:
1. If i already has a counter, increment it.
2. Else, if fewer than k − 1 counters are in use, start a counter for i at 1.
3. Else, **decrement every counter by 1**, removing any that reach 0 (and discard i).

The intuition: each decrement step "cancels" k distinct items against each other (the k − 1 tracked ones and the newcomer). In a stream of n items, that can happen at most n/k times. An item that occurs **more than n/k times** can't be completely cancelled, so it is certain to be in the summary at the end. Its stored count is an underestimate by at most n/k. A second pass, or a parallel exact count for the few surviving candidates, gives exact counts. With k = 2 it is the classic Boyer-Moore majority vote algorithm (one counter, finds the item occurring more than half the time, if one exists).

%%timeline Misra-Gries with 2 counters (k = 3) on the stream a b a c a d a: an unseen item arriving when both counters are in use decrements everyone.
1: a | counters a:1
2: b | a:1, b:1
3: a | a:2, b:1
4: c | *both full, decrement all: a:1, b gone, c discarded
5: a | a:2
6: d | a:2, d:1
7: a | *a:3, d:1. a occurs 4 > 7/3 times, so it must survive
%%

"a" ends with a counter of 3 against its true 4, an undercount, but it is correctly kept as the heavy hitter. "d" is also in the summary with 1; Misra-Gries can keep false candidates, which is why you verify the survivors.

Misra-Gries summaries are **mergeable**: add the two summaries' counters key by key, then if more than k − 1 keys remain, subtract the k-th largest count from all counters and drop those at zero or below. So each server can keep its own summary and a coordinator merges them, with the same n/k guarantee for the combined stream. The **Space-Saving** algorithm is a close relative used in many libraries: instead of decrementing everyone, a newcomer replaces the item with the smallest counter and inherits its count plus one, so it overestimates instead of underestimating.

## Count-min plus heap
The alternative: add each event to a count-min sketch (lesson 10.08), read back the item's estimated count, and offer (item, estimate) to a min-heap of size K. Memory is the sketch (fixed size, tens of kilobytes) plus K entries. Estimates can be slightly high, but heavy hitters are precisely the items count-min estimates well, because the error bound εN is small compared with their counts. A rare item can occasionally be overestimated enough to sneak into the heap, which is why you size ε so that εN is well below the expected K-th count.

Count-min + heap | fixed sketch + K | over, by at most epsilon N | partial, rare misses | yes, add sketches

## The pipeline
%%flow Top 10 hashtags per hour at 1 million events per second: partition by hashtag, count locally per minute, merge local top lists, combine 60 minutes.
Events, 1M per s -(partition by hashtag)-> Kafka, 64 partitions -(local counts per minute)-> *64 workers -(local top 100)-> Merger -(sum 60 minute buckets)-> Top 10, cached
%%

1. **Ingest.** Events go to Kafka, **partitioned by hashtag**, so every occurrence of a given hashtag goes to the same partition and the same worker, and its count on that worker is complete. At 1M events per second, 64 or more partitions spread the load (about 16,000 events per second per partition). For extremely hot hashtags, add a random suffix and sum later, as in lesson 10.03, at the price of making that hashtag's count span several workers.
2. **Count locally per minute.** Each worker keeps counts per hashtag in 1-minute tumbling buckets (exact counts if memory allows; count-min or Misra-Gries if not).
3. **Emit a local top list per minute.** Each worker sends its top N (say 100, more than K for safety) with counts.
4. **Merge.** A single merger combines the workers' lists. Because partitioning by hashtag makes the workers' key sets **disjoint**, no hashtag's count is split across workers, so the global top K for a minute is simply the top K of the union of local top lists. (If keys were not disjoint, a hashtag at number 101 on every one of 64 workers could be number 1 globally and be missed entirely.)
5. **Sliding hour.** Keep 60 minute-buckets of counts for candidate hashtags and add or subtract as minutes roll (lesson 10.06), then take the top 10.
6. **Serve.** Write the result to a cache (Redis) every minute; API reads never touch the pipeline.

### The subtle step: from minutes to an hour
Combining **per-minute top-100 lists** into an hourly top 10 is approximate. A hashtag that was 101st every single minute but steady all hour never appears in any minute's list, yet its hourly total could make it the hour's true number 8, beating a hashtag that spiked to number 1 for two minutes and vanished.

! Example: the steady hashtag the minute lists miss
! #marathon gets 1,200 uses every minute, all hour: 72,000 in total. It ranks about 101st each minute, so it never appears in a local top-100 list.
! #halftimeshow gets 30,000 uses in each of two minutes and almost nothing otherwise: 60,000 in total. It tops two minute lists.
! Summing the minute lists, the merger sees #halftimeshow at 60,000 and #marathon at 0. The true hourly ranking has #marathon ahead.

Remedies, from cheapest to most thorough:
- **Emit larger local lists** (top 1,000 instead of 100), shrinking the gap.
- **Keep per-hashtag hourly counts on each worker** (a running 60-bucket window per hashtag, lesson 10.06). Keys are disjoint per partition, so each worker can produce an exact hourly local top list, and the merge of those is exact.
- **Accept the approximation** for a "trending" feature and reconcile with a batch job for anything reported officially.

### Trending is not the same as top
Real trending features rarely show the raw most frequent hashtags, because the answer would always be the same perennial tags. They rank by **velocity**: this hour's count compared with a baseline, such as the same hour last week or an exponentially weighted average. The pipeline is the same; the score fed to the heap is, for example, `count_this_hour / (baseline + smoothing)`.

! Example: the numbers
! 1M events per second × 60 = 60M events per minute, 3.6 billion per hour. Suppose 2M distinct hashtags per hour. Exact hourly counters per hashtag: 2M × (key about 20 bytes + 8-byte count + hash map overhead, say 60 bytes) ≈ 120 MB in total. Spread over 64 workers, that's under 2 MB each, so exact counting per worker is perfectly affordable here, and even 61 minute-buckets per hashtag (about 120 MB per worker if every hashtag appeared every minute, far less in reality) is manageable.
! The merger receives 64 lists of 100 entries per minute: 6,400 entries, trivial.
! The sketches matter when keys are far more numerous (every URL on a CDN, every source IP, every search query) or memory per worker is tight: 500 million distinct keys per hour at 60 bytes is 30 GB, while a count-min sketch with ε = 0.0001 is under 1 MB.

## Common mistakes
- **Partitioning randomly, then merging top lists.** If a key's count is split across workers, merging local top lists can miss the true top items. Partition by key, or merge full summaries rather than top lists.
- **Sorting everything every minute.** Use a heap; the work should be proportional to K, not the number of keys.
- **Ignoring hot keys.** One hashtag at 200,000 events per second overloads its partition. Salt it and sum.
- **Serving from the pipeline.** Cache the result; the API should read a precomputed list.

Then say where it is approximate (minute lists versus hourly totals) and how you'd fix it, and mention Misra-Gries or count-min plus a heap if the key space is too large for exact counts.

## The problem
You want a **uniform random sample** of k items from a stream whose length n you don't know in advance, in one pass, without storing the stream. "Uniform" means every item that has passed has the same chance of being in the sample, and every set of k items is equally likely.

This comes up constantly in systems:
- Keep 1,000 sample log lines from a day of logs, so an engineer can see what typical errors look like without storing billions of lines.
- Sample requests for distributed tracing, where tracing everything would cost more than the service itself.
- Show a random sample of 100 rows from a query result that is still streaming in.
- Pick a survey panel from users as they log in during the day.
- Estimate statistics (median, distribution of sizes) over a stream by computing them on a sample.

The difficulty is that you don't know n. If you knew a day had exactly 10 million log lines, you could keep each one with probability 1,000/10,000,000 and get about 1,000. But traffic varies, the day isn't over yet, and you want a valid sample at any moment.

### Why the obvious approaches fail
- **Keep the first k.** Biased: the sample only contains the start of the day.
- **Keep everything, then pick.** Correct, but needs memory proportional to n, which is the thing you're trying to avoid.
- **Keep each item with a fixed probability p.** Needs n to choose p, and the sample size varies: too small on a quiet day, too large on a busy one.
- **Keep the last k.** Biased the other way: only the end of the day.

%%compare Ways to keep a sample of k from a stream of unknown length. Only reservoir sampling is uniform with fixed memory.
[Fixed probability p]
Keep each item with chance p
- Must know n to choose p
- Sample size varies with traffic
+ Trivial, stateless
[First k or last k]
Keep a window at one end
- Biased towards one end
+ Trivial
[*Reservoir sampling]
Keep k, replace with chance k/i
+ Uniform at every moment

%%

**Reservoir sampling** solves it, and the simplest version is a few lines of code.

## Algorithm R
1. Put the first k items into the **reservoir**, an array of k slots.
2. For the i-th item (i > k), draw a random integer j between 1 and i inclusive. If j ≤ k, **replace reservoir slot j** with item i. Otherwise, discard item i.

So item i enters the reservoir with probability **k / i**, and if it does, it evicts a uniformly random current member (because j, conditioned on being ≤ k, is uniform over 1 to k).

```
reservoir = []
for i, item in enumerate(stream, start=1):
    if i <= k:
        reservoir.append(item)
    else:
        j = random.randint(1, i)
        if j <= k:
            reservoir[j - 1] = item
```

%%flow Algorithm R with k = 1,000: the first thousand fill the reservoir, then item i replaces a random slot with probability 1,000 / i.
Items 1..1,000 -(fill)-> *Reservoir of 1,000 -(item i: keep with prob 1,000 / i)-> Replace random slot -(else)-> Discard
%%

Notice how the acceptance probability falls as the stream grows. Item 2,000 has a 50% chance; item 100,000 has 1%; item 10 million has 0.01%. Late items are rarely accepted, but there are many more of them, which is exactly what keeps the sample balanced.

## Why it is uniform
The proof is by induction on the number of items seen. The claim: after i items (i ≥ k), each of them is in the reservoir with probability k/i.

**Base case.** After k items, all k are in the reservoir: probability k/k = 1. True.

**Step.** Suppose after i − 1 items, each of them is in the reservoir with probability k/(i − 1). Now item i arrives:
- Item i is included with probability **k/i**. That matches the claim for item i.
- An earlier item that is currently in the reservoir is evicted at step i only if item i is included **and** item i picks its particular slot: probability (k/i) × (1/k) = 1/i. So it survives step i with probability 1 − 1/i = (i − 1)/i.
- Its probability of being in the reservoir after step i is therefore k/(i − 1) × (i − 1)/i = **k/i**.

Every item seen so far has the same probability k/i of being in the sample, at every point in the stream. That's what lets you stop at any time and have a valid sample. (A stronger version of the argument shows every subset of size k is equally likely, not just every individual item.)

! Example: a tiny trace with k = 2
! Stream A, B, C, D. After B: reservoir {A, B}, each with probability 1.
! C arrives (i = 3): kept with probability 2/3. If kept, it replaces A or B with equal chance. So A survives with probability 1 − (2/3)(1/2) = 2/3, and the same for B. All three items now have probability 2/3, which is k/i = 2/3.
! D arrives (i = 4): kept with probability 2/4 = 1/2. Each current member is evicted with probability (1/2)(1/2) = 1/4, so survives with 3/4. A's probability: 2/3 × 3/4 = 1/2. C's: 2/3 × 3/4 = 1/2. D's: 1/2. All four have probability 1/2 = k/i.

%%bars Probability that each item is in a reservoir of 1,000 after 5,000 items. The first item and the last are equally likely: that is what uniform means.
Item 1 | 20 | 20%
Item 1,000 | 20 | 20%
Item 2,500 | 20 | 20%
*Item 5,000 | 20 | 20%
%%

! Example: k = 1,000, item 5,000
! Item 5,000 is kept with probability 1,000/5,000 = 20%. If kept, it replaces a random one of the 1,000 slots.
! Each of items 1 to 4,999 was in the reservoir with probability 1,000/4,999 and survives this step with probability 1 − 1/5,000, giving 1,000/4,999 × 4,999/5,000 = 1,000/5,000 = 20%.
! All 5,000 items now have a 20% chance of being in the sample. By item 1,000,000, each has 0.1%. Memory never changed: 1,000 slots.

## How much work does it do?
Algorithm R is O(n): one random number per item. How many replacements happen? The expected number of times item i is accepted is k/i, so the total expected replacements after the first k is the sum of k/i for i from k + 1 to n, which is about k × ln(n/k).

! Example: replacements over a day
! k = 1,000 and n = 1 billion log lines. Expected replacements: 1,000 × ln(1,000,000) ≈ 1,000 × 13.8 ≈ 13,800. So of a billion items, only about 14,000 ever enter the reservoir after it fills. Algorithm R still generates a billion random numbers to decide that, which is where the next algorithm saves time.

## Faster: Algorithm L
Since later items are almost always discarded, **Algorithm L** (Li, 1994) computes how many items to **skip** before the next replacement, instead of flipping a coin for each one. The skip length follows a geometric distribution whose parameter it updates after each replacement, and the expected running time becomes **O(k(1 + log(n/k)))**, which is optimal: proportional to the number of replacements, not the number of items. Skipped items aren't even examined, which matters when reading items is cheap (seeking forward in a file, skipping records in a buffer) but random number generation or per-item work isn't. For the billion-line example, that's about 14,000 random draws instead of a billion.

## Weighted and distributed variants
### Weighted sampling
Sometimes items should be sampled in proportion to a weight: sample requests weighted by their latency, so slow ones are over-represented, or sample users weighted by spend. **A-Res** (Efraimidis and Spirakis) gives each item a key u^(1/w), where u is uniform random in (0, 1) and w is the item's weight, and keeps the k items with the largest keys in a min-heap. Heavier items get keys closer to 1 and are more likely to be kept.

### Distributed sampling
Algorithm R can't be run across ten servers and simply merged: each server's reservoir represents a different number of items, so combining them naively over-represents the quiet servers. The trick is to make the sample defined by a property of each item:
- Give every item a random **tag** in [0, 1).
- Keep the k items with the **smallest** tags (a max-heap of size k, so you can evict the largest).

The k smallest tags among n items form a uniform random sample, since tags are independent and identically distributed. Each server keeps its local k smallest. Merging means taking the k smallest of the union, which is exactly the k smallest tags of the combined stream: equivalent to sampling the combined stream directly. That makes it mergeable like the sketches in lesson 10.05.

%%flow Distributed reservoir sampling by random tags: each server keeps its k smallest tags, and the merge keeps the k smallest overall.
Server 1: k smallest tags, Server 2: k smallest tags -(union)-> *Keep k smallest -> Uniform sample of all streams
%%

If the tag is a hash of the item instead of a random number, the same item gets the same tag everywhere, which turns this into a sample of **distinct** items. That is exactly the idea behind the Theta sketch for distinct counting.

## Sampling in real systems
- **Tracing.** Head-based sampling decides at the start of a request (keep 1%). Tail-based sampling buffers spans and decides at the end, so it can keep all errors and slow requests plus a reservoir of normal ones. Reservoir sampling per endpoint gives each endpoint a guaranteed number of examples, even rare ones.
- **Logging.** A per-error-type reservoir keeps 100 examples of each distinct error message per hour, however noisy the noisiest one is.
- **Databases.** `TABLESAMPLE` and query planners' statistics collectors use sampling to estimate distributions without full scans.

## Limits and pitfalls
- **The reservoir must fit in memory.** For k in the millions, use the distributed tag approach with spill to disk.
- **When k is a large fraction of n**, simpler methods (shuffle, or Bernoulli sampling with a known n) are fine.
- **Bad randomness biases the sample.** Using `random() % i` with a small random range, or a poor generator, skews acceptance. Use a proper uniform integer generator.
- **Time-sensitive samples.** A day's reservoir is uniform over the day. If you want "recent" examples, use a sliding window of reservoirs (one per hour) or a decaying weighted scheme.
- **Small samples hide rare events.** A uniform sample of 1,000 from 1 billion contains, on average, one example of something that happens once per million. Stratify (one reservoir per category) when rare categories matter.

## In an interview
If the design needs examples from a stream ("keep sample logs", "trace a sample of requests"), say "reservoir sampling: keep k, then accept item i with probability k/i into a random slot", and give the one-line proof: the newcomer gets k/i; an existing item survives with (i − 1)/i, so k/(i − 1) × (i − 1)/i = k/i. Mention random tags for a mergeable distributed version.

By induction every item seen is in the sample with probability k/i at every moment. ## The problem: quantiles from a stream
Latency targets are stated as quantiles. "p99 under 300 ms" means 99% of requests are faster than 300 ms. A **quantile** q is the value below which a fraction q of the data lies: the median is the 0.5 quantile (p50), and p99 is the 0.99 quantile. Quantiles matter because averages hide the slow tail that users actually feel (lesson 01.03 shows a service with an 88 ms average and a 1 second p99).

An exact quantile needs every value, sorted. This is worse than exact distinct counting: you must keep a copy of every item and sort them. For a service handling 50,000 requests per second, an hour of latencies is 180 million numbers, 1.4 GB as doubles, per endpoint, per hour, before you try to combine servers. You need a compact, mergeable summary that answers quantile queries approximately, with the error where it hurts least.

The **t-digest** is one of the most widely used. It is a data structure for accurate online accumulation of rank-based statistics (quantiles, trimmed means), handling both floating-point and integer values, with digests that can be **merged**, which suits map-reduce and parallel streaming systems such as Spark. Elasticsearch's percentiles aggregation, several Prometheus-compatible systems, Apache Druid and many APM tools use it or its close relatives.

## Why not a simple histogram?
The first idea is fixed buckets: count values in 0 to 10 ms, 10 to 20 ms, and so on. That is what Prometheus histograms do (lesson 10.12), and it works when you know the range and the interesting thresholds in advance. But fixed buckets waste resolution where data is dense and lose it where data is sparse. If 99% of requests take 30 to 60 ms and the slow 1% are spread from 200 ms to 10 s, equal-width buckets either need thousands of buckets or report p99.9 as "somewhere between 1 and 10 seconds". The t-digest adapts its buckets to the data.

## How it works: clusters of values
A t-digest summarises the distribution as a sorted list of **centroids**. Each centroid is a pair: a **mean** value and a **count** of how many values it represents. Together the centroids are a compressed picture of the sorted data, where each centroid stands in for a run of neighbouring values.

Building it is a variant of one-dimensional k-means clustering. In the common `MergingDigest` implementation:
1. Incoming values are appended to a small buffer.
2. When the buffer fills, it is sorted and merged with the existing centroids, walking left to right in value order.
3. During the walk, each value or centroid is folded into the current centroid **if the result stays within the size limit for that position**; otherwise it starts a new centroid.
4. The result is again a sorted list of centroids, typically a few hundred.

### Answering a query
To estimate the value at quantile q, compute the target rank q × N, walk the centroids in order adding up counts until you reach that rank, and **interpolate** between the means of the neighbouring centroids. Each centroid is treated as sitting at the middle of the ranks it covers.

%%flow Answering a quantile query: turn the quantile into a rank, walk the sorted centroids accumulating counts, and interpolate between the two centroids around that rank.
p99 of N values -(rank = 0.99 N)-> Walk centroids, sum counts -(passes rank)-> *Interpolate between neighbours -> Estimated value
%%

! Example: reading p50 and p99 from a small digest
! N = 1,000 latencies summarised as nine centroids (mean, count): (10 ms, 1), (20, 5), (40, 200), (45, 400), (60, 300), (120, 80), (400, 10), (1,500, 3), (3,000, 1). The counts add up to 1,000.
! p99 is rank 990. Cumulative counts are 1, 6, 206, 606, 906, 986, 996, 999, 1,000. The (120, 80) centroid covers ranks 906 to 986, centred at 946. The (400, 10) centroid covers 986 to 996, centred at 991. Rank 990 lies between those centres, 44/45 of the way, so p99 ≈ 120 + 0.98 × 280 ≈ 394 ms.
! p50 is rank 500. The (45, 400) centroid is centred at 406 and the (60, 300) centroid at 756. 500 is 94/350 of the way: p50 ≈ 45 + 0.27 × 15 ≈ 49 ms.
! Notice where the precision is. The median comes from centroids of 400 and 300 values, but a 15 ms spread between them means the answer can't be far off. p99 comes from centroids of 80 and 10 values, and the extreme tail is held as single values (3,000 ms is one actual request).

## Unequal centroids: the scale function
The key design choice is that **centroids are not equal in size**. A **scale function** k(q) limits how many values a centroid may absorb, depending on where it sits in the distribution. The rule is that a centroid may span at most one unit of k: if a centroid covers quantiles from q_left to q_right, then k(q_right) − k(q_left) ≤ 1. Where k is steep, centroids must be narrow; where k is flat, they can be wide.

The original scale function is `k(q) = (δ / 2π) · asin(2q − 1)`, where δ is the **compression** parameter (typically 100 to 200). The arcsine is flat in the middle and steep at both ends. Working through the derivative, a centroid near quantile q can hold about `2π · N · √(q(1 − q)) / δ` values.

! Example: centroid sizes for 10 million values with compression 100
! At q = 0.5: 2π × 10,000,000 × 0.5 / 100 ≈ 314,000 values in one centroid.
! At q = 0.99: √(0.99 × 0.01) ≈ 0.0995, so about 62,500 values.
! At q = 0.9999: √0.0001 = 0.01, so about 6,300 values.
! At q = 0.999999: about 630 values. And the very first and last centroids are always kept as single values, so the minimum and maximum are exact.
! The total number of centroids stays around δ to 2δ, a few hundred, whatever N is: at 16 bytes each (a double mean and a count) that's a few kilobytes for 10 million or 10 billion values.

%%bars Approximate centroid capacity across the distribution for 10 million values and compression 100: huge in the middle, shrinking towards the edges, and single values at the extremes.
q 0.5 | 314000 | about 314,000 values
q 0.9 | 188000 | about 188,000
q 0.99 | 62500 | about 62,500
q 0.9999 | 6300 | about 6,300
q 0.999999 | 630 | about 630
*Extreme value | 1 | 1 value, exact
%%

Newer scale functions, based on logarithms, limit cluster size near the tails even more aggressively, roughly in proportion to q(1 − q) rather than its square root, which gives better relative accuracy at the extremes for the same number of centroids. The effect is the same in spirit: big clusters in the dense middle, tiny ones at the edges.

%%compare Spending a fixed budget of centroids: equal-sized clusters waste precision on the median, while t-digest's scale function moves it to the tails.
[Equal-size clusters]
Every centroid holds N / 200 values
- p99.9 blurred across 50,000 values
- Median precision nobody needs
+ Simple to reason about
[*t-digest scale function]
Large in the middle, tiny at the edges
+ Extreme quantiles nearly exact
+ Same few KB of memory
- Median error slightly larger
%%

## Why the tails get the detail
This lesson's question asks why. Three reasons:
1. **The tails are what people query.** p99, p99.9 and p0.1 are what latency, risk and SLO metrics care about. The median is rarely where the problem is.
2. **Accuracy must be relative to the edge.** A quantile error of 0.001 is negligible at the median (0.500 versus 0.501 changes nothing). At p99.9 the same error turns p99.9 into p99.8 or p100, which may be a very different latency: in a typical service, the gap between the 999th and 998th slowest of 1,000 requests can be hundreds of milliseconds. To keep the error small **relative to the distance from the edge** (an error of 1% of 1 − q), the tails need much finer resolution.
3. **Tail values are spread out.** In a latency distribution, the middle values are packed close together (thousands of requests between 42 and 43 ms), so merging many of them into one centroid loses almost nothing. The slowest requests may differ by seconds, so merging two of them into one mean blurs exactly the information you wanted. A centroid holding 900 ms and 4,000 ms reports 2,450 ms, which neither request took.

## Accuracy and cost
Typical figures for the main implementation:
- **Parts-per-million accuracy** for extreme quantiles, and typically under 1,000 ppm (0.1%) error in quantile terms for middle quantiles.
- On the order of **100 to 200 ns per value added** in `MergingDigest` (it varies with hardware and settings), which allocates no memory after creation, so it can sit in a hot request path.
- A **compression** parameter trades size for accuracy: doubling δ roughly doubles the centroids and halves the error.
- A digest typically holds a few hundred centroids, a few kilobytes regardless of N.
- Compared with KLL, another mergeable quantile sketch with provable worst-case bounds, t-digest is typically smaller and more accurate at the tails in practice, while KLL's guarantees hold for any input order.

%%matrix Mergeable quantile summaries compared. All of them merge across servers; they differ in where the error is and what is guaranteed.
Summary | Error is | Tail accuracy | Merge | Guarantee
Fixed histogram | bucket width | depends on buckets | yes, add counts | yes, within a bucket
Exponential histogram | relative in value | yes, bounded relative | yes, add counts | yes
t-digest | relative to edge in rank | yes, very good | yes, re-cluster | partial, empirical
KLL | absolute in rank | partial, same as median | yes | yes, proven
HdrHistogram | relative in value | yes | yes, add counts | yes, fixed range
%%

Note the two kinds of error. **Rank error** says how far the reported quantile is from the requested one (asked for p99, got p98.9). **Value error** says how far the reported number is from the true value (true p99 is 400 ms, got 412 ms). t-digest bounds rank error relative to the tail; exponential histograms such as DDSketch bound value error relative to the value. Both are good for latency; know which one your tool gives.

## Merging
Digests from many servers merge by pooling their centroids, sorting by mean and re-clustering under the same size limits. That is what makes global percentiles possible (lesson 10.12): each server keeps a digest per minute, a collector merges them, and p99 is read from the merged digest. Merging is not bit-for-bit lossless the way HLL's register max is, but the result stays within the same accuracy envelope, so you can merge per-minute digests into hours and hours into days. Averaging the servers' p99 values instead would be wrong, as the next lesson shows.

## Pitfalls
- **Sorted or adversarial input.** Feeding values in sorted order can degrade some implementations; the merging variant with a buffer copes well, but test with your real data order.
- **Very small N.** With a few dozen values, just keep them all. Digests shine at thousands and above.
- **Mixing compression settings** across the digests you merge makes accuracy unpredictable. Use one setting everywhere.
- **Confusing rank and value accuracy** when comparing tools or setting alert thresholds.

## In an interview
If a design needs latency percentiles across many servers or long periods, say "each server keeps a t-digest (or a histogram) per minute; we merge them centrally and read any quantile, because percentiles can't be averaged". If asked how t-digest works: sorted centroids of (mean, count); a scale function that allows big centroids in the middle and tiny ones at the tails; query by walking cumulative counts and interpolating.

> Takeaway: t-digest summarises a distribution as sorted centroids (mean and count), with a scale function that allows huge centroids in the middle and tiny ones, down to single values, at the tails. That gives parts-per-million accuracy at extreme quantiles in a few kilobytes, at a fraction of a microsecond per value, and digests merge across servers and time.

## The trap: averaging percentiles
Ten servers each report their p99 latency. The tempting global p99 is the average of the ten numbers. Dashboards do this every day, often without anyone noticing, because the query looks reasonable: `avg(http_request_duration_seconds{quantile="0.95"})` in Prometheus, or "average of p99" in a metrics UI. It is wrong. Averaging quantiles gives **statistically nonsensical values**: numbers that don't correspond to any real percentile of your traffic.

Why it is wrong:
- **Servers carry different traffic.** One server handling 90% of requests and another handling 1% count equally in an average.
- **Quantiles aren't linear.** The global p99 depends on where the slowest 1% of **all** requests lie. If one server is degraded, nearly all of the global slowest 1% may come from it; its p99 is high, the other nine are low, and their average hides the problem.
- **There is no formula** from ten p99 values to the true global p99. The information about the rest of each distribution is gone, the same non-additivity as distinct counts in lesson 10.05. Even a traffic-weighted average of p99s is wrong, because percentiles are not linear in the data.

! Example: the average hides a bad server
! Ten servers each handle 10,000 requests a minute, so 100,000 in total. Nine are healthy with p99 = 100 ms. The tenth has a slow disk: 20% of its requests take about 2 seconds, so its p99 is about 2,000 ms.
! Average of the ten p99s: (9 × 100 + 2,000) / 10 = 290 ms. Looks like a mild problem.
! True global p99: the slowest 1% of all requests is the slowest 1,000. The bad server alone has 2,000 requests at about 2 seconds, so all 1,000 of the global slowest are among them. The global p99 is about 1,900 to 2,000 ms. One user in a hundred waits two seconds, and the averaged dashboard says 290 ms.

%%bars The same traffic summarised two ways. Averaging the servers' p99s reports a number that matches no real percentile of the traffic.
9 healthy servers, p99 each | 100 | 100 ms
Bad server p99 | 2000 | 2,000 ms
Average of 10 p99s | 290 | 290 ms
*True global p99 | 1950 | about 1,950 ms
%%

! Example: the average can also cry wolf
! Now flip it. Nine servers handle 99% of traffic with p99 = 100 ms. A tenth is a canary handling 1% of traffic, and its p99 is 5,000 ms because it is cold.
! Average of p99s: (9 × 100 + 5,000) / 10 = 590 ms, which triggers an alert. True global p99: the canary's 1% of traffic includes maybe 1% slow requests, which is 0.01% of all traffic, nowhere near the slowest 1%. The global p99 is still about 100 ms. The average is wrong in both directions.

## What to aggregate instead: things that add
The fix is a general principle: **ship additive data, combine it, then compute the quantile once.** Counts add. Sums add. Bucket counts add. Sketches merge. Percentiles do neither.

Prometheus offers two metric types for latency, and the difference is exactly this:

| | Histogram | Summary |
| What the client exports | Counts per bucket (`le` = less than or equal), plus `_sum` and `_count` | Pre-computed quantiles, plus `_sum` and `_count` |
| Client cost | Cheap counter increments | Relatively expensive streaming quantile calculation |
| Quantile computed | On the server, at query time, any quantile | In the client, fixed quantiles and window chosen up front |
| Error | Limited by bucket width | Configurable, usually very low, but per instance |
| Aggregation across instances | Yes: bucket counts add | **No** |

A histogram bucket `http_request_duration_seconds_bucket{le="0.3"}` is a counter of how many requests took 0.3 seconds or less since the process started. It is cumulative: the `le="0.5"` bucket includes everything in `le="0.3"`. Because each bucket is a plain counter, the same bucket on 40 servers can be summed to get the fleet-wide count.

With histograms, the global p95 across replicas is:

`histogram_quantile(0.95, sum by (le) (rate(http_request_duration_seconds_bucket[5m])))`

Read it inside out. `rate(...[5m])` turns each server's ever-growing counters into requests per second over the last 5 minutes, per bucket. `sum by (le)` adds the same bucket across every server, giving one fleet-wide histogram. Only then does `histogram_quantile` estimate the 0.95 quantile from it.

%%flow Correct aggregation: sum the additive bucket counts across servers first, then compute the percentile once from the combined histogram.
10 servers: bucket counts -(rate, then sum by le)-> *Global histogram -(histogram_quantile 0.99)-> Global p99
%%

%%matrix What you can do with each kind of latency data once it leaves the server.
Data shipped | Sum across servers | Roll up over time | Any quantile later | Cost per request
Raw latencies | yes | yes | yes | huge, store everything
Per-server p99 | no | no | no | tiny
Histogram buckets | yes | yes | partial, bucket-limited | tiny
t-digest or DDSketch | yes, merge | yes, merge | yes | small
Mean only | partial, weight by count | partial | no | tiny
%%

## How histogram_quantile estimates
`histogram_quantile` finds the bucket containing the target rank and **interpolates linearly** inside it, assuming values are spread evenly within the bucket.

! Example: computing p95 from buckets by hand
! The summed per-second rates are: le 0.1 = 9,000; le 0.2 = 9,600; le 0.3 = 9,950; le +Inf = 10,000. So 10,000 requests per second in total.
! p95 is rank 0.95 × 10,000 = 9,500. That falls in the bucket from 0.1 to 0.2 seconds, which holds 9,600 − 9,000 = 600 requests per second, and rank 9,500 is 500 into it.
! Linear interpolation: 0.1 + (500 / 600) × (0.2 − 0.1) = 0.183 seconds. Prometheus reports p95 = 183 ms. The real p95 could be anywhere between 100 and 200 ms; 183 assumes the 600 requests are evenly spread across that bucket.

## The price of buckets
So the error is bounded by the bucket's width, and badly placed buckets produce misleading answers. An example with an SLO of p95 under 300 ms:
- Requests actually cluster at **220 ms**. A classic histogram with a 200 to 300 ms bucket estimates p95 as **295 ms**, making a healthy service look close to breaching its SLO.
- A **native histogram** (fine exponential buckets, each about 1.09 times the last) puts the value in a 210 to 229 ms bucket and estimates **228 ms**.
- After a change shifts latencies to 320 ms, the native histogram says 323 ms, while a classic 300 to 450 ms bucket says 443 ms.

%%bars Estimated p95 for requests that really cluster at 220 ms: wide classic buckets push the estimate towards the bucket's upper edge, while fine exponential buckets stay close.
True latency | 220 | 220 ms
*Native histogram estimate | 228 | 228 ms
Classic bucket 200 to 300 | 295 | 295 ms
%%

Hence the advice: choose bucket boundaries around your SLO thresholds (for example a boundary at exactly 0.3 s), or use native histograms, whose exponential buckets give bounded **relative** error everywhere. OpenTelemetry's exponential histograms map directly onto them. With a boundary at the SLO, the question that matters most, "what fraction of requests met the SLO?", is answered exactly: it is `le="0.3"` divided by the total, with no interpolation.

Each bucket is a separate time series per label combination, so buckets aren't free. 12 buckets × 40 pods × 20 endpoints × 5 status codes is 48,000 series for one metric. Native histograms store the populated buckets compactly in one series, which is another reason they exist.

Averages are still easy: `rate(_sum) / rate(_count)` gives mean latency, and both series add across instances. The mean is the one statistic you can combine correctly from per-server data, as long as you combine the sums and counts rather than averaging per-server means.

## Other mergeable options
The same principle covers the sketches in this module: ship a **t-digest** (lesson 10.11), **DDSketch** or **HdrHistogram** per server per interval, merge them centrally, then read any quantile. DDSketch uses logarithmically sized buckets so every value is within a chosen relative error (say 1%) and merging is just adding bucket counts. HdrHistogram does the same over a fixed value range with configurable precision. Prometheus histograms are the simplest bucketed version of this idea; native and OpenTelemetry exponential histograms are essentially DDSketch-style buckets.

### Time matters too
The same trap appears across time. "Average the p99 of each minute to get the hour's p99" is wrong for the same reason: a bad minute with 10 times the traffic counts the same as a quiet one. Store histograms or sketches per minute and merge them for the hour.

## Common mistakes
- **`avg()` over a quantile label.** Always wrong for combining instances; at best a rough "typical instance" view.
- **Using Summaries for anything you'll aggregate.** Summaries are fine for a single process; they can't be combined across replicas.
- **Default buckets.** Library defaults (5 ms to 10 s, roughly doubling) rarely match your SLO; add a boundary at the threshold you alert on.
- **`sum` without `by (le)`.** Summing away the `le` label merges all buckets into one number and destroys the histogram.
- **Forgetting `rate` before `sum`.** Summing raw cumulative counters across pods that restarted at different times gives garbage; take the rate per series first.

! Example: an SLO dashboard
! Each of 40 API pods exports `http_request_duration_seconds_bucket` with boundaries 0.05, 0.1, 0.2, 0.3, 0.5, 1, 2.5 (0.3 deliberately included because the SLO is p95 under 300 ms).
! Global p99: `histogram_quantile(0.99, sum by (le) (rate(http_request_duration_seconds_bucket[5m])))`.
! To spot a bad pod: the same query with `sum by (le, pod)`, which gives one p99 per pod. The fleet line and the pod lines are both correct; only averaging the pod lines would be wrong.
! SLO compliance: `sum(rate(..._bucket{le="0.3"}[5m])) / sum(rate(..._count[5m]))`, the fraction of requests under 300 ms. It is exact, because 0.3 is a bucket boundary: if it reads 0.962, then 96.2% of requests met the target and the SLO (95%) is met.

## In an interview
When you add monitoring to a design, say "each service exports latency histograms (or sketches); we aggregate bucket counts across instances and compute percentiles centrally, never averaging per-instance percentiles". If asked why, give the bad-server example in one sentence: the global slowest 1% can all come from one server, so the average of ten p99s can be several times too low.

> Takeaway: percentiles don't average, because each server's p99 hides its traffic volume and the shape of its distribution. Aggregate additive data instead: sum histogram bucket counts (or merge sketches such as t-digest or DDSketch) across servers and across time, then compute the quantile once. Bucket placement determines accuracy, so put boundaries at your SLO thresholds or use native exponential histograms.

?? A p99 is a single point of each server's distribution, not something that adds. Servers handle different amounts of traffic, and the global p99 is determined by where the slowest 1% of all requests fall, which may be almost entirely on one degraded server: with nine servers at 100 ms and one at 2 s handling a tenth of traffic, the average of p99s is 290 ms while the true global p99 is close to 2 s. No formula recovers the global value from ten percentiles, because the rest of each distribution has been thrown away. Instead, ship additive data such as histogram bucket counts or mergeable sketches like t-digest, sum or merge them across servers, and compute the global p99 once from the combined distribution.

## The problem
A live stream with 1 million viewers receives 10,000 reactions (hearts, likes, laughing faces) per second. Each viewer should see the reactions float up the screen more or less as they happen, and see a running total.

The naive design treats a reaction like a chat message: when someone taps a heart, send it to every viewer. That's 10,000 × 1,000,000 = **10 billion messages per second**. At even 50 bytes per message, that's 500 GB per second of outbound traffic, 4 terabits per second, for one stream. No system should do that, and it would be pointless anyway: no viewer can perceive 10,000 individual hearts per second. A phone screen shows maybe a few dozen floating hearts at a time.

This lesson pulls together the module's counting ideas (batching in lesson 10.01, time buckets in 10.06, merging partial counts in 10.05 and 10.09) and the delivery ideas of Module 11 into one design.

%%bars Messages per second delivered to viewers for one stream with a million viewers and 10,000 reactions per second.
Forward every reaction | 10000000000 | 10 billion/s
Aggregate every 100 ms | 10000000 | 10 million/s
*Aggregate every 200 ms | 5000000 | 5 million/s
Aggregate every 1 s | 1000000 | 1 million/s
%%

## Delivery: what live comments teach
Live comments on a video are the closer cousin of this problem and its design is the base we build on. Requirements: millions of concurrent live videos, thousands of comments per second per video, eventual consistency, and under **200 ms** end-to-end delivery. The key decisions:
- **Polling fails.** To get under 200 ms, each viewer would have to poll every 100 ms or so. A million viewers polling 10 times a second is 10 million requests per second, almost all returning "nothing new", crushing the database.
- **Server-Sent Events over WebSockets.** Viewers mostly read. SSE is a one-way server push over plain HTTP (lesson 11.02); writes (posting a comment or a reaction) go through ordinary HTTP POSTs. A two-way WebSocket channel adds connection complexity that this read-heavy pattern doesn't need.
- **Pub/sub between servers.** Viewers are spread over many realtime servers, each holding tens of thousands of open SSE connections. When a comment is created, it is published to a channel; servers subscribed to that channel forward it to their viewers. Channels are chosen by `hash(liveVideoId) % N` so a server only receives traffic for videos its viewers are watching. Redis pub/sub is a common choice because it is low latency, and its fire-and-forget delivery is acceptable since comments are also stored.
- **Co-locate viewers.** An L7 load balancer uses consistent hashing on the video ID so viewers of the same video tend to land on the same realtime servers, minimising how many servers must subscribe to each video's channel.
- **Mega-streams.** For hundreds of millions of viewers, comments are **sampled** (from 50% down to 1 to 2% as velocity rises) or delivered as periodic snapshots through a CDN (lesson 11.10).

## Aggregate reactions instead of forwarding them
Reactions differ from comments in one crucial way: they are **countable and interchangeable**. A heart from user A and a heart from user B look identical to other viewers. A comment's content matters; a heart's identity doesn't. So the system should forward **totals per time slice**, not events. "312 hearts and 40 wows in the last 200 ms" carries everything a viewer's screen needs.

%%compare Forwarding every reaction versus forwarding a count per tick. The aggregate design's cost depends on viewers and tick rate, not on how many people tap.
[Forward each reaction]
Tap -(publish)-> Every server -> Every viewer
- 10 billion messages per second
- Cost grows with reactions times viewers
- Phones drown in events they can't draw
[*Count per 200 ms tick]
Taps -(sum per tick)-> One update -> Every viewer
+ 5 updates per second per viewer
+ Cost independent of reaction rate
+ Same animation on screen
- Up to one tick of delay
%%

%%flow Reactions aggregated twice: ingest servers count per 200 ms, a per-video aggregator merges the partials, and each viewer gets one small update per tick.
Viewers send reactions, 10k per s -(POST)-> Ingest servers: count per type per 200 ms -(partial counts)-> *Aggregator for video -(5 updates per s)-> Pub/sub channel -> Realtime servers -(SSE)-> 1M viewers
%%

1. **Ingest.** Reactions arrive as small HTTP POSTs (or as messages on an existing connection) to stateless ingest servers behind a load balancer. Each server keeps in-memory counters per (video, reaction type), and every 200 ms emits a partial count such as `{video: v1, heart: 312, wow: 40}` instead of the 352 individual events.
2. **Aggregate.** Partial counts for the video go to one aggregator, for example through Kafka partitioned by video ID so all partials for v1 reach the same consumer. It sums the partials into a per-tick total and a running total (lessons 10.01 and 10.06). Output: one message per tick, regardless of reaction volume.
3. **Fan out.** The aggregator publishes one update per tick to the video's pub/sub channel. Each realtime server holding viewers of that video receives it once and pushes it to its local viewers over SSE.
4. **Render.** The client animates "312 hearts in the last 200 ms" as a burst of floating hearts, perhaps capped at 20 drawn hearts with the rest implied by the counter. The visual effect is the same as individual events.

### Two levels of aggregation
Why aggregate at both the ingest servers and the aggregator? Because each level shrinks traffic by a large factor. 10,000 reactions per second from 20 ingest servers become 20 × 5 = 100 partial-count messages per second to the aggregator, instead of 10,000. The aggregator then turns 100 messages per second into 5. This is the same tree-shaped combining you saw for top-K merging in lesson 10.09, and it only works because counts are additive.

%%tree The fan-out tree for one tick: one aggregate message becomes 500 server deliveries and then a million SSE frames, with no node sending more than a few thousand.

  Pub/sub channel v1 | delivers to subscribers
    Realtime server 1 | 2,000 viewers
      Viewer SSE frames | 2,000 per tick
    Realtime server 2 | 2,000 viewers
    *Realtime server 500 | 2,000 viewers
%%

## The numbers
| Design | Messages per second to viewers |
| Forward every reaction | 10,000 × 1,000,000 = 10 billion |
| One aggregate update every 200 ms | 5 × 1,000,000 = 5 million |

The aggregate approach is independent of reaction volume: 10,000 or 1 million reactions per second still produce 5 updates per second per viewer. Between servers, it's 5 messages per second per video per realtime server.

! Example: sizing the fan-out
! 1 million viewers on 500 realtime servers, 2,000 viewers each (servers can hold far more SSE connections, but the video's viewers are spread out for resilience).
! Pub/sub: the aggregator publishes 5 messages per second; the channel delivers 5 × 500 = 2,500 messages per second in total. Trivial for Redis.
! Each realtime server receives 5 messages per second and writes 5 × 2,000 = 10,000 small SSE frames per second, which is ordinary.
! Bandwidth per viewer: an update like `{"t":1731440400200,"heart":312,"wow":40,"total":4812330}` is about 60 bytes plus SSE framing, say 80 bytes. Five per second is 400 bytes per second, about 3 kilobits per second. Negligible next to the video itself, which is several megabits per second.

## Details that matter
- **Write path protection.** 10,000 POSTs per second is easy to spread over stateless servers. Rate-limit per user (nobody needs to send 100 hearts a second; cap at, say, 10 per second and count the rest as one), and **drop rather than queue** under overload. A lost heart doesn't matter; a backlog of hearts arriving 30 seconds late looks broken.
- **Exact totals?** If the final count matters (it's shown afterwards or stored), persist the aggregator's per-tick totals to a counter store with batching (lesson 10.01). If not, the in-memory aggregate is enough. Duplicates from retries barely matter for hearts, unlike ad clicks (lesson 10.03).
- **Personal feedback.** The user who tapped sees their own heart instantly, rendered locally, without waiting for the round trip. Otherwise the button feels laggy, and the 200 ms tick plus network makes it worse.
- **Hot videos.** One aggregator per video can become a hotspot for the biggest streams. Shard the ingest stream with random suffixes (`v1:0` to `v1:15`) so 16 aggregators each sum a share, and let a final step sum the 16 totals each tick, as in lessons 10.03 and 10.09.
- **Clock and ordering.** Ticks are numbered by the aggregator. A client that receives tick 1,042 after tick 1,043 (rare, but possible during a reconnect) can simply drop it: for an animation, old data is useless.
- **Late joiners and reconnects.** A client that connects or reconnects needs the running total, not the history. The first SSE message sends the current total, then deltas follow.
- **Mega-streams.** Lower the tick rate (1 per second instead of 5), or move to CDN-delivered snapshots that clients fetch every second from an edge cache.

## Walking one tick through the system
%%seq One 200 ms tick: ingest servers send partial counts, the aggregator sums them and publishes once, and each realtime server pushes the update to its viewers.
Viewers > Ingest servers : 2,200 reaction POSTs during the tick
Ingest servers > Ingest servers : count per video and type
Ingest servers > Aggregator : 20 partials, e.g. heart 103, wow 7
Aggregator > Aggregator : sum: heart 2,070, wow 130
Aggregator > Pub/sub : publish tick 1,042 to channel v1
Pub/sub -> Realtime servers : 1 message to each of 500
Realtime servers -> Viewers : SSE frame to each of 2,000 viewers
Viewers > Viewers : animate a burst sized to 2,070
%%

! Example: one tick
! Between 20:00:00.000 and 20:00:00.200, 2,070 hearts and 130 "wow" reactions arrive across 20 ingest servers, about 110 per server. At 20:00:00.200, each server sends its partial counts to the video's aggregator, which sums to `{tick: 1042, heart: 2070, wow: 130, totalHearts: 4812330}` and publishes it once.
! 500 realtime servers each receive that one message and push it to their 2,000 viewers. Each phone draws a burst of hearts sized to 2,070 (capped at, say, 20 visible hearts, with intensity scaled), and updates the total.
! A viewer on a train loses the connection for 8 seconds. When SSE reconnects, the server sends the latest total and the client skips the 40 ticks it missed. Nobody notices; there is nothing to catch up on.

## Common mistakes
- **Treating reactions as messages.** It works in a demo with 50 viewers and fails catastrophically at scale.
- **One message per reaction to the aggregator.** Without ingest-side batching, the aggregator becomes the hot spot at 10,000 messages per second per video.
- **Queueing under overload.** Late reactions are worse than dropped ones.
- **Waiting for the server to show my own heart.** Render locally first.
- **Storing every reaction event to show a total.** Store per-tick totals or a counter; keep raw events only if analytics needs them (lesson 10.07).

## In an interview
Lead with the arithmetic: "forwarding every reaction is 10 billion messages per second; the client can't use them anyway". Then: "reactions are interchangeable, so I'll count them in 200 ms ticks on ingest servers, merge per video, and push one small update per tick through pub/sub to realtime servers that hold the video's viewers over SSE". Close with the numbers: 5 updates per second per viewer, independent of reaction volume, and the knobs for bigger streams (tick rate, sharded aggregators, CDN snapshots).

> Takeaway: don't fan out individual reactions. Count them on ingest servers in short time slices, merge per video, and push one small aggregate update per tick through pub/sub to the realtime servers holding the video's viewers over SSE. Fan-out becomes proportional to viewers × tick rate, not viewers × reactions, and each viewer receives a few hundred bytes per second whatever the reaction rate.
