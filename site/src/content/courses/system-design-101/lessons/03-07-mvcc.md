## Many versions instead of many locks

The simplest way to isolate transactions is with locks: a reader locks a row so nobody changes it under them, a writer locks it so nobody reads half a change. It works, but readers and writers queue behind each other. A ten-minute report would block every update to the rows it touches.

**MVCC** (multiversion concurrency control) takes a different route. Each transaction (or each statement, depending on the isolation level) sees a **snapshot**: the database as it was at one moment. When a row is updated, the database does not overwrite it. It writes a **new version** of the row and keeps the old one for any transaction whose snapshot still needs it. Postgres, MySQL's InnoDB, Oracle, SQL Server (in snapshot mode) and most modern databases use some form of MVCC.

The headline benefit: **reading never blocks writing, and writing never blocks reading.** A long report keeps reading its consistent snapshot while users update the same rows. Writers still block other writers on the same row (two people cannot both change row 7 at once), but that is far rarer.

## How visibility works in Postgres

Every row version (Postgres calls it a **tuple**) carries two hidden fields:

- `xmin`: the ID of the transaction that created this version.
- `xmax`: the ID of the transaction that deleted or replaced it, or zero if it is still current.

Transaction IDs (**XIDs**) are handed out from a counter as transactions start writing. A **snapshot** records three things: the lowest XID still running, the next XID to be assigned, and the list of XIDs running at that moment. With that, a transaction can decide for any tuple: **a version is visible to me if its creator committed before my snapshot, and its deleter (if any) had not committed before my snapshot.**

An `UPDATE` is therefore "set `xmax` on the old version, and insert a new version with `xmin` = my XID". A `DELETE` just sets `xmax`. Nothing is physically removed at that point.

In read committed, a new snapshot is taken for each statement. In repeatable read and serializable, one snapshot is taken at the first statement and kept for the whole transaction (lesson 03.06).

~~~dg-timeline One row's versions over time, and which version each reader sees from its own snapshot.
[Writers] t1 | Tx 100 inserts row v1, price 10
[Readers] t2 | Report Tx 150 takes snapshot
[Writers] t3 | Tx 200 updates: v1 gets xmax 200, v2 created with price 12
[Writers] t4 | *Tx 200 commits
[Readers] t5 | Report Tx 150 reads row: sees v1, price 10
[Readers] t6 | New Tx 300 reads row: sees v2, price 12
~~~

~~~dg-seq Readers and writers do not block each other: each transaction reads from its own snapshot.
Tx A reader > Table : take snapshot
Tx B writer > Table : UPDATE row, creates v2
Tx A reader > Table : read row
Table -> Tx A reader : v1, from its snapshot
Tx B writer > Table : COMMIT
Tx C new > Table : read row
Table -> Tx C new : v2
~~~

## Two ways to store old versions

Databases differ in **where** the old versions live, and this decides what cleanup they need.

**Postgres** stores every version in the table itself. The old and new versions are both full tuples in the heap. Indexes point to tuples, so a new version usually needs new index entries too. One optimisation, **HOT** (heap-only tuple) updates, avoids that: if no indexed column changed and the new version fits on the same page, the indexes are not touched and the old tuple points to the new one.

**InnoDB and Oracle** update the row **in place** and copy the old values into a separate **undo log**. A reader that needs an older version follows a chain of undo records backwards to rebuild it. The table stays compact, but long-running readers make the undo log grow, and reading old versions gets slower the further back you go.

~~~dg-compare Postgres keeps old versions in the table; InnoDB updates in place and keeps old values in an undo log.
[Postgres: versions in heap]
UPDATE -> New tuple in table -> Old tuple marked dead
+ Rollback is instant
+ Old versions read directly
- Dead tuples bloat table and indexes
- Needs VACUUM
[InnoDB: undo log]
UPDATE -> Row changed in place -> Old values to undo log
+ Table stays compact
- Rollback must undo work
- Long readers grow undo log
- Purge thread cleans undo
~~~

## The catch: dead rows pile up

In Postgres, once no running transaction can possibly see an old version, it is **dead**. But it still occupies space in the table page and in every index that points to it. A table with heavy updates accumulates dead tuples: this is called **bloat**. Scans slow down because they read pages full of dead rows, and indexes grow because they hold entries for versions nobody can see. A table updated 10 times per row can, without cleanup, be mostly dead space.

~~~dg-state The life of a Postgres row version, from insert to reuse of its space or permanent freezing.
[*] -> Live : INSERT commits
Live -> Superseded : UPDATE or DELETE sets xmax
Superseded -> Dead : no snapshot can see it
Dead -> *Space reusable : VACUUM removes it
Live -> Frozen : VACUUM freezes old xmin
Frozen -> Superseded : later UPDATE or DELETE
~~~

## VACUUM's four jobs

This is why Postgres needs `VACUUM`. It has four jobs.

1. **Reclaim space.** Vacuum scans pages, removes dead tuples and their index entries, and records the freed space in the **free space map** so new rows can reuse it. Plain `VACUUM` runs alongside normal traffic and takes only a light lock, but it usually does not shrink the file on disk; it makes space reusable inside it. `VACUUM FULL` rewrites the table compactly and returns space to the operating system, but it takes an `ACCESS EXCLUSIVE` lock (blocking all reads and writes) and needs disk room for a full copy, so it is rarely the right tool on a live system.
2. **Update planner statistics.** `VACUUM ANALYZE`, or autovacuum's analyse step, refreshes the statistics the planner uses (lesson 03.05).
3. **Update the visibility map.** This is a bitmap with one bit per page meaning "every tuple on this page is visible to every transaction". Vacuum skips such pages next time, and **index-only scans** can avoid visiting the table for them. A table that is never vacuumed cannot use index-only scans effectively.
4. **Prevent transaction ID wraparound.** This is the job that can take a database down.

### Transaction ID wraparound

XIDs are 32-bit, so there are about 4.2 billion of them, and the counter wraps around. Postgres compares XIDs in a **circle**: for any XID, about 2.1 billion are treated as "in the past" and 2.1 billion as "in the future". If a row's `xmin` were left alone for more than 2.1 billion transactions, it would suddenly appear to be in the future, and the row would vanish from every query.

Vacuum prevents that by **freezing** old tuples: marking them as created "infinitely long ago", visible to everyone forever, regardless of the counter. As long as every table is frozen faster than XIDs are consumed, wraparound never matters.

If freezing falls behind, Postgres defends the data. It starts logging warnings when about 40 million XIDs remain before the danger point. With about 3 million left, it refuses to start any new transaction that would assign an XID, effectively stopping all writes until an administrator runs a vacuum. A busy system consuming 20,000 XIDs per second burns through 2 billion in a little over a day, so this is not a theoretical risk.

## Autovacuum

The **autovacuum** daemon is on by default and should stay on. It vacuums a table when its dead tuples exceed a threshold: by default 50 rows plus 20% of the table (`autovacuum_vacuum_scale_factor = 0.2`). It also forces an **anti-wraparound vacuum** on any table whose oldest unfrozen XID is more than 200 million transactions old (`autovacuum_freeze_max_age`), even if nothing else triggers it.

For big tables, 20% is far too lazy: a 500-million-row table would accumulate 100 million dead tuples before cleanup starts. Teams lower the scale factor per table (to 0.01 or less) and raise autovacuum's I/O budget so it keeps up.

### What stops vacuum working

Vacuum can only remove a version once **no snapshot anywhere** might still see it. The oldest snapshot in the system sets that horizon. Anything that holds an old snapshot pins every version created since:

- **Long-running transactions**, such as an analytics query that runs for 3 hours.
- **Idle-in-transaction sessions**: a connection that ran `BEGIN` and a query, then stopped. The transaction stays open indefinitely.
- **Stale replication slots**, where a replica or a change-data-capture consumer has disconnected but the slot remains, and old **prepared transactions** from two-phase commit.
- **Hot standby feedback** from a replica running long queries, which asks the primary to keep versions those queries need.

This is not theoretical. Notion's vacuum process was stalling on its monolithic Postgres, and transaction ID wraparound became an existential risk, which was one of the main pushes towards sharding (lesson 03.10).

<div class="lab">Worked example</div>

**the forgotten transaction**

A developer opens a `psql` session at 12:00, runs `BEGIN` and a `SELECT`, and goes to lunch. Their snapshot now pins every row version created after 12:00.

The orders table receives 5 million updates over the next 3 hours. Vacuum runs repeatedly but cannot remove any of the 5 million old versions, because the forgotten snapshot might need them.

At about 150 bytes per tuple plus index entries, that is roughly 1.5 GB of extra dead data. Queries that scanned 2 GB now scan 3.5 GB and slow down by about 75%. Index-only scans stop helping because the visibility map has few all-visible pages.

Setting `idle_in_transaction_session_timeout = '5min'` would have killed the session at 12:05, and vacuum would have kept up. Monitoring the age of the oldest transaction (`pg_stat_activity.xact_start`) catches the rest.

**how fast are you approaching wraparound?**

A database averages 5,000 write transactions per second. That is 432 million XIDs per day.

Autovacuum forces a freeze on a table once its oldest XID is 200 million old, so every busy table must be fully freeze-vacuumed roughly every 11 hours.

The largest table is 2 TB. If vacuum reads it at 100 MB/s, one pass takes about 5.8 hours. That fits, but with little margin. If a long transaction blocks freezing for 4 days, the oldest XID reaches about 1.7 billion old, uncomfortably close to the 2.1 billion limit. This is the arithmetic that should set alerting thresholds.

## Common mistakes

- **Turning autovacuum off** because it "uses I/O". The bloat and wraparound risk are far worse.
- **Leaving default thresholds on huge tables.** 20% of a billion rows is 200 million dead tuples.
- **Allowing long or idle transactions.** Set statement and idle-in-transaction timeouts.
- **Reaching for VACUUM FULL in production.** It locks the table for the whole rewrite; tools that rebuild tables online (such as `pg_repack`) are safer.
- **Forgetting replication slots.** An abandoned slot holds back cleanup and fills the disk with WAL.

## In an interview

If asked about Postgres at high write rates, mention MVCC bloat and vacuum unprompted: heavy updates create dead tuples, autovacuum must be tuned for large tables, long transactions block cleanup, and wraparound is the failure mode that stops writes. It shows you know how the database behaves under load, not just how to query it.
