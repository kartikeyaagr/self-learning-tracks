## Three common patterns

| Pattern | What repeats | Typical hit rate |
| --- | --- | --- |
| Shared system prompt | the first 500 to 3,000 tokens of every request | high |
| Multi-turn chat | the whole history before the newest message | very high, if turns reach the same replica |
| RAG | popular documents | depends on ordering and position |

Each has its own conditions for working well.

## Shared system prompts

This is the easiest case. Every request begins with the same tokens, and those blocks are almost always in use by some running request, so they are rarely evicted. Make sure the system prompt is byte-identical across requests. Keep per-user details after it.

## Multi-turn conversations

Turn n's prompt is turn n − 1's prompt, plus the assistant's reply, plus the new user message. The assistant's reply was generated by this engine, so its K and V were written to the cache during decode. If those blocks survive until the user's next message, the whole history is a cache hit, and only the new message needs prefill.

<div class="ex">
<div class="lab">Worked example</div>

**the gain over a long conversation**

A conversation reaches 10 turns, with a 1,500-token system prompt, 100-token user messages and 300-token replies.

Turn 10's prompt is about 1,500 + 9 × 400 + 100 = 5,200 tokens. Without caching, the conversation's turns prefill 1,600 + 2,000 + ... + 5,200 ≈ 34,000 tokens in total.

With caching, each turn prefills only its new user message plus the previous reply's partial last block, about 110 to 120 tokens. The total is about 2,700 tokens: more than 90% less prefill.

TTFT for turn 10 falls from about 150 ms to about 15 ms.

</div>

Three things can break this:

- **Time between turns.** Users pause for seconds or minutes. Under load, the conversation's blocks may be evicted before the next turn.
- **Template changes.** Some chat templates render earlier turns differently once a new one arrives, for example by removing reasoning text from previous assistant messages. The history no longer matches exactly.
- **Trimming.** When a conversation exceeds the context window and the oldest turns are dropped, every token after the cut shifts position. Nothing after the system prompt matches any more.

## RAG documents

RAG prompts look like: system prompt, retrieved documents, question. The system prompt is reused easily. The documents are reused only when the same documents appear in the same order at the same position, after an identical prefix.

- **Sort retrieved documents by a stable key**, such as document id, instead of by relevance score, which changes per query. Most models are not very sensitive to document order.
- **Put popular documents first.** If one document is retrieved for half of all questions, placing it right after the system prompt makes it part of a shared prefix.
- **Accept the limits.** If the first retrieved document differs, nothing after it matches. Standard engines need exact prefixes. Research systems explore position-independent caching of documents, but it changes outputs slightly and is not standard.

## Routing decides whether the cache is reachable

With several replicas, each has its own cache. A random or round-robin load balancer sends turn 2 of a conversation to a different replica from turn 1 most of the time. With 8 replicas, about 7 times in 8.

- **Session-sticky routing** sends all turns of a conversation to the same replica.
- **Prefix-aware routing** sends each request to the replica most likely to have its prefix cached, balanced against load. Module 22 covers it in depth.

Without one of these, multi-turn caching gains mostly disappear in a fleet.

## A checklist for reusable prompts

- Stable content first, variable content last.
- Deterministic rendering: identical whitespace, key order and formatting.
- No timestamps, request ids or experiment ids near the start.
- A trimming strategy that keeps the system prompt and drops whole old turns, accepting the miss when it happens, rather than editing old turns.
- Routing that keeps conversations together.
