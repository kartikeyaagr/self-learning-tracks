Real code chains them: load data, convert it, normalise it, batch it, run it through layers, compute a loss. This lesson walks through one small example and tracks the <strong>shape</strong> at every step, which is the single most useful habit for debugging.</p>\n<h3>The task</h3>\n<p>Classify 200 house listings as &quot;expensive&quot; or not from 3 features: area (m²), rooms, age (years).</p>\n<h3>Step by step, with shapes</h3>\n<pre class=\"code\"><code class=\"language-python\">import torch, torch.nn.functional as F\ntorch.manual_seed(0)\n</code></pre>\n<p><strong>1. Raw data to tensors.</strong></p>\n<pre class=\"code\"><code class=\"language-python\">X = torch.tensor(raw_features, dtype=torch.float32)   # (200, 3)\ny = torch.tensor(raw_labels)                           # (200,)  int64, values 0 or 1\n</code></pre>\n<p><strong>2. Normalise each feature</strong> (lesson 02.03 broadcasting). Area is in the hundreds and rooms are under 10; without this, area would dominate.</p>\n<pre class=\"code\"><code class=\"language-python\">mu, sd = X.mean(0), X.std(0)       # (3,), (3,)\nX = (X - mu) / sd                  # (200, 3) with (3,) -&gt; (200, 3)\n</code></pre>\n<p><strong>3. Split train and test</strong> with indexing (lesson 03.05).</p>\n<pre class=\"code\"><code class=\"language-python\">perm = torch.randperm(200)\ntr, te = perm[:160], perm[160:]\nXtr, ytr, Xte, yte = X[tr], y[tr], X[te], y[te]    # (160, 3) (160,) (40, 3) (40,)\n</code></pre>\n<p><strong>4. Parameters</strong> (lessons 03.01, 03.07).</p>\n<pre class=\"code\"><code class=\"language-python\">W = (torch.randn(3, 2) * (1/3) ** 0.5).requires_grad_()   # (3, 2)\nb = torch.zeros(2, requires_grad=True)                    # (2,)\n</code></pre>\n<p><strong>5. Gradients and an update.</strong></p>\n<pre class=\"code\"><code class=\"language-python\">loss.backward()                  # fills W.grad (3, 2) and b.grad (2,)\nwith torch.no_grad():\n    W -= 0.1 * W.grad; b -= 0.1 * b.grad\n    W.grad.zero_(); b.grad.zero_()\n</code></pre>\n<p><strong>7. Evaluate.</strong></p>\n<pre class=\"code\"><code class=\"language-python\">with torch.no_grad():\n    pred = (Xte @ W + b).argmax(1)            # (40,)\n    acc = (pred == yte).float().mean()        # scalar\n</code></pre>\n<h3>The shape trace</h3>\n<div class=\"tbl\"><table>\n<thead>\n<tr>\n<th>step</th>\n<th>tensor</th>\n<th>shape</th>\n</tr>\n</thead>\n<tbody><tr>\n<td>data</td>\n<td><code>X</code>, <code>y</code></td>\n<td><code>(200, 3)</code>, <code>(200,)</code></td>\n</tr>\n<tr>\n<td>stats</td>\n<td><code>mu</code>, <code>sd</code></td>\n<td><code>(3,)</code></td>\n</tr>\n<tr>\n<td>batch</td>\n<td><code>xb</code>, <code>yb</code></td>\n<td><code>(32, 3)</code>, <code>(32,)</code></td>\n</tr>\n<tr>\n<td>weights</td>\n<td><code>W</code>, <code>b</code></td>\n<td><code>(3, 2)</code>, <code>(2,)</code></td>\n</tr>\n<tr>\n<td>output</td>\n<td><code>logits</code></td>\n<td><code>(32, 2)</code></td>\n</tr>\n<tr>\n<td>loss</td>\n<td><code>loss</code></td>\n<td><code>()</code></td>\n</tr>\n</tbody></table></div>\n<p>If you can write a table like this for any model, you understand its code.</p>\n<h3>Habits that prevent bugs</h3>\n<ul>\n<li><strong>Print shapes</strong> when anything looks off: <code>print(x.shape, x.dtype, x.device)</code>.</li>\n<li><strong>Assert</strong> the shapes you rely on: <code>assert logits.shape == (xb.size(0), 2)</code>.</li>\n<li><strong>Overfit one batch first.</strong> If the loss on 32 examples will not go near zero, there is a bug.</li>\n<li><strong>Use <code>torch.no_grad()</code></strong> for evaluation, so no gradient memory is wasted.</li>\n<li><strong>Normalise with training statistics only.</strong> Compute <code>mu</code> and <code>sd</code> on the training split and reuse them on the test split. They differ in how the graph is recorded.</p>\n<p><strong>PyTorch</strong> records operations on any tensor with <code>requires_grad=True</code> as they execute. Calling <code>loss.backward()</code> walks that graph and <strong>accumulates</strong> into <code>.grad</code>. You must zero gradients between steps (<code>optimizer.zero_grad()</code>), and the accumulation is exactly what makes gradient accumulation across micro-batches work.</p>\n<p>Goodfellow et al. §6.5 describe what is being built: a computational graph whose nodes are operations, plus, for each operation, a rule (<code>bprop</code>) that maps the gradient of the output to gradients of the inputs. PyTorch builds this graph as a linked list of <code>grad_fn</code> objects: <code>loss.grad_fn.next_functions</code> walks backwards through it. Each node keeps the tensors it needs for its backward rule (a matmul saves both inputs; a ReLU saves a mask), which is where activation memory comes from. After <code>backward()</code> the graph is freed unless you pass <code>retain_graph=True</code>.</p>\n<p>A few behaviours follow directly from this design:</p>\n<ul>\n<li><strong>Leaves vs intermediates.</strong> Only leaf tensors (parameters, or tensors you created with <code>requires_grad=True</code>) get <code>.grad</code> populated. For an intermediate tensor call <code>.retain_grad()</code> first, or use a hook.</li>\n<li><strong>In-place operations</strong> can overwrite a tensor that a backward rule saved. PyTorch keeps a version counter on each tensor and raises &quot;one of the variables needed for gradient computation has been modified by an inplace operation&quot; rather than computing a wrong gradient.</li>\n<li><strong><code>.detach()</code></strong> returns a tensor sharing storage but cut out of the graph; <code>torch.no_grad()</code> stops recording altogether, which saves the memory of saved tensors during evaluation. <code>torch.inference_mode()</code> goes further and also skips the version counters.</li>\n<li><strong>Higher-order gradients</strong> work by building a graph of the backward pass: <code>torch.autograd.grad(loss, params, create_graph=True)</code>. TensorFlow does the same with nested tapes. You need this for gradient penalties and some meta-learning methods.</li>\n</ul>\n<p><strong>TensorFlow</strong> records only inside a <code>tf.GradientTape</code> context. You ask the tape for gradients explicitly, and it returns them instead of storing them on variables:</p>\n<pre class=\"code\"><code class=\"language-python\"># PyTorch\nlogits = model(x)\nloss = F.cross_entropy(logits, y)\nopt.zero_grad()\nloss.backward()\nopt.step()\n\n# TensorFlow\nwith tf.GradientTape() as tape:\n    logits = model(x, training=True)\n    loss = loss_fn(y, logits)\ngrads = tape.gradient(loss, model.trainable_variables)\nopt.apply_gradients(zip(grads, model.trainable_variables))\n</code></pre>\n<p>Points that trip people up when moving between them:</p>\n<div class=\"tbl\"><table>\n<thead>\n<tr>\n<th>Topic</th>\n<th>PyTorch</th>\n<th>TensorFlow / Keras</th>\n</tr>\n</thead>\n<tbody><tr>\n<td>Train vs eval mode</td>\n<td><code>model.train()</code> / <code>model.eval()</code></td>\n<td><code>training=True/False</code> argument per call</td>\n</tr>\n<tr>\n<td>Dense weight layout</td>\n<td><code>nn.Linear.weight</code> is <code>(out, in)</code></td>\n<td><code>Dense.kernel</code> is <code>(in, out)</code></td>\n</tr>\n<tr>\n<td>Conv layout</td>\n<td><code>NCHW</code>, weight <code>(out, in, kH, kW)</code></td>\n<td><code>NHWC</code> by default, kernel <code>(kH, kW, in, out)</code></td>\n</tr>\n<tr>\n<td>Loss input</td>\n<td>logits for <code>cross_entropy</code></td>\n<td>set <code>from_logits=True</code></td>\n</tr>\n<tr>\n<td>Gradient storage</td>\n<td>accumulates in <code>.grad</code></td>\n<td>returned by <code>tape.gradient</code></td>\n</tr>\n<tr>\n<td>Disable grad</td>\n<td><code>torch.no_grad()</code></td>\n<td>compute outside the tape</td>\n</tr>\n</tbody></table></div>\n<p>The layout differences are the whole content of Exercise 3: copy a trained PyTorch CNN&#39;s weights into an equivalent Keras model and get identical outputs. You need to transpose linear kernels, permute conv kernels, and handle the flatten order (NCHW flattens channels first, NHWC flattens them last).</p>\n<h3>Model-building APIs</h3>\n<p>PyTorch has one main abstraction, <code>nn.Module</code>, with parameters as attributes and a <code>forward</code> method. Keras has three: the <code>Sequential</code> API for stacks, the functional API for DAGs, and subclassing <code>tf.keras.Model</code> (or <code>tf.Module</code>) for anything custom. d2l.ai shows every chapter in both, and reading the two tabs side by side is the fastest way to learn the mapping.</p>\n</section><section class=\"art extra\"><div class=\"xlab\">Extra · goes beyond the Fanout lesson</div><h2>Graphs and compilation</h2><p class=\"cite\"><span class=\"lab\">Based on</span> TensorFlow guide: Better performance with tf.function · PyTorch torch.compile docs · Horace He, Making Deep Learning Go Brrrr · d2l.ai §13.1-13.2 (hybrid programming, asynchronous computation) · Fanout 04.19</p><p>Eager execution runs one Python operation at a time.
