Datasets change: labels are fixed, rows are added, bugs are cleaned. DVC (Data Version Control) lets Git track <em>which</em> data version goes with each commit, while the large files themselves live in cheap storage. Checking out an old commit then gives you the matching data too.</p>\n<h3>The idea in plain words</h3>\n<ul>\n<li><code>dvc add data/train.csv</code> computes a <strong>hash</strong> of the file (a fingerprint; any change to the file gives a completely different hash) and moves the file into a <strong>cache</strong> folder named by that hash.</li>\n<li>It writes a tiny text file, <code>data/train.csv.dvc</code>, containing the hash. <strong>Git tracks the small <code>.dvc</code> file; DVC tracks the big file.</strong></li>\n<li><code>dvc push</code> uploads the cache to a <strong>remote</strong> (S3, Google Drive, a shared disk). <code>dvc pull</code> downloads what the current <code>.dvc</code> files point to.</li>\n<li>Because files are stored by hash, a file that did not change between versions is stored <strong>once</strong>.</li>\n</ul>\n<h3>Worked example: storage with and without deduplication</h3>\n<p>A dataset of 5 files totalling about 1.4 GB. Over four versions you fix some labels, add rows and change the test split.</p>\n<figure class=\"dg viz\" data-viz=\"dvccache\" data-p=\"{}\"><div class=\"vz\"></div><figcaption>Each cell is a file&#39;s content hash in one version; ★ marks content DVC must store. Slide through the versions and compare a full copy per version with DVC&#39;s cache.</figcaption></figure>\n<p>With four versions, full copies take about 5.8 GB. DVC stores each distinct file once, about 2.4 GB, because <code>images.zip</code> (900 MB) never changed and is stored only once.</p>\n<h3>The commands</h3>\n<pre class=\"code\"><code class=\"language-bash\">git init &amp;&amp; dvc init\ndvc add data/                       # creates data.dvc, adds data/ to .gitignore\ngit add data.dvc .gitignore &amp;&amp; git commit -m &quot;Dataset v1&quot;\ndvc remote add -d store s3://my-bucket/dvc\ndvc push                            # upload the data\n\n# later: go back to the data used two commits ago\ngit checkout HEAD~2 -- data.dvc\ndvc checkout                        # restores the matching files from the cache\n</code></pre>\n<h3>Common mistakes</h3>\n<ul>\n<li><strong>Committing the data to Git as well.</strong> <code>dvc add</code> puts it in <code>.gitignore</code>; keep it that way.</li>\n<li><strong>Forgetting <code>dvc push</code>.</strong> Your teammate pulls the <code>.dvc</code> file and DVC cannot find the data.</li>\n<li><strong>Editing a tracked file and forgetting <code>dvc add</code>.</strong> The <code>.dvc</code> file still points at the old hash; <code>dvc status</code> shows the mismatch.</li>\n</ul>\n<h3>Try it yourself</h3>\n<ol>\n<li>You change one row of a 10 GB file. How much new data does DVC store?</li>\n<li>What does Git store about a DVC-tracked dataset?</li>\n</ol>\n<details><summary>Answers</summary><ol>\n<li>The whole new file, 10 GB, because DVC deduplicates whole files, not rows. Split huge datasets into many files (shards) so a small change touches one shard.</li>\n<li>Only the small <code>.dvc</code> file with the hash, size and path.</li>\n</ol>\n</details><blockquote class=\"callout\"><p><strong class=\"callout-label\">Key idea</strong> DVC stores data in a cache keyed by content hash and lets Git version the tiny pointer files.
