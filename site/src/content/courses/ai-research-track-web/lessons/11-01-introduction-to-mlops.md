For a research job, the same skills are what make a hiring panel trust your results: they can clone your repo and get your number.</p>\n<p>MLOps covers the lifecycle around the model: versioned data, tracked experiments, tested code, automated pipelines, deployment and monitoring. This lesson covers the first four; Lessons 11.08 and 4.4 cover the rest.</p>\n<p>Sculley et al.&#39;s &quot;Hidden Technical Debt&quot; paper is the classic argument for why this is needed. Its well-known figure shows the ML code as a small box in the middle of a much larger system: data collection, feature extraction, verification, configuration, serving infrastructure, monitoring. The paper names specific kinds of debt that are unique to ML and that this unit&#39;s tools exist to pay down:</p>\n<ul>\n<li><strong>Entanglement (&quot;changing anything changes everything&quot;).</strong> Inputs interact inside the model, so changing one feature&#39;s preprocessing can change the importance of all others. The defence is versioning everything together so a change is traceable.</li>\n<li><strong>Undeclared consumers and hidden feedback loops.</strong> Other systems silently use your model&#39;s outputs, or the model&#39;s outputs affect its future training data (a recommender trained on what it recommended).</li>\n<li><strong>Data dependencies.</strong> Unstable or unused input signals that nobody owns. These are harder to find than code dependencies because no compiler tracks them; data versioning and data tests do.</li>\n<li><strong>Glue code and pipeline jungles.</strong> Most of an ML system is code that moves data between general-purpose packages. Packaging and declared pipelines (DVC) keep it understandable.</li>\n<li><strong>Configuration debt.</strong> Configuration grows larger than the code and is rarely tested. Keeping all config in versioned files is the cheapest fix.</li>\n</ul>\n<p>Huyen&#39;s <em>Designing Machine Learning Systems</em> (ch. 1) frames the same point from the product side: in research, the priority is model performance on a fixed benchmark; in production, it is latency, cost, reliability and the fact that data keeps changing. A research engineer needs to be able to speak both languages.</p>\n<h3>Packaging a project</h3>\n<p>Move from notebooks to a package once the code works:</p>\n<pre class=\"code\"><code class=\"language-text\">myproject/\n  pyproject.toml        # dependencies, pinned; tool config\n  src/myproject/\n    data.py  model.py  train.py  evaluate.py\n  tests/\n  configs/              # YAML configs, one per experiment\n  dvc.yaml  params.yaml # pipeline definition and parameters\n  README.md\n</code></pre>\n<ul>\n<li>Pin dependency versions (with <code>uv</code>, <code>pip-tools</code> or Poetry lock files). &quot;Works on my machine&quot; is usually an unpinned dependency.</li>\n<li>Keep configuration out of code. Every run should be fully described by a config file plus a git commit.</li>\n<li>Use a formatter and linter (<code>ruff</code>) and run them in CI, so style never comes up in review.</li>\n</ul>\n<h3>Git for ML</h3>\n<p>Pro Git chapters 2-3 cover what you need: commits, branches, merges, rebasing, remotes. Git stores snapshots, not diffs: each commit points to a tree of content-addressed blobs, identified by the hash of their contents. That one idea explains why branches are cheap (a branch is a pointer to a commit), why identical files are stored once, and why DVC (next section) uses the same content-hashing design for data. ML-specific habits: commit before every experiment you might report, tag commits that produced paper results, never commit data or model weights (that is what DVC is for), and keep <code>.gitignore</code> covering checkpoints and caches.</p>\n</section></details>"
