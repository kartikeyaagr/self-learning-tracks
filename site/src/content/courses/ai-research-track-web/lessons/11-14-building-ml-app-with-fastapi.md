A small <strong>web API</strong> is the standard way: a sales dashboard sends a customer&#39;s data over HTTP and gets a probability back. FastAPI is popular for this because it validates inputs automatically and generates interactive documentation for free.</p>\n<h3>The idea in plain words</h3>\n<ul>\n<li>The API exposes <strong>endpoints</strong>: <code>POST /predict</code> takes customer features as JSON and returns a prediction; <code>GET /health</code> says the service is alive.</li>\n<li>A <strong>Pydantic model</strong> describes the expected input. Wrong types or missing fields are rejected with a clear 422 error before your code runs.</li>\n<li>Load the model and preprocessor <strong>once at start-up</strong>, not on every request.</li>\n<li>Run it with <strong>uvicorn</strong>, a fast server; it is what the Docker image&#39;s <code>CMD</code> starts (11.08).</li>\n</ul>\n<h3>Worked example: one request</h3>\n<pre class=\"code\"><code class=\"language-python\">from fastapi import FastAPI\nfrom pydantic import BaseModel, Field\nimport joblib, pandas as pd\n\nclass Customer(BaseModel):\n    Gender: str\n    Age: int = Field(ge=18, le=100)\n    Driving_License: int\n    Previously_Insured: int\n    Vehicle_Age: str\n    Vehicle_Damage: str\n    Annual_Premium: float = Field(gt=0)\n    Vintage: int\n\napp = FastAPI()\nmodel = joblib.load(&quot;artifacts/model.pkl&quot;)               # a Pipeline: preprocessor + classifier\n\n@app.get(&quot;/health&quot;)\ndef health():\n    return {&quot;status&quot;: &quot;ok&quot;}\n\n@app.post(&quot;/predict&quot;)\ndef predict(c: Customer):\n    p = float(model.predict_proba(pd.DataFrame([c.model_dump()]))[0, 1])\n    return {&quot;probability&quot;: round(p, 4), &quot;contact&quot;: p &gt;= 0.35}\n</code></pre>\n<pre class=\"code\"><code class=\"language-bash\">uvicorn app:app --port 8000\ncurl -X POST localhost:8000/predict -H &quot;Content-Type: application/json&quot; \\\n  -d &#39;{&quot;Gender&quot;:&quot;Male&quot;,&quot;Age&quot;:44,&quot;Driving_License&quot;:1,&quot;Previously_Insured&quot;:0,&quot;Vehicle_Age&quot;:&quot;1-2 Year&quot;,&quot;Vehicle_Damage&quot;:&quot;Yes&quot;,&quot;Annual_Premium&quot;:40454,&quot;Vintage&quot;:217}&#39;\n</code></pre>\n<p>Open <code>localhost:8000/docs</code> for an interactive page that lists every endpoint and lets you try it.</p>\n<h3>Worked example 2: choosing the threshold</h3>\n<p>The API returns <code>contact: true</code> above 0.35, not 0.5. It validates requests with <strong>Pydantic</strong> models and generates interactive docs at <code>/docs</code> automatically.</p>\n<pre class=\"code\"><code class=\"language-python\">from fastapi import FastAPI\nfrom pydantic import BaseModel, Field\nfrom contextlib import asynccontextmanager\n\nclass PredictRequest(BaseModel):\n    text: str = Field(min_length=1, max_length=2000)\n\nclass PredictResponse(BaseModel):\n    label: str\n    score: float\n\nstate = {}\n\n@asynccontextmanager\nasync def lifespan(app):\n    state[&quot;model&quot;] = load_model()      # load once, at startup\n    yield\n\napp = FastAPI(lifespan=lifespan)\n\n@app.get(&quot;/health&quot;)\ndef health():\n    return {&quot;status&quot;: &quot;ok&quot;}\n\n@app.post(&quot;/predict&quot;, response_model=PredictResponse)\ndef predict(req: PredictRequest):\n    label, score = state[&quot;model&quot;](req.text)\n    return PredictResponse(label=label, score=score)\n</code></pre>\n<p>Points to understand:</p>\n<ul>\n<li><strong>Validation is free.</strong> A request with a missing or wrong-typed field gets a 422 response with a precise error, before your code runs. Constrain inputs (length, ranges) so a single request cannot exhaust memory.</li>\n<li><strong>Load the model once</strong> at startup (the <code>lifespan</code> handler), never per request.</li>\n<li><strong>Sync vs async.</strong> FastAPI runs plain <code>def</code> endpoints in a thread pool, so a blocking model call does not freeze the server. <code>async def</code> endpoints run on the event loop and must never call blocking code directly.</li>\n<li><strong>Health and readiness endpoints</strong> let orchestrators know when the process is alive and when the model is loaded.</li>\n<li>Test with <code>fastapi.testclient.TestClient</code>, which calls the app in-process. Exercise 1 asks for tests covering validation errors, not just the happy path.</li>\n</ul>\n<p>Huyen ch. 7 separates two serving modes, and choosing between them is the first design decision:</p>\n<ul>\n<li><strong>Batch prediction.</strong> Compute predictions for all inputs periodically (nightly) and store them; serving is a lookup. Cheap and simple, but predictions are stale and you must know the inputs in advance.</li>\n<li><strong>Online prediction.</strong> Compute on request, as in the code above. Needed when inputs are new (a user&#39;s question) or freshness matters, at the cost of latency constraints and always-on infrastructure.</li>\n</ul>\n<p>LLM applications are almost always online. Huyen also notes that the <strong>model is often not the slowest part</strong>: tokenisation, network hops, feature lookups and post-processing add up. Measure the whole request before optimising the forward pass.</p>\n<h3>Batching requests</h3>\n<p>GPUs are far more efficient on batches than on single inputs. <strong>Dynamic batching</strong> collects requests arriving within a short window (a few milliseconds) or until a maximum batch size, runs them together, and returns each result to its caller. It trades a little latency for much higher throughput. For LLMs, servers such as vLLM go further with <strong>continuous batching</strong>: new requests join the running batch at each decoding step instead of waiting for the whole batch to finish, combined with paged KV-cache memory.
