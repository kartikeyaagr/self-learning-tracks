question: "Your Docker image for a FastAPI model server is 9 GB and rebuilds take 15 minutes for one-line code changes. What two Dockerfile changes help most?"
answer: "Order layers so dependencies are installed (copy <code>requirements.txt</code>, then <code>pip install</code>) before copying the code, so code changes reuse the cached layer; and use a slim base with CPU-only wheels or a multi-stage build, and a <code>.dockerignore</code> excluding data, checkpoints and <code>.git</code>."

Your model needs a specific Python, specific library versions, maybe system libraries. A <strong>Docker image</strong> packages the code with all of it, so the same thing runs on your laptop, in CI, on EC2 and on Kubernetes. Every later deployment lesson in this module ships a Docker image.</p>\n<h3>The idea in plain words</h3>\n<ul>\n<li>A <strong>Dockerfile</strong> is a recipe: start from a base image, copy files, install packages, say what command to run.</li>\n<li><code>docker build</code> follows the recipe and produces an <strong>image</strong>, made of stacked <strong>layers</strong>, one per instruction.</li>\n<li><code>docker run</code> starts a <strong>container</strong>: a running, isolated copy of the image.</li>\n<li>Layers are <strong>cached</strong>. If an instruction and its inputs did not change, Docker reuses the layer. Once one layer changes, every layer after it is rebuilt.</li>\n</ul>\n<h3>Worked example: order matters</h3>\n<p>Installing dependencies takes about 90 seconds; copying code takes 2.</p>\n<ul>\n<li><strong>Bad order</strong>: <code>COPY . .</code> then <code>RUN pip install</code>. Any code edit changes the copy layer, so pip install re-runs: 92 s per build.</li>\n<li><strong>Good order</strong>: <code>COPY requirements.txt .</code>, <code>RUN pip install</code>, then <code>COPY . .</code>. Editing code only rebuilds the last copy: 2 s. Only a dependency change pays the 90 s.</li>\n</ul>\n<figure class=\"dg viz\" data-viz=\"dockerlayers\" data-p=\"{}\"><div class=\"vz\"></div><figcaption>Switch between the two Dockerfile orders and choose what changed. Coral layers are rebuilt; teal ones come from the cache.</figcaption></figure>\n<h3>In code</h3>\n<pre class=\"code\"><code class=\"language-dockerfile\">FROM python:3.11-slim\nWORKDIR /app\nCOPY requirements.txt .\nRUN pip install --no-cache-dir -r requirements.txt\nCOPY . .\nEXPOSE 8000\nCMD [&quot;uvicorn&quot;, &quot;app:app&quot;, &quot;--host&quot;, &quot;0.0.0.0&quot;, &quot;--port&quot;, &quot;8000&quot;]\n</code></pre>\n<pre class=\"code\"><code class=\"language-bash\">docker build -t insurance-api:0.1 .\ndocker run -p 8000:8000 --env-file .env insurance-api:0.1   # secrets come in at run time\n</code></pre>\n<p>Add a <code>.dockerignore</code> (data, <code>.git</code>, checkpoints, <code>.env</code>) so they are not copied into the image.</p>\n<h3>Common mistakes</h3>\n<ul>\n<li><strong>Baking secrets into the image.</strong> Anyone who can pull the image can read them. Pass them at run time.</li>\n<li><strong>Huge images.</strong> Use <code>-slim</code> bases, <code>--no-cache-dir</code>, and keep datasets out. Big images are slow to push and to start.</li>\n<li><strong>Unpinned versions.</strong> <code>pip install pandas</code> today and next month give different images. Pin versions in <code>requirements.txt</code>.</li>\n</ul>\n<h3>Try it yourself</h3>\n<ol>\n<li>In the good order, you add a new package to <code>requirements.txt</code>. Which layers rebuild?</li>\n<li>What is the difference between an image and a container?</li>\n</ol>\n<details><summary>Answers</summary><ol>\n<li>The <code>COPY requirements.txt</code> layer and everything after it: pip install and the code copy.</li>\n<li>An image is the packaged, read-only recipe result; a container is a running instance of it (you can run many containers from one image).</li>\n</ol>\n</details><blockquote class=\"callout\"><p><strong class=\"callout-label\">Key idea</strong> A Docker image packages code and environment in cached layers. Put what changes least first, keep secrets and data out, and pin your versions.</p>\n</blockquote>\n</section><details class=\"deeper\"><summary>Go deeper: the original, more advanced notes (1 section)</summary><section class=\"art\"><h2>Containers with Docker</h2><p class=\"cite\"><span class=\"lab\">Based on</span> Docker: Get started and best-practices guide · Chip Huyen, Designing Machine Learning Systems ch. 7 (deployment) · MLOps Zoomcamp module 4 · Fanout 11.08</p><p>A model that runs on your laptop is not deployable until it runs the same way everywhere. Docker packages your code, its dependencies and the operating-system libraries it needs into an <strong>image</strong>. A running instance of an image is a <strong>container</strong>. Containers share the host kernel, so they start in seconds and are much lighter than virtual machines.</p>\n<h3>A Dockerfile for a model API</h3>\n<pre class=\"code\"><code class=\"language-dockerfile\">FROM python:3.11-slim\nWORKDIR /app\nENV PYTHONDONTWRITEBYTECODE=1 PYTHONUNBUFFERED=1\nCOPY requirements.txt .\nRUN pip install --no-cache-dir -r requirements.txt\nCOPY src/ ./src/\nCOPY models/ ./models/\nRUN useradd -m appuser\nUSER appuser\nEXPOSE 8000\nHEALTHCHECK CMD python -c &quot;import urllib.request; urllib.request.urlopen(&#39;http://localhost:8000/health&#39;)&quot;\nCMD [&quot;uvicorn&quot;, &quot;src.app:app&quot;, &quot;--host&quot;, &quot;0.0.0.0&quot;, &quot;--port&quot;, &quot;8000&quot;]\n</code></pre>\n<p>The details that make a Dockerfile good:</p>\n<ul>\n<li><strong>Layer caching.</strong> Each instruction is a cached layer. Copy <code>requirements.txt</code> and install dependencies <strong>before</strong> copying source code, so code changes do not reinstall everything.</li>\n<li><strong>Small base images</strong> (<code>-slim</code>), and <code>--no-cache-dir</code> for pip. Use <strong>multi-stage builds</strong> when you need compilers at build time but not at runtime.</li>\n<li><strong>Do not run as root.</strong> Create a user and switch to it.</li>\n<li><strong>No secrets in images.</strong> Pass them as environment variables or mounted secrets at runtime; anything in a layer can be extracted.</li>\n<li>A <code>.dockerignore</code> that excludes data, checkpoints, <code>.git</code> and virtual environments, so the build context stays small.</li>\n<li>Pin the base image version for reproducibility.</li>\n</ul>\n<p>How layers work, because it explains every item above: an image is a stack of read-only filesystem layers, one per instruction, each identified by a hash of its instruction and its inputs. When you rebuild, Docker reuses every layer up to the first one whose inputs changed, and rebuilds everything after it. Deleting a file in a later layer does not remove it from the earlier one; it is still in the image and still extractable, which is why a secret copied in and then deleted is still leaked.</p>\n<p>For GPU models, start from a CUDA runtime image (for example the <code>pytorch/pytorch</code> or <code>nvidia/cuda</code> runtime tags) and run with <code>docker run --gpus all</code>, which needs the NVIDIA container toolkit on the host. GPU base images are several gigabytes, so layer ordering matters even more.</p>\n<p><code>docker build -t mymodel:0.1 .</code> builds; <code>docker run -p 8000:8000 mymodel:0.1</code> runs and maps the port. Model weights can be baked into the image (simple, immutable) or downloaded at startup from a registry (smaller images, but startup depends on the network).</p>\n</section></details>"
