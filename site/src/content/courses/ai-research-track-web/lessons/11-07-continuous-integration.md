Teams require green checks before merging.</li>\n<li>Order checks from <strong>cheap and fast</strong> to <strong>slow</strong>: a syntax error should be reported in one minute, not after a 10-minute training run.</li>\n</ul>\n<h3>Worked example: what ML code should be tested</h3>\n<div class=\"tbl\"><table>\n<thead>\n<tr>\n<th>Test</th>\n<th>Example</th>\n<th>Catches</th>\n</tr>\n</thead>\n<tbody><tr>\n<td>Lint and types</td>\n<td><code>ruff</code>, <code>mypy</code></td>\n<td>typos, wrong types</td>\n</tr>\n<tr>\n<td>Unit test</td>\n<td><code>scale([0, 10])</code> returns <code>[0, 1]</code></td>\n<td>logic bugs in features</td>\n</tr>\n<tr>\n<td>Data test</td>\n<td>required columns present, no negative ages</td>\n<td>broken or changed data</td>\n</tr>\n<tr>\n<td>Training smoke test</td>\n<td>train 1 epoch on 100 rows, loss decreases</td>\n<td>wiring bugs</td>\n</tr>\n<tr>\n<td>Model test</td>\n<td>validation F1 ≥ the current model&#39;s</td>\n<td>quality regressions</td>\n</tr>\n</tbody></table></div>\n<figure class=\"dg viz\" data-viz=\"cipipe\" data-p=\"{}\"><div class=\"vz\"></div><figcaption>Pick a change and see where the pipeline stops it. Fast and deterministic.</li>\n<li><strong>Data tests.</strong> Expectations about inputs: schema, value ranges, no nulls in key columns, label distribution within bounds. Run on every new data version.</li>\n<li><strong>Model tests.</strong> Behavioural checks on the trained model:<ul>\n<li><em>Overfit a tiny batch</em> (training works at all).</li>\n<li><em>Invariance:</em> changes that should not matter (a name, a synonym) do not change the prediction.</li>\n<li><em>Directional expectations:</em> changes that should push the prediction one way do.</li>\n<li><em>Minimum functionality:</em> a handful of easy cases the model must get right.</li>\n<li><em>Loss decreases</em> over a few steps, and <em>no NaNs</em>.</li>\n</ul>\n</li>\n</ul>\n<p>The invariance, directional and minimum-functionality tests come from Ribeiro et al.&#39;s <strong>CheckList</strong>, which found serious failures in commercial NLP models that had high benchmark accuracy. Examples for a sentiment model: changing a person&#39;s name should not change the label (invariance); adding &quot;I hated it&quot; to the end of a positive review should lower the positive score (directional); &quot;This is not good.&quot; must be negative (minimum functionality). For an LLM fine-tuned on support tickets: rephrasing a question should not change the answer&#39;s facts; a ticket in all capitals should get the same routing.</p>\n<p>Breck et al.&#39;s <strong>ML Test Score</strong> turns these ideas into a rubric of 28 tests across data, model development, infrastructure and monitoring, scored by whether each is done manually or automated. It is a useful audit of your capstone repo: most research repos score near zero, and getting to a handful of automated tests already puts you ahead.</p>\n<p>How do you know your tests are any good? <strong>Mutation testing</strong>: deliberately introduce bugs (flip a sign in the loss, drop the softmax, swap two axes) and check that some test fails for each. Exercise 3 gives you mutants of a training module; your test suite must kill all of them.</p>\n<h3>Continuous integration</h3>\n<p>CI runs your checks automatically on every push and pull request.
