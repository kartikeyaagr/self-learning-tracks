@02.01
## An API is a contract
An **API** (application programming interface) is the promise a service makes to its callers: these are the resources, these are the operations, this is what you send, this is what comes back, and this is how errors look. Once other teams, mobile apps or paying customers depend on it, changing it is expensive. You cannot force every phone in the world to update its app on the day you rename a field.

That is why interviewers ask you to write the API early. It fixes the scope (every functional requirement should map to an endpoint), it shows you think about callers and not just servers, and it becomes the contract every component behind it must fulfil.

Most interview APIs, and most public APIs, are **REST over HTTP**. Lesson 02.03 covers HTTP and alternatives like gRPC; this lesson is about designing the contract well.

## Model resources, not actions
Model the API around **resources** (nouns) and use HTTP methods for the actions. You write `POST /urls`, not `POST /createShortUrl`. Resources are usually plural, and they nest when one belongs to another: `/users/{id}/posts`.

Every resource should have one **canonical name**: a path that identifies exactly one thing, such as `publishers/123/books/456`. Callers can store it, pass it around and use it in other calls. Keep nesting shallow (two levels is usually enough), because deep paths make URLs brittle when relationships change.

%%tree A resource hierarchy. Each node is a collection or an item with one canonical path, and the methods attach to these paths.
/v1
  /users | collection: GET lists, POST creates
    /users/{user_id} | item: GET, PATCH, DELETE
      /users/{user_id}/urls | that user's links
  /urls | collection of short links
    */urls/{code} | one link
      /urls/{code}:disable | custom action
  /{code} | public redirect, outside /v1
%%

Some operations are not natural creates, reads, updates or deletes: "cancel an order", "publish a draft", "resend a verification email". You have two reasonable options. Model them as a change of state (`PATCH /orders/123 {status: "cancelled"}`), or use a **custom method** written with a colon, `POST /orders/123:cancel`, which is the convention in Google's public API standards. Either is fine; what matters is consistency across the API.

## Methods and what they promise
Each HTTP method carries a meaning that clients, proxies and caches rely on. Two properties matter most:
- **Safe**: the request does not change anything on the server. Caches and crawlers may call safe methods freely.
- **Idempotent**: calling it twice has the same effect on the server as calling it once.

%%matrix What each HTTP method promises. Idempotent methods can be retried after a timeout without fear; POST cannot, without extra help.
Method | Safe | Idempotent | Cacheable | Typical use
GET | yes | yes | yes | read a resource or a list
POST | no | no | partial, rarely | create, or trigger an action
PUT | no | yes | no | replace a resource at a known ID
PATCH | no | partial, not guaranteed | no | change some fields
DELETE | no | yes | no | remove a resource
%%

Idempotency matters because networks fail and clients retry. A retried `PUT /users/42 {name: "Ana"}` is harmless: the result is the same. A retried `DELETE` is harmless: the second call finds nothing to delete (and may return 404, but the server state is the same). A retried `POST /orders` can create two orders. Lesson 02.09 shows how **idempotency keys** make POST safe to retry: the client sends a unique key in a header, and the server returns the stored result if it sees the same key again.

PATCH is idempotent if it sets fields to values (`{status: "shipped"}`), but not if it applies a relative change (`{balance: "+10"}`). Prefer absolute values.

## Where inputs go
- **Path** identifies the resource: `/urls/abc123`.
- **Query string** filters, sorts and paginates: `?limit=20&cursor=...&sort=-created_at`.
- **Body** carries the data you are creating or changing, usually JSON.
- **Headers** carry metadata: the auth token (`Authorization: Bearer ...`), content type, idempotency keys, conditional-request tags.

**Never take the caller's identity from the request body.** The server should derive "who is calling" from the verified auth token. If `POST /v1/urls` accepted `{owner_id: 42}`, any client could create links as any user. The same applies to `GET /v1/urls?user_id=42`: the server must check the caller is allowed to see user 42's links, or better, offer `GET /v1/me/urls` and read the user from the token.

## Status codes and errors
Use status codes as intended, so clients can react without parsing messages:

| Code | Meaning | Client should |
| 200 OK | success with a body | use the body |
| 201 Created | resource created | read the Location header or returned ID |
| 204 No Content | success, nothing to return | carry on |
| 400 Bad Request | malformed or invalid input | fix the request; retrying won't help |
| 401 Unauthorized | not authenticated | log in or refresh the token |
| 403 Forbidden | authenticated but not allowed | stop |
| 404 Not Found | no such resource (or hidden from you) | stop |
| 409 Conflict | clashes with current state, e.g. alias taken | change the input |
| 412 Precondition Failed | the resource changed since you read it | re-read and retry |
| 429 Too Many Requests | rate limited | wait for Retry-After, then retry |
| 500 Internal Server Error | server bug | maybe retry, report |
| 503 Service Unavailable | temporarily overloaded or down | retry with backoff |

The split between 4xx (the caller's fault, don't retry unchanged) and 5xx (the server's fault, retrying may help) is what lets client libraries decide automatically whether to retry.

Error bodies should have a stable, machine-readable code plus a human message, and details where useful:

```
{"error": {"code": "ALIAS_TAKEN", "message": "The alias 'sale' is already in use.", "field": "custom_alias"}}
```

Clients branch on `code`, never on the text of `message`, which you are free to reword.

### Concurrent updates
Two people edit the same resource; the second save silently overwrites the first. HTTP has a standard fix, **optimistic concurrency**: every GET returns an `ETag` header (a version tag). The client sends it back on update as `If-Match: "v7"`. If the resource has changed since, the server returns 412 and the client re-reads and retries instead of overwriting.

## Pagination: offset vs cursor
Every list endpoint must be paginated, because lists grow without bound. A user with 50,000 links must not receive them in one response.

**Offset pagination** (`?offset=40&limit=20`) is simple and lets users jump to page 5. It has two problems:
- **It gets slow on deep pages.** `OFFSET 20000 LIMIT 20` makes the database find and discard 20,000 rows before returning 20. Cost grows linearly with depth.
- **It is unstable under inserts and deletes.** If a new item is inserted at the top while someone is paging, everything shifts down by one, and they see the last item of page 1 again at the top of page 2. A deletion makes them skip an item.

**Cursor pagination** (`?page_token=<opaque>&page_size=20`) returns a token that encodes where the last page ended, usually the sort key of the last item. The next query is "items after this key": `WHERE (created_at, code) < (:last_created_at, :last_code) ORDER BY created_at DESC, code DESC LIMIT 20`. With an index on `(created_at, code)`, the database seeks straight to the right place, so every page costs the same at any depth, and inserts at the top don't shift later pages. You lose random page jumps, which most feeds and lists never need.

%%compare Offset versus cursor pagination for page 1,001 of a list sorted by creation time.
[Offset]
page 1001 -(OFFSET 20000 LIMIT 20)-> DB walks and discards 20,000 rows -> 20 rows
+ Simple, supports jump to page N
- Cost grows with depth
- Duplicates or gaps when rows change
[*Cursor]
next page -(WHERE key < last_key LIMIT 20)-> DB seeks via index -> 20 rows
+ Same cost at any depth
+ Stable while rows are inserted
- No jumping to page N
%%

Rules for good cursors:
- **Sort by a unique key**, or add a tie-breaker. Sorting only by `created_at` breaks when two items share a timestamp; `(created_at, code)` is unique.
- **Make the token opaque**: base64-encode it (and ideally sign it), so clients can't construct or depend on it and you can change the encoding later.
- **Return `next_page_token`**, and an empty one when there are no more pages. Clients loop until it is empty.
- **Cap the page size** on the server (for example a default of 20, a maximum of 100), whatever the client asks for.
- **Add pagination from day one.** Adding it later breaks clients that assumed one response contained everything.

! Example: why offset breaks while paging
! A user lists their links, newest first, 20 per page, with offset pagination. They load page 1 (links 1 to 20).
! While they read, they create a new link in another tab. Every existing link moves down one position.
! They load page 2 with `offset=20`. Position 21 is now the old link 20, which they already saw. They see a duplicate, and if a link had been deleted instead, they would silently skip one.
! With a cursor, page 2 is "links created before link 20's (created_at, code)". The new link is newer, so it does not affect the result: page 2 starts exactly at the old link 21.

## Consistency across the API
Google's public API standards (the AIPs) are a detailed, published style guide for resource APIs, and their main value is consistency. The ideas that come up most:
- **Standard methods**: Get, List, Create, Update, Delete, with predictable request and response shapes.
- **Custom methods** for actions that don't fit, with the colon syntax.
- **Resource names**: every resource has one canonical path.
- **Field names**: consistent `lower_snake_case`, with units in the name (`size_bytes`, `duration_seconds`, `expire_time`), so nobody guesses whether `timeout` is seconds or milliseconds.
- **List methods** take `page_size` and `page_token` and return `next_page_token`.

A caller who learns one endpoint can guess the rest. Inconsistency (some lists use `cursor`, others `page`; some timestamps are seconds, others ISO strings) is a tax on every client.

## Versioning, auth and rate limits
- **Versioning**: put a major version in the path (`/v1/`) or a header. **Additive changes** (new optional fields, new endpoints, new optional query parameters) need no new version, as long as clients ignore fields they don't recognise. **Breaking changes** (removing or renaming fields, changing types or meanings, making an optional field required) need a new major version, run alongside the old one until clients migrate.
- **Authentication**: **API keys** identify a calling application and suit server-to-server calls. User sessions usually use **tokens** such as JWTs (JSON Web Tokens), which carry signed claims (user ID, expiry, scopes) that any service can verify with a public key, without a database lookup. Short expiry times (minutes to an hour) limit the damage from a leaked token.
- **Rate limiting** protects the service from one noisy caller. Return 429 with a `Retry-After` header, and publish the limits so client developers can plan.

%%seq Creating a link, then reading the list. The server takes the owner from the token, and the list returns a cursor for the next page.
Client > API : POST /v1/urls {long_url} + Bearer token
API > API : verify token, owner = user 42
API -> Client : 201 {code: abc123}, Location: /v1/urls/abc123
Client > API : GET /v1/urls?page_size=20
API -> Client : 200 {urls: [20 items], next_page_token: "eyJj..."}
Client > API : GET /v1/urls?page_size=20&page_token=eyJj...
API -> Client : 200 {urls: [7 items], next_page_token: ""}
%%

## Common mistakes
- **Verbs in URLs** and inconsistent naming across endpoints.
- **Returning unbounded lists.**
- **Trusting user IDs sent in the body or query** without checking them against the token.
- **Breaking changes without a version bump**, such as renaming a field.
- **Leaking internals**: auto-increment database IDs (which reveal volumes and invite enumeration) or table structures copied straight into responses.
- **Using 200 for errors** with `{"success": false}` in the body, which defeats every HTTP-aware client, proxy and monitor.

! Example: URL shortener API
! `POST /v1/urls` with body `{long_url, custom_alias?, expires_at?}` returns `201 {code, short_url}`. A duplicate alias returns `409 ALIAS_TAKEN`. The client may send an `Idempotency-Key` header so a retried create doesn't make two links.
! `GET /{code}` returns `302` with a `Location` header pointing to the long URL, or `404` if unknown or expired. (302 rather than 301, so browsers don't cache the redirect forever and every click can be counted.)
! `GET /v1/urls?page_size=20&page_token=...` returns `{urls: [...], next_page_token}` for the caller's own links, newest first, using a cursor on `(created_at, code)`.
! `DELETE /v1/urls/{code}` returns `204`. The caller's identity always comes from the auth token, and deleting someone else's link returns 404 so codes can't be probed.

> Takeaway: model nouns with canonical names, use methods for what they promise (and make POST retry-safe with idempotency keys), derive identity from the auth token, return honest status codes with machine-readable errors, and paginate every list with an opaque cursor from day one.

?? POST /v1/urls {long_url, custom_alias?, expires_at?} creates a link and returns 201 with the code (409 if the alias is taken). GET /{code} redirects with 302 to the long URL, or 404. GET /v1/urls?page_size=20&page_token=... lists the caller's own links (owner taken from the auth token), newest first, and returns next_page_token. Use cursor pagination keyed on (created_at, code), encoded as an opaque token, because each page is an index seek that stays fast at any depth and does not skip or repeat rows when links are created or deleted while paging.

## Two ways for services to talk
Once a system is split into services, each service needs data or work from others. The orders service needs a price from catalogue, a charge from payments, and needs to tell email, analytics and the warehouse that an order exists. There are two families of interaction, and choosing between them per arrow is one of the most important decisions in a service-based design.

**Remote procedure invocation (RPI)**, also called synchronous request/response: service A sends a request to B and waits for a reply. REST over HTTP, gRPC and Thrift are all RPI. It is simple and familiar (it looks like a function call), and there is no extra infrastructure in the middle.

**Messaging**, also called asynchronous communication: A sends a message to a **broker** (Kafka, RabbitMQ, Amazon SQS, Google Pub/Sub) and moves on. B, and possibly C and D, consume it when they can. A doesn't wait and often doesn't know who the consumers are.

%%compare The same interaction done synchronously and through a broker. Synchronous calls couple the two services in time; a broker decouples them.
[Synchronous call]
Orders -(request, waits)-> Payments -(reply)-> Orders
+ Simple, immediate answer
+ No broker to run
- Orders is down when Payments is down
- Orders' latency includes Payments'
[Messaging]
Orders -(publish, returns)-> Broker -(later)-> Email, Analytics, Warehouse
+ Consumers can be slow or down
+ Many consumers, added without changing Orders
- Broker must be highly available
- Harder to trace and debug
%%

## What synchronous calls cost you
RPI's main weakness is **availability and latency coupling**. If A calls B synchronously on every request:
- A is only up when B is up. If B returns errors, so does A.
- A's latency includes B's latency, plus the network round trip.
- If B is slow, A's threads or connections pile up waiting for it, and A runs out of capacity too.

Chain five services like this and availability multiplies down (five 99.9% services in series give about 99.5%) while latencies add up. Worse, failures spread: one slow database at the bottom of the chain can exhaust thread pools all the way up. That chain reaction is called a **cascading failure**.

Other costs:
- **It only supports request/reply.** Notifications and fan-out to many consumers need something else.
- **The caller must find the callee.** Instances come and go, so you need **service discovery**: a registry (Consul, etcd, Kubernetes DNS) that maps a service name to the current healthy addresses, or a load balancer with a stable name in front.
- **You must defend against slow dependencies.** Every call needs a timeout (for example 800 ms), and repeated failures should trip a **circuit breaker**.

### The circuit breaker
A circuit breaker wraps calls to a dependency and tracks failures. When failures cross a threshold, it "opens" and fails calls immediately, without trying, for a cool-down period. This protects the caller's threads and gives the struggling dependency room to recover. After the cool-down, it lets a few trial calls through; if they succeed, it closes again.

%%state A circuit breaker. When a dependency keeps failing, the caller stops trying for a while instead of piling more load on it.
[*] -> Closed
Closed -> Closed : call succeeds
Closed -> *Open : failures over threshold (e.g. 50% of last 20)
Open -> Open : calls fail fast, no network call
Open -> Half-open : cool-down timer ends (e.g. 30 s)
Half-open -> Closed : trial calls succeed
Half-open -> Open : a trial call fails
%%

When the breaker is open, the caller needs a **fallback**: return a cached value, a default ("recommendations unavailable"), a degraded response, or a clear error. Designing those fallbacks is part of designing the call.

! Example: a cascading failure, and how to stop it
! The product page service has 200 worker threads and handles 1,000 requests per second, each calling the reviews service, which normally answers in 20 ms. By Little's Law, about 1,000 × 0.02 = 20 threads are busy waiting on reviews at any moment.
! The reviews database slows down and reviews now take 5 s. Busy threads needed: 1,000 × 5 = 5,000. The pool of 200 is exhausted in a fifth of a second, and product pages fail entirely, even for requests that would never have needed reviews.
! With a 300 ms timeout, at most 1,000 × 0.3 = 300 threads could be tied up, still too many. Add a circuit breaker that opens after half the recent calls time out: calls now fail in microseconds, pages render with "reviews unavailable", and the 200 threads are free for everything else.

## What messaging buys you, and costs you
Messaging decouples services **in time**. The broker stores messages durably, so the consumer can be down, slow or mid-deploy and the producer still succeeds. One message can reach many consumers, and new consumers can be added without changing the producer at all. The broker also absorbs bursts: if 10,000 orders arrive in a minute, the warehouse service works through them at its own pace.

Messaging supports several interaction styles:
- **Notification** (one way, fire and forget): "send this email".
- **Publish/subscribe**: "OrderPlaced" goes to every subscriber.
- **Request/async response**: A sends a request message with a **correlation ID** and a reply-to queue; B processes it and sends a reply with the same correlation ID; A matches them up later.
- **Publish/async responses**: A publishes a request and collects replies from several services for a while.

%%seq Request with an asynchronous reply. The correlation ID lets the requester match the reply to its request, whenever it arrives.
Orders > Broker : CheckCredit {corr_id: 77, reply_to: orders.replies}
Broker > Credit : deliver
Credit > Credit : evaluate customer
Credit > Broker : CreditChecked {corr_id: 77, ok: true}
Broker > Orders : deliver reply
Orders > Orders : match 77, confirm order
%%

The costs:
- **The broker is another critical system** that must be highly available, monitored and capacity-planned.
- **Request/response becomes awkward**: correlation IDs, reply queues, and timeouts for replies that never come.
- **The flow of a business process is harder to see.** No single piece of code says "after an order, we charge, then reserve, then ship"; it emerges from who subscribes to what. Distributed tracing and good event documentation become essential.
- **Duplicates and reordering.** Most brokers deliver **at least once**: if a consumer crashes after processing a message but before acknowledging it, the message is delivered again. Consumers must be **idempotent** (processing the same message twice has the same effect as once), usually by recording processed message IDs. Ordering is typically guaranteed only within a partition or queue, not globally.
- **Eventual consistency.** After an order is placed, the analytics dashboard may not show it for a few seconds.

### Publishing reliably: the outbox
A classic bug: the orders service commits the order to its database, then publishes OrderPlaced to the broker, and crashes between the two. The order exists but nobody hears about it. Or it publishes first and the database commit fails, announcing an order that doesn't exist. You can't wrap a database and a broker in one transaction cheaply.

The **transactional outbox** fixes this. In the same database transaction as the business change, the service inserts the event into an `outbox` table. A separate relay process reads new outbox rows and publishes them to the broker, marking them sent. If anything crashes, the relay simply retries, so events may be published twice (which idempotent consumers handle) but are never lost and never invented.

## Choreography vs orchestration
When a business process spans several services, you can coordinate it two ways:
- **Choreography**: each service reacts to events and emits its own. Orders emits OrderPlaced; payments hears it, charges, emits PaymentSucceeded; the warehouse hears that and ships. No central coordinator, very loosely coupled, but the overall flow is implicit and hard to change.
- **Orchestration**: one coordinator (an orchestrator service or a workflow engine such as Temporal or AWS Step Functions) tells each service what to do, in order, and handles failures and compensations. The flow is explicit and easy to see, at the cost of a central component that knows about everyone.

Short, simple flows suit choreography. Long flows with many steps and compensation logic (like the checkout saga in lesson 01.09) usually suit orchestration.

## How to choose
Ask one question per arrow: **does the caller need the answer to continue?**

%%tree Choosing per interaction. The deciding question is whether the caller needs the answer before it can respond.
Does the caller need the answer to continue?
  Yes: synchronous call
    *Keep the chain short, add timeouts and a breaker
    e.g. check password, read price, authorise payment
  No: announcing a fact
    Publish an event
    e.g. OrderPlaced to email, search, analytics
  No: long or bursty work
    Put a job on a queue
    e.g. transcode video, build report
%%

- **Need the answer now** (check a password, read a price to show the user, authorise a payment before confirming an order): use a synchronous call, and keep the chain short, ideally one or two hops.
- **Telling others something happened** (order placed, user signed up, profile updated): publish an event. The user should not wait for the welcome email to send, or for the search index to update.
- **Long or bursty work** (video transcoding, report generation, bulk imports): put a job on a queue and let workers pull at their own pace. Return "accepted" (HTTP 202) with a job ID the client can poll or be notified about.

A common shape is **synchronous at the edge and for reads on the critical path, asynchronous for side effects**. In interviews, saying out loud which arrows are synchronous and which are asynchronous is a strong signal.

! Example: checkout
! Sync: the order service calls payments and waits (with a 2 s timeout and an idempotency key), because the user must see "paid" or "declined" before leaving the page.
! Async: in the same transaction that saves the order, it writes OrderPlaced to its outbox. The relay publishes it. Email, analytics, loyalty points and the warehouse each consume it independently.
! If the email service is down for ten minutes, checkout keeps working. Its queue holds about 10 × 60 × 50 = 30,000 messages (at 50 orders a second), and when it comes back it works through them in a couple of minutes. Customers get their confirmations a little late; nobody loses an order.

%%timeline An email outage with asynchronous delivery. Checkout never notices; the queue absorbs the gap and drains afterwards.
[Checkout] 10:00 | orders succeed as normal
[Email] 10:00 | *email service crashes
[Queue] 10:05 | 15,000 messages waiting
[Email] 10:10 | service restarts
[Queue] 10:13 | backlog drained, emails ~10 min late
%%

## Common mistakes
- **Long synchronous chains**: A calls B calls C calls D, each adding latency and failure.
- **No timeouts**, so one slow dependency exhausts every caller's threads.
- **Using messaging for things that need an immediate answer**, then building awkward request/reply over queues.
- **Publishing events outside the database transaction**, losing or inventing events on crashes.
- **Non-idempotent consumers** that double-count when a message is redelivered.

## In an interview
Label every arrow sync or async. For sync arrows, mention timeouts, retries with backoff for idempotent calls, and a circuit breaker with a fallback. For async arrows, name the broker, say delivery is at least once so consumers are idempotent, and mention the outbox for reliable publishing.

> Takeaway: call synchronously only when you need the answer to proceed, and guard each call with a timeout, a circuit breaker and a fallback. Publish an event when you are announcing a fact, publish it reliably via an outbox, and make consumers idempotent. Every sync hop couples availability and latency.

?? Call B synchronously when A cannot continue without B's answer, such as authorising a payment before confirming an order or reading a price to show the user, and protect the call with a timeout, a circuit breaker and a fallback. Publish an event when A is announcing something that others react to, such as OrderPlaced triggering email, analytics and the warehouse, because then B's outages and slowness don't affect A, the broker buffers work while B catches up, and new consumers can subscribe without changing A.

## HTTP in one page
**HTTP** (Hypertext Transfer Protocol) is a client-server protocol for fetching and changing resources. The client (a browser, a mobile app, or another service) always starts the exchange by sending a request; the server answers each request with exactly one response. A web page is assembled from many such exchanges: the HTML, then dozens of scripts, stylesheets, images and API calls.

A request has a **method** (GET, POST...), a **path**, a protocol version, **headers** and an optional **body**. A response has a version, a **status code**, headers and an optional body. Over HTTP/1.1 it is plain text you can read:

```
GET /v1/urls/abc123 HTTP/1.1
Host: api.example.com
Authorization: Bearer eyJhbGciOi...
Accept: application/json

HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: private, max-age=60
ETag: "v7"

{"code":"abc123","long_url":"https://example.com/sale"}
```

Headers are where much of HTTP's power lives. They control **caching** (`Cache-Control`, `ETag`, `If-None-Match`), **authentication** (`Authorization`), **content negotiation** (`Accept`, `Content-Type`, `Content-Encoding: gzip`), and **cross-origin rules** for browsers (CORS headers).

HTTP is **stateless**: each request stands alone, and the server needn't remember anything between them. Sessions are layered on top with cookies or tokens sent on every request. Statelessness is what makes web servers easy to scale horizontally (lesson 01.08): any server can handle any request.

Because the meaning of methods, status codes and headers is standardised, **intermediaries** can work without understanding your application. Caches, CDNs, load balancers, auth gateways and corporate proxies all sit between clients and servers and act on standard headers. A CDN can cache your `GET /logo.png` for a day because of `Cache-Control: max-age=86400`, without knowing anything else about your site.

## How the versions differ
%%timeline The main HTTP versions. Each one attacked the cost of connections and the blocking between requests.
1996 | HTTP/1.0: new TCP connection per request
1997 | HTTP/1.1: keep-alive connections, pipelining (rarely usable)
2015 | HTTP/2: binary frames, multiplexed streams, header compression
2015 | gRPC released, built on HTTP/2
2022 | *HTTP/3 standardised: runs over QUIC on UDP
%%

- **HTTP/1.0** opened a new TCP connection for every request. Each TCP handshake costs a round trip, and TLS adds one or two more, so fetching 50 resources from a server 50 ms away wasted seconds on setup alone.
- **HTTP/1.1** kept connections open for reuse (**keep-alive**), which removed most of the setup cost. But each connection still carries one request at a time: a slow response blocks the ones behind it on that connection (**head-of-line blocking** at the HTTP level). It also defined **pipelining** (sending several requests before responses arrive), but responses must come back in order, and buggy proxies made it unusable in practice. Browsers worked around this by opening about six connections per host.
- **HTTP/2** keeps the same methods, status codes and headers, but sends them as **binary frames**. Each request/response pair is a **stream** with an ID, and frames from many streams are interleaved on one connection, so a slow response no longer blocks others at the HTTP level. Headers are compressed with **HPACK**, which matters because the same large headers (cookies, auth tokens, user agents) repeat on every request.
- **HTTP/3** runs over **QUIC**, a transport built on UDP (lesson 02.04). HTTP/2 still suffers head-of-line blocking at the TCP level: one lost packet stalls every stream on the connection until it is retransmitted. QUIC gives each stream independent delivery, builds TLS 1.3 into the handshake, and lets a connection survive a phone switching from Wi-Fi to mobile data.

%%seq Over HTTP/2, many requests share one connection as interleaved streams, and responses come back in whatever order they finish.
Client > Server : HEADERS stream 1 (GET /feed)
Client > Server : HEADERS stream 3 (GET /avatar.png)
Client > Server : HEADERS stream 5 (GET /ads)
Server -> Client : DATA stream 3 (avatar, fast)
Server -> Client : DATA stream 1 part 1
Server -> Client : DATA stream 5 (ads)
Server -> Client : DATA stream 1 part 2, end
%%

! Example: what connection reuse saves
! A mobile app makes 20 API calls on start-up to a server 100 ms away (one round trip, RTT = 100 ms).
! New connection per request, with TCP and TLS 1.2: about 1 RTT for TCP + 2 for TLS + 1 for the request = 4 RTT = 400 ms each. Even with six in parallel, about 4 rounds × 400 ms ≈ 1.6 s.
! HTTP/2 with one reused connection: 3 RTT of setup once (300 ms), then all 20 requests go out together and come back in about 1 RTT: roughly 400 ms in total. With TLS 1.3 (1 RTT handshake) it is about 300 ms.

## REST
**REST** (representational state transfer) is an architectural style on top of HTTP. In practice it means: resources identified by URLs, standard methods (GET, POST, PUT, PATCH, DELETE) with their standard meanings, standard status codes, and usually JSON bodies (lesson 02.01 covers designing them).

Strengths:
- **Universal**: every language, browser, proxy, CDN and command-line tool already speaks it. A partner can integrate with `curl` in five minutes.
- **Cacheable**: GET responses can be cached by browsers and CDNs using standard headers.
- **Easy to debug**: requests and responses are readable text; you can inspect them in browser developer tools.
- **Loosely coupled**: clients can ignore fields they don't use, so servers can add fields freely.

Weaknesses:
- **Verbose payloads**: JSON repeats every field name in every object, and numbers are stored as text.
- **No enforced schema**: the contract lives in documentation (often an OpenAPI spec) rather than being checked by the compiler. A typo in a field name is a runtime bug.
- **Over-fetching and under-fetching**: a fixed endpoint returns more than a screen needs, or a screen needs five calls to assemble.
- **Request/response only**: streaming needs extra mechanisms such as server-sent events or WebSockets.

## gRPC
**gRPC** is an RPC (remote procedure call) framework, open-sourced by Google in 2015. You define services and messages in a `.proto` file using **Protocol Buffers** (protobuf), a compact binary serialisation format:

```
service Pricing {
  rpc GetQuote (QuoteRequest) returns (Quote);
  rpc WatchPrices (WatchRequest) returns (stream Price);
}
message QuoteRequest { string ride_id = 1; int32 distance_m = 2; }
message Quote { int64 price_cents = 1; string currency = 2; }
```

A compiler (`protoc`) generates **client stubs** and **server skeletons** in many languages from this file. Calling a remote service then looks like calling a local function: `quote = pricing.GetQuote(request, timeout=0.2)`. The generated code handles serialisation, connection management and errors.

gRPC runs on HTTP/2 and supports four call types:
- **Unary**: one request, one response (like a normal function call).
- **Server streaming**: one request, a stream of responses (subscribe to price changes).
- **Client streaming**: a stream of requests, one response (upload a batch of location points).
- **Bidirectional streaming**: both sides send streams independently (a chat, or live driver locations to a matcher).

It also has built-in **deadlines**: the caller says "I need an answer within 200 ms", and the deadline travels with the call to downstream services, so work for a caller who has given up can be cancelled.

### Why protobuf is small
Protobuf doesn't send field names. Each field is sent as a small **tag** (field number plus a type code, usually 1 byte), then the value. Integers use **varints**, which take 1 byte for values under 128 and 2 bytes for values under 16,384. Strings are a length followed by the bytes.

! Example: the same object in JSON and protobuf
! JSON: `{"id":12345,"name":"Ana","active":true}` is 39 bytes.
! Protobuf, with id = 1, name = 2, active = 3: id is 1 tag byte + 2 varint bytes = 3; name is 1 tag + 1 length + 3 characters = 5; active is 1 tag + 1 byte = 2. Total: 10 bytes, about a quarter of the JSON.
! Parsing is cheaper too: no text scanning, no number parsing from digits, no field-name string comparisons. Across billions of internal calls a day, smaller messages and cheaper parsing save real CPU and network cost.

%%bars Size of the same small record in different encodings, in bytes. Binary formats drop field names and text-encoded numbers.
JSON, pretty-printed | 52 | ~52 bytes
JSON, compact | 39 | 39 bytes
JSON, gzipped (one tiny object) | 50 | ~50 bytes, no gain
*Protobuf | 10 | 10 bytes
%%

The `.proto` schema also gives you **type checking** and a clear contract between teams. Field numbers make it evolvable: add new fields with new numbers and old clients ignore them (lesson 01.11 covers the rules).

The downsides:
- **Browsers can't call gRPC directly**, because they don't expose the low-level HTTP/2 control gRPC needs. You need a proxy layer (gRPC-Web or a translating gateway).
- **Payloads aren't human-readable**; debugging needs tools like `grpcurl`.
- **HTTP caches and CDNs don't understand it**: every call is a POST to a method path.
- **Load balancing needs care.** gRPC keeps long-lived HTTP/2 connections and multiplexes all calls over them. A Layer 4 load balancer balances *connections*, so once a client is connected to one backend, all its calls go there. You need a Layer 7 balancer that balances individual calls, or client-side load balancing (lesson 02.06).

## GraphQL in brief
**GraphQL** lets the client send one query naming exactly the fields it wants, across related objects: "this user's name, their last 10 orders, and each order's first item's image". The server resolves it against a typed schema and returns exactly that shape. It fixes over-fetching and the many-round-trips problem for complex UIs, especially mobile apps on slow networks.

The costs: HTTP caching is harder (queries are usually POSTs with varied bodies), a single clever query can be very expensive (so servers need depth and cost limits), and naive resolvers cause the N+1 query problem (lesson 02.10 shows how DataLoader batches them). GraphQL is common as a **backend for frontend** layer that sits in front of REST or gRPC services.

%%layers What sits under a gRPC call. Each layer adds one capability; HTTP/3 would swap TCP for QUIC on UDP.
Generated stub | typed function call in your language
Protocol Buffers | compact binary messages from the .proto schema
*HTTP/2 | streams, multiplexing, header compression, flow control
TLS | encryption and server identity
TCP | reliable, ordered byte stream
%%

## Why REST outside, gRPC inside
| | Edge (public clients) | Internal (service to service) |
| Who calls | Browsers, mobile apps, third parties | Your own services |
| Who controls both ends | No one: clients vary and update slowly | You, in one organisation |
| Needs | Universal support, caching, easy debugging, stable public contract | Low latency, small payloads, strict typed contracts, streaming, deadlines |
| Good fit | REST (or GraphQL) | gRPC |

At the edge you don't control the clients. They're written in every language, run behind proxies, and need to be debuggable by outside developers. REST's universality and cacheability win. Inside, you control both ends, call volumes are huge, and the main risks are latency, CPU cost and teams breaking each other's contracts. gRPC's compact encoding, generated typed clients, multiplexing, streaming and deadlines win. An API gateway often translates between the two (lesson 02.05).

%%matrix REST, gRPC and GraphQL compared on the properties that usually decide the choice.
Property | REST | gRPC | GraphQL
Works from any browser | yes | no, needs a proxy | yes
Standard HTTP caching | yes | no | partial, with care
Compact payloads | no, JSON text | yes, protobuf | no, JSON text
Enforced typed schema | partial, OpenAPI optional | yes | yes
Streaming | partial, SSE or WebSockets | yes, 4 modes | partial, subscriptions
Easy to debug by hand | yes | partial, needs tools | yes
%%

! Example: ride-hailing
! The rider app calls REST endpoints on the API gateway: `POST /v1/rides {pickup, dropoff}`. The gateway authenticates the user and translates the call into gRPC.
! Inside, the ride service calls the pricing service with a unary gRPC call and a 150 ms deadline, and the matching service with another. The driver location service streams position updates to the matcher over a bidirectional gRPC stream: thousands of small protobuf messages per second on one HTTP/2 connection, with no per-message connection or header cost.
! The rider app gets live driver positions through a WebSocket from the gateway, since browsers and most mobile HTTP stacks handle that more easily than raw gRPC.

## Common mistakes
- **Exposing gRPC directly to third parties** who expect REST and curl.
- **Assuming HTTP/2 solves everything**: TCP-level head-of-line blocking still hurts on lossy mobile networks.
- **Putting a Layer 4 load balancer in front of gRPC** and wondering why one backend is overloaded.
- **REST without pagination or versioning**, or gRPC with reused field numbers.

## In an interview
Default to REST for client-facing APIs. Mention gRPC for high-volume internal calls, especially with streaming or tight latency budgets, and note the gateway that translates between them. If the client needs flexible, nested data for many screens, mention GraphQL as a BFF layer.

> Takeaway: REST wins at the edge because every client, proxy and cache understands it; gRPC wins inside because binary, schema-checked, multiplexed calls with deadlines and streaming are cheaper and safer at high volume. HTTP/2 multiplexes streams on one connection, and HTTP/3 removes TCP's head-of-line blocking.

?? Public clients like browsers, mobile apps and third-party developers need something universal, cacheable by standard HTTP caches and CDNs, and easy to debug with everyday tools, which is REST over HTTP with JSON. Between internal services the company controls both ends, so it can use gRPC's compact protobuf encoding, generated typed clients, HTTP/2 multiplexing, deadlines and streaming to cut latency, CPU and bandwidth at very high call volumes and to catch contract mistakes at compile time.

## The transport layer's job
**IP** (Internet Protocol) moves packets between machines, but it promises nothing. Packets can be lost when a router's queue overflows, duplicated, corrupted, or delivered out of order because they took different paths. Each packet is limited in size too, typically about 1,500 bytes on Ethernet, so anything bigger must be split up.

The **transport layer** sits on top of IP and decides how much of that mess the application sees. It also adds **ports**, so one machine can run many services: IP gets the packet to the machine, the port gets it to the right program. The two classic transport protocols are **TCP** and **UDP**, and a newer one, **QUIC**, sits between them.

%%layers Where TCP and UDP sit. Applications pick a transport; everything below is shared.
Application | HTTP, DNS, video calls, games, database protocols
*Transport | TCP (reliable stream) or UDP (datagrams), ports
Internet (IP) | addresses, routing, best-effort packets
Link | Ethernet, Wi-Fi, mobile radio: frames of ~1,500 bytes
%%

## TCP: reliable, ordered streams
**TCP** (Transmission Control Protocol) gives the application the illusion of a reliable, ordered **byte stream**, like a pipe between two programs. Underneath, it works hard to maintain that illusion:
- **Handshake**: before data flows, client and server exchange **SYN**, **SYN-ACK**, **ACK**, agreeing on starting sequence numbers. That costs one round trip before the first byte of data. TLS encryption adds one more round trip with TLS 1.3, or two with TLS 1.2.
- **Sequence numbers and ordering**: every byte is numbered, so the receiver can put segments back in order and discard duplicates.
- **Acknowledgements and retransmission**: the receiver acknowledges what it has received. If the sender gets no acknowledgement within a timeout, or sees three duplicate acknowledgements (a sign that one segment went missing while later ones arrived), it sends the missing segment again.
- **Flow control**: the receiver advertises how much buffer space it has (the **receive window**), so a fast sender cannot overwhelm a slow receiver.
- **Congestion control**: the sender also limits itself to protect the network. It starts slowly (**slow start**, doubling its sending window each round trip), and when it detects loss, it assumes the network is congested and cuts its rate, then grows it again gradually.
- **Checksums** detect corrupted segments.

%%seq TCP's three-way handshake costs one round trip before any data flows, and lost segments are resent.
Client > Server : SYN (seq = x)
Server -> Client : SYN-ACK (seq = y, ack = x+1)
Client > Server : ACK + first data
Server -> Client : data segments 1, 2, 3
Client > Server : ACK 1, ACK 1 again (2 missing)
Server -> Client : retransmit segment 2
%%

TCP connections also have a lifecycle of their own, which matters when you run servers at scale:

%%state A simplified TCP connection lifecycle from the client side. The TIME-WAIT state can pile up on busy servers that open and close many short connections.
[*] -> Closed
Closed -> SYN-sent : connect(), send SYN
SYN-sent -> *Established : receive SYN-ACK, send ACK
Established -> FIN-wait : close(), send FIN
FIN-wait -> Time-wait : receive peer's FIN, send ACK
Time-wait -> Closed : wait 2 x max segment lifetime
%%

The side that closes first sits in **TIME-WAIT** for up to a minute or two, so delayed packets from the old connection can't be confused with a new one. A proxy opening and closing thousands of short connections per second can run out of local ports this way, which is one more reason to reuse connections (connection pooling, HTTP keep-alive).

### The price: latency and head-of-line blocking
TCP's guarantees cost latency in three places:
- **Setup**: one round trip for the handshake (plus TLS) before any data.
- **Slow start**: a new connection can't use the full bandwidth immediately; it ramps up over several round trips.
- **Head-of-line blocking**: if one segment is lost, the receiver has later segments sitting in its buffer, but TCP will not hand them to the application until the missing one arrives, because it promised order. Everything waits at least one more round trip.

For a file download, that is exactly what you want: every byte, in the right order, and a few extra milliseconds don't matter. For live audio, a packet that arrives 300 ms late is useless: the moment it described has already been played.

! Example: how packet loss limits TCP throughput
! A rough rule for a long-running TCP flow: throughput ≈ segment size / (RTT × √loss rate).
! With 1,460-byte segments, a 100 ms round trip and 1% packet loss: 1,460 bytes / (0.1 s × 0.1) = 146,000 bytes per second, about 1.2 Mbit/s, however fast the link is.
! Cut the loss to 0.01% and the limit rises tenfold, to about 12 Mbit/s. Cut the RTT to 10 ms (a nearby CDN server) and it rises another tenfold. This is why CDNs place servers close to users, and why modern congestion control algorithms such as BBR, which react to measured bandwidth and delay rather than to every loss, help so much on lossy mobile links.

## UDP: just send it
**UDP** (User Datagram Protocol) is almost nothing on top of IP: ports, a length and a checksum, in an 8-byte header (TCP's header is at least 20 bytes). It sends **datagrams** straight to the target with no connection setup, no acknowledgements, no retransmission, no ordering and no congestion control. Each datagram arrives whole, or not at all, and possibly out of order. The application gets each one as it arrives.

That makes UDP fast and lightweight, but the application must tolerate loss, duplicates and reordering, or handle them itself. Many UDP applications add exactly the reliability they need and no more: a sequence number to detect gaps, perhaps a retransmission for important messages only.

Where UDP is used:
- **DNS**: a lookup is one small question and one small answer. A TCP handshake would double the cost. If the reply is lost, the client simply asks again after a short timeout.
- **Voice and video calls**: a call with a moment of static is better than one that is perfectly clear but a second behind. Codecs conceal lost packets (interpolating audio, repeating the last video frame) rather than wait for them.
- **Online games**: the latest position of a player matters, not an old one. If update 1,041 is lost, update 1,042 replaces it 16 ms later.
- **Live streaming**, telemetry, and other time-sensitive data.
- **QUIC** itself, which builds a full reliable protocol on top of UDP.

%%timeline A video call over UDP when one packet is lost. The receiver conceals the gap and keeps playing instead of waiting.
[Sender] 0 ms | frames 1, 2, 3 sent, 20 ms apart
[Network] 20 ms | *frame 2 packet lost
[Receiver] 60 ms | plays frame 1
[Receiver] 80 ms | frame 2 missing: conceal from frame 1
[Receiver] 100 ms | plays frame 3 on time
%%

### The abuse problem
Because UDP has no handshake, the source address on a datagram is never verified. That makes it easy to abuse:
- A **UDP flood** sends huge volumes of datagrams to random ports. The server burns resources checking for a listening program and replying with "port unreachable" messages.
- **Reflection and amplification attacks** send small requests with a forged source address (the victim's) to servers that send large replies, such as open DNS resolvers, so the victim is flooded with replies it never asked for.

Defences include rate limiting replies, dropping unexpected traffic at the network edge, and absorbing attacks across a large distributed network (a key service of DDoS protection providers). Protocols built on UDP, such as QUIC, add their own address validation before sending large responses.

## QUIC: the modern middle ground
**QUIC** runs over UDP but rebuilds reliability, ordering, congestion control and encryption in user space (in the application or a library, rather than in the operating system kernel). It is the transport under **HTTP/3**. Its key properties:
- **Independent streams**: like HTTP/2, many streams share one connection, but each stream has its own ordering. A lost packet only stalls the stream it belongs to; the others keep flowing.
- **Faster setup**: the transport and TLS 1.3 handshakes are combined into one round trip. Reconnecting to a known server can send data in the very first packet (**0-RTT**), with care, because 0-RTT data can be replayed by an attacker and so should only be used for idempotent requests.
- **Connection migration**: a connection is identified by a connection ID, not by the IP address and port. When a phone switches from Wi-Fi to mobile data and its IP changes, the connection survives.
- **Always encrypted**, including most of the transport metadata, which also stops middleboxes from ossifying the protocol.
- **Evolves faster**: because it lives in user space, browsers and servers can ship improvements without waiting for operating system updates.

%%compare Head-of-line blocking when one packet of stream B is lost. TCP stalls everything; QUIC stalls only stream B.
[HTTP/2 over TCP]
Packet 2 lost -> TCP holds packets 3 to 9 -> Streams A, B, C all wait
- One loss delays every stream
- Worse on lossy mobile networks
[*HTTP/3 over QUIC]
Packet 2 lost (stream B) -> QUIC delivers A and C -> Only B waits
+ Losses stay local to one stream
+ 1-RTT setup, survives network changes
- More CPU per byte than kernel TCP
%%

| | TCP | UDP | QUIC |
| Setup | Handshake (1 RTT, plus TLS) | None | 1 RTT including TLS, sometimes 0 |
| Delivery | Reliable, ordered | Best effort | Reliable, ordered per stream |
| Head-of-line blocking | Yes, whole connection | No | Only within a stream |
| Congestion control | Yes, in kernel | None (app's job) | Yes, in user space |
| Typical use | Web, APIs, databases, file transfer | DNS, VoIP, games, live media | HTTP/3 |

! Example: video call app
! Signalling (join a room, mute, chat messages) goes over WebSockets on TCP, because those messages must not be lost, and a 100 ms delay on a chat message is invisible.
! The audio and video media go over UDP (via WebRTC, using RTP packets). Audio is sent in 20 ms packets. With 2% loss, about 1 packet in 50 is missing; the codec fills each gap with a plausible guess, and listeners rarely notice.
! Over TCP, each lost packet would hold up everything behind it for at least one extra round trip, say 80 ms. The player would have to keep a larger buffer to hide those stalls, adding permanent delay to the conversation, which is exactly what makes calls feel awkward.

## In interviews
Default to TCP (usually via HTTP) for almost everything. Bring up UDP only when the problem is real-time media, games or similar data where low latency beats completeness, and say why: "UDP because a late frame is worse than a dropped frame." Mention QUIC and HTTP/3 if the question involves mobile clients on lossy networks or connection setup latency.

## Common mistakes
- **"UDP is faster, so use it for the API."** Then you rebuild reliability, ordering and congestion control yourself, badly.
- **Forgetting that UDP has no congestion control**, so a careless UDP sender can flood a network.
- **Ignoring connection setup cost**: opening a new TCP plus TLS connection per request to a distant server wastes several round trips each time.
- **Assuming TCP means data arrived.** TCP acknowledges receipt by the other machine's kernel, not that the application processed it. Application-level acknowledgements are still needed for business guarantees.

> Takeaway: TCP trades latency for reliability and order, which suits downloads, APIs and databases. UDP trades reliability for speed and leaves loss handling to the application, which suits real-time media where stale data is worthless. QUIC rebuilds reliable streams on UDP without connection-wide head-of-line blocking.

?? In a call or game, data is only useful if it is fresh. TCP would hold back every later packet until a lost one is retransmitted, causing freezes and forcing extra buffering delay, whereas UDP delivers whatever arrives and the app conceals small gaps or simply uses the next update. A file download needs every byte in the right order and doesn't care about a few milliseconds of delay, so TCP's handshake, retransmission, ordering and congestion control are exactly right.

## Two boxes that both "route requests"
Architecture diagrams often show a load balancer and an API gateway in the same spot, just behind the client, so it is easy to treat them as the same thing. Both receive requests and forward them somewhere else. But they solve different problems, and confusing them leads to designs where nobody handles authentication, or where a "load balancer" is expected to enforce per-user quotas it cannot even see.

A **load balancer** spreads traffic for **one service** across many identical instances. It answers: "which copy of this service handles this request?" It cares about health, capacity and even distribution.

An **API gateway** is the single entry point for clients into **many different services**. It answers: "which service handles this request, and what must happen before and after?" It cares about the API surface: routes, clients, keys, quotas, formats.

%%compare A load balancer spreads traffic across copies of one service; a gateway is the front door that knows the API and routes to many services.
[Load balancer]
Traffic -> LB -(round robin)-> Copies 1, 2, 3 of one service
+ Health checks, failover
+ Very fast, can be Layer 4
- Knows nothing about users or API keys
[API gateway]
Client -> Gateway: auth, rate limit -(/orders)-> Orders service
+ Auth, quotas, validation, translation
+ One public surface for many services
- Extra hop, more latency
- Critical component to keep up
%%

## What a load balancer does
Load balancing spreads traffic across a group of servers so that none is overloaded, and steers around servers that fail. Load balancers can be dedicated hardware appliances, software (HAProxy, NGINX, Envoy) or managed cloud services (AWS ALB and NLB, Google Cloud Load Balancing). They work at one of two levels:
- **Layer 4** (transport): routes by IP address and port without reading the request. It forwards TCP connections or UDP packets to a backend. It is very fast (millions of packets per second per node) and works for any protocol, but it can't see URLs, headers or users.
- **Layer 7** (application): terminates the HTTP connection, reads the request, and can route by path, host, header or cookie. It can also terminate TLS, add headers, and retry idempotent requests on another backend. It costs more CPU and adds a little latency.

Its core features: **health checks** (stop sending to backends that fail), **algorithms** for picking a backend (round robin, least connections, hashing), **TLS termination**, and **connection management**. Lesson 02.06 covers these in depth.

## What an API gateway does
Without a gateway, every client would need to know dozens of service addresses, make many calls per screen, speak each service's protocol, and authenticate separately with each. Every service would reimplement token checks, rate limits and logging. The gateway gives clients one front door and centralises those cross-cutting concerns:
- **Routing**: `/users/*` to the user service, `/orders/*` to the order service, `/v2/search` to the new search service. Routing by API path is the gateway's core job.
- **Authentication and authorisation**: verify the token (signature, expiry, scopes) once at the edge, so services don't each reimplement it. The gateway usually forwards the verified identity to services in a trusted header.
- **Rate limiting and quotas** per client, per user or per API key: "free tier: 1,000 calls a day; paid: 100 per second".
- **Request validation**: reject malformed requests (bad JSON, missing fields, oversize bodies) before they reach your services.
- **Protocol translation**: accept REST and JSON from the client, call gRPC internally (lesson 02.03).
- **Composition**: one client call that fans out to several services and merges the results, saving round trips on slow mobile networks.
- **Response transformation and caching**: strip internal fields, reshape responses for a client version, cache public GETs.
- **Observability**: consistent access logs, metrics per route and per client, and a trace ID added to every request.
- **API lifecycle**: versioning, API key issuance, developer portals and usage billing, especially for public APIs.

Products include Kong, Tyk, AWS API Gateway, Apigee, Azure API Management, and Envoy-based gateways.

%%seq One request passing through a gateway. Each step can reject the request before any backend service does work.
Client > Gateway : GET /v1/orders/981 + Bearer token
Gateway > Gateway : validate JWT signature, expiry, scope
Gateway > Gateway : rate limit: user 42 at 37 of 100 per min
Gateway > Gateway : route /v1/orders/* to orders service
Gateway > Orders LB : gRPC GetOrder(981), user=42, trace=ab12
Orders LB > Orders pod 3 : forward
Orders pod 3 -> Gateway : Order message
Gateway -> Client : 200 JSON, X-RateLimit-Remaining: 63
%%

### How rate limiting works at the gateway
The most common algorithm is the **token bucket**. Each client has a bucket that holds up to B tokens and refills at R tokens per second. Each request takes one token; if the bucket is empty, the request gets **429 Too Many Requests** with a `Retry-After` header. B controls how big a burst is allowed; R controls the sustained rate. With many gateway instances, the counts must be shared (usually in Redis) or split per instance, otherwise a client could get N times its limit by spreading calls across N gateways.

! Example: a token bucket in action
! A partner's API key has a bucket of B = 20 tokens refilling at R = 5 per second.
! At 12:00:00 the partner fires 30 requests at once. The first 20 succeed (bucket now empty) and the other 10 get 429 with `Retry-After: 1`.
! Over the next second the bucket refills 5 tokens. If the partner then sends steadily at 5 per second, every request succeeds. If it sends 8 per second, 3 of every 8 are rejected. The partner's average can never exceed 5 per second, while short bursts of up to 20 are absorbed smoothly.

## Backends for frontends
A single gateway serving web, iOS, Android and partner APIs tends to grow a tangle of client-specific logic. A common variation is **Backends for Frontends (BFF)**: one gateway per client type. The mobile BFF returns small, pre-composed payloads tuned for slow networks; the web BFF returns richer data; the partner API is stable and versioned slowly. Each BFF is often owned by the team that builds that client, so they can change it without negotiating with everyone else.

%%tree Backends for frontends: one edge layer per client type, each shaped for its client, all calling the same internal services.
Edge
  Web BFF | rich pages, server-side rendering
  *Mobile BFF | small composed payloads, one call per screen
  Partner API gateway | stable v1 contract, API keys, quotas
Internal services
  Users
  Orders
  Catalogue
  Payments
%%

## How they fit together
In practice you use both, in layers. The gateway is itself a horizontally scaled service, so there is a load balancer in front of the gateway fleet. Behind the gateway, each backend service runs many instances, so there is a load balancer (or client-side balancing, or a service mesh sidecar) in front of each service too.

%%layers The usual layering from the internet inward. Gateways handle API concerns; load balancers handle distribution at each tier.
DNS and CDN | resolve api.example.com, serve cached static content
Edge load balancer | Layer 4 or 7, TLS termination, spreads across gateways
*API gateway fleet | auth, rate limits, validation, routing, translation
Service load balancers | one per service, health checks, algorithms
Service instances | stateless copies of each service
%%

The gateway's main costs:
- **An extra network hop**: typically 1 to 5 ms with auth and routing, more if it calls an external identity provider on every request (cache token verification keys instead).
- **A critical component**: if the gateway is down, everything is down. It must be redundant across zones, with capacity for peak traffic plus a failed zone.
- **A risk of becoming a monolith**: if business logic creeps into the gateway ("just add this discount rule here"), every team ends up deploying through it. Keep it to cross-cutting concerns.

The lines between the two have blurred: Layer 7 load balancers can do path routing and some auth, and many gateways have built-in load balancing. A **service mesh** (Istio, Linkerd) moves load balancing, retries, mutual TLS and metrics into a sidecar proxy next to every service, handling internal (east-west) traffic, while the gateway handles external (north-south) traffic.

| | Load balancer | API gateway |
| Distributes across | Identical copies of one service | Different services |
| Understands | Connections (L4) or HTTP (L7) | Your API: routes, clients, keys, quotas |
| Typical features | Health checks, algorithms, TLS termination | Auth, rate limits, validation, translation, composition |
| Added latency | Microseconds (L4) to about 1 ms (L7) | About 1 to 5 ms |
| Examples | AWS NLB/ALB, HAProxy, NGINX | Kong, AWS API Gateway, Apigee |

%%matrix Which box can do which job. A Layer 4 balancer can't do anything that requires reading the request.
Capability | L4 load balancer | L7 load balancer | API gateway
Spread load, health checks | yes | yes | yes
TLS termination | partial, passthrough or terminate | yes | yes
Route by URL path | no | yes | yes
Verify user tokens | no | partial, some products | yes
Per-user or per-key rate limits | no | partial, basic | yes
REST to gRPC translation | no | no | yes
Compose several services | no | no | yes
%%

## In interviews
Draw the gateway at the edge, say it handles routing, authentication and rate limiting, put load balancers in front of each service tier, and move on. Don't spend minutes on it unless asked. If asked to go deeper, discuss where the rate limit counters live, how the gateway is made highly available, and what happens to latency.

! Example: food delivery app
! The mobile app sends every call to api.example.com. DNS points that at a regional edge load balancer, which terminates TLS and spreads requests across 12 gateway instances in three zones.
! The gateway checks the JWT (signature verified locally with a cached public key, about 0.1 ms), applies a 100 requests per minute limit per user using counters in Redis (about 0.5 ms), and routes `/restaurants` to the catalogue service and `/orders` to the order service, translating to gRPC.
! For the home screen, the mobile BFF fans out to catalogue, promotions and recent orders in parallel and returns one response, so the phone makes one request instead of three over a 150 ms mobile link.
! Behind each service, another load balancer spreads requests across its instances using least connections. If one zone fails, the edge balancer stops sending to its gateways within seconds of failed health checks.

## Common mistakes
- **Expecting an L4 load balancer to authenticate or rate-limit per user.** It can't see users.
- **Putting business logic in the gateway.**
- **A single gateway instance**, which is a single point of failure.
- **Per-instance rate limits** that let clients multiply their quota by the number of gateways.
- **Calling the identity provider on every request** instead of verifying signed tokens locally.

> Takeaway: a load balancer spreads load across copies of one service, using health checks and an algorithm; a gateway is the front door that knows your API and handles routing, auth, rate limits, validation and translation. Real systems use both, in layers, and keep business logic out of the gateway.

?? A plain Layer 4 load balancer sees only IP addresses and ports, so it cannot: (1) authenticate users by verifying tokens or API keys, (2) route requests by URL path or header to different services, or (3) apply per-user or per-key rate limits and quotas. Gateways also validate requests, translate REST and JSON into gRPC, combine responses from several services into one, and add consistent logging, metrics and tracing.

## Why load balancers exist
A **load balancer** sits in front of a group of servers (the **backends**, or the **pool**) and decides which one handles each request or connection. It gives you:
- **No traffic to unhealthy servers**: it detects failed backends and routes around them.
- **No single overloaded server**: work is spread so queues stay short.
- **No single server as a point of failure**: losing one backend costs a fraction of capacity, not the service.
- **TLS termination**: the balancer decrypts traffic, so backends skip the encryption work and certificates live in one place.
- **Painless deploys and scaling**: drain a backend (stop new requests, let current ones finish), update it, add it back; add servers under load and remove them at night.
- **Optional affinity**: pin a client or a key to one server when that helps (sessions, caches).

The catch is that a single load balancer is itself a single point of failure. Load balancers therefore run in pairs or clusters:
- **Active-passive**: one serves traffic while a standby watches its heartbeats. If heartbeats stop, the standby takes over the shared virtual IP address (for example with the VRRP protocol, as keepalived does), usually within a few seconds.
- **Active-active**: several balancers all serve traffic. DNS returns several addresses, or routers spread packets across them using equal-cost multipath routing (ECMP). Managed cloud load balancers work this way behind a single name.

Load balancing only works well when backends are **stateless**. If session data lives on one server, the balancer must pin users to it, and losing that server loses the sessions. Keep that state in a shared store such as Redis instead (lesson 01.08).

## Layer 4 vs Layer 7
- **Layer 4** load balancers look at IP addresses and ports only. They pick a backend when a connection opens and forward its packets (often by rewriting addresses with NAT, or by passing packets through untouched with direct server return). They are cheap and fast, handle millions of packets per second, and work for any TCP or UDP protocol: databases, MQTT, custom protocols. But every request on a connection goes to the same backend, and they can't route on content.
- **Layer 7** load balancers terminate the client's connection, read the HTTP request, pick a backend **per request**, and open (or reuse) their own connection to it. They can route by path, host, header or cookie (send `/video` to video servers, `/billing` to hardened servers), retry a failed idempotent request on another backend, add headers, and compress responses. This costs more CPU and adds a little latency, typically well under a millisecond.

%%compare Layer 4 balances connections using only addresses and ports; Layer 7 reads each HTTP request and can route on its content.
[Layer 4]
Packet -(IP and port only)-> L4 LB -(whole connection)-> Server 2
+ Very fast, any protocol
+ Can pass TLS through untouched
- One backend per connection
- Can't route on path or headers
[Layer 7]
HTTP request -(path, headers, cookie)-> L7 LB -(/api/*)-> API pool
+ Per-request balancing and routing
+ Retries, header rewriting, TLS termination
- More CPU per request
- HTTP-family protocols only
%%

The connection-versus-request difference matters a lot for long-lived connections. An HTTP/2 or gRPC client keeps one connection open for hours and sends thousands of requests over it (lesson 02.03). Behind a Layer 4 balancer, all of those requests land on one backend. With a few large clients, a few backends get almost all the load. A Layer 7 balancer, or client-side load balancing where the client itself spreads calls across a list of backends, fixes this.

## The algorithms
The algorithm decides which backend gets the next request. The differences show up clearly when request costs vary.

**Round robin** sends to each server in turn: A, B, C, A, B, C. It is fair when every request costs the same and every server is the same size. When some requests are expensive, a server that happens to receive several slow ones in a row builds a queue while others sit idle, because round robin doesn't look at how busy anyone is.

**Weighted round robin** gives bigger servers a bigger share. With weights 5 and 1, the first server gets 5 of every 6 requests. Useful when the pool mixes instance sizes, or to send a small share of traffic to a canary.

**Dynamic weighted round robin** adjusts weights from observed latency or errors, so a server that slows down automatically gets less.

**Least connections** sends each request to the server with the fewest requests currently in flight. A server stuck on slow work naturally has more open requests, so it gets skipped until it catches up. In simulations with varying request costs, least connections handles overload better than round robin, dropping the fewest requests.

**Least time / PEWMA** (peak exponentially weighted moving average) scores each server by its recent latency multiplied by its in-flight requests, reacting quickly to latency spikes. It tends to give the best latency, at the cost of more complexity and tuning.

**Hashing** (on client IP, or a key such as user ID or URL) sends the same key to the same server every time. That's useful for caches and sessions. Plain `hash % N` remaps almost every key when N changes, so balancers offer **consistent hashing** (NGINX's `hash $key consistent`), where adding a server only moves a small share of keys (lesson 02.07).

**Power of two random choices** picks two servers at random and sends to the less loaded of the two. It sounds too simple to work, but it is remarkably effective: the maximum queue length drops dramatically compared with picking one at random. It is especially useful when many load balancers share the same backends, because no balancer can see the others' counts, and "least connections" computed on partial information makes all of them pile onto the same apparently idle server.

%%timeline Round robin with uneven request costs. Server A receives two slow reports in a row and builds a queue, while B and C finish quickly and sit idle.
[Server A] 0 ms | report request, 900 ms
[Server B] 0 ms | page request, 20 ms
[Server C] 0 ms | page request, 20 ms
[Server A] 30 ms | *2nd report queued behind the 1st
[Server B] 30 ms | idle
[Server C] 30 ms | idle
[Server A] 60 ms | 3rd request queued, waits ~1.8 s
%%

An important detail: in such simulations, round robin often has the best **median** latency but poor **p95 and p99**, because most requests land on idle servers while a few wait behind slow ones. Averages hide the problem; always judge an algorithm on its tail.

! Example: round robin versus least connections with mixed requests
! Three servers each handle one request at a time. 90% of requests take 10 ms; 10% are reports that take 1,000 ms. Requests arrive every 50 ms, so on average each server is about 70% busy (an average request costs 0.9 × 10 + 0.1 × 1,000 = 109 ms).
! Round robin: every third request goes to server A regardless. When A gets a report, the next requests assigned to A queue behind it: A receives one every 150 ms, so about 6 or 7 requests pile up during the report and wait up to a second each. With reports arriving every half second or so across the pool, this keeps happening, so p99 is around a second or more, even though B and C are often idle.
! Least connections: while A is busy with the report, its in-flight count is 1 and B and C are usually at 0, so new requests go to them. Only when all three are busy does anyone queue. The p99 drops to roughly the cost of a report plus a little, and short requests rarely wait behind long ones.

## Health checks and recovery
A load balancer is only as good as its knowledge of which backends are healthy:
- **Passive checks**: watch real traffic. NGINX counts failures and marks a server down after `max_fails` failures within `fail_timeout`, then tries it again after that period.
- **Active checks**: probe an endpoint such as `/health` on a schedule (every 5 to 10 seconds), with thresholds: unhealthy after 3 consecutive failures, healthy again after 2 successes. The thresholds stop one dropped probe from flapping a server in and out.
- **What to check**: a liveness endpoint that only says "the process is running" misses a server whose database connection is broken. A deep check that tests every dependency can take the whole fleet out when a shared dependency blips. A common compromise is to check the server's own critical resources and leave shared dependencies to circuit breakers.
- **Slow start**: a server that comes back (or a new one) ramps up its weight gradually, for example over 30 seconds, so it isn't overwhelmed while its caches and connection pools are cold, and knocked over again.
- **Connection draining**: when removing a server, stop new requests but let in-flight ones finish (for example within 30 seconds).
- **Backup servers** only receive traffic when all primaries are down.

%%state A backend's life as the load balancer sees it. Thresholds and slow start stop servers from flapping in and out.
[*] -> Healthy
Healthy -> Suspect : 1 failed check
Suspect -> Healthy : next check passes
Suspect -> *Unhealthy : 3 failures in a row
Unhealthy -> Slow start : 2 checks pass
Slow start -> Healthy : weight ramps to full over 30 s
Healthy -> Draining : removed for deploy
Draining -> Removed : in-flight requests done
%%

**Sticky sessions** use a cookie (or the client IP) to pin a client to one server. They're convenient for legacy apps that keep sessions in memory, but they make load uneven (one heavy user stays on one server) and hurt when that server dies or is drained.

| Algorithm | Best when |
| Round robin | Requests and servers are uniform |
| Weighted round robin | Servers differ in size, or for canary traffic |
| Least connections | Request cost varies a lot, or connections are long-lived (WebSockets) |
| Least time / PEWMA | You care most about tail latency and can afford complexity |
| Consistent hash | Server holds per-key state, such as a cache |
| Power of two choices | Many balancers share the same backends |

Server 1, round robin | 14200 | 14,200
Server 2, round robin | 6100 | 6,100

! Example: chat servers with WebSockets
! A chat service runs 3 servers and holds about 30,000 open WebSockets in total. Each socket stays open from minutes to many hours.
! Round robin counts connections evenly at the moment they open, but some users disconnect after a minute while others stay all day, and a server restarted for a deploy comes back empty while the others keep their sockets. After a few hours one server might hold 14,000 live sockets and another 6,000. The busy one runs hot on memory and CPU.
! Least connections sends each new socket to the server with the fewest open ones, so the counts converge back towards 10,000 each, and a freshly restarted server fills up quickly instead of staying underused.

## Common mistakes
- **One load balancer with no redundancy.**
- **Layer 4 in front of gRPC or HTTP/2**, pinning heavy clients to one backend.
- **Judging algorithms by average latency.** Look at p99.
- **Health checks that are too shallow or too deep**, missing broken servers or ejecting the whole fleet together.
- **No slow start**, so recovered servers get knocked straight back down.
- **Sticky sessions instead of a shared session store.**

## In an interview
Draw a load balancer in front of every stateless tier, say it is redundant, and name the algorithm with a reason: "least connections, because report requests vary widely in cost" or "consistent hashing on user ID, because each server caches user data". Mention health checks and draining for deploys.

> Takeaway: round robin is fine for uniform work; least connections wins when request cost varies or connections are long-lived, and hashing when servers hold per-key state. Balance requests, not just connections, for HTTP/2 and gRPC, make the balancer itself redundant, and judge algorithms on p99, not the average.

?? Least connections beats round robin when requests vary widely in cost or duration, or when connections are long-lived, like WebSockets or streaming. ## Why route by key at all
Most load balancing (lesson 02.06) treats backends as interchangeable: any server can handle any request. Sometimes that is wasteful or impossible, and you want **the same key to go to the same server every time**:
- **Cache locality**: if all requests for user 42 hit the same cache server, that server holds user 42's data and the hit rate is high. Spread randomly, every server must cache everything, so each needs the full working set in memory, and a new item is missed once on every server before it is cached everywhere.
- **Stateful connections or sessions**: a chat room, a multiplayer game session or a collaborative document lives on one server, and every participant must reach that server.
- **Partitioned data**: a database or cache shard owns part of the key space, and requests for a key must go to its owner.

The routing function is a **hash** of the key: a function that turns any key into a number that looks random, so keys spread evenly. The question is how to map that number to a server, especially when servers are added or removed.

## The problem with modulo
The obvious approach is `server = hash(key) % N`. It spreads keys evenly and is trivial to compute. It works until N changes.

Going from 3 servers to 4 changes the result of the modulo for most keys. A key keeps its server only if `hash % 3` happens to equal `hash % 4`, which is true for just a quarter of keys. So **75% of keys move**. In general, going from N to N + 1 servers moves N / (N + 1) of the keys: 90% when going from 9 to 10.

For a cache tier, that is a disaster. Almost every lookup misses at once, and the database behind the cache is suddenly hit with nearly the full read load it was protected from. The same happens when a server crashes: N drops by one and almost everything moves.

! Example: a cache stampede from modulo hashing
! A cache tier of 9 servers absorbs 95% of 200,000 reads per second, so the database sees 10,000 per second, which is comfortable.
! One cache server dies. With `hash % 8` instead of `hash % 9`, about 8 / 9 ≈ 89% of keys now map to a different server, where they are not cached. The hit rate drops from 95% to roughly 10% until caches refill.
! The database briefly receives about 180,000 reads per second, eighteen times its normal load. It slows down, requests time out, and the cache can't refill because the database can't answer. One server failure has become an outage.

## The hash ring
**Consistent hashing** places both servers and keys on a circle of hash values (for example 0 to 2³² − 1, wrapping around). Each server is hashed (by name or address) to a position on the ring. A key belongs to the **first server found by walking clockwise** from the key's position.

- **Adding a server** only takes the keys between it and the previous server counter-clockwise. On a ring of 0 to 100 with servers at 15, 50 and 75, adding a server at 90 takes only the keys from 75 to 90 (previously owned by the server at 15, which wrapped round): about 15% of the key space, instead of 75%.
- **Removing a server** hands only its keys to the next server clockwise. Every other key stays where it was.

On average, only about **1/N of keys move** when one server joins or leaves, which is the minimum possible: the new server has to get its fair share from somewhere.

%%compare Adding a fourth server. Modulo hashing reshuffles most keys; a hash ring moves only the slice the new server takes over.
[Modulo: hash % N]
3 servers -(add 1)-> 4 servers -> 75% of keys move
- Cache hit rate collapses
- Same on any server failure
[*Hash ring]
3 servers -(add 1 at 90)-> 4 servers -> ~25% move, all to the new server
+ Other servers keep their keys
+ Failure moves only the dead server's keys
%%

%%bars Share of keys that move when a fifth server joins a pool of four. Modulo moves almost everything; a ring moves only the new server's fair share.
hash % N | 80 | 80%
*Hash ring | 20 | 20%, the minimum possible
%%

## Virtual nodes
With only a few servers, their positions on the ring are random, so the gaps between them are uneven. One server may own 40% of the ring and another 10%. And when a server leaves, its entire slice lands on one neighbour, doubling that neighbour's load.

The fix is to place each physical server at **many points** on the ring, called **virtual nodes** (vnodes): for example 100 to 200 points per server, each at the hash of "server-A#1", "server-A#2", and so on. Each server now owns many small slices scattered around the ring:
- **Even ownership**: the sizes of many small slices average out. With 100 or more vnodes per server, each server's share is typically within about 10% of the mean.
- **Spread-out failover**: when a server leaves, its many small slices go to many different neighbours, so the extra load is shared across the whole pool.
- **Weighting**: a server with twice the memory gets twice as many vnodes and so twice the keys.

The cost is a bigger lookup table (servers × vnodes positions, kept sorted so the lookup is a binary search), which is still tiny: 50 servers × 200 vnodes is 10,000 entries.

### Variations in real systems
- **Redis Cluster** splits the key space into **16,384 fixed hash slots** (`CRC16(key) % 16384`) and assigns ranges of slots to nodes. Rebalancing means moving whole slots between nodes. The client keeps a slot-to-node map and is redirected (`MOVED`) if it is out of date. Fixed slots give the same benefit as a ring with explicit control over what moves.
- **Cassandra** and **DynamoDB** use rings with virtual nodes to place data partitions on storage nodes.
- **Load balancers** such as NGINX (`hash $key consistent`), HAProxy and Envoy (ring hash and Maglev) offer consistent hashing for routing requests.

%%tree A Redis Cluster slot map. Keys hash to one of 16,384 slots, and each node owns ranges of slots that can be moved one at a time.
Key space: 16,384 slots
  Node A | slots 0 to 5460
  Node B | slots 5461 to 10922
    *Slot 7000 moving to Node D
  Node C | slots 10923 to 16383
  Node D | new, receiving slots
%%

## The hot-key problem
Consistent hashing balances **keys**, not **traffic**. If one key is enormously popular (a celebrity's profile, a viral video, the front page during a big news event), its server is overloaded while others are idle. Every other key that happens to live on that server suffers too: their requests queue behind the hot key's, so latency rises for cold keys that did nothing wrong.

Ways to handle hot keys:
- **Replicate hot keys** to several servers and spread reads across the copies. Writes must update all copies, so this suits read-heavy hot keys.
- **Salt the key**: store it under `video123#1` to `video123#8`, so it maps to eight positions on the ring; readers pick a suffix at random. Writers update all eight.
- **A local cache in front**: each application server keeps the hottest few hundred keys in its own memory for a second or two, so most reads for the hot key never reach the cache tier at all.
- **Monitor and rebalance adaptively**: detect keys whose request rate crosses a threshold and apply the above automatically.

! Example: salting a viral key
! A cache server can handle about 20,000 reads per second. A video goes viral and its metadata key receives 60,000 reads per second, all to one server.
! Salting into 8 copies spreads that to 7,500 reads per second per copy, on (most likely) 8 different servers, each comfortably under capacity alongside its normal traffic.
! The cost: an update to the video's metadata now writes 8 keys, and a reader may briefly see an old copy while the writes land. For view counts and titles, that's fine.

## Consistent hashing with bounded loads
Replication and salting need you to know which keys are hot. A refinement developed at Google gives a hard guarantee instead: **cap each server's load**. Compute the average load per server and set a capacity of `(1 + ε)` times that average, for example ε = 0.25 means 125% of average. A request goes to its key's usual server unless that server is at its cap, in which case it walks clockwise to the next server with room.

%%flow Bounded loads: if the key's own server is already at its cap, the request walks on round the ring to the next server with room.
Request for key k -(hash ring)-> Server B at 125% cap -(full, skip)-> Server C at 90% -(under cap)-> *Served by C
%%

This guarantees that no server exceeds the cap, while keeping most keys on their usual server: overflow only happens to requests that would have overloaded someone. The parameter ε trades the two goals: a small ε keeps load very even but moves more requests away from their home server (more cache misses); a large ε keeps more keys at home but allows more imbalance. When servers are added or removed, the expected number of moved keys grows as ε shrinks, roughly in proportion to 1/ε².

Google uses it in Cloud Pub/Sub. Vimeo added it to HAProxy for routing video requests to cache servers, and cut the bandwidth of their busiest cache servers by almost 8 times, because popular videos no longer overloaded single servers.

! Example: an image cache tier
! 10 cache servers sit in front of object storage, chosen by consistent hash of the image ID with 150 virtual nodes each. Each server holds about 10% of images.
! An 11th server is added. About 1/11 ≈ 9% of images move to it; the other 91% keep hitting warm caches. With modulo hashing, about 91% would have moved.
! A viral image would overload one server. With bounded loads at ε = 0.25, once that server reaches 1.25 times the average load, extra requests spill to the next server on the ring, which fetches the image once and then serves it from its own cache. The hot image ends up warm on two or three servers, and no server goes over 125%.

## Common mistakes
- **`hash % N` for anything stateful**, which reshuffles everything on every change.
- **Too few virtual nodes**, leaving one server with twice its share.
- **Assuming even keys means even load**: hot keys break that.
- **A poor hash function** (or hashing sequential IDs with something weak), which clusters keys.
- **Clients with different ring views**, for example one app server that hasn't learned about a new node, so the same key goes to two places. Distribute membership through one source of truth.

## In an interview
Whenever a design has a cache tier, sharded storage or sticky stateful servers, say "consistent hashing with virtual nodes, so adding or losing a node moves only about 1/N of keys". Then raise hot keys yourself, and offer replication, salting, a local cache or bounded loads as the fix.

> Takeaway: route a key to the same server to keep its cache warm or its state in one place. Use consistent hashing so membership changes move only about 1/N of keys, virtual nodes to even out ownership and spread failover, and replication, salting or bounded loads for keys that are hot.

?? Routing the same key to the same backend keeps that server's cache warm for it (a high hit rate without every server caching everything), keeps per-key state such as a session or chat room in one place, and matches requests to the shard that owns the data. If one backend gets too hot, for example because a viral key lives on it, its queue grows and latency and errors rise for every key it owns, even cold ones, and it may fall over and push its load onto a neighbour. Fixes are replicating or salting the hot key, a local cache in front, or consistent hashing with bounded loads so overflow spills to the next server on the ring.

## Events are a public API
When a service publishes events, other teams build on them. The billing team consumes OrderPlaced to raise invoices; the data team loads it into the warehouse; the email team sends confirmations; a fraud model scores it. Some of those consumers you know about. Others were added last month by a team you have never met.

The event's shape is therefore a **contract**, just like a REST endpoint (lesson 02.01), with two extra difficulties:
- **Producer and consumers deploy at different times.** There is no moment when everyone upgrades together. For days or weeks, old producers and new consumers (and new producers and old consumers) run side by side.
- **Old events stick around.** In a log such as Kafka, events may be retained for days, months or forever, and a new consumer may replay all of them from the beginning. Your newest code must still read the oldest events.

Getting the contract right means agreeing on three things: what the event **means**, what it **carries**, and how it is allowed to **change**.

%%tree One producer, many consumers, some of which the producer never hears about. Any change to the event's shape reaches all of them.
Orders service | publishes OrderPlaced v1
  Event log | keeps events for days or forever
    Billing | raises invoices
    Email | sends confirmations
    Data warehouse | may replay from the start
    *Teams you haven't met | added last month
%%

## What kind of event is it?
"Event-driven" covers four different patterns, and confusing them causes muddled designs.

**Event notification**: "Order 123 was placed." The event is small: an ID, a type, a timestamp. A consumer that needs details calls back to the producer's API. This is very decoupled (the producer knows nothing about consumers), but every consumer that needs data adds load on the producer, and the overall flow is hard to see because no one place describes it.

**Event-carried state transfer**: the event includes the data consumers need: customer name, address, line items, totals. Consumers keep their own copy of what they need and never call back. That cuts load on the producer and removes the runtime dependency (the producer can be down and consumers still have their data). The costs: data is duplicated across services, events are larger, consumers are eventually consistent, and the event's schema is now a much bigger contract.

**Event sourcing**: every change to an entity is stored as an event (OrderCreated, ItemAdded, AddressChanged, OrderShipped), and the **event log is the source of truth**. Current state is rebuilt by replaying the events. You get a full audit trail and can rebuild or reinterpret history (add a new report and compute it for all past orders). But schema changes are hard, because you must still understand events written years ago, and replays of large histories take time, so you add snapshots.

**CQRS** (command query responsibility segregation): separate models for writing (commands) and reading (queries), often with events flowing from the write side to build read-optimised views. Useful for complex domains or very different read and write loads. It adds a lot of complexity and is often used where a single model would do.

%%compare Two styles of event for the same order. A notification is small and makes consumers call back; state transfer carries what they need.
[Event notification]
OrderPlaced {order_id: 123} -> Consumer -(GET /orders/123)-> Orders API
+ Tiny contract, easy to evolve
+ Consumers always get fresh data
- Every consumer loads the producer
- Producer down: consumers stuck
[*Event-carried state transfer]
OrderPlaced {order_id, customer, items, total} -> Consumer stores its copy
+ No call-backs, producer can be down
+ Consumers fully independent
- Bigger contract, harder to change
- Copies are eventually consistent
%%

Be explicit about which you are publishing. A common failure is a "notification" event that grows a few fields at a time until it is a half-complete state transfer that nobody designed.

### Name events as facts
Events describe things that **have happened**, in the past tense: OrderPlaced, PaymentFailed, AddressChanged. A message that asks for something to happen (SendEmail, ChargeCard) is a **command**, with a single intended recipient and a different contract. Mixing the two makes it unclear who is responsible for what.

## A standard envelope: CloudEvents
If every producer invents its own event format, every consumer writes custom parsing, and generic tooling (routing, tracing, dead-letter handling) can't work across events. **CloudEvents**, a CNCF (Cloud Native Computing Foundation) project that graduated in January 2024, defines a common **envelope** of metadata around your payload:
- **Required**: `id` (unique per event from a source), `source` (which system produced it, as a URI), `specversion` (the CloudEvents version), and `type` (such as `com.shop.order.placed`).
- **Optional**: `time`, `subject` (the entity it's about, such as the order ID), `datacontenttype` (such as `application/json`), and `dataschema` (a link to the schema of the payload).

It defines bindings for HTTP, Kafka, AMQP, MQTT, WebSockets and others, and is supported by services such as Amazon EventBridge and Azure Event Grid.

%%layers A CloudEvents envelope: standard metadata around your payload. Routers and tools read the envelope; only consumers read the data.
id, source | unique event ID and the producer that emitted it
type, subject | what happened, and to which entity
specversion, time | envelope version and when it happened
dataschema, datacontenttype | which schema version, which format
*data | your payload, e.g. the order
%%

Even if you don't use CloudEvents itself, every event should carry the same basics:
- A **unique ID**, so consumers can deduplicate. Most brokers deliver at least once, and consumers must handle repeats (lesson 02.02).
- A **type** and a **source**.
- A **timestamp** of when the thing happened (not when it was published).
- A **schema version**, so consumers know how to parse it.
- Often a **correlation or trace ID**, to follow one business transaction across services.

## Evolving the schema safely
The data inside the event will change. The question is which changes are safe, and in which order to deploy them.

A **schema registry** (Confluent Schema Registry is common with Kafka; AWS Glue and others exist) stores every version of each event's schema (in Avro, Protobuf or JSON Schema). Producers register the schema they write with, and each message carries a small schema ID. The registry rejects a new schema version that would break the agreed **compatibility mode**:

%%matrix Schema compatibility modes. Each mode allows different changes and implies a different deploy order.
Mode | Add optional field | Remove optional field | Add required field | Rename or retype | Deploy first
Backward (common default) | yes | yes | no | no | consumers
Forward | yes | yes | yes | no | producers
Full | yes | yes | no | no | either
None | yes | yes | yes | yes | coordinate by hand
%%

- **Backward compatible** (Confluent's default): consumers using the **new** schema can read data written with the **old** one. Allowed: delete fields, add optional fields with defaults. Upgrade **consumers first**, then producers.
- **Forward compatible**: consumers using the **old** schema can read data written with the **new** one. Allowed: add fields, delete optional fields. Upgrade **producers first**.
- **Full**: both directions at once. Only add or remove optional fields with defaults. Upgrade in **any order**.
- **Transitive** variants (BACKWARD_TRANSITIVE and so on) check a new version against **all** earlier versions, not just the previous one. This matters when consumers may replay old data from a log: version 7 must still read events written with version 1.

The practical rules, whatever the mode:
- **Add fields as optional, with defaults.**
- **Never change a field's type or meaning.** Changing `total` from a decimal in pounds to an integer in pence, under the same name, silently corrupts every consumer.
- **Never reuse a removed field's name** (or, in protobuf, its number).
- **Consumers must ignore fields they don't recognise**, rather than failing on them. This "tolerant reader" habit is what makes adding fields safe.
- **For a truly breaking change, publish a new event type or topic** (`OrderPlaced.v2`), run both in parallel, migrate consumers one by one, and retire v1 only when its last consumer has moved.

%%seq The registry stops a breaking change before it ships. The producer's build registers the new schema, and the registry checks it against the compatibility mode.
Producer CI > Registry : register OrderPlaced v3 (renames total to amount)
Registry > Registry : check FULL_TRANSITIVE against v1, v2
Registry -> Producer CI : 409 incompatible: field total removed without default
Producer CI > Registry : register v3b (adds optional amount, keeps total)
Registry -> Producer CI : OK, schema id 57
%%

! Example: adding a discount to OrderPlaced
! Version 1 has `{order_id, customer_id, total}`. The team adds `discount_code` as an optional field defaulting to null, and registers it.
! Old consumers receive events with an extra field and ignore it; they keep working. New consumers read `discount_code` when present, and see null for old events in the log. Both directions work, so the deploy order doesn't matter.
! Months later someone proposes renaming `total` to `amount`. The registry, set to FULL_TRANSITIVE, rejects it, because old consumers would no longer find `total`, and new consumers couldn't read old events. The team instead adds `amount` alongside `total`, writes both for a deprecation period, migrates consumers to `amount`, and only then considers dropping `total` in a new event type.

! Example: a breaking change done properly
! The payments team needs OrderPlaced to carry money as `{amount_minor: 1999, currency: "GBP"}` instead of a float `total: 19.99`, because floats caused rounding bugs. That changes type and meaning, so no compatibility mode allows it in place.
! Week 1: the producer starts publishing `OrderPlaced.v2` to a new topic, alongside v1. Week 2 to 6: each consumer team switches to v2 at its own pace; a dashboard shows which consumer groups still read v1. Week 7: v1 has no consumers left, and the producer stops publishing it. The log keeps old v1 events for replays, with a small adapter that converts them to v2 on read.

## Ordering and other semantics
The contract covers behaviour as well as shape:
- **Ordering**: is order guaranteed per entity? In Kafka, events with the same key (for example `order_id`) go to the same partition and stay in order; across keys there is no order. Consumers should not assume more than you promise.
- **Delivery**: at least once is normal, so say so, and include the ID for deduplication.
- **Completeness**: does OrderUpdated carry the full new state, or only the changed fields? Full state is easier for consumers and safer if one event is lost.
- **Retention**: how far back can a consumer replay?

## Common mistakes
- **Leaking internal database rows as events**, so every column change is a breaking change for other teams.
- **Changing a field's meaning without changing its name.**
- **Strict consumers that reject unknown fields**, turning every addition into an outage.
- **No event ID**, so duplicates can't be detected.
- **Assuming global ordering** across keys or partitions.

## In an interview
When a design publishes events, name a few with their key fields, say whether they carry state or just notify, and say how they evolve: "events carry an ID, type, timestamp and schema version, go through a schema registry in backward-compatible mode, and we only add optional fields; breaking changes get a new event version".

> Takeaway: treat events as a public API. Know whether an event is a notification or carries state, give every event an ID, type, source, time and version, enforce compatibility with a schema registry, evolve only by adding optional fields that tolerant readers ignore, and publish a new event version for anything breaking.

?? The new field must be optional (with a default, typically null), and old consumers must ignore fields they don't recognise instead of rejecting the event. Then events in the new format still parse for them (forward compatibility), while new consumers can still read old events in the log that lack the field (backward compatibility). No existing field may change its name, type or meaning, and a schema registry enforcing the compatibility mode should check the new schema before it ships.

## Every remote call can fail in three places
A local function call either returns or throws. A remote call has a third outcome: **you don't know**. To see why, look at where a call to another service can break:
- **On connection**: the request never reached the server (DNS failure, connection refused, TLS handshake timeout). The server did nothing. **Safe to retry.**
- **During processing**: the server received the request, started the work, and something broke (a crash, a dependency error). If all the work was in one database transaction that rolled back, nothing happened and a retry is safe. If the work had side effects outside the transaction (it called a card network, sent an email), state may be half done.
- **On response**: the server finished the work, but the reply was lost (the connection dropped, a proxy timed out, the client gave up a millisecond too early). The client sees a timeout and has **no idea whether the charge went through**.

The third case is why "just retry" is dangerous. **A timeout does not mean the operation failed.** It means you don't know. Retrying a payment that actually succeeded charges the customer twice.

%%seq The unknown case: a timeout doesn't tell the client whether the server did the work. The idempotency key makes the retry safe.
Client > Server : POST /charges $50, key k1
Server > Server : charge succeeds, store k1 + result
Server -> Client : reply lost
Client > Client : timeout after 2 s
Client > Server : retry, same key k1
Server > Server : k1 already done
Server -> Client : same 201 result, charged once
%%

## Timeouts
Set a timeout on **every** remote call. Without one, a caller waits forever on a dependency that has hung, holding a thread, a connection and memory. Enough of those and the caller runs out of resources too (the cascading failure in lesson 02.02).

Use two timeouts:
- A **connection timeout** (how long to wait to establish the connection), usually short: tens to a few hundred milliseconds inside a data centre, since a healthy server accepts connections almost instantly.
- A **request timeout** (how long to wait for the whole response), based on how long the operation normally takes.

Choosing the request timeout is a trade-off:
- **Too long**, and threads pile up waiting on a dead dependency, and users wait for an answer that never comes.
- **Too short**, and you time out healthy requests that were just a little slow, retry them, and add load, sometimes to a server that was only slow because it was busy.

A good method: decide what false timeout rate you can accept (say 0.1%), and set the timeout at the dependency's matching latency percentile (p99.9). Add margin for long network paths. Then check what the timeout actually covers: in some clients, DNS lookup and TLS setup sit outside it, in others inside.

A real failure of this kind: a service had a 20 ms timeout on calls to a dependency, comfortably above that dependency's normal latency. After every deployment, error rates spiked, because new processes had to establish fresh TLS connections, and the TLS handshake alone took longer than 20 ms. The fix was to open and warm connections at startup, before taking traffic.

### Deadlines across a chain
In a chain of calls, a fixed timeout per hop doesn't add up correctly. If the user-facing request has 1 s and service A calls B with a 1 s timeout, which calls C with a 1 s timeout, C may keep working long after the user has gone. Better to pass a **deadline** ("this must finish by 12:00:00.950") down the chain, as gRPC does. Each service uses the time remaining, and drops work whose deadline has already passed.

## Retries are selfish
A retry improves your chance of success by using more of the server's capacity. That is fine for rare, **transient** errors: a dropped connection, a single overloaded instance, a leader election. When the server is failing **because it is overloaded**, retries make it worse: every failed request comes back two or three times, so a server struggling at 100% of capacity is now asked for 200% or 300%, and recovery is delayed or prevented.

Retries also **multiply across layers**. If a request passes through five layers and each layer retries 3 times on failure, a failure at the bottom can produce 3⁵ = 243 attempts on the bottom service for one user request.

%%bars Worst-case attempts reaching the bottom service when every layer makes up to 3 attempts. Retrying at one layer only keeps it at 3.
1 layer retries | 3 | 3 attempts
2 layers | 9 | 9
3 layers | 27 | 27
4 layers | 81 | 81
*5 layers | 243 | 243
%%

So:
- **Retry at one layer only**, usually the one closest to the failure or the top-level caller, and let the others fail fast.
- **Cap attempts**: a small maximum, typically 2 or 3 in total.
- **Use a retry budget**: a token bucket where each retry costs a token and successful calls slowly refill it. While tokens last, retry freely; when they run out, stop retrying (or retry only at a slow fixed rate). This caps retries at, say, 10% of traffic, so retries can never triple the load. AWS SDKs have used this approach since 2016.
- **Only retry what can succeed.** A 400 Bad Request or 403 Forbidden will fail the same way next time. Retry connection errors, timeouts on idempotent calls, 503 and 429 (respecting `Retry-After`).
- **Only retry what is safe**: idempotent operations, or ones protected by an idempotency key.

%%tree Should this failed call be retried? Most of the decision is about whether a retry can succeed and whether it is safe.
Call failed
  4xx client error
    429 Too Many Requests | retry after Retry-After
    400, 401, 403, 404, 409 | don't retry: same answer
  Connection never established | retry: server did nothing
  Timeout or 5xx after sending
    Idempotent (GET, PUT) or has a key | *retry with backoff
    Not idempotent, no key | don't retry blindly: check status first
%%

## Exponential backoff with jitter
Retrying immediately rarely helps: whatever caused the failure is probably still there. Wait longer after each failure: **exponential backoff**, for example 100 ms, 200 ms, 400 ms, 800 ms, up to a cap such as 10 s.

Backoff alone has a problem. When a server has a brief outage, thousands of clients fail at the same moment. With identical backoff schedules, they all retry at the same moment too: at +100 ms, then +300 ms, then +700 ms. Each wave hits the server like a wall, a **thundering herd**, and can knock it over again just as it recovers.

**Jitter** adds randomness to each wait so retries spread out. A common form is **full jitter**: `sleep = random(0, min(cap, base × 2^attempt))`. Instead of 10,000 retries landing in the same millisecond, they spread evenly across the whole backoff window. The same idea applies to cron jobs, cache expiry times and periodic timers: if every client refreshes at exactly midnight or exactly every 60 seconds, add a random offset.

%%widget backoff Every client fails at once and retries five times with exponential backoff. Without jitter the retries land together in spikes; jitter spreads them out.
%%

! Example: backoff with and without jitter
! 10,000 clients lose their connection to a service at the same instant. Each retries with base 100 ms, doubling, cap 5 s.
! No jitter: all 10,000 retries arrive within a millisecond at +100 ms. If the service can take 2,000 requests per 100 ms, 8,000 fail and retry together at +300 ms, then again at +700 ms. The service sees periodic walls of thousands of requests and idles in between.
! Full jitter: the first retries are spread evenly over 0 to 100 ms, the second over 0 to 200 ms after that, and so on. The service sees a steady stream it can handle, and most clients succeed within their first two or three attempts.

## Idempotency keys
Timeouts and retries are only half of the story. The fix for the "lost response" case is making the operation **safe to repeat**, even when it isn't naturally idempotent like a POST that creates a charge. The standard design, used by Stripe and many payment APIs:
- The **client generates a unique key** per logical operation (for example a UUID) and sends it in an `Idempotency-Key` header. Every retry of the same operation reuses the same key.
- The server **stores the key together with the result** of the first attempt.
- If the same key arrives again, the server **returns the stored result** instead of doing the work again. If the first attempt is still in progress, it returns a "try again shortly" (409 or 429). If the first attempt broke halfway, the server resumes or completes it from where it stopped.

%%state The lifecycle of an idempotency key on the server. A retry finds the record and gets the stored answer instead of a second charge.
[*] -> New key
New key -> *Processing : insert key + request hash, start work
Processing -> Completed : work done, response stored
Processing -> Failed, retryable : dependency error, rolled back
Failed, retryable -> Processing : retry with same key
Completed -> Completed : retry returns stored response
Completed -> Expired : retention window ends
%%

Further rules, as applied in Amazon EC2's `RunInstances` API and similar systems:
- **Store the key and perform the change atomically**, in one database transaction, so you never record a key without doing the work, or do the work without recording the key.
- **Store the original request parameters** (or a hash of them). If the same key arrives with different parameters, return a validation error: the caller has a bug, and silently returning the old result would hide it.
- **Return a response that means the same as the first one**, not an error like "already exists". The caller should not need special handling for retries.
- **A late retry after the resource was deleted** still gets the original resource back (now shown as terminated), not a newly created one.
- **Don't derive the key from a hash of the parameters.** Two identical requests may both be intended: a user really might buy the same $5 item twice, or launch two identical servers.
- **Keys can't be kept forever.** Keep them for at least as long as clients might retry (Stripe keeps them 24 hours), and long enough to cover the resource's life plus a window after which late retries are assumed gone.

! Example: payment API
! The client sends `POST /charges` with `Idempotency-Key: 7f3c...` and `{amount: 2000, currency: "USD"}`.
! The server, in one transaction, inserts `(key 7f3c, request hash, status processing)` together with a pending charge record. It then calls the card network (which itself accepts an idempotency reference, so a resumed attempt can't double-charge), and in a second transaction marks the charge succeeded and stores the response (201, charge ID ch_91) on the key's row. The response is lost on the way back.
! The client times out after 2 s, waits 200 ms plus jitter, and retries with the same key. The server finds key 7f3c, sees the request hash matches, and returns the stored 201 with charge ID ch_91. The customer is charged once.
! If the client had sent the same key with `amount: 3000`, the server would return 422, because the key is tied to the original parameters.

## Common mistakes
- **No timeout**, or an infinite default in the HTTP client library.
- **Retrying at every layer**, multiplying load during an outage.
- **Retrying non-idempotent writes without a key.**
- **Backoff without jitter**, creating synchronised retry waves.
- **Retrying 4xx errors** that can never succeed.
- **Storing the idempotency key outside the transaction** that does the work.

## In an interview
For any write that matters (payments, orders, bookings), say: "Every call has a timeout. The client retries with exponential backoff and jitter, at most 3 attempts, only at the edge. Writes carry a client-generated idempotency key, stored with the result in the same transaction, so a retry after a lost response returns the original result." That one paragraph covers most of what interviewers look for.

> Takeaway: a timeout is not a failure, it is "unknown". Time out every call, pass deadlines down chains, retry sparingly at one layer with exponential backoff, jitter and a retry budget, and make writes safe to repeat with client-generated idempotency keys stored atomically with the result.

?? A timeout cannot tell the client whether the request never reached the server or whether the charge completed and only the reply was lost, so a blind retry may charge the customer twice. With an idempotency key, the client generates a unique key for the payment and sends the same key on every attempt. The server stores the key, the request parameters and the result atomically with the charge, and when the key arrives again it returns the stored result instead of charging again (or an error if the parameters differ), so retries become safe.

## Why batching helps
Almost every operation has a **fixed cost** on top of the work itself: a network round trip, a system call, a disk seek or flush, a transaction commit, a request's headers and authentication, a lock acquisition. If you do 1,000 operations one at a time, you pay that overhead 1,000 times. Group them into one batch and you pay it once.

Write it as a formula. If each call has a fixed overhead `F` and each item costs `c`, then the time per item with batch size `b` is `F / b + c`. As `b` grows, the overhead per item shrinks towards zero and throughput approaches the limit set by the per-item work alone. Batching is one of the most effective throughput tools there is, and it shows up everywhere: database bulk inserts, Kafka producers, TCP itself (Nagle's algorithm), GPU inference, log shippers, and the `WHERE id IN (...)` query that replaces a hundred single-row lookups.

%%compare The same 1,000 messages sent one at a time and in batches of 100. The work per message is the same; the overhead is paid ten times instead of a thousand.
[One at a time]
1,000 messages -(1,000 round trips)-> Broker -> 1,000 x overhead
- ~1 s of round trips on one connection
- 1,000 small disk writes
[*Batched]
1,000 messages -(10 batches of 100)-> Broker -> 10 x overhead
+ ~20 ms of round trips
+ 10 large sequential writes
- Each message waits for its batch
%%

! Example: the arithmetic of amortisation
! A client sends records to a service 1 ms away (a 1 ms round trip). Processing each record takes 10 µs on the server. The client sends on one connection, one request at a time.
! Batch size 1: each record costs 1 ms + 0.01 ms ≈ 1.01 ms, so about 990 records per second.
! Batch size 100: each batch costs 1 ms + 100 × 0.01 ms = 2 ms, so 100 / 0.002 = 50,000 records per second, fifty times more.
! Batch size 1,000: 1 ms + 10 ms = 11 ms per batch, about 91,000 records per second. The gain is flattening, because the per-item work now dominates. Past this point bigger batches buy little throughput and cost more latency and memory.

%%bars Records per second on one connection as batch size grows, with a 1 ms round trip and 10 µs of work per record. Gains are huge at first, then flatten.
Batch of 1 | 990 | ~1,000/s
Batch of 10 | 9100 | ~9,100/s
Batch of 100 | 50000 | 50,000/s
*Batch of 1,000 | 91000 | ~91,000/s
Batch of 10,000 | 99000 | ~99,000/s
%%

## Kafka: batching all the way down
Kafka is a good case study because its design is built around two inefficiencies: **too many small I/O operations**, and **excessive byte copying**. Its fixes:

**Message sets.** The protocol is built around a "message set" abstraction that groups messages. The producer sends a batch in one network request, amortising the round trip over many messages. The broker appends the whole batch to its log in one write. Consumers fetch large, linear chunks at a time. Network packets get bigger and disk writes become large **sequential appends**, which are fast even on spinning disks (around 200 MB/s sequential, against about 2 MB/s for random 8 KB writes).

**Producer knobs.** Two settings control batching on the producer:
- `batch.size`: the maximum bytes in one batch per partition (16 KB by default). When a batch is full, it is sent immediately.
- `linger.ms`: how long the producer waits for more messages before sending a batch that is not full. Historically the default was 0 (send as soon as possible); recent versions default to a few milliseconds. A larger linger gives fuller batches and higher throughput, but each message waits longer.

**One binary format everywhere.** Producer, broker and consumer share the same message format, so batches pass from the producer's memory, through the broker's disk, to the consumer without being decoded and re-encoded.

**Zero-copy.** The naive way for a program to send a file to a socket takes four copies and two system calls: disk to the kernel's page cache, page cache to a buffer in the application, application buffer back into a kernel socket buffer, socket buffer to the network card. Kafka uses the `sendfile` system call, which tells the kernel to send data from the page cache straight to the network card. The application never touches the bytes, so serving many consumers costs little CPU.

%%compare Sending log data to a consumer. The naive path copies the bytes through the application; sendfile hands them from the page cache straight to the network card.
[Naive read and write]
Disk -> Page cache -> App buffer -> Socket buffer -> NIC
- 4 copies, 2 system calls
- CPU and memory bandwidth spent on copying
[*sendfile (zero-copy)]
Disk -> Page cache -(sendfile)-> NIC
+ No copies through the application
+ Data already cached serves many consumers
%%

**The page cache as the cache.** Rather than keeping its own in-process cache, Kafka relies on the operating system's page cache. On a machine with 32 GB of RAM, that gives roughly 28 to 30 GB of cache with no garbage-collection pauses, and the cache survives a broker process restart.

**Batch compression.** The producer compresses a whole batch at once (gzip, Snappy, LZ4 or zstd). A batch of similar JSON events compresses far better than each event alone, because the field names and common values repeat across messages: ratios of 5 to 10 times are common for a batch, against very little for a single small message. The broker decompresses the batch only to validate it (for example, that the record count matches the header), writes it to disk still compressed, and sends it to consumers compressed; consumers decompress. Compression thus saves network, disk and page cache all at once.

## DataLoader: batching inside one request
The same idea works at the application layer. GraphQL resolvers naturally ask for data one item at a time: load a user, then each of their 10 friends, then each friend's best friend. That is the **N+1 problem**: one query for the list, then one query per item. A single GraphQL query can easily make 13 or 130 database calls.

**DataLoader** (a small library from the GraphQL ecosystem, with ports in most languages) fixes it. Every call to `loader.load(key)` returns a promise, and the loader collects all keys requested during one tick of the JavaScript event loop. At the end of the tick, it calls your **batch function once** with all the keys, so 13 queries become a few `WHERE id IN (...)` queries.

%%seq DataLoader collects the keys requested in one tick of the event loop and makes one batched call, then hands each caller its own result.
Resolver A > DataLoader : load(user 7)
Resolver B > DataLoader : load(user 9)
Resolver C > DataLoader : load(user 7)
DataLoader > DataLoader : end of tick: keys [7, 9], 7 cached once
DataLoader > Database : SELECT * FROM users WHERE id IN (7, 9)
Database -> DataLoader : 2 rows
DataLoader -> Resolver A : user 7
DataLoader -> Resolver B : user 9
DataLoader -> Resolver C : user 7 (same object)
%%

Its rules:
- **The batch function must return results in the same order and the same length as the keys**, filling gaps with null or an error. A database returns rows in any order, so you re-order them by key.
- **It also caches by key** within its lifetime, so loading the same user twice returns the same result without a second query.
- **Create a new loader per request.** A loader shared across requests would leak one user's cached data into another user's response (a security bug), and its cache would grow forever.
- **`maxBatchSize`** caps the batch (useful when the database limits the size of `IN` lists), and **`batchScheduleFn`** can wait longer than one tick (for example a few milliseconds) to collect more keys, which adds latency.

## The cost: latency and blast radius
Batching makes the **first item wait for the last**. An item that arrives just after a batch was sent waits for the whole next window. Every batching system has a knob that trades latency for throughput: Kafka's `linger.ms`, DataLoader's schedule function, a database driver's flush interval, a log shipper's flush period. Most also have a **size cap**, so a batch is sent as soon as it is full, without waiting out the timer. "Send when 100 items **or** 10 ms, whichever comes first" is the standard shape.

%%timeline A batch with a 10 ms linger and a size cap of 5. Messages that arrive early wait longest; a full batch leaves without waiting for the timer.
0 ms | message 1 arrives, timer starts
3 ms | messages 2 and 3 arrive
10 ms | *timer fires: batch of 3 sent, message 1 waited 10 ms
11 ms | message 4 arrives, new timer starts
12 ms | messages 5 to 8 arrive: batch is full
12 ms | batch of 5 sent at once, no wait for timer
%%

Other costs:
- **Partial failure.** If one item in a batch fails (a constraint violation in a bulk insert, one invalid record), you must decide: fail the whole batch (simple, but one bad record blocks 999 good ones), or return per-item results (more complex for both sides). Most good batch APIs return per-item status.
- **Memory.** Items wait in memory before being sent, and a slow downstream means batches pile up. Buffers must be bounded (lesson 02.11).
- **Loss on crash.** An unsent batch lives only in memory. If the process crashes, it is gone, unless you write it to disk first or the producer only acknowledges its own callers after the batch is sent.
- **Uneven latency.** Items arriving just after a batch leaves wait the longest, so batching widens the latency distribution.
- **Bigger blast radius.** A batch that hits a timeout or a poison record affects every item in it.

| Knob | Turn up | Turn down |
| Max wait (linger) | Fuller batches, higher throughput | Lower per-item latency |
| Max size | Fewer round trips, better compression | Smaller failures, less memory, less per-batch latency |

! Example: analytics events from a mobile SDK
! The SDK used to send one HTTP request per tap, about 50 requests per minute per active user. With 2 million concurrently active users, that is about 1.7 million requests per second at the ingestion endpoint, each paying for TLS records, headers and an authentication check, and draining phone batteries by waking the radio constantly.
! Batching every 10 seconds or every 100 events, whichever comes first, cuts that to about 6 requests per minute per user: about 200,000 requests per second, an eightfold reduction, and each gzip-compressed batch is about a fifth of its raw size.
! The cost: events show up on dashboards up to 10 seconds later, and an app crash could lose the unsent batch, so the SDK appends events to a small file on disk and deletes them only after the server acknowledges the batch. Duplicate sends after a crash are removed on the server using each event's ID.

## Common mistakes
- **No size cap**, so a burst creates one enormous batch that times out.
- **No time cap**, so a quiet period leaves items waiting indefinitely.
- **All-or-nothing batches** where one bad record blocks the rest.
- **Sharing a DataLoader between requests.**
- **Batching on a latency-critical path** (a user waiting on a click) with a long linger.

## In an interview
Mention batching whenever you see many small writes: event ingestion, logging, metrics, notification fan-out, bulk database inserts. Name both knobs ("flush every 50 ms or 500 records"), say what latency that adds, and say how you handle a failed item and a crash with unsent data.

> Takeaway: batching amortises fixed per-call costs (round trips, syscalls, commits, headers) over many items, often for tenfold or bigger throughput gains, and enables better compression and sequential I/O. You pay in latency, memory and blast radius, controlled by a maximum wait time paired with a maximum batch size.

?? Batching costs latency: items that arrive early wait for the batch to fill or for the timer to fire, so per-item latency rises and becomes more uneven. It also adds memory use, a larger blast radius when a batch fails (or harder per-item error handling), and possible loss of an unsent batch on a crash. The knob is the maximum wait time (such as Kafka's linger.ms or DataLoader's batch schedule), usually paired with a maximum batch size so a full batch is sent immediately.

## What backpressure is
**Backpressure** is resistance to the flow of data through software: input arrives faster than the system can turn it into output. The name comes from fluid in pipes, where a narrow section pushes back against the flow behind it. A web server receives more requests than its database can answer; a log shipper reads files faster than it can upload them; a producer publishes events faster than the consumer can process them.

Backpressure is not a bug in itself. It is a fact of any pipeline whose stages run at different speeds, and you must handle it somewhere. If you don't choose how, the system chooses for you, usually by **running out of memory**: the excess piles up in an unbounded buffer until the process is killed, losing everything in the buffer at once.

The classic illustration is the sitcom scene of a worker on a chocolate factory conveyor belt that runs too fast. The worker first sets chocolates aside to deal with later (**buffering**), then starts eating and hiding them (**dropping**). The proper fix would have been to slow the belt (**controlling the producer**).

%%flow A producer that outruns its consumer. The bounded buffer between them fills, and something must give.
Fast producer -(1,000 items/s)-> *Bounded buffer, filling at 800/s -(200 items/s)-> Slow consumer
%%

## The three strategies
There are three fundamental responses, plus scaling.

**1. Control the producer.** Tell the producer to slow down, or make it wait. Nothing is lost and memory stays flat. This is the best option whenever it is possible. Examples:
- **TCP flow control**: the receiver advertises how much buffer space it has left, and the sender stops when the window is zero. That's backpressure across machines, built into every TCP connection.
- **Node.js streams**: `writable.write()` returns `false` when the writer's internal buffer is above its high-water mark, and `pipe()` pauses reading until the `drain` event.
- **Blocking queues**: a producer thread calling `put()` on a full bounded queue simply blocks until there is room.
- **gRPC and HTTP/2** have per-stream flow-control windows; **RSocket** and **Reactive Streams** have explicit demand signals.

It is often impossible with users: you can't tell people to click less, or stop a sensor from measuring. But you can push back on them with a fast error (429 or 503) that tells their client to back off (lesson 02.13).

**2. Buffer.** Absorb bursts in a queue and let the consumer catch up when the burst passes. This is great for **short spikes**: a traffic burst that lasts seconds, a consumer pausing for a deploy. It doesn't help with a **sustained** imbalance: if the producer is always faster, the buffer just grows until it is full.

**Unbounded buffers are a leading cause of servers crashing with out-of-memory errors.** Consider copying a file by reading at 150 MB/s and writing at 100 MB/s, with an unbounded buffer in between: memory grows by 50 MB every second. A 6 GB file takes 40 seconds to read, and by then about 2 GB is sitting in memory. Always **bound buffers**, by size, by count, or by age.

**3. Drop.** Discard or sample some of the input. This is fine for data where only the latest value matters or where a sample is enough: mouse movements, metrics samples, live position updates, video frames in a real-time call. It is unacceptable for payments, orders or anything that someone will look for later. Choose *what* to drop: the oldest items (the newest are fresher), the newest (keep what you have already committed to), or a random sample.

**And: scale out, or accept it.** Add more consumers, if the work can be parallelised and the bottleneck isn't something shared like a database. Or accept a growing backlog when it causes no real harm (a nightly report that finishes an hour later).

%%compare The three ways to handle a producer that is faster than its consumer. Which one fits depends on whether you can slow the source and whether every item matters.
[*Control the producer]
Producer -(waits or is told 429)-> Consumer pace
+ Nothing lost, memory flat
- Not possible for users or sensors
- Slowness spreads upstream
[Buffer]
Producer -> Bounded queue -> Consumer
+ Absorbs short bursts
- Adds latency
- Must be bounded, or it ends in OOM

### Pull beats push
**Pull-based** systems handle backpressure naturally, because the consumer asks for the next N items only when it is ready: Reactive Streams' `request(n)`, async iterators, Kafka consumers polling for the next batch, workers pulling jobs from a queue. The consumer's pace sets the flow.

**Push-based** systems (webhooks, a server streaming events to clients, a message broker pushing to subscribers) must add explicit signals: credit or demand counts, acknowledgements with a maximum number unacknowledged (RabbitMQ's **prefetch** count), or HTTP 429 responses.

%%seq Pull-based flow control. The consumer grants credit for a few items at a time, so the producer can never get far ahead.
Consumer > Producer : request(3)
Producer -> Consumer : item 1
Producer -> Consumer : item 2
Producer -> Consumer : item 3
Producer > Producer : no credit left, wait
Consumer > Consumer : process items 1 to 3
Consumer > Producer : request(3)
Producer -> Consumer : item 4
%%

## When the buffer is a queue between services
A message queue between services (SQS, RabbitMQ, Kafka) is a buffer, and it needs special care. A queue lets producers keep succeeding while consumers are down or slow, which is often exactly the point. But **the work doesn't go away**: it waits, and someone has to catch up.

Queue systems are **bimodal**: they behave well when the backlog is near empty, and badly for a long time once it is not. Every message now waits behind the backlog, so latency jumps from milliseconds to minutes or hours, and it stays high until the backlog drains.

! Example: catching up after an outage
! Producers send 1,000 messages per second. Consumers normally process 1,000 per second, with capacity for up to 1,200.
! Consumers fail for one hour. The backlog grows to 1,000 × 3,600 = 3.6 million messages.
! When consumers return, they run flat out at 1,200 per second while 1,000 per second keep arriving, so the backlog shrinks by only 200 per second. Draining 3.6 million takes 18,000 s: **five hours**, during which every new message waits behind the backlog.
! With capacity for 2,000 per second (double), it would drain at 1,000 per second, in one hour. The rule of thumb: after an outage of T, you need double your normal capacity for another T just to catch up.

%%timeline A one-hour consumer outage with only 20% spare capacity. The backlog takes five times longer to drain than it took to build.
10:00 | consumers crash, backlog starts growing
11:00 | *consumers back: 3.6 million messages waiting
12:00 | backlog 2.9 million, new messages wait ~40 min
14:00 | backlog 1.4 million
16:00 | backlog drained, latency back to normal
%%

### Techniques for queues
- **Measure the age of the oldest message**, not just the count. "50,000 messages" means nothing without the processing rate; "oldest message is 12 minutes old" tells you exactly how far behind you are, and is what users feel.
- **Per-customer fairness**: in a multi-tenant queue, one customer's spike delays everyone. Rate-limit each producer, or **shuffle-shard** customers across several queues, so each customer maps to a small random subset of queues and a noisy one can only fill those.
- **Overflow and sideline queues**: move a heavy customer's excess, or old messages, to a separate queue so fresh work keeps flowing, then process the sideline when there is capacity.
- **Newest first**: for real-time data, process recent messages first and the backlog later (or never).
- **Drop stale messages** with a time to live (TTL) when newer data supersedes them.
- **Backpressure to producers**: reject or throttle new work for a workload whose backlog is too deep.
- **Limit concurrency per workload** using **Little's Law**: work in flight = arrival rate × time each item takes. At 100 messages per second, if a downstream call slows from 100 ms to 10 s, in-flight work grows from 10 to 1,000. Without a cap, that means 1,000 threads or connections, which can exhaust the consumer or crush the downstream.
- **Heartbeat long jobs**: extend the visibility timeout while working, so the queue doesn't redeliver the message to a second worker while the first is still busy.
- **Dead-letter queues** for messages that fail repeatedly (a "poison" message that always crashes the consumer), with an alarm, so one bad message doesn't block or loop forever.

%%bars Work in flight at a steady 100 messages per second as the time per message grows. Little's Law: in flight = arrival rate x latency.
100 ms per message | 10 | 10 in flight
1 s | 100 | 100
5 s | 500 | 500
*10 s | 1000 | 1,000 in flight
%%

! Example: notification fan-out
! A celebrity posts, creating 10 million push notifications within a minute. The push workers can send 50,000 per second, so the burst takes over three minutes to send even at full speed.
! The fan-out service writes to a bounded queue rather than calling the push service directly. Workers pull at their own pace (pull-based control), so the push provider is never asked for more than it can take.
! Each notification has a TTL of 30 minutes: if the backlog ever grows beyond that, stale notifications are dropped rather than buzzing phones hours after the event.
! Celebrity fan-outs go to a separate queue from ordinary users' notifications, so a direct message from a friend isn't stuck behind 10 million celebrity alerts. The alarm watches the oldest message's age in each queue.

## Common mistakes
- **Unbounded buffers and queues** "because we don't want to lose anything", which loses everything when the process dies.
- **Alarming on queue length instead of age.**
- **Scaling consumers into a shared bottleneck**: 50 consumers hammering one database go no faster than 10.
- **No dead-letter queue**, so one poison message blocks a partition.
- **Treating a queue as infinite capacity** that removes the need for capacity planning.

## In an interview
Whenever two stages run at different rates, say what happens when the fast one outruns the slow one: "workers pull from a bounded queue; we alarm on the oldest message's age; we drop location updates older than 30 seconds; and the API returns 429 when the backlog for a tenant passes a limit". Naming all three strategies, and choosing per data type, is what interviewers look for.

> Takeaway: when producers outrun consumers you can slow the producer, buffer within a limit, or drop what is replaceable, and pull-based designs make the first option natural. Unbounded buffers only postpone a crash. In queues, measure the age of the oldest message, plan spare capacity to catch up after outages, and isolate noisy producers.

(2) Buffer in a bounded queue to absorb bursts, alarming on the age of the oldest item, accepting that a sustained 2x imbalance will still fill it. (3) Drop or sample excess items when only recent data matters, such as position updates or metrics. You can also scale out the consumer to match the producer's rate, if the bottleneck isn't a shared resource.

@02.12
## Averages lie at scale
A service that responds within about 100 ms feels fluid to people; beyond a few hundred milliseconds it feels sluggish. Large services answer each user request by asking many servers at once: a web search query touches thousands of index servers, a social feed calls dozens of services, a product page assembles prices, stock, reviews and recommendations in parallel. The user waits for **the slowest** of those answers.

So a rare slow response on an individual server, which is harmless in a small system, becomes the **normal** experience at scale. The **tail** of the latency distribution (the p99, the p99.9: the slowest 1% or 0.1% of responses) stops being an edge case and starts deciding what most users see. This lesson explains why tails exist, how fan-out amplifies them, and the techniques large systems use to build a predictably fast whole out of unpredictable parts.

%%flow Fan-out amplifies the tail: the root must wait for every leaf, so the request is as slow as its slowest leaf.
User request -> Root server -(fan out to 100 leaves)-> *1 leaf hits its p99 -> Whole request slow
%%

## Why individual servers are sometimes slow
Even identical, well-tuned machines running the same code have occasional latency spikes. The causes are mostly shared resources and background work:
- **Contention** for CPU cores, processor caches, memory bandwidth and network with other processes on the same machine (and, in the cloud, with other tenants).
- **Background activity**: daemons, log rotation, compaction in storage engines, periodic health and metrics jobs.
- **Garbage collection pauses** in managed runtimes such as the JVM and Go, which can stall a process for milliseconds to, in bad cases, seconds.
- **Queueing** at several layers: in the server's request queue, in the kernel, in network switches. A request that arrives just behind a burst waits for the whole burst.
- **Hardware behaviour**: CPUs throttling under power or heat limits; SSDs running internal garbage collection, which can make some reads 100 times slower than usual; devices waking from power-saving states.
- **Cold paths**: a cache miss, a cold JIT, a new TLS connection.

You can reduce each of these, but not remove them all. So the realistic goal is not "no slow responses" but **"slow responses on parts don't become slow responses for users"**.

## The fan-out maths
If each server is slow (beyond its p99) 1% of the time, independently, then a request that needs **all** of N servers is fast only if every one of them is fast:

`P(request slow) = 1 − 0.99^N`

For N = 100: 0.99¹⁰⁰ ≈ 0.366, so about **63%** of requests are slow. Each server's p99 has become the requests' typical latency. Even at 1 slow response in 10,000 per server, a request touching 2,000 servers is slow 1 − 0.9999²⁰⁰⁰ ≈ 18% of the time.

%%bars Chance that a request sees at least one leaf at its p99, by fan-out width, in percent. Wide fan-out turns a 1% tail into the common case.
1 leaf | 1 | 1%
10 leaves | 9.6 | ~10%
40 leaves | 33 | ~33%
100 leaves | 63 | ~63%
*500 leaves | 99.3 | ~99%
%%

Real measurements at Google show the effect. In one service, a single leaf request had a p99 of 10 ms, but the p99 for waiting on all leaves was 140 ms. Waiting for just 95% of the leaves cut that p99 to 70 ms: **the slowest 5% of leaves caused half of the tail**.

%%widget tail 100 sample requests: each one waits for every leaf, so one slow leaf makes the whole request slow. Hedging means both copies must be slow.
%%

## Fixing it within a request
These techniques react to slowness while a request is in flight.

### Hedged requests
Send the request to one replica. If it hasn't answered by the time a normal request would have (say the **95th percentile** latency for that call), send a copy to **another replica**, and use whichever answers first; cancel the other. Because you only hedge the slowest 5% of calls, this adds only about **5% more load**, but it removes most of the tail: a request is now slow only if **both** replicas are slow.

In a Google benchmark that read 1,000 keys spread across 100 BigTable servers, hedging after 10 ms cut p99.9 latency from 1,800 ms to 74 ms, while sending only 2% more requests.

%%seq A hedged request. If the first replica hasn't answered by its p95, a second copy goes to another replica, and the first answer wins.
Client > Replica A : read key k
Client > Client : wait p95 (10 ms), no reply
Client > Replica B : same read (hedge)
Replica B -> Client : value, used
Client > Replica A : cancel
%%

! Example: what hedging does to the fan-out maths
! A request fans out to 100 leaves; each leaf call is slow 1% of the time, independently. Without hedging, 1 − 0.99¹⁰⁰ ≈ 63% of requests hit a slow leaf.
! With hedging, a leaf call ends up slow only if the first replica is slow **and** the hedge is slow too: roughly 0.01 × 0.01 = 0.0001 (ignoring the short wait before the hedge goes out).
! Now 1 − 0.9999¹⁰⁰ ≈ 1% of requests are slow, down from 63%. The cost: about 5% more leaf calls (only the ones still pending at p95 are hedged), and every slow request still pays the 10 ms hedge delay rather than the full slow-path latency.

Hedging only works for requests that are **safe to send twice** (reads, or idempotent writes, lesson 02.09), and only when slowness is **independent** across replicas. If every replica is slow because the whole cluster is overloaded, hedging adds load where it hurts most, so limit hedges with a budget.

### Tied requests
Hedging still waits before sending the second copy. **Tied requests** send to two servers at once, each knowing about the other. Both put the request in their queue. When one of them actually **starts** the work, it tells the other to cancel its copy. Because most of the variability is queueing time, this captures most of the benefit with almost no duplicated work. Delaying the second send by about 1 ms avoids the case where both start at the same instant. In Google's measurements, tied requests cut median latency by 16% and p99.9 by about 40%, with under 1% extra disk work.

%%compare Two ways to send a request to more than one replica. Hedging waits before duplicating; tied requests duplicate at once but cancel as soon as one starts work.
[Hedged]
Send to A -(no reply by p95)-> Send to B -> First reply wins
+ Only ~5% extra requests
+ Simple: no server changes
- Slow requests still wait the p95 delay
[Tied]
Send to A and B -(one starts work)-> Other cancels -> One reply
+ Cuts queueing delay from the start
+ Under 1% duplicated work
- Servers must talk to each other to cancel
%%

## Fixing it across requests
These techniques work over longer timescales, shaping where load goes:
- **Micro-partitions**: split data into many more pieces than there are machines (around 20 per machine). Load can then be rebalanced in small steps by moving a few partitions, and when a machine fails, its partitions are recovered by many machines in parallel.
- **Selective replication**: add extra replicas for partitions that are hot or important, so their load is spread more thinly.
- **Latency-induced probation**: when one machine is consistently slow, temporarily stop sending it real traffic. Keep sending it **shadow requests** to measure its latency, and bring it back when it recovers. Slowness is often temporary (a background job, a noisy neighbour), so this removes the outlier without losing the machine.
- **Good-enough results**: in search, return once most leaves have answered, instead of waiting for every one. A given leaf holds the best result for fewer than 1 in 1,000 queries, so users rarely notice the difference. The same applies to feeds and recommendations: show the page without the slow piece.
- **Canary requests**: send a new query to one or two leaves first, and only fan out to thousands if they respond normally. This stops a "query of death" (one that triggers a crash bug) from crashing thousands of servers at once.

And inside each server:
- **Prioritise interactive requests over batch work**, and keep low-level queues short so the priorities actually take effect: a priority scheduler can't help if 500 batch requests are already sitting in the kernel's socket buffer.
- **Split long requests into slices** (time-slicing), so short requests don't wait behind one huge one.
- **Control background work**: throttle compactions and garbage collection, or schedule them during quieter periods.

%%timeline Latency-induced probation for one slow server. It is taken out of rotation while it is slow and brought back once shadow requests show it has recovered.
10:00:00 | server 17 p99 rises to 300 ms (others 20 ms)
10:00:30 | *server 17 put on probation: no real traffic
10:00:30 | shadow requests continue, every 1 s
10:04:00 | background compaction on server 17 finishes
10:04:30 | shadow p99 back to 20 ms: server 17 restored
%%

## What to measure
Report **p50, p99 and p99.9**, not averages, and set SLOs on percentiles (lesson 01.03). Measure at the **user-facing** level as well as per service, because the fan-out maths means per-service percentiles understate what users see. Percentiles can't be averaged across servers: combine histograms instead. When a design fans out, say so, estimate the width, and say how you will control the tail.

! Example: news feed assembly
! Building a feed calls 40 services (posts, ads, profiles, ranking features) in parallel. Each has a p99 of 50 ms and a typical latency of 15 ms. If each is slow 1% of the time, about 1 − 0.99⁴⁰ ≈ 33% of feeds wait on at least one slow call, so the feed's p75 is already around the services' p99.
! The team applies three fixes. Profile lookups are reads served by three replicas, so they are hedged after their p95 (25 ms). The ads call has a strict 80 ms budget: if it's not back, the feed renders without that ad slot. Ranking features fall back to a cached, slightly older feature vector if not back in 60 ms.
! The slow-call probability for the feed drops to a few percent, and the worst case is bounded at roughly 80 ms plus rendering, instead of whatever the slowest service happens to do.

## Common mistakes
- **Reporting averages**, which hide the tail completely.
- **Assuming per-service p99 is what users see** in a fan-out design.
- **Hedging non-idempotent writes**, which can perform the operation twice.
- **Unlimited hedging**, which adds load during overload.
- **Waiting for every part** of a response when a partial answer would do.

## In an interview
When a request fans out (search, feeds, aggregation pages, scatter-gather queries across shards), point out the tail amplification with the 1 − 0.99^N calculation, then propose hedged requests for idempotent reads, timeouts with partial results for optional parts, and replicas for hot partitions. Mention that you would track p99 and p99.9 at the user-facing endpoint.

> Takeaway: with fan-out, rare slowness on each server becomes common slowness for users: 1 − 0.99^N. Measure percentiles at the user-facing level, and cut the tail with hedged or tied requests, good-enough partial answers, probation for slow machines, micro-partitions and selective replication.

The chance that all 100 are fast is 0.99^100 ≈ 0.366, so about 63% of requests are slow, even though each server is slow only 1% of the time. This is why tail latency on individual servers matters so much for fan-out systems, and why techniques like hedged requests (where a leaf call is slow only if both copies are slow) are used to cut it.

@02.13
## Overload makes everyone fail
When a server receives more requests than it can handle, it doesn't just slow down a little. Requests queue for threads, CPU, memory, connections and locks, and past a certain point latency shoots up: the hockey stick from lesson 01.04, where a server at 95% utilisation has queues many times longer than one at 70%.

This turns into an **outage** because clients have timeouts. Once the server's latency passes the client's timeout, the client gives up and reports an error. But the server doesn't know that. It keeps working on the abandoned request, spends CPU and database time producing a response nobody will read, and only then moves on to the next one, which has probably also been abandoned. The server is 100% busy and produces almost nothing useful.

It helps to separate two measures:
- **Throughput**: requests the server handles per second.
- **Goodput**: requests handled **correctly and in time** for the client to use the answer.

If median latency equals the client timeout, half the requests fail even though the server is "working" on all of them. Then clients **retry**, adding even more load to a server that is already drowning. In a deep call chain where each layer retries, overload at the bottom amplifies itself (lesson 02.09), and the system can settle into a **stable overloaded state**: it stays down even after the original spike has passed, because retries alone keep it overloaded. This is sometimes called a **metastable failure**.

%%widget queue Latency against load for a single queue: flat at first, then a hockey stick as the server nears 100% busy.
%%

## Shed load instead
**Load shedding** means that when a server is near its limit, it **rejects extra requests immediately**, with a quick error such as 503 Service Unavailable or 429 Too Many Requests, so that it can finish the requests it has accepted within their deadlines. Some users get a fast "try again", and everyone else gets a working service. Goodput stays flat as load rises past capacity, instead of collapsing.

%%compare The same server at twice its capacity. Without shedding every request slows past the timeout; with shedding, half are refused quickly and the other half stay fast.
[No shedding]
2x traffic -> Queue grows -> All requests time out
- Latency climbs past the client timeout
- Work done for clients who gave up
- Retries add even more load
- Goodput falls towards zero
[*Shedding]
2x traffic -(reject ~50% early, 503)-> Accepted requests stay fast
+ Goodput stays at capacity
+ Rejected clients learn quickly and back off
- Some users see errors
%%

%%bars Useful responses per second for a server with capacity 1,000, at different offered loads. Without shedding, goodput collapses past capacity; with shedding it plateaus. (Illustrative numbers.)
1x load, no shedding | 1000 | 1,000/s
1.5x load, no shedding | 400 | ~400/s, most time out
2x load, no shedding | 50 | ~50/s
*2x load, with shedding | 980 | ~980/s
%%

### How to decide when to shed
A server needs a signal that it is near its limit. Common choices:
- **Concurrency limit**: cap the number of requests in progress (for example 800). The next request beyond that is rejected. This is simple and directly tied to resource use; tools such as adaptive concurrency limiters adjust the cap automatically from observed latency.
- **Queue time**: reject a request if it has waited in the queue longer than some fraction of its deadline. A request that waited 900 ms of a 1 s budget is better dropped than served.
- **CPU or memory utilisation** above a threshold, measured over a short window.
- **Deadline already passed**: if the caller sent a deadline and it has expired, drop the request without doing any work.

### Make rejection cheap
Fast rejection only works if rejecting costs much less than serving. Check for hidden costs: a log line written for every rejection, a TLS handshake completed before rejecting, an expensive authentication step before the shedding check. Shed as early as possible, ideally before parsing the body. Also keep rejected requests **out of latency metrics**, or median latency will look great precisely while the service is shedding 60% of its traffic.

! Example: shedding with a concurrency limit
! A service handles each request in 50 ms of work, and can run 40 requests at once before latency starts climbing, so its capacity is about 40 / 0.05 = 800 requests per second. Clients time out after 1 s.
! Without a limit, at 1,600 requests per second the queue grows by 800 every second. After 2 seconds, a new request waits behind 1,600 others, about 2 s, past the timeout. Practically every request now fails, and retries push the load higher.
! With a limit of 40 in progress and a short queue of 40 (at most about 100 ms of waiting), requests beyond that get an immediate 503. About 800 per second are served in roughly 50 to 150 ms; about 800 per second are rejected in under a millisecond each and retry later with jitter. Half the users succeed at once, instead of almost none.

## Decide what to shed
Not all requests matter equally. Give each request a **criticality**. One widely used scheme has four levels:

%%layers Request criticality, from most to least protected. An overloaded server rejects the lowest level first.
CRITICAL_PLUS | must never be shed if avoidable, e.g. payment confirmation
*CRITICAL | default for user-facing traffic, e.g. login, checkout
SHEDDABLE_PLUS | can tolerate some failure, e.g. batch jobs that retry
SHEDDABLE | dropped first, e.g. prefetch, analytics, background sync
%%

An overloaded server rejects the lowest criticality first, and only moves up a level when shedding the lower ones isn't enough. Criticality is **propagated** to downstream calls, so a backend knows that a request is part of a critical checkout, not a background job, even three hops away. Also:
- **Never shed health checks** from the load balancer. If the server rejects them, the balancer pulls it from the pool, its traffic moves to the others, and they overload in turn: shedding turns into a cascade.
- **Prefer real users over crawlers**, and callers within their quota over those bursting above it.
- **Let started work finish**: prioritise a request that completes a workflow (the payment step of a checkout already in progress) over one that starts a new one (a new visitor's home page). Abandoning half-finished work wastes everything already spent on it.

## Measure capacity correctly
Requests per second is a poor capacity measure, because requests vary wildly in cost (a cached profile read versus a full-text search), and the mix changes over the day. A limit of "1,000 requests per second" will be too loose when the mix shifts to expensive requests, and too tight when it shifts to cheap ones.

Measure capacity in **resources**, such as CPU seconds or database time consumed. Give each customer a **quota** in those units. Then, in a global overload, only the customers above their quota see errors, while customers within their share continue normally.

## Help clients back off
Shedding on the server still costs something per rejected request. Clients can help.

**Client-side adaptive throttling.** Each client tracks, over the last two minutes, how many requests it sent (`requests`) and how many the backend accepted (`accepts`). Normally the two are equal. When the backend starts rejecting, `requests` grows faster than `accepts`. Once `requests` exceeds `K × accepts` (Google uses K = 2), the client starts **rejecting some requests locally**, without sending them, with probability `max(0, (requests − K × accepts) / (requests + 1))`. The backend then spends no effort rejecting those requests at all, and the client automatically sends more again as the backend recovers.

**Retry budgets.** At most 3 attempts per request, and retries limited to **10% of a client's traffic**. Without the budget, a fully failing backend sees up to 3 times the normal request rate; with it, at most about 1.1 times. Retry only at the layer directly above the overloaded one, so retries don't multiply through the stack.

**Deadlines.** Pass the remaining time budget down the call chain. A server receiving a request whose deadline has passed drops it immediately, and a server whose remaining budget is too small for the work it would need to do can refuse up front.

%%seq Deadline propagation. Each hop passes on the time remaining, and a backend drops work whose caller has already given up.
Client > Frontend : GET /feed, deadline 1,000 ms
Frontend > Frontend : 300 ms queued under load
Frontend > Ranking : rank(user), 700 ms left
Ranking > Ranking : 720 ms queued
Ranking > Ranking : deadline passed: drop, no work done
Ranking -> Frontend : DEADLINE_EXCEEDED
Frontend -> Client : 503, Retry-After 2
%%

! Example: adaptive throttling in numbers
! A client sends 1,000 requests per second to a backend that, overloaded, now accepts only 300 per second.
! Over the window, requests = 1,000 and accepts = 300, so K × accepts = 600. The client rejects locally with probability (1,000 − 600) / 1,001 ≈ 40%.
! It now sends about 600 per second, of which the backend accepts its 300. The backend rejects 300 instead of 700, saving that work. As the backend recovers and accepts rise, the local rejection probability falls back to zero on its own, with no configuration change.

## Queues and testing
- **Bound queues** by size and by time spent waiting, and drop requests that have waited too long.
- Under overload, serving **newest first** (LIFO) favours requests whose clients are still waiting, rather than ones that have probably timed out. Some systems switch from FIFO to LIFO only when the queue is long.
- **Load test past the breaking point.** Push to 2 or 3 times capacity and check that goodput rises to a plateau and stays flat, rather than falling off a cliff. Test recovery too: when load drops, does the service come back, or does it stay stuck because of retries?
- **Watch autoscaling.** If shedding keeps CPU looking normal, CPU-based autoscaling may never trigger. Scale on concurrency, queue depth, or the shed rate as well.

! Example: ticket sale
! A concert goes on sale and traffic jumps to 20 times normal. Without shedding, the ticket service's latency climbs past the 2 s client timeout within seconds; users hammer refresh, retries multiply the load, and almost nobody gets a ticket.
! With shedding, each server accepts up to its tested limit of 800 concurrent requests and returns 503 with `Retry-After` for the rest. Browsing seat maps (SHEDDABLE) is rejected before seat holds and checkouts (CRITICAL), and a checkout already in progress is always allowed to finish.
! Accepted checkouts complete in about 300 ms. Clients retry with jitter and within their retry budget, and a virtual waiting room at the edge admits users at the rate the backend can actually serve. The sale completes in 40 minutes with every ticket sold, instead of an hour-long outage.

## Common mistakes
- **No limit at all**, relying on timeouts to "naturally" cap load.
- **Shedding health checks**, causing cascades.
- **Expensive rejections**: heavy logging or full request parsing before deciding to reject.
- **Capacity limits in requests per second** when costs vary widely.
- **Unbounded retries** that keep the system overloaded after the spike ends.

## In an interview
When traffic can spike (sales, launches, breaking news), say how the service protects itself: "each server caps in-flight requests and returns 503 fast beyond that; requests carry a criticality so background work is shed first; clients retry with jitter within a 10% retry budget; deadlines propagate so abandoned work is dropped". Then mention load testing beyond capacity.

> Takeaway: under overload, a fast "no" protects the requests you accept and keeps goodput at capacity instead of collapsing. Shed early and cheaply, by criticality, measure capacity in resources, propagate deadlines, and cap retries so clients don't finish the job of knocking you over.

The server then spends its capacity on requests whose clients have already given up and are retrying, so goodput drops towards zero while load keeps rising, and the system can stay stuck even after the spike passes.
