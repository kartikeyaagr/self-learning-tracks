## What observability means
Observability is the ability to understand what a system is doing **from the outside**, using only the data it already emits. The practical test is this: when something breaks in a way nobody predicted (an "unknown unknown"), can an engineer find the cause from existing signals, without shipping new logging first? If the first step of every investigation is "add more logging and wait for it to happen again", the system is not observable enough.

Monitoring and observability overlap but are not the same. **Monitoring** watches for failures you already know about: a dashboard of CPU, an alert when the error rate crosses 1%. **Observability** lets you ask questions you did not think of in advance: "Are slow checkouts all from users on the new Android build who pay with one particular card issuer?" Monitoring tells you a known thing is wrong. Observability lets you investigate an unknown thing.

In a single-process application you could attach a debugger or read one log file. In a distributed system a single user click might touch a gateway, five services, two databases, a cache and a queue, running on dozens of machines. No one machine holds the whole story. The data each component emits about itself is called **telemetry**, and it comes in three main signals: **metrics**, **logs** and **traces**. Each answers a different kind of question, and a real investigation usually moves between all three.

%%matrix Each signal is good at a different question; real debugging moves between all three.
Signal | Is something wrong? | Which service? | Exactly why? | Cheap at scale?
Metrics | yes, alerts and dashboards | partial, per-service graphs | no, aggregated away | yes, fixed cost per series
Traces | partial, if sampled well | yes, the waterfall shows it | partial, span attributes | partial, needs sampling
Logs | partial, by counting lines | partial, if trace IDs present | yes, full event detail | no, cost grows with traffic
%%

## Metrics: is something wrong, and how much?
A **metric** is a number aggregated over time: requests per second, error count, CPU utilisation, queue depth, latency percentiles. A metric is stored as a **time series**: a name, a set of labels (for example `service="checkout", region="eu-west"`) and a stream of (timestamp, value) points. A million requests become a single counter incremented a million times. That is why metrics are cheap: their storage cost depends on how many series you have, not on how much traffic you serve.

That fixed cost has one trap. Every unique combination of label values creates a new series. A label like `user_id` with 10 million values creates 10 million series, and the metrics database falls over. This is the **cardinality** problem. Keep metric labels to low-cardinality values (service, endpoint, status code, region) and put high-cardinality detail in logs and traces.

The weakness of metrics is that they throw detail away. A latency graph can show checkout p99 jumping from 300 ms to 2 s. It cannot show you which request, which user or which downstream call was slow.

### The four golden signals
If you can measure only four things about a service, measure these:
- **Latency**: time to serve a request. Track successful and failed requests separately. A fast HTTP 500 drags the average down and hides the problem, and a slow error is worse than a fast one.
- **Traffic**: demand in the system's own unit. HTTP requests per second for a web service, concurrent sessions for a video stream, reads and writes per second for a key-value store.
- **Errors**: failed requests. They can be explicit (HTTP 500), implicit (HTTP 200 with the wrong content) or by policy (anything slower than a promised 1 s counts as failed). Load balancer counts catch outright failures; only end-to-end probes catch wrong content.
- **Saturation**: how full the most constrained resource is (CPU, memory, connection pool, disk, queue). Many systems degrade well before 100%, so pick a target utilisation. Rising latency is often the first sign of saturation, and predictions count too ("the disk fills in 4 hours").

%%layers The four golden signals, from what users feel at the top to what predicts the next outage at the bottom.
*Latency | how long requests take; split success and failure
Traffic | how much demand: requests/s, sessions, transactions
Errors | explicit 500s, wrong 200s, too slow counts as failed
Saturation | how full the tightest resource is
%%

Two related shorthands are worth knowing. **RED** (Rate, Errors, Duration) is the golden signals minus saturation, used for request-driven services. **USE** (Utilisation, Saturation, Errors) is for resources such as disks, CPUs and network links. Use RED on every service endpoint and USE on every machine and pool.

## Why averages lie
A service handling 1,000 requests per second with a 100 ms **average** latency can still have 1% of requests (10 every second) taking 5 seconds. The average hides the tail, and the tail is what users complain about. It gets worse with fan-out. If one page calls 20 backends in parallel and each has a 1% chance of being slow, the chance that at least one is slow is 1 − 0.99^20, about 18%. One backend's 99th percentile becomes the page's typical case.

The fix is to record **histograms**: count each request into a latency bucket instead of keeping raw values or a single mean. Buckets usually grow geometrically, roughly ×2 to ×3 each step (0 to 10 ms, 10 to 30, 30 to 100, 100 to 300, 300 ms to 1 s, 1 to 3 s). From the bucket counts you can estimate any percentile and see the shape of the distribution. Crucially, histograms can be **added together**: you can merge histograms from 200 servers and compute a correct fleet-wide p99. You cannot average 200 per-server p99 values and get the fleet p99; that number is meaningless.

%%bars Latency of one checkout endpoint over five minutes. The mean looks healthy; the tail is where users suffer.
p50 | 120 | 120 ms
Mean | 180 | 180 ms
p90 | 310 | 310 ms
*p99 | 2000 | 2,000 ms
p99.9 | 4800 | 4,800 ms
%%

Resolution should match the goal. A CPU graph averaged per minute hides one-second spikes that cause tail latency. A useful trick: sample CPU every second into a histogram with 5% buckets, and ship that histogram once a minute. You keep the spikes without paying for per-second storage.

! Example: sizing a metrics system
! You run 300 services, each on about 20 pods. Each pod exports 150 series (request counts per endpoint and status, a latency histogram with 12 buckets per endpoint, runtime stats). That is 300 × 20 × 150 = 900,000 active series.
! Scraping every 15 seconds gives 900,000 ÷ 15 = 60,000 samples per second. Compressed time-series storage needs about 1 to 2 bytes per sample, so a day is 60,000 × 86,400 × 2 ≈ 10 GB. Very manageable.
! Now a developer adds a `customer_id` label to the request counter, with 50,000 active customers. One metric explodes to 300 × 20 × 50,000 = 300 million series. The metrics database runs out of memory within the hour. That one label is the classic cardinality outage.

## Logs: what exactly happened?
A **log** is a timestamped record of a single event. Logs carry the detail metrics throw away: the user ID, the full error message, the SQL that timed out, the version of the client. Their cost grows with traffic: at 20,000 requests per second, with 10 log lines of 500 bytes each per request, you write 100 MB per second, about 8.6 TB per day. That is why teams sample debug logs, keep only a few days of hot storage and drop noisy lines.

Logs on their own **lack context**. A line that says "payment call failed" does not say which incoming request triggered it or what else that request did on other machines. Two changes make logs useful in a distributed system:
- Make them **structured**: emit JSON fields (`{"level":"error","order_id":"o-981","status":503,"trace_id":"abc"}`) instead of free text, so you can filter and group by any field rather than grep for phrases.
- Put a **trace ID** (or request ID) in every line, so you can pull every log line for one request across every service with a single query.

## Traces: where did the time go?
A **span** is one unit of work: an HTTP handler, a database query, a call to another service. A span has a name, a start time, a duration, a parent span ID, **attributes** (key-value metadata such as `http.request.method = GET`, `http.route = /webshop/articles/:article_id`, `http.response.status_code = 200`) and span events (structured log messages inside it).

A **trace** is the tree of spans for one request. The root span covers the request from start to finish; child spans cover the steps inside it. Tools draw a trace as a **waterfall**: one horizontal bar per span, nested under its parent and placed on a shared time axis, so the long bar is obvious at a glance. Gaps between child spans are also informative: they show time spent inside the service itself (queuing, garbage collection, CPU work) rather than waiting on a dependency.

### Context propagation
For a trace to cross service boundaries, every service must pass the trace ID and its own span ID along with each outgoing call. Over HTTP this is a header; the W3C standard is `traceparent`, which looks like `00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01`: a version, a 16-byte trace ID, an 8-byte parent span ID and flags (the last bit says whether this trace is sampled). The receiving service reads the header, creates a child span with that parent, and passes its own span ID onward. Over a message queue, the same context travels in message headers, so a trace can follow work into an asynchronous consumer.

Propagation is the fragile part. One service that forgets to forward the header, or one thread pool that drops the context, splits the trace in two. Use an instrumentation library (OpenTelemetry is the common standard) that patches HTTP clients, database drivers and queue clients automatically.

%%seq Context propagation: each hop reads the incoming trace context, starts a child span and forwards the context on.
Browser > API gateway : POST /checkout (no trace header)
API gateway > API gateway : start trace abc, root span g1
API gateway > Checkout : traceparent abc / parent g1
Checkout > Checkout : start span c1, parent g1
Checkout > Payment : traceparent abc / parent c1
Payment > Payment : start span p1, parent c1 (1,700 ms)
Payment -> Checkout : 200 OK after 1.7 s
Checkout -> API gateway : 200 OK after 1.85 s
API gateway -> Browser : 200 OK after 1.9 s
%%

### Sampling
Recording every span of every request is expensive at high traffic. **Head-based sampling** decides at the start of the trace (for example, keep 1% at random) and propagates the decision in the flags, so all services agree. It is cheap but will usually miss the rare slow or failed request you care about. **Tail-based sampling** buffers all spans of a trace in a collector until it completes, then keeps it if it was slow, failed or otherwise interesting, plus a small random share of normal traces. It catches the outliers but needs a collector tier with enough memory to hold every in-flight trace for some seconds.

! Example: debugging a slow checkout end to end
! 1. **Metrics** raise the alert: checkout p99 rose from 300 ms to 2 s at 14:05, while the error rate is flat. Traffic is normal, so it is not simply load.
! 2. **Traces**: open a handful of slow checkout traces from after 14:05. In the waterfall the `payment.authorize` span takes 1.7 s of the 1.9 s; inventory and pricing spans are normal. The slow service is the payment service.
! 3. **Logs**: filter payment-service logs by those trace IDs. They show "waiting for connection from pool" for 1.6 s before each call to the card processor.
! 4. Back to **metrics** to confirm the cause: the payment service's connection pool saturation is at 100% since a 14:00 deploy that halved the pool size from 40 to 20. Roll back, and p99 returns to 300 ms within two minutes.

## Alerting on symptoms, not causes
Separate **what is broken** (the symptom: errors, slow responses users feel) from **why** (the cause: database refusing connections, CPU at 100%, a failed disk). Page people on symptoms. Use cause metrics on dashboards for debugging, and page on a cause only when it is definite and imminent, such as a disk that will fill within an hour or a cluster down to its last replica.

Why? A cause alert can fire with no user impact (CPU at 95% may be fine), and many causes can produce one symptom, so you would need a cause alert for every possible failure and still miss the new one. A symptom alert catches every failure that matters, including ones you never imagined.

Rules for pages:
- Every page must be **urgent**, **actionable** and need **human judgement**. If the response is mechanical (restart the process, add a node), automate it instead.
- People can only respond with urgency a few times per shift before fatigue sets in. Noisy alerts train people to ignore pages, and then they miss the real one.
- Delete alert rules that rarely fire usefully, and signals that appear in no dashboard and no alert.

The Bigtable team at Google learned the cost of noise. Their SLO was set on mean latency, but the slowest 5% of requests were much slower, so alerts fired constantly and engineers missed real problems among the noise. The team temporarily set the target at the 75th percentile and turned off email alerts. With fewer interruptions, the on-call engineers had the time to fix the underlying causes, and the target was tightened again later.

## Common mistakes
- **Averages on dashboards.** Plot p50, p99 and p99.9 from histograms. Never average percentiles across hosts.
- **High-cardinality labels on metrics.** User IDs, order IDs and URLs with IDs in them belong in logs and traces.
- **Unstructured logs with no trace ID.** You end up grepping 40 machines and guessing which lines belong together.
- **Broken propagation.** One service or async hop that drops the trace header, so traces end abruptly at that boundary.
- **Random head sampling only.** At 1% you discard 99% of the rare failures you most want to see.
- **Alerting on every cause.** Dozens of CPU and memory alerts with no user impact, and on-call learns to ignore them.

## In an interview
When you finish a design, add an observability paragraph. Say you would emit RED metrics per endpoint as histograms, structured logs with trace IDs, and distributed traces with OpenTelemetry and tail-based sampling. Say you would alert on user-facing SLOs (lesson 14.02 covers burn-rate alerts) and keep cause metrics for dashboards. If the interviewer asks "checkout is slow, how do you find out why?", walk the loop: metric alert, slow traces, span waterfall, logs for that span by trace ID, confirm with a cause metric.

> Takeaway: metrics tell you something is wrong and how much; traces tell you which service and which call; logs tell you exactly what happened inside it. Record latency as histograms, keep metric labels low-cardinality, propagate a trace ID through every hop, and page only on symptoms users feel.

## Why reliability needs a number
"Make it more reliable" is not a goal anyone can finish. Engineers always want more stability, product teams always want more features, and without a shared number the argument is settled by whoever shouts loudest after the last outage. Service level objectives turn reliability into a measured quantity with a target, and the error budget turns the gap between 100% and that target into something both sides can spend.

The key insight is that **100% is the wrong target**. Users cannot tell the difference between 99.99% and 100% when their own Wi-Fi, phone and ISP fail far more often than that. Every extra nine costs roughly ten times more (more replicas, more regions, slower releases), and the last one is practically infinite. So you pick a level that keeps users happy, and treat everything above it as room to move fast.

Three terms stack on top of each other:

%%layers The vocabulary stack: you measure an SLI, aim for an SLO, and promise an SLA with a safety margin below it.
SLA | contract with customers; missing it costs money or credits
*SLO | internal target for an SLI over a window, e.g. 99.9% in 28 days
SLI | the measurement: good events divided by total events
Telemetry | raw logs, metrics and probes the SLI is computed from
%%

The **SLA** (service level agreement) is an external contract: "if monthly availability is below 99.9%, you get 10% credit". The SLO is internal and should be stricter than any SLA, so you notice trouble and react before it costs money. Many internal services have SLOs and no SLA at all.

## SLIs: measuring what users feel
A **service level indicator** (SLI) is best expressed as a ratio: **good events divided by total events**, giving a value from 0% to 100%. Keeping every SLI in this one shape means the same tools can chart, alert and report on any of them. Examples:
- successful HTTP requests ÷ all HTTP requests (availability);
- gRPC calls that succeed in under 100 ms ÷ all calls (latency);
- search results served from the full index ÷ all results, including degraded ones (quality);
- pipeline runs that finished within 1 hour of their data arriving ÷ all runs (freshness).

Separate the **specification** (what users care about: "the home page loads in under 100 ms") from the **implementation** (how you measure it). The same specification can be measured in several places, each with a blind spot:
- **Server logs or metrics**: cheap and complete for requests that arrive, but blind to requests that never reached you (DNS failure, load balancer down).
- **Load balancer metrics**: catch backend crashes, but still miss failures before the load balancer.
- **Synthetic probers**: catch network and DNS failures, but only test the paths you script.
- **Client-side telemetry** (JavaScript or app instrumentation): closest to what users feel, but noisy (users' own bad networks) and the most work.

Start with the cheapest measurement that is good enough, then improve it when you find it misses real pain.

Which SLIs to pick depends on what the component does:
| Component | Typical SLIs |
| Request-driven (APIs, web) | availability, latency, quality |
| Pipeline (batch, streaming) | freshness, correctness, coverage |
| Storage | durability, availability, latency |

Keep it to about three to five SLIs per service. More than that and nobody knows which one matters.

## SLOs and the error budget
An SLO is a target for an SLI over a window: "99.9% of requests succeed, measured over 28 days". The **error budget** is what is left: 100% − 99.9% = 0.1% of requests are allowed to fail in that window. For a time-based view, 0.1% of 28 days is about 40 minutes of full outage.

| SLO | Budget per 28 days | Budget per year |
| 99% | 6.7 hours | 3.65 days |
| 99.9% | 40 minutes | 8.8 hours |
| 99.95% | 20 minutes | 4.4 hours |
| 99.99% | 4 minutes | 53 minutes |

Notice what 99.99% means operationally: a 4-minute budget per month is less than the time it takes a human to wake up, log in and understand a page. A four-nines service needs automatic failover and automatic rollback; people alone cannot meet it.

### Setting the first SLO from data
A good way to start is to measure current performance and set the SLO just below it. Consider a mobile game API. Over four weeks it served 3,663,253 requests, of which 97.123% succeeded, with p90 latency of 432 ms and p99 of 891 ms. The team set SLOs just below current performance: 97% availability, 90% of requests under 450 ms, 99% under 900 ms.

! Example: pricing incidents in budget
! The availability budget is 3% of 3,663,253, about **109,897 failed requests** per four weeks.
! A bad release that caused 14,066 errors cost 14,066 ÷ 109,897 ≈ **13%** of the budget.
! A database failure with a 20-hour restore caused about 72,000 errors: about **65%**.
! Bad releases happen two or three times a year; the database failure happened once in several years. Over a year, releases cost 3 × 13% ≈ 39% of a month's budget, the restore 65% once in many years. Per year, the releases are the bigger cost and the cheaper fix. So the team first invests in safer releases (canaries, automatic rollback), then in faster restores.

That is the real power of an error budget: it lets you rank reliability work by how much budget each class of failure actually burns.

**Windows.** A **rolling** window (say the last 28 days) matches how users remember outages: a bad Tuesday still counts for four weeks. Use a whole number of weeks so every window holds the same number of weekends (traffic patterns differ). **Calendar** windows (this month, this quarter) match business planning and SLA contracts, but reset abruptly: an outage on the 30th and one on the 2nd land in different months. A common default is a four-week rolling window for operational decisions, with weekly summaries for prioritising and quarterly reports for planning.

## The error budget policy
An SLO only matters if missing it changes behaviour. The **error budget policy** is a short written agreement, signed off in advance by product, development and SRE (site reliability engineering), saying what happens as the budget is spent. Typical rules:
- While budget remains, teams ship freely. A healthy service should spend some of its budget; never touching it means you could take more risk and move faster.
- When budget is being spent quickly, reliability work from recent incidents moves to the top of the backlog and risky launches slow down.
- When the budget is exhausted, **freeze production changes** except fixes and security patches, until enough budget returns as the window rolls forward.
- Work only on reliability until the service is back within its SLO, with leadership backing to turn down feature requests.
- In extreme cases (budget exceeded several times over), escalate to senior leadership.

%%state The error budget policy as a state machine: spending changes what the team is allowed to do.
[*] -> Healthy
Healthy -> At risk : burn rate above 1 for days
At risk -> Healthy : burn slows, postmortem fixes land
At risk -> *Exhausted : budget reaches 0
Healthy -> Exhausted : one big outage
Exhausted -> Frozen : policy freezes non-fix releases
Frozen -> Healthy : window rolls past the outage
%%

The policy also needs an **escalation path** for disagreements and a rule for outages caused by dependencies (a cloud provider failure still burns your budget from the user's point of view; freezing anyway is friendlier to users, though some teams exclude it).

All three groups must agree to it, because each gives something up. Product agrees the threshold is good enough for users, developers agree to slow down when it is missed, and SRE agrees it can be met without heroics. If one party will not enforce the policy, change the SLO until they will. An unenforced SLO is just a dashboard.

## Alerting on the budget: burn rate
Alerting whenever the error rate crosses 0.1% is too noisy. A 0.1% error rate for 10 minutes uses only 0.02% of a 30-day budget, yet such an alert could fire up to 144 times a day while the SLO is still comfortably met. The better measure is **burn rate**: how fast you are spending the budget relative to the even pace. A burn rate of 1 uses exactly the whole budget by the end of the window. For a 99.9% SLO over 30 days:

%%bars How long a 30-day budget for a 99.9% SLO lasts at different burn rates (error rate = burn rate × 0.1%).
Burn 1 (0.1% errors) | 720 | 30 days
Burn 2 (0.2%) | 360 | 15 days
Burn 6 (0.6%) | 120 | 5 days
Burn 14.4 (1.44%) | 50 | 50 hours
*Burn 1,000 (100%) | 0.72 | 43 minutes
%%

The formula is: budget consumed = burn rate × alert window ÷ SLO period. Recommended starting thresholds:
| Severity | Long window | Short window | Burn rate | Budget used |
| Page | 1 hour | 5 minutes | 14.4 | 2% |
| Page | 6 hours | 30 minutes | 6 | 5% |
| Ticket | 3 days | 6 hours | 1 | 10% |

Check the first row: 14.4 × 1 h ÷ 720 h = 2%. The intuition: "if this continues, we lose the whole month's budget in about two days; wake someone up."

The **short window** (one twelfth of the long one) is the "multiwindow" part. An alert fires only when both windows exceed the threshold. The long window shows the burn is significant; the short window shows it is still happening. When errors stop, the short window drops below the threshold within minutes and the alert clears, instead of firing for another hour while the long window slowly forgets.

%%timeline A 10-minute outage at 20% errors against a 99.9% SLO: the 1-hour window detects it, the 5-minute window lets it clear quickly.
10:00 | Deploy goes out, error rate jumps to 20% (burn 200)
10:01 | 5-minute burn above 14.4
10:04 | *1-hour burn crosses 14.4: both windows high, page fires
10:06 | On-call rolls back
10:10 | Errors stop; about 4.6% of the month's budget is spent
10:15 | 5-minute burn back below 14.4, alert clears
11:10 | 1-hour window finally forgets the outage
%%

**Low-traffic services** break this maths. At 10 requests an hour, a single failure is a 10% error rate and a burn rate of 100. Options: add synthetic traffic so there is enough signal, group small services that share failure domains into one SLO, add client retries so one failure is not a user-visible failure, or deliberately set a lower SLO.

! Example: half the budget gone in week one
! A 99.9% SLO over 4 weeks with 3 million requests has a 3,000-error budget. One outage in week 1 causes 1,500 errors: 50% spent in 25% of the window, so the average burn rate so far is 2.
! The burn-rate alert paged during the outage (1-hour burn far above 14.4). Now the policy applies. You are not out of budget, so no freeze yet. But at a burn of 2 you would run out around day 14.
! So the team prioritises the outage's postmortem actions, slows risky launches (more canary time, no big migrations), and watches the 3-day ticket alert. If a second incident uses the rest, the freeze starts and lasts until the rolling window moves past the first outage, roughly three weeks later.

## Common mistakes
- **SLO set at 100% or at the SLA.** You have no budget to ship with and no warning before you owe credits.
- **SLIs that users do not feel.** CPU utilisation is not an SLI; "checkout succeeded in under 1 s" is.
- **Averages as SLIs.** "Mean latency under 200 ms" can be met while 5% of users wait 5 s. Use "fraction of requests under the threshold".
- **No signed policy.** The budget runs out, product wants the launch anyway, and nothing happens. Then the SLO means nothing.
- **Alerting on raw thresholds.** Paging on every 1% spike creates fatigue; use burn rate with two windows.

## In an interview
When you state non-functional requirements, phrase availability as an SLO ("99.9% of redirects succeed in under 100 ms over 28 days") and translate it into a budget ("about 40 minutes a month"). That tells the interviewer whether you need multi-region failover (four nines) or just good deploy hygiene (three nines). If asked about operations, mention burn-rate alerting and a freeze policy.

> Takeaway: define SLIs as good ÷ total events users feel, set an SLO slightly below what you achieve, and treat the remainder as a budget to spend. A signed error budget policy decides in advance what happens as it runs out, and burn-rate alerts with a long and a short window tell you when it is running out too fast.

## Why incidents need structure
An **incident** is an unplanned event that degrades a service enough that it needs a coordinated response: users cannot check out, a region is down, data is being corrupted. Every team has the technical skill to fix most incidents. What usually fails is the response itself: who is doing what, who is talking to whom, and who is still looking at the big picture.

Consider a typical unmanaged incident. The on-call engineer, call her Mary, is paged when one datacentre stops serving. Two more fail, the remaining ones overload, and the whole service goes down. Then the response falls apart:
- **Tunnel vision.** Mary dives into logs and rolls back a release, which does not help. Deep in the details, she loses sight of the bigger picture and of simple mitigations such as shedding load or draining traffic to a healthy region.
- **Poor communication.** Developers join informally and nobody knows who is doing what. Two people restart the same service. Executives demand updates directly from Mary and suggest fixes, pulling her out of the work every five minutes.
- **Freelancing.** Another engineer, Malcolm, on his own initiative, pushes an untested CPU affinity change to production. The servers restart with it and fail, making things worse. Nobody knew he was doing it, so for twenty minutes nobody can explain the new failure.

The fix is not smarter engineers. It is a structure that gives each person one job and makes the state of the response visible to everyone.

## The incident lifecycle
An incident moves through recognisable stages. Naming them helps everyone know what the current goal is: during mitigation the goal is to stop user pain, not to understand root cause.

%%state The lifecycle of an incident: mitigation comes before root cause, and nothing is closed until the follow-ups are tracked.
[*] -> Detected
Detected -> Declared : alert or report, IC named
Declared -> Mitigating : roles assigned, channel opened
Mitigating -> *Mitigated : user impact stopped
Mitigated -> Resolved : root cause fixed, temporary changes reverted
Resolved -> Postmortem : review written and reviewed
Postmortem -> Closed : action items owned and tracked
Mitigated -> Mitigating : impact returns
%%

- **Detected**: an alert fires, or a customer or engineer reports a problem.
- **Declared**: someone decides this is an incident, names an incident commander and opens a channel.
- **Mitigating**: the team works to stop user impact as fast as possible.
- **Mitigated**: users are no longer hurt, though the system may be in a temporary state (a flag disabled, a region drained).
- **Resolved**: the underlying cause is fixed and temporary changes are reverted.
- **Postmortem** and **closed**: the team writes up what happened and tracks follow-up work to completion.

## Roles: separate the deciding from the doing
A good incident process is modelled on the **Incident Command System** used by fire and emergency services. Its core idea is a **recursive separation of responsibilities**: everyone knows their role and stays inside it. That also frees people to act without second-guessing each other.

%%tree Incident roles: the commander owns every role not yet handed out, and large incidents split recursively.
*Incident commander | overall picture, assigns work, holds unassigned roles
  Operations lead | the only people who change production
    Responder: database
    Responder: networking
  Communications lead | status page, stakeholder updates, incident doc
  Planning lead | bugs, handoffs, food, list of temporary changes
  Scribe | timeline of actions and decisions
%%

- **Incident commander (IC)**: holds the overall picture, sets priorities, assigns work and removes blockers. The IC holds every role that has not been handed out yet. In a small incident the IC might also be the comms lead; in a large one each role has its own person.
- **Operations lead**: works with the IC to actually change the system. **Only the operations team changes production during the incident.** That single rule stops a Malcolm. Anyone with an idea brings it to the IC or ops lead instead of acting on it.
- **Communications lead**: the public face of the response. Sends regular updates to stakeholders and users (status page, support team, executives), shielding the responders from interruptions. Often keeps the incident document current.
- **Planning lead**: handles longer-term needs: filing bugs, arranging handoffs and food on a long incident, and recording every temporary change ("we disabled the recommendations cache flag at 14:20") so it can be reverted later.

### Why the commander must not be the fixer
Fixing needs deep focus on one technical thread: reading a stack trace, testing a hypothesis, watching a graph after a change. Coordinating needs a wide view: is the current approach still the right one, is anyone working on mitigation rather than diagnosis, who needs an update, who else should join, how long have we been at this? These two modes of attention conflict. A person deep in a debugger stops noticing that the incident is 40 minutes old, that a second team has quietly started a risky change, or that a simple failover would end the outage now. That is exactly what failed for Mary.

There is also a decision-quality reason. The fixer is invested in their current theory. A commander who is not hands-on can ask "what if it's not the deploy?" and redirect people without ego. And there is a communication reason: if the fixer is also the person executives call, every update costs ten minutes of focus.

When any role gets too big, its holder asks for more people or splits off a **sub-incident** with its own commander, which reports to the main one. The structure scales recursively.

## Running the response
- **A known command post**: one agreed place where responders coordinate, such as a dedicated chat channel (`#inc-2024-11-12-checkout`) or a video bridge. Chat gives you a timestamped log for free.
- **A live incident document**: the IC's most important artefact. Many people can edit it at once. It holds current status, user impact, a timeline, actions taken and who owns what, with the most important information at the top. It is messy but useful, and it becomes the raw material for the postmortem.
- **Regular cadence**: the comms lead posts an update at a fixed interval (every 15 or 30 minutes) even if nothing changed. Silence makes stakeholders go hunting for responders.
- **Explicit handoff**: at the end of a shift, brief the new IC by voice or video and do not leave until they have said "I have command". Then announce in the channel who is in charge.

### Severity levels
Most organisations define severity levels in advance, so the size of the response matches the size of the problem without debate.
| Level | Meaning | Response |
| SEV1 | major user-facing outage or data loss | IC and full roles, executives informed, status page |
| SEV2 | significant degradation, a key feature down | IC and ops, comms to affected teams |
| SEV3 | minor impact or a contained internal problem | on-call handles, ticket, no formal roles |

### When to declare
Declare early. It is far easier to close a small incident than to bolt structure onto a big one halfway through. Declare if any of these is true: you need a second team, customers can see the outage, or the problem is still unsolved after an hour of focused work.

### Mitigate first
The priorities, in order, are: stop the bleeding, restore service, and preserve evidence for later analysis. Rolling back, failing over, draining a region, disabling a feature flag or shedding load usually beats debugging during the outage. A rollback that works in 3 minutes is better than a root-cause fix that takes 3 hours, even if you are not sure the deploy caused it. Before mitigating, take a quick snapshot of evidence if it is cheap (a heap dump, a copy of the logs, the current config) because a restart may destroy it.

! Example: a checkout incident, minute by minute
! 14:02: the checkout error-rate burn alert pages Priya. Error rate is 20%. She acknowledges and declares a SEV1 at 14:05, naming herself IC, and opens `#inc-checkout`.
! 14:07: she asks Sam to be ops lead and Leo to handle comms. Leo posts the first status page update at 14:10 ("Some customers cannot complete payment; we are investigating") and promises another in 30 minutes.
! 14:09: Sam notes a deploy of the payment service at 13:58. Priya decides: roll back now, investigate later. Another engineer suggests restarting the database; Priya logs the idea and asks him to gather database metrics instead of acting.
! 14:16: rollback complete. Error rate falls to 0.1% by 14:19. Priya marks the incident mitigated, keeps it open, and asks the planning lead to note that the deploy pipeline for payments is paused.
! 14:40: Leo posts the all-clear. Next day, a postmortem finds the new version's connection pool was half the size. User impact lasted about 17 minutes at roughly 20% errors, which spends about 8% of a 99.9% monthly error budget (burn rate 200 × 17 minutes ÷ 43,200 minutes).

## Blameless postmortems
After the incident, the team learns from it. A **postmortem** is a written record: impact (who, how many, how long), a timeline, actions taken, root causes and contributing factors, what went well, where you got lucky, and follow-up actions with owners and priorities. Teams agree in advance on what triggers one, for example:
- user-visible downtime or degradation beyond a threshold;
- **any** data loss;
- on-call intervention such as a rollback or rerouting traffic;
- resolution time beyond a threshold;
- a monitoring failure (a human found the problem before the alerts did).

**Blameless** means the postmortem looks for contributing causes in systems and processes, not for a guilty person. It assumes everyone acted reasonably with the information and tools they had at the time. The reason is practical: if people fear punishment, they hide mistakes and stay quiet about near misses, and the organisation stops learning. The approach comes from healthcare and aviation. You cannot fix people, but you can fix systems so the next person makes a better choice. "An engineer ran a command on the wrong host" becomes "production and staging hosts have identical prompts and the tool asks for no confirmation".

Wording matters. A blaming note says the backend must be rewritten because it keeps breaking and someone is tired of being paged. A blameless version proposes the rewrite as an action item, because the current runbook is long and hard to learn, and future on-call engineers would benefit.

**Review.** Senior engineers review each draft for completeness. Was the key data collected? Is the impact assessed? Is the root cause analysed deeply enough (ask "why" several times, and look for multiple contributing factors, not one)? Are the actions specific, owned and prioritised? Was it shared widely? An unreviewed postmortem, or one whose action items never get done, might as well not exist. Teams keep the culture alive with a "postmortem of the month", reading groups on old incidents, and the **Wheel of Misfortune**, where new engineers replay a past incident as a role-play with a game master.

## Common mistakes
- **The IC debugs.** The commander starts typing commands and nobody is coordinating any more.
- **Debugging before mitigating.** Forty minutes spent finding the bug while a rollback was available.
- **Changes outside the ops lead.** Well-meaning freelancers make the incident harder to understand.
- **No update cadence.** Stakeholders fill the silence by pinging responders directly.
- **Forgotten temporary changes.** A flag disabled during the incident is still off three months later.
- **Postmortems that name a person.** People learn to hide mistakes, and the next incident is worse.

## In an interview
Incident response comes up in behavioural rounds and in operations-heavy design rounds. Describe the roles, the "only ops changes production" rule and mitigate-first. When asked for a story, structure it as detection, declaration, mitigation, resolution and the postmortem's system-level fixes.

> Takeaway: give incidents a structure. One commander coordinates and holds the big picture; only the operations lead changes production; a communications lead handles updates; everything goes into a live document. Mitigate first, then write a blameless postmortem whose action items fix the system, not the person.

## Most outages come from change
A system that nobody touches tends to keep working. Most outages in mature systems are triggered by a change: a code deploy, a configuration push, a schema migration, a certificate rotation, an OS patch. That makes the deployment process the single biggest lever on reliability. The aim is not to stop changing things (that would stop the business). The aim is to make every change **small, gradual, observable and reversible**.

Amazon puts the principle as "avoid walking through one-way doors". A two-way door is a change you can walk back through: a code deploy you can roll back in minutes. A one-way door is a change you cannot easily undo: dropping a column, deleting data, sending a million emails, writing data in a format old code cannot read. Prefer two-way doors, make walking back through them fast and automatic, and when you must go through a one-way door, do it slowly and deliberately.

## Deployment strategies
Before looking at a full pipeline, it helps to know the three basic ways to replace version N with version N+1 on a fleet.

%%compare Three ways to replace the running version: they trade cost, speed of rollback and how long two versions coexist.
[Rolling]
Replace hosts in batches, e.g. 33% at a time
+ no extra capacity needed
+ simple, the default in most orchestrators
- old and new versions run together for the whole rollout
- rollback is another rolling deploy, minutes
[Blue/green]
Run a full second fleet, switch traffic at the load balancer
+ instant switch and instant switch back
+ new fleet tested before it gets traffic
- double capacity during the switch
- all users move at once, so a bug hits everyone
[*Canary]
Send a small share of traffic to N+1, compare with N
+ a bug hits 1% of users, not 100%
+ automated metrics comparison decides
- needs good per-version metrics
- mixed versions run together
%%

- **Rolling deployment**: take a batch of hosts out of the load balancer, upgrade them, health-check them, put them back, repeat. Kubernetes Deployments do this by default (`maxUnavailable`, `maxSurge`).
- **Blue/green**: two complete environments. "Blue" serves traffic while "green" gets the new version and is tested; the load balancer or DNS then flips all traffic to green. Blue stays warm for a quick flip back. Its catch: if the new version changes the database, flipping back does not undo that.
- **Canary**: named after the canaries miners carried to detect gas. A small slice of production traffic (1%, then 5%, then 25%) goes to the new version, and an automated comparison of its error rate and latency against the old version decides whether to continue. Most large companies combine canaries with rolling batches.

A fourth tool sits beside all three: **feature flags**. Deploying the code and turning the feature on become separate steps. The new code ships "dark" (present but switched off), and the flag is turned on for 1% of users, then more. Turning a feature off is then a config change taking seconds, not a deploy taking an hour.

## A production pipeline in detail
Amazon sends every change through the same pipeline, whether code, infrastructure, configuration or OS patches:
1. **Source and build.** Code review is the last manual approval. Builds compile, run unit tests, and package and sign the artifact.
2. **Pre-production.** *Alpha* and *beta* stages run functional and integration tests. *Gamma* is the most production-like stage: same deployment configuration, same alarms, continuous synthetic "canary" traffic, deployed in several regions.
3. **Gamma one-box.** The new version goes to one host (or container, or a slice of Lambda traffic) while the rest stays on the old version for 30 to 60 minutes. This catches problems that only appear when old and new versions run side by side.
4. **Production in waves.** The goal is never to hurt two regions, or two Availability Zones (AZs, separate datacentres within a region) in one region, at once.
   - **Wave 1**: a low-traffic region, one AZ or cell at a time.
   - **Wave 2**: a high-traffic region, where rare code paths actually get exercised.
   - **Later waves** grow: 3 regions, then up to 12, then the rest. Each still deploys to only one AZ per region at a time.
5. Each wave starts with a **one-box** stage taking at most about 10% of the region's or AZ's traffic, then a **rolling deployment** that replaces at most 33% of hosts at a time.

%%timeline One change moving through production waves: the blast radius only widens after the previous step has baked.
Day 1 09:00 | Gamma one-box, bake 1 h
Day 1 11:00 | Wave 1: one-box in a small region, bake 1 h
Day 1 13:00 | Wave 1 rolling, one AZ at a time
Day 2 01:00 | *12 h bake complete, no alarms
Day 2 10:00 | Wave 2: one big region, bake 2 to 4 h
Day 3 | Waves 3 and 4: 3 regions, then 12
Day 4 to 5 | Remaining regions; change fully deployed
%%

**Bake time** gives slow problems time to show up: memory leaks that take hours to exhaust RAM, daily batch jobs, rare code paths, timezone bugs at midnight. Typical minimums are 1 hour after each one-box, 12 hours after the first regional wave, and 2 to 4 hours after each later wave. A bake can also require a minimum amount of traffic, such as at least 100 calls to the Create API, to prove the new code actually ran. A normal change reaches all regions in about **4 to 5 business days**. Emergency fixes take a faster, approved path.

**Automatic rollback.** Every service has a high-severity alarm in each region covering errors, p50/p90/p99 latency, CPU, memory, disk, error log lines and health checks. These roll up into one aggregate alarm per team, together with the synthetic canary alarms. If it fires, every in-flight deployment for that team in that region rolls back to the previous artifact without a human. One-box stages get alarms scoped to just that box, because 10% of traffic may not move the service-wide numbers enough to notice.

**Blockers and windows.** The pipeline will not start a deployment while the team's alarm is firing. It deploys only when on-call engineers are likely to be awake and at work: not at night, at weekends or on holidays, and for many teams not on Friday afternoons. But windows that are too narrow make changes pile up into large, risky bundles, which is worse.

! Example: what a canary catches that a test misses
! A new version adds a cache lookup on the product page. Tests pass. In the one-box stage it serves 10% of one AZ's traffic, about 400 requests per second.
! After 25 minutes the one-box alarm fires: its p99 is 900 ms against 250 ms on the old hosts, because the cache client opens a new TCP connection per request under real concurrency, something the single-threaded integration test never did.
! The pipeline rolls the box back automatically. Users affected: 10% of one AZ in one small region for 25 minutes, roughly 0.1% of global traffic. Without the one-box stage, a rolling deploy would have reached a third of the fleet before anyone looked.

## When rollback itself is unsafe
Here is the trap. Rollback is only safe if the old version can still work with everything the new version did. In a distributed system, a rolling or canary deployment means **old and new versions run at the same time**, reading each other's data and talking to each other over the network. After a rollback, the old version must also read anything the new version wrote while it ran.

The most common problem is a **protocol or format change**. Two examples:
- **Compression.** V2 compresses data it writes to disk or cache. V1 cannot read compressed data. During the rollout, V1 hosts reading data that V2 hosts wrote fail with parse errors. Roll back to V1 and every record V2 wrote is now unreadable by every running host.
- **Heartbeats.** Servers send heartbeats every 5 s and drop peers that are silent for 5 s. "Just changing a number" to 10 s means new servers go quiet for 10 s, so old servers drop connections to new ones across the fleet, and the cluster partitions itself.

%%seq Why rollback breaks: V2 writes a format V1 cannot read, and the data outlives the rollback.
V2 host > Store : write order 42 as JSON
V1 host > Store : read order 42
Store -> V1 host : JSON bytes
V1 host > V1 host : parse as XML fails, 500 error
Operator > V2 host : roll back to V1
V1 host > Store : read order 42 again
Store -> V1 host : still JSON, still fails
%%

## The two-phase deployment
The fix is to split a format change into two deployments, each of which is safe to roll back on its own. For example, moving stored data from XML to JSON:
| Phase | Version | Reads | Writes | Why rollback is safe |
| Prepare | V2 | XML and JSON | XML | No JSON exists yet, so V1 is fine |
| Activate | V3 | XML and JSON | JSON | V2 can read JSON, so rolling V3 back to V2 is fine |

%%state The two-phase change as fleet states: each arrow forward can be undone by the arrow back.
[*] -> All V1
All V1 -> Mixed V1/V2 : deploy Prepare
Mixed V1/V2 -> All V1 : roll back, no JSON exists
Mixed V1/V2 -> *All V2 : 100% of hosts, bake days
All V2 -> Mixed V2/V3 : deploy Activate
Mixed V2/V3 -> All V2 : roll back, V2 reads JSON
Mixed V2/V3 -> All V3 : bake, backfill old XML
%%

The heartbeat version works the same way. In Prepare, servers accept up to 10 s of silence but still send every 5 s. In Activate, they start sending every 10 s.

Precautions:
- **Prepare must reach 100% of hosts** before Activate starts. A deploy tool that calls a deployment "successful" once most hosts are healthy is not enough; one host that missed Prepare will fail to read JSON. Check the version on every host, including ones that were out of rotation.
- **Bake between phases** for several days. Once V3 has written JSON, rolling all the way back to V1 is unsafe again, so be sure V2 is good first.
- **Do not drop XML support afterwards** until a backfill has rewritten all old records to JSON. Then a third deploy can remove the XML reader.

### Serialisation habits that avoid the problem
- Use standard, evolvable formats (JSON, Protocol Buffers, Avro) instead of custom binary layouts.
- Store an explicit **format version** with the data, so readers know what they are parsing.
- Do not serialise classes you do not own; a library upgrade can change their layout.
- **Tolerate and keep unknown fields**: if an old version reads a record with a new field and writes it back, it should preserve that field, not erase it. Protocol Buffers do this by default. With this rule, many changes do not need two phases at all.
- New fields must be **optional** with a sensible default, so old writers that omit them do not break new readers.

### Test rollback, do not reason about it
Testing must use several hosts and the same deployment configuration as production. A one-host test environment makes every deploy atomic and hides mixed-version bugs completely. A good test is: deploy to half the fleet (old and new side by side), finish the deployment, then roll back fully, with continuous traffic hitting every API throughout and all errors counted.

! Example: adding a "currency" field to orders
! V2 adds `currency` to the stored order record and requires it when reading. Halfway through the rollout, a V1 host updates an order written by V2 and saves it without `currency` (it does not know the field), so V2 hosts reading that order fail. Rolling back also does not fix the records already written.
! Safe version: Prepare (V2) reads `currency` if present and defaults to USD otherwise, preserves unknown fields on write, and does not write `currency` yet. Once V2 is on 100% of hosts, Activate (V3) starts writing it. Rolling back V3 to V2 is safe because V2 reads records with or without the field. A backfill then sets `currency` on old orders, and only after that may code treat it as required.

## Common mistakes
- **"It's just a config change."** Configuration pushes cause as many outages as code; send them through the same staged pipeline.
- **Global changes at once.** A bad flag flipped for 100% of users in every region is a global outage.
- **Rollback never tested.** The first rollback attempt happens during an incident, and it fails.
- **One-way doors inside two-way doors.** A deploy that also drops a column or rewrites data cannot be rolled back, whatever the deploy tool says.
- **Huge bundles.** Twenty changes in one deploy: when it breaks, nobody knows which one.

## In an interview
When a design involves changing a data format, an API contract or a cluster protocol, say out loud: "during the rollout both versions run, so I will deploy readers first and writers second". Mention canaries with automatic rollback, one AZ or region at a time, and feature flags to separate deploy from release. It shows you understand that a design must survive its own upgrades.

> Takeaway: roll out in small, widening waves, one AZ or region at a time, with bake time and alarms that roll back automatically. During a rollout old and new versions run together, so any change to data formats or protocols needs two phases: first teach every reader the new format, then switch the writers.

## The constraint: no downtime, no wrong data
Code is easy to roll back; data is not. A deploy that goes wrong can be reverted in minutes, but a migration that rewrote 200 million rows, dropped a column or locked a table for an hour has already done its damage. Database migrations are the most common one-way doors (lesson 14.04) in software, so they need their own discipline.

Two things make them hard. First, **the application keeps running**: there is no maintenance window in which nothing reads or writes. Old and new versions of the code run side by side during every deploy, so at every moment both must work against whatever schema exists. Second, **scale**: operations that are instant on a 10,000-row table take hours on a 2-billion-row table, and some of them hold locks that block every query while they run.

Stripe is a good case study because it has both constraints at their extreme. It has no maintenance windows, every service must keep getting correct data during a migration, and the data runs to hundreds of millions of objects. At one second per object, migrating 100 million objects one by one would take over three years, so even the backfill has to be designed.

## Expand and contract
The case: each Customer record used to hold its subscriptions **inline** (first a single field, later an array). Every subscription change rewrote the whole customer, and finding subscriptions meant scanning customers. The goal was a separate `subscriptions` table.

The pattern is called **expand and contract** (also parallel change or dual writing). First you expand: add the new structure alongside the old, so both exist. Then you migrate traffic onto it step by step. Finally you contract: remove the old structure. In four steps:
1. **Dual write.** Write every change to both the old place and the new table. Then **backfill** the existing data into the new table.
2. **Switch reads.** Move every read to the new table, after verifying it returns the same answers.
3. **Switch writes.** Make the new table the only place written to.
4. **Remove the old data.** Delete the old field and its contents.

%%timeline Expand and contract over several weeks: at every point one store is complete and correct, and each step can be undone.
Week 1 | Create subscriptions table, empty
Week 1 | Dual writes ramped 1% to 100%, watching DB load
Week 2 | Backfill copies historic subscriptions; verify job confirms none missing
Week 3 | *Shadow reads compare old and new; reads switch to new table
Week 5 | Writes moved to new table one code path at a time
Week 7 | Old accessor raises errors; stragglers fixed
Week 8 | Old arrays emptied lazily, final sweep deletes the rest
%%

Each step can be rolled back on its own, and each runs for a while before the next. That is the whole point: you never flip everything at once, and you never reach a state where neither store is trustworthy.

**Step 1 in detail.** Dual writes were ramped up gradually while watching database metrics, because writing twice adds load. Existing subscriptions were copied lazily whenever they were updated. The rest needed a **backfill**. Instead of scanning the production database (which would compete with live traffic), Stripe loaded a database snapshot into Hadoop. A MapReduce job (written in Scalding) listed the subscription IDs to copy, and a fleet of workers copied them in parallel. Afterwards the job ran again to confirm nothing was missing.

**Step 2** used GitHub's Scientist library (lesson 14.06) to read from both stores and compare results in production. Mismatches raised alerts. Reads moved to the new table only once results matched.

**Step 3** was the hardest. Subscription logic (updates, proration, renewals) spanned thousands of lines across services. Stripe changed one small code path at a time, never more than a few hundred lines at once, with more Scientist experiments along the way. To find forgotten callers, they made the old accessor **raise an error** if anything still used it.

**Step 4.** Old arrays were emptied lazily as customers were loaded. A final job swept up whatever was left.

! Example: sizing a backfill
! You must copy 400 million rows. A single worker doing one row per round trip at 2 ms manages 500 rows per second: 400,000,000 ÷ 500 = 800,000 s, about 9 days.
! Batch 1,000 rows per statement at about 200 ms per batch: 5,000 rows per second per worker. Twenty workers give 100,000 rows per second: 4,000 s, just over an hour of pure work.
! But the primary also serves live traffic and replicas must keep up. If replication lag climbs above 5 s, pause. In practice you might throttle to 20,000 rows per second, so plan for about 6 hours, run it in the quiet period, and make it resumable (track the last ID copied) so a crash does not restart from zero.

## Schema changes without locking the table
The same idea applies within one table. Some `ALTER TABLE` operations rewrite the whole table or take a lock that blocks reads and writes, which on a big table blocks traffic for minutes or hours. Which operations do this depends on the database and its version, so always check before running one in production.

There is a subtle extra hazard in PostgreSQL. Even a "fast" `ALTER TABLE` needs a brief exclusive lock. If a long-running query holds a conflicting lock, the `ALTER` waits in the queue, and **every new query on that table queues behind the ALTER**. A 1 ms change can cause a 2-minute outage. Always set `lock_timeout` (say 2 s) so the migration gives up and retries instead of blocking everyone.

### The safe sequence for a new required column
1. **Add the column as nullable**, with no default that forces a rewrite. On modern databases this changes only metadata and is instant. (PostgreSQL 11 and later can also add a column with a constant default instantly, but a volatile default such as `now()` still rewrites.)
2. **Deploy code that writes it** for all new and updated rows. Old code that does not know the column still works, because the column accepts NULL.
3. **Backfill** old rows in small batches (say 1,000 rows each, with short pauses), so you avoid huge transactions, long lock waits and replication lag.
4. **Add the NOT NULL constraint** once every row has a value. In PostgreSQL, add `CHECK (col IS NOT NULL) NOT VALID` first (instant, enforced for new writes), then `VALIDATE CONSTRAINT` separately; validation scans the table without blocking writes. From PostgreSQL 12, a validated check constraint lets `SET NOT NULL` skip its own full scan.
5. Only then deploy code that **relies** on the column always being present.

%%state A new required column moves through states; at each one, both the old and the new code still work.
[*] -> Absent
Absent -> Nullable : ADD COLUMN, metadata only
Nullable -> Written : deploy code that fills it
Written -> Backfilled : batched UPDATE of old rows
Backfilled -> Checked : CHECK NOT VALID, then VALIDATE
Checked -> *Required : SET NOT NULL, code relies on it
%%

If you add NOT NULL first, one of two bad things happens: the database rewrites or scans the table under a heavy lock to fill or check the value, or old code still running during the deploy fails every insert because it does not supply the new column.

### Other common changes, done safely
| Change | Unsafe way | Safe way |
| Rename a column | `RENAME COLUMN` while old code runs | add new column, dual write, backfill, move reads, drop old |
| Drop a column | drop, then deploy code | deploy code that ignores it, wait, then drop |
| Add an index | `CREATE INDEX` (blocks writes) | `CREATE INDEX CONCURRENTLY` in PostgreSQL, online DDL in MySQL |
| Change a column type | `ALTER TYPE` with a table rewrite | new column, dual write, backfill, switch |
| Add a foreign key | add and validate in one step | add `NOT VALID`, then `VALIDATE` separately |

Notice the order for dropping: **code first, schema second**. For adding: **schema first, code second**. In both cases the schema must always be compatible with every version of code that might be running.

## gh-ost: online schema change for MySQL
For changes MySQL cannot do in place, GitHub's **gh-ost** copies the table instead of altering it:
1. Create an empty **ghost table** with the new schema.
2. **Copy existing rows** into it in small batches, in primary key order.
3. At the same time, **read the MySQL binary log** (the replication stream of every row change) and apply every insert, update and delete on the original table to the ghost table.
4. When the ghost table has caught up, **cut over**: atomically rename the tables so the ghost becomes the real table and the original is kept under another name.

%%seq gh-ost: copy rows, replay changes from the binary log, then swap the tables atomically.
gh-ost > MySQL : CREATE TABLE _orders_gho (new schema)
gh-ost > MySQL : copy rows 1 to 1,000 into ghost
App > MySQL : UPDATE orders row 57
MySQL -> gh-ost : binlog event: row 57 updated
gh-ost > MySQL : apply same update to ghost
gh-ost > MySQL : copy rows 1,001 to 2,000 (repeat)
gh-ost > gh-ost : ghost caught up, wait for quiet period
gh-ost > MySQL : RENAME orders to _orders_del, _orders_gho to orders
%%

Older tools (such as pt-online-schema-change) did step 3 with **triggers** on the original table. gh-ost avoids triggers, because they add work to every write inside the application's own transaction, compete for locks, and cannot be paused: once the trigger exists, every write pays for it.

%%compare Trigger-based online schema change versus binlog-based: same idea, different way of capturing ongoing changes.
[Triggers]
app write -(same transaction)-> trigger -> ghost table
- extra work inside every app transaction
- cannot pause without dropping triggers
- lock contention on busy tables
[*Binlog (gh-ost)]
app write -> binlog -(async)-> gh-ost -> ghost table
+ app transactions unchanged
+ true pause when replicas lag
+ cut-over can wait for a quiet time
%%

Reading the binlog asynchronously gives gh-ost control:
- **True pause.** When throttled (for example because replicas are lagging), it stops all its own writes, both row copying and event applying, so the primary returns to normal load.
- **Interactive control.** You can change settings such as batch size while it runs, through a socket.
- **Postponed cut-over.** You can delay the swap until a quiet period or until a human approves.
- **Test on a replica.** It can run the whole migration on a replica and leave both tables for comparison. GitHub runs this continuously against production replicas.

! Example: the lock queue outage
! At 10:00 an analyst starts a 5-minute report query on `orders`. At 10:01 a migration runs `ALTER TABLE orders ADD COLUMN note text`, which needs a short exclusive lock but must wait for the report.
! From 10:01, every new `SELECT` and `INSERT` on `orders` waits behind the ALTER. The connection pool fills in seconds, and checkout returns errors for 4 minutes, until the report finishes.
! With `SET lock_timeout = '2s'`, the ALTER gives up at 10:01:02, nothing queues behind it, and the migration tool retries a minute later. Same change, no outage.

## Common mistakes
- **Changing schema and code in one deploy** so that old code running during the rollout breaks against the new schema.
- **One giant UPDATE** to backfill: a single transaction that holds locks for an hour and floods replication.
- **No lock timeout**, so a quick DDL queues behind a slow query and blocks the table.
- **Dropping the old column too early**, before every reader has moved and before you are sure you will not roll back.
- **No verification** after the backfill: assuming the copy worked instead of counting and comparing.

## In an interview
If your design changes a data model, say how you would migrate it live: expand, backfill in throttled batches, verify with shadow reads, switch reads, switch writes, contract. Mention that schema changes go first and code relying on them second, and that you would set lock timeouts and use online tools for large tables.

> Takeaway: change data at scale with expand and contract: dual write, backfill, move reads (verified), move writes, then delete the old data, so each step can be undone. For schema changes, add columns as nullable, backfill in throttled batches, add constraints last, set lock timeouts, and use tools like gh-ost that copy into a shadow table and swap instead of locking the live one.

?? Adding a NOT NULL column directly can force the database to rewrite or scan the whole table under a heavy lock to fill or check the value, blocking traffic on a large table. It also breaks any old code still running during the deploy that inserts rows without the new column. Adding it as nullable is an instant metadata change that every version of the code tolerates. Code then starts writing the column, a batched backfill fills old rows without long locks or replication lag, and only when every row has a value do you add the constraint (in PostgreSQL as a NOT VALID check, then validated separately without blocking writes). Every step is small, safe while old and new code coexist, and reversible.

## The problem: proving a new read path is right
In a data migration (lesson 14.05) or a rewrite, there comes a moment when you switch reads from the old path to the new one: from the monolith to a new service, from the old table to a new store, from a hand-written SQL query to a search index. Tests cover the cases you thought of. Production has the cases you did not: odd rows from 2014, a customer with 40,000 subscriptions, rounding in a currency with three decimal places, a timezone that changed its rules. A new path can pass every test and still return different answers for 0.3% of real requests, and you will not know until customers complain.

The reliable way to be sure is to run both paths **in parallel on real traffic**, compare their answers, and cut over only once they agree. This is called a **shadow read**, and when you use it to gradually move read traffic off an old system (typically a monolith) you are doing a **read drain**: draining reads from the old path while proving at each step that the new one matches it.

It fits a larger pattern for replacing monoliths, the **strangler fig**: a new system grows around the old one, taking over one capability at a time, until the old one can be removed. Each capability moves in the same order: build the new path, dual write so it has the data, shadow read to prove it, switch reads, switch writes, retire the old code.

%%tree A strangler-fig migration: each capability of the monolith is drained separately, reads before writes.
Monolith
  Orders capability
    Dual write to orders service | done
    *Shadow reads at 25% | in progress
    Switch reads | waiting
    Switch writes | waiting
  Search capability | fully moved to search service
  Billing capability | not started
%%

## GitHub Scientist
Scientist is GitHub's Ruby library for exactly this job (ports exist for many other languages). You wrap the old code as the **control** (`use`) and the new code as the **candidate** (`try`):

```ruby
def allows?(user)
  science "widget-permissions" do |e|
    e.context user: user
    e.use { model.check_user(user).valid? }  # control: old path
    e.try { user.can?(:read, model) }        # candidate: new path
  end
end
```

Each time the experiment runs, Scientist:
1. decides whether to run the candidate at all (`enabled?`, for example 1% of calls);
2. runs both blocks **in random order**, so neither always benefits from warm caches or suffers from cold ones;
3. measures the time each one takes;
4. **rescues any exception from the candidate**, so a bug in the new code cannot break the request;
5. compares the two results;
6. **always returns the control's result** to the caller;
7. passes everything (both values, both timings, any mismatch, the context) to your `publish` method, which sends counters and timings to metrics and stores mismatches for review.

%%seq One request inside an experiment: both paths run, the user gets the old answer, the comparison is published.
Caller > Scientist : allows?(user 42)
Scientist > Scientist : enabled? yes (1% sample)
Scientist > New path : candidate (runs first this time)
New path -> Scientist : false, 38 ms
Scientist > Old path : control
Old path -> Scientist : true, 112 ms
Scientist > Publisher : mismatch, timings, context user 42
Scientist -> Caller : true (control result)
%%

The control result is always returned, so users are never exposed to the new path's answers. The cost is extra load: the candidate runs as well, adding its latency to the request (Scientist runs both blocks in the same thread by default) and its queries to the new store.

## In-process versus traffic mirroring
Scientist compares inside the application. Another approach is to mirror at the network layer: a proxy or service mesh copies a share of requests to the new service and discards its responses.

%%compare Two ways to shadow reads: compare inside the application, or copy traffic at the proxy and compare offline.
[*In-process (Scientist)]
request -> app -(both paths)-> compare -> publish
+ compares the actual returned values
+ full context: user, inputs, both results
- candidate latency added to the request
- needs code changes in the old system
[Proxy mirroring]
request -> proxy -(copy)-> new service -> discard
+ no change to the old code
+ new service can be tested at full load
- responses must be logged and diffed offline
- only safe for side-effect-free requests
%%

In-process comparison is better for correctness work because you compare the exact values. Mirroring is better for load testing the new service, and it is the only option when you cannot change the old system.

## Running the experiment
1. **Start small.** `enabled?` turns on the candidate for a small percentage of calls, which limits extra load and the risk from a slow candidate. Scientist does **not** protect you from a candidate that hangs, so put a timeout inside the candidate block and keep the percentage low at first.
2. **Calibrate.** First run the control against itself. Random ordering plus data changing between the two reads (a row updated in the few milliseconds between them) creates false mismatches, so you learn the background noise rate before blaming the new code.
3. **Investigate mismatches.** Each one is either a bug in the new path, a bug in the old path that you must now either reproduce or consciously fix, or noise from timing and ordering.
4. **Teach it about known differences.** `compare` sets what "equal" means, such as comparing only IDs, ignoring list order or rounding floats. `ignore` marks mismatches you understand (for example, the new store returns a slightly newer timestamp). `clean` trims what gets stored for review, so you do not log sensitive data.
5. **Ramp up** until the mismatch rate is zero or fully explained, over a long enough period to cover rare paths: monthly billing jobs, end-of-year reports, the largest customers.
6. **Cut over.** Make the new path the real one. Keep dual writes in place for a while, so the old path stays current and you can switch back if a problem appears.
7. **Retire.** After a quiet period, delete the old read path. Make any remaining old accessor raise an error first, to flush out callers you missed.

%%state A read drain as a sequence of states; any mismatch sends you back to fix before ramping further.
[*] -> Calibrating
Calibrating -> Shadow 1% : control vs control noise known
Shadow 1% -> Fixing : unexplained mismatches
Fixing -> Shadow 1% : fix or ignore rule shipped
Shadow 1% -> Shadow 100% : clean for days
Shadow 100% -> *Cut over : zero unexplained for weeks
Cut over -> Shadow 100% : problem, switch back
Cut over -> Retired : old path deleted
%%

### The big caveat: reads only
Scientist is only safe around code that **does not change data**. Running a write twice, once in each path, would apply it twice: two charges, two emails, two rows. For writes, use dual writing (14.05) and compare the stored results afterwards with a reconciliation job, or make the candidate compute what it *would* write and compare that, without writing.

Even "reads" can hide side effects: a read that updates a `last_seen` column, warms a cache, increments a rate-limit counter or triggers lazy migration. Check that the candidate path is genuinely side-effect free before wrapping it.

### Comparing at the right level
Decide what "the same" means before you start. Comparing whole JSON documents byte for byte produces endless false mismatches from field order, float formatting and timestamps. Normalise both sides first: sort lists that have no defined order, round floats, drop fields that are expected to differ. But do not normalise away real differences: if the old path returns orders sorted by date and the client depends on that order, the order is part of the contract and must match.

! Example: draining order reads out of a monolith
! A monolith answers `GET /orders?user=…` from its own tables; a new orders service should take over. A calibration run (control against control) shows 0.05% background mismatches from orders updated between the two reads.
! Week 1: the candidate runs on 1% of 8,000 requests per second, about 80 per second, and 3% of those mismatch. Investigation finds two causes: the new service sorts ties on the same timestamp differently (fixed by a `compare` that sorts by ID first) and it misses cancelled orders older than 2019 (a real backfill bug: the copy job filtered on a status that did not exist then; fixed and re-run).
! Weeks 2 and 3: ramp to 10%, then 100%. Unexplained mismatches stay at 0 over 14 days, including a month-end. The new path's p99 is 40 ms against 120 ms for the old.
! Cut over reads, keep dual writes for a month, then make the monolith's order query raise an error in staging, find one forgotten admin report still calling it, move it, and delete the old path.

! Example: the cost of shadowing
! At 100% shadowing, the new service handles the full 8,000 requests per second as extra load, and each request now does both queries. If the old path takes 120 ms and the new 40 ms and they run one after the other, request latency rises to about 160 ms. So you ramp: at 10%, average added latency is 4 ms and the new service sees 800 requests per second, which also doubles as a load test of the new service before it carries real traffic.

## How Stripe used it
In Stripe's subscriptions migration (14.05), Scientist experiments read subscriptions from both the old inline field and the new table on live traffic. Any mismatch raised an alert. Errors in the new path did not affect users. Reads moved only once the results matched. During the hardest step, switching writes, more experiments checked each small change. Finally, the old accessor was made to raise an error, flushing out any caller that still used it.

## Common mistakes
- **Shadowing writes.** Double charges and duplicate emails. Shadow only side-effect-free reads.
- **Comparing too strictly or too loosely.** Byte equality drowns you in noise; over-normalising hides real bugs.
- **No timeout on the candidate.** A hanging new path slows every sampled request.
- **Cutting over too early.** Two clean days miss the monthly job and the largest customer.
- **Removing dual writes at cut-over.** You lose the ability to switch back cheaply.
- **Logging sensitive data in mismatch records** without cleaning it.

## In an interview
When your design replaces a component, the interviewer may ask "how would you migrate?" Describe the strangler approach: dual write, backfill, shadow reads with result comparison and a mismatch dashboard, ramp, cut over with dual writes still on, then retire. Say explicitly that shadowing is for reads and that writes are verified by reconciliation.

> Takeaway: before switching reads, run the new path in the shadow of the old one on real traffic. Return the old result, catch the new path's errors, compare results and timings, calibrate against background noise, and ramp up until mismatches are zero or explained. Only shadow side-effect-free reads, and keep dual writes after cutting over so you can switch back.

?? Run both paths on live traffic with a tool like GitHub Scientist. The old path is the control and its result is always returned to the user. The new path runs as the candidate, its exceptions are caught and its result and timing are compared and published. First run control against control to learn the background noise, then start at a small percentage, investigate each mismatch and either fix it or add an explicit ignore or compare rule, and ramp up. ## Nobody wants backups; they want restores
"No one really wants to make backups; what people really want are restores." A backup is only valuable if you can restore from it, within the time your users can tolerate, to the state you actually need. A green "backup job succeeded" tick tells you a process exited cleanly. It does not tell you the file is complete, readable, decryptable, or restorable in less than three weeks. So measure teams on restore success, not on backup jobs completing.

Two kinds of copy are often confused:
- **Backups** exist to load back into the running application quickly after a loss. They are taken daily, hourly or continuously, because everything since the last one is at risk.
- **Archives** are long-term copies kept for audit, legal or compliance reasons, such as financial records kept for 7 years. A week to retrieve one is fine, and they often cannot be loaded straight back into the current version of the application.

Two numbers frame every backup design (lesson 14.08 develops them for whole-site disasters). The **recovery point objective (RPO)** is how much recent data you can afford to lose, measured in time: with nightly backups, up to 24 hours of writes. The **recovery time objective (RTO)** is how long the restore may take before service is back.

## Ways data gets lost
Data loss is classified along three axes:
- **Cause**: user action, operator mistake, application bug, infrastructure defect, faulty hardware, or site disaster.
- **Scope**: widespread (everyone's data) or narrow (a few users or one table).
- **Rate**: "big bang" (a million rows replaced by ten in a minute) or **creeping** (ten rows a minute, for weeks).

That gives 24 kinds of failure (6 × 2 × 2), and no single defence covers them all. A dropped table is noticed in seconds; a bug that silently truncates one field on 0.1% of new records may go unnoticed for months. When Google analysed 19 of its own data recovery efforts, the most common user-visible losses came from **software bugs** deleting data or breaking references between records, not from hardware. The hardest ones were low-grade corruption discovered **weeks or months** later, by which time every recent backup contained the damage too.

## Replication is not a backup
"Replication and redundancy are not recoverability." Replicas, RAID and multi-AZ databases protect against hardware failure: a disk dies, a machine dies, a datacentre loses power. But if a bug or a person deletes or corrupts data, replication faithfully copies the damage to every replica within milliseconds. `DELETE FROM orders` with a missing `WHERE` clause runs on all three replicas. What you need are copies **from a point in time before** the damage.

%%compare Replication versus backups: they protect against different failures, and you need both.
[Replication]
primary -(milliseconds)-> replica -> replica
+ survives disk, host, AZ failure
+ failover in seconds, almost no data loss
- copies deletes and corruption instantly
- no way to go back in time
[*Point-in-time backups]
primary -(snapshot + log)-> separate storage
+ restore to before the bad write
+ survives bugs, operators, ransomware
- restore takes minutes to days
- loses writes since the last copy
%%

## Defence in depth: three layers
%%layers Three layers of protection, from fastest to recover at the top to widest coverage at the bottom.
*Soft deletion | deleted data hidden but kept 15 to 60 days; undo in minutes
Tiered backups | snapshots (minutes), distributed copies (hours), offsite (days)
Early detection | validators find corruption before it spreads into every backup
%%

**1. Soft deletion.** Deleted data is marked as deleted and hidden but kept for a while before being destroyed. Typical periods are 15, 30, 45 or 60 days; Gmail's Trash keeps messages 30 days. This covers the most common case, a user or a bug deleting something, and recovery takes minutes, without a restore at all. Most account hijackings and integrity problems are noticed within 60 days, so keeping soft-deleted data much longer adds little. (Lesson 14.09 covers how soft deletion interacts with privacy law.)

**2. Backups, tiered.**
- **Tier 1**: frequent snapshots close to the live data, kept for hours to a few days, restorable in minutes. Database snapshots on the same storage system are typical.
- **Tier 2**: copies on a separate distributed filesystem or object store, kept for a week or two, restorable in hours. If you release twice a week, keep at least two weeks, so a bug can be caught and you can restore to before the release that introduced it.
- **Further tiers**: tape or offsite object storage in another region or account, taken less often and kept longer, which survive the loss of a whole site or a compromised account.

Google often keeps 30 to 90 days of backups. Copies should sit on **different technology** and ideally in a **different trust domain** from the live data. If a filesystem bug can destroy the data, a backup on the same filesystem can be destroyed with it. If an attacker or a buggy script with production credentials can delete the database, it should not also be able to delete the backups. That is why object-lock or write-once storage, separate cloud accounts and offline copies matter, especially against ransomware.

**3. Early detection.** Bad data spreads over time: into new records derived from it and into every new backup. Once your oldest backup is newer than the corruption, it is unrecoverable. **Out-of-band validators** check invariants independently of the application: do files in Drive match their folder listings? Does every message reference in Gmail point at a real message? Does the sum of ledger entries equal the account balance? Gmail's validators detect inconsistencies within 24 hours, which is what lets developers ship more than once a week. Validate only the invariants whose failure would really hurt users; overly strict validators raise false alarms and get ignored.

## Point-in-time recovery: how it works
Most production databases combine a periodic **base backup** (a full copy) with a continuous archive of the **write-ahead log** (WAL in PostgreSQL, binlog in MySQL), the ordered record of every change. To restore to any moment, you load the latest base backup taken before that moment, then replay the log up to the exact second you want.

%%timeline Point-in-time recovery: restore Sunday's base backup, replay the log to one second before the bad DELETE.
Sun 02:00 | Base backup taken
Sun to Tue | WAL segments archived every minute or every 16 MB
Tue 14:32:00 | *DELETE without WHERE wipes the orders table
Tue 14:40 | Restore starts: copy base backup to new server
Tue 15:20 | Replay WAL from Sunday to Tue 14:31:59
Tue 16:05 | Restored copy verified, orders table exported back
%%

PostgreSQL offers three backup methods, and the third is the one behind point-in-time recovery:
| Method | How | Good | Limits |
| SQL dump | `pg_dump` exports one database as SQL from a consistent snapshot; `pg_dumpall` for the whole cluster | portable across versions; restore single tables | slow for large databases; no point-in-time recovery |
| File system copy | copy the data directory with the server stopped, or an atomic snapshot of all volumes | fast for big data | whole cluster only; same major version; needs downtime or atomic snapshots |
| Continuous archiving (PITR) | a base backup (`pg_basebackup`) plus every WAL segment archived (`archive_command`) | restore to any moment, e.g. one second before a bad `DELETE` | more moving parts; a failing archive must be alerted on |

Note what RPO and RTO look like here. RPO is the gap since the last archived WAL segment, often under a minute. RTO is the time to copy the base backup plus the time to replay the log, and replay time grows with the distance from the base backup. That is why base backups are taken daily or weekly rather than monthly.

! Example: how long will the restore take?
! The database is 4 TB. Base backups are taken weekly, and the system writes 300 GB of WAL per day. Disaster strikes on day 6.
! Copying 4 TB from object storage at 500 MB/s takes 4,000,000 ÷ 500 = 8,000 s, about 2.2 hours.
! Replaying 6 × 300 GB = 1.8 TB of WAL at, say, 150 MB/s takes 12,000 s, about 3.3 hours.
! Total RTO is about 5.5 hours plus verification. If the target is 2 hours, you need daily base backups (cutting replay to under 40 minutes), a faster copy path (local snapshots), or a delayed replica (a replica deliberately kept, say, 1 hour behind, so you can stop it before it applies a bad change).

## Untested backups fail
Recovery paths that never run quietly break. Real failures include backups that are zero bytes because a disk filled, encryption keys that were rotated and lost, a restore that needs a tool nobody has installed since the old engineer left, credentials that expired, a schema in the backup that no longer matches the application, and restores that would take three weeks because the bandwidth was never measured. You only know you can recover your recent state if you actually do so. So:
- run restores **continuously and automatically**, end to end, into a test environment;
- check that the restored data is complete and correct (row counts, checksums, application-level queries), not just that the job finished;
- measure how long a restore takes, and compare it with your RTO;
- alert when a restore test **fails to report success** (a missing heartbeat), not only when it reports failure, because a broken test system usually reports nothing;
- rehearse the rare restores too: a single table, a single user's data, a whole region from offsite copies.

Two cases show the difference:
- **Gmail, February 2011.** A bug lost user data, and Google restored it from tape for the first time at that scale. Because restores had been rehearsed, the team gave a reliable estimate, recovered over 99% of the data before the estimated finish, and restored every affected account within hours of it.
- **Google Music, March 2012.** A refactored deletion pipeline had a race condition and deleted about 600,000 audio files belonging to 21,000 users. It went unnoticed for a month.

! Example: the Google Music restore, by the numbers
! Of the roughly 600,000 deleted files, 436,223 were on tape. Restoring them took 5,475 restore jobs and recalling 5,337 tapes, about 1.5 PB.
! 17 tapes turned out to be bad, and the offsite vendor left out 1,862 tapes from the shipment, so redundant copies were used. It took almost 7 days.
! About 161,000 files had never been backed up at all, because they were uploaded after the last backup and deleted before the next. Those users had to re-upload them.
! The fixes: alert on the **global** deletion rate (for example above 10× its usual 95th percentile), so a deletion bug is caught in hours rather than a month, and keep more frequent backups for new uploads.

## Common mistakes
- **Treating replicas as backups.** They copy the mistake.
- **Backups in the same account and region as production**, deletable with the same credentials.
- **Never restoring.** The first real restore is during the incident, and it fails or takes days.
- **Retention shorter than detection time.** If corruption is noticed after 30 days and you keep 14, every backup is already bad.
- **Measuring backup success, not restore success.**

## In an interview
For any stateful component, say how it is backed up and how fast it restores. "Postgres with daily base backups and continuous WAL archiving to object storage in another account: RPO about a minute, RTO a few hours, tested weekly by an automated restore." Mention soft delete for user mistakes and validators for silent corruption.

> Takeaway: backups only count if restores work, so test restores continuously and automatically and measure their time. Replication copies mistakes, so you also need point-in-time copies on different technology, outside production's credentials. Layer soft deletion, tiered backups and validators that catch corruption before it reaches every backup.

?? Because a backup's only purpose is the restore, and the restore path is exactly what silently breaks when it never runs: jobs that produce empty or partial files, lost encryption keys, missing tools or credentials, unreadable tapes, schemas that no longer match, or restores that take far longer than the outage you can afford. You only find out when you need it, which is the worst possible time. You only know you can recover if you actually do, so run restores continuously and automatically, verify the restored data and the time it took against your RTO, and alert when a restore test does not report success.

## What counts as a disaster
Lesson 14.07 dealt with losing data inside a running system. Disaster recovery (DR) deals with losing the **whole location** a workload runs in, or losing trust in it: a cloud region outage, a fire or flood at a datacentre, a fibre cut that isolates a region, a large operator mistake (deleting a production account), or ransomware that encrypts everything reachable. An event is a disaster when the workload can no longer meet its business goals in its main location, and the only way back is to run somewhere else or rebuild.

Separate DR from **high availability**. Availability is about frequent small failures (a host dies, a bug ships, a traffic spike) and is handled inside the region with redundancy, load balancing and automatic restarts. It is measured as an average over time, like 99.95% per month. DR is about rare, large events and is measured **per event** by two numbers the business must set.

## Two numbers: RPO and RTO
- **RPO (recovery point objective)**: the most data you can afford to lose, measured in time. An RPO of 5 minutes means at most the last 5 minutes of writes may be lost. It is set by how often data reaches the recovery location: nightly backups give an RPO of up to 24 hours; asynchronous replication with 1 s lag gives about 1 s; synchronous replication gives zero.
- **RTO (recovery time objective)**: the longest you can be down, from the moment of the disaster until service is restored. It is set by how much must be done before the recovery location can serve: rebuilding everything takes hours; flipping DNS to a running copy takes minutes.

%%timeline RPO looks backward from the disaster to the last recoverable copy; RTO looks forward to restored service.
13:55 | Last write that reached region B
*14:00 | Region A fails: writes 13:55 to 14:00 lost (RPO 5 min)
14:03 | Health checks confirm, failure detected
14:05 | Failover decision made
14:12 | Region B scaled up, DNS switched
14:15 | Service restored (RTO 15 min)
%%

Two consequences are easy to miss. First, **detection is part of the RTO**. The clock starts when the region fails, not when someone notices, so a 15-minute RTO cannot include a 10-minute wait for a human to wake up. Second, **RPO is about the data that was acknowledged to users**. If you told a customer "order placed" and then lost the order, they will be far angrier than if the order had failed. With asynchronous replication you are accepting that some acknowledged writes can be lost.

How do you pick the numbers? Ask the business what an hour of downtime and an hour of lost data cost (revenue, contractual penalties, regulatory exposure, reputation). Then compare with what each strategy costs per month. A payments system might need RPO zero and RTO 5 minutes; an internal reporting tool might accept RPO 24 hours and RTO 2 days.

## The four strategies
Lower RPO and RTO cost more, because more of the system must already be running and up to date in the recovery region.

%%matrix The four DR strategies: each step up keeps more running in the recovery region, buying lower RPO and RTO for more money.
Strategy | Data in region B | Servers in region B | Typical RPO | Typical RTO | Cost
Backup and restore | backups only | none | hours | hours to a day | low
Pilot light | live replica | off or not deployed | seconds to minutes | tens of minutes | low to medium
Warm standby | live replica | small fleet running | seconds | minutes | medium
Active/active | live, all regions write | full fleet serving | near zero | near zero | high
%%

### Backup and restore
Only backups exist in the recovery region (copied there on a schedule). After a disaster you create everything: networks, databases from backups, servers, load balancers. This depends entirely on **infrastructure as code** (Terraform, CloudFormation and similar): if the environment can only be rebuilt from someone's knowledge and a wiki page, it cannot be rebuilt in a crisis. RPO is the backup interval; RTO is the time to provision everything plus the time to restore the data, often several hours for a large database. Cheapest by far, because you pay only for storage.

### Pilot light
The core data is replicated live into the recovery region (a database replica, replicated object storage), but application servers are switched off or not deployed. Like a gas boiler's pilot flame, the smallest piece is always lit so the rest can be ignited quickly. On failover you promote the database replica, deploy or start the servers, scale them up and switch traffic. RPO is the replication lag (seconds). RTO is tens of minutes, mostly provisioning and scaling.

### Warm standby
A smaller but **fully working** copy of the whole system runs in the recovery region all the time: database replica, a few application servers, load balancers, everything wired up. It can serve traffic **immediately** at reduced capacity. On failover you promote the database, switch traffic and scale the fleet up. Because it is always running, it is also always testable: you can send a trickle of synthetic or real traffic to it every day. Warm standby is the cheapest option that reliably gives an RTO of minutes.

%%compare Pilot light versus warm standby: both have live data in region B; only warm standby can serve the moment you switch.
[Pilot light]
DB replica live -(failover)-> deploy servers -> scale up -> switch DNS
+ cheapest way to keep data current
- cannot serve until servers start
- untested paths: AMIs, quotas, config
- RTO tens of minutes
[*Warm standby]
DB replica + small fleet -(failover)-> switch DNS -> scale up
+ serves at once at reduced capacity
+ can take test traffic every day
- pay for an idle small fleet
- RTO minutes
%%

### Multi-site active/active
The full system runs in two or more regions, and all of them serve traffic. A region failure is no longer a separate "failover" event: health-checked routing just stops sending users to the failed region, and the others absorb the load (so each must have spare capacity, typically running at no more than about 50% to 66% of what it can handle). RPO and RTO approach zero.

The cost is not just doubled infrastructure. The hard part is **writes in several regions**. Either each record has a single home region that accepts its writes (users partitioned by region, with failover of ownership), or every region accepts writes and you must resolve conflicts (last-writer-wins, CRDTs, or application merge rules; lesson 06.03 covers replication). Global strongly consistent databases (Spanner, CockroachDB) solve this with consensus across regions, at the cost of cross-region latency on every write.

### A concrete data layer
Managed databases make the lower rungs easy. Aurora Global Database, for example, replicates to secondary regions with typical lag under one second and can promote a secondary region to read/write in under a minute. That gives an RPO of about a second and a database RTO of a minute. The rest of the RTO comes from everything around the database: application servers, caches, queues, secrets, DNS.

! Example: picking a strategy
! An online store says it can lose at most 1 minute of orders (RPO 1 min) and be down at most 15 minutes (RTO 15 min). It earns about $20,000 an hour.
! Backup and restore is out: restoring a 2 TB database alone takes hours. Pilot light might meet 15 minutes if starting servers is fully automated, but first boot, cache warm-up and quota surprises make it tight.
! Warm standby fits: database replicated with second-level lag, 4 application servers already running in region B (against 40 in region A), failover by promoting the replica, switching DNS (with a 60 s TTL) and autoscaling to 40. Extra cost: perhaps $3,000 a month for the standby fleet and replica.
! Add hourly snapshots and versioned object storage in case of corruption, and a quarterly game day that measures the real failover time.

## Replication does not save you from corruption
The point from 14.07 applies here with extra force. Continuous replication copies **destructive** changes too: deletes, corruption, ransomware encryption, a bad migration. Warm standby and active/active protect against losing a region, not against losing the data's integrity. So every strategy still needs **point-in-time backups or object versioning**, ideally in a separate account with separate credentials, so you can restore to a moment before the damage.

## Failover mechanics and the split-brain risk
Failing over a database means **promoting** a replica to be the new primary. Three hazards come with it:
- **Lost writes.** With asynchronous replication, writes that reached the old primary but not the replica are gone (that is your RPO). Some may surface later when the old region returns, and must be reconciled, not silently merged.
- **Split brain.** If the old primary is not dead but only cut off, both regions may accept writes. Prevent it with **fencing**: revoke the old primary's ability to write (shut it down, remove its credentials, or require a lease or epoch number that the old one no longer holds).
- **Clients still pointing at the old region.** DNS caches, connection pools and hard-coded endpoints keep traffic flowing to the failed side. Use low DNS TTLs, health-checked routing and clients that re-resolve.

%%seq A warm-standby failover: detect, fence the old primary, promote, switch traffic, scale.
Monitor > Monitor : deep health checks fail in region A for 3 min
Monitor > Operator : page: region A down, approve failover?
Operator > Region A DB : fence: revoke write access
Operator > Region B DB : promote replica to primary
Region B DB -> Operator : read/write, last 2 s of writes lost
Operator > DNS : point api.example.com to region B
Operator > Region B fleet : scale from 4 to 40 servers
Region B fleet -> Operator : serving full traffic
%%

Should failover be automatic? For tight RTOs, yes, triggered by **deep health checks** that test real user actions (log in, load a product, place a test order) from several vantage points, not shallow pings. But automated failover on a false alarm is an outage you caused yourself, and flapping between regions is worse. Many teams automate everything except the final decision, which a human approves with one click.

## Testing: the only recovery that works is one you practise
Paths you rarely run do not work when you need them. Assumptions go stale quietly: the DR region's database instance is too small to take the full load, service quotas there were never raised, a config change or a new secret was only added in the main region, the machine images are months old, or the runbook refers to a tool that was retired. The only error recovery that works reliably is the path you test frequently.

So run **game days** that actually fail over (in production, during working hours, with everyone ready), measure the RTO and RPO you really achieve, and fix what broke. Some companies go further and run active/active precisely so that "failover" is exercised every day by normal traffic shifting.

! Example: a game day that found three problems
! The team simulates the loss of region A at 10:00. Target RTO is 15 minutes.
! Failover is approved at 10:04. Replica promotion takes 50 s. Then autoscaling stalls at 25 instances: the instance quota in region B was never raised. A support request takes 40 minutes.
! Meanwhile 30% of traffic still goes to region A: a mobile app version pins a regional hostname.
! Payments fail in region B because the payment provider's API key was rotated in region A's secret store only.
! Measured RTO: 52 minutes. Fixes: raise and monitor quotas, remove regional hostnames, replicate secrets automatically. The next game day achieves 11 minutes.

## Common mistakes
- **No RPO and RTO agreed with the business**, so nobody knows whether the plan is good enough.
- **Treating replicas as the backup**: ransomware or a bad delete reaches region B in a second.
- **Never testing failover**, then discovering quotas, secrets and stale images during the real event.
- **Forgetting dependencies**: DNS, identity provider, secrets, third-party APIs, CI/CD and monitoring must also work from the recovery region.
- **No fencing**, so a partitioned old primary keeps accepting writes and you end up with two diverged databases.

## In an interview
Ask for RPO and RTO early, or state them ("I'll assume we can lose a few seconds of data and be down for at most 15 minutes"). Then pick the cheapest strategy that meets them, name it, and say what replicates and how failover happens. Mention point-in-time backups alongside replication, and regular failover tests.

> Takeaway: RPO is how much data you can lose; RTO is how long you can be down, including detection. Cost rises as you keep more running elsewhere: backup and restore (hours), pilot light (tens of minutes), warm standby (minutes), active/active (near zero). Replication copies corruption, so keep point-in-time backups too, fence the old primary on failover, and test failover regularly.

?? RPO (recovery point objective) is the most data the business can afford to lose, measured as time between the last copy that reached the recovery location and the disaster. RTO (recovery time objective) is the longest it can afford to be down, from the disaster (not from when someone notices) until service is restored. For an RTO of minutes, use warm standby: a scaled-down but fully working copy in another region with live data replication, which can serve traffic immediately after the database is promoted and traffic switched, and only needs scaling up. Active/active gets close to zero but costs much more and needs multi-region writes. Pilot light, which must start servers first, is typically tens of minutes, and backup and restore is hours.

## Why deletion is a design problem
Storing data is easy to design; getting rid of it is not. A modern system copies every piece of user data many times on purpose: replicas for availability, caches for speed, search indexes for queries, events for other services, warehouses for analytics, backups for recovery. Each copy was added by a different team for a good reason, and none of them was designed with "and later, delete exactly this one person" in mind.

Privacy law makes that a hard requirement. Beyond the law, there are good engineering reasons to delete: data you no longer hold cannot leak in a breach, does not cost storage, and does not need protecting. **Data retention** is the policy for how long each kind of data is kept; **deletion** is the machinery that enforces it, both on a schedule and on request.

## The legal requirement
Under the EU's GDPR, Article 17 sets out the "right to erasure" (often called the right to be forgotten). A person can ask a company to erase their personal data, and the company must do so **"without undue delay"** when one of several grounds applies:
- the data is no longer needed for the purpose it was collected for;
- the person withdraws consent and there is no other legal basis;
- the person objects to the processing and there are no overriding legitimate grounds;
- the data was processed unlawfully;
- a law requires erasure;
- it was collected from a child for an online service.

The company must respond to the request within one month (extendable in complex cases). If it **made the data public**, it must also take reasonable steps to tell other companies processing it to erase links and copies. California's CCPA/CPRA and many other laws have similar rights.

There are **exceptions**, where keeping data is necessary for: freedom of expression, a legal obligation (such as tax records the law says to keep for years), public health, archiving and research in the public interest, or establishing and defending legal claims. So erasure is not always total. A bank may have to keep transaction records for seven years while deleting marketing data and app analytics immediately. (This is an engineering summary, not legal advice.)

**Personal data** is broader than names and emails: it includes anything that can identify a person directly or indirectly, such as IP addresses, device IDs, location histories, photos and user IDs that link to any of these.

## Where a user's data actually lives
Deleting the row in `users` is the easy part. By the time a request arrives, the data has usually been copied all over the system.

%%tree Where one user's data ends up: deletion has to reach every branch, not just the users table.
User 42
  Primary stores
    Users DB row | the easy part
    Posts, messages, orders, comments | in other services' databases
    *Other users' copies | feed entries, message threads, mentions
  Derived stores
    Read replicas
    Caches and CDN | profile photo cached at the edge
    Search index
    Object storage | originals, thumbnails, transcodes
  Pipelines
    Kafka topics and dead-letter queues
    Warehouse, data lake, ML training sets
  Operations
    Logs and traces | emails, IPs in log lines
    Backups and archives | snapshots before the request
  Third parties | email, payments, analytics, support desk
%%

- **Primary databases**: the user row and everything that references it (posts, messages, orders, comments), spread across every service that owns a piece.
- **Denormalised copies**: entries in other users' precomputed feeds (lesson 11.05), message threads, notifications, @mentions.
- **Replicas and read stores**: database replicas, search indexes, caches (Redis, CDN copies of a profile photo).
- **Object storage**: uploaded photos, videos and documents, plus all their derived versions (thumbnails, transcodes).
- **Event streams and queues**: Kafka topics retaining events for 7 days or forever, dead-letter queues holding failed messages.
- **Analytics**: data warehouse tables, data lake files, ML training sets and feature stores.
- **Logs**: application logs and traces that contain emails, IP addresses or user IDs.
- **Backups and archives**: every snapshot taken before the deletion.
- **Third parties**: email providers, payment processors, analytics and advertising vendors, customer support tools.

Each kind of store needs a different deletion method:
| Store | How deletion works | Typical delay |
| Primary DB | delete rows, cascade or tombstone references | seconds |
| Cache, CDN | explicit purge, or TTL expiry | seconds to hours |
| Search index | delete by ID, gone after segment merge | minutes |
| Kafka topic | compacted topics take a tombstone; others expire by retention | days |
| Warehouse, lake | rewrite partitions or files without the user | days, batched |
| Logs | retention expiry, or keep personal data out of them | 30 days |
| Backups | expire on rotation, or crypto-shred | months |
| Third parties | API deletion call, contractual obligation | days to weeks |

## How a large provider does it
A large cloud provider (Google Cloud) deletes data in four stages, finishing within about **180 days** end to end:
1. **Request.** A deletion request for a resource, project or account. The data is marked for deletion immediately, with a target of within 24 hours, and stops being served.
2. **Soft delete and recovery period.** Up to about **30 days** during which an accidental deletion can be undone (deleted service accounts, for instance, are disabled for 30 days). After it, a purge signal goes to every product, and it is resent until every product confirms.
3. **Logical deletion from live systems.** The data is marked as free space and overwritten over time. Storage systems built on log-structured files, such as Bigtable, remove it during garbage collection and **compaction** (lesson 07.12) that run on a schedule, because rewriting files is expensive. This takes about **two months**: the recovery period plus two compaction cycles.
4. **Expiry from backups.** Backups are large snapshots on daily, weekly and monthly cycles. They are not edited to remove one user. Instead, deleted data stops being copied into new backups, and old backups **expire** on their normal schedule. This finishes within about **six months**.

%%timeline One deletion request at a large cloud provider: each stage is bounded, so the whole pipeline finishes within about 180 days.
Day 0 | *Request received, data marked deleted within 24 h
Day 0 to 30 | Recovery window: soft deleted, can be restored
Day 30 | Purge signal sent to every product, resent until confirmed
Day 30 to 60 | Compaction cycles overwrite it in live storage
Day 60 | Gone from all live systems
Day 60 to 180 | Older backups expire on their normal rotation
Day 180 | Gone everywhere
%%

The usual argument for a tail like this is that "without undue delay" is judged against what is technically reasonable, and that data in an expiring backup is not being used for anything. The key is that the delay is **bounded and documented**, and that a restored backup must re-apply pending deletions before it is used.

## The deletion pipeline
For your own systems, treat deletion as a distributed workflow, not a statement.

%%seq A deletion request as a tracked workflow: every store must confirm, and the coordinator retries until all have.
User > Account service : delete my account
Account service > Account service : soft delete, schedule purge day 30
Account service > Event bus : UserDeleted(42) on day 30
Event bus > Posts service : UserDeleted(42)
Event bus > Search indexer : UserDeleted(42)
Event bus > Warehouse job : UserDeleted(42)
Posts service -> Deletion tracker : done
Search indexer -> Deletion tracker : done
Deletion tracker > Warehouse job : no ack after 48 h, resend
Warehouse job -> Deletion tracker : done (nightly rewrite)
Deletion tracker > Deletion tracker : all 14 stores confirmed, close request
%%

1. **Accept and soft delete.** Hide the account immediately so nothing more is shown or processed, and schedule a purge date (lesson 03.13 covers soft delete).
2. **Publish a deletion event** on a durable bus that every service and pipeline holding personal data consumes.
3. **Track confirmations.** A deletion tracker records which stores must confirm and resends to any that have not. The request closes only when every store has said "done".
4. **Handle late arrivals.** Events still in flight (a queued message that creates a comment for user 42 after deletion) must be rejected. Keep a list of deleted IDs, or tombstones, that writers check.
5. **Notify third parties** through their deletion APIs and record the response.

## Crypto-shredding
Editing every backup to remove one person is impractical: backups are large, compressed, sometimes immutable by design (lesson 14.07), and rewriting them risks corrupting them. **Cryptographic erasure** (crypto-shredding) solves this. Encrypt each user's (or each resource's) data with its own key, and keep the keys in a separate key store that is **not** in the long-lived backups (or is backed up with a much shorter retention). To delete, destroy the key. Every copy of the data, including the ones in backups, replicas and forgotten exports, becomes unreadable at once.

%%compare Deleting a user from backups: rewriting every copy versus destroying one key.
[Rewrite backups]
find user 42 -> rewrite each snapshot -> verify
- hundreds of TB rewritten per request
- breaks immutable backups
- misses copies you do not know about
[*Crypto-shredding]
user 42 data -(encrypted with K42)-> stores and backups
destroy K42 -> every copy unreadable
+ one small operation
+ reaches unknown copies too
- key store becomes critical
- must encrypt per user from day one
%%

Google Cloud uses this in Cloud Storage, which lets logical deletion finish before every block is physically overwritten. The costs are real: every read needs a key lookup (cached, so a few microseconds), the key store must be extremely available and itself backed up carefully, and losing a key by accident is permanent data loss. It works best for large blobs (files, message bodies) rather than for every small row.

! Example: how much key material?
! 50 million users, one 256-bit data key each, wrapped (encrypted) by a master key in a key management service. Each wrapped key plus metadata is about 100 bytes, so all keys fit in 5 GB, easily held in a replicated database and a memory cache.
! Reading a user's photo means fetching the wrapped key (cache hit, under 1 ms), unwrapping it, then decrypting the photo with AES-GCM at several GB per second on modern CPUs. The overhead is negligible next to the network transfer.
! A deletion destroys one 100-byte row. The 20 GB of that user's photos across live storage, two replicas and 12 backup snapshots are unreadable from that moment.

! Example: tracing one deletion through a social app
! User 42 deletes their account on 1 March. The account is hidden at once and the purge is scheduled for 31 March.
! On 31 March the `UserDeleted` event goes out. Posts and comments are deleted; replies by other users stay but show "deleted user". 900 entries in followers' precomputed feeds are removed by the feed service. The search indexer deletes 312 documents. The CDN purges the avatar URL. Photos are crypto-shredded.
! Kafka topics with 7-day retention drop the old events by 7 April. The warehouse job rewrites affected daily partitions overnight. Logs (which only carry the pseudonymous ID) expire after 30 days. The payment processor is called to delete the stored card; invoices are kept for 7 years under tax law, with the reason documented.
! Backups expire by the end of August. If one is restored before then, the restore procedure replays the deletion list first.

## Designing for deletion from the start
- **Keep a data inventory**: a map of every store that holds personal data, with an owner, kept up to date. A new store is not allowed into production without an entry.
- **Use one stable internal user ID everywhere**, so every store can find a person's data by a single key.
- **Set retention limits by default**, so data expires even without a request: logs 30 days, Kafka 7 days, raw analytics events 13 months, backups 90 days.
- **Keep personal data out of logs**, or log pseudonymous IDs instead of emails and IPs.
- **Use soft delete with a fixed purge date**, so mistakes can be undone but deletion is guaranteed.
- **Separate what you must keep** (invoices required by tax law) from what you must delete, and document the legal reason.
- **Anonymise rather than delete** where aggregate value remains: replacing a user ID with a random value in analytics is acceptable only if the result truly cannot be linked back.

## Common mistakes
- **Deleting only the primary row** and leaving search, caches, feeds and the warehouse untouched.
- **No confirmation tracking**, so a consumer that was down that day never deletes anything.
- **Restoring an old backup** and silently bringing deleted users back.
- **Personal data in logs and metrics labels**, which then live in systems with no deletion path.
- **Unbounded retention** "just in case", which makes every request harder and every breach bigger.

## In an interview
If the system stores personal data, mention deletion briefly: a deletion event consumed by every store, tracked to completion, retention limits by default, backups that expire on a bounded schedule, and per-user encryption keys for large blobs. It shows you think about the whole lifecycle of data, not just the write path.

> Takeaway: erasure is a pipeline, not a `DELETE` statement. Map every copy (primary stores, denormalised copies, replicas, caches, search, object storage, streams, warehouse, logs, backups, vendors), send a deletion event to all of them and track that each confirms, let backups expire on a fixed schedule, and use per-user encryption keys so destroying a key erases the copies you cannot reach.

## Security as a design property
Security in system design is less about clever cryptography and more about boring, consistent checks in the right places. Most real breaches come from a missing authorisation check, a misconfigured storage bucket, an unlimited endpoint or a leaked credential, not from someone breaking TLS. And a growing share of harm is **abuse** rather than intrusion: attackers using your legitimate features (signup, login, password reset, checkout, messaging) at a scale or in a way you never intended.

Two words get mixed up constantly:
- **Authentication** (authn) answers "who are you?": passwords, sessions, tokens, MFA.
- **Authorisation** (authz) answers "are you allowed to do this, to this object?": permission checks on every action.

A system can have perfect authentication and still leak every customer's data if it forgets authorisation on one endpoint.

A useful habit is **threat modelling**: for each component, ask what an attacker could do and what it would cost you. A simple checklist is STRIDE: Spoofing identity, Tampering with data, Repudiation (denying an action because nothing was logged), Information disclosure, Denial of service, and Elevation of privilege. You do not need to be exhaustive; you need to find the cheap, likely attacks before attackers do.

## The common vulnerability lists
OWASP, an open security community, maintains two widely used lists of the most critical risks, built from data on real vulnerabilities.

**OWASP Top 10 (2025), web applications:**
1. **Broken access control**: users can act outside their permissions, such as viewing another user's data or reaching admin functions.
2. **Security misconfiguration**: default passwords, open storage buckets, verbose error pages, unneeded features left on.
3. **Software supply chain failures**: vulnerable or malicious dependencies, build systems and update channels.
4. **Cryptographic failures**: sensitive data sent or stored without strong encryption; weak password hashing.
5. **Injection**: untrusted input interpreted as code or queries (SQL, shell commands, cross-site scripting).
6. **Insecure design**: missing security controls in the design itself, such as no rate limit on a password reset.
7. **Authentication failures**: weak passwords allowed, credential stuffing not stopped, broken sessions.
8. **Software or data integrity failures**: trusting updates, plugins or serialised data without verifying them.
9. **Security logging and alerting failures**: attacks not logged, logs not watched, no alert.
10. **Mishandling of exceptional conditions**: errors that fail open, leak information, or leave the system in a bad state.

**OWASP API Security Top 10 (2023):**
1. **Broken object level authorisation (BOLA)**: `GET /orders/1234` returns order 1234 without checking it belongs to the caller. It is the top API risk because every endpoint that takes an ID can have it.
2. **Broken authentication**.
3. **Broken object property level authorisation**: returning or accepting fields the user should not see or set (`is_admin: true` in a profile update, called **mass assignment**).
4. **Unrestricted resource consumption**: no limits on request rate, payload size, page size or expensive operations.
5. **Broken function level authorisation**: normal users can call admin endpoints.
6. **Unrestricted access to sensitive business flows**: automated abuse of legitimate features, such as bots buying all the tickets or mass account creation.
7. **Server-side request forgery (SSRF)**: making the server fetch a URL the attacker chooses, including internal addresses like the cloud metadata service at `169.254.169.254`.
8. **Security misconfiguration**.
9. **Improper inventory management**: forgotten old API versions and undocumented endpoints that still work.
10. **Unsafe consumption of APIs**: trusting data from third-party APIs too much.

## Broken object level authorisation, step by step
BOLA deserves a closer look because it is so common and so simple. The developer checks that the caller is logged in, then loads the object by the ID in the URL. Nobody checks that the object belongs to the caller.

%%seq A BOLA attack: authentication succeeds every time, authorisation is never checked.
Attacker > API : log in as a normal user (own account 7)
API -> Attacker : session token
Attacker > API : GET /invoices/88213 (own invoice)
API -> Attacker : 200, invoice data
Attacker > API : GET /invoices/88214 (someone else's)
API > DB : SELECT * FROM invoices WHERE id = 88214
DB -> API : row for account 912
API -> Attacker : 200, another customer's invoice
Attacker > Attacker : loop IDs 1 to 100,000
%%

! Example: a BOLA bug, found and fixed
! `GET /api/invoices/88213` returns the invoice to any logged-in user. An attacker loops over IDs 1 to 100,000 at 20 requests per second and downloads every customer's invoices in under 90 minutes. Login worked perfectly; authorisation was missing.
! Fix: the query becomes `SELECT … WHERE id = $1 AND account_id = $caller_account` (taken from the session, never from the request). It returns 404, not 403, for other people's IDs, so the attacker cannot even learn which IDs exist.
! A regression test checks that a second account gets 404 on the first account's invoices. A per-user rate limit and an alert on "more than 200 distinct invoice IDs per user per hour" catch the next one. Random, unguessable IDs (UUIDs) slow enumeration down, but they are a second line of defence, never the only one: IDs leak through URLs, emails and logs.

## Defence in layers
No single control stops everything, so the recurring defences sit at different layers. Each layer stops a different class of attack, and each assumes the one above might fail.

%%layers Defence in depth for a public API, from the network edge down to the data.
Edge | TLS, DDoS scrubbing, web application firewall, per-IP rate limits
Gateway | authentication, per-user and per-key quotas, size limits, timeouts
*Service | authorisation on every object, input validation, field allow-lists
Data | row-level security, least-privilege credentials, encryption at rest
Detection | logs of auth failures and denials, anomaly alerts, audit trail
%%

- **Authorisation on every object access.** Check `order.owner_id == caller` in the data layer, not just at login. Centralise it (a policy library or service) so it is not reimplemented, slightly differently, in 40 handlers.
- **Validate and limit input.** Use parameterised queries (never string-concatenate SQL), allow-lists of fields that can be updated, and limits on body size, page size and query complexity (GraphQL depth limits).
- **Rate limits and quotas** (lesson 14.11) per user, per API key and per IP, plus stricter ones on sensitive flows: login, signup, password reset, checkout, sending messages.
- **Bot and abuse defences** for business flows: challenges (CAPTCHA or proof-of-work) only when signals look suspicious, device fingerprinting, email or phone verification, and **velocity checks** ("5 accounts from this device today").
- **Least privilege.** Each service's database user can touch only its own tables; each machine role can read only its own secrets. A compromised service then exposes little.
- **Secrets and dependencies**: secrets in a vault with rotation, never in code or images; dependency scanning; signed builds and pinned versions.
- **SSRF protection**: when the server fetches user-supplied URLs (webhooks, link previews), resolve the host and block private and metadata address ranges, and fetch from an isolated network.
- **Logging and alerts** on authentication failures, permission denials and unusual volumes, so an attack is noticed while it is happening.

## Case: a public signup endpoint
A signup form is open to anyone on the internet, so it attracts abuse. Think about who benefits from abusing it: spammers want many accounts, fraudsters want free-tier credits, attackers want to know who your users are, and some want to make you pay for SMS messages.

%%matrix Abuse vectors on a public signup endpoint and which defences help against each.
Abuse | Rate limit by IP | Rate limit by target | CAPTCHA on suspicion | Verify email/phone | Uniform response
Fake account bots | yes | partial | yes | yes | no
Account enumeration | partial | yes | partial | no | yes
SMS or email pumping | yes | yes, per number | yes | no, it is the attack | no
Credential stuffing | yes | yes, per account | yes | no | partial
Resource exhaustion | yes | no | partial | no | no
%%

| Abuse | What it costs you | Defence |
| Fake account creation by bots | spam, fake reviews, free-tier abuse, polluted metrics | per-IP and per-device rate limits, CAPTCHA when signals look automated, email or phone verification before the account can act |
| Account enumeration ("email already registered") | attackers learn who has accounts, then target them with phishing or stuffing | the same response and timing whether or not the email exists; send the "you already have an account" message by email instead |
| SMS or email pumping | attackers trigger verification messages to premium-rate numbers or spam lists; you pay per message | rate limit per phone number, per number prefix and per IP; block high-risk country prefixes you do not serve; cap daily spend and alert on it |
| Credential stuffing via the linked login | reused leaked passwords take over accounts | rate limits per account and per IP, breached-password checks, MFA |
| Resource exhaustion | huge payloads or slow requests tie up servers | size limits and timeouts at the gateway |

! Example: an SMS pumping attack, priced
! Signup sends a 6-digit code by SMS. An attacker scripts 40,000 signups overnight using phone numbers in a range they share revenue on, at premium-rate destinations costing about $0.08 per message.
! Cost by morning: 40,000 × $0.08 = $3,200, and the attacker keeps a share. None of these accounts ever verifies.
! Defences, in order of payoff: a cap of 3 codes per phone number per day and 20 per number prefix per hour; a global spend alert at 3× normal hourly SMS volume; blocking country prefixes with no customers; a CAPTCHA before sending a code when the IP or device is new; and monitoring the ratio of codes sent to codes verified (normal is 80%; under attack it falls to 2%).

### Uniform responses and timing
Account enumeration works because the system behaves differently for existing and new emails. Fixing the message is not enough if the response time also differs: checking a password hash for an existing user might take 200 ms (bcrypt is deliberately slow) while a missing user returns in 5 ms. Attackers can measure that. Make both paths do similar work, or do the slow work asynchronously and return immediately in both cases.

## Common mistakes
- **Authorisation only at the gateway or UI.** Hidden buttons do not stop direct API calls.
- **Trusting IDs, roles or tenant IDs from the request body** instead of from the authenticated session.
- **Mass assignment**: binding the whole JSON body to the database model, so a user sets `role=admin`.
- **No limits on cost-generating flows** such as SMS, email, file processing or AI calls.
- **Secrets in code, images or logs**, discovered later in a public repository.
- **Detailed error messages** (stack traces, SQL) returned to clients.
- **No logging of denials**, so a slow enumeration attack runs for weeks unnoticed.

## What a rate limiter is for
A **rate limiter** caps how many requests a client may make in a period: 100 per second per user, 5 login attempts per minute per account, 10,000 calls per day per API key. Requests over the limit are rejected straight away, usually with HTTP **429 Too Many Requests**. It protects the system from a single client using more than its share, whether by accident (a retry loop, a runaway test script, a buggy mobile release) or on purpose (scraping, credential stuffing, denial of service). It also enforces commercial plans: the free tier gets 60 requests a minute, the paid tier 6,000.

This lesson is about **where** to put the limiter, **what key** to count by and how to make shared counting correct and fast. Lesson 14.12 covers the counting algorithms themselves, and lesson 15.02 puts it all together in a design.

## Rate limiters and load shedders
Two related tools solve different problems:
- A **rate limiter** limits how fast each **client** can send. It is about fairness and suits cases where a client can spread its requests out without changing the outcome.
- A **load shedder** decides based on the **whole system's** health. During overload it drops low-priority traffic so critical traffic survives, regardless of which client sent it (lesson 02.13).

Stripe runs four, in order of how often they fire:
1. **Request rate limiter**: N requests per second per user, with short bursts allowed. It is the most important; it rejected millions of requests in one month, mostly from runaway test scripts. Test mode and live mode get the same limits, so scripts do not break on launch.
2. **Concurrent requests limiter**: at most, say, 20 requests **in flight** per user. This protects expensive endpoints from clients that retry slow requests and pile on. It fired about 12,000 times in a month.
3. **Fleet usage load shedder**: requests are split into critical (creating a charge) and non-critical (listing charges). A share of capacity, say 20%, is always kept for critical requests; non-critical ones beyond their share get HTTP 503.
4. **Worker utilisation load shedder**: the last line of defence. When workers run out, it sheds traffic in order: test mode first, then GETs, then POSTs, keeping critical methods longest. It sheds and restores gradually to avoid flapping. It fired about 100 times in a month.

%%bars How often each of Stripe's limiters fired in one month: everyday per-user limits do most of the work, emergency shedding is rare.
*Request rate limiter | 3000000 | millions
Concurrent requests limiter | 12000 | about 12,000
Worker utilisation shedder | 100 | about 100
%%

Note the second one: a concurrency limit catches a problem a rate limit misses. A client sending 10 requests per second is well under a 100 per second limit, but if each request takes 30 s because the endpoint is slow, that client holds 300 workers. Counting requests **in flight** (increment on start, decrement on finish) bounds that.

### Rollout advice
- **Fail open** by default: if the limiter's store is down or the limiter has a bug, let traffic through rather than taking the API down.
- Return **429** for rate limits and **503** for load shedding, with messages that tell the client what to do.
- Put each limiter behind a **feature flag** as a kill switch, with metrics on how often it fires and for whom.
- **Dark launch** first: log what it *would* block, tune thresholds so legitimate usage passes, and sometimes help heavy customers change their code before enforcing.

## Where to put the limiter
There are three main placements, and the choice decides what the limiter can see and how accurate it is.

%%compare Three places to run a rate limiter: what it can see, what it costs, and how accurate the shared count is.
[In-process]
request -> app server -(local counter)-> handler
+ no extra hop, microseconds
+ keeps working if the network fails
- each of 20 servers counts alone
- user gets about 20x the limit
[Dedicated service]
request -> app -(RPC)-> limiter service -> store
+ global view, rich business context
- extra hop on every request
- another service that can fail
[*Gateway + shared store]
request -> gateway -(Lua script)-> Redis -> app
+ rejects before the app does any work
+ one place for every service's rules
- sees only HTTP data: IP, headers, token
%%

| Placement | Good | Bad |
| In each app server (in-process) | fastest, no extra hop | each server sees only its share; with 20 servers a user effectively gets about 20× the limit |
| Dedicated rate-limit service | global view, can use business context | extra network hop per request, another thing that can fail |
| API gateway or load balancer | rejects bad traffic before it reaches the app; most common | only sees HTTP data (IP, headers, token), not business details |

The usual choice is the **gateway**, with shared state in **Redis** (or a similar fast store) so all gateway instances count the same user together. In-process limiting still has a place: as a cheap, coarse **local** guard (for example, each server allows at most 2× its fair share) that keeps working if Redis is unreachable. Many systems use both: a local limit for protection, a global limit for fairness.

Why not just divide the limit by the number of servers? Because load balancers do not spread one user's traffic evenly. With sticky sessions or few connections, all of one user's requests may land on one server, which would reject them at a twentieth of the limit while the other 19 sit idle.

## Which key to limit by
The **key** is what the counter is attached to. It decides who shares a limit.

%%matrix Choosing the rate-limit key: each is right for a different kind of traffic and wrong for another.
Key | Works before login? | Fair per person? | Survives IP changes? | Matches billing? | Easy for attacker to rotate?
User ID | no | yes | yes | partial | no, needs accounts
API key | no | partial, one key many servers | yes | yes | no, keys are issued
IP address | yes | no, NAT groups many users | no | no | yes, botnets and proxies
Target account | yes | yes | yes | no | no, targets are fixed
%%

| Key | Use when | Watch out for |
| **User ID** (from the session or JWT) | logged-in users; fairest per person | does not help on unauthenticated endpoints |
| **API key** | developer APIs, per customer or per app; matches billing and plans | one customer may run many servers on one key; leaked keys |
| **IP address** | anonymous traffic: login, signup, public pages; first line against floods | NAT: an office, university or mobile carrier puts thousands of users behind one IP, so set IP limits higher; attackers rotate IPs |

**NAT** (network address translation) is the big trap with IP limits. A mobile carrier's carrier-grade NAT may put tens of thousands of phones behind a few hundred public IPv4 addresses. A limit of 10 signups per hour per IP would block a whole city. With IPv6, the opposite problem appears: one user can have billions of addresses (a /64 block), so limit by the /64 prefix, not the full address.

Real systems **layer** several keys, and the most restrictive rule that applies wins.

%%tree A layered rule set: a request is checked against every rule that applies, and the strictest decides.
Incoming request
  Global | 50,000 req/s across all clients
  Unauthenticated routes
    Per IP | 300 req/min
    Login: per target account | 5 failures/min
    Signup: per IP /24 or /64 | 20 per hour
  Authenticated routes
    *Per user ID | 100 req/s, burst 200
    Per API key, by plan | free 60/min, paid 6,000/min
    Expensive endpoint: per user | 2 exports per hour
%%

Login is the classic example of needing two keys. Limiting by IP alone misses a botnet that tries one password per IP against the same account from 10,000 IPs. Limiting by target account catches that, while the IP limit catches one IP trying many accounts (credential stuffing).

## Making it correct and fast
### Atomic updates
Reading the counter, computing the new value and writing it back must happen as one step. Otherwise two concurrent requests both read "99 of 100", both pass and both write 100: one extra request slips through, and under heavy concurrency many do. In Redis, do the whole check in a **Lua script**, which runs atomically on the server, or use a single atomic command (`INCR` for a fixed window counter).

%%seq Two gateways check the same user against one Redis key; the Lua script makes each check atomic.
Gateway 1 > Redis : EVAL limiter.lua key=rl:user:42 (rate 100/s)
Redis > Redis : refill tokens, take 1, 0 left
Redis -> Gateway 1 : allowed, remaining 0
Gateway 2 > Redis : EVAL limiter.lua key=rl:user:42
Redis > Redis : refill (2 ms passed, 0.2 tokens), none to take
Redis -> Gateway 2 : rejected, retry after 8 ms
Gateway 2 > Gateway 2 : 429, Retry-After: 1
%%

### Scale and latency
One Redis instance handles roughly 50,000 to 100,000 limiter checks per second (each check is several operations inside the script). The check adds a network round trip, typically 0.2 to 1 ms in the same datacentre. For 1 million requests per second, shard by client key across about 10 to 20 shards; Redis Cluster does this with its 16,384 hash slots, and because all of one key lives on one shard, the Lua script still sees the whole count.

! Example: sizing the limiter store
! The API serves 400,000 requests per second at peak from 8 million active users. Each request needs one limiter check against the per-user key and, for 20% of requests on unauthenticated routes, one more against an IP key: 480,000 checks per second.
! At about 60,000 checks per second per Redis shard with headroom, you need 480,000 ÷ 60,000 = 8 shards; use 12 so losing one shard (and its replica failing over) does not overload the rest.
! Memory: a token bucket stores two numbers per key, about 100 bytes with Redis overhead. 8 million users plus 3 million IP keys is 11 million keys × 100 bytes ≈ 1.1 GB. Set a TTL on each key (say twice the refill time) so idle users disappear on their own.

### Hot keys
One huge customer sending 50,000 requests per second on one API key puts all that load on one Redis shard. Options: give that key a local pre-limiter on each gateway that only forwards a sample to Redis, split its limit into N sub-keys (`key:0` to `key:7`, each with an eighth of the limit, chosen at random per request), or batch: each gateway takes tokens in blocks of 100 and spends them locally.

### Fail open or closed?
Stripe fails open: a limiter outage should not become an API outage. A social API might choose to fail closed, because Redis failures often happen during traffic spikes, exactly when backends need protection. Payments and security endpoints (login, password reset) usually fail closed or fall back to a strict local limit. Either way, alert when the fallback activates.

### Tell the client
Return 429 with headers such as `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset` and `Retry-After`. Reject immediately rather than queueing, so the client's own timeout and backoff logic works. Well-behaved clients then retry with exponential backoff and jitter (lesson 02.09).

### Configuration
Rules change often (a customer upgrades, an attack starts). Store them in a rules table or config service; gateways poll it about every 30 seconds and cache rules locally, with pushes for urgent changes such as blocking an attacking IP range.

! Example: the 20-server mistake
! A team limits each user to 100 requests per minute with an in-memory counter on each of 20 app servers behind a round-robin load balancer. A scraper sends 1,800 requests per minute. Each server sees about 90, under its 100, so nothing is blocked: the effective limit is 2,000.
! Moving the counter to Redis at the gateway, keyed by user ID, blocks the scraper after 100. A legitimate user who sends bursts of 30 is unaffected.

## Common mistakes
- **Per-server counters** behind a load balancer, giving each client N times the limit.
- **Read-then-write without atomicity**, letting concurrent requests slip through.
- **IP-only limits** that block whole offices and mobile networks while botnets walk past.
- **Trusting `X-Forwarded-For` blindly**: clients can set it. Use the address your own edge proxy recorded.
- **No kill switch or dark launch**, so a mistuned rule blocks your biggest customer on day one.
- **Limiting only request count** when cost varies wildly per request; weight expensive calls or add a concurrency limit.

Say where the limiter lives (gateway, shared Redis, Lua for atomicity), what the keys are (user ID, API key, IP with NAT-aware limits, layered), what happens when Redis fails (fail open with a local fallback) and what the client sees (429 with Retry-After). Then mention that load shedding is a separate, system-wide mechanism.

Limit by user ID when logged in, API key for developer APIs, and IP for anonymous traffic (with NAT-friendly limits), layering several keys with the strictest winning.

## What the algorithm has to answer
Every rate limiter, wherever it runs (lesson 14.11), has to answer one question on every request: "has this client used up its allowance for the current period?" The algorithm decides what "the current period" means and how much state you keep to answer it. The choices trade **accuracy** (does it ever allow more than the limit, or block someone under it?), **memory per client**, **cost per request** and **burst behaviour** (can a client send its whole allowance in one second?).

There are four common algorithms. This lesson builds them up from the simplest, shows exactly where each one leaks, and works through the sliding window counter that large edge networks use.

## Fixed window: simple but leaky
A **fixed window counter** keeps one counter per client per calendar window, keyed like `count:user42:12:01`. Each request increments it; if the result is above the limit, reject. When the minute changes, a new key starts at zero. In Redis it is just two commands: `INCR key` and, on the first request of the window, `EXPIRE key 60`.

It is cheap (one integer per client) and easy to reason about. The flaw is at the **boundary**. With a limit of 100 per minute, a client can send 100 requests at 12:00:59 (allowed: window 12:00 has room) and 100 more at 12:01:00 (allowed: window 12:01 just reset). That is **200 requests in about one second**, twice the limit, and it can happen at every minute boundary.

Why exactly 2×? The limiter only ever looks at calendar windows, but a real 60-second period can start anywhere. Any 60-second span that straddles a boundary covers the end of one window and the start of the next, and each part can hold up to the full limit. So the worst case for any rolling 60 seconds is 2 × limit. Another example: a limit of 5 per minute lets 10 requests through between 2:00:30 and 2:01:30 if 5 arrive at 2:00:59 and 5 at 2:01:00.

There is a second, subtler problem: **synchronised clients**. If many clients are blocked until the window resets, they all retry at 12:01:00, creating a spike at every boundary. Adding random jitter to `Retry-After` helps.

## Sliding window log: exact but heavy
To be exact, store the **timestamp of every accepted request**. In Redis, use a sorted set per client with the timestamp as the score. On each request:
1. `ZREMRANGEBYSCORE key 0 (now − 60s)` removes timestamps older than one window.
2. `ZCARD key` counts what is left.
3. If the count is under the limit, `ZADD key now now` and allow; otherwise reject.

Run it as a Lua script so the three steps are atomic. This is exact for any rolling 60 seconds: no boundary burst, ever.

The cost is memory and work. A limit of 5,000 per hour means up to 5,000 timestamps per client, each about 16 to 20 bytes in a sorted set with overhead, so roughly 100 KB per heavy client. For a million clients near their limit, that is around 100 GB. Each request also does a logarithmic-time sorted set update. Some implementations store rejected requests' timestamps too (so a client hammering the API stays blocked), which makes it heavier still.

## Sliding window counter: the approximation
The **sliding window counter** gets most of the log's accuracy for the fixed window's cost. Keep **two counters** per client: the previous window's count and the current window's count. Estimate the count over the last full window by assuming the previous window's requests were spread evenly across it:

`rate = prev_count × (window − elapsed) / window + curr_count`

Here `elapsed` is how far you are into the current window. The fraction `(window − elapsed) / window` is how much of the previous window still lies inside the rolling 60 seconds that ends now.

! Example: one decision, worked through
! Limit 50 per minute. It is 12:01:15, so we are 15 seconds into the current minute, with 18 requests so far. The previous minute (12:00) had 42.
! The rolling 60 seconds ending now runs from 12:00:15 to 12:01:15. It covers the last 45 seconds of the previous minute (45/60 = 75% of it) plus the current 15 seconds.
! `rate = 42 × 45/60 + 18 = 31.5 + 18 = 49.5`. That is under 50, so the request is allowed, and the current counter becomes 19.
! Five seconds later (elapsed 20 s, assume no more requests), `rate = 42 × 40/60 + 19 = 28 + 19 = 47`. The estimate falls as the old window slides out of view, freeing allowance gradually rather than all at once.

%%compare The same boundary attack against a fixed window and a sliding window counter.
[Fixed window]
12:00:59 -(100 requests, count 100)-> allowed
12:01:00 -(counter resets to 0)-> 100 more allowed
- 200 requests in 1 second
- worst case 2x the limit
[*Sliding window counter]
12:00:59 -(100 requests, count 100)-> allowed
12:01:00 -(estimate 100 x 60/60 + 0 = 100)-> rejected
+ second burst blocked
+ still only two integers per client
%%

Applying it to the boundary attack: at 12:01:00 with 100 requests in the previous minute, `100 × 60/60 + 0 = 100`, so the second burst is **rejected**. As time passes the allowance comes back smoothly: at 12:01:30 the estimate is `100 × 30/60 = 50`, so 50 more requests are allowed. The 2× burst is gone.

### How wrong can the approximation be?
The even-spread assumption is the only source of error. If the previous window's 100 requests all came in its first second, by 12:01:30 they are truly outside the rolling window, yet the estimate still counts 50 of them, so the limiter is stricter than necessary. If they all came in its last second, the estimate undercounts and allows slightly more than an exact log would. The error is bounded by the previous window's count times the fraction remaining, and in practice it averages out.

Cloudflare measured it on 400 million requests from 270,000 sources. Only **0.003%** of requests were wrongly allowed or blocked, and the average difference from the true rate was 6%. There were no false positives (nobody under the limit was blocked); 3 sources slipped through, each by less than 15% over the limit.

Why Cloudflare chose it:
- **Two numbers per counter**, so memory stays tiny across millions of rules and clients.
- **One atomic operation per request**: a memcache `INCR` on the current counter, plus one `GET` that fetches both counters. Cloudflare's stack could rely only on `GET`, `SET` and `INCR`; compare-and-swap failed under attack because of contention on hot keys.
- **One setting**: just a rate. The leaky bucket used by NGINX needs a rate and a burst size, which are hard for customers to tune correctly.

## How it runs at the edge
- **Anycast** routing sends a client to its nearest data centre (a point of presence, or PoP), and a given IP normally keeps reaching the same one. So each PoP counts **on its own**, with no global coordination: lower latency, and one PoP failing does not affect others. The cost is that a client deliberately spread across PoPs could get a limit per PoP, which is acceptable for abuse protection.
- Inside a PoP, counters live in a **memcache cluster behind Twemproxy**, sharded with consistent hashing (lesson 04.07).
- **Counting is asynchronous**: increments happen off the request path, so legitimate requests are not slowed.
- When a client goes over, a **mitigation flag** with an end time is set. Servers check only the flag and cache it locally until it expires, so an attacking source costs almost nothing per request after the first few.

%%seq At the edge: counting happens off the hot path, and once a client is over, a cached flag blocks it cheaply.
Client > Edge server : request 1 from IP X
Edge server > Edge server : no local block flag, serve request
Edge server > Memcache : async INCR current window for X
Edge server > Memcache : GET prev and current counts for X
Memcache -> Edge server : estimate 1,040 of limit 1,000
Edge server > Memcache : SET block flag for X until 12:03:00
Client > Edge server : request 2 from IP X
Edge server > Edge server : local flag cached, return 429 at once
%%

This handled several billion requests a day and attacks of up to 400,000 requests per second against a single domain.

## The token bucket, for comparison
The **token bucket** is the other common choice. A bucket holds up to *capacity* tokens and refills at *rate* tokens per second; each request takes one token, and a request with no token is rejected. You store only two numbers per client, `tokens` and `last_refill`, and compute the refill lazily on each request: `tokens = min(capacity, tokens + (now − last_refill) × rate)`.

It deliberately **allows bursts** up to capacity and then enforces the average rate. For example, capacity 4 and refill 2 per second: an idle client can send 4 requests at once, then 2 per second after that. Choose a sliding window when you want "never more than N in any 60 seconds", and a token bucket when short bursts are fine or even desirable (Stripe allows bursts so customers can handle flash sales). The **leaky bucket** is its mirror image: requests enter a queue that drains at a fixed rate, smoothing output but adding delay.

%%widget bucket A token bucket in action: bursts pass while tokens last, then requests are rejected until it refills at a steady rate.
%%

! Example: memory for 10 million clients
! Fixed window or sliding counter: two 8-byte integers plus key overhead, about 80 to 100 bytes per client in Redis: roughly 1 GB for 10 million clients.
! Token bucket: the same, about 1 GB.
! Sliding log at a limit of 1,000 per hour, with an average client holding 200 timestamps at about 20 bytes each: 4 KB per client, 40 GB in total, and heavy clients at the limit cost 20 KB each. The log is 40 times larger for the same clients, which is why it is reserved for low limits where exactness matters (5 password attempts per 15 minutes).

%%matrix The four algorithms compared: the sliding window counter and token bucket are the usual production choices.
Algorithm | Memory per client | Boundary burst | Allows deliberate bursts | Exact
Fixed window | 1 counter | yes, up to 2x limit | partial, by accident | no
Sliding log | 1 timestamp per request | no | no | yes
Sliding counter | 2 counters | no, nearly none | no | partial, 0.003% wrong
Token bucket | tokens + last refill | no | yes, up to capacity | yes, for its own definition
%%

## Common mistakes
- **Using a fixed window for security limits** where a 2× burst matters (login attempts).
- **Non-atomic updates**, which let concurrent requests slip past any of these algorithms.
- **Forgetting TTLs**, so idle clients' counters fill memory forever.
- **A sliding log for high limits**, burning gigabytes to be exact where an approximation would do.
- **Clock disagreement** between servers computing windows; use the store's clock (Redis `TIME`) or a single time source.

## In an interview
If asked to design a rate limiter, name the algorithms, explain the fixed window's boundary problem in one sentence with numbers, and pick either a sliding window counter (smooth, cheap, nearly exact) or a token bucket (allows bursts) with a reason. Show the formula and one worked decision. That level of detail is usually what distinguishes a strong answer.

> Takeaway: fixed windows reset at boundaries and let up to 2× the limit through any rolling period. A sliding log is exact but stores every timestamp. The sliding window counter keeps two numbers and weights the previous window by its overlap; at large scale it was wrong on only 0.003% of requests. Use a token bucket when you want controlled bursts.

A client can use the whole limit at the very end of one window and the whole limit again at the start of the next, because the counter resets in between. ## What multi-tenancy means
A **tenant** is a customer organisation in a software-as-a-service (SaaS) product: a company using Slack, a shop on Shopify, a team on Jira. A **multi-tenant** system serves many tenants from one codebase and, to a varying degree, one set of infrastructure. The alternative, a separate installation per customer, is how enterprise software used to be sold, and it is why upgrades took years.

Multi-tenancy is an economic decision first. Sharing infrastructure lets you serve 10,000 small tenants for a fraction of what 10,000 separate stacks would cost, and ship one change to all of them at once. But sharing creates three engineering problems that every design must answer:
1. **Isolation**: tenant A must never see or change tenant B's data, even when code has a bug.
2. **Noisy neighbours**: one tenant's heavy usage must not degrade everyone else.
3. **Operations per tenant**: onboarding, backup and restore, migration, data residency and billing for each tenant.

## Tenant isolation is more than login
The key point comes first: **authentication and authorisation are not isolation**. Getting past the login screen or API gateway does not mean tenant A's code path cannot touch tenant B's data. If a handler builds a query from a request parameter and forgets the tenant filter, an authenticated user of tenant A reads tenant B's rows. Isolation means each request is limited to its own tenant's resources **all the way down**, so a bug or a malicious query cannot cross over.

## Silo, pool and bridge
There are three basic models, distinguished by what tenants share.

%%compare The three tenancy models: what tenants share, and what that buys or costs.
[Silo]
Tenant A -> App A -> Database A
+ strongest isolation, no noisy neighbours
+ per-tenant cost, backup and residency are easy
- idle capacity per tenant
- onboarding means provisioning
- N deployments and N migrations
[*Pool]
Tenants A, B, C -> shared app -> shared DB
+ cheapest, capacity follows total load
+ onboarding is inserting a row
+ one deploy, one migration
- isolation depends on every query
- noisy neighbours, big blast radius
[Bridge]
Tenants A, B -> shared app -> DB per tenant
+ mix per layer or per tier
+ premium tenants can be siloed
- two operating models to run
%%

**Silo**: each tenant gets dedicated resources: its own database, its own stack, or even its own cloud account or virtual network.
- Good: meets strict compliance, **no noisy neighbours**, easy cost per tenant, small blast radius (one tenant's outage stays with them), per-tenant encryption keys and regions are natural.
- Bad: cost (idle resources per tenant), heavy onboarding (provisioning infrastructure for each new tenant), slower to roll out changes, monitoring spread across many places, and limits on how many accounts or databases you can operate. Twenty siloed tenants may be manageable; a thousand hurts.

**Pool**: all tenants share the same infrastructure, and data is separated by a tenant ID column or key prefix.
- Good: cost efficiency (capacity follows total load, not the sum of peaks), one place to deploy and operate, faster to ship, easy onboarding.
- Bad: **noisy neighbours**, harder cost attribution, **a bigger blast radius** (an outage hits everyone), and customers in regulated industries may refuse to share.

**Bridge**: a mix, decided per layer or per service. For example, a shared web and application tier with a separate database (or schema) per tenant.

**Tiering** packages these as plans: free and basic tenants in the pool, premium or regulated tenants in silos, perhaps with their own region. The same code runs in both; a routing layer looks up each tenant's placement.

### A middle option: schema per tenant
Between shared tables and a database per tenant sits **schema per tenant**: one database server, with one schema (namespace) per tenant holding its own copy of every table. It gives cleaner separation than a `tenant_id` column and easy per-tenant export, without a server per tenant. But a PostgreSQL server with 10,000 schemas × 200 tables has 2 million tables, which strains the catalogue, backups and migration tooling. It works up to hundreds or low thousands of tenants per server.

Two rows deserve more explanation.

**Migrations.** With shared tables, one `ALTER TABLE` covers everyone (done safely, as in lesson 14.05). With 5,000 tenant databases, a migration is 5,000 runs. Some will fail halfway (a lock timeout on one large tenant, a network blip), leaving the fleet on mixed schema versions. The application must cope with both versions until every database catches up, and you need tooling that tracks each tenant's schema version and retries.

**Per-tenant restore.** A tenant deletes half its data by mistake and wants yesterday back. With a database per tenant, restore that database. With shared tables, you restore the whole shared backup to a scratch server, extract that tenant's rows, and merge them back without touching anyone else's newer data: hours of careful work.

Many systems use the pool by default and move big or regulated tenants to silos.

! Example: the cost of siloing small tenants
! You have 4,000 tenants. 3,900 are small (under 1 GB, a few requests per second); 100 are large.
! Silo for everyone: the smallest managed database instance costs about $50 a month, so 4,000 × $50 = $200,000 a month, most of it idle.
! Pool for the 3,900 small tenants on a sharded cluster of 6 databases at $1,500 each ($9,000), plus silos for the 100 large ones at $400 each ($40,000): $49,000 a month. Roughly a quarter of the cost, and the 100 tenants who most need isolation still get it.

## Making the pool safe
Enforce the tenant boundary **below** application code, so a forgotten filter cannot leak data:
- **Tenant context from the token.** The JWT (or session) carries the tenant ID, signed by the identity service; services take it from there, never from a request parameter or body field the user can change.
- **Database-enforced filters.** PostgreSQL **row-level security**: set `app.current_tenant` per connection or transaction, and a policy `USING (tenant_id = current_setting('app.current_tenant'))` means even a query that forgets `WHERE tenant_id = …` sees only its tenant's rows.
- **Scoped credentials.** For DynamoDB, an IAM condition on `dynamodb:LeadingKeys` restricts a request to items whose partition key starts with its tenant ID. Generate these policies on the fly from templates, filling in the tenant ID from the token, instead of creating thousands of static policies.
- **Tenant ID in every key.** Cache keys, object storage paths, search index filters and queue messages all carry the tenant ID. A cache key of `user:42` instead of `t:acme:user:42` is a classic cross-tenant leak.

%%seq Each request carries its tenant, and the database enforces it even when the code forgets the filter.
Client > Gateway : request + JWT (tenant=acme)
Gateway > Service : forward, tenant context = acme
Service > Token manager : credentials scoped to acme
Token manager -> Service : temporary credentials (acme rows only)
Service > Database : SET app.current_tenant = acme
Service > Database : SELECT * FROM orders (no filter)
Database -> Service : only acme rows (row-level security)
%%

A watch-out with connection pools: if the tenant setting is set per connection and a pooled connection is reused for another tenant without being reset, the next request runs as the wrong tenant. Set it per transaction (`SET LOCAL`) so it is cleared automatically on commit.

## Noisy neighbours
In the pool, one tenant running a giant export, a badly written integration or a sales event can consume the shared database, cache or workers. Defences, from cheapest:
- **Per-tenant rate limits and quotas** (lesson 14.11) at the gateway, by plan.
- **Per-tenant concurrency limits** on expensive work: at most 4 export jobs per tenant at once.
- **Fair queuing** for background work: one queue per tenant served round-robin, so a tenant with 1 million queued jobs does not starve a tenant with 10.
- **Per-tenant metrics** (requests, CPU seconds, rows scanned) so you can see who is causing load, and bill for it.
- **Move the tenant**: relocate a consistently heavy tenant to its own shard or silo.

## Shuffle sharding: limiting the blast radius
Sharding the pool limits how many tenants one problem can hurt. Shuffle sharding does much better than plain shards with the same hardware.

Start with 8 workers and no sharding: one "poison" request that crashes workers, retried by the client, can crash them one after another and take down **everyone**. **Regular sharding** into 4 shards of 2 workers limits a bad tenant to its shard: 25% of tenants affected.

**Shuffle sharding** gives each tenant its own random pair of workers out of the 8. There are C(8,2) = **28** possible pairs. Two tenants may share one worker, but rarely both. If a bad tenant kills its two workers, any other tenant still has at least one healthy worker, as long as its client retries on the other one. Only tenants with that exact pair, about 1/28 or 3.6%, lose both. That is **7 times better** than regular sharding, using the same 8 workers.

%%bars Share of tenants that lose all their workers when one tenant's poison request kills its workers: 8 workers in the first three rows, Route 53's 2,048 name servers in the last.
No sharding | 100 | 100%
Regular sharding, 4 x 2 | 25 | 25%
*Shuffle sharding, pairs of 8 | 3.6 | 3.6%
Shuffle sharding, 4 of 2,048 | 0.0000000001 | about 0%
%%

%%tree Shuffle sharding with 8 workers: tenants overlap on single workers but almost never on their whole set.
Workers 1 to 8
  Rainbow | workers 1 and 4
  Rose | workers 1 and 8
  Sky | workers 4 and 6
  Moss | workers 2 and 7
  *Poison from Rainbow kills 1 and 4 | Rose keeps 8, Sky keeps 6, Moss untouched
%%

At scale it gets dramatic. Route 53 has 2,048 virtual name servers and gives each domain 4 of them: C(2048,4) ≈ **730 billion** combinations, enough for every domain to have a unique set, and no two domains share more than 2. A DDoS against one domain saturates its 4 servers, while every other domain keeps at least 2 healthy ones. The attacked domain can then be moved to dedicated capacity. It costs nothing extra: it is just a smarter way to assign existing capacity.

! Example: checking the shuffle-shard arithmetic
! With 8 workers and pairs, the number of distinct pairs is 8 × 7 ÷ 2 = 28. If tenants are spread evenly across pairs, the fraction sharing Rainbow's exact pair is 1/28 ≈ 3.6%.
! The fraction sharing exactly one worker with Rainbow: pairs that contain worker 1 or worker 4 but not both. Each has 6 other partners besides each other, so 6 + 6 = 12 pairs, 12/28 ≈ 43%. Those tenants lose one worker and see some failed first attempts, but retries on the surviving worker succeed.
! The other 15 pairs (54%) share nothing and are unaffected. Compare regular sharding, where 25% are fully down and 75% unaffected: shuffle sharding trades a larger partial impact for a far smaller total outage.

## Common mistakes
- **Tenant ID from the request body** rather than from the signed token.
- **Relying on every developer to remember `WHERE tenant_id`** with no database-level backstop.
- **Cache, search or storage keys without the tenant ID**, leaking data across tenants.
- **Siloing everyone too early**, then drowning in thousands of databases to migrate.
- **No per-tenant metrics**, so a noisy neighbour cannot be identified or billed.
- **Pooled connections that keep the previous tenant's setting.**

## In an interview
Ask about tenant count and size distribution, and about compliance needs. Then propose pool by default with a tenant ID from the token, row-level security as a backstop and tenant IDs in every key; silos for large or regulated tenants behind a routing layer; per-tenant limits and fair queues for noisy neighbours; and shuffle sharding to shrink blast radius.

> Takeaway: pool tenants for cost and speed, silo them for isolation, compliance and blast radius, and mix the two by tier or layer. In the pool, enforce the tenant boundary below the code (tenant from the token, row-level security, scoped credentials, tenant IDs in every key), contain noisy neighbours with per-tenant limits, and use shuffle sharding so one bad tenant can only hurt a tiny fraction of the others.

?? Shared tables with a tenant_id are cheapest for many small tenants, make onboarding an insert, need one schema migration for everyone, and make cross-tenant analytics easy. But isolation depends on every query filtering correctly (row-level security and scoped credentials are the backstop), one tenant's heavy load can slow everyone, and per-tenant restore, data residency and per-tenant keys are hard. A database per tenant gives strong isolation even when code has bugs, no noisy neighbours, easy per-tenant backup, restore, residency and cost tracking, and suits regulated customers. But it wastes money on idle small tenants, onboarding means provisioning, and every migration runs thousands of times and can leave tenants on mixed versions. A common answer is to pool by default and silo large or regulated tenants.
