## Why distributed is different
On one machine, a function call is all or nothing. It returns, or it throws, or the whole program crashes and takes the caller with it. Either way you know what happened. A **distributed system** is a set of programs on separate machines that cooperate by sending messages over a network, and that certainty disappears. Across a network, the caller and the callee no longer share fate: one can crash while the other carries on, and the network between them can lose, delay, duplicate or reorder messages on its own.

A single request and reply between a client and a server takes eight separate steps:
1. The client puts the request on the network.
2. The network delivers it to the server.
3. The server validates it.
4. The server updates its state (writes to its database, say).
5. The server puts the reply on the network.
6. The network delivers the reply.
7. The client validates the reply.
8. The client updates its own state.

Any one of these steps can fail while the others succeed. If step 2 fails, nothing happened. If step 6 fails, the server did the work but the client never hears about it. The nastiest outcome is **UNKNOWN**: the client waited, gave up, and cannot tell whether the server did the work or not. That is why idempotency (lesson 02.09) matters so much: if you cannot know whether an operation ran, you need to be able to run it again safely.

%%seq The eight steps of one remote call. Any one can fail while the others succeed, and failures after step 4 leave the client unsure.
Client > Network : 1. put request on network
Network > Server : 2. deliver request
Server > Server : 3. validate, 4. update state
Server > Network : 5. put reply on network
Network -> Client : 6. deliver reply
Client > Client : 7. validate, 8. update state
%%

### Why testing gets so much harder
Each remote call can end in several distinct outcomes: failed to send, a retryable error, a fatal error, success, or unknown. Code that makes three remote calls in a row has dozens of combinations of outcomes to handle. A function that needed a handful of test cases on one machine can need dozens or hundreds once its steps are remote.

Distributed bugs also hide. They need a rare combination (a timeout on this call, while that node is restarting, during a deploy) and can stay latent for months. When they do trigger, they tend to **spread** along the network rather than stay local. One real example: an amazon.com catalogue server's disk filled up, so it started returning empty responses very quickly. The load balancer, which judged health by response time, saw a server answering fast and sent it more traffic. A single broken machine drew in a large share of requests and took down a big part of the site. A failure that would have been contained on one machine became a system-wide outage because of how the parts interacted.

## The models we reason with
To reason about anything in this module, you first state your assumptions. A **system model** is an explicit list of what can go wrong with the network, the nodes and timing. Algorithms are proven correct under a particular model, and they can break when reality violates it.

### Network models
- **Reliable links**: every message sent is eventually delivered, though maybe reordered. Rarely true on its own.
- **Fair-loss links**: messages can be lost, duplicated or reordered, but if you keep retrying, one eventually gets through. This is the usual assumption, and retries plus de-duplication turn it into a reliable link (TCP does exactly this).
- **Arbitrary links**: an attacker can drop, change or inject messages. Encryption and authentication (TLS) turn this back into fair-loss.

### Node models
- **Crash-stop**: a node that crashes never comes back.
- **Crash-recovery**: a node can crash and restart. It loses its memory but keeps whatever it wrote to disk. This is the realistic model for servers.
- **Byzantine**: a node can do anything, including lying, sending conflicting messages or acting maliciously.

### Timing models
- **Synchronous**: there are known upper bounds on message delay, processing time and clock drift. If a reply has not arrived within the bound, the node is definitely dead.
- **Partially synchronous**: the system behaves synchronously most of the time, but sometimes the bounds are exceeded, for periods of unknown length.
- **Asynchronous**: no timing bounds at all. A message can take any amount of time. No clocks you can trust.

%%matrix The common system models. Real datacenter systems are best described by the last row.
Model | Messages lost? | Nodes restart? | Nodes lie? | Delay bounded?
Synchronous, crash-stop | no | no | no | yes, always
Asynchronous, crash-stop | partial, delayed | no | no | no
Byzantine | yes | yes | yes | maybe
Partially sync, crash-recovery | yes | yes | no | partial, usually
%%

Real systems are best modelled as **partially synchronous with crash-recovery nodes and fair-loss links**. Networks are usually fast, but a switch can buffer packets for seconds, a TCP retransmission can take 200 ms or more, and a virtual machine can be paused by its host. An algorithm that silently assumes synchrony ("a reply always comes within 100 ms") can break when a garbage collection pause or network hiccup violates the assumption, which is exactly when you need it to work.

## Classic impossibilities
Two thought experiments show the limits of what any protocol can achieve.

### The two generals
Two armies camp on either side of a valley. They win only if they attack at the same time. They can only communicate by messengers who cross the valley and might be captured. General A sends "attack at dawn". But A does not know the message arrived, so B sends back an acknowledgement. Now B does not know the acknowledgement arrived, so A acknowledges the acknowledgement. And so on. **No finite number of messages makes both generals certain** that they agree, because the last message sent can always be lost, and its sender cannot know.

The practical lesson: you cannot get certainty of agreement over an unreliable channel. So design for outcomes you can **reconcile** afterwards. An online shop that is unsure whether a charge went through can check later and refund a duplicate. Do not design something that requires both sides to be certain at the same moment.

### The Byzantine generals
Now some generals are traitors who send different messages to different peers. Agreement is possible only if **fewer than one third** of the participants are faulty: you need at least **3f + 1** nodes to tolerate f liars. Most datacenter systems assume crash faults, not Byzantine ones, because the machines are run by one organisation. Byzantine fault tolerance matters for blockchains and some aerospace systems, where participants cannot be trusted or hardware may corrupt data.

## Crashed or slow? The central problem
To act on a failure, a node first has to **detect** it. A **failure detector** usually works with timeouts: send a message (or expect a regular heartbeat), and if nothing arrives within T seconds, **suspect** the node.

But silence has many causes, and from the outside they all look identical:
- The node **crashed**.
- The node is alive but **slow**: a 5 second garbage collection pause, CPU starvation, a disk stall, overload.
- The **request was lost** or delayed in the network.
- The **reply was lost** or delayed in the network.
- The network is **partitioned**: the node is fine and talking to others, just not to you.

%%compare Four very different situations produce the same observation: no reply within the timeout.
[Crashed]
Request -> Node dead -> No reply
- Never answers
[Slow]
Request -> GC pause 5 s -> Reply arrives late
- Answers after you gave up
[Message lost]
Request -> Packet dropped -> No reply
- Node never saw it, or did the work
[*From outside]
Request -> ? -> Silence
- All four look identical
%%

A node only learns about a peer through the messages it receives. It has no way to look inside the other machine. In an asynchronous network, there is no upper bound on how long a message can take, so whatever timeout you pick, a healthy but slow peer can exceed it. This is not a weakness of a particular implementation. It is a fundamental property, and it is behind a famous result (often called **FLP**, after its authors' initials): in a purely asynchronous system where even one node may crash, no deterministic algorithm can guarantee that nodes always reach agreement. Real consensus systems (lesson 06.06) get around it by relying on timing assumptions for **progress** while keeping **safety** independent of timing.

### Perfect and eventually perfect detectors
A **perfect** failure detector never suspects a live node and eventually suspects every crashed one. It only exists in a synchronous system. In practice you get an **eventually perfect** detector: it may wrongly suspect a slow node for a while, but eventually it stops making mistakes. Practical detectors like the **phi accrual** detector (used by Cassandra and Akka) do not give a yes or no answer. They output a suspicion level based on how late the heartbeat is compared with the recent history of heartbeat intervals, and you choose the threshold.

### The timeout trade-off
Timeouts trade **fast detection** against **false alarms**. A short timeout notices a crash quickly but misjudges slow nodes, triggering unnecessary failovers that themselves cause load and disruption. A long timeout avoids false alarms but leaves the system waiting on a dead node.

! Example: picking a heartbeat timeout
! A node sends heartbeats every 100 ms. Measured over a week, 99.9% of heartbeats arrive within 120 ms of the previous one, but garbage collection pauses occasionally delay one by up to 2 s, and once a month a network blip delays them by 4 s.
! Timeout 300 ms: crashes detected in about 0.3 s, but every long GC pause triggers a false failover: several per day.
! Timeout 5 s: no false alarms seen in the data, but a real crash leaves writes stalled for 5 s.
! A common answer is around 1 to 2 s plus tuning garbage collection to shorten pauses, accepting a rare false alarm, and making sure that a false alarm is safe (see below). Many systems use something like this: ZooKeeper session timeouts are usually several seconds, and Raft election timeouts are commonly 150 to 300 ms on fast local networks and longer across regions.

### Designing around uncertainty
Because you cannot tell crashed from slow, every decision made after a timeout must be **safe even if the suspected node is still alive**:
- A node declared dead may still be running and acting on old beliefs. If it was the leader, you may now have two leaders (lesson 06.07). Fencing tokens (06.09) protect storage from the old one.
- A request that timed out may still have been executed. Retries must be idempotent.
- A lock holder that paused past its lease may wake up and keep writing (06.08).
- Timeouts should be set from measured latency distributions, not guessed.

%%timeline A "dead" node that was only paused. The rest of the cluster moved on, and the old node wakes up believing nothing changed.
0 s | Node A is leader, sending heartbeats
0.2 s | *A enters a 6 s garbage collection pause
2.2 s | Peers stop hearing A, timeout fires
2.5 s | Peers elect B as new leader
6.2 s | *A wakes up, still thinks it is leader, tries to write
6.3 s | Storage rejects A's stale term or token
%%

! Example: the unknown payment
! The order service calls the payment service with a 2 s timeout. At 2 s there is no answer. The possibilities: the request never arrived; the payment service crashed before charging; it charged the card and crashed before replying; or the reply is still in flight and will arrive at 2.3 s.
! The order service cannot tell which. If it gives up, the customer may have been charged for an order that does not exist. If it retries naively, the customer may be charged twice.
! The fix: the order service generates an **idempotency key** once per order and sends it with every attempt. It retries with the same key. The payment service stores the key with the result of the first charge, so a repeat returns the stored result instead of charging again. Whatever happened, the customer is charged at most once, and the order service eventually learns the outcome.

## Common mistakes
- **Treating a timeout as "the operation failed".** It means "I do not know".
- **Assuming a node declared dead is dead.** It may come back and act.
- **Guessing timeouts** instead of setting them from measured latency percentiles.
- **Relying on synchronised clocks or bounded delays** for correctness.
- **Testing only the happy path and clean crashes**, never pauses, partitions or lost replies.

## In an interview
Whenever your design has one component detect another's failure (failover, leader election, health checks), say the key sentence: "a timeout cannot distinguish a crashed node from a slow one, so the action after the timeout must be safe if the node is still alive". Then name the mechanism that makes it safe: idempotency keys, terms, fencing tokens.

> Takeaway: in a distributed system any step of a call can fail independently, and a timeout cannot distinguish a dead node from a slow one or a lost message. Design so that every decision made on a timeout stays safe even when the suspected node is alive.

## What a consistency model is
When several clients read and write shared data at the same time, and that data may be copied across several machines, you need rules for what a read is allowed to return. A **consistency model** is exactly that: a contract stating which **histories** (sequences of operations with their start times, end times and results) the system is allowed to produce.

A stronger model forbids more strange outcomes (called **anomalies**), which makes programs easier to write because you can reason as if there were one copy and one user at a time. Stronger models usually cost latency (replicas must coordinate before answering) or availability (some nodes must refuse requests when they cannot coordinate). Weaker models are faster and more available but push the reasoning onto you.

The models form a hierarchy. At the top sits **strict serializability**. Below it there are two branches. One branch is about transactions: serializable, snapshot isolation, repeatable read, read committed. The other is about single objects and replicas: linearizable, sequential, causal, then the session guarantees and plain eventual consistency.

## Two families that people mix up
The words sound alike, but there are two separate questions:
- **Isolation** (transactions over **multiple objects**): what can concurrent transactions see of each other's partial work? Serializable, snapshot isolation and read committed live here (lesson 03.06 covers them).
- **Consistency of replicated data** (operations on **single objects**, in **real time**): when one client's write completes, will every later reader see it, no matter which replica they ask? Linearizable, sequential, causal and eventual live here.

A database can be strong on one axis and weak on the other. A single-node PostgreSQL in serializable mode is serializable and, because there is one copy, also linearizable. Add asynchronous read replicas and reads from those replicas are no longer linearizable, even though transactions on the primary are still serializable.

%%tree The consistency hierarchy. Each model implies the ones below it on its branch; strict serializability sits on top of both.
Strict serializable
  Serializable | transactions, any serial order
    Snapshot isolation
      Read committed
  Linearizable | one object, real-time order
    Sequential | one global order, not real time
      *Causal | causes before effects
        Read-your-writes, monotonic reads
          Eventual
%%

## Linearizability
**Linearizability** (also called atomic consistency or strong consistency) is about operations on a **single object**, such as a key or a register. The rule: each operation appears to take effect atomically at a single point in time somewhere between when it started and when it finished, and that order respects **real time**. If write A finishes before read B starts, B must see A's value or something newer.

The intuition is that the system behaves **as if there were exactly one copy of the data**, even if there are five replicas. Once any client has seen the new value, no client may later see the old one.

Why it matters: linearizability is what you need for anything that relies on "the latest value" being unique. A lock (two clients must not both see "unlocked"), a unique username (two sign-ups must not both see "available"), a leader lease, an account balance check before a withdrawal.

Its cost: it cannot stay available during a network partition. A replica cut off from the others cannot know whether a newer write happened elsewhere, so it must refuse to answer (lesson 06.04). It also costs latency in normal operation, because a write must reach a quorum or the leader must confirm it is still the leader before a read.

%%seq A linearizability violation: a read that starts after a write completed still returns the old value from a lagging replica.
Client A > Replica 1 : write x = 2
Replica 1 -> Client A : ok (write complete)
Client B > Replica 2 : read x (replica lagging)
Replica 2 -> Client B : x = 1, not linearizable
%%

! Example: is this history linearizable?
! Register x starts at 0. Client A runs write(x = 1) from t = 0 to t = 10 ms. Client B runs read(x) from t = 2 to t = 4 ms and gets 1. Client C runs read(x) from t = 6 to t = 8 ms and gets 0.
! B's read overlaps A's write, so B may see 0 or 1; seeing 1 means the write's "instant" was before t = 4 ms. C's read starts at t = 6 ms, after B's read finished with 1. In real-time order, C must therefore see 1 or newer. It saw 0. This history is **not** linearizable, even though every read overlapped the write. Once anybody has seen the new value, nobody may see the old one.

## Serializability
**Serializability** is about **transactions**, which may touch many objects. The rule: the result of running transactions concurrently must equal the result of running them one at a time in **some** serial order. Crucially, that order does not have to match real time. A serializable database is allowed to place a transaction that started later before one that finished earlier, as long as the outcome matches some serial schedule.

So serializability protects you from anomalies **between** transactions, such as **write skew**: two doctors each check "is at least one other doctor on call?", both see yes, both go off call, and now nobody is on call. Under serializability one of the two transactions would have run first, and the second would have seen only one doctor left.

But serializability alone allows **stale reads** in real time. A serializable system could legally answer your read-only transaction from a snapshot taken a minute ago, ordering it "before" the latest writes. Some distributed databases do exactly this for read-only transactions to make them faster.

### Strict serializability
**Strict serializability** combines both: transactions are serializable, and the serial order respects real time. If transaction T1 commits before T2 starts, T2 sees T1's effects. Google Spanner offers this, using tightly bounded clock uncertainty (lesson 06.05) to order transactions across the globe. FoundationDB and CockroachDB (for single-key operations) aim for similar guarantees.

| | Linearizable | Serializable | Strict serializable |
| Unit | One operation on one object | Transactions over many objects | Transactions over many objects |
| Real-time order? | Yes | No | Yes |
| Prevents write skew? | No (no transactions) | Yes | Yes |
| Example violation | Read misses a write that already completed | Two transactions break an invariant together | Either of those |

### Sequential consistency
Between linearizable and causal sits **sequential consistency**: all clients see all operations in one single order, and each client's own operations appear in the order it issued them, but that global order need not match real time. Your write might "take effect" after a read that began later. It is weaker than linearizability and rarely offered by name in databases, but you meet it in CPU memory models.

## Eventual consistency and its stronger cousins
At the weak end, describe consistency from the client's point of view:
- **Strong**: after a write completes, every later read sees it.
- **Weak**: reads may not see it. The period during which they might not is the **inconsistency window**.
- **Eventual**: if no new writes happen, all reads eventually return the last written value. DNS is the classic example: change a record, and resolvers around the world pick it up over minutes to hours as caches expire.

Eventual consistency on its own promises very little: no bound on how long "eventually" is, and no promise about what you see in the meantime. You might see a new value, then an old one, then the new one again. So there are useful in-between guarantees, which can be combined:
- **Read-your-writes**: you always see your own updates. Other people may not yet.
- **Session consistency**: read-your-writes within a session (a login, a connection).
- **Monotonic reads**: once you have seen a value, you never see an older one. Time does not go backwards for you.
- **Monotonic writes**: one client's writes are applied everywhere in the order it made them.
- **Writes follow reads**: if you read a value and then write, your write is ordered after the value you read.
- **Causal consistency**: if one operation could have influenced another (a reply to a comment), everyone sees them in that order. Unrelated operations may be seen in different orders by different people. Causal consistency is the strongest model that can stay available during a partition.

Monotonic reads and session consistency are the most practical for developers. Most "eventually consistent" product bugs are really missing session guarantees: a user posts a comment, refreshes, and it is gone because the read hit a lagging replica.

### How systems provide session guarantees
- **Read-your-writes**: route a user's reads to the primary for a short time after they write, or send the version (log position) of their last write with each read and only read from a replica that has caught up to at least that version.
- **Monotonic reads**: pin each user to one replica (by hashing the user ID), so they never jump from a fresh replica to a staler one. If that replica fails, move them to one that is at least as current.
- **Causal**: carry a dependency marker (a vector clock or version, lesson 06.05) with each write, and do not make a write visible on a replica until the writes it depends on are visible too.

! Example: the comment that disappears and reappears
! A user posts a comment at t = 0. The write goes to the primary. Replica R1 applies it at t = 0.2 s, replica R2 at t = 3 s.
! At t = 1 s the user refreshes. The load balancer picks R1: the comment appears. At t = 1.5 s they refresh again and hit R2: the comment is gone. At t = 4 s it is back. Every step is "eventually consistent", but the user sees time go backwards.
! Fix 1, monotonic reads: pin this user's reads to R1. Fix 2, read-your-writes: the write returns log position 5,041; the client sends it with reads, and R2 (at position 5,030) either waits briefly or forwards the read to the primary. Neither fix needs linearizability across all users.

## Choosing
Pick per operation, not per system:
- **Linearizable or serializable**: money movement, unique usernames, inventory decrements, seat booking, leader election, locks. Anything where two clients acting on stale data would break an invariant.
- **Causal**: comments and replies, chat messages, anything where effects must not be seen before causes.
- **Eventual plus session guarantees**: social feeds, like counts, view counts, recommendations, profile pictures. Strangers seeing a change a second late is fine; the writer not seeing their own change is a bug.

## Common mistakes
- **Saying "strongly consistent"** without saying whether you mean linearizable, serializable or both.
- **Assuming serializable implies fresh reads.** It does not; it allows reading from the past.
- **Assuming the C in ACID is the C in CAP.** ACID's C means "invariants hold", which is the application's job.
- **Paying for linearizability everywhere** when only a few operations need it.

## In an interview
When you choose a database or replication scheme, say which operations need which guarantee. "Username claims need a linearizable compare-and-set; the feed is eventually consistent with read-your-writes for the person who posted." That one sentence shows you understand the hierarchy and its costs.

> Takeaway: linearizability is about single objects in real time: once anyone sees a new value, nobody sees the old one. Serializability is about transactions over many objects in some serial order, not necessarily real-time order. Strict serializability is both. Most applications need strong guarantees for a few operations and session guarantees such as read-your-writes for the rest.

## Why replicate
**Replication** keeps copies of the same data on several machines, called **replicas**. There are three reasons to do it:
- **Durability and availability**: if one machine dies, the data survives and the service keeps running on the others.
- **Read throughput**: more copies can serve more reads in parallel.
- **Latency**: a copy near the user (in their region) answers faster than one across an ocean.

If data never changed, replication would be trivial: copy it once. The hard part is keeping the copies in agreement while data changes, when messages can be delayed and machines can fail at any moment. There are three main designs, distinguished by **who is allowed to accept writes**: one leader, several leaders, or no leader at all.

%%compare The three replication designs, by who accepts writes. Each step to the right gains write availability and pays in conflicts.
[*Single leader]
Writes -> Leader -(log)-> Followers
+ No write conflicts
+ Simple to reason about
- Leader is a bottleneck
- Failover needed on leader loss
[Multi-leader]
Writes -> Leader per region -(async)-> Other leaders
+ Local, fast writes everywhere
+ Regions work when cut off
- Concurrent writes conflict
[Leaderless]
Writes -(to all N)-> Replicas -(W acks)-> Done
+ No failover, any node takes writes
- Conflicts and repair needed
- Tunable but subtle guarantees
%%

## Single-leader replication
One node, the **leader** (or primary), accepts all writes. It records each change in a **replication log** and streams it to the other nodes, the **followers** (replicas, secondaries), which apply the changes in the same order. Reads can go to the leader or to any follower. This is how PostgreSQL, MySQL, MongoDB replica sets and most relational databases work.

### Synchronous or asynchronous
The key choice is when the leader tells the client "your write succeeded".
- **Synchronous** replication waits until followers confirm they have the write. No acknowledged write is lost if the leader dies. But every write pays the round trip to the slowest synchronous follower, and if a synchronous follower is down or slow, writes stall.
- **Asynchronous** replication acknowledges as soon as the leader has written locally. Writes are fast. But if the leader crashes, writes it acknowledged and had not yet shipped are **lost**, and followers serve **stale reads** while they lag (replication lag).
- **Semi-synchronous** is the common middle ground: one follower is synchronous and the rest are asynchronous. Every acknowledged write exists on at least two machines. If the synchronous follower fails, another is promoted to synchronous.

%%timeline Replication lag in an asynchronous setup. The client is told "done" before followers have the write, so a read from a follower can miss it.
[Leader] 0 ms | Write x = 5 committed locally
[Leader] 1 ms | *Ack sent to client
[Follower 2] 3 ms | Still has x = 4, serves a stale read
[Follower 1] 4 ms | Applies x = 5
[Follower 2] 250 ms | Applies x = 5 after a slow network spell
%%

### Replication lag in numbers
In a healthy datacenter, lag is usually under a few milliseconds. Under load, during a large batch update, or across regions, it can grow to seconds or minutes. Lag causes the anomalies from lesson 06.02: a user who writes and then reads from a lagging follower does not see their own change (missing read-your-writes); a user whose successive reads hit different followers sees data go backwards (missing monotonic reads).

### Failover
When the leader dies, a follower must be promoted. Done automatically, that means: detect the failure (with a timeout, which can be wrong, lesson 06.01), choose the most up-to-date follower, reconfigure clients to send writes to it, and stop the old leader from accepting writes if it comes back. Each step has pitfalls. With asynchronous replication, the new leader may lack the last writes of the old one; those writes are usually discarded. A false failure detection can produce **two leaders** (split brain, lesson 06.07). GitHub once had an incident where a promoted MySQL follower was behind, and auto-increment IDs it reissued collided with IDs already stored in Redis, exposing some private data to the wrong users.

## Multi-leader replication
Several nodes accept writes, typically one leader per datacenter. Each leader replicates its changes asynchronously to the others. Writes stay local and fast (a few milliseconds instead of a 100 ms round trip to a distant leader), and each datacenter keeps working if the link to the others is cut.

The price is **write conflicts**: two leaders accept changes to the same record at the same time, and neither knows about the other until replication catches up. You need a resolution rule:
- **Last writer wins (LWW)**: keep the write with the highest timestamp. Simple, but it silently discards the other write, and clock skew (06.05) can make the "last" write actually the earlier one.
- **Merge logic**: application code combines the versions (union the items in two shopping carts).
- **CRDTs** (conflict-free replicated data types): counters, sets and text types designed so that concurrent updates always merge to the same result, whatever the order.

Offline-capable apps (calendars, note-taking apps) are multi-leader systems in disguise: each device is a leader while offline.

## Leaderless replication and quorums
In **Dynamo-style** systems (Cassandra, Riak, ScyllaDB, and Amazon's original Dynamo, the ancestor of DynamoDB), there is no leader. The client, or a coordinator node acting for it, sends each write to all **N** replicas responsible for the key, and considers the write successful once **W** of them acknowledge. A read asks **R** replicas and takes the newest value among their answers (by version number or timestamp).

### Why W + R > N works
The rule: if **W + R > N**, every set of W replicas and every set of R replicas must share at least one replica. This is the pigeonhole principle. There are only N replicas; if the write set and read set together name more than N, at least one replica is in both. That overlapping replica has the latest acknowledged write, and since the reader picks the newest version among its R answers, it returns that write.

Take N = 3, W = 2, R = 2. A write succeeded on some 2 of the 3 replicas. A read asks some 2 of the 3. Two sets of 2 drawn from 3 cannot be disjoint, since that would need 4 distinct replicas. So at least one replica in the read set holds the new value.

%%widget quorum When W + R > N, every read set shares at least one replica with the latest write set.
%%

! Example: tracing a quorum read and write
! N = 3 replicas A, B, C hold `cart:7` at version 3. A client writes version 4 with W = 2. A and B acknowledge; C is slow and has not received it yet. The write is reported as successful.
! Another client reads with R = 2. Whatever pair it reaches: {A, B} both return v4; {A, C} returns v4 and v3, so the client takes v4; {B, C} the same. Every possible read set sees v4.
! With R = 1 instead (W + R = 3, not greater than N), a read that happens to reach only C gets v3: a stale read.
! The client that saw v4 from A and v3 from C can also send v4 back to C, which is **read repair**.

| N | W | R | W + R > N? | Effect |
| 3 | 2 | 2 | Yes | Overlapping quorums; tolerates one node down for reads and writes |
| 3 | 3 | 1 | Yes | Fast reads, but any one node down blocks writes |
| 3 | 1 | 3 | Yes | Fast writes, but reads need every node |
| 3 | 1 | 1 | No | Fastest, eventually consistent; reads can miss writes |
| 5 | 3 | 3 | Yes | Tolerates two nodes down for both |

Lower W means faster, more available writes. Lower R means faster reads. W + R > N is the knob that buys overlap. Latency is set by the slowest replica you wait for: with N = 3 and W = 2, a write waits for the second-fastest replica, which hides one slow node.

### Why quorums are not a full guarantee
Even with W + R > N, edge cases weaken the guarantee:
- **Sloppy quorums**: if some of the key's home replicas are down, some systems write to other nodes temporarily ("hinted handoff") to stay available. Now the W nodes that acknowledged may not overlap the R nodes a reader asks.
- **Concurrent writes**: two writes to the same key at the same time may land in different orders on different replicas. With last-writer-wins, one is silently lost.
- **Partial failure**: a write that reached only 1 of the needed 2 replicas is reported as failed but is not rolled back. A later read may or may not see it.
- **Read and write racing**: a read concurrent with a write may see the new value on one replica and the old on another, and a second read may see the old again.

So quorums by themselves do not guarantee linearizability (06.02). They give a strong "probably fresh" property that is good enough for many workloads.

### How stale replicas catch up
- **Read repair**: when a read notices one replica returned an older version, the client or coordinator writes the newer version back to it. Good for frequently read keys.
- **Anti-entropy**: a background process compares replicas and copies missing data. Comparing every key would be slow, so replicas build **Merkle trees**: hash trees where each leaf is a hash of a range of keys and each parent hashes its children. Two replicas compare root hashes; if they differ, they descend only into the branches that differ, finding a handful of mismatched keys among billions with a few dozen hash comparisons.
- **Hinted handoff**: if a replica is down, another node stores its writes as "hints" and hands them over when it returns.

%%tree A Merkle tree over a replica's key ranges. Two replicas compare top-down and only descend where hashes differ.
Root hash | differs between replicas
  Hash of keys 0 to 499 | matches, skip
  *Hash of keys 500 to 999 | differs, descend
    Keys 500 to 749 | matches, skip
    *Keys 750 to 999 | differs, sync these keys
%%

## State machine replication
The strongest form of replication: every replica starts in the same state and applies the same sequence of **commands** in the same order, so they all end in the same state. Deterministic commands plus identical order equals identical replicas. The hard part is getting every replica to agree on that order, even when nodes fail. That is **consensus** (lesson 06.06), which Raft, Paxos and ZooKeeper's Zab provide. etcd, ZooKeeper, Consul and the metadata layers of most distributed databases work this way.

## Availability arithmetic
Replication raises availability only if failures are independent. The two basic formulas:
- Components **in sequence** (all must work) multiply: two 99.9% components give 0.999 × 0.999 ≈ 99.8%.
- Components **in parallel** (any one is enough) give 1 - (1 - A)^n: two 99.9% replicas give 1 - 0.001² = 99.9999%.

! Example: what replication buys, and what it does not
! A database server is up 99.9% of the time, about 8.8 hours down a year. Two replicas with instant, perfect failover: 99.9999%, about 32 seconds a year.
! Reality is worse. Failover takes 30 s and happens about 4 times a year (2 minutes). Correlated failures (same rack power, same bad deploy, same software bug on both) happen too. A realistic result might be 99.99%, about 53 minutes a year: still a big improvement, but not six nines. Put replicas in different availability zones, stagger deploys, and measure failover time.

## Common mistakes
- **Reading from async followers** for data the user just wrote.
- **Assuming W + R > N gives linearizability.** It narrows the window but does not close it.
- **Last-writer-wins** on data where losing a write matters.
- **Untested failover**, which finds its bugs during a real outage.
- **Replicas in the same rack or zone**, so one failure takes all of them.

## What CAP actually says
A **network partition** is a failure where some nodes cannot communicate with others, even though every node is still running. A cable is cut, a switch fails, a misconfigured firewall drops traffic between two availability zones. Each side can still talk to clients, but not to the other side.

The **CAP theorem** says that during a partition, a replicated data system must choose between two properties:
- **Consistency (C)**: every read returns the most recent write, as if there were one copy.
- **Availability (A)**: every request that reaches a non-failed node gets a non-error response.

It cannot have both. Imagine replicas A and B are cut apart, and a client writes x = 2 to A. Another client now asks B for x. B has two options. It can **answer** with what it has (x = 1), which keeps it available but returns a stale value. Or it can **refuse** (error or wait) until it can confirm with A, which keeps it consistent but unavailable. There is no third option: B cannot know about a write it never received.

The "P" (partition tolerance) is not really a choice. Networks do fail, so any system that spans more than one machine must handle partitions. The real choice is **between C and A, during a partition**. That is why the popular slogan "pick two of three" is misleading: you cannot pick CA for a distributed system, because you do not get to opt out of partitions.

%%seq During a partition a replica that has not seen the latest write must choose: answer with stale data (A) or refuse (C).
Client 1 > Replica A : write x = 2
Replica A -> Client 1 : ok
Replica A > Replica B : replicate x = 2 (lost, partition)
Client 2 > Replica B : read x
Replica B -> Client 2 : choose A: x = 1 (stale) or choose C: error
%%

### CAP's definitions are narrower than you think
CAP is a precise theorem, and its definitions are much stricter than everyday usage:
- **Consistency in CAP means linearizability** (lesson 06.02). It is unrelated to the C in ACID, which means "the database keeps your invariants".
- **Availability means every request to a non-failed node** eventually gets a non-error response. Not "most requests", not "99.99% uptime", and not "fast". A system that answers after two minutes counts as available.
- It models a **single register** (one value), and considers **only network partitions**. Crashes, disk failures, bugs and overload are not part of it.
- It says nothing about **latency**, which is what users experience every day.

So a system can fail to be "CAP-available" and still have excellent real-world availability (a majority side keeps serving and the minority is a tiny share of clients), and a system can be "CAP-consistent" for some operations and not others.

## Why the CP and AP labels mislead
Many databases are casually labelled "CP" or "AP". Look closely and most fit neither label cleanly:
- A typical **single-leader database** with async followers is neither. A client cut off from the leader cannot write (not available), and reads from followers can be stale (not linearizable).
- **ZooKeeper** is usually called CP, but its default reads are served by whichever server you are connected to and may be stale, so they are not linearizable. You need to call `sync` before a read to make it so.
- **Dynamo-style stores** (Cassandra, Riak) are usually called AP. With quorum settings (W + R > N), a minority side of a partition cannot reach a quorum, so it is not fully available, and quorums still do not guarantee linearizability (06.03).
- **One system can offer different guarantees per operation.** DynamoDB offers eventually consistent and strongly consistent reads on the same table. Cassandra lets you pick a consistency level per query. MongoDB's behaviour depends on read and write concern settings.

The more useful habit: talk about **specific consistency models** and **per-operation trade-offs**, not labels for whole systems.

%%matrix What happens to each kind of request on the minority side of a partition, for common setups. Real behaviour depends on configuration, not on a label.
Setup | Writes on minority side | Reads on minority side | Normal-case read latency
Raft or ZooKeeper (linearizable reads) | no, refused | no, refused | partial, leader round trip
ZooKeeper default reads | no, refused | partial, only in read-only mode | yes, local server, maybe stale
Single leader, async followers | no, refused | yes, maybe stale | yes, any replica
Cassandra at QUORUM | no, if no quorum | no, if no quorum | partial, waits for 2 of 3
Cassandra at ONE | yes, accepted | yes, maybe stale | yes, fastest replica
%%

## PACELC: the trade-off you live with every day
CAP only applies **during** partitions, and partitions are rare: perhaps a few minutes a year in a good datacenter. But every replicated system faces a trade-off **all the time**, even when the network is perfect. To make a write consistent, it must reach other replicas, possibly in another region, before it is acknowledged. That costs **latency**. To make a read consistent, you must ask the leader or a quorum, not just the nearest replica. That also costs latency.

**PACELC** extends CAP to capture this: if there is a **P**artition, choose **A**vailability or **C**onsistency; **E**lse (normal operation), choose **L**atency or **C**onsistency.

Systems get a two-part label: PA/EL, PC/EC, PA/EC or PC/EL.

| System | During partition | Normal operation | Label |
| Dynamo, Cassandra, Riak (default settings) | Availability | Latency | PA/EL |
| BigTable, HBase | Consistency | Consistency | PC/EC |
| VoltDB / H-Store, Megastore | Consistency | Consistency | PC/EC |
| MongoDB (classic defaults) | Availability | Consistency | PA/EC |
| PNUTS (Yahoo) | Consistency | Latency | PC/EL |
| Spanner | Consistency | Consistency | PC/EC |

%%tree PACELC as a decision tree. The first question rarely applies; the second applies to every request.
Is the network partitioned?
  Yes, rare | choose one
    Availability | answer, maybe stale
    Consistency | refuse or wait
  *No, almost always | choose one
    Latency | answer from nearest replica
    Consistency | wait for leader or quorum
%%

### Why PACELC is more useful than CAP
- It explains why systems like Cassandra **weaken consistency when nothing is broken**. They are not preparing for partitions; they are cutting latency on every request.
- It forces you to state the **normal-case cost** of your choice, which is what users feel every day. A design that is "CP" may add 100 ms to every write because of a cross-region round trip.
- It makes the "else" choice **tunable per operation**, matching how real systems work.

### Where the latency comes from
The trade-off comes directly from how replication works:
- **Send updates to all replicas at once** (leaderless): different replicas might receive concurrent updates in different orders. To agree on an order you need a coordination round, which costs latency. Skipping it costs consistency.
- **Send updates through a leader**: the leader orders updates. But then either the leader waits for replicas before acknowledging (latency) or it does not (a crash loses writes, and reads from replicas can be stale).
- **Read from a replica**: either check with the leader that you are up to date (latency) or accept that you might be behind (consistency).
- **Quorums**: waiting for more replicas reduces staleness and adds the latency of the slowest one you wait for.

! Example: the price of EC across regions
! Replicas live in Virginia, Oregon and Frankfurt. Round trips: Virginia to Oregon about 70 ms, Virginia to Frankfurt about 90 ms.
! EC (consensus with a majority): a write from Virginia must reach one other region before it is acknowledged, so it takes at least 70 ms plus processing, maybe 80 ms in total. A linearizable read must confirm with a majority too.
! EL (acknowledge locally, replicate asynchronously): the write takes about 2 ms. Other regions see it 70 to 90 ms later, and a crash of the Virginia node in that window loses it.
! For a "like" button, 2 ms with a tiny risk of losing a like is the right trade. For a bank transfer, 80 ms is cheap insurance. Same infrastructure, different choice per operation.

%%bars Write latency for one write originating in Virginia under different "else" choices. Consistency costs at least one cross-region round trip.
Local ack, async replication (EL) | 2 | ~2 ms
Quorum in one region (3 zones) | 5 | ~5 ms
*Majority across 3 regions (EC) | 80 | ~80 ms
Wait for all 3 regions | 100 | ~100 ms
%%

## How to use this in interviews
Do not say "we pick AP" for a whole system. Say it per operation, and cover both halves:
- "Likes and view counts tolerate staleness, so they are acknowledged locally and replicated asynchronously, and reads go to the nearest replica (PA/EL)."
- "Payments and username claims need one strongly consistent source, so they go through the leader with synchronous replication, accept the extra latency, and fail rather than diverge if the leader is unreachable (PC/EC)."

Good questions to ask: "If two regions lose contact, should users in the smaller one still be able to write?" and "How many milliseconds of write latency is acceptable?" The answers place each operation in the PACELC grid.

! Example: global shopping cart
! A store runs in two regions. During a partition between them, the cart stays writable in both (PA): a user adding items in either region succeeds, and carts are merged afterwards by taking the union of items (a removed item may reappear, which the business accepts).
! In normal operation, cart writes are acknowledged locally and replicated asynchronously (EL), so adding to the cart takes 20 ms instead of 120 ms.
! Checkout, by contrast, goes to the region that owns the order and uses a strongly consistent inventory decrement (PC/EC). If that region is unreachable, checkout shows "try again shortly" rather than risk selling the last item twice.

## Why physical time is not enough
On one machine, ordering events is easy: read the clock, and the event with the smaller timestamp happened first. Across machines that breaks. Each machine has its own quartz clock, and quartz clocks **drift**, typically by 10 to 100 parts per million, which is up to about 8 seconds a day. NTP (lesson 04.11) pulls them back towards the true time, but only to within a few milliseconds on a good network, and much worse after a network hiccup. Clocks can even jump **backwards** when NTP corrects them.

So if machine A logs an event at 10:00:00.005 and machine B logs one at 10:00:00.003, you **cannot** conclude that B's happened first. A's clock might be 10 ms fast. Systems that order writes by wall-clock time (last-writer-wins) silently lose data this way: a write that genuinely came later, from a machine with a slow clock, is discarded as "older".

! Example: last-writer-wins loses a write
! Node A's clock is 15 ms fast; node B's is accurate. At true time 12:00:00.000 a client writes x = "red" via A, stamped 12:00:00.015. At true time 12:00:00.010 another client writes x = "blue" via B, stamped 12:00:00.010.
! "blue" really happened 10 ms later, but its timestamp is smaller. When replicas compare timestamps, "red" wins everywhere and "blue" vanishes with no error. Any clock skew larger than the gap between two writes can reorder them.

The way out is to stop asking "what time was it?" and instead ask "**could this event have influenced that one?**" That idea, causality, is the foundation of logical clocks.

## Happens-before
Event a **happened before** event b, written a → b, if one of these holds:
- a and b are on the same process, and a came first in that process's order.
- a is the sending of a message and b is the receipt of that same message.
- There is some event c with a → c and c → b (transitivity: a chain of the first two rules).

If neither a → b nor b → a, the events are **concurrent**, written a ∥ b. Concurrent does not mean "at the same instant". It means neither could have influenced the other: no chain of messages connects them. The system genuinely cannot say which came first, and for many purposes it does not matter.

Happens-before is a **partial order**: some pairs of events are ordered, others are not. It captures exactly the causal structure of the system and nothing more.

%%seq Happens-before: a send happens before its receipt, so a1 causally precedes b1. Node C's event is connected to neither, so it is concurrent with both.
Node A > Node A : event a1
Node A > Node B : message m
Node B > Node B : event b1 (after receiving m)
Node C > Node C : event c1 (concurrent with a1 and b1)
%%

## Lamport clocks
A **Lamport clock** is a single integer counter per process, designed so that causality always shows up in the numbers. The rules:
1. Before each local event (including a send), increment the counter.
2. Attach the counter value to every message you send.
3. When you receive a message carrying value m, set your counter to max(your counter, m) + 1, and use that as the receive event's timestamp.

This guarantees the **clock condition**: if a → b, then L(a) < L(b). Causes always get smaller numbers than their effects.

To get a **total order** (every pair of events ordered), break ties by process ID: compare (L, process ID) pairs. This total order is consistent with causality, which makes it useful. For example, if every replica applies commands in Lamport-timestamp order, they all apply them in the same order, which is the core of a replicated state machine. The same idea gives a mutual exclusion algorithm without a central coordinator: requests are granted in timestamp order.

%%seq Lamport clocks: on receipt, take max(local, received) + 1, so a message's receipt always gets a bigger number than its send.
Node A > Node A : local event, L = 1
Node A > Node B : send with L = 2
Node B > Node B : L was 0, now max(0, 2) + 1 = 3
Node B > Node C : send with L = 4
Node C > Node C : L was 7, now max(7, 4) + 1 = 8
%%

### What Lamport clocks cannot tell you
The clock condition only works one way. L(a) < L(b) does **not** imply a → b. Two concurrent events still get different numbers, and from the numbers alone you cannot tell whether the smaller one caused the larger one or whether they were completely independent.

In the trace above, Node C's counter was already 7 from its own unrelated activity. If C had an unrelated event at L = 5, and A an event at L = 6, the numbers say 5 < 6 but there is no causal link. Lamport clocks lose this information because they squash all of a process's knowledge into one number.

There is also an anomaly with events outside the system. If a user does action A in one app, then phones a friend who does action B, B really happened after A, but no message inside the system connects them, so the system may order B first. Physical clocks with a **known, bounded** error can fix this: Google Spanner's TrueTime exposes clock uncertainty as an interval (typically a few milliseconds) and makes a transaction wait out that uncertainty before committing, so real-time order is respected even between unconnected clients.

## Vector clocks
A **vector clock** keeps one counter **per process**, so a process tracks how much it knows of every other process's history. For three processes A, B, C, a vector looks like [A:2, B:0, C:1].
1. On a local event or a send, increment **your own** entry.
2. Attach the whole vector to every message.
3. On receipt, take the **element-wise maximum** of your vector and the message's vector, then increment your own entry.

To compare two vectors V and W:
- If every entry of V is less than or equal to the matching entry of W, and they are not equal, then V < W: the event with V **happened before** the event with W.
- If V < W fails and W < V fails, the events are **concurrent**. For example [A:2, B:2, C:0] and [A:0, B:0, C:1]: the first has more of A and B, the second more of C.

This is exactly the converse that Lamport clocks lack: **V(a) < V(b) if and only if a → b**. So vector clocks can **detect concurrency**. That is their whole purpose.

%%timeline Version vectors (vector clocks for one data item) across two replicas of a cart. After a partition, neither vector dominates the other, so the store knows the edits were concurrent.
[Replica X] t1 | Cart created, [X:1, Y:0]
[Replica Y] t2 | Receives a copy (no edit), [X:1, Y:0]
[Replica X] t3 | Partition. Add book, [X:2, Y:0]
[Replica Y] t4 | Add pen, [X:1, Y:1]
[Replica X] t5 | *Sync: [X:2, Y:0] vs [X:1, Y:1], neither dominates, conflict
[Replica X] t6 | App merges to book + pen, [X:3, Y:1]
%%

! Example: comparing vectors step by step
! Three events have vectors e1 = [A:1, B:0, C:0], e2 = [A:2, B:1, C:0] and e3 = [A:1, B:0, C:1].
! e1 vs e2: 1 ≤ 2, 0 ≤ 1, 0 ≤ 0, not equal, so e1 → e2.
! e1 vs e3: 1 ≤ 1, 0 ≤ 0, 0 ≤ 1, not equal, so e1 → e3.
! e2 vs e3: A is 2 > 1 (so e2 is not before e3), but C is 0 < 1 (so e3 is not before e2). They are concurrent.
! Lamport clocks on the same history might give e1 = 1, e2 = 3, e3 = 2. Reading those numbers you would conclude e3 came before e2, and you could not tell that e2 and e3 were independent edits that might conflict.

### The cost of vector clocks
A vector has one entry per process, so it grows with the number of writers. With 5 replicas that is trivial. With millions of client devices, it is not. Real systems use variations:
- **Per-replica entries** rather than per-client, so the vector is as long as the replica count.
- **Version vectors**: the same idea applied to replicas of a data item rather than to every event.
- **Dotted version vectors** (used by Riak) fix a subtle problem where several clients writing through the same replica produce false conflicts or lost updates.
- **Pruning**: drop the oldest entries when a vector grows past a limit, accepting occasional false conflicts.

## Hybrid logical clocks
A **hybrid logical clock (HLC)** combines a physical timestamp with a small logical counter. It stays close to wall-clock time (so timestamps are meaningful to humans and usable for "read as of 10:00"), but it always respects causality like a Lamport clock: a receipt never gets a timestamp below its send, even if the receiver's physical clock is behind. CockroachDB and YugabyteDB use HLCs to order transactions without special clock hardware.

Clock | Size | Respects causality | Detects concurrency | Close to real time
Wall clock | one timestamp | no, skew reorders | no | yes
Lamport clock | one integer | yes | no | no
Vector clock | one integer per node | yes | yes | no
Hybrid logical clock | timestamp plus counter | yes | no | yes
TrueTime interval | two timestamps | yes, with commit wait | no | yes, bounded error

## Where these appear
- **Conflict detection** in multi-leader and leaderless stores. Amazon's original Dynamo attached vector clocks to shopping cart versions, so two concurrent updates were both kept and merged by the application instead of one silently overwriting the other. Riak does the same with dotted version vectors.
- **Causal broadcast**: deliver messages so that causes always arrive before effects. A replica holds back a message until it has delivered everything the message's vector says came before it. Compare with FIFO broadcast (per-sender order) and total order broadcast (one global order, which needs consensus).
- **Last-writer-wins** with Lamport timestamps or HLCs gives a cheap total order, but silently discards one of two concurrent writes. Fine for a "last seen" timestamp, wrong for a shopping cart.
- **Distributed debugging and tracing**: ordering log lines from many services by causality rather than by skewed timestamps.

| Size | One integer | One integer per node |
| If a → b | L(a) < L(b) | V(a) < V(b) |
| If L(a) < L(b) or V(a) < V(b) | Nothing certain | a → b |

## Common mistakes
- **Ordering writes by wall-clock time** across machines and losing updates to skew.
- **Treating a Lamport order as causal order.** It is consistent with causality, but it invents an order between concurrent events.
- **Using vector clocks keyed by client** and letting them grow without bound.
- **Assuming concurrent means simultaneous.** It means "not causally connected", which can be seconds apart.

If your design merges replicas or accepts writes in several places, say how you detect conflicts. If last-writer-wins is acceptable, say so explicitly and say what is lost.

## The problem consensus solves
**Consensus** means several servers agreeing on a value, such that once a value is decided, the decision never changes, even if some servers crash and restart. It sounds modest. It turns out to be the foundation for almost every strongly consistent distributed system.

The main use is a **replicated state machine**. Each server keeps a **log** of commands (`set x = 5`, `delete y`) and a **state machine** that applies them (for example a key-value table). If every server applies the same commands in the same order, every server ends in the same state, because the commands are deterministic. Consensus is how servers agree on that order: for each position (index) in the log, which command goes there.

With that, a cluster can keep a single consistent view of things that must never diverge: who the leader is, what the configuration is, which writes are committed, who holds a lock. It does so while tolerating failures of a minority of servers.

A correct consensus algorithm must guarantee:
- **Safety**: servers never decide different values for the same log index, and a decided value is never undone. This must hold no matter how messages are delayed or reordered.
- **Liveness**: the cluster eventually makes progress, as long as a majority of servers is running and can talk to each other with reasonable delays.

Recall from lesson 06.01 that in a fully asynchronous system no algorithm can guarantee both. Real algorithms keep safety unconditionally and rely on timing (timeouts) only for liveness. If the network misbehaves, they stall; they never give wrong answers.

**Paxos** solved consensus first and is famously hard to understand and implement. **Raft** was designed to give equivalent fault tolerance and performance while being easier to understand, by splitting the problem into three parts: leader election, log replication and safety.

## Raft's building blocks
### Terms
Raft divides time into numbered **terms**: 1, 2, 3 and so on. Each term begins with an election, and has **at most one leader**. If an election fails (nobody wins), the term ends with no leader and a new term starts. Terms act as a logical clock: every message carries the sender's term, and a server that sees a higher term than its own immediately updates its term and, if it was a leader or candidate, steps down to follower. Messages with a stale (lower) term are rejected.

### Server roles
Every server is in exactly one of three states:
- **Follower**: passive. Responds to requests from leaders and candidates. Every server starts here.
- **Candidate**: trying to become leader.
- **Leader**: handles all client requests and replicates log entries to followers.

%%state A Raft server's roles. Timeouts start elections; a majority of votes makes a leader; any higher term sends a server back to follower.
[*] -> Follower
Follower -> Candidate : election timeout, no heartbeat
Candidate -> Candidate : split vote, timeout, new term
Candidate -> *Leader : votes from a majority
Candidate -> Follower : sees current leader or higher term
Leader -> Follower : sees higher term
%%

## Leader election step by step
1. The leader sends regular **heartbeats** (empty AppendEntries messages), for example every 50 ms.
2. Each follower has an **election timeout**, randomised for each server, for example between 150 and 300 ms. If it hears nothing from a leader in that time, it assumes the leader has failed.
3. It becomes a **candidate**: increments its term, votes for itself, and sends **RequestVote** to every other server.
4. Each server grants **at most one vote per term**, first come first served, and only to a candidate whose log is **at least as up to date** as its own. Raft defines up to date by the last log entry: a later term wins; with equal last terms, the longer log wins.
5. A candidate that collects votes from a **majority** (including itself) becomes leader and immediately sends heartbeats to assert authority.
6. If two candidates split the vote and nobody gets a majority, both time out (at different random moments) and try again in a new term. The randomisation makes repeated split votes rare: usually one server times out well before the others and wins before anyone else starts.

The "up to date" rule in step 4 is what makes elections safe for data. A committed entry is stored on a majority. A candidate needs votes from a majority. The two majorities overlap in at least one server, which holds the entry and will refuse to vote for a candidate missing it. So **a new leader always has every committed entry**.

%%timeline A leader crash and re-election in a 5-node Raft cluster with 150 to 300 ms election timeouts.
0 ms | Leader A (term 4) sends its last heartbeat, then crashes
150 ms | Followers start missing heartbeats
212 ms | *D's random timeout fires first: term 5, votes for itself
214 ms | C and E grant votes; D now has 3 of 5, a majority
215 ms | D becomes leader for term 5, sends heartbeats
240 ms | B's timeout would have fired, but it heard D first
%%

## Log replication step by step
1. A client sends a command to the leader. (A follower that receives one redirects the client to the leader.)
2. The leader appends the command to its own log as a new entry tagged with the current term and the next index.
3. It sends **AppendEntries** to every follower in parallel. Each call includes the **index and term of the entry just before** the new ones.
4. A follower checks that its own log has an entry at that previous index with that term. If yes, it appends the new entries and replies success. If no, it rejects, and the leader steps back one entry (or more, with optimisations) and retries, until it finds the point where the logs agree. Then the follower deletes any conflicting entries after that point and takes the leader's.
5. Once the entry is stored on a **majority** of servers (the leader counts itself), it is **committed**. The leader applies it to its state machine and replies to the client.
6. The leader includes its latest commit index in later AppendEntries (and heartbeats), so followers learn which entries are committed and apply them too.

The consistency check in step 4 enforces the **Log Matching Property**: if two logs contain an entry with the same index and term, the logs are identical in all entries up to that index. Inductively, every successful AppendEntries proves the follower's log matches the leader's up to that point.

%%seq A Raft write in a 3-node cluster: the leader commits once a majority (itself plus one follower) has the entry.
Client > Leader : SET x = 5
Leader > Follower 1 : AppendEntries (term 3, index 7, prev 6/3)
Leader > Follower 2 : AppendEntries (term 3, index 7, prev 6/3)
Follower 1 -> Leader : ok, now 2 of 3 have it
Leader > Leader : commit index 7, apply x = 5
Leader -> Client : ok
Follower 2 -> Leader : ok (late, already committed)
%%

### The subtle commit rule
A leader only counts replicas towards commitment for entries from its **own current term**. Entries from earlier terms become committed indirectly, when a later entry from the current term is committed after them. Why? Because an old entry that is on a majority could still, in a specific sequence of crashes, be overwritten by a leader from a different term that never saw it. Committing a current-term entry on a majority rules that out, because any future leader must then have that entry and everything before it. Practical systems have a new leader append a no-op entry at the start of its term to commit earlier entries promptly.

## What Raft guarantees
- **Election Safety**: at most one leader per term.
- **Leader Append-Only**: a leader never overwrites or deletes its own entries; it only appends.
- **Log Matching**: same index and term means identical logs up to there.
- **Leader Completeness**: a committed entry appears in the log of every later leader.
- **State Machine Safety**: no two servers ever apply different commands at the same index.

Raft needs one timing condition for liveness: **broadcastTime ≪ electionTimeout ≪ MTBF**. A heartbeat round trip (perhaps 0.5 to 20 ms) must be much shorter than the election timeout (150 to 300 ms locally, more across regions), which must be much shorter than the average time between server failures (months). Break the first inequality and the cluster holds elections constantly.

Two practical extensions: **membership changes** use **joint consensus**, where during the switch decisions need majorities of both the old and new configurations, so there is never a moment when two disjoint majorities could each elect a leader. And logs are compacted with **snapshots** that record the state machine plus the last included index and term, so the log does not grow forever.

## Why a majority
The whole algorithm rests on one fact: **any two majorities of the same cluster overlap in at least one server**. In a 5-node cluster, any 3 and any other 3 must share at least one node, because 3 + 3 = 6 > 5. From that:
- Two leaders cannot both win in the same term: each needs a majority of votes, and the overlapping server votes only once per term.
- A committed entry is on a majority, and any future leader needs votes from a majority, which includes at least one server holding that entry. With the up-to-date voting rule, committed data survives every leader change.

A minority cannot do either. Two servers out of five could disagree with the other three forever; if they could commit on their own, the two sides could commit different values at the same index.

| Cluster size | Majority | Failures tolerated |
| 1 | 1 | 0 |
| 3 | 2 | 1 |
| 4 | 3 | 1 |
| 5 | 3 | 2 |
| 7 | 4 | 3 |

A cluster of 2f + 1 servers tolerates f failures. A fourth server does not help (4 servers still tolerate only 1, and you now need 3 to agree instead of 2), which is why clusters have odd sizes. Larger clusters tolerate more failures but every write waits for more acknowledgements, so 3 or 5 is typical; 7 is rare.

%%matrix What a 5-node Raft cluster can do as servers fail. It stops rather than risk inconsistent answers.
Servers up | Elect a leader | Commit writes | Linearizable reads | Margin left
5 of 5 | yes | yes | yes | 2 more failures
4 of 5 | yes | yes | yes | 1 more failure
3 of 5 | yes | yes | yes | none
2 of 5 | no | no | no | stalled until one returns
%%

## When too many fail
A 5-server cluster keeps working with 2 failures; with more, it stops making progress but never returns an incorrect result.

! Example: 2 of 5 down
! Nodes A to E, A is leader in term 7. A rack loss takes out A and B. C, D and E stop receiving heartbeats. D's timeout fires first; it starts term 8 and gets votes from C, E and itself: 3 of 5, a majority.
! D becomes leader and keeps committing writes, each needing 3 acknowledgements (D plus C and E). Every write now needs **all** remaining servers, so one slow server slows every write, and there is no margin left.
! Now C also fails. D and E are 2 of 5. D can append entries but can never reach 3 acknowledgements, so nothing commits. Clients time out. Linearizable reads also stop, because D cannot confirm it is still the leader. E's election attempts fail too. The moment A, B or C returns, a majority exists again and the cluster resumes, with no committed data lost.

! Example: a partition with the old leader on the minority side
! In a 5-node cluster, leader A and node B are partitioned from C, D and E. A still thinks it is leader (term 7) and accepts a client write, appending it at index 50. It sends AppendEntries, but only B answers: 2 of 5, so index 50 is never committed and A never acknowledges the client.
! On the majority side, C wins term 8 and commits different entries at index 50 and beyond. When the partition heals, A sees term 8, steps down, and C's AppendEntries overwrites A's uncommitted entry 50. The client that wrote via A got a timeout, not a success, so no acknowledged write was lost.

## Where it is used
etcd (the data store behind Kubernetes), Consul, CockroachDB, TiKV, YugabyteDB, Kafka's KRaft controller and many others use Raft. ZooKeeper uses a similar protocol called ZAB; Google's Chubby and Spanner use Paxos variants. Implementing Raft from scratch is a classic exercise in distributed systems courses, and is the best way to learn its corner cases.

## Common mistakes
- **Even-sized clusters**, which add cost without adding fault tolerance.
- **Spreading 3 nodes across 2 zones**, so losing the zone with 2 nodes stops the cluster. Use 3 zones.
- **Election timeouts close to network latency**, causing constant elections across regions.
- **Reading from followers** and expecting linearizable results.

## Why have a leader
**Leader election** is the process by which a group of identical processes picks one of them to be in charge of something: accepting writes for a shard, running scheduled jobs, assigning work, coordinating a migration. The others stand by, ready to take over.

Having one process in charge has real benefits:
- **One place to reason about.** Concurrency, logs and metrics all live in one process. Debugging "who did this?" has one answer.
- **Efficiency.** The leader can tell the others what happened, instead of the group reaching agreement on every single change. One consensus round to elect a leader can cover millions of decisions.
- **Easier consistency.** One node sees and orders every change, so ordering conflicts cannot arise between peers.
- **Simpler code.** Most programmers find "if I am the leader, do X" much easier to write correctly than a peer-to-peer protocol.

And real drawbacks:
- **A single point of failure.** When the leader dies, the work stops until a new one is chosen.
- **A single point of scaling.** All the work goes through one machine.
- **A single point of trust.** A buggy leader can do a lot of damage quickly, and followers will faithfully copy its mistakes.
- **Harder partial deployments.** You cannot easily test new leader code on 1% of traffic when there is only one leader.

The usual fix for the scaling problem is **sharding**: split the data into many shards and give each shard its own leader, so leadership is spread across the fleet. DynamoDB, Amazon EBS and EFS all work this way, as do Kafka (a leader per partition) and CockroachDB (a leader per range). It is also worth asking whether you need a leader at all. Workflows, idempotent APIs and optimistic locking (conditional writes) often solve the coordination problem without one.

## How elections usually work: leases
The most common practical approach is a **lease** stored in a strongly consistent store:
1. There is one record, say `leader/scheduler`, with fields: holder, lease duration, version.
2. A candidate tries a **conditional write**: "set holder = me, if the record is empty or its lease has expired". The store's strong consistency ensures only one candidate's write succeeds.
3. The winner is leader. It **heartbeats**: renews the lease well before it expires (for example every 3 s for a 10 s lease).
4. If the leader stops renewing (crash, partition, pause), the lease expires and another candidate's conditional write succeeds.

%%seq Leader election by lease: whoever holds the lease is leader and must renew it before it expires; when renewals stop, another node takes over.
Node A > Lock service : acquire lease, 10 s
Lock service -> Node A : granted, epoch 41
Node A > Lock service : renew at 3 s, 6 s, 9 s
Node A > Node A : crashes, renewals stop
Node B > Lock service : acquire (lease expired)
Lock service -> Node B : granted, epoch 42
%%

### Use proven tools
Writing your own election code is a classic source of bugs. Use something tested: the DynamoDB lock client, ZooKeeper's leader election recipe, etcd's election API, Consul sessions, or Kubernetes' `Lease` objects (which is how Kubernetes controllers pick an active instance). Consensus systems such as Raft (06.06) elect leaders internally using terms. ZooKeeper offers a recipe using **ephemeral sequential nodes**: each candidate creates a node like `/election/n_0000000017`, which disappears automatically if its session dies, and the one with the lowest number is leader (lesson 06.12).

### Two implementation details that matter
- **Measure the lease with local elapsed time** (a monotonic timer that only counts forward), not by comparing wall-clock timestamps across machines. Wall clocks can jump (06.05). The lease holder should consider its lease over **earlier** than the server does, by a safety margin, to allow for clock drift and message delay.
- **Do not heartbeat from a separate background thread** that is unaware of the real work. If the work thread hangs, the heartbeat thread keeps a useless leader in office forever. If the heartbeat thread dies, the lease lapses while the work thread carries on as if nothing happened. Tie renewal to the health of the actual work.

## Two leaders at once
Here is the uncomfortable truth: **a distributed system cannot guarantee exactly one leader at every moment**. During failures there may briefly be zero leaders (between the old one dying and the new one being chosen) or two (the old one does not know it has been replaced). The election itself can be correct, with only one node granted the lease, and still two nodes behave as leader. How that happens:
- **A long pause.** The old leader is stopped by a garbage collection pause, a VM migration, a swap storm or a slow disk for longer than its lease. Its lease expires, a new leader is elected, and the old one resumes, still believing it is in charge. From its point of view no time passed.
- **A partition.** The old leader is cut off from the lock store but can still reach the database or file storage it writes to. It cannot renew, so its lease lapses, but its writes still land.
- **Check-then-act gaps.** Checking "do I still hold the lease?" before each write does not fix it on its own: the pause can happen **between** the check and the write.

%%timeline Two leaders at once: the election was correct, but the old leader's pause makes its view of the world stale.
0 s | A holds lease (epoch 41), renews every 3 s
4 s | A checks: lease valid until 13 s, starts a write
4.1 s | *A enters a 15 s garbage collection pause
13 s | A's lease expires on the lock service
13.5 s | B acquires the lease, epoch 42, starts writing
19.1 s | *A wakes, finishes its write as epoch 41
%%

This is the same situation as lesson 06.01's "crashed or slow?" problem. The cluster decided A was gone because it was silent. A was merely slow, and now it acts on stale beliefs.

## What stops them corrupting data
Since you cannot prevent two nodes **believing** they lead, the protection must sit at the **resource being changed** (the database, the file, the queue), which sees every write and can reject the stale ones.

### Fencing tokens and epochs
Every time leadership is granted, the lock service hands out a number that **only goes up**: a term (Raft), an epoch, ZooKeeper's zxid, an etcd revision, a database sequence. The leader sends this number with every write. The storage remembers the highest number it has seen and **rejects** writes with lower numbers.

When the old leader wakes up and writes with token 41, storage has already seen 42 from the new leader and refuses. The old leader gets an error, realises it has been replaced, and steps down. Lessons 06.08 and 06.09 cover fencing tokens in detail.

%%seq Fencing with epochs: the storage remembers the highest epoch it has seen and rejects the paused old leader's write.
New leader B > Storage : write job 991, epoch 42
Storage -> New leader B : ok, highest epoch now 42
Old leader A > Storage : write job 991, epoch 41
Storage -> Old leader A : rejected, 41 < 42
Old leader A > Old leader A : step down
%%

### Conditional writes
If the resource is a database, it can do the check itself: store the current leader's epoch in a row and make every write conditional on it. `UPDATE jobs SET status = 'dispatched' WHERE id = 991 AND leader_epoch <= 42` combined with bumping the epoch on takeover, or a DynamoDB `ConditionExpression`. The database's atomic conditional update is the fence.

### Other defences
- **Idempotent work**: if the leader's actions are idempotent and recorded durably before they are announced, two leaders mostly waste effort rather than corrupt state. Sending the same "dispatch job 991" twice is harmless if the worker de-duplicates on job ID.
- **Check the lease often**, especially just before side effects, and stop work immediately when renewal fails. This narrows the window but does not close it.
- **Keep an audit trail** of who led when, with epochs, so you can reconstruct incidents.
- **Model the algorithm.** Teams at AWS and elsewhere use formal specification languages such as TLA+ to check election and failover logic for these edge cases before writing code.

%%compare Protecting data from a stale leader. Checking your own lease narrows the window; only a check at the resource closes it.
[Leader checks its own lease]
Check lease -(pause here)-> Write -> Stale write lands
- Pause between check and write
- Partition hides lease loss
+ Simple, no storage changes
[*Resource checks the epoch]
Write with epoch -> Storage compares -> Stale write rejected
+ Works whatever the leader believes
+ Old leader learns and steps down
- Storage must support the check
%%

! Example: a scheduler leader
! A cron-like scheduler runs as three instances. The leader holds a lease in DynamoDB: 10 s, renewed every 3 s. Each takeover increments an epoch counter.
! Leader A stalls in a 15 s garbage collection pause. Its lease expires at 10 s. B takes over with epoch 42 and starts dispatching jobs.
! A wakes up and tries to mark job 991 as dispatched with epoch 41. The jobs table write uses a condition expression requiring the item's epoch to be at most the writer's epoch, and B already wrote epoch 42 on that item. So A's write fails with a conditional check error. A treats this error as "I am no longer leader", stops its loops and rejoins as a candidate. No job is dispatched twice.

! Example: sizing the lease
! You want failover within about 15 s. Lease 10 s, renew every 3 s: a leader survives up to two lost renewals (a brief network blip) without losing leadership.
! On a crash, the worst case is: crash just after a renewal, lease expires 10 s later, candidates poll every 2 s, so a new leader is in place within about 12 s.
! Shorter leases give faster failover but more false takeovers during garbage collection pauses or network blips. If pauses up to 5 s are common, a 3 s lease would cause frequent leader changes, each with a burst of rejected stale writes.

## Common mistakes
- **Believing the election guarantees one leader.** It guarantees one lease holder; it cannot stop an old holder acting.
- **No fence at the resource.** The single most common bug.
- **Comparing wall clocks** across machines to decide whether a lease expired.
- **Heartbeat threads that outlive the work**, or vice versa.
- **Leases shorter than common pause times.**

## In an interview
When your design has a leader (a scheduler, a shard owner, a primary), say how it is elected (lease in etcd, ZooKeeper or DynamoDB, or Raft internally), how fast failover is, and then volunteer the split-brain problem and the fix: "every write carries the leader's epoch, and the storage rejects older epochs". Interviewers often ask "what if the old leader comes back?", and this is the answer.

> Takeaway: leader election usually uses a lease with heartbeats in a strongly consistent store, but no scheme can stop an old, paused or partitioned leader from believing it still leads. Protect the data at the resource, with fencing tokens, epochs or conditional writes that reject the stale leader.

## What a distributed lock is for
A **lock** guarantees **mutual exclusion**: only one holder at a time may do a particular thing. On one machine a mutex does this cheaply and reliably, because the operating system sees every thread and knows instantly when one dies. A **distributed lock** extends the idea across many machines: only one process anywhere in the fleet may process job 77, modify file X, run tonight's billing, or apply a schema migration.

Before reaching for one, ask the question that decides everything else: **why do you want the lock?**
- **Efficiency**: avoid doing the same work twice. If the lock occasionally fails and two processes run, you send a duplicate email, recompute a report or waste some CPU. Annoying, but not dangerous.
- **Correctness**: prevent concurrent changes that would corrupt data. If the lock fails, you lose an update, double-charge a customer or corrupt a file. Dangerous.

For efficiency, a simple lock that is right 99.99% of the time is perfect. For correctness, "usually right" is not good enough, and as this lesson shows, **no lock alone** can be fully right; the protected resource must take part.

%%compare Two reasons to lock, with very different requirements. Decide which one you have before choosing a mechanism.
[Efficiency lock]
Two holders -> Duplicate work -> Mild cost
+ A single Redis key is enough
+ Simple and fast
- Rare double runs, accept them
[*Correctness lock]
Two holders -> Corrupted data -> Real damage
+ Consensus-backed lock service
+ Fencing tokens checked by the resource
- More moving parts and latency
%%

## Why locks need leases
Imagine a lock with no expiry. A client takes it and then crashes, hangs forever on a bug, or gets cut off by a network partition. The lock service has no way to know the client will never release it, so the lock is held forever and every other client waits forever. A single crashed machine deadlocks the whole system.

So distributed locks are **leases**: a lock granted for a limited time. The holder must either finish and release, or **renew** (extend) the lease before it expires. If it does neither, the lock service assumes it has failed and frees the lock for someone else. A lease is the distributed answer to "how do I know the holder is dead?": you do not know, so you decide in advance how long you are willing to wait.

Every serious lock service works this way:
- **Chubby**, Google's lock service built on Paxos and used by GFS and Bigtable to elect masters, provides coarse-grained, advisory locks held for hours or days, with sessions kept alive by periodic keep-alive messages. It prioritises availability and reliability over raw performance.
- **ZooKeeper** ties locks to **sessions**. A lock is an ephemeral node that disappears if the session's heartbeats stop for longer than the session timeout.
- **etcd** has explicit **leases** with a TTL; keys attached to a lease are deleted when it expires.
- **Redis** locks are keys with a TTL (`SET lock:job77 <token> NX PX 30000`).
- **Databases** can act as lock services: a row with an owner and an expiry time, taken with a conditional update.

### Choosing the lease length
The lease length is a trade-off:
- **Too short**, and healthy holders lose the lock during normal hiccups (a 2 second garbage collection pause, a slow disk write), causing needless handovers and more double-holder windows.
- **Too long**, and when a holder really crashes, everyone waits a long time before the lock is freed.

A common pattern: a lease several times longer than the expected worst pause (say 30 s), renewed at a third of that (every 10 s), with renewal failures causing the holder to stop work immediately.

%%state A lease-based lock as seen by the lock service. Expiry frees the lock whether or not the holder knows.
[*] -> Free
Free -> Held : acquire, token 33
Held -> Held : renew before expiry
Held -> Free : holder releases
Held -> *Expired : no renewal within TTL
Expired -> Held : another client acquires, token 34
%%

## The problem leases create
Expiry solves the deadlock problem, but it creates a new one. The lease expires by the **lock service's** sense of time. The holder finds out later, if at all. Nothing stops the holder from continuing to act after its lease has gone. Here is the failure scenario, step by step:
1. Client 1 gets the lock with a 10 s lease, reads a file, and starts modifying it.
2. Client 1 hits a long **stop-the-world** garbage collection pause. Every thread freezes. The lease expires while it is frozen.
3. Client 2 gets the lock, reads the file, writes its changes, and releases.
4. Client 1 wakes up. From its point of view, no time has passed. It still believes it holds the lock, and writes its version of the file, **overwriting client 2's work**.

%%seq The lease problem: client 1 pauses past its lease, client 2 gets the lock and writes, then client 1 writes anyway.
Client 1 > Lock service : acquire (lease 10 s)
Client 1 > Client 1 : GC pause 15 s
Client 2 > Lock service : acquire (lease expired)
Client 2 > Storage : write version B
Client 1 > Storage : write version A, overwrites B
%%

### Why checking does not help
The obvious fix is "check the lease is still valid just before writing". It does not work, because the pause can happen **between** the check and the write. Client 1 checks at t = 9.9 s ("still valid until 10 s"), and then pauses before the write leaves the process. There is always a gap, however small, between checking and acting, and any pause can land in it.

### Pauses are more common than you think
A process can stop for seconds at a time without crashing:
- **Garbage collection**: stop-the-world pauses in JVMs and other runtimes, occasionally many seconds on large heaps.
- **Virtual machine suspension or live migration** by the hypervisor.
- **Page faults and swapping** when memory is under pressure.
- **CPU starvation** on an overloaded host, or a noisy neighbour.
- **Network delays**: a write that leaves the client in time can sit in a queue or be retransmitted. GitHub once saw network packets delayed by about 90 seconds; a write sent while the lease was valid arrived long after it expired.
- **Clock jumps**: if expiry is computed from a wall clock and NTP steps that clock forward, a lease can expire early.

So a lease **guarantees no deadlock** (a crashed holder cannot block everyone forever) but **reintroduces two holders at the same time** whenever a holder is paused or slow. It swaps a liveness problem for a safety problem.

! Example: the double holder, in numbers
! A worker fleet uses a 30 s lease. The JVM's worst observed garbage collection pause is 4 s, and the host occasionally suffers a 40 s VM migration pause, about once a month across the fleet.
! With 2,000 lock acquisitions an hour, most pauses are harmless (4 s is well inside 30 s). But the monthly 40 s pause, if it hits a lock holder mid-task, guarantees a double-holder window of about 10 s: the lease expires at 30 s, another worker takes over, and the first resumes at 40 s still writing.
! A longer lease (60 s) would cover that pause but delays recovery from real crashes by a minute. No lease length removes the risk; it only changes how rare it is. That is why correctness needs a fence.

## Fencing tokens
The fix is to let the **resource** do the check, because only the resource sees the writes actually arriving, in the order they arrive.
1. Each time the lock service grants the lock, it returns a **fencing token**: a number that strictly increases with each grant (33, then 34, then 35).
2. The client includes the token with every write to the protected resource.
3. The resource remembers the **highest token it has processed** and **rejects** any write carrying a lower one.

Replay the scenario: client 1 got token 33 and paused. Client 2 got 34 and wrote; the storage recorded 34. When client 1 wakes and writes with 33, the storage sees 33 < 34 and refuses. Client 1 gets an error and learns it lost the lock.

%%seq Fencing tokens: the storage rejects a write carrying a token older than one it has already accepted.
Client 1 > Lock service : acquire, gets token 33
Client 1 > Client 1 : pause, lease expires
Client 2 > Lock service : acquire, gets token 34
Client 2 > Storage : write with 34, accepted
Client 1 > Storage : write with 33
Storage -> Client 1 : rejected, 33 < 34
%%

Where tokens come from: anything the lock service guarantees to increase. ZooKeeper's **zxid** (transaction ID) or a znode's version; an etcd **revision** (every change to etcd increments a global revision); a database **sequence**; a Raft **term**. Chubby has the same idea under the name **sequencers**: a lock holder gets an opaque sequencer string that it passes to servers, which check it with Chubby (or compare it with the last one seen) before acting.

The resource must cooperate. That is easy for a database (`UPDATE ... WHERE lock_token < 34`) and for storage you build yourself; it is harder for systems you do not control, like a third-party API. For those, idempotency keys or making the operation naturally idempotent is the fallback. Lesson 06.09 looks at fencing again in the context of Redis's Redlock debate.

## Choosing a lock
- **Efficiency only**: a single Redis instance is fine. Acquire with `SET key <random token> NX PX ttl`; release with a short Lua script that deletes the key only if it still holds your token. Document that it can occasionally fail and make sure that failure is harmless.
- **Correctness**: a consensus-backed lock service (ZooKeeper, etcd, Consul) **plus** fencing tokens checked by the resource. The consensus backing ensures the lock service itself does not hand the same lock to two clients when one of its own nodes fails; the fencing handles paused clients.
- **Often simplest of all: skip the external lock.** If the data lives in a database, use the database's own guarantees. `SELECT ... FOR UPDATE` row locks, a unique constraint (only one row per job can be inserted), or a conditional update on a version column (optimistic concurrency). These are already enforced at the resource, so there is no gap between lock and write.

! Example: exclusive file processor
! Workers process uploaded files and write results to a results table. Worker A takes an etcd lease on `file/77` and receives revision 5012 as its token. It stalls for 40 s on a stuck disk; the lease (30 s TTL) expires.
! Worker B acquires the lock and receives revision 5020. Both eventually finish and write results.
! The results table stores the highest token per file and only accepts a write if its token is greater: `UPDATE results SET data = ?, token = 5020 WHERE file_id = 77 AND token < 5020`. B's result is accepted. A's late write, with 5012, matches no rows, so A sees "0 rows updated", logs that it lost the lock, and discards its work.

## Common mistakes
- **Locks without a TTL**, so a crash deadlocks everyone.
- **Releasing without checking ownership.** A client whose lease expired deletes the new holder's lock. Always compare the token before deleting.
- **Trusting "I checked the lease"** as protection against pauses.
- **Using an efficiency lock for correctness**, then losing data during a failover.
- **Lease shorter than common pauses**, causing constant handovers.

## In an interview
When a design needs mutual exclusion, say which kind ("this is a correctness lock"), name the service (etcd or ZooKeeper), give the lease length and renewal interval, and then volunteer the pause problem and the fencing token fix. Better still, ask whether the database's own row locks or conditional writes can do the job without a separate lock.

> Takeaway: a lock must have a lease, or a crashed or partitioned holder blocks everyone forever. But the lease expires on the lock service's clock, so a paused or delayed holder can keep acting after someone else has the lock. Fencing tokens checked by the protected resource close that gap.

?? Without a lease, a client that crashes, hangs or is partitioned while holding the lock would block every other client forever, because the lock service can never be sure it is dead, so the lock must expire unless renewed. The new problem is that expiry is decided by the lock service's sense of time, and a client paused by garbage collection, VM migration or a slow network may not notice its lease has gone: it can keep acting, even after checking the lease, while another client holds the lock, so two holders exist at once and can overwrite each other's work. Fencing tokens, increasing numbers checked by the resource, make that safe.

## Locks on a single Redis
Redis is the most common place teams build a distributed lock, because it is already there, it is fast (a lock round trip is well under a millisecond) and it has the two primitives a lease needs: set-if-absent and expiry. The basic recipe has two halves.

**Acquire**: `SET resource my_random_value NX PX 30000`. `NX` sets the key only if it does not exist, so only one client can succeed. `PX 30000` attaches a 30 second expiry, which is the lease (lesson 06.08). The value is a **random token** unique to this client and this acquisition, for example 20 random bytes. It identifies the owner.

**Release**: delete the key **only if it still holds my token**, atomically, with a short Lua script:

```
if redis.call("get", KEYS[1]) == ARGV[1] then
  return redis.call("del", KEYS[1])
else
  return 0
end
```

Why the check? Suppose client A's lease expired while it was slow, and client B acquired the lock. If A then ran a plain `DEL`, it would delete **B's** lock, and a third client could acquire it while B is still working. The token comparison prevents a client from releasing a lock it no longer owns. The comparison and the delete must be in one script because Redis runs scripts atomically; a separate `GET` then `DEL` could be split by another client's `SET`.

### The replication weakness
A single Redis node is a single point of failure, so production Redis usually has a primary and a replica with automatic failover. That breaks the lock in a specific way, because Redis replication is **asynchronous**:
1. Client A acquires the lock on the primary.
2. The primary crashes before the key is copied to the replica.
3. The replica is promoted to primary. It has no lock key.
4. Client B acquires the same lock on the new primary.

Now A and B both hold the lock. The window is small (milliseconds of replication lag), but at scale, with failovers happening, it will occur.

## Redlock
**Redlock** is an algorithm designed to avoid that single point of failure without relying on replication. It uses **N independent Redis primaries** (typically 5), with no replication between them, ideally on separate machines or zones. To acquire a lock:
1. Read the current time in milliseconds.
2. Try to set the key on each of the N nodes in turn, using the same key and the same random value, with `NX PX ttl`. Use a short per-node timeout (for example 5 to 50 ms for a 10 s TTL), so a dead node does not stall the whole attempt.
3. Compute how long acquisition took. The lock is acquired **only if** a majority of nodes (at least 3 of 5) succeeded **and** the total time spent is less than the TTL.
4. The lock's **validity time** is the TTL minus the time spent acquiring, minus an allowance for clock drift between nodes.
5. If acquisition failed (fewer than a majority, or validity time not positive), release the key on **all** nodes, including those that seemed to fail, then retry after a random delay so competing clients do not keep colliding.

The majority requirement means that if one node crashes and loses its keys, the lock is still held on enough other nodes to stop a second client getting a majority. But a node that restarts **empty** could tip the balance: if A held the lock on nodes 1, 2 and 3, and node 3 restarts without the key, B could get 3, 4 and 5. So crashed nodes should stay down for at least the maximum TTL before rejoining (**delayed restart**), or persist with `fsync` on every write, so a restarted node cannot forget a lock it granted.

%%seq Redlock: acquire the same key with the same token on a majority of 5 independent Redis nodes, quickly enough that time remains on the lease.
Client > Client : t0 = now, ttl = 10 s
Client > Redis 1 : SET k token NX PX 10000 (ok)
Client > Redis 2 : SET k token NX PX 10000 (ok)
Client > Redis 3 : SET k token NX PX 10000 (timeout)
Client > Redis 4 : SET k token NX PX 10000 (ok)
Client > Redis 5 : SET k token NX PX 10000 (taken)
Client > Client : 3 of 5 in 40 ms, validity about 9.9 s
%%

! Example: computing Redlock's validity time
! TTL is 10,000 ms. The client tries 5 nodes with a 50 ms timeout each. Nodes 1, 2 and 4 succeed in 3 ms each; node 3 times out after 50 ms; node 5 refuses because another client holds the key there. Total elapsed: 3 + 3 + 50 + 3 + 3 = 62 ms.
! 3 of 5 is a majority. Validity = 10,000 - 62 - drift allowance. With an allowance of 1% of TTL plus 2 ms (102 ms), validity is about 9,836 ms. The client must finish its work, or extend the lock, within that time.
! If node 3 had taken 9,950 ms to time out instead, validity would be negative and the client would release everything and retry. That is why per-node timeouts must be much smaller than the TTL.

## Why Redlock is unsafe for correctness
Redlock is controversial. The main argument against it, made by distributed systems researchers, goes like this.

### No fencing tokens
Redlock's token is a **random** value, not an increasing number. The protected storage cannot compare two random values and decide which holder is newer, so it cannot reject a stale holder. Lesson 06.08 showed that with any lease-based lock, a paused client can wake up after its lease expired and keep writing. The standard defence is a fencing token checked by the resource, and Redlock does not produce one. Generating a safely increasing token across 5 independent nodes would itself need consensus, which Redlock was designed to avoid.

### Timing assumptions
Redlock's safety depends on **timing**: bounded network delay, bounded process pauses and clocks that run at roughly the right rate. Real systems violate all three occasionally (06.01). The sharpest example is a clock jump:

%%timeline A clock jump on one Redis node lets two clients each believe they hold a majority.
t = 0 s | *Client A acquires on nodes 1, 2, 3 (TTL 10 s)
t = 1 s | Network cuts A off from nodes 4 and 5
t = 2 s | Node 3's clock jumps forward 10 s (NTP step)
t = 2 s | Node 3 thinks A's key expired, deletes it
t = 3 s | *Client B acquires on nodes 3, 4, 5: also a majority
t = 3 s | A and B both believe they hold the lock
%%

Redis stores key expiry as an absolute wall-clock time, so a node whose clock jumped forward could expire a lock early, letting a second client win a majority. A process pause has the same effect without any clock problem: a client gets the majority, pauses in garbage collection past the TTL, and resumes acting while another client holds the lock. Redlock does measure time spent **during** acquisition, but it cannot detect a pause that happens **after** acquisition, between deciding "I hold the lock" and performing the write.

### The conclusion of that argument
Redlock is **too heavy for efficiency locks** (where a single Redis node is enough, and the occasional double run is acceptable) and **not safe enough for correctness locks** (where you need a consensus system such as ZooKeeper or etcd, which also provides increasing tokens, plus fencing at the resource).

## The counter-argument
Redlock's defenders make several points worth knowing:
- If your storage can check fencing tokens, it can already perform atomic compare-and-set, so it is effectively linearizable for that resource and you barely need the external lock. A random unique token, stored and compared with compare-and-set, gives similar protection: write only if the resource's current owner value matches mine.
- A client pausing after acquiring a lock is a problem for **every** auto-expiring lock system, including ZooKeeper and etcd, not just Redlock. Fencing is the answer in all cases.
- Redis should use a **monotonic clock** for expiry (time that only moves forward, unaffected by NTP steps), and operators should configure NTP to **slew** (adjust gradually) rather than step, and avoid manual clock changes.
- Redlock measures elapsed time during acquisition, so delays and pauses **during** acquisition are detected.

Opinions on Redlock still differ. The practical consensus: **Redlock, or a single Redis lock, is fine for avoiding duplicate work. For anything where two holders would corrupt data, put a check at the resource**, and ideally get the lock and its token from a consensus-backed service.

%%matrix Lock options compared. Only consensus plus a check at the resource is safe against paused clients.
Option | Survives a node crash | Increasing token | Safe if client pauses | Good for
Single Redis key | no | no | no | efficiency
Redis primary plus replica | partial, failover can lose it | no | no | efficiency
Redlock on 5 nodes | yes | no | no | efficiency
etcd or ZooKeeper lease | yes | yes | no, alone | correctness with fencing
Any lock plus fenced writes | yes | yes | yes | correctness
%%

## How a fencing token protects storage
The mechanism is simple once you see it:
1. The lock service issues token 33 to client A.
2. A pauses; its lease expires. The service issues token 34 to client B.
3. B writes to storage with token 34. Storage accepts and records 34 as the highest token seen for this resource.
4. A resumes and writes with token 33. Storage sees 33 < 34 and rejects the write.

The storage does the enforcement, so it does not matter that A wrongly believes it still holds the lock. A's beliefs can be as stale as they like; its writes cannot land. In a database, the check is a conditional update:

`UPDATE accounts SET balance = ?, lock_token = 34 WHERE id = 1 AND lock_token < 34`

If A later runs the same statement with 33, the `WHERE` clause matches no row, so "0 rows updated" tells A it lost the lock.

%%seq A fencing token in action: storage keeps the highest token seen and refuses anything older.
Lock service -> Client A : token 33
Client A > Client A : pause, lease expires
Lock service -> Client B : token 34
Client B > Storage : write with 34
Storage -> Client B : ok, highest now 34
Client A > Storage : write with 33
Storage -> Client A : rejected, 33 < 34
%%

Two requirements make it work. Tokens must be **strictly increasing** across grants, which is why they come from a consensus system (an etcd revision, a ZooKeeper zxid). And the check-and-write at the resource must be **atomic**; a separate "read highest token, then write" would reopen the race.

! Example: Redis lock for a report job versus a balance update
! Generating a daily report twice is wasteful but harmless. A single Redis lock is enough: `SET report:2026-11-09 host-7-<random> NX PX 600000`, released with the token-checking script. If a failover lets two hosts run it, two identical reports are written and the second overwrites the first. Nobody is hurt.
! Updating an account balance is not harmless. There the service uses the database row itself: each account has a `version` column, the update is `UPDATE accounts SET balance = 150, version = 8 WHERE id = 1 AND version = 7`, and a writer that sees "0 rows updated" re-reads and retries. No Redis lock is involved at all; the database's atomic conditional update is both lock and fence.

## Common mistakes
- **Plain `DEL` to release**, deleting another client's lock after your lease expired.
- **Using Redlock or Redis for a correctness lock** with no check at the resource.
- **Per-node timeouts close to the TTL**, leaving no validity time.
- **Restarting a Redlock node immediately** with no persistence.
- **Separate read and write** for the fencing check.

## In an interview
If someone proposes "a Redis lock", ask whether it is for efficiency or correctness. For efficiency, agree and mention the token-checked release. For correctness, explain the pause problem and say: "the resource must reject stale holders, so I'd use an etcd lease's revision as a fencing token, or skip the lock and use a conditional write on a version column".

> Takeaway: a single Redis lock, or Redlock across several nodes, is fine for avoiding duplicate work. For correctness a lock alone is never enough, because a paused client can outlive its lease: the protected resource must reject stale holders using increasing fencing tokens or conditional writes.

?? Each lock grant comes with a strictly increasing number (for example an etcd revision or ZooKeeper zxid). The client sends that token with every write, and the storage atomically remembers the highest token it has accepted for the resource and rejects any write carrying a lower one. So if a client's lock expired while it was paused and a newer client has already written with a higher token, the stale client's write is refused (for example a conditional UPDATE ... WHERE lock_token < 34 matches no rows), regardless of what the stale client believes about holding the lock.

## The problem: slow is worse than dead
When a service you depend on **crashes**, calls to it fail fast: the connection is refused in a millisecond, you get an error, and you move on. When it becomes **slow** or hangs, something much worse happens. Every call waits until a timeout. While it waits, the calling thread (or connection, or memory for the request) is tied up doing nothing.

Callers have finite resources. A service with a pool of 200 worker threads, each normally busy for 50 ms per request, can serve 200 / 0.05 = 4,000 requests per second. If one dependency starts taking 10 seconds, every request that touches it holds a thread for 10 seconds, and the pool empties within moments. Now requests that **never needed** the slow dependency also queue, because there are no free threads. The caller is effectively down. Its own callers then see it as slow, and the same thing happens to them.

This chain reaction is a **cascading failure**: one slow component takes down everything upstream of it. It is one of the most common shapes of large outages.

%%timeline How one slow database cascades into a full outage when nothing limits waiting.
0 s | Database latency rises from 5 ms to 5 s
2 s | Service B's 100 threads all wait on the database
4 s | Service A's calls to B now hang too
6 s | *A's thread pool is full; requests that never touch B also stall
10 s | Load balancer health checks on A time out
15 s | *A marked unhealthy everywhere; whole site down
%%

## Timeouts first
Every remote call needs a **timeout** (lesson 02.09). Without one, a hung dependency holds resources forever, and no amount of other cleverness helps. Setting timeouts well is harder than it looks:
- **Base them on measurements.** Set the timeout a little above the dependency's healthy p99 or p99.9 latency. If p99 is 80 ms, a 200 ms timeout is reasonable; a 30 second default is not.
- **Avoid deadlines far above normal latency.** Suppose normal latency is 50 ms and the timeout is 100 s. If 5% of requests start hanging, each one holds a thread for 100 s while healthy requests take 50 ms. Hung requests quickly come to occupy nearly every thread, and most of **all** requests (healthy ones included) end up failing. Latency becomes **bimodal**: either fast, or stuck until the huge deadline.
- **Propagate deadlines.** Pass the remaining time budget down the call chain (gRPC does this with deadlines in request metadata). If the user's request has 300 ms left and service A has used 250 ms, it tells service B "you have 50 ms". B does not start expensive work that can no longer be useful.
- **Cancel** work that is no longer needed. When the caller gives up, the callee should stop too, rather than finishing a query whose answer nobody will read.

! Example: why a 100 s timeout is worse than a 1 s one
! A service has 200 threads and receives 2,000 requests per second. Normal latency is 50 ms, so on average 2,000 × 0.05 = 100 threads are busy.
! A dependency starts hanging 5% of requests. With a 100 s timeout, 100 hanging requests arrive per second and each holds a thread for 100 s. Within about 2 seconds, all 200 threads are stuck. From then on, almost every request, healthy or not, waits for a thread and times out upstream: close to 100% failure from a 5% problem.
! With a 1 s timeout, the 100 hanging requests per second each hold a thread for 1 s, occupying about 100 threads. Healthy requests need another 95 threads. Total 195 of 200: tight, but the service keeps working and only the 5% fail.

Timeouts bound how long each call waits. But a timeout still makes every call to a dead dependency wait for the full timeout, and still sends every request to a service that is already struggling. That is what circuit breakers fix.

## The circuit breaker
A **circuit breaker** wraps calls to one dependency and watches their outcomes. Like an electrical breaker, it **trips** when something is wrong and stops the flow entirely, then allows a careful reset. It has three states.
- **Closed** (normal): calls go through. The breaker counts failures: errors, timeouts, rejections.
- **Open** (tripped): once failures cross a threshold, calls fail **immediately** without contacting the dependency. No waiting, no network traffic.
- **Half-open** (testing): after a **reset timeout** (a cool-down, for example 30 s), the breaker lets a small number of trial calls through. If they succeed, it closes. If they fail, it opens again for another cool-down.

%%state A circuit breaker's three states. While open, calls fail in microseconds instead of waiting for a timeout.
[*] -> Closed
Closed -> Closed : under threshold
Closed -> *Open : failures cross threshold
Open -> Half-open : cool-down elapses
Half-open -> Closed : trial calls succeed
Half-open -> Open : a trial call fails
%%

### Choosing the threshold
Thresholds come in two styles:
- **Consecutive failures**: open after 5 failures in a row. Simple, works for low-traffic calls.
- **Failure rate over a window**: open when at least 50% of calls fail, over a sliding window of the last 20 calls or the last 10 seconds, with a **minimum number of calls** (say 20) before the rate counts. Without the minimum, 1 failure out of 1 call is "100%" and the breaker opens on noise. Libraries such as Resilience4j also support a **slow-call rate**: count calls slower than a threshold as failures even if they eventually succeed, which is what catches a dependency that is slow rather than erroring.

### Practical notes
- **Log every state change and alert when a breaker opens.** An open breaker is a symptom of a real problem.
- **Let operators trip or reset breakers by hand**, for example to cut off a dependency during an incident.
- **Not every error should count.** A 404 "not found" or a 400 "bad request" is a normal answer from a healthy service, not a sign of sickness. Count timeouts, connection errors and 5xx responses.
- **One breaker per dependency** (and sometimes per endpoint or per host), so one sick dependency does not block calls to healthy ones.
- **Run calls on a bounded pool** (a bulkhead, below), so the breaker can also count "pool exhausted" as a failure.

%%seq A breaker opening and later recovering: once open, calls fail instantly; after the cool-down, one trial call decides.
Caller > Breaker : call 1 to 20 (half time out)
Breaker > Breaker : 50% failures, OPEN
Caller > Breaker : call 21
Breaker -> Caller : fail fast in 0.01 ms, use fallback
Breaker > Breaker : 30 s later, HALF-OPEN
Breaker > Dependency : trial call
Dependency -> Breaker : ok in 40 ms
Breaker > Breaker : CLOSED
%%

## Why failing fast is good
It sounds odd to deliberately fail requests that might have succeeded. But compare the alternatives: wait 2 seconds and then fail, or fail in 10 microseconds. Either way the request fails. Failing fast is better for everyone:
- **It protects the caller.** Threads are not stuck waiting, so the caller keeps serving the many requests that do not need the broken dependency. The cascade stops here.
- **It protects the dependency.** A struggling service that keeps receiving full traffic (plus retries) cannot recover; it spends all its capacity on requests that will time out anyway. An open breaker gives it breathing room.
- **It gives clear, immediate errors.** Users and upstream services get an answer they can handle (show cached data, queue the work, show "try again later") instead of a long hang that looks like a broken page.
- **It recovers automatically.** Half-open probes detect when the dependency is healthy again, with no human involved, and they do it with a trickle of traffic rather than a flood.

### What to do when the breaker is open
A breaker returns an error; your code decides what that means. Options, roughly in order of preference:
- **Serve stale or cached data**: last known recommendations, cached prices for display.
- **Degrade the feature**: render the page without the widget.
- **Defer the work**: queue a credit card authorisation for later, accept the order, confirm by email.
- **Fail the operation** clearly, with a useful message.

%%compare A slow dependency with only timeouts versus with a circuit breaker in front of it.
[Timeouts only]
Request -(waits 2 s)-> Sick service -> Timeout error
- Every call pays the full timeout
- Threads pile up in the caller
- Sick service keeps getting hammered
[*Timeout plus breaker]
Request -(breaker open)-> Fallback in 0.01 ms -> Degraded page
+ Caller threads stay free
+ Sick service gets room to recover
+ Probes close the breaker when healthy
%%

## The wider toolkit against cascades
Circuit breakers are one tool among several that work together:
- **Load test** to know your limits. This is the most important step: you cannot set thresholds, pool sizes or timeouts without knowing where things break.
- **Shed load** and **serve degraded results** when overloaded (lesson 02.13). Reject excess work early and cheaply rather than accepting everything and serving nobody.
- **Limit retries.** Use randomised exponential backoff, a per-request retry limit, and a **retry budget** (for example, retries may add at most 10% to traffic). Retry at **one layer only**: if three layers each make up to 4 attempts, one user request can become 4 × 4 × 4 = 64 attempts at the database, exactly when it is least able to cope.
- **Bulkheads**: separate thread pools, connection pools or capacity per dependency or per client, like the watertight compartments of a ship. If the recommendations pool fills, the payments pool is untouched.
- **Beware slow startup and cold caches.** A service that just restarted may be much slower until its caches warm, and can be knocked over again immediately.
- **Beware health checks that kill overloaded servers.** If a health check fails because a server is busy, the orchestrator restarts it, its load moves to the remaining servers, which then fail their health checks too. Health checks should test liveness, not whether the server is momentarily slow.

%%bars Worst-case attempts reaching the bottom service for one user request when every layer retries. Retrying at one layer keeps it bounded.
Retry at one layer, 3 tries | 3 | 3 attempts
Two layers, 3 tries each | 9 | 9 attempts
Three layers, 3 tries each | 27 | 27 attempts
*Three layers, 4 tries each | 64 | 64 attempts
%%

! Example: recommendations widget
! The product page calls a recommendations service with a 150 ms timeout, through a breaker that opens at 50% errors over at least 20 calls and retries after 30 s, on its own bulkhead pool of 30 threads.
! The recommendations service slows to 2 s per call. Without the breaker, every page render waits the full 150 ms timeout for the widget, and at 3,000 page views per second the 30-thread pool is constantly full, so many renders wait even longer for a thread.
! With the breaker, after about 20 failed calls (well under a second at this traffic) it opens. Pages render immediately with cached bestsellers in place of personalised picks. Every 30 s a single probe checks whether recommendations are back; when one succeeds, the breaker closes and personalised widgets return. Users barely notice.

## Common mistakes
- **No timeout**, or a library default of 30 to 60 seconds.
- **Counting client errors** (404, 400) as failures, so a healthy service trips the breaker.
- **One breaker for everything**, so one bad dependency blocks calls to all of them.
- **Retrying inside an open breaker's fallback**, which defeats it.
- **Retries at every layer**, multiplying load during an incident.
- **No fallback**: the breaker opens and the page shows a raw error.

## In an interview
When your design calls another service, say: "every call has a timeout based on its p99, a circuit breaker per dependency, retries with backoff at one layer and a retry budget, and a fallback". Then explain the one line that matters most: the breaker makes failures fast so threads stay free and the sick dependency can recover.

> Takeaway: timeouts bound how long you wait; a circuit breaker stops calling a failing dependency at all. By failing fast it keeps the caller's threads free, gives the dependency room to recover, lets callers fall back to degraded responses, and probes automatically for recovery, which stops one slow service from cascading into an outage.

?? Once failures (errors, timeouts or slow calls) cross a threshold, the breaker opens and rejects calls immediately, in microseconds, instead of letting every call wait for a timeout. That is good because the request would fail anyway: failing fast frees the caller's threads and connections so it keeps serving everything that does not need the broken dependency, stopping a cascading failure; it gives the struggling dependency room to recover instead of being hammered by requests and retries; it gives users and upstream services an immediate error they can handle with a fallback such as cached or degraded data; and half-open trial calls close the breaker automatically once the dependency is healthy.

## Why gossip
Large clusters need every node to know two kinds of things: **who else is alive** (membership and failure detection), and **shared state** that changes over time (which node owns which data, configuration, schema versions, load). The question is how to spread that knowledge to hundreds or thousands of nodes cheaply and reliably.

The obvious approaches do not scale:
- **Everyone heartbeats everyone.** With N nodes that is N × (N - 1) messages per interval. For 1,000 nodes sending a heartbeat every second, that is about a million messages a second, just to say "I'm alive". Cost grows as O(N²).
- **A central server** collects heartbeats and broadcasts changes. Now that server is a hot spot and a single point of failure, and its view of who is alive is only as good as its own network links.
- **Broadcast trees** (a node tells its children, who tell theirs) are efficient but fragile: one failed interior node cuts off a whole subtree.

**Gossip protocols** (also called **epidemic protocols**) spread information the way rumours or diseases spread through a population. Each node periodically picks a few other nodes **at random** and exchanges what it knows with them. Nobody is in charge, no node is special, and no single failure stops the spread.

## How gossip spreads information
The basic loop on every node, once per **round** (a fixed interval, for example every 1 second or every 200 ms):
1. Pick **k** random peers (the **fanout**, typically 1 to 4).
2. Send them your recent updates (or a summary of your state).
3. Merge whatever you receive, keeping the newest version of each item.

There are three styles of exchange:
- **Push**: informed nodes send updates to random peers. Fast at the start, when few nodes know and almost every push reaches someone new. Slow at the end, because most pushes land on nodes that already know.
- **Pull**: every node asks random peers "what's new?". Slow at the start, fast at the end: the last few uninformed nodes are very likely to ask someone who knows.
- **Push-pull**: both at once. Combines the fast start and the fast finish, and is what most systems use.

Delivery to every node is not strictly guaranteed. But the probability that some node is missed shrinks very quickly with each extra round, so with suitable settings, full coverage is extremely likely. And the protocol tolerates lost messages and crashed nodes naturally: if one exchange fails, the information arrives by another path a round later.

### How fast: O(log N) rounds
In each round, every informed node tells a few more. So the number of informed nodes roughly **multiplies** each round, until most of the cluster knows. Starting from 1 node with a fanout of 2 (each informed node tells 2 others), the informed count goes roughly 1, 3, 9, 27, 81, and so on: multiplying by 3 each round. Reaching N nodes takes about log base 3 of N rounds, plus a few extra rounds to catch the stragglers as pushes start landing on nodes that already know.

In general the information reaches all N nodes in about **O(log N)** rounds. With 1,000 nodes, that is on the order of 10 rounds; with 1,000,000 nodes, around 20. Meanwhile each node sends only a **constant** number of messages per round (k), however big the cluster is. So total traffic grows as O(N) and time grows as O(log N). That combination is why gossip scales.

%%timeline A rumour spreading through 1,000 nodes with fanout 2. Growth is roughly threefold per round until most nodes know, then a short tail catches the rest.
Round 0 | 1 node knows
Round 1 | about 3 know
Round 2 | about 9 know
Round 4 | about 80 know
Round 6 | *about 550 know; many pushes now hit informed nodes
Round 8 | about 990 know
Round 10 | all 1,000 know, with very high probability

## SWIM: gossip-based membership
**SWIM** (Scalable Weakly-consistent Infection-style process group Membership) is the most influential gossip-based membership protocol. HashiCorp's Serf and Consul use it with modifications, as do many other systems. Its key idea is to **separate two jobs** that naive designs mix together.

### Job 1: failure detection
Each **protocol period** (length T, say 1 second), every node does this:
1. Pick one peer and send it a **ping**.
2. If an **ack** comes back in time, the peer is alive. Done.
3. If not, ask **k** other random nodes (say 3) to ping the target on your behalf: a **ping-req**. They ping it and forward any ack.
4. If no ack arrives by the end of the period, by any route, the target is **suspected**.

The indirect ping is the clever part. A missing ack might mean the target is dead, or just that the link between **you and it** is bad. If 3 other nodes, on different network paths, also cannot reach it, the target is much more likely to be dead. This cuts false alarms caused by one bad link.

%%seq SWIM failure detection: a direct ping, then indirect pings through other members before suspecting the target.
Node A > Node C : ping
Node A > Node A : no ack within timeout
Node A > Node B : ping-req C
Node B > Node C : ping
Node C -> Node B : ack
Node B -> Node A : ack (C is alive)
%%

### Job 2: dissemination
Membership updates ("D joined", "E left", "F suspected", "F confirmed dead") need to reach everyone. Instead of sending separate messages, SWIM **piggybacks** them on the ping, ping-req and ack messages that are flowing anyway. Each update is attached to a node's next several messages, then dropped. Because every node pings a random peer each period, updates spread like gossip, in a number of periods that grows logarithmically with group size. No extra messages are needed.

### Refinements that matter
- **Suspicion before death.** A node that fails its probes is first marked **suspect**, and that is gossiped. If the node is actually alive, it hears the rumour about itself and **refutes** it by gossiping an "alive" message with a higher **incarnation number** (a counter only that node may increase). Only if no refutation arrives within a suspicion timeout is it declared **dead**. This sharply cuts false positives from nodes that were merely slow for a moment.
- **Round-robin probing.** Instead of choosing a fully random peer each time, each node probes members in a shuffled order and reshuffles each pass. Every member is then probed within a bounded time, rather than possibly being skipped by bad luck.

%%state How a SWIM member sees a peer. Suspicion gives a slow node time to refute before it is declared dead.
[*] -> Alive
Alive -> Suspect : direct and indirect pings fail
Suspect -> Alive : refutes with higher incarnation
Suspect -> *Dead : suspicion timeout passes
Dead -> Alive : rejoins with new incarnation
%%

The results: each member sends and receives about **2 messages per period** regardless of group size (a constant load), and the expected time to first detect a failure does **not** grow with group size. In tests with 10% packet loss, the suspicion mechanism kept far more members correctly in the group than the basic version without it.

## Where gossip is used
- **Cassandra and ScyllaDB**: every second, each node gossips with up to three others about cluster state: which nodes are up, their token ranges (which data they own), schema versions and load. Each piece of state carries a version so newer information always wins.
- **Consul and Serf**: membership and failure detection on SWIM, with practical changes. They add a periodic **full state sync over TCP** between random pairs (faster convergence, and recovery after a partition heals); a **dedicated gossip layer** besides piggybacking, so gossip can run often (every 200 ms) while failure probes run slower (every second); and they keep dead nodes' state for a while so full syncs include it.
- **Lifeguard** extensions (from HashiCorp) tackle false positives caused by the **detecting** node being unhealthy. If a node is overloaded, it sends and processes messages late and wrongly suspects others. Lifeguard adds **nack** messages to indirect probes, so a node that keeps missing nacks realises **it** may be the degraded one and slows its own failure detector. It also starts the suspicion timeout long and shortens it as other nodes independently confirm the suspicion.
- **Redis Cluster**: nodes gossip slot ownership and failure reports over a cluster bus; a primary is marked failed when a majority of primaries report it.
- **Anti-entropy** between replicas (lesson 06.03) is gossip-like too: random pairs compare Merkle trees and repair differences.

! Example: a 1,000-node cluster learns of a failure
! Node 417 crashes at t = 0. Probing order means some node probes 417 within about one protocol period: say node 52 at t = 0.6 s. No ack. Node 52 sends ping-req to 3 random members; none get an ack. At t = 1 s, node 52 marks 417 **suspect** and piggybacks that on its next messages.
! Each period, every node that knows tells the nodes it pings. After about log2(1,000) ≈ 10 periods of 1 s, essentially the whole cluster has heard "417 suspect".
! Node 417 does not refute within the suspicion timeout (say 5 s, though implementations scale it with log N), so at about t = 6 s it is declared dead, and that is gossiped too. Its token ranges are taken over by their replicas. Had 417 merely been paused for 3 s, it would have woken, heard the rumour and refuted it with incarnation + 1, staying in the cluster.

## Trade-offs
- **Eventually consistent.** Different nodes have slightly different views for a few rounds. One node may think 417 is alive while another already marked it suspect.
- **Not for decisions that need agreement.** Who is the leader, which write committed, who holds a lock: these need consensus (06.06). Gossip is for spreading information where a few seconds of disagreement is harmless.
- **Message size.** If each round sends the whole state, messages grow with cluster size. Systems gossip **digests** (version summaries) and pull the full details only for items that differ.
- **Tuning.** Faster rounds mean faster spread and more bandwidth. Shorter suspicion timeouts mean faster detection and more false positives.

## Common mistakes
- **Using gossip for leader election** or anything that must have one agreed answer.
- **Suspicion timeouts that ignore cluster size**, causing false deaths in large clusters.
- **Ignoring the detecting node's own health**, so one overloaded node accuses everyone.
- **Gossiping full state** every round in large clusters.

## In an interview
If your design has hundreds of nodes that must know about each other, say "membership and failure detection via a SWIM-style gossip protocol, so per-node load is constant and news reaches everyone in about log N rounds", and keep the authoritative decisions in a small consensus group.

> Takeaway: gossip spreads information by having each node exchange state with a few random peers each round, reaching all N nodes in about O(log N) rounds with constant work per node and no single point of failure. SWIM uses it for scalable failure detection, with indirect pings and suspicion to keep false positives low.

## The problem
Every distributed system carries a small set of **shared facts** that all its parts must agree on:
- **Membership**: which nodes are currently in the cluster.
- **Leadership**: who is leader of each shard or each job.
- **Placement**: which shard (range of keys) lives on which node. This is often called the **shard map** or routing table.
- **Configuration**: feature flags, limits, timeouts, the current schema version.
- **Discovery**: where each running instance of each service can be reached (IP and port).

These facts are **metadata**: data about the system, not the users' data. They are small (kilobytes to a few megabytes), they change rarely (seconds to hours between changes), and they are read constantly. But they must be **correct**, because disagreement is dangerous. If two storage nodes each believe they own shard 7, both accept writes for it and the data diverges. If half the routers think node N4 is alive and half think it is dead, requests go to a node that is no longer serving. A wrong shard map can be worse than no shard map.

So metadata lives in a special kind of store: a **coordination service** backed by consensus.

## Coordination services: ZooKeeper
ZooKeeper is the classic example, built specifically to hold this kind of data.

### The data model
Data is a tree of **znodes**, addressed by paths like a file system: `/services/payments/instance-3`. Each znode holds a small amount of data (the limit is about 1 MB, but typical values are bytes to kilobytes) and has a **version number** that increases on every change. Three special features make it a coordination tool rather than just a small database:
- **Ephemeral znodes** exist only as long as the **session** of the client that created them. The client keeps the session alive with heartbeats. If the client crashes or loses its connection for longer than the session timeout (often 2 to 30 s), the session expires and all its ephemeral znodes vanish. This makes membership automatic: a node is "in the cluster" exactly as long as it is alive and connected.
- **Watches** notify a client when a znode or its children change, so clients do not have to poll. A watch fires once; the client re-reads and sets a new watch.
- **Sequential znodes** get a monotonically increasing counter appended to their name by the server (`lock-0000000017`). This gives a total order to anything that creates them, which is the building block for locks, queues and elections.

%%tree A typical ZooKeeper tree for one cluster. Ephemeral nodes vanish when their owner's session dies; sequential nodes get increasing suffixes.
/
  /config
    payments | timeouts, flags; services watch this
  /services
    /api
      *i-7 | ephemeral: 10.0.3.7:8080
      i-9 | ephemeral: 10.0.4.2:8080
  /election
    n_0000000017 | ephemeral sequential: current leader
    n_0000000018 | watches n_17
  /shards
    7 | owner N2, version 41
%%

### How it runs
ZooKeeper runs as an **ensemble** of servers, usually 3 or 5. Writes go through a leader and are committed once a majority has them, using ZooKeeper's **ZAB** protocol (similar to Raft, lesson 06.06). Every committed change gets a **zxid**, a transaction ID that increases across the whole ensemble.

Reads are served by whichever server the client is connected to, straight out of RAM, which makes them fast but possibly slightly behind the leader. A client that needs the very latest value calls `sync` first, which makes its server catch up with the leader. ZooKeeper stays available while a majority is up, keeps all data in memory (with a write-ahead log and snapshots on disk), and performs best for read-heavy workloads, around 10 reads per write or more.

Its guarantees:
- **Sequential consistency**: updates from one client are applied in the order sent.
- **Atomicity**: an update either fully succeeds or fully fails.
- **Single system image**: a client sees the same view whichever server it connects to, and never goes backwards in time even if it reconnects to another server.
- **Durability**: once applied, an update persists until overwritten.
- **Timeliness**: a client's view is up to date within a bounded time.

### Classic recipes
A handful of patterns built from these primitives cover most uses.
- **Leader election**: each candidate creates an ephemeral sequential node under `/election`. The one with the lowest number is leader. Each other candidate watches **only the node just before it**, not the leader. When the leader dies, its node vanishes and only the next candidate is notified; it checks that it is now the lowest and takes over. Watching the leader directly would wake every candidate at once (a herd effect) for no reason.
- **Locks**: the same pattern under `/locks/resource`. The zxid or the node's version doubles as a **fencing token** (lesson 06.08).
- **Service discovery**: each instance registers an ephemeral node under `/services/name`; clients list the directory and watch it.
- **Configuration**: a znode holds the config; every service watches it and reloads on change.

%%seq ZooKeeper leader election: each candidate watches only its predecessor, so a leader's death wakes exactly one node.
Node A > ZooKeeper : create /election/n_ (ephemeral sequential)
ZooKeeper -> Node A : n_17, lowest, so A leads
Node B > ZooKeeper : create, gets n_18, watch n_17
Node C > ZooKeeper : create, gets n_19, watch n_18
Node A > Node A : crashes, session expires
ZooKeeper -> Node B : watch fired: n_17 deleted
Node B > Node B : n_18 now lowest, become leader
%%

### Alternatives
- **etcd**: a key-value store with Raft consensus, a flat key space with prefixes rather than a tree, **leases** instead of sessions, watches over key ranges, and a global **revision** number on every change. It is the store behind Kubernetes, which keeps every object (pods, services, deployments) in it.
- **Consul**: Raft for its strongly consistent catalogue and key-value store, plus SWIM gossip (lesson 06.11) for membership and failure detection among potentially thousands of agents. It adds built-in health checks and DNS-based discovery.

## Service registries
In a microservice system, instances change constantly: autoscaling adds and removes them, containers get new IP addresses on every restart, deployments replace them. Hard-coding addresses is impossible, so a **service registry** keeps a database of services and their live instances.

How instances get in:
- **Self-registration**: each instance registers itself on startup, sends heartbeats (or answers health checks) while running, and deregisters on clean shutdown. If it crashes, missed heartbeats remove it.
- **Third-party registration**: the platform registers instances on their behalf. Kubernetes does this implicitly: the control plane tracks which pods are ready and updates the endpoints for each service.

How clients find them:
- **Client-side discovery**: the client queries the registry (and caches the result), then picks an instance itself, applying its own load balancing. Netflix Eureka with its client libraries works this way.
- **Server-side discovery**: the client calls a fixed address (a load balancer or router), which queries the registry and forwards the request. Kubernetes Services and cloud load balancers work this way.

%%compare Client-side versus server-side discovery. Both read the same registry; they differ in who picks the instance.
[Client-side]
Client -(query registry)-> Instance list -(client picks)-> Instance
+ No extra hop
+ Client can balance smartly
- Discovery logic in every client
- Every language needs a library
[*Server-side]
Client -> Load balancer -(queries registry)-> Instance
+ Clients stay simple
+ One place to change routing
- Extra hop and component
%%

Examples of registries: Netflix Eureka, ZooKeeper, Consul, etcd and Kubernetes' own endpoints. The drawbacks: the registry is another critical component that must be highly available, and clients cache its data, which goes stale if it fails. Eureka deliberately chose availability: when many instances stop heartbeating at once (which looks more like a network problem than mass death), it enters a **self-preservation** mode and stops expiring them, preferring a slightly stale list to an empty one.

## Why not a normal database?
You could store the shard map in a PostgreSQL table. Here is why you usually should not.

| Need | Consensus-backed store | Typical database |
| No conflicting answers through failover | Yes: every change is on a majority before it is visible | Async replica promoted on failover can lose or reorder recent changes |
| Membership tied to liveness | Yes: sessions, ephemeral nodes, leases | No: needs your own heartbeat and cleanup job |
| Change notification | Yes: watches | Polling, or a separate change stream |
| Increasing ID per change | Yes: zxid, etcd revision | Possible with a sequence, but not tied to failover safety |
| Survives a minority of servers failing | Yes, automatically | Depends on failover setup, often minutes |

- **Strong consistency under failure.** A consensus-backed store replicates each change to a majority before acknowledging it, so it never shows two nodes conflicting answers about the leader or a shard's owner, even across failovers. A single database is a single point of failure; a replicated one with asynchronous replicas can lose acknowledged updates or show them out of order when a replica is promoted (lesson 06.03).
- **Sessions and ephemeral data.** Membership is tied to liveness automatically. With a normal table you need heartbeat columns, a reaper job and careful clock handling.
- **Watches.** Change notifications reach every interested client within milliseconds, instead of polling every few seconds.
- **Ordering and fencing.** Every change gets a monotonically increasing ID (zxid, etcd revision), usable directly as a fencing token.

The trade-off: these stores are small (all data in memory, typically a few gigabytes at most; etcd's default limit is 2 GB) and relatively slow for writes (each write is a consensus round, often thousands per second rather than hundreds of thousands). So they hold **metadata, never application data**. Putting user records in ZooKeeper is a classic mistake.

! Example: shard map for a key-value store
! A storage cluster keeps its shard-to-node map in etcd under `/shards/{id}`. Each storage node holds a 10 s lease and registers under `/nodes/{name}`. A controller watches `/nodes`.
! Node N4 crashes at t = 0. Its lease expires at about t = 10 s, and etcd deletes `/nodes/N4`. The controller's watch fires. In one etcd transaction it reassigns N4's 40 shards to their replicas and bumps each shard's revision.
! Routers watch `/shards` and update their routing tables within milliseconds. Requests are stamped with the shard-map revision the router used; storage nodes reject requests carrying an older revision than they know, so a router with a stale view gets an error and refreshes rather than writing to the wrong owner.

! Example: why polling a database falls short
! The same cluster uses a PostgreSQL table for the shard map, with 500 routers polling every 2 s: 250 queries per second just to check for changes, and changes take up to 2 s to be noticed.
! Worse, during a database failover to an async replica, the last shard reassignment (written 50 ms before the crash) is lost. Half the routers already read it and route shard 12 to N7; the new database says N2. Both nodes accept writes for shard 12 until someone notices. With etcd, the reassignment would either be committed on a majority (and survive) or not acknowledged at all.

## Common mistakes
- **Storing application data** in the coordination service.
- **Treating ZooKeeper reads as linearizable** without `sync`.
- **Watching the leader node** in an election recipe, causing a herd on every failover.
- **Ignoring session expiry** in clients, so a client continues acting as leader after its ephemeral node has gone.
- **Clients that cannot survive a registry outage.** Cache the last known list and keep using it.

## The problem DHTs solve
A **distributed hash table (DHT)** stores key-value pairs across many nodes, and lets any node find the value for any key, with **no central directory** and **no node knowing all the others**. It offers the same two operations as an ordinary hash table, `put(key, value)` and `get(key)`, but the table is spread over thousands or millions of machines.

DHTs were designed for **peer-to-peer** networks: file sharing, decentralised storage, blockchain node discovery. Three properties of those environments shape the design:
- **Huge membership.** Millions of nodes. No single node can hold a list of all of them, let alone keep it current.
- **Churn.** Nodes join and leave constantly; a typical peer might stay online for minutes or hours.
- **No trust and no centre.** There is no company running a directory server, and any central server would be a single point of failure (and of legal or political attack).

Consistent hashing (lesson 04.07) already answers **who owns a key**: hash nodes and keys onto the same ring, and a key belongs to the next node along. What a DHT adds is **routing**: how do you reach that owner when you only know a few dozen other nodes? The answer in every major DHT is the same trick: keep a small routing table that is **dense near yourself and sparse far away**, so that every hop at least halves the remaining distance, and a lookup takes **O(log N)** hops.

## Chord
Chord is the simplest DHT to understand. It supports exactly one operation: given a key, return the node responsible for it. Storing values on top of that is easy once you can find the right node.

### The ring
- Every node and every key gets an **m-bit identifier** by hashing (for example SHA-1 of the node's IP address, or of the key). With m = 160, there are 2^160 positions, arranged in a circle from 0 to 2^m - 1.
- A key belongs to its **successor**: the first node whose ID is equal to or follows the key's ID going clockwise.

### Why a successor pointer is not enough
If each node only knew its successor, a lookup could follow successors around the ring until it reached the owner. That is correct, but with N nodes it takes up to N hops, about N/2 on average. With a million nodes that is half a million network round trips: useless.

### The finger table
Each node n keeps a **finger table** of up to m entries. The i-th finger points to the successor of the position **n + 2^(i-1)**. So node n knows the nodes roughly 1, 2, 4, 8, 16, 32 and so on positions ahead of it, up to half the ring away. It knows its close neighbourhood in detail and the far side of the ring only coarsely, much like you know your own street well and only the major cities of other countries.

To look up key k, node n finds the finger that gets **closest to k without passing it**, and forwards the query there. That node does the same with its own fingers. Because the fingers double in distance, each hop at least halves the remaining distance to the target. Halving a distance of up to 2^m takes at most m steps, but with N nodes spread over the ring, only about log2 N hops matter. So a lookup takes **O(log N)** hops, and each node stores only **O(log N)** distinct routing entries.

  +1: successor of 9 | node 10
  +2: successor of 10 | node 10
  +4: successor of 12 | node 14
  +8: successor of 16 | node 21
  +16: successor of 24 | node 32
  *+32: successor of 40 | node 42
%%

! Node 42's fingers point to the successors of 43, 44, 46, 50, 58 and 10. The closest one before 54 is the successor of 50, say node 51. Remaining distance: 3.

### How many hops in practice
On average a lookup takes about **½ log2 N** hops, because the first hop typically covers half the distance and the remaining distance is random. For a million nodes, log2 of a million is about 20, so a typical lookup is about **10 hops**. If each hop is a 50 ms internet round trip, that is roughly half a second, which is why DHTs suit peer-to-peer systems better than latency-sensitive datacenter services.

### Churn
When a node joins, it takes over some keys from its successor; when it leaves, its keys go to its successor. Either way only about **1/N of keys** move. Fixing everyone's routing tables after a join or leave takes **O(log² N)** messages. Nodes run a periodic **stabilisation** protocol: each node asks its successor "who is your predecessor?", fixes its successor pointer if a new node has slipped in between, and notifies the successor about itself. Fingers are refreshed periodically too. Correctness only needs successor pointers to be right; fingers just make it fast, so stale fingers slow lookups down but do not break them.

### Failures
Each node keeps a **successor list** of several (say r = log N) successors, not just one. If the first is dead, it uses the next. With such lists, lookups still succeed with high probability even if half the nodes fail at once. Values are also **replicated** on the first few successors of their key, so data survives the owner's failure.

## Kademlia
Kademlia is the most widely deployed DHT. It uses the same "halve the distance each hop" idea with a different, cleverer distance function.

### XOR distance
The distance between two IDs is their **bitwise XOR**, read as an integer. For example d(1011, 1001) = 0010 = 2. XOR distance has useful properties:
- It is **symmetric**: d(a, b) = d(b, a). (Chord's clockwise distance is not, so Chord nodes cannot learn useful routing information from queries they receive. Kademlia nodes can.)
- d(a, a) = 0, and for any point and any distance there is exactly one other point at that distance.
- It respects shared prefixes: two IDs that share a long common prefix are close. The **position of the first differing bit** decides the rough distance.

### k-buckets
Each node keeps one **bucket** per bit position of the ID: bucket i holds contacts whose distance from the node is between 2^i and 2^(i+1), which means they share exactly the first (m - i - 1) bits with the node. Each bucket holds up to **k** contacts (typically k = 20). Half of all IDs fall in the farthest bucket, a quarter in the next, and so on, but each bucket holds at most k. So a node knows many nodes near itself and a few far away: the same dense-near, sparse-far shape as Chord's fingers.

%%tree Kademlia k-buckets for a node with ID 0000 (4-bit IDs). Each bucket covers a range of XOR distance twice as wide as the last and keeps at most k contacts.
Node 0000
  Bucket 3: IDs 1xxx | half the space, keep 20
  Bucket 2: IDs 01xx | a quarter, keep 20
  Bucket 1: IDs 001x | an eighth
  *Bucket 0: ID 0001 | nearest neighbour
%%

### Lookup
Lookups are **iterative**: the node doing the lookup stays in control rather than forwarding the query.
1. Pick the **α** closest contacts to the target from your own buckets (α is typically 3).
2. Send them **FIND_NODE** (or FIND_VALUE) in parallel. Each replies with the k closest contacts **it** knows.
3. Add those to your candidate list and query the α closest ones you have not asked yet.
4. Stop when a round produces no contacts closer than the closest you already have. The k closest nodes found are where the key lives.

Each round roughly halves the distance, giving O(log N) rounds. Querying α nodes in parallel means one slow or dead node does not stall the lookup.

### Preferring long-lived nodes
When a node learns of a new contact for a bucket that is already full, it **pings the oldest contact** in that bucket. If the oldest answers, it is kept and the newcomer is dropped. Measurements of peer-to-peer networks show that the longer a node has been online, the more likely it is to stay online for another hour, so old contacts are the better bet. This policy also resists some attacks: flooding the network with new fake nodes cannot push out established contacts.

### The protocol
Kademlia has just four RPCs: **PING** (are you alive?), **STORE** (keep this key-value pair), **FIND_NODE** (give me the k closest nodes to this ID), and **FIND_VALUE** (like FIND_NODE, but return the value if you have it). Values are stored on the k nodes closest to the key and republished periodically so they survive churn.

Kademlia is used by **BitTorrent's Mainline DHT** (which lets torrents work without a central tracker, with millions of concurrent nodes), **IPFS**, and **Ethereum's** node discovery protocol.

## The general idea
Both designs give each node a routing table that is **dense near itself and sparse far away**, with entries spaced exponentially. Every hop jumps to a node at least about twice as close to the target. So **log N hops suffice without anyone knowing the full membership**, each node stores only O(log N) contacts, and the failure of any node affects only its own small neighbourhood. Other DHTs (Pastry, Tapestry, CAN) differ in geometry but follow the same principle.

## DHTs in datacenter design
Inside a datacenter, the trade-offs flip. A cluster has hundreds or thousands of nodes, not millions; nodes are trusted and long-lived; and every millisecond of latency matters. Every node (or client) can simply hold the **whole ring**: a few thousand entries is a tiny amount of memory. So datacenter systems use **one-hop** designs: Dynamo and Cassandra gossip the full ring membership to all nodes (lesson 06.11), and a client or coordinator routes a request directly to a replica of the key in a single hop. Redis Cluster clients cache the full slot map for the same reason (05.02).

! Example: when to choose which
! A storage service with 300 nodes in two datacenters, latency budget 10 ms: the full ring is 300 entries, a few kilobytes. One-hop routing via gossiped membership costs nothing and avoids 4 to 5 extra hops that a DHT would need (about 1 ms each inside a datacenter, too much for the budget).
! A peer-to-peer file sharing network with 5 million nodes, half of which change every few hours: keeping a full ring on every node would mean gossiping millions of changes per hour to millions of nodes. A Kademlia DHT keeps about 20 × 23 ≈ 460 contacts per node and finds any key in roughly 11 or 12 hops (half of log2 of 5 million, about 22). Half a second per lookup is fine for starting a download.

## Common mistakes
- **Proposing a multi-hop DHT inside a datacenter**, where every node can know the full ring.
- **Assuming O(log N) means fast.** Ten internet round trips is hundreds of milliseconds.
- **Forgetting replication.** A key stored on one node disappears when that peer goes offline.
- **Confusing consistent hashing with a DHT.** Consistent hashing decides ownership; the DHT's routing tables decide how to reach the owner.

## In an interview
If asked how a node finds a key without a directory, describe the finger table or k-buckets in one sentence, then the halving argument for O(log N). Then add the practical note: in a datacenter-sized cluster you would just gossip the full ring and route in one hop.

> Takeaway: a DHT finds the owner of a key without a central directory by giving each node routing pointers spaced exponentially around the ID space (Chord's fingers, Kademlia's k-buckets). Each hop at least halves the distance to the key, so lookups take O(log N) hops while each node knows only O(log N) others. Inside a datacenter, a full membership view and one-hop routing are usually better.
